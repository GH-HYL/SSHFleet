对 `HEAD` 与用户提供的固定点之间的 diff 做双轴复查：

- **标准（Standards）**：代码是否符合本仓库成文的编码标准？
- **规格（Spec）**：代码是否忠实实现了源头的 issue／规格？

两个轴都作为**并行子 agent** 运行，以免彼此污染上下文，然后本技能汇总它们的发现。

问题追踪器（issue tracker）应该已经提供给你了。如果没有，告诉用户去跑 `/setup-matt-pocock-skills`。

## 流程

### 1. 钉住固定点

用户说的是什么，固定点就是什么（一个提交 SHA、分支名、标签、`main`、`HEAD~5` 等等）。如果他们没有指定，就问。

一次性记下那条 diff 命令：`git diff <fixed-point>...HEAD`（三点，这样比较是针对 merge-base 的）。同时用 `git log <fixed-point>..HEAD --oneline` 记下提交列表。

在往下走之前，先确认固定点能解析（`git rev-parse <fixed-point>`）且 diff 非空。一个坏的 ref 或空的 diff 应该在这里失败，而不是在两个并行子 agent 内部失败。

### 2. 找出规格来源

按这个顺序找源头的规格：

1. 提交消息里的 issue 引用（`#123`、`Closes #45`、GitLab 的 `!67` 等），通过追踪器文档里的工作流取回。
2. 用户作为参数传进来的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能相匹配的规格文件。
4. 如果什么都没找到，就问用户规格在哪里。如果他们说没有，**规格**子 agent 就跳过，并报告「no spec available」。

### 3. 找出标准来源

在仓库里搜出每一个记录了代码应当如何书写的文件。当 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md` 存在时，它必须在清单上。

无论仓库成文了什么，标准轴永远额外带着下面这份**坏味道基线（smell baseline）**：一组固定的 Fowler 代码坏味道（《重构》第 3 章），即使仓库什么都没写也照样适用。有两条规则约束它：

- **仓库优先。** 仓库里成文的标准永远获胜；当它认可某种基线会标记的做法时，把这个坏味道压掉。
- **永远是判断题。** 每个坏味道都是一条带标签的启发式（「疑似 Feature Envy」），绝不是硬性违规。和这里任何标准一样，工具链已经强制的东西就跳过。

每条坏味道的读法是*它是什么* → *怎么修*；拿它去比照 diff：

- **神秘命名（Mysterious Name）**：函数、变量或类型的名字不能揭示它做什么或存什么。→ 改名；如果找不到诚实的名字，那说明设计本身是浑浊的。
- **重复代码（Duplicated Code）**：同一段逻辑形状在本次改动的多个 hunk 或文件里出现。→ 把共有的形状抽出来，两处都调它。
- **依恋情结（Feature Envy）**：某个方法伸手去够另一个对象的数据，比够自己的还多。→ 把这个方法搬到它所依恋的数据上。
- **数据泥团（Data Clumps）**：同样的那几个字段或参数总是结伴同行（一个想被生出来的类型）。→ 把它们捆成一个类型，传那个类型。
- **基本类型偏执（Primitive Obsession）**：用一个基本类型或字符串顶替一个值得拥有自己类型的领域概念。→ 给这个概念一个它自己的小类型。
- **重复的 switch（Repeated Switches）**：针对同一类型的同一个 `switch`／`if` 级联在本次改动中反复出现。→ 换成多态，或者两处共用一张映射表。
- **霰弹式修改（Shotgun Surgery）**：一次逻辑上的改动迫使 diff 中许多文件散落地被编辑。→ 把一起变的东西收拢进一个模块。
- **发散式变化（Divergent Change）**：一个文件或模块因为几个不相关的原因被编辑。→ 拆开，让每个模块只因一个原因而变化。
- **夸夸其谈通用性（Speculative Generality）**：为规格并不存在的需求添加的抽象、参数或钩子。→ 删掉它；内联回去，直到真实需求出现。
- **过长的消息链（Message Chains）**：调用方不该依赖的长串 `a.b().c().d()` 导航。→ 把这段行走藏到第一个对象上的单个方法里。
- **中间人（Middle Man）**：一个类或函数基本上只是往下转发。→ 砍掉它，直接调真正的目标。
- **被拒绝的遗赠（Refused Bequest）**：子类或实现者忽略或覆写了它继承来的大部分东西。→ 放弃继承，改用组合。

### 4. 并行启动两个子 agent

把两个子 agent 调用一起发出去，用前台方式，然后汇总它们返回的报告。

**标准子 agent 的提示词**应包含：

- 完整的 diff 命令和提交列表。
- 你在第 3 步找到的标准来源文件清单，**外加第 3 步那份坏味道基线**的全文粘贴（子 agent 没有别的途径拿到它）。
- 任务简报：「按文件／hunk 在相关处报告：(a) diff 违反某条成文标准的每一处：引用该标准（文件 + 规则）；以及 (b) 你发现的任何基线坏味道：说出它的名字并引用那个 hunk。区分硬性违规和判断题：成文标准的违反可以是硬性的，但基线坏味道永远是判断题，且仓库中成文的标准优先于基线。工具链强制的东西跳过。400 字以内。」

**规格子 agent 的提示词**应包含：

- diff 命令和提交列表。
- 规格的路径或取回的内容。
- 任务简报：「报告：(a) 规格要求但缺失或只做了一半的需求；(b) diff 中没被要求的行为（范围蔓延）；(c) 看起来实现了、但实现方式看着不对的需求。每条发现都引用规格中的那一行。400 字以内。」

如果规格缺失，就跳过规格子 agent，并在最终报告里注明这一点。

### 5. 汇总

把两份报告分别放在 `## Standards` 和 `## Spec` 标题下呈现，原文照录或轻度清洗。**不要**合并或重排这些发现，因为两个轴是刻意分开的（见*为什么分两个轴*）。

最后用一句话总结：每个轴的发现总数，以及*每个轴内部*最严重的问题（如果有）。不要跨轴选出一个总冠军：那正是这种分离所要防止的重排。

## 为什么分两个轴

一次改动可以通过一个轴而在另一个轴上失败：

- 遵循了每一条标准，但实现的是错的东西 → **标准通过，规格失败。**
- 完全按 issue 要求做了，但破坏了项目的约定 → **规格通过，标准失败。**

分开报告可以防止一个轴掩盖另一个轴。
