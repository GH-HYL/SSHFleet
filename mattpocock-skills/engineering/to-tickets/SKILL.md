# to-tickets（To Tickets）

把一份计划、规格或对话拆成一组**工单（ticket）**：曳光弹式的垂直切片，每个都声明**阻塞（block）**它的那些工单。

问题追踪器与分诊标签词表本应已经提供给你。如果没有，告诉用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

从对话上下文中已有的内容出发。如果用户以参数形式传了一个引用（规格路径、issue 编号或 URL），就去取回它，并读取其完整正文与评论。

### 2. 探查代码库（可选）

如果你还没探查过代码库，就探查一遍以了解代码的当前状态。工单标题与描述应使用项目的领域词表词汇，并遵守你正在触及区域的 ADR。

寻找预先重构（prefactor）代码的机会，让实现更轻松。「先让改动变得容易，再做容易的改动。」

### 3. 起草垂直切片

把工作拆成**曳光弹（tracer bullet）**工单。

<vertical-slice-rules>

- 每个切片都贯穿每一层（schema、API、UI、测试）切出一条狭窄但完整的路径：是垂直的，而不是某一层的水平切片
- 一个完成的切片本身即可演示或验证
- 每个切片的规模要能放进一个全新的上下文窗口
- 任何预先重构都应最先完成

</vertical-slice-rules>

给每个工单写上它的**阻塞边（blocking edge）**：在它开始之前必须完成的其他工单。没有阻塞者的工单可以立即开始。

**大范围重构是垂直切分的例外。** **大范围重构（wide refactor）** 是一次机械性改动（重命名一列、改变共享符号的类型），其**影响半径（blast radius）** 铺满整个代码库，于是一次编辑就同时打断成千上万个调用点，任何垂直切片都无法落绿。不要硬把它塞进一发曳光弹；把它安排成**扩张–收缩（expand–contract）**。先扩张：在旧形式旁边加上新形式，让什么都不坏。再按影响半径分批迁移调用点（按包、按目录），每一批自成一个工单，被扩张这一步阻塞，并且因为旧形式还在，批次之间 CI 一直保持绿色。最后收缩：在没有调用方残留之后删除旧形式，这个工单被每一个迁移批次阻塞。当连各批次本身都无法单独保持绿色时，保留这个次序，但让它们共用一个集成分支，而所有分支共同阻塞一个最终的集成并验证工单；只有在那一处才承诺绿色。

### 4. 拷问用户

把提议的拆分以编号列表呈现。对每个工单展示：

- **标题（Title）**：简短的描述性名称
- **被谁阻塞（Blocked by）**：哪些其他工单（如果有）必须先完成
- **它交付什么（What it delivers）**：这个工单让什么端到端行为变得可用

问用户：

- 粒度感觉对吗？（太粗 / 太细）
- 阻塞边是否正确：每个工单是否只依赖真正卡住它的工单？
- 是否有工单该合并或进一步拆分？

反复迭代直到用户认可这个拆分。

### 5. 把工单发布到已配置的追踪器

发布已认可的工单。**如何**发取决于 `/setup-matt-pocock-skills` 配置的追踪器；不管哪种方式工单本身都一样，只有阻塞边的形态不同：

- **本地文件** → 每个工单在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下写一个文件，按依赖顺序（阻塞者在前）从 `01` 编号。每个文件的「Blocked by」列出它依赖的编号/标题。使用下面的 per-ticket 文件模板：一个文件一个工单，绝不合并成单个文件。
- **真实的问​题追踪器（GitHub、Linear……）** → 按依赖顺序（阻塞者在前）每个工单发布一个 issue，好让每个工单的阻塞边能引用真实标识符。平台有原生阻塞关系就用它；否则把每个工单的「Blocked by」设为那些阻塞性 issue。如果来源是一个已有 issue，就把每个工单做成它的子 issue（见追踪器文档中的操作）。除非另有指示，应用 `ready-for-agent` 分诊标签；这些工单按构造就是 agent 可抓取的。

沿**前沿（frontier）**推进：任何阻塞者都已完成的工作单。对于纯线性链条，就是从上到下。

不要关闭或修改任何父 issue。
