# Design It Twice（设计两遍）

当用户想为某个选中的深化候选者探索备选接口时，使用这个并行子 agent 的模式。基于 "Design It Twice"（Ousterhout）：你的第一个想法多半不是最好的那个。

使用 [SKILL.md](SKILL.md) 中的词汇：**模块（module）**、**接口（interface）**、**接缝（seam）**、**适配器（adapter）**、**杠杆（leverage）**。

## 流程

### 1. 框定问题空间

在拉起子 agent 之前，为选中的候选者写一份面向用户的问题空间说明：

- 任何新接口都需要满足的约束
- 它会依赖的东西，以及它们属于哪一类别（见 [DEEPENING.md](DEEPENING.md)）
- 一段粗略示意性的代码草图，用来给约束打地基——不是提案，只是让约束变得具体的一种方式

给用户看这份说明，然后立刻进入第 2 步。用户一边读一边想，子 agent 在另一边并行干活。

### 2. 拉起子 agent

并行拉起 3 个以上子 agent。每一个都必须为深化后的模块产出一个**截然不同**的接口。

给每个子 agent 一份独立的技术简报（文件路径、耦合细节、来自 [DEEPENING.md](DEEPENING.md) 的依赖类别、接缝背后放着什么）。这份简报独立于第 1 步那份面向用户的问题空间说明。给每个 agent 一个不同的设计约束：

- Agent 1：「最小化接口：最多瞄准 1–3 个入口点。让每个入口点的杠杆最大化。」
- Agent 2：「最大化灵活性：支持多种用例和扩展。」
- Agent 3：「为最常见的调用方优化：让默认情形变得微不足道。」
- Agent 4（如适用）：「围绕端口与适配器设计，以处理跨接缝的依赖。」

简报里要同时带上 [SKILL.md](SKILL.md) 的词汇和 GLOSSARY.md 的词汇，好让每个子 agent 的命名都与架构语言和项目的领域语言保持一致。

每个子 agent 产出：

1. 接口（类型、方法、参数，外加不变量、顺序、错误模式）
2. 用法示例，展示调用方如何使用它
3. 实现在接缝背后藏了什么
4. 依赖策略与适配器（见 [DEEPENING.md](DEEPENING.md)）
5. 权衡取舍：杠杆在哪里高，在哪里薄

### 3. 呈现并比较

依次呈现各个设计，让用户能逐个吸收，然后用散文式的文字做比较。从**深度（depth）**（接口处的杠杆）、**局部性（locality）**（改动集中在哪里）和**接缝位置（seam placement）**三个方面作对照。

比较之后，给出你自己的推荐：你认为哪个设计最强，以及为什么。如果不同设计中的元素能很好地结合，就提出一个混合方案。要有主见：用户想要的是一个有力的判断，不是一份菜单。
