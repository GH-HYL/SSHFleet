# Deepening（深化）

在给定依赖的前提下，如何安全地深化一簇浅模块。假定你已掌握 [SKILL.md](SKILL.md) 中的词汇：**模块（module）**、**接口（interface）**、**接缝（seam）**、**适配器（adapter）**。

## 依赖分类

评估一个深化候选者时，先给它的依赖分类。类别决定了深化后的模块如何跨接缝被测试。

### 1. 进程内（In-process）

纯计算、内存状态、没有 I/O。永远可深化：把这些模块合并，直接通过新接口测试。不需要适配器。

### 2. 可用本地替身（Local-substitutable）

有本地测试替身的依赖（用 PGLite 代替 Postgres、内存文件系统）。只要替身存在就可深化。深化后的模块在测试套件里带着这个替身运行来测试。接缝是内部的；模块的外部接口上没有端口（port）。

### 3. 远程但自有（端口与适配器 / Ports & Adapters）

你自己跨网络边界的服务（微服务、内部 API）。在接缝处定义一个**端口（port）**（接口）。深模块拥有逻辑；传输方式作为**适配器**注入。测试用内存适配器。生产用 HTTP/gRPC/队列适配器。

建议的说法形态：*「在接缝处定义一个端口，为生产实现一个 HTTP 适配器、为测试实现一个内存适配器，这样逻辑就待在一个深模块里，即使它跨网络部署。」*

### 4. 真正的外部（模拟 / Mock）

你不掌控的第三方服务（Stripe、Twilio 等）。深化后的模块把这个外部依赖作为注入的端口接收；测试提供一个模拟适配器（mock adapter）。

## 接缝纪律

- **一个适配器意味着假想的接缝。两个适配器才意味着真实的接缝。** 除非至少有两个适配器站得住脚（通常是生产 + 测试），否则不要引入端口。只有一个适配器的接缝不过是间接层。
- **内部接缝与外部接缝。** 一个深模块既可以有内部接缝（对其实现私有，供它自己的测试使用），也可以有位于其接口处的外部接缝。不要仅仅因为测试用到，就把内部接缝通过接口暴露出去。

## 测试策略：替换，不要分层

- 一旦深化后模块接口处的测试存在，浅模块上的旧单元测试就成了废物；删掉它们。
- 在深化后模块的接口处写新测试。**接口就是测试面（test surface）**。
- 测试断言的是穿过接口可观察到的结果，不是内部状态。
- 测试应当能在内部重构中存活，因为它们描述的是行为，不是实现。如果实现一变测试就得改，那它就是在绕过接口做测试。
