# tdd（Test-Driven Development）

TDD 就是红 → 绿这个循环。本技能是让这个循环产出值得保留的测试的参考：什么是好测试、测试放在哪里、反模式（anti-pattern），以及循环的规则。每一节在每一次循环中都适用：在循环之前和之中查阅它们，而不是之后。

探查代码库时，读一读 `GLOSSARY.md`（如果存在），好让测试名和接口（interface）词汇与项目的领域语言一致，并遵守你正在触及区域的 ADR。

## 什么是好测试

测试通过公开接口（public interface）验证行为，而不是验证实现细节。代码可以整个换掉，测试不该因此改变。好测试读起来像一份规格（specification）：「用户可以用有效的购物车结账」准确告诉你存在什么能力，而且它在重构（refactor）后依然成立，因为它不关心内部结构。

示例见 [tests.md](tests.md)，模拟（mocking）指南见 [mocking.md](mocking.md)。

## 接缝（Seam）：测试放在哪里

**接缝（seam）** 是你用来测试的公开边界：你在这个接口上观察行为，而不伸进内部。测试住在接缝处，绝不针对内部实现。

**只在事先商定的接缝上测试。** 在写任何测试之前，先写下被测的接缝，并与用户确认。没有确认过的接缝上不写测试。你不可能测试所有东西，所以事先商定接缝，正是让测试精力落在关键路径和复杂逻辑上、而不是每个边界情况上的办法。

问：「公开接口是什么，我们该测哪些接缝？」对每个提议的接缝，用一行说明它能抓到什么、漏掉什么。

当这个接口本身的形状都存疑时（模块有多深、接缝该在哪里、接口该暴露什么），调用 Skill 工具加载 "codebase-design" 以获取词汇。它是模块、接口、深度、接缝、适配器、杠杆与局部性这些术语的共同出处，是一份用来查阅的参考，不是一场要跑的会话。

## 反模式

- **与实现耦合（Implementation-coupled）**：模拟内部协作者、测试私有方法，或通过旁路渠道验证（比如查数据库而不走接口）。破绽：重构时测试就挂了，但行为并没有变。
- **同义反复（Tautological）**：断言用与代码相同的方式重算期望值（`expect(add(a, b)).toBe(a + b)`、手工以同样方式导出的快照、把常量断言为等于它自己），于是它按构造就是通过的，永远不可能与代码不一致。期望值必须来自独立的事实来源：一个已知正确的字面量、一个演算过的例子、规格。
- **水平切分（Horizontal slicing）**：先写完所有测试，再写所有实现。批量测试验证的是_想象中_的行为：你测的是事物的_形状_而非面向用户的行为，测试对真实改动变得不敏感，而且你在理解实现之前就锁定了测试结构。改用**垂直切片（vertical slice）**：一个测试 → 一个实现 → 重复，每个测试都是一发**曳光弹（tracer bullet）**，回应上一轮循环教给你的东西。

## 循环的规则

- **先红后绿。** 先写失败的测试，再只写刚好能通过它的代码。不要预判未来的测试，也不要添加投机性功能。
- **一次一个切片。** 每轮循环：一个接缝、一个测试、一个最小实现。
- **重构不属于这个循环。** 它属于复查阶段（见 `code-review` 技能），而不是红 → 绿的实现循环。
