用户要求做一次**复盘（retrospective）**。你要提出的是对编码 agent **环境**的改进建议，以改善未来的运行。

## 步骤

1. 调用 Skill 工具并传入 `writing-for-agents`，取写作风格指南。

2. 阅读用户指定那次会话的一手来源。这可能意味着在本机翻查会话日志。如果用户没指定会话，就默认当前这一次。

3. 在以下几类里寻找可改进的候选。

- **导航（Navigation）**：agent 找对文件有多容易？文件之间有没有隐藏依赖？加一个**导航指针（navigation pointer）**会不会更容易？_适用场景_：这次会话花了很长时间才找到某条信息。
- **自动化检查（Automated checks）**：有没有能抓住 agent 所犯错误的自动化检查？lint、类型检查、测试、文件系统 linter？先读仓库自己的检查命令（它的 `package.json`／构建工具里的 `lint`／`check` 脚本、它的 CI workflow），这样「已经存在但没接上、或悄悄坏掉的检查」才算发现，而不是重新发明一遍。一个没有**护栏（guardrail）**（既没有 pre-commit hook，也没有跑其 lint／typecheck／test 命令的 CI job）的仓库本身就是一项发现：没做 lint 的仓库是一处长期错失的机会，而不是中性的默认状态。_适用场景_：agent 犯了某个自动化检查本可抓住的错误，或者仓库根本没有护栏。
- **编码规范（Coding standards）**：该不该给**复查 agent（reviewer agent）**一条新规则去执行？现有规则该删还是该讲清？先把违规归类：**机械性**的违规（固定的语法模式、被禁的 API、某种 import 形状、文件位置规则）就该配一个确定性检查，没有例外：仓库自己 linter 里的自定义规则、一个新的 pre-commit hook，或者一个新的 CI job，哪个在仓库的语言和现有护栏下最便宜就用哪个。默认是去建检查，而不是写规则。把 `CODING_STANDARDS.md` 留给真正的**判断题（judgement calls）**（跨文件一致性、「跟周边风格一致」，以及任何护栏永远替代不了的东西）。_适用场景_：复查 agent 没能抓住某个错误。
- **全局 AGENTS.md**：有没有哪些引导指令该被挪到编码规范（或自动化检查）里去？_适用场景_：AGENTS.md 文件特别大——无论是在仓库里，还是在用户的全局作用域里。
- **工具开销（Tool economy）**：agent 有没有做出本可精简的昂贵工具调用？有没有什么自定义工具链（CLI、MCP）特别费 token？_适用场景_：agent 做了一次昂贵的工具调用。
- **空操作（No-ops）**：找出引导文件里那些并不改变 agent 行为的指令。_适用场景_：引导文件又大又难用。
- **信息获取（Information access）**：寻找提升 agent 信息获取能力的机会。把 dev server 日志分流出来、给第三方服务只读访问。_适用场景_：有一条关键信息 agent 拿不到。

4. 按严重程度排序，把这些候选呈现给用户。

## 参考

### 实现与复查

记住，所有工作都经过两个阶段：实现与复查。实现 agent 承受最大的**上下文压力（context pressure）**。它负责探索、写代码、调试失败。

复查 agent 的上下文压力最小——它拿到的是一个 diff，所以不需要探索。它通常也不需要写代码或调试。

这意味着，施加编码规范应该是复查 agent 的职责，而不是实现 agent 的。

### 文件

你可以访问仓库里的若干文件：

- `CLAUDE.md`／`AGENTS.md`：这些文件会被推进任何在本仓库工作的 agent 的上下文窗口。它们应当极其克制地使用，通常只用来放指向其他文件的**导航指针**。
- `CODING_STANDARDS.md`：这个文件在复查时读，不在实现时读。如果规范文件超过 1,000 行，就给 docs 目录加**导航指针**。
- Docs：把 docs 当作参考文件用，由其他文件指过来。写新文档之前先找找有没有现成的。
- Skills：用技能来承载文档（因为它们的 description 会进入 agent 的上下文窗口），或者承载用户调用的命令。遵循 `writing-for-agents` 技能里的建议。
