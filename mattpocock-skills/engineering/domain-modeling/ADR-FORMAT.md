# ADR 格式

ADR 存放在 `docs/adr/`，使用顺序编号：`0001-slug.md`、`0002-slug.md`，依此类推。

懒创建 `docs/adr/` 目录：只在需要第一个 ADR 时创建。

## 模板

```md
# {Short title of the decision}

{1-3 sentences: what's the context, what did we decide, and why.}
```

就这样。一篇 ADR 可以只有一段话。它的价值在于记录*有过*某个决策以及*为什么*，而不在于把各节填满。

## 可选章节

只有在确实增加价值时才包含这些。多数 ADR 不需要它们。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：当决策会被重新审视时有用
- **Considered Options**：只有当被否决的备选方案值得记住时才写
- **Consequences**：只有当存在不显然的下游影响需要点明时才写

## 编号

扫描 `docs/adr/`，找到现有的最大编号，加一。

## 何时提议写一篇 ADR

以下三条必须全部成立：

1. **难以回退**：以后改主意的代价是实在的
2. **脱离上下文会让人意外**：未来的读者会看着代码疑惑“他们到底为什么这么做？”
3. **是真实取舍的结果**：确实存在其他选项，而你是出于具体理由选了这一个

如果一个决策容易回退，就跳过它：你直接回退就是了。如果它并不让人意外，没人会疑惑为什么。如果并不存在真实的备选方案，那就没什么可记录的，除了一句“我们做了显而易见的事”。

### 什么算数

- **架构形态。**“我们用的是 monorepo。”“写模型是事件溯源的，读模型投影进 Postgres。”
- **上下文之间的集成模式。**“Ordering 与 Billing 通过领域事件通信，而不是同步 HTTP。”
- **带锁定的技术选择。**数据库、消息总线、认证提供方、部署目标。不是每个库：只是那些换掉要花一个季度的。
- **边界与范围决策。**“Customer 数据由 Customer 上下文拥有；其他上下文只按 ID 引用它。”明确的“不做”和“做”一样有价值。
- **对显而易见路径的刻意偏离。**“我们用手写 SQL 而不是 ORM，因为 X。”任何合理的读者会假设成相反做法的地方。这些能阻止下一位工程师去“修复”一个本来就是刻意如此的东西。
- **代码里看不见的约束。**“因为合规要求，我们不能用 AWS。”“因为合作方 API 合约，响应时间必须低于 200ms。”
- **否决理由不显然的被否决方案。**如果你考虑过 GraphQL，出于微妙的理由选了 REST，就记下来；否则半年后会有人再次提议 GraphQL。
