# triage（Triage）

让项目问题追踪器上的 issue 走完一台小型的状态机，经历各个分诊角色（triage role）。

如果本仓库把外部拉取请求当作请求入口（见 issue-tracker 配置），分诊也覆盖它们：**一个 PR 就是附带代码的 issue**，使用相同的角色、相同的状态、相同的状态机，只是下文标了「for a PR」的几处差异。按追踪器配置，把光秃秃的 `#42` 解析成 issue 或 PR。

分诊期间发布到问题追踪器的每条评论或 issue，都**必须**以此声明开头：

```
> *This was generated by AI during triage.*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何写出经久耐用的 agent 简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知识库如何运作

## 角色

两个**类别（category）**角色：

- `bug`：有东西坏了
- `enhancement`：新功能或改进

五个**状态（state）**角色：

- `needs-triage`：维护者需要评估
- `needs-info`：等待报告者提供更多信息
- `ready-for-agent`：已完整写明规格，可交给 AFK agent
- `ready-for-human`：需要由人来实现
- `wontfix`：不会处理

对于 PR，同样的状态是就所附代码而言的：`ready-for-agent` 意味着已附上简报，agent 应对该 diff 采取下一步；`ready-for-human` 意味着可以交给人合并了。

每个已分诊的 issue 都应恰好带一个类别角色和一个状态角色。如果状态角色互相冲突，先标出来并询问维护者，再做任何其他事。

这些是标准角色名。问题追踪器中实际使用的标签字符串可能不同。映射本应已经提供给你。如果没有，告诉用户运行 `/setup-matt-pocock-skills`。

状态转移：未打标签的 issue 通常先进入 `needs-triage`；从那里它可以转到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后，`needs-info` 回到 `needs-triage`。维护者随时可以覆盖。把看起来不寻常的转移标出来，先问再继续。

## 调用

维护者调用 `/triage` 并用自然语言描述他们想要什么。解读这个请求并行动。例如：

- 「给我看看有什么需要我处理的」
- 「我们看看 #42」（issue 或 PR）
- 「把 #42 移到 ready-for-agent」
- 「有什么是 agent 可以接手做的？」

## 展示需要关注的内容

查询问题追踪器，呈现三个桶，最旧的在前：

1. **未打标签（Unlabeled）**：从未分诊过。
2. **`needs-triage`**：评估进行中。
3. **自上次分诊记录以来报告者有活动的 `needs-info`**：需要重新评估。

当 PR 在范围内时，把外部 PR 也放进这些桶里，并给每一行打上 `[PR]` 或 `[issue]` 标记。发现环节只浮现*外部* PR（追踪器配置定义了谁算外部），所以协作者正在进行的 PR 不算分诊工作。这个过滤只用于发现；被明确点名的 PR 无论作者是谁都要分诊。

展示数量以及每项一行摘要。让维护者来挑选。

## 分诊某个具体的 issue 或 PR

1. **收集上下文。** 读完整的 issue 或 PR（正文、评论、标签、作者、日期；若是 PR，还要读 diff）。解析此前的分诊记录，以免重复问已经解决的问题。使用项目的领域词表探查代码库，遵守该区域的 ADR。对代码库跑两项检查：(a) **冗余（redundancy）**：按领域概念（而不只是请求的措辞）搜索所请求行为是否已有实现，并报告你查过哪里。若已找到，它就是一个「已实现」的 `wontfix`（第 5 步）。(b) **先前已否决（prior rejection）**：读取 `.out-of-scope/*.md`，把任何与本次请求相似的文件浮出来。

2. **给建议。** 把你的类别与状态建议连同理由告诉维护者，再加一段与该请求相关的简要代码库概述（包括它是否已实现）。等待指示。

3. **验证说法。** 在任何拷问之前，先检查这个说法站不站得住。对于 bug，按报告者的步骤复现它。对于 PR，确认 diff 确实做了它声称的事：把它检出，跑相关测试或命令。报告结果：已确认（连同代码路径）、失败，或细节不足（一个强烈的 `needs-info` 信号）。经过确认的验证能造就强得多的 agent 简报。

4. **拷问（如需）。** 如果这个请求需要充实，就调用 Skill 工具两次，加载 "grilling" 和 "domain-modeling"，一轮问题一轮问题地把它拷问成形，打磨领域术语，并在决策落定时就地更新 `GLOSSARY.md`/ADR。

5. **落实结果：**
   - `ready-for-agent`：发一条 agent 简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：结构与 agent 简报相同，但要说明为什么它无法被委派（需要判断、需要外部访问、需要设计决策、需要人工测试）。
   - `needs-info`：发分诊记录（模板见下）。
   - 对于 `wontfix`，关闭该 issue，评论内容取决于*为什么*：
     - **已实现（Already implemented）**：改动已经在代码库里了。指出它在哪；**不要**写入 `.out-of-scope/`（那个知识库是给*被否决*的请求用的，不是给已构建的）。
     - **已否决（bug）**：给出礼貌的解释，然后关闭。
     - **已否决（enhancement）**：写入 `.out-of-scope/`，在评论里链到它，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：应用该角色。若有部分进展，可选地加一条评论。

## 快速状态覆盖

如果维护者说「把 #42 移到 ready-for-agent」，相信他们，直接应用该角色。确认你即将做的事（角色变更、评论、关闭），然后行动。跳过拷问。如果在没有拷问会话的情况下直接移到 `ready-for-agent`，问他们是否要写一份 agent 简报。

## needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

把拷问期间确定下来的一切都记在「established so far」下，免得工作丢失。问题必须具体且可执行，不能是「请提供更多信息」。

## 恢复此前的会话

如果 issue 或 PR 上已存在此前的分诊记录，读它们，检查报告者是否已回答了任何悬而未决的问题，并在继续之前呈现一幅更新后的图景。不要重问已解决的问题。
