# wizard（Wizard）

**向导（wizard）** 是一个 bash 脚本，它一步步引导人走完一套手工流程：这套流程手动做很繁琐，每次重新解释给 AI 也很繁琐。它打开每一个 URL，明说要点击和复制什么，捕获那些值，把它们写到该去的地方（`.env`、GitHub secrets），在每个阶段都确认，并显示还剩多少阶段。它可能配置第三方服务、跑一次性迁移，或把项目从一个状态搬到另一个状态。

令人愉快的 UX 已经由 [template.sh](template.sh) 解决了：逐阶段进度、确认门、跨平台打开 URL（包括 WSL）、隐藏式密钥输入、幂等的 `.env` 更新插入、`gh secret`/`gh variable` 写入，以及收尾摘要。**你的工作只是界定流程范围并撰写它的各个阶段。** `STAGES` 标记之上的那部分库在每个向导里都一模一样；这种一致性正是重点：绝不要手工编辑它。

向导默认是一次性的：为一次运行而构建，保存到临时目录或 `scripts/` 路径，事后删掉。只有当用户想要一条应当留在仓库里的可重复安装路径时才提交它。

## 流程

### 1. 界定流程范围

弄清人必须采取的每一个手工步骤，以及一路上被捕获的每一个值。先读仓库，不要凭空就问：

- 对于配置类：`.env`、`.env.example`、`.env.*`、`README`、`docker-compose*`、框架配置，以及 `.github/workflows/*`（每一处 `secrets.*` / `vars.*` 引用都是向导必须产出的一个值）。
- 对于迁移或过渡：当前状态、目标状态，以及两者之间不可逆的动作。

然后把有序的阶段列表以及每个阶段产出的值给用户看，并确认：他们可以增加、删除或调换顺序。

**完成条件：**每个阶段都按顺序命名了，并且对每个被捕获的值，你都知道 (a) 人从哪里拿到它，(b) 它写到哪里（`.env`、一个 GitHub secret、两者都要，还是哪里都不写；有些阶段是纯动作），以及 (c) 它是密钥（隐藏输入）还是公开的。

### 2. 勾画每个阶段的旅程

对每个阶段，写出人要走的那条精确路径：打开哪个 URL、在那里做什么、值显示在哪里、它填进哪个变量：例如「Dashboard → Developers → API keys → Reveal test key → copy」。在你并不真正了解当前 UI 或确切命令的地方，就说明这一点，并去问用户或查文档：绝不要凭空编造可能不存在的步骤。

**完成条件：**每个阶段都能追溯到具体指令，一个陌生人也能照着做。

### 3. 撰写向导

把 `template.sh` 复制到目标路径。把示例阶段替换成每一步一个 `stage`，按依赖顺序排列。使用库里的辅助函数：`stage`、`say`/`step`、`open_url`、`ask`/`ask_secret`、`write_env`、`set_secret`/`set_var`、`pause`/`confirm`。把 `TOTAL_STAGES` 设为你写下的阶段数。

守住模板设定的标准：在索取某个值之前先打开它的 URL，任何密钥都用 `ask_secret`，每个被持久化的值都用 `write_env`，只有 CI 真正需要的值才用 `set_secret`，任何不可逆动作之前都 `confirm`。每个 `stage` 都清屏，所以只看得见当前这一步：让每个阶段只做一件专注的事，这样人需要的东西不会滚出屏幕。不要动标记之上的那部分库。

### 4. 验证并交接

- `bash -n <script>`；如果有 `shellcheck` 就跑一下。
- `chmod +x <script>`。
- 不要自己端到端跑它：它会打开浏览器，并且在人的输入上阻塞。改为静态地追踪它：第 1 步里的每个值都被捕获并落在第 1 步所说的地方，而且每个 `set_secret` 名字都与 CI 中某一处 `secrets.*` 引用完全一致。
- 告诉用户怎么运行它。如果它是一条可重复的安装路径，就提交它，并从 README 链接过去，好让下一个人跑脚本，而不是去问 AI。
