# 逻辑原型（Logic Prototype）

一个自包含的单一 HTML 文件（一份**可分享的演示**），让任何人都能靠点按钮来驱动一个状态模型。当问题关乎**业务逻辑、状态转移或数据形状**时用它：就是那种在纸上看着挺合理，真推进真实用例里才觉得不对的东西。

因为就一个文件、什么都不用装，你可以直接把它丢给非开发者（设计师、PM、领域专家），让他们亲身感受这个模型。所以它说的是他们的语言，不是代码的语言。

## 什么时候该用这种形态

- 「我不确定这个状态机能不能处理先 X 后 Y 的那个边界情况。」
- 「这个数据模型到底能不能表达……那种情况？」
- 「我想在动手写之前先摸清这个 API 该长什么样。」
- 任何有人想**按按钮、看状态变化**的场景。

如果问题是「这东西该长什么样」，那就走错分支了。用 [UI.md](UI.md)。

## 过程

### 1. 把问题写清楚

在写代码之前，先写下你正在做原型的是哪个状态模型、哪个问题。一段话，放在演示的顶部（放在看得见的引言里，而不只是注释）。一个回答错问题的逻辑原型纯属浪费，所以把问题显式写出来，以便日后核对——无论用户是当下盯着看，还是离开一阵再回来看。

### 2. 把逻辑隔离进一个可移植的模块

把真正的逻辑（回答问题的那个部分）放进单个 `<script>` 块里，写成一个小的纯模块，日后能原样拎出来、放进真实代码库。它周围的那个页面是用完即弃的；这个模块不是。

合适的形态取决于问题：

- **一个纯 reducer**：`(state, action) => state`。适合动作是离散事件、状态是单个值的情况。
- **一个状态机**：显式的状态和转移。适合「此刻到底哪些动作是合法的」本身就是问题一部分的情况。
- **一组作用在普通数据类型上的纯函数**。适合没有隐含的当前状态、只有转换的情况。
- **一个拥有清晰方法面的类或模块**，当逻辑确实持有持续的内部状态时。

挑最贴合所问问题的形态，*而不是*最容易接到页面上的形态。保持纯净：没有 DOM，没有 `document`，没有伸手进去的按钮处理函数。页面调用它；没有任何东西反向流动。这正是让原型在自身生命周期结束后仍有价值的原因：一旦问题有了答案，那个已验证的 reducer／状态机／函数组就能自己升格进真实模块。

### 3. 构建可分享的 HTML 文件

一个文件，纯 HTML/CSS/JS：不用框架，不用打包器，不用服务器，全部内联，这样双击就能打开、邮件转发也还能用。任何人都应该能靠打开它来运行它。

按非开发者的口味来写。每个标签都用**领域语言**，不是代码语言：按钮和状态读起来像业务，而不像 reducer。用大白话解释正在发生什么。

用清爽的层级自上而下排布：

1. **标题和一行说明**，讲清这个演示让你探索什么（即第 1 步里的问题）。
2. **当前状态**：完整的相关状态，渲染成一个可读的面板（带标签的字段，而不是原始的 JSON 转储），每次点击后重新渲染，让变化看得见。在有助于非开发者跟上的地方，点出刚刚变了什么。
3. **自由操作按钮**：每个动作一个按钮，始终可用，让任何人都能任意顺序地戳弄这个模型。每次点击派发它对应的动作并重新渲染状态。
4. **引导式走查**：一组**场景**，每个标签页一个。每个标签页里有一段关于该场景的简短白话描述（它铺陈的情境，以及要留意什么），下面则列出该场景中按顺序要**按的按钮**。每一步都是真实的按钮：点它就执行那个动作并前进到下一步。启动一个走查会重置到已知的初始状态，这样这个场景每次跑起来都一样。

挑选能展示那些别扭用例的场景——那些在纸上难以想清楚的：正常路径、一个棘手的边界情况、一次本应非法的尝试。

保持美观但克制：干净的排版、充裕的间距、一种强调色。不要动画，不要花招：任何会跟状态和按钮抢戏的东西都不要。

### 4. 交付出去

把文件发给他们，或者替他们打开。他们什么时候得空就什么时候点走查和自由操作；有意思的时刻是他们说出「等等，这不该可能啊」或者「咦，我以为 X 会不一样」的时候；那些就是_想法_里的 bug，而这正是全部意义所在。如果他们想要新动作或新场景，加上去。原型是会演化的。

### 5. 留存答案和原型

一旦原型回答了它的问题，先留存答案，再按 [SKILL](SKILL.md) 描述的方式留存原型。逻辑分支特有的映射关系是：已验证的 reducer／状态机／函数组升格进真实模块（决策，被吸收）；HTML 外壳则随行到那个把原型作为一手来源保存的一次性分支上，而由于它是一个自包含文件，在那儿重跑依然轻而易举。

## 反模式

- **不要加测试。** 一个需要测试的原型就不再是原型了。
- **不要把它接到真实数据库上。** 除非问题专门关于持久化，否则就用内存状态。
- **不要泛化。** 别搞「要是以后想支持 X 怎么办」。原型只回答一个问题。
- **不要把逻辑和页面搅在一起。** 如果那个纯模块引用了 DOM、`document` 或按钮处理函数，它就不再能被拎出来了。让页面只做纯模块之上的一层薄壳。
- **不要伸手去拿框架、打包器或服务器。** 一个收件人双击就能打开的文件；React 应用或开发服务器会毁掉「可分享」。
- **不要把 HTML 外壳送进生产。** 这个页面是为让人手动点着玩而优化的。它背后那个逻辑模块才是值得留下的部分。
