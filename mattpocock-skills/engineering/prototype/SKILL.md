# 原型（Prototype）

原型就是**用来回答某个问题的用完即弃的代码**。问题决定形态。

## 选一条分支

弄清正在回答的是哪个问题——看用户的提示词、看周边代码，或者用户就在旁边的话直接问：

- **「这套逻辑／状态模型对味吗？」** → [LOGIC.md](LOGIC.md)。构建一个单一的、可分享的 HTML 文件（自由操作按钮，加上分标签页的引导式走查），把状态机推进那些在纸上很难想清楚的用例里，而且要能让非开发者上手操作。
- **「这东西该长什么样？」** → [UI.md](UI.md)。在同一个路由上生成若干个差异极大的 UI 变体，通过 URL search param 和底部悬浮栏切换。

两条分支产出的东西截然不同，所以选错会让整个原型白做。如果问题确实模棱两可，而用户又联系不上，就默认选和周边代码更匹配的那条分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部写明这个假设。

## 两条分支都适用的规则

1. **从第一天起就是用完即弃，并且明确标注。** 把原型代码放在它实际将被使用的地方附近（放在它为之做原型的模块或页面旁边），这样上下文一目了然；但命名要让人一眼看出这是原型、不是生产代码。对于用完即弃的 UI 路由，遵守项目已有的路由约定；不要发明新的顶层结构。
2. **运行成本极低。** UI 原型从项目任务运行器的一条命令启动：`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示是用户双击就能打开的一个 HTML 文件。两种方式启动都不需要动脑。
3. **默认不做持久化。** 状态活在内存里。持久化正是原型要_验证_的东西，不是它该依赖的东西。如果问题明确涉及数据库，就打一个草稿库或本地文件，并用明确的「PROTOTYPE, wipe me」来命名。
4. **别打磨。** 不要测试，不要超出让原型_能跑起来_所需的错误处理，不要抽象。重点是快速学到东西。
5. **把状态显出来。** 每个动作之后（逻辑原型）或每次切换变体时（UI 原型），打印或渲染出完整的相关状态，让用户看见发生了什么变化。
6. **做完就留存。** 把任何已验证的决策融进真实代码，然后把原型本身作为**一手来源**留存：把它提交到一个用完即弃的分支上，放在 main 之外，并在实现 issue 上留一个指向该分支的上下文指针。答案也要留存（结论，以及它了结的那个问题），记在 issue 或某次提交里。main 分支只保留已验证的决策。
