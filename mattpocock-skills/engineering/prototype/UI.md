# UI 原型（UI Prototype）

在同一个路由上生成**若干个差异极大的 UI 变体**，用底部悬浮栏切换。用户在浏览器里来回翻看变体，挑中一个（或者从每个里各偷一点），然后把其余的扔掉。

如果问题关乎逻辑／状态，而不是东西长什么样，那就走错分支了。用 [LOGIC.md](LOGIC.md)。

## 什么时候该用这种形态

- 「这个页面该长什么样？」
- 「我想在定下来之前先看看这个仪表盘的几个方案。」
- 「给设置页试试另一种布局。」
- 任何用户否则就得花一整天在脑子里比较三张模糊草图的时候。

## 两种子形态：强烈优先子形态 A

当一个 UI 原型**紧贴着应用其余部分**时（真实的页头、真实的侧边栏、真实的数据、真实的密度），判断起来要容易得多。单独一个用完即弃的路由是个真空：每个变体孤立看都挺好。只要存在一个说得通的现成页面可以承载这些变体，就默认用子形态 A。只有当原型确实没有就近的归宿时，才去用子形态 B。

### 子形态 A：对现有页面的调整（首选）

路由已经存在。变体渲染**在同一个路由上**，由 `?variant=` URL search param 控制。现有的数据获取、参数和鉴权全部保留。只换渲染。这是默认选项；除非有明确理由不这么做，否则就选它。

如果原型的对象还没有自己的页面、但*天然就该住在某个页面里*（仪表盘的一个新分区、设置页上的一张新卡片、现有流程里的一个新步骤），那它仍然是子形态 A。把变体挂载在宿主页面里。

### 子形态 B：新建页面（最后手段）

只有当被做原型的东西确实没有现成页面可住时（例如一个全新的顶层界面，或者一个没法嵌进任何合理位置的流程），才用它。

按项目已有的路由约定创建一个**用完即弃的路由**。不要发明新的顶层结构。命名要让人一眼看出是原型（例如在路径或文件名里带上 `prototype` 一词）。同样的 `?variant=` 模式。

在决定用子形态 B 之前，先自查一下：真的没有现成页面能承载它吗？空路由会掩盖有内容的页面本会暴露的设计问题。

两种子形态的底部悬浮栏是一样的。

## 过程

### 1. 写清问题并定下 N

默认 **3 个变体**。超过 5 个就不再是差异极大，而开始变成噪音，所以上限就卡在这儿。

用一行写下计划，放在原型所在的位置或文件顶部的注释里：

> 「设置页的三个变体，通过 `?variant=` 切换，挂在现有的 `/settings` 路由上。」

无论用户当下在不在、会不会反驳，这都管用。

### 2. 生成差异极大的变体

起草每个变体。每个都要满足：

- 页面的用途，以及它能访问到的数据。
- 项目的组件库／样式体系（TailwindCSS、shadcn、MUI、纯 CSS，随便什么）。
- 一个清晰导出的组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须在**结构上不同**：不同的布局、不同的信息层级、不同的主要可供性，而不只是颜色不同。三张微调过的卡片网格不算 UI 原型，那是壁纸。如果两份草稿出来太像，就带着明确的「不要用卡片网格」的指导重做其中一个。

### 3. 把它们接起来

在路由上创建一个单一的切换组件：

```tsx
// pseudo-code, adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形态 A（现有页面）：把所有现有的数据获取保留在切换器之上；每个变体只改所渲染的子树。

子形态 B（新页面）：`/prototype/<name>` 下那个用完即弃的路由挂载同一个切换器。

### 4. 构建悬浮切换器

屏幕底部居中的一个小的固定定位条，含三部分：

- **左箭头**：循环到上一个变体（到头回绕）。
- **变体标签**：显示当前变体 key，如果变体导出了名字，也显示那个名字。例如 `B (Sidebar layout)`。
- **右箭头**：向前循环（到头回绕）。

行为：

- 点箭头会更新 URL search param（用框架自己的 router，例如 Next 上的 `router.replace`、React Router 上的 `navigate` 等），这样变体就能被分享、刷新也稳定。
- 键盘：`←` 和 `→` 方向键也能循环。当 `<input>`、`<textarea>` 或 `[contenteditable]` 获得焦点时，不要拦截方向键。
- 视觉上与页面明显区分（例如高对比度的胶囊形、淡淡的阴影），让它一眼就不像是被评估的设计的一部分。
- 在生产构建里隐藏：用 `process.env.NODE_ENV !== 'production'` 或等价检查来控制，这样一次误合入的原型就不会把这条栏发给用户。

把切换器放进单个共享组件里，好让两种子形态都能复用它。放在项目里共享 UI 该待的地方。

### 5. 交付出去

把 URL（以及那些 `?variant=` key）摆出来。用户什么时候得空就什么时候翻。有意思的反馈通常是**「我要 B 的页头配 C 的侧边栏」**，那才是他们真正想要的设计。

### 6. 留存答案并清理

一旦某个变体胜出，先留存答案（哪个变体、为什么），再按 [SKILL](SKILL.md) 描述的方式留存原型。把胜出者融进真实代码，其余的都挪到用完即弃的分支上，而不是挪进 main：

- **子形态 A**：把胜出者融进现有页面；从 main 里删掉落选的变体和切换器。
- **子形态 B**：把胜出的变体提升为一个真实路由；从 main 里删掉那个用完即弃的路由和切换器。

完整的变体集合是一手来源，所以它落在用完即弃的分支上，而不是垃圾桶——留在 main 分支里的变体组件和切换器很快会腐烂，还会让下一个读者困惑。

## 反模式

- **只有颜色或文案不同的变体。** 那是微调，不是原型。真正的变体在结构上互不同意。
- **变体之间共享太多代码。** 共享一个 `<Header>` 没问题；共享一个 `<Layout>` 就毁了意义。每个变体都该有自由扔掉布局的权力。
- **把变体接到真实的写操作上。** 只读原型就够了。如果某个变体需要写，就把它指向一个桩（stub）：问题是「这该长什么样」，不是「后端能不能跑」。
- **把原型直接提升到生产。** 变体代码是在原型的约束下写的（没有测试，错误处理极少）。融进去时要好好重写。
