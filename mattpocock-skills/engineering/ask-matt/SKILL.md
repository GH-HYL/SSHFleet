# Ask Matt（问 Matt）

你记不住每一个技能，所以开口问。

在说明某个技能做什么、或建议跳过某一步之前，先读那个技能的 SKILL.md：这里的摘要只用于定位方向。

**流程（flow）** 是穿过这些技能的一条路径。大多数路径沿着同一条**主流程（main flow）**走，另有两处**上匝道（on-ramp）**汇入其中。其余的都是独立技能，或者垫在底下的一层词汇表。

## 主流程：想法 → 交付

大多数工作走的那条路线。你有一个想法，想把它做出来。

1. **`/grill-with-docs`** 通过访谈把想法打磨清楚。只要你**在一个工作目录里做事**，就从这里开始：它是有状态的，会把它了解到的东西留在 `GLOSSARY.md` 和 ADR 里。（没有工作目录？那就改用 `/grill-me`，在「独立技能」一节里讲。两者跑的是同一个 `/grilling` 原语；`grill-with-docs` 是那个会留下纸面痕迹的，所以只要手边有仓库可供留痕，两者之中它更优。）
2. **分支判断：你是不是能在对话里把每个问题都敲定？** 如果某个问题需要一个能跑起来的答案（状态、业务逻辑、一个你必须亲眼看到才能判断的 UI），那就绕道走一趟原型，两个方向都用 **`/handoff`** 来搭桥（原型住在它自己的目录里，这正是 `/handoff` 的用武之地；见「阶段边界」）：
   - 先 **`/handoff`** 出去，然后针对那个文件开一个全新的会话，
   - 用 **`/prototype`** 以用完即弃的代码回答那个问题，
   - 再 **`/handoff`** 把你学到的东西带回来，并在最初的想法线程里引用它。
3. **分支判断：这是不是一次要跨多个会话的构建？**
   - **是** → **`/to-spec`**（把线程变成一份规格），然后 **`/to-tickets`** 拆成曳光弹工单（tracer-bullet ticket），每张都声明它的**阻塞边（blocking edge）**。接着用两种方式之一推进工单：
     - **`/implement`** 逐张工单做，**每张之间都 `/clear` 上下文**。在本地追踪器上，那是 `.scratch/<feature>/issues/` 下每张工单一个文件，手工按阻塞者优先的顺序推进；在真实追踪器上，依赖边会变成原生阻塞链接，于是任何阻塞者都已完成的工单都可以抓来开工。每张工单都是自包含的，所以上一张的上下文可以随手丢掉。
     - **`/implement-spec`** 一次跑完整份规格。它把工单读成一张**任务图（task graph）**，跨就绪**前沿（frontier）**并行跑实现者子 agent，把所有东西落到同一个**集成分支**上。当你更想统筹整场构建、而不是亲自逐张驱动工单时，就用它。
   - **否** → 就在原地、同一个上下文窗口里 **`/implement`**。

   无论走哪条路，代码都是靠驱动 **`/tdd`**（一次一个红-绿切片）建起来的，并以 **`/code-review`** 收尾——那是对 diff 的双轴复查（标准 + 规格）。`/implement` 每张工单都跑这两个；`/implement-spec` 的实现者们各自驱动 `/tdd`，而它只在集成分支上跑一次 `/code-review`。当你只想测试先行地做出一个具体行为、并不需要完整规格时，单独用 **`/tdd`**；当你想针对某个固定点复查分支或 PR 时，单独用 **`/code-review`**。

   当工作以 pull request 形式提上去时，**`/pr`** 负责塑造正文：能展示改动的最小可视化、证明其有效的改动前后证据，以及一次单向门还是双向门的判断。它是模型调用的，所以 agent 只要写 PR 就会去够它。

4. **`/retro`** 闭上这个回路。一次构建之后，尤其是走歪了的那种，它回过头审视这次会话，并提出对 agent **环境**的改动建议，而不是对代码的：导航路标、自动化检查、`/code-review` 所执行的编码标准、引导文件、工具链。机械性的错误变成确定性检查；需要判断的地方变成编码标准。下一次构建于是从更好的环境起步。

### 上下文卫生

把第 1–3 步保持在**同一个不间断的上下文窗口**里（`/to-tickets` 之前不要压缩也不要清空），这样拷问、规格和工单全都建立在同一套思考之上。之后每个 `/implement` 都从工单出发、重新开局。`/retro` 要在它所回顾的那个会话里跑，趁你还没清空；清空之后，就把它指向那个会话的日志。

这件事的限度是**[智能区（smart zone）](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍能保持敏锐推理的那个窗口（在顶尖模型上约 150k token）。如果一次会话在 `/to-tickets` 之前就逼近它，不要硬撑着让质量下降；在最近的阶段边界处 `/compact` 然后继续（见「阶段边界」）。

## 上匝道

一种会产生工作的起始处境，随后汇入主流程。

- **Bug 和需求堆成山** → **`/triage`**。它让 issue 在分诊角色之间流转，产出 agent 可上手的 issue，之后由 **`/implement`** 接手。

  分诊只针对**不是你创建**的 issue：bug 报告、外部进来的功能请求、任何原始抵达的东西。`/to-tickets` 产出的工单已经是 agent 可上手的，所以**不要对它们做分诊**。

- **有东西坏了** → **`/diagnosing-bugs`**。用于那些难啃的：一眼看不穿的 bug、时有时无的抖动、在两个已知良好状态之间悄悄混进来的回归。在拿到一条**紧凑的反馈回路**（一条已经能在这个 bug 上变红的命令）之前，它拒绝空想，然后带着回归测试去修。修好之后，在同一个会话里跑 **`/retro`**，问问本可以怎么预防这个 bug；如果真正的发现是没有一条好的接缝把它锁住，那就是 **`/improve-codebase-architecture`** 的活儿了。

- **一项巨大而雾蒙蒙的工程：绿地项目，或者一次远超单个会话容量的大功能构建** → **`/wayfinder`**，这里认知负担最重的流程。当从这里到目的地的路还看不见时，它在问题追踪器上画出**决策工单**的**共享地图**，一次解决一个，产出的是**决策，不是交付物**，直到雾被推回去、路变清晰。**`/grill-with-docs`** 打磨的是你能在一个会话里握得住的想法，wayfinder 服务的是你握不住的那个；它更慢也更密，所以留给的正是那种情况，绝不要用在一个边界清晰的功能上。

  地图变清晰之后，**它是交接，不是构建**：在 **`/to-spec`** 处汇入主流程，由它把地图里相互关联的决策坍缩成一份可执行的计划，然后照常 `/to-tickets` 和 `/implement`。把地图直接接进 `/implement` 会跳过这次坍缩，把那些关联的细节丢掉，所以只有当这项工程最终发现确实很小的时候，才直接进 `/implement`。

## 代码库健康

不是功能工作，只是日常保养。

- 只要你有空让代码库保持适合 agent 在其中作业，就可以跑 **`/improve-codebase-architecture`**。它把**深化机会**摆到台面上；挑中一个就会**生成一个想法**，你可以把它带到主流程的 `/grill-with-docs` 里去。它是找出候选者的勘察；**`/codebase-design`**（见下）则是你为选中者做设计的工作台。

## 垫在底下的词汇表

两份模型调用的参考文档，跑在其他技能*底下*，各自是自身词汇的唯一事实来源。当出问题的是**词**而不是流程时，直接够它们；也可以让上面的技能把它们拉进来。

- **`/domain-modeling`**：打磨项目的*领域*语言——质疑一个含糊的术语、拆解一个超载的词（"account" 干了三份活）、把难以回退的决策记成一份 ADR。它是 `/grill-with-docs` 所驱动的主动纪律，用来让 `GLOSSARY.md` 保持为一份干净整洁的词表。
- **`/codebase-design`** 是深模块（deep module）的词汇（module、interface、depth、seam、adapter、leverage、locality），用来设计一个模块的*形状*：在干净的接缝处、用小接口封装大量行为。`/tdd` 和 `/improve-codebase-architecture` 都说这门语言。

## 阶段边界

一个**阶段（phase）** 是会话内部的一整块工作：拷问、实现、QA。在两个阶段之间的**边界（boundary）** 上你有五个选项，而在它们之间做选择，是这整张地图上最模糊的一个决策：

- **继续（Continue）**：原地不动。不花代价，不丢东西。
- **`/clear`**：清空窗口，当这里的一切对接下来都不重要时。
- **`/handoff`** 写一个可携带的 markdown 文件。很窄：只用于**新的宿主环境（harness）**、**新目录**、**同事**，或者在**阶段中途**把一条支线任务分叉出去。它买到的是可携带性。
- **子 agent（Subagent）**：把一个范围收得很紧的任务送到它自己的窗口，拿一份报告回来。
- **`/compact`** 压缩当前上下文，并用它给一个新会话播种。这是**默认项**，位于决策树的底部而不是第一个够到的。

读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 了解那棵有序的决策树：五个问题、每个分支背后的推理，以及为什么一手来源（primary source）的代价使得**继续**成为最先该排除的那个。在边界**处**做这个决策；阶段中途，要么继续，要么把剩下的拆给子 agent。

## 独立技能

完全在主流程之外。

- **`/grill-me`**：和 `/grill-with-docs` 一样不留情面的访谈，但**无状态**：它在本地什么都不存，也不建 `GLOSSARY.md`。当你**不在一个工作目录里做事**时够它（打磨一份计划、一个设计、一篇文字，任何底下没有仓库的东西）。如果你在工作目录里，就改用 `/grill-with-docs`：它跑同一场访谈还留下纸面痕迹，所以严格来说它更好。
- **`/grilling`** 是访谈这个原语本身：回合、前沿、事实归 agent 管而决策归你管。`/grill-me` 和 `/grill-with-docs` 是两个有名字的入口，而 `/triage`、`/wayfinder` 和 `/improve-codebase-architecture` 都在内部跑它。只有当你想要这场访谈而不要外面任何包装时，才直接够它。
- **`/prototype`** 是一个小小的、用完即弃的程序，回答一个设计问题：这个状态模型对不对味，或者这个 UI 该长什么样。用完即弃是对代码写法的约束，不是毁掉它的承诺：答案会折进真正的代码里，而原型本身作为一份**一手来源**保留在从 main 切出的 `prototype/<name>` 分支上，并由实现用的 issue 指向它。它是主流程第 2 步里的那趟绕道，但只要某个设计问题在纸面上难以敲定，随时都可以够它。
- **`/research`**：把阅读的跑腿活委派给一个**后台 agent**：它对照**一手来源**调研一个问题，然后在仓库里留下一份带引用的 Markdown 文件。它读它的，你接着干你的。它产出的这份文件是拿到主流程 `/grill-with-docs` 里*去用*的东西，因为调研是喂给思考的，而不是替代思考的。
- **`/to-questionnaire`** 出现在挡路的那个东西不在你脑子里、也不在代码库里，而在**别人脑子里**的时候，它会写一份问卷给对方填。它是 `/grill-me` 的反面：它不问你就主题做访谈，而是就**这次发送**（发给谁、你需要拿回什么）访谈你，再把问题对准那个缺口。拿回来的东西是 `/grill-with-docs` 或 `/to-spec` 的素材。
- **`/wizard`** 针对的是只有**人**才能执行的步骤：资源开通基础设施、配置凭证或 CI 密钥、在陌生的第三方控制台里点来点去、跑一次性的迁移或切换上线。它生成一个交互式 bash 脚本，逐个打开 URL、逐个捕获取值、写进 `.env` 和 GitHub secrets，于是这套流程不再是你每次都要向 agent 重新解释一遍的东西。它是模型调用的，所以 agent 一撞上只有你能过的那堵墙就会去够它。如果 agent 自己就能做，那就该它做；这个技能用于人确实处在回路中的场合。
- **`/wait-what`** 是对一条没送达的消息的纠偏。在对话中途、在任何其他技能内部用它，agent 就会用你当时缺失的上下文、以大白话、使用 `GLOSSARY.md` 的词汇，把它刚说的东西重新讲一遍。它是事后补救；`/grill-with-docs` 才是事前的解药，因为早早商定好的共同语言，才是让那些行话压根不出现的原因。
- **`/teach`**：跨多个会话来学一个概念，把当前目录当作有状态的工作区。
- **`/writing-for-agents`** 是撰写 agent 所消费文档的参考：技能、AGENTS.md、被指向的文档。

## 前置条件
