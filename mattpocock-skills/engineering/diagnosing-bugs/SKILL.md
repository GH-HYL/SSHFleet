# 诊断缺陷（Diagnosing Bugs）

一套应对疑难缺陷的纪律。只有在明确给出理由时才可跳过某个阶段。

在探索代码库时，读 `GLOSSARY.md`（如果存在），以建立相关模块的清晰心智模型，并检查你正在改动的区域里的 ADR。

## 脱敏

本技能要求你展示命令、输出和捕获的产物。**必须先脱敏每一个密钥**：在它的位置写上 `<REDACTED>`。把循环构建在环境变量之上，这样凭据留在环境里，而不是留在你展示的内容里。捕获的产物带有认证头：只引用承载信号的那些行。

如果脱敏后的输出不足以诊断该缺陷，说明这一点并询问用户。

## 阶段 1：构建反馈回路（feedback loop）

**这就是本技能的核心。** 其余都是机械劳动。如果你对该缺陷有一个**紧凑**的通过/失败信号（一个会在*这个*缺陷上变红的信号），你就能找到原因；二分查找、假设检验、埋点都只是消费它。如果你没有这样的信号，盯再多代码也救不了你。

在这里投入不成比例的精力。**要激进。要创造。拒绝放弃。**

### 构建回路的方式，大致按此顺序

1. **失败测试**，在任意能触达该缺陷的接缝（seam）上：单元、集成、e2e。
2. **Curl / HTTP 脚本**，打向运行中的开发服务器。
3. **CLI 调用**，带一个 fixture 输入，把 stdout 与已知正确的快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer），驱动 UI 并对 DOM/console/network 做断言。
5. **重放捕获的 trace。** 把真实的网络请求 / payload / 事件日志存到磁盘；在隔离环境中让它重走该代码路径。
6. **一次性测试装置（harness）。** 起一个系统的最小子集（单个服务、依赖用模拟对象（mock）），用一次函数调用走完缺陷所在的代码路径。
7. **属性 / 模糊测试循环。** 如果缺陷是“有时输出错误”，跑 1000 个随机输入，寻找失效模式。
8. **二分查找测试装置。** 如果缺陷出现在两个已知状态（commit、数据集、版本）之间，把“在状态 X 启动、检查、重复”自动化，这样你能 `git bisect run` 它。
9. **差分循环。** 把同一输入分别跑过旧版本与新版本（或两套配置），对输出做 diff。
10. **人在回路（HITL）bash 脚本。** 最后手段。如果必须由人来点击，用 `scripts/hitl-loop.template.sh` 来驱动*他*，这样循环仍然是结构化的。捕获的输出回流给你。

构建出正确的反馈回路，缺陷就解决了 90%。

### 收紧回路

把回路当成一个产品。一旦你有了*一个*回路，**收紧**它：

- 我能让它更快吗？（缓存环境搭建、跳过无关初始化、收窄测试范围。）
- 我能让信号更锐利吗？（对具体症状做断言，而不是“没崩”。）
- 我能让它更确定吗？（固定时间、固定 RNG 种子、隔离文件系统、冻结网络。）

一个 30 秒且不稳定的回路只比没有回路好一点点；一个 2 秒且确定性的回路才是紧凑的，是调试的超能力。

### 非确定性缺陷

目标不是干净的重现，而是**更高的复现率**。把触发条件循环 100 次、并行化、加压力、收窄时间窗口、注入 sleep。50% 概率抖动的缺陷可调试；1% 的不可调试，所以持续提高复现率，直到它可以被调试。

### 当你确实构建不出回路时

停下来并明确说明。列出你试过的东西。向用户要：(a) 能复现它的那个环境的访问权，(b) 一份脱敏的捕获产物（HAR 文件、日志转储、core dump、带时间戳的录屏），或 (c) 允许添加临时的生产环境埋点。**不要**在没有回路的情况下继续去提假设。

### 完成标准：一个会变红的紧凑回路

阶段 1 完成的标志是回路**紧凑**且**能变红**：你能说出**一条命令**（一个脚本路径、一次测试调用、一个 curl），你**已经至少运行过它一次**（展示这次调用及其输出，已脱敏），并且它满足：

- [ ] **能变红**：它走的是真实的缺陷代码路径，并对**用户的确切症状**做断言，因此它能在这个缺陷上变红、在修复后变绿。不是“运行不报错”；它必须能够*抓住这个具体的缺陷*。
- [ ] **确定性**：每次运行结论相同（不稳定的缺陷：按上文，固定一个高复现率）。
- [ ] **快**：秒级，不是分钟级。
- [ ] **Agent 可运行**：你能无人值守地运行它；只有通过 `scripts/hitl-loop.template.sh` 才引入人在回路。

如果你发现自己在命令出现之前就靠读代码来建立理论，**停下：直接跳到假设正是本技能要防的失败。** 没有能变红的命令，就没有阶段 2。

## 阶段 2：复现 + 最小化

运行回路。看着它随缺陷出现而变红。

确认：

- [ ] 回路产生的失效模式是**用户**描述的那一个，而不是恰好相近的另一个失效。错缺陷 = 错修复。
- [ ] 该失效在多次运行中可复现（或者，对非确定性缺陷，复现率高到足以作为调试依据）。
- [ ] 你已经捕获了确切的症状（错误信息、错误输出、慢的耗时），以便后续阶段验证修复确实解决了它。

### 最小化

一旦它变红，把重现缩小到**仍然会变红的最小场景**。**一次一个地**砍掉输入、调用方、配置、数据和步骤，每砍一刀就重跑回路，只保留对失效起承重作用的部分。

为什么要费这个劲：最小重现会缩小阶段 3 的假设空间（剩下的可疑活动部件更少），并成为阶段 5 中干净的回归测试。

完成标志是**剩下每个元素都承重**：去掉其中任何一个，回路就变绿。

在你完成复现**且**最小化之前，不要继续。

## 阶段 3：提出假设

在测试任何一个之前，先产生 **3–5 个排好序的假设**。只生成单个假设会锚定在第一个看似合理的想法上。

每个假设必须**可证伪**：说出它给出的预测。

> 格式：“如果 <X> 是原因，那么 <改动 Y> 会让缺陷消失 / <改动 Z> 会让它更糟。”

如果你说不出预测，这个假设只是一种感觉：丢弃它或让它更锐利。

**在测试之前把排序后的清单展示给用户。** 他们常常掌握着能瞬间重排顺序的领域知识（“我们刚给第 3 项部署了一处改动”），或者知道一些他们早已排除的假设。这是一个便宜的检查点，能省大量时间。不要为此阻塞；如果用户不在，就按你的排序继续。

## 阶段 4：埋点

每个探针都必须对应阶段 3 中某个具体的预测。**一次只改一个变量。**

工具偏好：

1. 如果环境支持，用**调试器 / REPL 检查**。一个断点胜过十条日志。
2. 在能区分各假设的边界处打**有针对性的日志**。
3. 绝不要“把所有东西都打日志然后 grep”。

**给每条调试日志打上唯一前缀标签**，例如 `[DEBUG-a4f2]`。最后的清理就变成一次 grep。没打标签的日志会活下来；打了标签的会死。

**性能分支。** 对性能回归，日志通常是错的。改为：先建立基线测量（计时测试装置、`performance.now()`、profiler、查询计划），然后二分。先测量，后修复。

## 阶段 5：修复 + 回归测试（regression test）

**在修复之前**写回归测试，但前提是存在**正确的接缝**。

正确的接缝是指：测试能在该处复现**真实的缺陷模式**，就像它在调用点发生的那样。如果唯一可用的接缝太浅（缺陷需要多个调用方时却只做单调用方测试、无法复现触发该缺陷的调用链的单元测试），在那里写回归测试只会给出虚假的信心。

**如果不存在正确的接缝，这本身就是发现。** 记下它。代码库架构正在阻碍这个缺陷被锁定。把它标记给下一阶段。

如果存在正确的接缝：

1. 把最小重现转成该接缝上的一个失败测试。
2. 看着它失败。如果你是通过改动代码或 fixture 强行制造红色的，就先对一份原始副本做 `diff`，证明这处改动确实生效了，再信任它。
3. 应用修复。
4. 看着它通过。
5. 对原始（未最小化的）场景重跑阶段 1 的反馈回路。

## 阶段 6：清理

宣布完成之前必须做到：

- [ ] 原始重现不再复现（重跑阶段 1 的回路）
- [ ] 回归测试通过（或记录下缺少接缝这一事实）
- [ ] 所有 `[DEBUG-...]` 埋点已移除（`grep` 该前缀）
- [ ] 一次性原型已删除（或移到明确标记的调试位置）
- [ ] 最终被证明正确的假设写进了 commit / PR 信息，好让下一个调试者学到东西
