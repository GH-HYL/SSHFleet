一个含糊的想法到来了，它大得超出单个 agent 会话，而且裹在迷雾中：从这里到**目的地（destination）**的路还看不见。寻路（Wayfinding）讲的是找到那条路，而不是朝目的地猛冲。本技能把这条路画成仓库问题追踪器上的一张**共享地图（shared map）**，然后一次处理一个**决策工单（decision ticket）**（其解决即一个决策的问题，而不是要执行的构建切片），直到路线清晰。

目的地因每次行动（effort）而异，而给它命名是画图的第一步：它塑造每一个工单。它可能是要交接并反复迭代的一份规格、要在规划开始前锁定的一个决策，或就在原地做出的一个改动，比如一次数据结构迁移。地图与领域无关：工程工作、课程内容，任何符合这个形状的都行。

## 规划，而非动手

Wayfinder 默认是**规划**：每个工单解决一个决策，当路清晰时就完成了地图，在有人去把那件事做掉之前不再有什么要决定。那种「干脆直接动手」的拉力，通常正是你已到达地图边缘、该交接了的信号。某次行动可以在其 **Notes** 里覆盖这一点，把执行也带进地图本身，但除此之外，产出决策，而不是交付物。

## 以名相称

每张地图和每个工单都是一个 issue，所以它有一个**名字**：它的标题。在一切由人阅读的地方（叙述、地图的 Decisions-so-far），都用那个名字来指代它，绝不用光秃秃的 id、编号或 slug。一堵 `#42, #43, #44` 的墙是读不下去的；名字一眼就能读。id 和 URL 不会消失；名字包裹着它的链接，但它们是乘在名字_之内_的，绝不代替名字。

## 地图（The Map）

地图是本仓库问题追踪器上的单个 issue，标记为 `wayfinder:map`，是标准产物。它的工单是地图的子 issue。

地图是一份**索引**，不是仓库。它列出已做出的决策，并指向承载其细节的那些工单；一个决策只存在于一个地方，即它的工单，所以地图从不复述它，只摘其要点并给出链接。

**地图、它的子工单、阻塞关系与前沿查询在物理上存在哪里，因追踪器而异。** 问题追踪器本应已经提供给你。如果没有，告诉用户运行 `/setup-matt-pocock-skills`。查阅追踪器文档的「Wayfinding operations」一节，了解_本_仓库如何表达它们。如果没有提供任何追踪器，就默认使用本地 markdown 追踪器。

### 地图正文

整张地图的低分辨率视图，每个会话加载一次。未关闭的工单**不**列出来：它们是未关闭的子 issue，靠查询找到。

```markdown
## Destination

<what reaching the end of this map looks like: the spec, decision, or change this effort is finding its way to. One or two lines; every session orients to it before choosing a ticket.>

## Notes

<domain; skills every session should consult; standing preferences for this effort>

## Decisions so far

<!-- the index: one line per closed ticket, enough to judge relevance, then zoom the link for the detail the ticket holds -->

- [<closed ticket title>](link): <one-line gist of the answer>

## Not yet specified

<!-- see "Fog of war": in-scope fog you can't ticket yet; graduates as the frontier advances -->

## Out of scope

<!-- see "Out of scope": work ruled beyond the destination; closed, never graduates -->
```

### 工单

每个工单都是地图的一个**子 issue**；追踪器的 issue id 就是它的身份。它的正文是那个问题，规模定为一次 10 万 token 的 agent 会话：

```markdown
## Question

<the decision or investigation this ticket resolves>
```

每个工单带一个 `wayfinder:<type>` 标签，取自 `research`、`prototype`、`grilling`、`task`（见 [工单类型](#ticket-types)）。`wayfinder:` 标签是地图及其工单唯一携带的标签，绝不带像 `ready-for-agent` 这样的分诊标签：它们是决策，不是实现工作。

一次会话通过把工单指派给驱动地图的开发者来**认领（claim）**它，而且是在任何工作之前**首先**做，好让并发的会话跳过它。那个指派人_就是_认领：一个未关闭、未指派的工单就是未被认领的。

阻塞使用追踪器的**原生（native）**依赖关系：这一点至关重要，因为它能在追踪器自己的 UI 中_可视化地_呈现前沿，于是人不用打开地图就能看到什么可以拿。只有缺少原生阻塞的追踪器才退回到正文约定。当阻塞某个工单的每个工单都已关闭时，该工单即**解除阻塞（unblocked）**；**前沿（frontier）**就是那些未关闭、未阻塞、未被认领的子工单，即已知世界的边缘。

答案不属于正文；它在解决时被记录（见 [沿地图推进](#work-through-the-map)）。解决工单时产生的资产从该 issue 链接过去，而不是粘贴进来。

## 工单类型（Ticket Types）

每个工单要么是 **HITL**（人在回路（human in the loop），与一个为自己发言的人_一起_工作），要么是 **AFK**，由 agent 独自驱动。HITL 工单只能通过那场实时交流来解决；agent 绝不代替人的那一方（一个自问自答的拷问 agent 已经违反了这一点）。

- **Research（AFK）**：阅读文档、第三方 API，或本地资源（如知识库），以浮出一个决策正在等待的事实。由调用 Skill 工具加载 "research" 的子 agent 解决。当你需要当前工作目录之外的知识时使用。
- **Prototype（HITL）**：通过做一个可反应的廉价、粗糙、具体的产物（一份提纲、一个粗略想法、一个桩（stub），或 UI/逻辑代码）来提升讨论的保真度，做法是调用 Skill 工具加载 "prototype"。把该原型作为资产链接。当关键问题是「它看起来该是什么样」或「它行为该是什么样」时使用。
- **Grilling（HITL）**：对话。默认情形。始终调用 Skill 工具两次，加载 "grilling" 和 "domain-modeling"。
- **Task（HITL 或 AFK）**：在一个_决策_做出之前必须发生的手工工作：没有什么要决定、要原型化或要研究的，但讨论被它卡住，直到它做完。注册某个服务好让它的 API 可被评判、开通访问权限、搬动数据好让它的形状可见。这是唯一_动手做_而非做决定的一类，它靠解除某个决策的阻塞来挣得自己的位置，而不是靠交付目的地。agent 在能做到时独自驱动它（AFK）；否则它给人一份精确的清单（HITL）。工作完成时即为解决；答案记录做了什么以及任何由此产生、后续工单依赖的事实（凭据位置、新 URL、行数）。

## 战争迷雾（Fog of war）

地图是_刻意_不完整的：看不见的就别画。在实时工单之外是**战争迷雾（fog of war）**：对于那些你能看出即将到来、却还无法确定下来的决策与调查的模糊视野，因为它们挂在仍然开放的问题上。解决一个工单会清掉它前方的雾，把如今可被明确的东西逐块升级成新工单，一次一个，直到通往目的地的路清晰、不再有工单剩下。

地图的 **Not yet specified** 一节就是写下那片模糊视野的地方：疑似的问题、以后要回看的区域。它是_朝向_目的地的未发现前沿：这里的一切都在范围内，只是还不够清晰到能立成工单。视野允许多松就写多松、多全就写多全；它同时充当路标，让协作者看出这次行动正要往哪去。

**是雾还是工单？** 判据是你现在能否精确地陈述那个问题，_而不是_你现在能否回答它。

- **立成工单，当**问题已经清晰，即使它被阻塞、你还不能动手。
- **归入 Not yet specified，当**你还无法把话说得那么清晰。不要把雾预先切成工单大小的碎块：它比一个工单更粗糙，而一块雾在前沿抵达它时，可能升级成好几个工单，也可能一个都不是。

**Not yet specified** 排除已经决定的（Decisions so far）、已经是实时工单的，以及超出范围的（下一节）。

## 范围之外（Out of scope）

雾只会_朝向_目的地聚拢。目的地确定了范围，所以超出它的工作就是**范围之外（out of scope）**：它不是雾，也不属于 **Not yet specified**。它在地图上有自己的 **Out of scope** 一节：你有意识地排除在_这次_行动之外的工作。决定它归属的是范围，不是清晰度。

范围之外的工作永远不会升级（前沿止于目的地），所以只有当目的地被重画时它才会回来，而且是作为一次全新的行动，而不是恢复。

判定某个东西在范围之外，是一个划定范围的动作，而不是路线上的某一步。当一个已经存在的工单被发现位于目的地之外（画图时误纳，或被某次解决暴露出来），就**关闭它**（已关闭的工单无疑已不在前沿），并在 **Out of scope** 一节留一行：要点，加上为什么它在范围之外，并链接那个已关闭的工单。它不进 **Decisions so far**，那一节记录的是实际走过的路线；范围边界不是路线上的某一步。

## 调用

两种模式。无论哪种，**每个会话绝不解决超过一个工单**，research 工单除外。

### 画出地图

用户带着一个含糊的想法来调用。

1. **给目的地命名。** 调用 Skill 工具两次，加载 "grilling" 和 "domain-modeling"，来确定这张地图要通往什么：那份规格、决策或改动。目的地确定了范围，所以先把它定下来。
2. **画出前沿。** 再拷问一次，这次是**广度优先（breadth-first）**：在整个空间里铺开，而不是在任何一条线索上深入，浮出开放的决策和当下可走的第一步。**如果这没有浮出任何雾**（通往目的地的路已经清晰，整段旅程小到一次会话就能走完），你就不需要地图。停下来，问用户想怎么进行。
3. **创建地图**（标签 `wayfinder:map`）：填好 Destination 和 Notes，Decisions-so-far 留空，把雾勾画进 **Not yet specified**。
4. **创建你现在能明确的工单**，作为地图的子 issue，然后在**第二遍**里接上阻塞边（issue 需要先有 id 才能互相引用）。交叉引用也在那一遍里用真实 id 写：占位的 `#<n>` 会自动链接到一个不相关的 issue。接线会把它们分进前沿与被阻塞两类；你还没法明确的一切留在雾里：**Not yet specified** 一节。
5. **派出 research 子 agent。** 对你刚创建的每个 `research` 工单，起一个调用 Skill 工具加载 "research" 的子 agent 并行解决它，把它的发现捕获在一个一次性的 `research/<name>` 分支上，并从该工单给出一条上下文指针。推送该分支但不开 PR：它永远不会被合并。
6. 停下：画图是一个会话的工作量；它自己不解决任何东西。

### 沿地图推进

用户带着一张地图（URL 或编号）来调用。工单是**可选**的：不给的话，由你而不是用户来挑下一个决策。

1. 加载**地图**：低分辨率视图，不是每个工单的正文。
2. 挑选工单。如果用户点名了某个，就用它。否则按顺序取前沿上的第一个工单。**认领它：**在任何工作之前把它指派给自己。
3. 按其 `wayfinder:<type>` 标签所指的类型来解决它（见 [工单类型](#ticket-types)）。读标签，不只是正文：正文从不说明类型。**按需拉近（Zoom as needed）**：随时取回任何相关或已关闭工单的完整正文；按 `## Notes` 区块点名的技能调用 Skill 工具。拿不准时，调用 Skill 工具两次，加载 "grilling" 和 "domain-modeling"。
4. 记录这次解决：把答案作为**解决评论**发出，**关闭**该 issue，并**追加一条上下文指针**到地图的 Decisions-so-far。
5. 加入新浮出的工单（先创建再接线）；把答案使之可明确的雾升级掉，并从 **Not yet specified** 中清掉每一块已升级的雾，让它只作为它的新工单存在。如果答案暴露出某个工单（这个或另一个）位于目的地之外，就**把它判定为范围之外**，而不是在路线上解决它。如果该决策使地图的其他部分失效，就更新或删除那些工单。

用户可能会并行跑未被阻塞的工单，所以要预期其他会话正在并发编辑追踪器。
