你已经被提供了一份规格（spec）。这份规格应当关联着若干工单（ticket），描述如何实现该规格。

问题追踪器（issue tracker）应当已经提供给你。如果没有，告诉用户运行 `/setup-matt-pocock-skills`。

目标是整份规格在一个**集成分支（integration branch）**上实现完毕，每个工单都按问题追踪器关闭工作的方式被解决。

工单不是一串步骤。它们是一张**任务图（task graph）**，彼此之间存在阻塞关系。这意味着总有一批**就绪前沿（frontier）**上的工单可以被直接抓取。

与子 agent 之间的通信应当稀疏。主要通过**上下文指针（context pointer）**沟通：指向规格、工单、研究笔记和之前的 commit。不要重复那些通过指针就能获取的信息。

**实现者子 agent（implementer subagent）**应尽可能放到后台运行，以获得最大并发度。

## 步骤

1. 读规格和工单，理解任务图。

2. （可选）用一个**探索子 agent（exploration subagent）**完成工单所需的任何探索——相关代码库文件或外部文档。确保探索子 agent 能保存文件——它应当把 markdown 笔记保存在仓库之外的某个目录，供之后所有子 agent 访问。这样**实现者子 agent** 就能专注于实现而不是探索。

3. 创建集成分支。如果问题追踪器通过 PR 关闭工作，或者用户要求开一个，就在步骤 5 的第一次合并之后开一个草稿 PR（一个相对 main 没有超前提交的分支开不了 PR），并标注它会关闭该规格和这些工单。

4. 用**实现者子 agent** 实现每个工单，每个都在自己的工作树（worktree）和自己的分支上。每个实现者子 agent：
   - 开始前确认自己的工作树基于集成分支，如果不是就重置到它上面；
   - 调用 Skill 工具并传入 `tdd` 来构建该工单；
   - 在报告完成之前，把集成分支的最新提交合并进自己的分支

5. 一个**实现者子 agent** 完成后，用一个**合并子 agent（merger subagent）**把它的工作合并到集成分支。

6. 如果这改变了可用工单的**就绪前沿**，就再启动更多**实现者子 agent** 处理新工单。这样可以获得最大并发度。

7. 所有工单完成后，在集成分支上调用 Skill 工具并传入 `code-review`。用单个**实现者子 agent** 修复代码复查提出的所有问题。

8. 如果存在草稿 PR，把它标为可复查。否则，按问题追踪器关闭工作的方式逐个解决工单，并报告集成分支。

9. 清理所有**实现者子 agent** 的工作树。
