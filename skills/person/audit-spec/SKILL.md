# 规格审计

**用途**：开工前判一件事——**照这份规格写出来，已定的架构会不会被磨掉**。附带查四样别的技能挡不住的：明着违反 ADR、验收标准缺、边界（不做）缺、使用者可见面被改。

**什么时候跑**：**每回都跑**，这是作者的工作流（ADR 审计、规格审计、质量审计每次都跑，为的是弥补「不懂开发」）。但跑之前先过一道门：**手上这份规格，是实现合同还是交接书？** 是交接书就不审，一句话收尾。

**为什么在开工前**：结构问题在代码里被发现，改法通常是重写；在规格里被发现，改法是改一句话。这是这个技能存在的唯一理由——不是审得更细，是审得更早。

**不判**：实现好不好、能不能跑、代码对不对——这时候还没有代码。文案好坏、手册口径也不归这里，那是 `/audit-docs`。**「有没有替开发者拍板」也不归这里**——那与 `/audit-docs` 的一致性轴重复，同一个问题不问两遍。

**三个角色按这一套用**：开发者下指令、拍板；执行者照技能干活（AI 或后来的维护者）；使用者用做出来的工具。

**审完做什么**：两条路——要他拍板的报上去，改法唯一的自己改掉。他只看前一条。

## 零、进门：这份规格是哪一种

作者的实际流程是两段：

1. **撞见问题，先开议题**——AI 自动生成的那份 `spec.md` 只是**交接书**（这件事是什么、我担心什么、下次从哪接着聊）。这时**不审**，审了也是白审，它本来就打算重写。
2. **腾出手来，写完 ADR，重写规格**——这时它才是**实现合同**（要做成什么样、怎么验收）。**这才是本技能的对象。**

**判据机械三条，满足任意一条就算实现合同**：

- 引用了 ADR（写了编号，或路径落在 `docs/adr/` 下）；
- 有 `Testing Decisions` 一节，或有能当验收项的清单；
- 有 `Out of Scope` 一节。

**三条一条都不满足 → 报一句「尚未进入合同阶段，本技能不审」，收尾。不输出任何问题。**

**判据不足时不硬判**：结构定义仍在施工期（议题里的决策工单还没全部 `resolved`），凡落到还没定的那一块，写「判据不足，跳过」并点名缺哪一条，不许拿常识补。

## 一、取判据

**判据只有仓库**，三类，按可靠性排。

### 1.1 结构决定（最硬）

两处，按形状认——编号和目录名会换，形状不换。

- `docs/adr/` 里状态为 `accepted`、内容约束代码结构的那几篇。内容去那儿读，不抄进来。
- `docs/issues/<议题目录>/` 里 `Status: resolved` 的决策工单，`## Answer` 是更细的结构判据。

**先确认它还算数**：读 `状态:` 行与 `## 更新记录`，被取代的顺指针走到当前决定。作废的不拿来判。

**本技能不抄这些决定的内容。** 抄一遍就有两份，ADR 改了口径这一份不会跟着改——那是第二个真相。

### 1.2 词表与既有形状

`GLOSSARY.md` 里的术语定义；新工程已有的导出符号。规格里一个概念两个名字、一个名字两个意思，或要求一个与既有符号同形的新函数，逐个报出来。

### 1.3 仓库既有的写法约束

仓库里 spec 的写法模板（该有哪几节）、测试接缝的约定（说定测哪个口子才写测试）、结构决定里讲代价的那一段。

## 二、查什么

**四条轴，各查一层，条数相当**，可以派四个只读子 agent 并行。

轴一到轴三判的是**腐蚀**，一句话判据：

> 照这份规格写出来，已 accepted 的结构决定里，哪一条会从**「结构上做不到」退化成「纪律上不该做」**？

结构决定的立身之本不是"定了几个站、分了几层"，是**把纪律从靠人盯换成结构上够不着**。所以腐蚀不是"某条决定被违反"，是**那条决定失去牙齿**——违反了也不报错、不编译不过、没人看得见。

**拼接只是最典型的一种**：想要一个值，本来该回上游纵切加字段，图省事就地拿一个。它之所以危险，不是因为它难看，是因为**它把「够不着」变成了「够得着，只是不该」**——从那一刻起，后面每一个 AI 都有了一条可走的路。

**所以这三轴不看"写得对不对"，看"写得会不会让人走上那条路"。** 每条末尾那句「退化成什么」就是判定标准——想不出退化后的样子，这条不成立，别报。

轴四判的是**这张纸自己的毛病**，判据不一样，见那一节。

### 轴一：数据流与归属（5 条）

数据只往下走，一件事只在一处产出。

1. **穿站回取**。某站要的数据不在上一站交给它的交接件里，规格的解法是「执行时再读一遍配置 / 清单 / argv」，而不是「回上游那条纵切把字段加进交接件」。
   *退化：下游随时能拿到源头，交接件变成可选。*
2. **同一件事算两遍**。上游已算出的值不在交接件上，规格让下游重算。代价不是性能，是两处将来会不一致。
   *退化：同一事实有两个来源，改一处另一处不知道。*
3. **共享可变状态**。规格里出现包级变量、单例、全局配置对象、共享缓冲，让某处能「伸手去拿」。判据是：有没有人真的写它，不是语法上能不能写。
   *退化：够不着变成够得着，而且没有任何一处代码需要改就能改到。*
4. **东西搬到不该在的那一站**。一个值、一件事、一个结论，本该由某一站产出，规格把它挪到别处产出：这一站替上游定值、替下游下结论，或把归类、构造权搬去别的站。
   *退化：同一件事有了两个产出地，两边都觉得自己算得对；改口径时只改一处，另一处继续用旧值。*
5. **阶段顺序被动过**。规格跳掉某一站，或把两站的先后调过来。
   *退化：没人说得清「这个值是那站定的还是这站改的」，正是交接件要防的那件事。*

### 轴二：唯一出口与塔尖（6 条）

能出字、能退出、能拍板的，都只有一处。

6. **自己出字**。规格让某处自己 `print`、自己拼报错串、自己决定报错长什么样，而不走已定的构造点或输出包。
   *退化：报错格式回到「每个包一套」，而那正是上一次重构要治的病。*
7. **自己退场**。规格让某站在内部 `os.Exit`、`panic` 了事、或自行中断流程。
   *退化：退出权散开，收尾（defer、日志落盘、码页还原）随时断。*
8. **契约长出行为**。要求往契约（站点之间传的那份数据结构）里加校验、格式化、拼装、默认值填充。
   *退化：契约从「一张纸」变成抽屉，下游依赖它就开始成环。*
9. **横切长出业务**。要求横切包（日志、控制台、交互、归档、退出码这类叶子包）里做业务判断。判据是「它产不产业务数据」。
   *退化：叶子包不再纯，人人依赖的包开始被业务缠住，环从这里长出来。*
10. **横切导出零件**。要求横切包导出「拼个路径」「顺手格式化一下」这类谁都能拿去拼的 helper。
    *退化：叶子包的导出面从几个整件事变成一堆零件，谁都够得着，下次绕路就有现成的拼装件。*
11. **塔尖变厚**。规格让入口的依赖面越出它该有的那几样——出现了不属于这套结构的包，或标准库里没被点名过的符号。判据看依赖清单，不看行数：拼接、判规则、读写文件、装配数据，只有落进清单才算数。清单本体去结构决定里读，不抄。
    *退化：塔尖从「用了什么一眼数得清」变成「谁都能进来」，再没有一处能对不读代码的人说清它靠了什么。*

### 轴三：模块与接口（6 条）

一个包只干一件事；对外给的是整件事，不是一堆零件。

12. **加站、劈站、并站**。规格描述的处理环节既不属于已定的那几站、也不是横切——它在悄悄加一站；或把某一站劈成两个、把两站并成一个。
    *退化：站的这个切法失去意义，之后没有「该放哪儿」的答案。*
13. **反向依赖**。下游站要 import 上游站（例：报告站 import 执行站的数据类型），或塔尖替某一站做它该做的事。
    *退化：单向变双向，改一站要连带改上下游，改动面从此不可预测。*
14. **新模块无家**。规格描述的新东西说不清属于哪一站、也不像横切——尤其「来回穿插」的那类。它不是大模块，是到处都要用一小点的那种。
    *退化：它会被随手塞进某一站，或被攒成一个新的 `common`。这是最容易发生、也最难事后看出来的一类。*
    *追问一句：它是横切（不产数据、叶子包），还是业务（产数据、该归某一站）？两者都说不清的，就是这一类。*
15. **已有的包长成杂物**。规格让一个**已经存在**的包开始装互不相干的东西。判据：这个包能不能一句话说清它是干什么的；说不清，或者要用「和」把三件事串起来，就报。新东西找不到家是 14，不是这条。
    *退化：包名变成了「其他」，新人不知道往哪儿放，于是什么都往里放；这个包此后谁都不敢改，也拆不动。*
16. **导出零件而不是整件事**。规格要求某包导出的是「格式化字节」「拼个路径」「判一下类型」这种小件，而不是「生成主密钥」「执行一次上传」这种整件事。
    *退化：深模块变浅模块。零件一多，复用零件这条路就宽了——AI 想省事时不用再造，拼一拼就行。*
17. **接口变宽**。一个函数十个参数、返回五个值、或要求调用方先调 A 再调 B 再调 C 才能用。整件事的复杂度漏到了调用方。
    *退化：模块深度消失，调用方要懂内部次序，边界形同虚设。*

### 轴四：这张纸自己的毛病（6 条）

这一轴不看实现会怎么抄近路，看规格本身：写反了、写漏了、写多了、给自己开了口子、动到了使用者。18–20 与 23 没有「退化」可答，它们查的就是有没有。

18. **明着违反结构决定**。规格直接写了跟已 accepted 决定相反的话（不是绕开，是反着来）。**逐条照抄原文比对**，指出撞的是哪个编号哪一句。
    *与轴一到三的区别：那三轴是「没说清、实现抄近路」，这一条是「规格明着写反了」。*
19. **验收标准缺**。没有 `Testing Decisions`，也没有能当验收项的清单。撞的是仓库 spec 模板与测试接缝的约定——**「动手前先把『这回测哪个口子』说定，没说定不写测试」**。缺这一节，整份测试决策作废。
20. **边界缺 `Out of Scope`**。撞的是文档规范里那句：「明确的『不做』和明确的『做』一样值钱……**不列，下一个人会当成漏项补上**」。重构期尤其致命：没写「这次不碰配置格式」，执行者某天顺手就改了。
21. **「暂时」「特殊情况」「先这样」「这次例外」**。规格里出现这类措辞，或某条要求只在少数路径生效而没写清边界。
    *退化：例外一旦落地就再没人收回来，而腐蚀都是从一次例外开始的——有一个，就有第二个。*

    **这一条最隐蔽**：它看着是务实，实际是把「做不到」改成「这次可以做」。凡是这类措辞，一律报，不问轻重。
22. **为还没发生的情形多造一样东西**。多留一个没人读的字段、提前把两处长得像的东西抽成一个共用件、为一个用不上的地方先加一层或一个开关。判据：这样东西现在就在用吗；不是，就报。16、17 管形状难看，这条管根本不该存在。
    *退化：「按事实造东西」退成「先留着不亏」；预留一旦免费，往后每个 AI 都会替未来留一手，没人再为以后付账。*
23. **使用者可见面被改**。这次重构的前提是行为不变，而使用者能感知的只有三处：**报错与提示的措辞、配置字段、退出码**。规格里任何一处动到这仨，单独拎出来——不是不许改，是**必须让开发者知道**。

## 三、怎么走

**门槛**：只审文档，不跑程序，不需要测试环境。

**顺序**：先过「零、进门」。判成交接书就直接收尾，不往下走。

**分批**：一次审一个议题（一个 `docs/issues/<slug>/` 目录）。`spec.md` 加全部 `issues/NN-*.md` 一起过，不拆批——工单脱离 spec 判不出结构风险。

**四轴可以并行**，各派一个只读子 agent；也可以一个人顺序过。

**派活时写明**：只做只读分析；判据原文整段贴上（轴名、编号、那句「退化成什么」）；只报命中不给修法；每条带 `file:line`；找不到落点写「无落点」，不许推定。

**规格里没有的，不算命中**（轴四第 19、20 条的「缺某一节」除外——那两条查的就是有没有）。

**二十三项不要求全命中。一项都没中就是没有**——别为了凑输出硬找。反过来，一条规格里同时踩中三条轴，说明它整体方向就偏了，汇总时单说一句。

命中报回来，本节到此为止。怎么处置归下一节。

## 四、汇总

**只归主 agent**。子代理到上一节收尾，这一节它不看。

**先核**：各轴报回来，先回原文核判据。落不到原文的不算。

**再分**：剩下的只有两类——改法唯一的（术语不统一、抄写错、清单重复），不用他点头；其余的，等他拍板。分不出来的按「边界」那条判。

**自己定的当场改**：一次改完，改完不再回头讨论。

**要拍板的写进正文**：这几条才是他看的。自决的那些不进正文，收成末尾一行。

## 五、输出

**两段，没有第三段**：要他拍板的写成正文，自己改的收成末尾一行。他看不过来——正文多一句过程，前面每条都轻一分，最后等于没报。

### 没有命中时

```text
规格审计：<议题名>｜无命中
过了一遍 spec.md 与 N 张工单，四条轴各 0 条。
```

**就这两句，不加别的。** 作者每回都跑这个技能，凑条数等于让后面每一条都失去分量。这轮动过手的，末尾照补一行。

### 有命中时

腐蚀在前，**每条都要能回答「退化成什么」**——答不出的不报（轴四 18、19、20、23 除外，那几条查的就是有没有）。写成不打开文件也能判轻重的样子：原文、撞的是哪条、退化成什么，三段齐。

```text
规格审计：<议题名>｜腐蚀 3 条，纸面 2 条

架构腐蚀
1. 轴一-1 穿站回取
   原文：<spec 或工单原句>（<file:line>）
   撞的是：<结构决定或决策工单的哪一条，照抄原句>（<file:line>）
   退化成：<照这么写之后，哪条约束从「做不到」变成「不该做」>
2. 轴四-21 例外口子
   原文：<…>（<file:line>）
   退化成：<这个例外一旦落地，谁以后还会照着原路走>
3. …

纸面
1. 轴四-19 验收标准缺 —— 全文没有 `Testing Decisions`，也没有可判定的验收项。
2. 轴四-23 使用者可见面 —— 原文：<…>（<file:line>）改的是报错措辞，切换时使用者会看到不一样的提示。

判据不足
- <哪一块结构还没定，因此这一处判不了>
```

**收尾两行，顺序不变**：

```text
过了一遍 spec.md 与 N 张工单，腐蚀 X 条、纸面 Y 条、判据不足 Z 处。
顺手改了：<file> 统一站名；<file> 删掉重复验收项。
```

第一行是分母，对不上说明抽查了几段就交，不是通读。第二行是自决那一类，只列动了哪几处——不解释为什么改，不报子代理交了几条、驳了几条。这轮没动手就只留第一行。

## 边界

- **不给修法，不排优先级**，但每条要说清「退化成什么」——只报问题不给后果，开发者判不了轻重。
- **不判实现**：规格说「要做什么」，不要求它写「放哪个包」。拿包名去卡规格是反的——那会逼规格提前把结构定死。只卡**边界会不会被绕过**这一类必须回答的问题。
- **不查「有没有替开发者拍板」**——那与 `/audit-docs` 一致性轴重复，同一个问题不问两遍。
- **不替开发者选**。两个方案都合理时，把代价摆出来，写「待定」，不推荐。
- **不拿"最佳实践"当判据**。判据只有仓库里的结构决定；通用的分层理论、设计模式一律不作数——那是教科书的意见，不是他的决定。
- 判据没落定就写「判据不足」，不拿常识补位。
- **不把小事推给他定**：只有一种改法的不进正文，自己改掉（判法见「四、汇总」）。
