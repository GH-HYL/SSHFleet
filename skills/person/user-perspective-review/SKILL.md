# 用户视角审查

1. 必须派子代理审，主代理只派单、对照、拍板。

   主代理知道设计为什么这么做，会把设计者的解释当成用户已知，审出来的结论是自己给自己打分。子代理不带上下文，只拿三样输入：用户此刻的目标、界面原文（照抄）、触发时系统的真实状态。多给一样，污染就回来了。

   给它的活只有一句：指出哪句话会让用户理解错，给出改法。不让它评价设计，不让它提需求。

2. 唯一判据：把这句话念给没用过这个东西的人，他能不能复述出「是哪个东西」和「不管会怎样」。

   缺一样就不合格。判据要能当场判——「更友好」「更清晰」不是判据，用户会理解成什么才是。

3. 五问，逐条过，不过就改。

   这个词讲的是系统的内部状态，还是用户看得见的后果？
   这个动作指向用户看得见的东西吗？
   同一屏的数字对得上吗，单位有没有跳？
   第一句回答的是他最担心的那个问题吗？
   他凭什么知道这里能点？

4. 先说「你原来那套还成不成立」，再说变化。

   变化摆在最前面时，人会把陌生内容当成故障证据。详情、提示、列表都按这个顺序。

5. 动词复用产品自己的词，不造新词，不用数据操作词。

   按钮写用户此刻想做的动作，不写维护数据结构。可展开要有静态标记，不能只靠悬停；点了没反应的东西不许出现。

6. 输出只有一张表：位置｜原文｜用户会理解成｜改成。

   末尾一句判据结论，再加一份「故意不改」的条目，防止下一个人照着直觉再改一遍。不写理由，不写过程。

7. 只审表达。

   不审整体体验（会退化成「我觉得」），不审需求该不该做，不改字号间距配色；不确定后果就写「无法确认」，不编。
