# 用户视角审计

1. 审的是**用户使用时的所见所懂**，不是实现。

   做东西的人看的是系统里发生了什么：状态机、内部记录、错误码。用的人只看两件事——我选了什么，它现在管不管用。中间那段实现他既看不见，也不需要知道；凡是只在实现里成立的说法，对他都不成立。

2. 必须换人审，不是换角度想。

   主 agent 知道为什么这么设计，会把设计者的解释当成用户已知，审出来的结论是自己给自己打分。派一个没上下文的子 agent，只给它三样：用户此刻想做什么、原文（照抄）、此时系统的真实情况。多给一样，污染就回来了。

   给它的活只有一句：指出哪句话会让用户理解错，并给改法。不让它评价设计，不让它提需求。

3. 唯一判据：念给没用过这个东西的人，他能不能复述出「是哪个东西」和「不管会怎样」。

   缺一样就不合格。判据要能当场判——「更友好」「更清晰」不算判据，用户会理解成什么才算。

4. 五问，逐条过，不过就改。

   这句话讲的是系统内部的状态，还是用户看得见的后果？
   这个动作指向用户看得见的东西吗？
   同一处的数字对得上吗，单位有没有跳？
   第一句回答的是他最担心的那个问题吗？
   他凭什么知道这里能点？

5. 先说「你原来那套还成不成立」，再说变化。

   变化摆在最前面时，人会把陌生内容当成故障证据。

6. 动词复用产品自己的词，不造新词，不用数据操作词（纳入、应用、提交）。

   按钮写用户此刻想做的动作，不写维护数据结构。可展开要有静态标记，不能只靠悬停；点了没反应的东西不许出现。

7. 输出只有一张表：位置｜原文｜用户会理解成｜改成。

   末尾一句判据结论，再加一份「故意不改」的条目，防止下一个人照着直觉再改一遍。不写理由，不写过程。

8. 只审表达。

   不审整体体验（会退化成「我觉得」），不审需求该不该做，不改字号间距配色；不确定后果就写「无法确认」，不编。
