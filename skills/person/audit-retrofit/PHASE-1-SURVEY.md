# 一、梳理

> 全局约束与段间导航见 [SKILL.md](./SKILL.md)；本文件只讲本段做法。

## 1.1 确认主场

判据看三样：议题目录下有没有 `issues/` 子目录、`git diff` 有没有实现改动、ADR 头部元数据里的「实施载体」写的是「待排期」还是具体路径。三样齐了才是主场。

**只认「代码已落地」这一种形态**：手头只有 ADR、代码零改动的，不归这里；这种需求另走 `audit-docs`。

文档不齐、或还没验收就想跑：问开发者一次。他说强行跑，就按现有材料跑——**本技能不为它降要求，也不保证质量**。

## 1.2 定锚

**基准只取 ADR 的「决定」与「理由」。** 议题文档里的实施方法、行号、清单、勾选状态，全是待审对象。

把 ADR 的「决定」逐条抄成**大方向锚**，编号，随每份提示词下发。开头一句固定：

> 以此为准。议题文档里的具体修法是被审对象，不要被它带偏；发现实现与锚不符，报锚，不要报工单。

**每条锚要标授权来源**：开发者明示的，还是执行者推导的。**推导的那些是重点审对象。**

**锚可以被质疑，但只能单列回报。** 子 agent 发现锚与源码、实测或上游 ADR 对不上，**不许改写锚，也不许并进普通发现**——另起一节「锚质疑」，写清哪条锚、哪份证据、按什么判；改不改锚由开发者定。

## 1.3 盘代码面

- **git 范围**：从议题自述的摸底基准到 HEAD；`git show --stat` 确认主提交的文件面。开发者没说范围就自己定，并在清单里写清理由。
- **代码落点**：哪个模块目录、哪些包被大量改动。
- **复现环境**：有无现成测试机、账号、构建方式。

## 1.4 查既往审计记录

**审过的点不要再审。** 查议题目录有没有 `audit.md`、`findings-*.md`、`audit-run-*/`（本技能的产物目录）、其他历史报告；有就列出来：审过什么、结论是什么、改过没有。

## 1.5 传什么、不传什么

判据：**传「不要怎么走」，不传「路已经走过了」。**

| 类型                           | 传不传               |
| ------------------------------ | -------------------- |
| **被证伪的结论**（试过、错了） | **必传，且标明**     |
| **踩过的坑**（方法错误）       | **传方法，不传结论** |
| **已验证的结论**（测过、对了） | **不传**           |

写法：「X 这个方向已经证伪，原因是 Y，**不要再走**」，而不是「X 已经证伪，所以你只需要验 Z」。

## 1.6 交接清单

产物落议题目录下的 `audit-run-<日期>/`，**不落 `build/`**。里面放 `分发缺口.md`（分发审的缺口清单）、`提示词.md`（下发的提示词包全文，改一次留一版，标 `v1`/`v2`）、`回执/`（各轴回执）、`报告.md`（收尾）。清单六节：

1. **被审对象**——哪些文件、哪些代码，以及「只看不碰」的边界。
2. **关键前提**——是不是主场、文档齐不齐、有没有强行跑的授权。
3. **锚**——ADR 核心主张，编号，标授权来源。
4. **必须知道的背景**——被证伪的方向（含原因）、踩过的坑（只给方法）、已审过的轮次。
5. **建议的审计轴**——按代码结构定，不套模板。
6. **环境与授权**——环境事实（哪台机、工具与解释器版本、账号，写成已核的实测）、授权范围、只读声明。**每条子 agent 指令都要原样复述这些事实**，不许让它自己再摸一遍。
