# 审计架构

> **用途**：审计一份文档（ADR / spec / 工单 / 报告）时，按什么维度看、按什么格式出结论。
>
> **性质**：这是**标准**，不是某一次的审计记录。每次审计的结论落在被审文档的 `## Comments` 或独立审计报告里，**标准本身改动要走约束类文件的同意**（本文件属 `docs/agents/`，按 `AGENTS.md` 的载体约定维护）。
>
> **适用对象**：本仓库内 `docs/` 下的 ADR、spec、工单，以及它们引用的代码事实。

---

## 一、审计要回答的三个问句

审计不是「读一遍提意见」，每一份文档都要能回答下面三问。**任何一问答不上来，就是缺陷**：

1. **它说的是不是事实？** —— 引用的代码行、命令输出、提交号、路径，逐一去核，能对上才算。
2. **它说的是不是该说的？** —— 该写的字段全不全、该界定的边界清不清、该留的证据在不在。
3. **它能不能被下一个人接走？** —— 只拿这份文档、不读对话、不猜上下文，能否知道「要做什么、做到哪算完、为什么这么做」。

## 二、六个审计维度

按「先事实、后形式、再交付」的顺序查。每个维度给出**判据**与**常见问题**。

### 维度 1 · 事实（Fact）

**判据**：文档里每一处**可被外部验证**的断言都成立。

- `file:line` 指向的代码，内容与文档描述一致（行号允许小幅漂移，指到的代码必须对）
- 引用的命令、输出、退出码，照写出来的能复现
- 提交号存在且对得上所述改动
- 术语与 `GLOSSARY.md` 一致（同一概念不出现两个名字）

**常见问题**：
- 行号漂移但**指到的不是那段代码**（比漂移更严重）
- 「全仓 grep 零命中」这类**过强表述**，实际有命中
- 复现命令写得跑不通（路径错、参数缺、环境依赖没交代）

### 维度 2 · 结论（Verdict）

**判据**：每条结论都有**够格的证据**支撑，且证据与结论的强度匹配。

- 推断与实证分清：「实测确认」与「据代码推断」不能混写成同一个肯定句
- 未完成验证的，**明写「未验证」**并给出验证方式，而不是隐去
- 结论不超出证据——一行代码只能证明行为路径，不能证明「不会出问题」

**常见问题**：
- 只看了分支顺序就断言「走不到」（历史上有过：D3 撤销）
- 把「我认为」写成「事实是」
- 证伪失败的方向没记下来，下一个人重新踩

### 维度 3 · 形式（Format）

**判据**：形态符合本仓库载体约定（见 `issue-tracker.md`、`triage-labels.md`、`个人开发规范` 四·3）。

- spec：`Status:` 行、问题陈述 / 方案 / 使用者故事 / 实现决策 / 测试决策 / 不在本次范围 / Comments
- 工单：一条一个文件、编号 `NN-`、`Status:`、`Blocked by:`
- ADR：`状态 / 日期 / 决策人 / 背景 / 决定 / 理由 / 影响 / 备选方案`
- 更新关系：同一决策的细节修正**就地改**；旧决策被取代**加「更新记录」并指过去**，旧文原样保留
- 使用者可见文案：只写当下，不写沿革（「此前是……现已改为……」出现在面向使用者的段落即为缺陷）

**常见问题**：
- 文件名里带状态（`spec-已闭环.md`）
- 自造字段、自造文件名（`handoff`、`final-report`、`open-questions`）
- 计数写死却没随条目增减更新（「现存 9 条」但列了 10 条）
- 废弃段落直接删掉，看不出决策怎么变的

### 维度 4 · 内容（Content）

**判据**：该有的东西一件不缺，且**不多写不该写的**。

**必须有**：
- 问题陈述写清「现在的行为哪里不对、使用者会遇到什么」
- 方案给出**可执行的决定**，不是一个方向词
- 边界：不在范围的、接受的代价、已知的坑，**明写**
- 验收：做到什么程度算完，**可观测**

**不该有**：
- 实现细节混进决策文档（ADR 里写具体改哪个函数）
- 决策文档里出现「待定」却没有指向谁、什么时候定
- 用「按最合理的处理」代替一个选择

**常见问题**：
- 方案只写方向（「改成正则匹配」），不写「多写几条正则枚举」这类可落地的形态
- 受过的代价没写，下一个人重新讨价还价
- 「待定」项没有 owner、没有触发条件

### 维度 5 · 一致性（Consistency）

**判据**：文档之间、文档与代码之间不打架。

- 同一件事在 spec / ADR / 工单 / CHANGELOG 里的说法一致
- 引用关系双向可查：A 说「见 B」，B 确实承载了那个结论
- 移交了的东西在新地方有对应，旧地方有指向
- 计数、编号不重不漏

**常见问题**：
- spec 说「已移交」，新议题里找不到对应条目
- ADR 的决定与 spec 的处置方向各说各的
- 两处写了同一版本号但值不同

### 维度 6 · 可执行性（Actionability）

**判据**：换一个人（或 agent）只拿这份文档，能开工。

- 工单能独立验证：做完有明确的「怎么知道做对了」
- 依赖关系写明：`Blocked by:` 指到的确实还没做完
- 风险与工作量有交代，尤其是重构类改动
- 有歧义时，文档已替人做掉选择，或明确标出「这个要问谁」

**常见问题**：
- 工单没有验收项，做没做完靠感觉
- 重构类改动没写影响面，实施时才发现牵一发动全身
- 接缝没定，测试写在哪全靠猜

## 三、审计结论的格式

审计结论一律按下面格式写，**一条一个条目**，不许合并成一句「整体不错，建议优化」。

```markdown
| # | 维度 | 严重度 | 位置 | 问题 | 依据 | 建议 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 事实 | 高 | spec.md:12 | 引用的 `parse.go:44` 实际是另一段代码 | `parse.go:44` 现为 X，文档描述的是 `:52` | 改行号 |
```

**严重度**：

| 档 | 含义 | 处理 |
| --- | --- | --- |
| **高** | 结论错误或会误导开工 | 必须修，修前不得动工 |
| **中** | 缺关键内容，或形式不合载体约定 | 应修 |
| **低** | 措辞、排版、可选补充 | 可修可不修，需明示 |

**审计报告本身必须包含**：

1. **审的对象与范围**（文件清单、审的时候的提交）
2. **结论表**（按上面格式）
3. **未验证项**（想查但因环境、权限、时间没查成的，明写）
4. **审计者签名**（哪个 agent / 哪一轮，避免把机器意见当作者意见）

## 四、审计的边界

- **审计只提结论，不改文档**。改不改、怎么改，由作者定。
- **不因「看起来更好」就判为问题**（观感类不算缺陷，同 `个人开发规范` 三·2 的取向）。
- **拿不准就标「待作者确认」**，不替作者拍板。
- **红线 4**：审计中发现的本轮范围外问题，只报告、不修。

## 五、审计与复查的关系

| | 审计（本文件） | 复查（`/code-review`） |
| --- | --- | --- |
| 对象 | 文档：ADR / spec / 工单 | 代码改动 |
| 时点 | 文档定稿后、动工前 | 代码写完、交付前 |
| 产出 | 问题表（按上节格式） | 规范符合度 / 规格符合度两轴报告 |

两者**不能互相替代**：文档审计通过，不等于代码正确；代码复查通过，不等于当初的决策站得住。
