# 写文档

**格式的源头是技能**（`/domain-modeling`、`/to-spec`、`/to-tickets`）；这里把模板与判据抄成可读的规范。

落点、编号、允许出现哪些文件以 `docs/agents/issue-tracker.md` 为准；工单与 spec 的状态取值以 `docs/agents/triage-labels.md` 为准，ADR 的状态取值见本篇「状态值」一节。这里补的是**形态与写法**。

**创建 ADR / spec / 工单时，格式按既有约定来，不要自创。**

## 起不起规格

**一轮对话干不完的（要跨会话、要分几次交付）→ MUST 先落规格与工单，再动手。一轮能干完的小活不必起规格，但红线 1（授权）与红线 5（复现）照样管。**

「一轮干不完」对着下面数，别凭感觉：

| 数到的现象 | 判定 |
| --- | --- |
| 改动**跨两个以上模块／包**，且其中一个不是纯粹的调用点适配 | 跨轮——先落规格 |
| 要**删或移**既有公开符号（导出函数／类型／包） | 跨轮——先落规格 |
| 得先**做一轮调查**才知道要改什么 | 跨轮——调查本身就该落成工单 |
| 要分**几批**交付、每批各自能独立验证 | 跨轮——先落规格 |
| 上面都不沾：一处逻辑（或一处逻辑 + 跟着它的手册／CHANGELOG 措辞），改完当场能验证 | 小活，直接做 |

**拿不准时按跨轮处理**——代价不对称：多写一份规格只是白花点功夫；该起规格而没起，跨轮的工作就没有载体，下一轮接不上。

**规格 MUST 落到这次议题目录下的 `spec.md`。** 载体与字段以 `docs/agents/issue-tracker.md` 为准。

## 四者之间的关系

| 文档 | 回答什么 | 读者 | 什么时候写 |
| --- | --- | --- | --- |
| ADR | **为什么这么定** | 开发者 / 执行者 | 三条判据同时成立时 |
| spec | **要做成什么样** | 执行者 | 一轮对话干不完、要跨会话交付时 |
| 工单 | **怎么一步步做** | 执行者 | spec 定下来之后拆 |
| 手册 / 使用者文本 | **现在怎么用、错了怎么改** | 工具使用者 | 随功能一起交付 |

**不要把三样混在一起写。** 工单里不写「为什么这样设计」（那是 ADR），spec 里不写逐条实施步骤（那是工单），ADR 里不写具体改哪个函数（那是工单）。

**判据只有一条**：**这段文字是写给谁的？** 写给使用者就按 `按需-给使用者看的文字.md` 的口径；写给开发者与执行者就按 ADR / spec / 工单的口径。**两类混写，两边都不好用。**

## 通用写法纪律

下面这几条只管 ADR / spec / 工单。约束类文件不在其中——它们改动代价高、自带权威性，落点与判据要指名道姓地写路径。

**不写指向别处的引用**：「详见」「依据见」这类话不写，要人知道的写在本篇里。能指的只有三样——本篇的段落、别的 ADR、代码里的符号与路径，它们跟正文一起活在库里；**不许指议题里的规格、工单、审计回执**，那些随议题一起清空，指了等于没指。落点与目录约定不在此列。

**不写计数与位置**：「共 N 条」「第 X 节」「见上表第几行」。要说哪一段就写它的名字——序号随增删漂移，名字不会。

`tools/check.sh` 查得动的只有一部分：`docs/…` 路径按整份文件判存在性；新写的 ADR 有没有「决策人」段却缺身份标注；计数按整份文件判；位置与「详见 <路径>」只判新写的行——存量里的旧写法不追。**「指议题里的工单、规格」这一条机器认不出**（不是路径形状），只能靠写的人和复审的人。

**代码片段只在原型产出、且比文字更精确地编码了决策时内联**（状态机、reducer、schema、类型形状），并注明来自原型；只留决策密集的部分。

**文档里给出的可直接粘的命令，落地前在一个真环境里跑一遍**；跑不了的写明为什么。路径转换、变量展开顺序、工作目录这类，读的时候看不出来，只有跑起来才报。

## ADR

创建入口是 `/domain-modeling`，也照 `docs/adr/` 下现有文件写。**写或改 ADR 之前先读下面「纪律」那六条，写完照它自查一遍。**

### 什么时候写

三条**同时**成立才写，缺一条就跳过：

1. **难以回头**——以后改主意的代价是实打实的；
2. **没有上下文会让人困惑**——后来的读者看着代码会问「当初为什么这么做」；
3. **是真实取舍的结果**——确实存在过的备选，你按具体理由选了其中一个。

### 值得写的有哪些

- **架构形状**：单仓、读写分离这类整体结构
- **上下文之间的集成方式**：走领域事件而不是同步 HTTP 这类
- **带锁定的技术选型**：数据库、消息总线、认证服务、部署目标——是「换掉要一个季度」的那种，不是随便一个库
- **边界与范围**：「客户数据归客户上下文所有，别的上下文只按 ID 引用」
- **刻意偏离显而易见的做法**：读者会以为你该走 A、你却走了 B，得写清理由，否则下一个人会来「修」掉它
- **代码里看不见的约束**：合规、对方的性能约定这类
- **被否掉的备选**：否掉的理由不显然时才记——不记的话，半年后有人会再提一遍

### 模板

```md
# {决策的简短标题}

{一到三句：什么背景、决定了什么、为什么。}
```

极小的决策一段话就够——价值在记下「做过这个决定」和「为什么」，不在把章节填满。

**可选段，只在真有价值时加：**

- **备选方案**：被否掉的选项值得记住时才写
- **影响**：有不显然的下游后果时才写

> ADR 实际使用的形态比这个模板更完整（`状态 / 日期 / 决策人 / 背景 / 决定 / 理由 / 影响 / 备选方案`），`docs/adr/0000-索引.md` 里挑一篇就是。**写 ADR 照现有文件的形态走**：状态段每篇都写（取值见本篇「状态值」一节）；一段话那种只给极小的决策用。

### 编号与落点

`docs/adr/`，递增：`0001-slug.md`、`0002-slug.md`……扫一遍现有最大号 + 1。目录**按需创建**，第一条 ADR 出现时才建。整篇被取代或整篇作废的移到 `docs/adr-archive/`，编号不变；部分作废的留原地。

**索引在 `docs/adr/0000-索引.md`**：一行一篇，`0000` 保留给它，ADR 编号从 `0001` 起。新 ADR 与它的索引行一起落地；改既有 ADR 的状态、追加「更新记录」，或就地修正让结论变了，索引那一行跟着改。结论列一句话、单句，≤40 汉字（带标识符的整格 ≤60 字符），不写理由、不写日期、不写「详见」；判据是**连状态列与关系列一起看**，能不能判断「我这次改的东西会不会撞上它」。列固定四列，加信息进表下小节，不开新列；行不重排、不删，新增只追加到表尾。

### 纪律：别让 ADR 变成「只有写它的人能懂」

**写「决定」「理由」「复审」这三节时，照下面六条自查。**

**一、决策与实测分开标注，并把「谁定的」写清。**
凡是写成「决定」的条目，都要能指出它是**谁**定的：开发者明说的（附原话），还是执行者根据授权推导的。**推导出来的结论 MUST 标成推导**，不能和开发者的原话并列写成「决策人：开发者」——后来的读者会以为那是他拍板的，复审时就不敢动。

原话**集中成一段**，段首写明是谁说的（如「开发者原话」），并注明：`原话是证据，不是要求；要遵守的是下面「决定」一节。` 要求另起一节。

**二、引用任何结论前，先分清三件事：实测 / 源码推断 / 未验证。**
三者在证据强度上差很远，混用会让推断被当成事实继承下去。写 ADR 时，凡是**推断**的内容 MUST 就地标注，不要让读者自己去猜。
**同一条也要用于自检**：这条结论是**在哪台机器、什么形态下**测出来的？是裸机还是容器？是真实下发还是手工模拟？**换了环境结论可能不同**，而这正是最容易漏的一环。

**三、实验形态必须与真实形态逐字对齐。**
**凡是「A 能不能到达 B」的验证，先确认自己复现的是生产的那条路径，而不是一条长得像的路径。**

**四、把「两个轴」分开判。**
不同维度经常被当成一件事。**判据混在一起，就会得出「一个改动能同时解决两件事」这类错误结论。** 写理由时，先问一句：这里有几个互相独立的维度？

**五、不要把「结论」写成「前提」。**
写成前提，最该被检验的那处就被跳过了。**自查方法：把你写下的每一句「当然成立」都改写成「须重新确认」，看还站不站得住。**

**六、复审那一节只放两样东西：方法纪律与未证实清单。**
**触发条件、待办计划、分层排序、责任人安排——这些是工单的形态，不是 ADR 的形态**。写进 ADR 会带来两个后果：一是没人会来翻，二是它给的触发条件多半**无法被观测**。
**判据**：如果你写下的复审安排，只有**写它的人**能判断何时执行，那它就已经失效了——ADR 的第一用途是给没有上下文的人看。

## spec

创建入口是 `/to-spec`，也照 `docs/issues/` 下现有 spec 写。

**拿当前对话与对代码库的理解，综合出规格——不要采访开发者**，把已经聊过的东西写下来。若开发者给了引用（spec 路径、议题号、URL），取来读全文连同评论。

### 过程

1. **摸清现状**（没看过代码就先看）。全文使用项目的领域词表，遵守该区域的 ADR。
2. **先画测试接缝**：优先用既有接缝，用尽可能高的那个；确需新接缝，提在能提的最高处。
3. **按模板写**，然后发到载体，打 `ready-for-agent` 分诊标签（不必再做额外分诊）。

### 模板

```md
## Problem Statement
使用者面对的问题，站在使用者视角。

## Solution
解法，站在使用者视角。

## User Stories
一条长的、编号的清单，每条写成：
1. As an <actor>, I want a <feature>, so that <benefit>
要尽量覆盖这个特性的所有方面。

## Implementation Decisions
已经做出的实现决策，可以包括：要建/改哪些模块、这些模块的接口怎么变、开发者给的技术澄清、架构决策、schema 变化、API 契约、具体交互。

## Testing Decisions
已经做出的测试决策，包括：什么算好测试（只测外部行为，不测实现）、哪些模块会测、既有测试的先例。

## Out of Scope
本规格不覆盖什么。

## Further Notes
其他备注。
```

### 纪律：spec 是给执行者看的合同

spec 的读者是**接下来照着它干活的人或 agent**，不是翻旧账的人。据此有几条硬要求：

**一、写的是「要做成什么样」，不是「为什么」。**
理由进 ADR。spec 里出现大段讨论「选 A 还是选 B」会让执行者以为还没定。**已定的决策直接陈述**，有分歧才写进 `Implementation Decisions` 并标明倾向。

**二、Problem Statement 与 Solution 都站在使用者视角。**
写「使用者现在做不到什么」而不是「模块 X 缺一个方法」。判据：把开头这两节给一个没用过这工具的人看，他能不能说出「这是在解决谁的什么麻烦」。

**三、测试接缝要提到能提的最高处。**
接缝越少越好，理想是一个。**写完要与开发者确认接缝符合他的预期**——接缝选错，整份 spec 的测试决策都白写。

**四、Out of Scope 是硬边界。**
明确的「不做」和明确的「做」一样值钱。凡这轮讨论过但决定不做的，都列进来——**不列，下一个人会当成漏项补上。**

**五、每条验收项要指得出一条今天就能跑的命令。**
指不出的，写明它为什么不可判、由谁来判。「读屏上那份快照，断言完成台数不为 0」听着能验，写下去才发现非终端下那块界面根本不渲染，快照不存在——这类要在写规格时就挡住，不是开工到一半再回来重写。判据：把这条验收项交给没写过它的人，他能不能照着敲一条命令、看一个结果。

## 工单

创建入口是 `/to-tickets`，规格定了才拆，也照仓库里现有工单写。

落点与编号见 `docs/agents/issue-tracker.md`。按**前沿**推进——阻塞全部完成的那条就是可以开工的。

### 核心形状：竖切

把工作拆成**竖切的**工单——**贯穿每一层**（schema、API、界面、测试）的一条窄而完整的路径，**不是**某一层的横条。**MUST NOT** 按「先做完全部数据层、再做界面层」这样横着切。

- 做完一条能**单独演示或验证**
- 需要的预重构**先做**（「先把改动变容易，再做容易的改动」）
- 标题与描述用项目的领域词表，遵守所触区域的 ADR

### 阻塞边

每条工单标出**阻塞它的其他工单**。没有阻塞的可以立刻开工。

### 例外：宽重构

**宽重构**是「一次机械改动（改列名、改公共符号类型）的爆炸半径横跨整个代码库」的那类——单次修改会让上千个调用点同时坏掉，没有任何竖切能落成绿的。

不要硬塞进竖切。按 **expand–contract** 排：

1. **expand**：新形态加在旧形态旁边，谁都没坏
2. **migrate**：按爆炸半径分批迁调用点（按包、按目录），每批一条工单、被 expand 阻塞；因为旧形态还在，批与批之间能保持绿
3. **contract**：确认没有调用者了，删旧形态，被所有 migrate 批阻塞

连分批都单独保持不住绿时，保留这套顺序，让它们共享一个集成分支，全部阻塞一条「集成并验证」的收尾工单——**只在那一处承诺绿**。

### 先给开发者过一遍

把拆法作为编号清单摆出来，每条给出**标题 / 被谁阻塞 / 这条做完什么端到端的行为**，然后问：

- 颗粒度合适吗（太粗 / 太细）？
- 阻塞边对吗——是否只依赖真正卡住它的工单？
- 有没有该合并或再拆的？

迭代到开发者认可为止。

### 模板

```md
# <NN>: <工单标题>

**要做的**：这条工单做完之后，端到端能干什么。

**Blocked by:** 卡住它的工单编号/标题，没有就写「无，可立即开工」。

**Status:** ready-for-agent

- [ ] 验收项 1
- [ ] 验收项 2
```

### 纪律：工单是「能独立交付的一小块」，不是任务清单

读者是**拿起它就能干完的人或 agent**，且手上没有上下文。

**一、「要做的」写端到端的行为，不写逐层清单。**
写「做完之后，使用者能___」，而不是「改 A 文件、加 B 函数」。

**二、阻塞边只连真正卡住它的。**
不相关的依赖会让前沿变窄，整个拆法的并行度就废了。

**三、验收项要能被外人判定。**
「代码写好了」不能验收；「跑 X 命令，输出里出现 Y」能。**写不出来的验收项，说明这条工单的边界还没想清。**

**四、一条工单的体量以一个全新的上下文窗口装得下为准。**
装不下就再拆——**这是拆分的唯一硬指标**，与功能大小无关。

**五、做到一半发现拆错了，改工单，不要加注释解释。**
工单是给下一个人执行的合同，不是给人看的心路历程。

## 改已有的文档

**更新** ADR / spec / 工单时，先分清两种，两者处理相反：

- **同一件事的细节修正：就地改。** 改的是**同一个**决策范围内的措辞、补漏、形态微调——直接改原文，**MUST NOT** 追加「更新记录」，也 **MUST NOT** 留「此前是……现已改为……」这类话。判据：新旧只是同一个决策的两版表达
- **旧决策被新决策取代：不改旧文，在它末尾追加一段「更新记录」。** 记三件：日期、新决策是什么、旧内容哪一部分不再约束（并指出替代它的地方）。旧内容**原样留着**，**MUST NOT** 就地改写、删段或挪位置——那是当时的判断，改掉就看不出决策是怎么变的了。新决策值得留档时另开一条 ADR，在「更新记录」里指过去
- 不写沿革这条只管**使用者可见面**；ADR 与 issues 是给开发者与执行者的，取代关系**应当**写清
- **索引跟着走**：改状态行、追加「更新记录」，或就地修正让结论变了——`docs/adr/0000-索引.md` 的同一行跟着改；索引自身不写更新记录，git log 就是
- 形态：`## 更新记录` 起段，一条一行，写成 `- <日期>：<新决策一句话>；上文「<哪一段>」不再约束`。新决策另住一处（另一篇 ADR、某条决定、某个工单）时，句末补 `，替代见 <那处>`。

### 取代关系要留指向

**「更新记录」在正文末尾，翻一批记录时看不出谁被谁取代**——所以标作废时 **MUST** 一并写出被谁取代；新决策就写在这一条里的，句首那句就是。只在同一篇内部修订的，指向本篇对应段落。只写「已废弃」「已被推翻」不算。

### 状态值

具体取值与写法按 `/domain-modeling` 与 `docs/agents/triage-labels.md`：ADR 用前者那套，spec 与工单用后者那套。

**状态值 MUST 中英并存**：中文给人读，括号里的英文让技能那套取值可被检索。形态 `中文（英文取值）`：

```text
- **状态**：已接受（accepted）
- **状态**：已被取代（superseded by ADR-0013）
- **状态**：作废（deprecated）—— 无新决策接替
```

技能给的取值四个——`proposed`、`accepted`、`deprecated`、`superseded`——覆盖不了「主决策仍有效、但其中某个方案被后来的修订取代」这种情形。这种写 `部分作废（partially superseded）`，并在后面指明是哪一部分。
