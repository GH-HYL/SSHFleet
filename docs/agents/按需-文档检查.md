# 文档检查

**管的是改一份已经写成的约束类文件**：`docs/agents/` 下全部、`AGENTS.md`、技能正文。ADR、spec、工单的改法在 `按需-写文档.md`，两者相反——那边允许「更新记录」，这边不许留沿革。

机器查得动的走 `bash tools/check.sh --docs`（查哪四样见它文件头），这一篇只管它查不动的。

**顺序固定：先问该不该动，再删，再改，最后才加。** 换过来，就会拿新内容盖住该删的那一处。

## 一、该不该动

三问，顺序不能换：

| 问 | 过不了 |
| --- | --- |
| 服务谁：写给执行者照做的，还是给开发者拍板的 | 按读者的口径写；两类混写，两边都不好用 |
| 有没有普适性：只碰上一次的现场算不算 | 不算，留在议题里 |
| 配不配这个身份：判据该住哪儿 | 判据住仓库，取判据的步骤住技能；写错地方就多一份要维护的副本 |

**举例最容易在第三问翻车。** 通用文件里的例子会被读成引用——下一个人照着那个编号去找，找不到，或者找到的是另一个项目的东西。通用文件只说形状：「文档规范里那句」，不写「`docs/x.md` 三、3」。自查一句：把这份文件搬到另一个仓库，这句还成不成立？不成立，就是借当前项目举了例。

## 二、删

- **废话。** 判据在 `必读-总则.md`，查法分两类：叙述与解释（不像条目那样自带边界，最容易掺）；条目里描述事情时绕圈（整条不算废话，但一句能压成几个字而没压）。
- **沿革。** 总则已经禁了，这里补处置：改写时把旧的那句直接替掉，不留痕。旧口径与现行口径在一份文件里并存，下一个人分不清哪句还作数，最后只能两份都当判据。
- **过程。** 只留最终定下的，不留当时怎么想的。过程留着，后来的人会拿被否掉的方案去反驳现行结论。要留过程，留在议题目录。
- **写出别节的话。** 一句跨到别节，就跟别处同类规定重复——重复不会严丝合缝，总会偏一点，改一次多一个矛盾源。写完回看：这句在别处是不是已经说过。

## 三、改

- **先认清要的是什么，别照着说的硬改。** 他说的做法不等于他要的结果：做法聊着聊着会变形，目的不会。为了「按他说的改」改掉了他真要的东西，是最常见的跑偏。
- **先读上下句和整节的主题。** 单看一句觉得不通，往往是它靠着上下文才成立；照着眼前这句改，改完自己顺了，整段反而断了。硬改的样子：句子单拿出来挑不出毛病，放回原位却跟前后说的不是一件事。
- **精简不靠字数。** 同一条约束写三行与写一行，判据一样多，多出来的两行只是让人以为说清了；字数一撑，虚的地方反而看不出来。判据没变，就是该删。
- **碰上数字顺手核。** 记忆里的数写的时候对，环境一变就错，还错得看不出来。改文档时遇上已有的数字，跑一遍命令取个现值，比另开一轮便宜。

## 四、加

- **收 AI 会忘的，不收常识。** 判据是「它会不会想不起来」，不按学科分。深模块、错误分层、命名一致都是行规，每样都能忘；「函数要有名字」是真常识，写进去纯占地方。
- **不靠列举，写禁止的形态。** 「列出来的都合规」与「没列的都合规」是两码事：前者要求穷举，漏掉的那处成了合法出口，而漏掉的位置永远比想到的多。反过来定一条禁止形态，让全部情况落进去——「某形式只许一处出现」，不用数有多少处。
- **每条都想一遍绕法。** 判据不是「这句话对不对」，是「照它写会被怎么绕过」：呈现效果一样、底下实现分叉，就是绕过。想不出绕法的，八成没对着问题，或者本该交给工具管。
- **能用术语就用。** 术语是打包好的钩子：看见「深模块」「竖切」，边界、例外、违反形态自动被勾起来。自造说法要绕一圈才说得清，写到第三处含义已经各不一样，而没人觉得需要回头统一。
- **过得了时间。** 三问：明年还成立吗；量级变了还成立吗；换个人照着判，判得一样吗。有一问答不上，记下的就是这一次的现场，不是规矩。
