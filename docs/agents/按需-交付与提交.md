# 交付与提交

## 交付要验过

报「做完了」时 **MUST** 真的跑一遍：能跑的命令跑一次，看改前红、改后绿。

报告里一句话说清跑了哪条、结果如何即可，不必贴整段输出；**MUST NOT** 只写「已修复」「已实现」。

## 交付前核验文档状态

报「做完了」之前，把这一轮碰过的 spec 与工单的 `Status:` 行、ADR 的「状态」行**更新到与实际相符**。做完的工单不该还挂着 `ready-for-agent`（下一轮的人会照着它重做一遍），动过的规格不该停在原状态。

**判据是这一轮的结论有没有落回它该在的地方**——四样各去哪，按 `按需-写文档.md` 的「四者之间的关系」。

## 提交

- 提交信息**必须中文**，一行 `类型(可选作用域): 简短描述`；类型 `feat` / `fix` / `refactor` / `docs` / `chore` / `style` / `test`。功能完成且文档整理完毕后自动提交
- 标题只写「做了什么」；「为什么」放正文，一到两句，只写从 diff 里看不出来的（为什么这么选、放弃了什么、踩过什么坑）
- **提交前有闸门**：新机器先跑一次 `bash tools/install-hooks.sh`。被拒就修，不许用 `--no-verify` 绕；查什么见 `tools/check.sh` 的文件头

## CHANGELOG 与版本号

**只记使用者能直接体验到的**功能新增、体验优化、问题修复。**不记**：内部代码符号（函数／变量／模块／文件名）、实现细节与重构拆分、测试与构建工具链。

**改代码时只动 CHANGELOG 这一处**：在 `CHANGELOG.md` 顶部 `## 未发布` 下找到或新建当天的三级标题（`### yyyy-MM-dd`），条目写在其下，依次按 `#### Added` 新增、`#### Changed` 用法或观感变了、`#### Fixed` 修掉的问题、`#### Removed` 撤掉的东西分类，当天没有的那类不写标题——与已发布的段同一套。**只看前 100 行，MUST NOT 全读。** 条目只留最终形态——同一天改了几茬就改当天那一节，**MUST NOT** 追加平行条目，也 **MUST NOT** 把过程写进去；一件事实在变大了就另起一条，**MUST NOT** 把两件事糅进一句。相对上一版变了什么、为什么改，照常写进去。

**MUST NOT** 动版本段头、入口文件的版本常量、git tag——版本号由开发者发布时定：跑 `python tools/release/release.py`，选个档位，脚本在最近一次发布的号上加一。执行者不参与。

**程序里的版本**：帮助信息单列一行 `版本: v<号>+<短提交号> (<提交时间>)`，号只从入口常量取；构建标识自动注入，**MUST NOT** 手工维护或由脚本注入。问「这是哪一次代码」以构建标识为准。
