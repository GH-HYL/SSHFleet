# 文档格式规范（ADR / spec / 工单）

> **为什么有这一份**：格式的源头是技能（`/domain-modeling`、`/to-spec`、`/to-tickets`），但那几个技能里有设了 `disable-model-invocation` 的，**那部分执行者调不到**。本文件把技能里的模板与判据抄成可读的规范，让执行者不靠调用也能照办。
>
> **上游不是本文件**：技能原文在 `/domain-modeling`、`/to-spec`、`/to-tickets` 三个技能自带的模板文件里（`ADR-FORMAT.md`、`SKILL.md`）。技能更新后本文件可能落后——**有出入时以技能原文为准**。
>
> **本仓库的载体约定另有其文**：落点、编号、状态取值、允许出现哪些文件，见 `issue-tracker.md` 与 `triage-labels.md`；本文件只管**内容形态**。

## 一、ADR

### 什么时候写

三条**同时**成立才写，缺一条就跳过：

1. **难以回头**——以后改主意的代价是实打实的；
2. **没有上下文会让人困惑**——后来的读者看着代码会问「当初为什么这么做」；
3. **是真实取舍的结果**——确实存在过的备选，你按具体理由选了其中一个。

容易回头的决策不写（反正会改）；不让人困惑的不写（没人会问）；没有备选的项不写（只是「做了显而易见的事」）。

### 值得写的有哪些

- **架构形状**：单仓、读写分离这类整体结构
- **上下文之间的集成方式**：走领域事件而不是同步 HTTP 这类
- **带锁定的技术选型**：数据库、消息总线、认证服务、部署目标——是「换掉要一个季度」的那种，不是随便一个库
- **边界与范围**：「客户数据归客户上下文所有，别的上下文只按 ID 引用」——**明确的「不做」和明确的「做」一样值钱**
- **刻意偏离显而易见的做法**：读者会以为你该走 A、你却走了 B，得写清理由，否则下一个人会来「修」掉它
- **代码里看不见的约束**：合规、对方的性能约定这类
- **被否掉的备选**：否掉的理由不显然时才记——不记的话，半年后有人会再提一遍

### 模板

```md
# {决策的简短标题}

{一到三句：什么背景、决定了什么、为什么。}
```

**就这么多。** ADR 可以只是一段话。它的价值在于记下「做过这个决定」和「为什么」，不在于把章节填满。

### 可选段（只在真有价值时加）

- **状态**：`proposed | accepted | deprecated | superseded by ADR-NNNN`——决策会被重新翻出来时才需要
- **备选方案**：被否掉的选项值得记住时才写
- **影响**：有不显然的下游后果时才写

### 编号与落点

`docs/adr/`，递增：`0001-slug.md`、`0002-slug.md`……扫一遍现有最大号 + 1。目录**按需创建**，第一条 ADR 出现时才建。

> 本仓库现状：ADR 实际使用的形态比技能模板更完整（`状态 / 日期 / 决策人 / 背景 / 决定 / 理由 / 影响 / 备选方案`），见 `docs/adr/` 下现有文件。**写 ADR 照现有文件的形态走**，技能模板是下限不是上限。

### 纪律：别让 ADR 变成「只有写它的人能懂」

**写 ADR 时，尤其是写「决定」「理由」「复审」这三节时，照下面六条自查。** 它们都来自这个仓库真实踩过的坑，不是通用道理。

**一、决策与实测分开标注，并把「谁定的」写清。**
凡是写成「决定」的条目，都要能指出它是**谁**定的：开发者明说的（附原话），还是执行者根据授权推导的。**推导出来的结论 MUST 标成推导**，不能和开发者的原话并列写成「决策人：开发者」——后来的读者会以为那是他拍板的，复审时就不敢动。

**二、引用任何结论前，先分清三件事：实测 / 源码推断 / 未验证。**
三者在证据强度上差很远，混用会让推断被当成事实继承下去。写 ADR 时，凡是**推断**的内容 MUST 就地标注，不要让读者自己去猜。
**同一条也要用于自检**：这条结论是**在哪台机器、什么形态下**测出来的？是裸机还是容器？是真实下发还是手工模拟？**换了环境结论可能不同**，而这正是最容易漏的一环。

**三、实验形态必须与真实形态逐字对齐。**
一次真实教训：判断「`export` 的环境变量能否穿过 `sudo`」时，把实验写成「`sudo` 套 `sudo`」、变量在**外层 sudo 之后**才设置——测的其实是另一件事，结论与事实相反。**凡是「A 能不能到达 B」的验证，先确认自己复现的是生产的那条路径，而不是一条长得像的路径。**

**四、把「两个轴」分开判。**
不同维度经常被当成一件事。真实教训：「提示语是哪种语言」与「字符按字节还是按字符计」是两个轴，一个 locale 取值可以在第一个轴上满足、在第二个轴上退化。**判据混在一起，就会得出「换一个值能同时解决两件事」这类错误结论。** 写理由时，先问一句：这里有几个互相独立的维度？

**五、不要把「结论」写成「前提」。**
真实教训：ADR 的立论之一是「某取值永远可用」，而这句话本身是**结论**、有待验证。把它写成复核时不必再问的前提，正好让它最该被检验的地方被跳过。**自查方法：把你写下的每一句「当然成立」都改写成「须重新确认」，看还站不站得住。**

**六、复审那一节只放两样东西：方法纪律与未证实清单。**
**触发条件、待办计划、分层排序、责任人安排——这些是工单的形态，不是 ADR 的形态**（见本文件 5.1 的三类输出）。写进 ADR 会带来两个后果：一是没人会来翻，二是它给的触发条件多半**无法被观测**（真实教训：有一版写了六条触发条件，其中五条依赖工具根本不采集的信息）。
**判据**：如果你写下的复审安排，只有**写它的人**能判断何时执行，那它就已经失效了——ADR 的第一用途是给没有上下文的人看。

## 二、spec

### 怎么写

拿当前对话与对代码库的理解，**综合出规格**——**不要采访开发者**，把已经聊过的东西写下来。若开发者给了引用（spec 路径、议题号、URL），取来读全文连同评论。

### 过程

1. **摸清现状**（没看过代码就先看）。全文使用项目的领域词表，遵守该区域的 ADR。
2. **先画测试接缝**：优先用既有接缝，用**尽可能高**的那个；确需新接缝，提在能提的最高处。接缝越少越好，理想是一个。**跟开发者确认这些接缝符合他的预期。**
3. **按模板写**，然后发到载体，打 `ready-for-agent` 分诊标签（不必再做额外分诊）。

### 模板

```md
## Problem Statement
使用者面对的问题，站在使用者视角。

## Solution
解法，站在使用者视角。

## User Stories
一条长的、编号的清单，每条写成：
1. As an <actor>, I want a <feature>, so that <benefit>
要尽量覆盖这个特性的所有方面。

## Implementation Decisions
已经做出的实现决策，可以包括：要建/改哪些模块、这些模块的接口怎么变、开发者给的技术澄清、架构决策、schema 变化、API 契约、具体交互。
不要写具体文件路径与代码片段——它们很快就会过期。
例外：原型产出的片段若比文字更精确地编码了某个决策（状态机、reducer、schema、类型形状），可内联并注明来自原型；只留决策密集的部分，不是能跑的小样。

## Testing Decisions
已经做出的测试决策，包括：什么算好测试（只测外部行为，不测实现）、哪些模块会测、既有测试的先例。

## Out of Scope
本规格不覆盖什么。

## Further Notes
其他备注。
```

### 纪律：spec 是给执行者看的合同

spec 的读者是**接下来照着它干活的人或 agent**，不是翻旧账的人。据此有几条硬要求：

**一、写的是「要做成什么样」，不是「为什么」。**
理由进 ADR。spec 里出现大段讨论「选 A 还是选 B」会让执行者以为还没定。**已定的决策直接陈述**，有分歧才写进 `Implementation Decisions` 并标明倾向。

**二、Problem Statement 与 Solution 都站在使用者视角。**
写「使用者现在做不到什么」而不是「模块 X 缺一个方法」。判据：把开头这两节给一个没用过这工具的人看，他能不能说出「这是在解决谁的什么麻烦」。

**三、测试接缝要提到能提的最高处。**
接缝越少越好，理想是一个。**写完要与开发者确认接缝符合他的预期**——接缝选错，整份 spec 的测试决策都白写。

**四、Out of Scope 是硬边界。**
明确的「不做」和明确的「做」一样值钱。凡这轮讨论过但决定不做的，都列进来——**不列，下一个人会当成漏项补上。**

## 三、工单

### 核心形状：竖切

把工作拆成**竖切的**工单——**贯穿每一层**（schema、API、界面、测试）的一条窄而完整的路径，**不是**某一层的横条。

- 做完一条能**单独演示或验证**
- 每条的大小以**一个全新的上下文窗口装得下**为准
- 需要的预重构**先做**（「先把改动变容易，再做容易的改动」）
- 标题与描述用项目的领域词表，遵守所触区域的 ADR

### 阻塞边

每条工单标出**阻塞它的其他工单**。没有阻塞的可以立刻开工。

### 例外：宽重构

**宽重构**是「一次机械改动（改列名、改公共符号类型）的爆炸半径横跨整个代码库」的那类——单次修改会让上千个调用点同时坏掉，没有任何竖切能落成绿的。

不要硬塞进竖切。按 **expand–contract** 排：

1. **expand**：新形态加在旧形态旁边，谁都没坏
2. **migrate**：按爆炸半径分批迁调用点（按包、按目录），每批一条工单、被 expand 阻塞；因为旧形态还在，批与批之间能保持绿
3. **contract**：确认没有调用者了，删旧形态，被所有 migrate 批阻塞

连分批都单独保持不住绿时，保留这套顺序，让它们共享一个集成分支，全部阻塞一条「集成并验证」的收尾工单——**只在那一处承诺绿**。

### 先给开发者过一遍

把拆法作为编号清单摆出来，每条给出**标题 / 被谁阻塞 / 这条做完什么端到端的行为**，然后问：

- 颗粒度合适吗（太粗 / 太细）？
- 阻塞边对吗——是否只依赖真正卡住它的工单？
- 有没有该合并或再拆的？

迭代到开发者认可为止。

### 发布

- **本地文件**：`docs/issues/<feature-slug>/issues/<NN>-<slug>.md`，**一条一个文件**，按依赖顺序从 `01` 编号（阻塞者在前），**绝不合并成单个文件**
- 按**前沿**推进：阻塞全部完成的那条就是可以开工的

### 模板

```md
# <NN>: <工单标题>

**要做的**：这条工单做完之后，端到端能干什么——站在使用者视角，不是逐层的实现清单。

**Blocked by**：卡住它的工单编号/标题，没有就写「无，可立即开工」。

**Status**：ready-for-agent

- [ ] 验收项 1
- [ ] 验收项 2
```

**不要写具体文件路径与代码片段**——它们过期得很快。例外同 spec：原型产出的、比文字更精确编码决策的片段可以内联并注明。

### 纪律：工单是「能独立交付的一小块」，不是任务清单

读者是**拿起它就能干完的人或 agent**，且手上没有上下文。

**一、「要做的」写端到端的行为，不写逐层清单。**
写「做完之后，使用者能___」，而不是「改 A 文件、加 B 函数」。

**二、阻塞边只连真正卡住它的。**
不相关的依赖会让前沿变窄，整个拆法的并行度就废了。

**三、验收项要能被外人判定。**
「代码写好了」不能验收；「跑 X 命令，输出里出现 Y」能。**写不出来的验收项，说明这条工单的边界还没想清。**

**四、一条工单的体量以一个全新的上下文窗口装得下为准。**
装不下就再拆——**这是拆分的唯一硬指标**，与功能大小无关。

**五、做到一半发现拆错了，改工单，不要加注释解释。**
工单是给下一个人执行的合同，不是给人看的心路历程。

## 四、手册与说明性文档

**手册的读者是工具使用者，不是维护者。** 这一条的推论比想象中多：

**一、手册不写沿革。**
「此前是……」「现已改为……」这类话**MUST NOT** 出现，因为使用者只关心「现在怎么用」。**新增功能按「它本来就这样」写。** 沿革留在 CHANGELOG、ADR、提交信息里。

**二、手册不写实现过程。**
「实验形态」「源码推断」「实测发现」都不该出现在手册里。使用者要的是结论，不是取证过程。

**三、手册的每一句都要能照着做出一个动作。**
判据：这句话是让使用者「做什么」，还是让他「知道什么」？只说「知道」而不说「做什么」的段落，要么补上动作，要么删。

**四、示例必须真跑过。**
手册里的每一条命令、每一份配置样例，**MUST** 能原样复制粘贴跑通。**写不出来就跑一遍再贴**——示例是使用者照抄的第一处来源，错了比没有更糟。

**五、常见问题按「症状」组织，不按「原因」组织。**
使用者是先看到现象才来翻手册的，他搜的是「乱码」「连不上」，不是「locale 未生成」。

## 五、面向使用者的文本（不止手册）

**这一节管**：程序的帮助文本、报错信息、运行提示、配置注释、终端输出。**它们与手册同一受众，按同一套口径写。**

### 5.1 区分三类输出

不是所有输出都给使用者看，写文案前先分清：

| 类型 | 例 | 读者 | 怎么写 |
| --- | --- | --- | --- |
| **使用错误**（参数用错、配置写错、前置条件不满足） | 「`-f` 指定的文件不存在；提示：把节点写进 CSV，再用 `-f` 指向它」 | 使用者 | **按下面 5.2 的口径写**，因为它给使用者看 |
| **程序缺陷**（不该发生的事发生了） | panic、`nil pointer`、内部断言失败 | 维护者 | 保留原文与现场，**不要包装成好听的话**——砍掉信息反而增加排查成本 |
| **运行结果**（命令执行成功与否） | 退出码、失败分类 | 使用者（看结论）+ 维护者（看原文） | 结论用使用者语言，原文原样保留不裁剪 |

**判据**：这段文字出现时，**使用者能做点什么吗**？能做 → 属第一类，按使用者口径；只能交给维护者 → 属第二类，保留现场。

### 5.2 使用者可见文本的四条硬要求

**一、站在使用者那边写，不站开发者角度。**
假定读者没看过源码。凡是要靠内部知识才看得懂的说法（模块名、函数名、库名、内部步骤、行话），一律换成他的语言。
**自查**：把这句话给一个没用过这工具的人看，他知不知道下一步做什么？

**二、简洁干练准确，不写解释与铺垫。**
判据：删掉这句，使用者不会少知道一件他需要知道的事，就删。
反面例子：先讲机制再讲怎么做。写成「怎么做 + 为什么这样做才对你有用」，不铺垫机制。

**三、只写当下，不写沿革。**
约束类文件（本规范、`AGENTS.md`、`docs/agents/` 下的口径）、技能正文、使用者可见的提示与手册，**MUST NOT** 出现「此前是……」「现已改为……」「原『X』」这类话。读者只该知道现在是什么。

**四、说清「怎么改」，不只说「哪里错」。**
一条错误提示的价值在于把使用者从卡住带到能继续。**只说「参数错误」的提示等于没说。**
形态：**哪里错了 → 为什么 → 怎么改**，三样缺一不可。

### 5.3 与 CHANGELOG 的边界

**「只写当下」管的是读者只该知道当下的东西**：约束类文件、技能正文、使用者可见面。CHANGELOG、git 提交、ADR、工单、代码注释里**可以**直说「此前怎样、现在怎样」，那是给维护者判断升级用的。
**判据是读者是谁**：使用者与照着规矩干活的人，读到的只能是当下；维护者读到的可以是全过程。

## 六、四者之间的关系

| 文档 | 回答什么 | 读者 | 什么时候写 |
| --- | --- | --- | --- |
| ADR | **为什么这么定** | 维护者 / 执行者 | 三条判据同时成立时 |
| spec | **要做成什么样** | 执行者 | 一轮对话干不完、要跨会话交付时 |
| 工单 | **怎么一步步做** | 执行者 | spec 定下来之后拆 |
| 手册 / 使用者文本 | **现在怎么用、错了怎么改** | 工具使用者 | 随功能一起交付 |

**不要把四样混在一起写。** 工单里不写「为什么这样设计」（那是 ADR），spec 里不写逐条实施步骤（那是工单），ADR 里不写具体改哪个函数（那是工单），**手册里不写取证过程与沿革**（那是 ADR 与 CHANGELOG）。

**判据只有一条**：**这段文字是写给谁的？** 写给使用者就按第四节、第五节的口径；写给维护者与执行者就按 ADR / spec / 工单的口径。**两类混写，两边都不好用。**
