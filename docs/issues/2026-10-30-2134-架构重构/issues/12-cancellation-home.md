# 12: 取消（Ctrl+C）归谁管——现在信号处理一半在执行站、一半在报告站

**Type**：grilling
**Status**：resolved
**Blocked by**：无，可立即开工

## Question

老工程里信号处理与取消分在两处：`internal/ssh/exec.go` 管执行期的中断，`internal/output/reporter.go` 管汇报期的收尾。两头各管一半。

取消（cancellation）是典型横切关注点：它不属于任何一站，却每一站都可能要响应。ADR-0032 定的五个叶子包里没有它的位置。

这件事故障起来很难查：中断之后要保证 `defer` 跑完、日志落盘、码页还原、归档写完。老入口注释写着「一 os.Exit，defer 不跑、日志不落盘、码页不还原，收尾全断」——取消走的正是这条最容易断的路径。

要定的：

1. 取消归哪个包——新建横切包？还是并入 `exitcode`（都属于「收场」）？还是归塔尖（它是唯一知道全局的地方）？
2. **取消信号怎么传到各站**：靠 `context.Context` 逐层往下递（Go 的通行做法），还是靠一个共享的取消标志（简单，但那是共享可变状态，跟「只传不可变物」的原则打架）。
3. 五站各自的收尾责任：哪一站负责「已经发出去的东西要不要回滚」（老工程有 ADR-0022 上传失败即回滚），哪一站负责写归档。
4. 取消之后算不算一次「正常结束」：退出码给什么、归档照不照写、统计里怎么记。

答案要能落成一句判据：按 Ctrl+C 之后，东西按什么顺序收，谁保证它收得完。

## Answer

**依据**：开发者 2026-11-01「我原来的设计就是提前收工。比如说，SH 执行的时候，没有执行的任务就是任务已取消……它是不会直接中断的，因为直接中断的话，各种回收清理都做不了」。

### 一、一句话判据

**取消是通知，不是杀死。** 塔尖订阅信号、往下递通知；在跑的收手、没跑的记作未执行、已经发出去的由产它的那一站收回；然后照常走完结算与报告，进程只在塔尖退一次。

### 二、信号只订阅一处，分两段

- **执行期之前**：塔尖自己接住，还了控制台码页就退，退出码 130。那一段最容易按（参数写错想重来、在确认屏上犹豫），而那时 `defer` 一个都跑不到，只有它能收。
- **执行期开始**：换成「往下发通知」，塔尖不再自己退；早段那条当场收掉，免得它抢先退出、把收尾打断。

判据：**订阅信号的点只许在塔尖**（ADR-0032 第五条已点名 `signal.Notify` 只许塔尖用），别处连订阅的资格都没有。

### 三、为什么不能直接中断

直接中断就是让信号把进程打死：`defer` 不跑，码页不还原、日志不落盘、归档写不完、上传到一半的残留留在目标机上。所以取消只能是通知——**「收得完」不靠谁记得收，靠「取消永远不杀死进程，进程只在塔尖退一次」这条结构**。

### 四、取消往下走，用一路传的通知，不用共享标志

用 `context.Context` 逐层往下递（Go 的通行做法，老代码已是这样）。**不设共享的取消标志**：那是可变全局状态，任何一个包都能读写，出事时说不清是谁翻的，且翻回去就没法恢复。

### 五、取消写在纸上三处，各写各的

- **执行站**：每个节点结果上记一格「被中断」。中途按停的按**连没连上**分两种——没连上归「连不上」，连上了跑到一半归「任务已取消」。这是既有分类表的口径，不动。
- **结算站**：算一次「节点总数 − 实际结果数 = 未执行」，另记一个「本次被中断」的标记。**中断造成的缺额不算异常**：总数校验那一栏留空，既不写「通过」也不写「异常」。
- **报告站**：中断时统计行改口径，把「未执行：N（执行被中断）」列出来；屏幕上一句「已收到中断信号，停止执行，已完成的结果已写入日志与输出文件」由它出（它是五站里管「跑完之后」的那一站，塔尖不拼这句话）。

**没跑的任务不进结果，只在统计里以缺额出现。** 它没连过目标机，没有「发生了什么」可写；硬给它造一行，会让「没发生」和「发生了、结果是取消」长得一样。

### 六、收尾谁负责

- **已经发出去的东西归执行站**：上传中途按停照样回滚，残留留在目标机上是它自己造成的（ADR-0022「要么全传上去、要么一个都不留」）。
- **目录与文件谁产谁写**（ADR-0032 第四条）：归档目录归归档包，报告与两张表格归报告站。
- **顺序**：停新的 → 等在跑的收手 → 回滚 → 结算 → 报告 → 塔尖退。

### 七、退出码照旧，不为它单列

- **执行中被按停：仍是 0。** 那是一次提前收工，报告已经出了，结果在报告里；脚本要判断，去看报告。
- **执行期之前被按停：仍是 130。** 那时还没有报告，只有「没开始」这一件事可说。
- **取消不进「结局」表，但退出码表里得有它**：塔尖认的仍是那五种结局，不为取消加第六种——它不是「这一趟走哪条路」，是「走的路上被按停」，落在执行站交回的那张纸上就够。可 130 这个数得有出处：退出码表里加一种「被中断 → 130」，塔尖认出是这一种，再交 `exitcode` 查表。**两张表别混**：结局是塔尖认的入口结论，退出码是 `exitcode` 查的种类。

代价：同一个 Ctrl+C 在两个时刻给的号不一样。这是老代码的样子，重构不顺手改。

### 八、这条不覆盖什么

- 跑到一半那行进度数字怎么出、怎么收——13 号。
- 「部分成功」这类分类判据——既有分类表的口径，不动。

## 更新记录

- 2026-11-01：取消定为「提前收工」——塔尖订阅信号并向下递通知、进程只在塔尖退、照常走完结算与报告；题干「信号处理一半在执行、一半在报告」「新建横切包」「并入 `exitcode`」「归塔尖所以塔尖变厚」四处不再约束，替代见上文 `## Answer`。三处不成立：信号订阅本来就只在塔尖，执行站只是响应、报告站只是特意不去抢；取消不产数据、也不属于收场查表，所以不是横切包、也不并入 `exitcode`；塔尖只多一件「订阅」，不加判断，不构成变厚。
