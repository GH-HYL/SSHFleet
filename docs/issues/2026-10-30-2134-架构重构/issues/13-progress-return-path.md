# 13: 实时进度怎么从执行站走到呈现站——过不过整理站，走事件还是轮询

**Type**：grilling
**Status**：open
**Blocked by**：02, 03

## Question

老工程里进度这条链跨好几个包：`internal/ssh` 的进度读写器（包裹 SFTP 读写的 `io.Writer` / `io.Reader`，按 500ms 节流）、`internal/batch/progress.go` 的进度聚合器（跨调用保存状态、与 worker pool 同生命周期）、`internal/output` 负责渲染。

按五站分法，这三块要拆开：采集归执行站，聚合归谁？渲染归呈现站。**难点在聚合器**——它跨调用保存状态，是五站里唯一「有状态」的东西，而五站其余部分都是「入 → 出」的纯函数形状。

骨架对这个问题的答案是写一句「Hooks 是事件上报通道，不是反向驱动——它只能收进度，改不了主流程走向」，并给了判据：回调里能不能让程序少走一站？不能，所以合规。但**这条只说了「可以收」，没说进度怎么送出去**。

要定的：

1. **进度走哪条路**：① 执行站直接调呈现站的渲染函数（等于执行站 import 呈现站，方向倒着）；② 执行站发事件、塔尖转交（塔尖就厚了）；③ 走回调（骨架的 Hooks 方案，但回调要由谁注入）；④ 呈现站定时去问执行站要快照（轮询）。
2. **聚合器归谁**：它有状态。放执行站，那执行站要对外暴露「当前进度」；放呈现站，那呈现要 import 执行站的数据类型。
3. **整理站要不要参与**：整理站的职责是把「事实」变成「结论」；进度是过程不是结论。若不过整理站，那五站的单向性在这里就破了一个口——这条口子要不要明确写进结构定义。
4. **节流放在哪一层**：现在 500ms 的节流在数据采集侧，渲染侧还有一层。重构后合并到一处还是各留一层（各留一层会互相抵消）。

答案要能落成一句判据：执行到一半时，屏幕上那行进度数字是从哪条路径走到终端的。
