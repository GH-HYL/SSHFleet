# 10: 冻结期老工程修了缺陷怎么回放到新工程——台账还是切换前一次对齐

**Type**：grilling
**Status**：resolved
**Blocked by**：无，可立即开工

## Question

作者定的：老工程冻结，只修紧急缺陷。但「只修紧急缺陷」依然会修——每修一次，新工程就落后一次，而两套代码没法用 `git merge` 带上（不同目录、不同结构）。

同一条还牵着配置：新工程自带一份 `config/`，格式与老工程完全一致。开发期若因为某个缺陷改了字段，两份会走样。

要定的：

1. **回放机制**取哪种：① 修的时候顺手在新工程里同步改一遍；② 记一份补丁台账（哪次提交、改了什么、新工程对应改哪儿），切换前一次对齐；③ 干脆不修，等新工程上线后再说。三者代价不同，②最不容易漏但也最容易过期。
2. 台账放哪儿——议题目录下单独一份文件？还是各工单的 `## Comments`？`docs/agents/issue-tracker.md` 对自造文件名有黑名单，得挑一个载体认的名字。
3. **两份配置怎么防走样**：靠人记，还是加一处机械核对（比如一个脚本比对两份 `config/` 的字段名集合）。
4. 老工程这一轮已经修过的（`CHANGELOG.md` 未发布段里有两处 `#### Fixed`：2026-10-29 一条、2026-10-27 一条），要不要补记进台账。

答案要能落成一句做法：老工程下一次修缺陷时，执行者第一步该做什么。

## Answer

**约定（作者 2026-11-01 提，本节据此写）**：**冻结期只要动了老代码，不论大小都开一个议题**；没有交集题目录里的新议题，就等于没动老代码，不需要考虑回放。**议题目录就是账本，不另造清单。**

作者同日的判断给了这条约定底气：「老工程的紧急缺陷也都是小修小补……直接原地打补丁，也不考虑什么设计之类的了。这些都属于紧急修复，不会影响新工程的。」

### 一、平时：不记账，只开议题

修老代码 → 开议题 → 修完。**没有常驻台账**，因为台账会过期（写着「新工程改某某处」，等真去看时那处已经被后来的改动换掉了）。

**补丁议题长这样**（照载体现有的规矩，不新造文件类）：新建一个议题目录 `docs/issues/<日期-时间-主题>/`，里面一条工单，`Type: task`；每次修一条就往该工单的 `## Comments` 追加一行，**不写 `## Answer`**——它不是决策，是事件流。修完把 `Status:` 改掉即可。

议题里至少要写清两样，否则切换前对账要重读代码：

- **动了哪一块**，对得上五站的哪一站；
- **动没动配置字段或必须项清单**——这一类最危险，因为那份知识不在代码里，逐字比对只能告诉你「起不来」，不会告诉你缺哪个字段（下面第三节说明为什么比对兜不住它）。

### 二、切换前：一把对账，两份对一眼

**起点是 2026-10-30**（作者定冻结那一天，也就是 ADR-0032 落盘那天）。往后到切换那一刻，这段里开过、且真改了老代码的议题都在对账范围内。

1. 拉这段开过的议题，逐条判「要不要补进新工程」；
2. 拉这段老工程的提交列表（`git log --since=2026-10-30 -- modules/SSHFleet_Go`），两份对一眼。**差一条**（有提交、没议题）就是「改了却没开议题」，当场补议题，不算数过关。

两条合起来是互补的：议题是人的记忆，提交列表是机器的事实。只信一边都会漏。

### 三、两张网，各管一头，都缺不得

- **对账**：抓「有没有漏」。
- **逐字比对**（规则在 08 号答案第五节）：抓「行为一不一样」。漏掉的那笔只要影响输出，它就会红。
- **配置字段名集合核对**：抓「两份配置走没走样」。这一条必须单列，**比对兜不住它**——比对是拿同一份配置喂两个二进制，新工程不认某个字段时直接忽略、输出照样一样，所以字段改了而新工程没跟上，比对是绿的。核对只比**字段名集合**，不比默认值（值本来就允许不同）；新工程 `config/` 一落地就开始跑，之后每次交付跑一次，不一致就红。

  **谁跑：新工程里一条测试，跟着 `go test` 一起跑**，不另加命令、不加脚本——它读两份 `config/`、比字段名集合，红了就报「哪几个名字只在一边」。它不进 07 那套越界检查（这不是越界），也不进红线区（判的是两个工程一致，不是结构），属自定义区。

这三张网缺一不可，这也是平时可以不记账的原因。

### 四、窗口的边界（作者 2026-11-01 原话）

> 「自打切换那一刻，有问题就解决新代码的问题，老的就真的彻彻底底冻结了。」

所以回放窗口只有一段：**从冻结之日到切换那一刻**。切换之后不再有任何回放义务，老工程只等下一次大改被删。

### 五、这一条不覆盖什么

- 老工程已经修过的（冻结前，CHANGELOG 未发布段里 10-29、10-27 那两笔）：**不补记**。
- 冻结期新功能怎么办：一律进新工程——这条不是 ADR-0032 第六条写的（那条只说「只修紧急缺陷」），是地图「Decisions so far」里那句「老工程冻结：只修紧急缺陷，新功能一律进新工程」。
- 新工程内部怎么组织代码：动工范畴，本图不收。

**一处标成推导，复审时可推翻**：「新工程是从冻结那一刻的老代码摊出来的」是执行者的推断（依据是 04 的摊法按当时的代码逐块搬，加上老工程「原样不动」），ADR 里没有这一句。若将来发现摊的不是那个时点，第五节第一条「不补记」就不成立。
