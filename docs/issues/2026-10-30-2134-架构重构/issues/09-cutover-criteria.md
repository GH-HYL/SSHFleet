# 09: 切换判据定在哪一步——什么条件下才敢让新工程顶替旧工程

**Type**：grilling
**Status**：resolved
**Blocked by**：02, 04, 08

## Question

老工程冻结，不等于切换。切换（cutover）是这一整件事唯一的对外动作，一旦做错，使用者手上的工具就换了，配置要重写、行为可能变、出问题没退路。

要定的：

1. **切换的硬条件**是什么——五站贯通？五种执行模式全跑通？三条密钥子命令跑通？还是必须加一条「重构前后输出逐字比对通过」（见 08 第 4 点）。
2. **切换那天动哪些东西**：`tools/release/release.py` 第 54 行写死 `modules/SSHFleet_Go`，`APP_NAME` 是 `SSHFleet`；`.gitignore` 第 88 行排除 `modules/*_bak*/`。三处都要改，谁先谁后、出错了怎么退。
3. **老工程切换后怎么处置**：改名成 `SSHFleet_Go_bak` 会立刻被 `.gitignore` 排除、从版本库里消失，而它是当前发布版唯一源码。要不要保留、以什么形态保留。
4. **退路**：切过去之后发现不行，怎么切回来。这一条必须先写，不能事后补。

答案要能落成一句判据：满足哪几条，才允许执行切换。


## Answer

**依据**：开发者 2026-11-01「行，按照你的建议来」——点的是这套（判据三档、切换不改名、退路靠已有的发布 tag 与脚本指向）。

### 一、判据分三档，别混成一句

「能开始搬」「可以对外切」「切换那天做什么」是三件事：前一件宽，后一件窄。

**建站门槛（最宽）**：能编译、红线绿。红线那套判据在 07 与 08，这里只点名，不重写。

**可切门槛（三条硬条件，全过才允许动手）**：

1. **五站贯通**：一条具体路径跑通——**命令模式、一台机器、出厂配置只改一处**（填那台的地址与登录），从参数一路到出报告，退出码 0。不写「全跑通」，因为「全」判不出来。
2. **都用过一遍**：五种执行模式（命令、脚本、上传、下载、改密）加三条密钥子命令，各在验证环境（`docs/测试环境使用指南.md` 那套 Podman 沙盒）对着真机器跑过一次。**通过标准三样**：退出码 0；该有的落盘产出都在；报告里那台算成功。不是「跑完看一眼」。
3. **逐字比对最近一次通过**：两个二进制、同一份配置清单，归一化后 stdout 与六项落盘产出一致，规则照 08 号答案第五节。**时点**：新工程第一次能整条跑起来就比对一次，之后每次交付跑一次；切换前必须最近一次是绿的。08 说的「拿到可跑的二进制就把 A/B 补上」指的就是这个第一次，两处不冲突。

### 二、切换当天：五步，一步不能省

**第 0 步·前置（满足不了就别开）**：新工程目录下已经有 `main.go` 与 `config/` 那三份配置——发布脚本一开始就查这两样，缺了当场停。

1. **先确认退路的锚在。** 切换前最后一次发布已经打过 `v<版本>` 的 tag（发布脚本本来就打，不需要新造一套命名）。确认它在、并且两端都推过；没有就先按原样发一次。
2. **改发布脚本里那一行目录名，然后提交。** 脚本打包前会查工作区干净，改完不提交，下一步必失败——这一步原答案漏了，是真会卡住的那种漏。
3. **冒烟用临时编出来的二进制，不走发布脚本。** 原因：脚本那条路是正式发布——封更新日志段、改版本常量、commit、打 tag，那些动作不该在冒烟前发生。冒烟三条：`--help`（版本行在首行下方）、空参数敲一记（出同一屏）、命令模式一条真机。
4. **冒烟过了，再走发布脚本出包。**
5. **出完包，新工程即成默认发布源**——它就是第 2 步改的那一行，此后不再改回。

**为什么是这个顺序**：前三步任何一步不对，都停在「还没人拿到新包」的状态里。**错要错在没人受影响的时刻。**

### 三、只改一处，另外两处不动

Question 问的是「三处都要改」，实际只改一处：

- **发布脚本的目录名**：要改，这是唯一真正指路的。
- **`.gitignore` 的 `modules/*_bak*/`**：不动。不改名就不会命中；改了反而给将来留个陷阱。
- **`APP_NAME`**：不动。使用者看到的名字还是 `SSHFleet`，这次是重构不是换产品，不该让他改脚本。

### 四、退路（先写，不事后补）

- **锚**：切换前最后一次发布的 `v<版本>` tag。用它，不新造「带日期的 tag」——多一套命名就多一处要维护，而发布 tag 本来就钉住了那一刻的源码。
- **退回的动作**：发布脚本目录名指回老工程 → 提交 → 重新出包。两次编辑加一次提交，不碰 git 历史、不碰目录名。
- **两个远端**：切之前先把 tag 两边推齐，再推分支。锚先落地。

### 五、不改名，理由两条

- 忽略规则里有 `modules/*_bak*/`，一改名就命中，**老工程当场从版本库消失**（已被跟踪、又被新规则命中的文件，git 不再显示）。而它是当前发布版的唯一源码。
- 改名解决不了任何问题。它躺在原地、还能编译、还能被打包，就是退路；改名只是把安全网摘了挂墙上。

### 六、老工程什么时候删

**不在切换当天。** 切换后原地留着、不再维护、不再打包；等下一次大改（版本号进下一个大档）之后再删。那时发布 tag 已经钉住了切换前的样子，删掉不留坑。

### 七、这条不覆盖什么

- 版本号打什么档位：开发者跑发布脚本时选，执行者不参与。
- 新工程的代码怎么写：动工范畴，本图不收。
- 冻结期修了缺陷怎么回放：10 号。
- 迁移期两份配置会不会走样：**已由 10 号答**——两份 `config/` 的字段名集合必须相等，新工程配置一落地就跑一次，之后每次交付跑。它不进上面三条门槛，但切换前必须绿，否则切换当天直接起不来。
