# 01: 上传失败即回滚，退役「部分成功」

**要做的**：上传一个目录，第 3 个文件失败时，目标机上**一个本次的文件都不留**——前两个已传成功的与第 3 个半成品都被删掉；结果里说清「删了几个、有没有没删掉的」；分类只剩「成功」或「失败」两种，不再出现「部分成功」。

**被谁阻塞**：无，可立即开工（决策见 ADR-0022）。

**状态**：done（2026-10-20）

**依据**：`docs/adr/0022-上传失败即回滚.md`

## 验收

- [x] **回滚范围**：失败时删除的是**本次已写成功的远端完整路径**与当前失败文件的半成品；不 `find`、不匹配通配符、**不删目录**。给出能证明「只删本次写的」的测试或真机记录。
  落定：`writtenPaths`（sftp.go，只记写成功的）+ `rollbackWith` 单测（`rollback_test.go`：只删点名路径、空清单不动作）+ 真机用例「第二个文件撞名：回滚掉先传成的那个，原文件不动」。
- [x] **回滚成功**：目标机恢复到本次执行前的样子；报错原文里追加一句陈述事实的报文（~~`sshfleet.transfer.rollback`~~ → 最终实现为 **`sshfleet.transfer.rolled_back`**），**不静默、不无限重试**。
- [x] **回滚部分失败**：清理本身失败时，如实写出「删了几个、还剩哪些路径」（~~`sshfleet.transfer.rollback_failed`~~ → 最终实现为 **`sshfleet.transfer.rollback_partial`**，left 路径清单写在报文里）。
- [x] **sudo 路径**：`--sudo` 上传失败时同样能删掉 root 属主的文件（真机用例「sudo 路径同样回滚」）。
- [x] **报文与分类退役**：`sshfleet.transfer.finished` 不再产出；出厂配置里「部分成功」分类删除。
- [x] **语料与断言**：语料「部分成功 3/5」改写为下载逐文件行认领；`verdict` / `output` 里的断言跟着改（`TestJudgeStructuralFacts`、`terminal_test.go`）。
- [x] **行为说明**：使用手册 2.3 写明「失败会把本次已经传上去的文件删掉」。
- [x] **实机验证**：真机造中途失败（第 2/3 个文件撞名两种时序），目标机上没有本次留下的文件；分类见 Comments 端到端复核。
- [x] `go build ./...`、`go vet ./...`、`go test ./...` 全绿。

## Comments

- 2026-10-20：**下载不做回滚**（ADR-0022 决定第 5 条）。本工单只管上传。
- 2026-10-20：这条会**撤掉报文议题的 08**（传输部分成功的计数口径）——不存在中间态，那个数字冲突自然消失。报文议题的 07 要等本工单做完再收口。
- 2026-10-20：**实现**：`rollbackUpload`（逐条点名删，`sudo rm -f` / SFTP `Remove`）+ `rollbackWith`（与「怎么删」解耦，便于单测删不掉的情形）+ `RollbackMessage`（纯函数，产 `rolled_back` / `rollback_partial`）。三处失败出口与取消路径都走回滚。
- 2026-10-20：**取消也回滚**。原计划只覆盖失败，实现时补上：被 Ctrl+C 中断同样留下「传一半」，与本决策的「要么全成要么全不成」相抵。这一条比工单原文多做了，理由记在这里。
- 2026-10-20：**真机七场景全过**（`internal/ssh/upload_rollback_test.go`，`-tags integration`）：全成功不回滚、第一个就撞名不写不发报文、第二个撞名回滚先传成的且原文件不动、中途失败清掉已写的、预检失败不进循环、sudo 路径同样回滚、回滚本身照实报告。
- 2026-10-20：**端到端取证**（真机、`/tmp/partial` 预置一个 `two.bin`）：传 3 个文件、第 2 个撞名 → 错误详情 `sshfleet.transfer.rolled_back: 2 of 2 written files removed`，分类「远程文件已存在」，目标机上只剩原本那个 `two.bin`、内容未变。
- 2026-10-20：**测试中发现的层级事实**（写进了用例注释）：多文件上传按**相对上传根的路径**落盘，`-u` 下的 `ff/a.txt` 落到 `目标目录/ff/a.txt`，不是 `目标目录/a.txt`。先前按后者造同名文件，测出来的自然是「全成功」。
- 2026-10-20：**遗留待定**：下载中途失败时没有汇总报文，分类只能靠逐文件那行的报文或系统原话；若逐文件行里出现 `permission denied` 之类，会被「权限不足」先认走。不在本工单范围，记录备查。
- 2026-10-20：**`SFTP失败` 按语义拆开**（作者定）。它原来把五种失败归成一类，原因、应对方、责任方全不同。现在拆成：

  | 分类名 | 认领的报文 | 使用者做什么 |
  | --- | --- | --- |
  | 目标机不支持 SFTP | `client_failed` | 找管理员开 sftp 子系统 |
  | 目标机写入失败 | `remote_file_failed` / `tmp_failed` | 查目标机磁盘、权限 |
  | 本机写入失败 | `local_file_failed` | 查本机磁盘、权限 |
  | 上传目标不是目录 | `remote_not_dir` | 改 `-p` |
  | 上传失败已回滚 | `rolled_back` | 本次没留残留，可直接重传 |
  | 上传回滚未清干净 | `rollback_partial` | **必须先手工清理**再重传 |

  `tmp_failed` 并进「目标机写入失败」：它只出现在 `--sudo` 下，本质仍是目标机写不进去，单独立一条会让分类表多一个难懂的名字。
- 2026-10-20：**顺序规则**：回滚那两条**排在所有传输失败原因之前**（含「远程文件已存在」）。依据是使用者拿到统计块先要知道「目标机现在干不干净、能不能直接重传」，「为什么失败」在错误详情里一条就看得全。已补用例锁住（`撞名触发回滚：统计块优先显示回滚状态`）。
- 2026-10-20：**「远程文件已存在」的 tip 改了**。原写「上次执行留下的残留」——回滚生效后本次不留残留，那句会误导。现改为「目标机上原本就有一个同名文件，工具不覆盖——要覆盖先把它清掉再传」。
- 2026-10-20：**Ctrl+C 取消也回滚**（作者确认要这个行为）。集成用例「按 Ctrl+C 取消时同样清掉已传的」用进度回调在第一个文件传成后触发取消，断言目标机清空。**真机八场景全过**。
- 2026-10-20：**端到端复核**：第三个文件撞名 → 统计块显示「上传失败已回滚」，提示语写明「目标机没有残留，可以直接重传」，目标机上只剩原有的那个文件。
