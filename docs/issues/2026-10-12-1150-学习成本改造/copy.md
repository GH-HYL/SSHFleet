### 1.4 `--sudo` 的当前配置值怎么显示（已定）

需求：**这个默认值来自配置文件，所以帮助里要显示的是"当前配置的值"**，不是写死的字面量。

定的排版是——**只在不带 `no-` 的那一行上标记，标的是"不加任何参数时用的是哪种身份"**：

```text
       --sudo               [当前配置: 开]    这次以 root 身份执行
       --no-sudo                              这次以登录用户身份执行（配置是开时用它改回来）
```

配置里是关时，就渲染成：

```text
       --sudo               [当前配置: 关]    这次以 root 身份执行
       --no-sudo                              这次以登录用户身份执行（配置是关时用它改回来）
```

这样处理有三个好处：① 用户扫一眼就知道"我什么都不加会怎样"；② 标记只出现一次，不会有"两行都标、看着像两个独立默认值"的误解；③ `--no-sudo` 的职责由后半句括注说清，不需要再占一个标记位。

> 括注里的"配置是开/关时用它改回来"跟随配置值变化——它的意思是"当配置值让你不满意时，用另一个开关单次覆盖"。

**实施时的落地口径（2026-09-24 定，本行以下为回写内容）**：

- **配置为关时不出那句括注**：原本这里写的是"配置是关时用它改回来"，但配置已经是关的时候，`--no-sudo` 没有任何东西可"改回来"。实际渲染成：
  `--no-sudo    这次以登录用户身份执行`（无括注）。配置为开时才有 `（配置是开时用它改回来）`。
- **程序名是运行时的**：上文样张里的 `SSHFleet` 是理想写法，实际渲染取当前可执行文件名（Windows 上即 `SSHFleet.exe`），用法行、缩进说明与示例里统一用同一个名字。
- **`[当前配置: 开/关]` 是唯一一处读配置的标记**，与 `-n` / `-t` / `-T` 那三处 `[默认: …]` 同属标记列。

### 9.1 一条危险规则的处置（2026-09-24 实测更正：不需要动）

危险规则文件里有一条规则叫 **`使用 --no-preserve-root 危险旗标`**，级别是 `high`。

**它是什么**：`rm` 自带一层保护——直接 `rm -rf /` 它会拒绝执行，除非你显式加 `--no-preserve-root` 告诉它"别拦我"。所以这个旗标出现在命令行里，等于操作者在**主动拆掉最后一道保险**。举例：`rm --no-preserve-root -rf /` —— 这一条会把根目录连同系统一起删掉。

**原先的处置方案是"把它归入 `递归删除根目录`"，现已作废——现状就是这个效果。** 实测（跑发布规则）：四种写法 `rm -rf /` / `rm --no-preserve-root -rf /` / `rm -rf / --no-preserve-root` / `rm --no-preserve-root -rf /*` **全部**命中 `递归删除根目录`、级别 `forbidden`。原因是危险正则跑在归一化之后的字符串上，而归一化会把 `rm` 的旗标拍平成固定次序，`--no-preserve-root` 落进了那条正则的覆盖范围。**规则名不改、级别不改、不加新规则。**

**规则名不改**这一点与作者裁定一致：分类内容要真实，不需要修饰——本次的工作是降低学习成本，不是替规则起好听的名字。

> 我此前建议把这条规则名改成"绕过根目录保护"（理由是用户在提示屏上只看得到这一行），**该建议已作废**；此前的"它只判 high"的结论也已作废，详见 `spec.md` 13.7 / 13.8。

**四处问题**：

1. **第 1 行 `# -*- coding: utf-8 -*-` 是 Python 的编码声明**（工具早期是 Python 写的），对 TOML 毫无作用，纯噪音。
2. **`password_security = 3`** —— 随包模板出厂就是最高等级，陌生人改完三行一执行就撞主密钥那条链。
3. **`secret_dir = "~/.MyPW"`** —— 模板自带一个自己不支持的值（配置路径一律绝对路径，不支持 `~`）。
4. **注释口吻是"字段是什么"**，且带内部映射（`（清单第 2 列留空时用）`）——那是给已经懂工具的人看的。

### 11.4 一处 TOML 层面的约束（写模板时必须知道）

**`[account]` 这个表在一个文件里只能出现一次。** 所以"基础配置 / 进阶配置分两个物理分区"如果靠"写两个 `[account]`"实现，TOML 会直接报**重复表**。

也就是说：**分区只能靠注释与排列顺序，不能靠独立成表。**

**2026-09-24 定下的排法**（已被同日的作者重排取代，见 11.2 / 11.3 第 15 条）：基础配置 7 项里，`user` / `port` / `password` 属 `[account]` 表，`sudo` 与三个超时属 `[execution]` 表。想让**基础配置 7 项连续排在最前**，唯一的表顺序是 `[execution]` → `[account]`（3 项基础）→ 注释分界 → 4 项进阶 → `[enable]` → `[upload]`。作者随后裁定**账号信息置顶优先于"基础 7 项连续"**，现行为 11.2。

### 11.5 明确不动的

- **主文件名 `SSHFleet.conf` 不改**（建议与理由见 `spec.md` 14.4（1））——它在文档与报错里反复出现，是用户认路的锚点
- **字段总数仍是 17 个**（基础配置 7 + 进阶配置 10），一个不少、一个不多
- **出厂值本身**：逐字段取什么值由作者在发布前自定，本节只锁结构（2026-09-24）
