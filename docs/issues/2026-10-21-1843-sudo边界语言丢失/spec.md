## 问题陈述

同一份配置、同一份代填表，在 CentOS 7 与 Ubuntu 上表现不一样：**CentOS 上脚本读到配置里的 locale，Ubuntu 上读到目标机自己的（常常是 `C`）**。

脚本按 locale 输出不同文案时，触发词只写了一种语言，于是「一半命中、一半等超时」或「整批失配」；更糟的是语言被改错之后，`cut -c` 这类按字符取位的操作会把中文切坏，脚本的基本功能就不成立了。

## 结论

| 项 | 取定 |
| --- | --- |
| 编码 | **不给用户配**。工具每次执行时判断，尽量让目标机按 UTF-8 算字符；做不到就保持原样 |
| 语言 | **只留一个开关**：新开 `[locale]` 段，键 `english`，默认 `false`；开 → 提示语统一英文 |
| `[env]` 出厂内容 | 只剩两行：`PATH` 与 `TERM`（`dumb`，代价见「影响」）；用户仍可自由增删自己的变量 |
| 拼接形态 | 外壳仍是 `sh -c '…'`，里面多一段固定片段（片段 162 字节，整条 174 字节） |
| `-a` | 与其余模式同一套 |

## 编码的判断逻辑（工具内建，用户看不见）

1. 问机器：`locale charmap` 是不是 `UTF-8`。
2. 是 → 什么都不做，前置片段在这台机器上等于没有。
3. 不是 → 在 `C.UTF-8` / `en_US.UTF-8` 两个中性名里挑一个**确实存在**的（大小写、连字符不计，`C.utf8` / `en_US.utf8` 同样认）。
4. 挑到 → 只 `export LC_CTYPE=<挑到的>`；挑不到、`locale` 不存在、输出为空 → 一个变量都不设。

三条不变式：

- **只动 `LC_CTYPE`**：不碰 `LANG`、`LC_ALL`、`LC_MESSAGES`、排序。
- **永不降级**：只在「现在不是 UTF-8、且机器上有 UTF-8 可选」时才动手。
- **永不告警**：不设 `LC_ALL`；候选只在确实存在的名字里挑。

## 语言开关

配置里新开一段，出厂形态：

```toml
# 提示语语言：只管语言，不管编码（编码由工具处理，没有开关）
# 开 = 统一英文；关 = 自适应，跟随目标节点的语言环境
[locale]
english = false
```

开 → 前置片段多一句 `export LC_MESSAGES=C`；`LANGUAGE` 不用清（在 `C` 下 gettext 忽略它，实测）。关 → 什么都不加。

**为什么不在 `[env]` 里**：`[env]` 是环境变量表，一个布尔混进去会被读成"能传下去的一个变量"。语言开关不是环境变量，它决定"要不要加那一句"。

## 已核实的事实

1. **两类机器没有交集**。CentOS 7.9 有 `en_US.UTF-8`、没有 `C.UTF-8`；Ubuntu 26.04 只有 `C` / `C.utf8` / `POSIX`，没有 `en_US`。
2. **`LC_ALL` 设错会告警，类别变量设错是静默的**。`LC_ALL=<不存在>` 每次调用一行 `setlocale` 并落到 `C`；`LC_CTYPE=<不存在>` 静默回落、不告警。
3. **非交互会话拿不到 `LANG`**（CentOS 的 sshd 没配 `pam_env`、`/etc/environment` 是空的；Ubuntu 的 `/etc/default/locale` 只有一行注释），两台测试机上 `charmap` 都是 `ANSI_X3.4-1968`。
4. **只设 `LC_CTYPE` 不动语言与排序**：实测两台机器 `cut -c1-2` 都出完整「中文」、提示语都是英文、`sort` 仍是字节序。
5. **`LC_MESSAGES=C` 压得住 `LANGUAGE`**（apt 中文包对照：`LC_MESSAGES=C LANGUAGE=zh_CN` 仍出英文）。
6. **`TERM=dumb` 能压彩色，只在有 PTY 时有意义**。`-a` 的 PTY 下 `ls --color=auto` 由 25 行转义变 0 行；无 PTY 时本来就 0 行。
7. **失败分类的关键词全是英文原话**，语言出中文就整批落「未归类」——这是语言开关存在的主要理由。

## 影响

- **下发行**：`sh -c 'if [ "$(locale charmap …)" != UTF-8 ]; then …; fi; <英文开关那一行>; [sudo ]解释器 …'`。片段 162 字节、整条 174 字节，`-a` 的正文上限从约 92KB 减约 200 字节。
- **日志**：「命令行」一行会带这段判断，可读性下降。
- **`--no-shell`**：按契约不生效。
- **没有 `sh` 的目标**（交换机、小型机）：走 `--no-shell`，本规格不覆盖。
- **`TERM=dumb` 的代价**：`clear`、`tput cup` 返回 1；ncurses 类交互安装器预期也会失败（未测）。
- **字符语义仍按实现而异**：`C.UTF-8` 下 GNU `cut -c` 按字符，`mawk` 本来就按字节（与 locale 无关），uutils 的 `wc -m` 两处都按字符。手册里写这条必须带实现名。

## 测试接缝（2026-10-28 定，随决策更新）

工单里的自动化测试落在这两个口子上，端到端留手工：

- **前置片段的生成**：编码逻辑固定存在（没有开关），语言开关开 / 关两种产出一边一条，**逐字断言整串**；另断言片段里**不含单引号**（否则外层 `sh -c` 的引号要套娃）。
- **`ssh.BuildCommand` 的整串断言**：命令模式与 sudo 模式各一条，断言 `sh -c '<片段>; sudo bash'` 的完整形态；反例禁用词：`sudo env`、`sudo -E`、`bash -c 'export`。
- **落点**：四种下发形态（命令 / 脚本 / sudo / 代填）各一条整串断言，加开关开、关两条逐字断言，都在下发行拼装这一个口子上。
- **不进自动化的**：容器里跑中文 `cut` 断言 4/8 字节（Ubuntu + CentOS 两台）、包内配置检查（要跑 `release.py`，属发布动作）。

## 存量配置

**不考虑。** 工具尚未发布，`[env]` 的形状可以整段重写。出厂不再给 `LANG` / `LC_ALL`；用户自己在 `[env]` 里写这两行，格式照既有校验走（TOML 语法、变量名合法），内容上不与工具自己设的变量做冲突判断。

## 不做

- 不改外壳形态（仍是 `sh -c '…'`，不引入 `sudo env`、`sudo -E`）。
- 不改目标机的 `/etc/sudoers`、不代跑 `localedef`。
- 不给编码留用户开关——留了就会有人关掉，然后回来报「切半个字」。
- 不覆盖没有 `sh` 的目标（交换机、小型机走 `--no-shell`）。
- 不处理 `-a` 的 PTY 丢字符（另议）。
