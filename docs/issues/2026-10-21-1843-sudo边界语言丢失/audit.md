## 一、A 类：硬伤（处置方式唯一，直接定下修法）

### A1 ADR 第七节漏了打包模板——只改 `SSHFleet.conf` 会做出一个「本地变了、发出去的包没变」的工单

- **位置**：`docs/adr/0024-env穿过sudo边界.md:301`；`modules/SSHFleet_Go/config/SSHFleet-for-linux.conf:46-47`、`SSHFleet-for-windows.conf:46-47`；`build-linux.sh:58-59,101,103`、`build-windows.bat:29-30,104`
- **证据**：ADR 写「**配置**：`config/SSHFleet.conf` 的 `[env]` 段」；而打包脚本实际是把 `SSHFleet-for-*.conf` 复制成包内的 `config/SSHFleet.conf`。**这一点本轮没有核实到根**：`build-linux.sh` / `build-windows.bat` 只做「模板 → 包内 `SSHFleet.conf`」的复制，至于程序运行时会不会**再把工作区那份写回去或另读一份**，本轮没有确认（若能确认它不回写，A1 的结论更强；若会回写，B1 就不只是「跟不跟着改」，而是「谁覆盖谁」）。
- **后果**：照第七节写工单，改完工作区那份，发布包里仍是 `en_US.UTF-8`。验收「出厂值已是 `C`」会通过，实际什么都没发出去。
- **修法**：第七节首条改为「出厂值 = 随包发布的两份模板（`SSHFleet-for-linux.conf` / `SSHFleet-for-windows.conf`）」，工作区那份 `SSHFleet.conf` 是否跟随由作者定（见 B1）。

### A2 ADR 第七节漏了 10 处需同步改的文档与注释

- **定位**：完整清单在 §三「改动面清单」。
- **后果**：其中 `docs/4-进阶知识手册.md:82` 最重——它整段在论证「为什么钉死成 `en_US.UTF-8`」「中文都是正常中文」「比 `C.UTF-8` 更普遍、行为更稳」，**方向与决定 1 相反**。只改配置不改它，手册会在发布包里教用户一件与出厂值相反的事。
- **修法**：把 §三 清单整体写进第七节「影响」。

### A3 `C` 的失效形态论证漏掉了解释器——这条决定验收标准

- **位置**：`0024:134`、`:155`、`:247`、`:251`；`modules/SSHFleet_Go/internal/ssh/command.go:331`（`python` 入表）；`config/SSHFleet.conf:57-59`（`.py = python3`）
- **证据**：`0024:247` 写「`C` 的失效形态是『不存在』」。**实测**（WSL Ubuntu-26.04，python3 14.4）：`LC_ALL=C` 下默认行为的 Python 3.7+ 走 PEP 540 UTF-8 mode、写中文正常；显式 `PYTHONUTF8=0` 时 `sys.stdout.encoding=ascii`，`print("中文")` 抛 `UnicodeEncodeError`、退出码 1，`open("中文.txt")` 同样抛。**推理**（未实测）：Python 3.6 及更早**没有** UTF-8 mode，默认即上述失败形态；CentOS 7 出厂的 python3 正是 3.6。6.4 自己列举的解释器包含 `python3` / `perl` / `php`，而 3.5/3.7 的代价表只比了 **bash 与 GNU 文本工具**。
- **后果**：选 `C` 的真实风险不止「输出里多几行警告」，还包括「整类脚本直接报错退出」——后者更响、更容易被当成工具故障。ADR 把结论写成了全称，而它只对 shell 与 GNU 文本工具这一层成立。
- **修法**：3.5/3.7 补一张「`LC_ALL=C` 下各解释器」的表；6.1 的「失效形态最稳」限定为「shell 与 GNU 文本工具这一层最稳」。这一项要不要进入决定的理由主干，见 B3。

### A4 「perl 7 行」不能当常数写

- **位置**：`0024:153-157`
- **证据**：ADR 写 `perl` 缺 locale 时固定 7 行，并给出了 7 行的逐行构成。WSL Ubuntu 实测为 **20 行**（19 行警告 + 1 行程序输出），ADR 列的 7 行里没有 `LC_CTYPE`…`LC_TELEPHONE` 那 12 行。另：同批取证产物 `build/audit-check/结论汇总.md:41` 记的是「bash **2** 行、perl 7 行」，而 ADR 写「bash **1** 行」——两处至少一处是错的。
- **后果**：这组行数是「警告污染输出、破坏逐字可比」这一核心论证的量化基础。数字被当成常数写死，复核时一测就对不上。
- **修法**：改为区间（如「7～19 行，随 perl 版本与是否逐条列出 `LC_*` 而变」），并注明在**哪台机器**数出来的。

### A5 「200 组抽样」整张表没有产物

- **位置**：`0024:199-206`（3.8 全表）
- **证据**：`build/` 下全部探针脚本与产出里检索 `抽样` / `200 组` / `85%` / `170`，**零命中**（已排除 `build/adr-review/` 对话记录）。3.8 没有脚本、没有结果、没有机器标注，也没标 GNU 与 uutils 各对应哪个平台。
- **后果**：3.8 是全文量化最强的表（0% / 85% / 12 行），却最没有来源。它被用来支撑「排序差异可以接受」，而这条支撑决定了决定 1 的取舍。
- **修法**：补脚本与输出并注明机器；补不出来就**删掉具体百分比**，只保留定性结论（「大小写混排时排序会不同」）。

### A6 `0016` 的备选方案表被混装了两套否掉理由

- **位置**：`docs/adr/0016-环境变量值由目标机展开.md:43`；对照 `0024:339`
- **证据**：`0016:43` 原有理由「引入外部程序依赖，与『目标机只要 `/bin/sh` 在就能跑』的取向冲突」；同一格末尾被追加「本条在 2026-10-21 复核后**维持不变**——ADR-0024 曾考虑改为 `sudo env` 承载……带来安全面与 sudoers 兼容风险」。而 `0024:339` 描述的理由只有后者。
- **判据**：`0015:62` 与 `0016:43` 否掉的是「用 `env` **设任意变量名**」；`0024` 否掉的是「`sudo env K=V` **绕过 sudo 的环境过滤**」。**这是两个不同的备选**，塞进同一格会让后来的读者以为其中一处写错了。
- **修法**：`0016:43` 恢复原状；`0024` 的结论只进 `0016` 的更新记录，并写明「针对的是另一个备选」。

### A7 决定 3「只各加一行更新记录」已经被自己的执行违反过

- **位置**：`0024:237`、`:24`、`:26`；`0015:69`；`0016:43`
- **证据**：ADR 三处重申「只各加一行更新记录」「不改正文」。实际：`0015:69` 远不止一行且掺入了「被证实」这一新判断；`0016` 改的是**备选表正文**而不是更新记录，而 `0016` 本身没有更新记录节。另 `0024:24` 把 `0016` 的决定（值一律双引号、由目标节点展开）列进了「**`0015` 的主体**」清单——归属错。
- **后果**：「只加更新记录」这条决定不可验收，派生出的工单没有判据，执行时必然再次越界。
- **修法**：改写为可验收的形式——「`0015` / `0016` 只改『状态』行与『更新记录』，其余行 diff 必须为 0」；并修正 `0024:24` 的归属。

### A8 「多数发行版保留 `LC_*`」没有被 2 台机器证实

- **位置**：`0024:297`；`docs/adr/0015-远端环境前缀进配置.md:54`、`:69`
- **证据**：`0024:297` 称该说法「在本轮被**证实**」。而 3.2 只有 2 台机器（WSL2 Ubuntu-26.04 / CentOS-7.9），`0024:92` 自己说机制在两边并不相同、`0024:99` 说 Ubuntu 那侧的 `env_check` 是字符过滤而非保留白名单，`0024:386-387` 又承认 SLES / 信创**完全未验证**。`0015:69` 据此写下「被证实……该条无需修改」。
- **后果**：一句未经证实的断言获得了 ADR 背书并被封存，以后没人会回来查。
- **修法**：`0015:69` 与 `0024:297` 同改为「在已测两台成立（机制不同）；SLES / 信创未验证，该条仍属未证实」。

### A9 第四节「实测支持」支持的只是「不改字节链路」

- **位置**：`0024:207`、`:217`、`:224`
- **证据**：`0024:215` 的实测是「三处与目标机 `od -c` 逐字节一致」，`0024:221` 的实测是「切成 936 后同一份字节被解成乱码」。两条证明的是**工具不比目标机多改一个字节**。而 `0024:217`「乱码发生在屏幕那一环」是推断，`0024:222` 自己承认「没能在出厂 936 的机器上直接复现」。
- **后果**：「实测支持」一词把「不改字节链路是安全的」偷换成了「乱码不属于本工具」，而后者是全称判断。
- **修法**：`0024:207` 标题改为「不改变字节链路」；`0024:217` 降为「最可能的一环」；`0024:224` 的「实测支持」改为「实测支持不改字节链路，屏幕那一环属推断」。

### A10 第四节「xlsx 唯一的改写是 `ToValidUTF8`」不确

- **位置**：`0024:213`；`modules/SSHFleet_Go/internal/output/xlsx.go:40-46`
- **证据**：`cleanForExcel` 里除了 `strings.ToValidUTF8`，还有 `ansiEscapeRe.ReplaceAllString`、`excelInvisibleRe.ReplaceAllString`、以及 `\r\n → \n` 的归一。ADR 只说了一处。
- **更要紧的是它没说的**：目标机若仍是 GBK 输出，`ToValidUTF8` 会把 GBK 字节**批量换成 U+FFFD**。现象会从「一片乱码」变成「一片 `�`」，看起来更像工具坏了、更难回溯。
- **修法**：`0024:213` 补齐改写点；并补一句 GBK 输出经过此处时的可见后果。

### A11 第四节「重审」承诺没有可执行形态

- **位置**：`0024:224`；`0024:378-395`（12.2 三类清单）
- **证据**：`0024:224` 只写了「若将来出现『工具内确实看到乱码』的报告，第四节结论需要重审」。12.2 的三类清单里**没有乱码**——没有环境、没有命令、没说看哪几处产物。
- **后果**：真出报告时无从下手，容易重蹈 2.2 记录的那个坑（形态错了再测一遍）。
- **修法**：12.2 的（一）补一行：在 `ACP=936` 的机器上跑 `ls` 列中文名，比对 `terminal-output.txt` 的 `od -c`、xlsx 单元格、终端三处。

### A12 第四节承诺的「手册责任」指不到任何一份手册

- **位置**：`0024:224`（写「见第七节」）、`0024:299-305`（第七节）
- **证据**：第七节**一个字没提乱码**；全文「手册」只出现两次（`:224`、`:304`），都没点名哪一册哪节。`docs/5-常见问题.md` 按症状分节（启动 / 连接 / 执行 / 上传 / 加密 / 结果），但 `乱码` / `方块` / `码页` / `字体` **零命中**。
- **后果**：`doc-guide.md:236-237` 要求常见问题按症状组织、使用者搜的是「乱码」。手册里没有这一节，这条承诺就永远到不了使用者面前——**一条没有认领的决定**。
- **修法**：决定 5 后补一条手册清单（见 §三），或在决定 5 里写明由哪份载体认领。

### A13 第七节把已知的不确定性交还给无从判断的人

- **位置**：`0024:305`
- **证据**：原文「使用者若确需按字符处理中文，把它改回 `en_US.UTF-8` 即可，代价是 3.5 的警告风险由他自己承担」。而 `0024:249` 刚判定这种警告污染是「不可接受的不确定性」，且 `0024:249` 明说「2000 台机器里有多少台没生成 `en_US.UTF-8` 是**不可知的**」。
- **后果**：一个无从知道自己机器状态的使用者，被要求为一个 ADR 自己判定不可接受的风险负责；他照做之后在中文机上当场踩 3.5。
- **修法**：改为附前提的条件句——「改回前先在该机跑 `locale -a | grep -i en_US`；未生成时改回只会引入 3.5 的警告」。

### A14 第一节留下的两个「待定项」没有下文

- **位置**：`docs/issues/2026-10-21-1843-sudo边界语言丢失/spec.md:20`、`:31-37`；`0024:233-239`（决定）、`:352-356`（第十二节）
- **证据**：spec 列了五个待定项。ADR 的「决定」只关闭了「取值」「落点」两项。「兼容性口径」（老配置怎么办）只落在第七节影响里一句「不提供自动迁移」，没进决定清单；「使用者可见面」里的诊断建议——**「代填触发词中英各挂一个」——ADR 全文零提及**。第十二节把待办一律甩给尚未建立的载体。
- **另一处同类丢失**：`spec.md:20` 把「CentOS 能穿过、Ubuntu 不能」登记成「已核实的事实」，而 `findings` 第五节自己写的是「未验证的假设」。**该归因已被本轮实测推翻**（两边都能穿过、机制不同），但 spec 那行至今仍写作事实，没有降级或订正。
- **后果**：① 照 ADR 派生的工单很可能只盯配置，产出「改了两个字符串 + 文档加一句」，而**起因议题里那个「中文触发词失配」的病仍然没治**——这是五项里唯一能直接止血的建议；② 谁若从 spec 入手理解本案，会先读到一条已被推翻的结论。
- **修法**：① ADR 文末加一张**诉求关闭表**（五项 → 本 ADR 的决定 / 明确不做 / 随载体），逐项落定归属；② spec 那一行与 findings 同口径降级，并注明「归因已被 ADR-0024 第二节推翻」。

### A15 `0016` 备选表那次追加，把复核记录的时机也一起塞进了正文

- **位置**：`docs/adr/0016-环境变量值由目标机展开.md:43`；`docs/adr/0015-远端环境前缀进配置.md:69`
- **证据**：`0016:43` 那格写着「本条在 **2026-10-21 复核后**维持不变」，但 `0016` 全文**没有更新记录节**，这条复核因此没有任何登记处；而 `0015:69` 的更新记录说 Ubuntu 那侧靠 `env_check`、`0024` 6.6 也这么引。同一次复核在两份上游文件里的落点不同（`0015` 进「更新记录」、`0016` 进「备选表正文」）。
- **后果**：这是 A6 的连带项——即使 `0016` 那格的措辞改对了，「复核过这一下」这件事仍无处可查；将来谁引用 `0016`，会以为那一格本来就这么写。
- **修法**：与 A6 同批处理；`0016` 若确需记录这次复核，就给它补一节「更新记录」，而不是留在备选表里。

### A16 `C` 的代价缺一条使用者能自查的判据

- **位置**：`0024:187-195`（3.7 代价表）、`0024:304`（第七节）、`0024:262`（U22 那句）
- **证据**：3.7 列出了具体会退化的命令（`awk length / substr / index`、`cut -c`、`${#s}`、`grep -o .`、`wc -m`、`[[:alpha:]]`），但第七节只写「须写进配置手册」，**没有把这些命令收成一句可执行的判据**。作者在 `0024:262` 给的是对**他那批脚本**的判断（「一般这些东西不会是中文」），不是写给使用者的。
- **后果**：使用者读不出「我会不会踩坑」；而 `C` 的退化是静默的（无警告），踩了也不会立刻发现。这一条与轴 3 说的「可预测不等于可观测」是同一件事的两面。
- **修法**：第七节把 3.7 那张表收成一句判据：「脚本里出现 `cut -c` / `awk substr` / `${#s}` / `wc -m` / `[[:alpha:]]` 且要处理中文，就别用 `C`；要改回 `en_US.UTF-8`，先按 A13 的自查确认该机已生成」。这句同时就是手册要写的那段。

## 二、B 类：需要作者决策（判断题，本文不给结论）

### B1 「出厂值」改哪几份文件

改了发布模板之后，工作区那份 `SSHFleet.conf`（作者本机的）跟不跟着改？

- **跟着改**：本地与发布一致，但会动到你自己的配置。
- **不跟着改**：少动一处文件，但本地跑出来与包内不一致，以后排查容易被自己骗。
- **代价**：只差一处文件，但决定了以后「出厂值」这个词指几个文件。

### B2 决定 1 的验收是「改值」还是「效果」

ADR 主论点是「未生成 locale 的机器会多 1～7 行警告」，但第八节明令不探测环境，**验收写不出「警告消失」**（需缺 locale 的真机）。

- **选项一**：验收就写「两份模板的值为 `C`、注释改口、手册同步」——可判、可完成，但工单看起来像「改两个字符串」。
- **选项二**：验收补一条效果项（在缺 locale 的机器上跑一次，确认不再有 locale 设置告警）——更接近初衷，但需要一台特意做出缺 locale 的机器，且要不要建这种环境是另一件事。
- **代价**：选一，验收通过而目标未必达成；选二，工单多一个环境依赖。

### B3 「解释器失败形态」进不进 ADR 的主理由

A3 证明了「`C` 没有失效形态」只对 shell 与 GNU 文本工具成立。python 3.6 会直接 `UnicodeEncodeError`。

- **选项一**：进主理由——6.1 改口为「shell 与 GNU 文本工具这一层最稳」，并把「`C` 下非 shell 解释器的失败形态」列进 12.2 未证实清单。诚实地把承诺收窄。
- **选项二**：保持现状——理由只针对 batch 场景最常用的一类脚本（bash），不改。
- **代价**：选一，6.1 那句「可预测性比最优性重要」的说服力会下降；选二，将来有人拿 `C` 跑 `.py` 脚本挂了，会回来问「ADR 不是说没有失效形态吗」。

### B4 「留空」这个候选要不要处置

`spec.md:35` 列的第三个取值是「留空（跟随目标机）」。ADR 第十节备选表里**没有这一行**；第八节只否掉了「探测环境再配套传变量」，没有否掉「全量留空」。而 `docs/3-进阶配置手册.md:297` 正好教用户「把它的值留空」。

- **选项一**：补一行否掉理由（例如「留空 = 跟随目标机，同一批机器行为不同，破坏逐字可比」）。
- **选项二**：不处理，就让它待在那里。
- **代价**：选一，备选表多一行、论证更完整；选二，使用者照手册自然会想到这条路，而 ADR 没告诉他为什么不选它。

### B5 `0015:54` 末句要不要回头改

`0015:54` 写着「不带外部依赖就修不了这一点」。`0024` 的结论是变量**能**穿过 sudo，这句已经不准确。

- **选项一**：改（这属于「改上游正文」，与 A7 定下的「只加更新记录」相抵，需要你先放宽那条口径）。
- **选项二**：不改，只在 `0024` 里说明该句已被后续实测修正。
- **代价**：上游正文改不改，决定的是「ADR 之间是薄指针还是厚指针」这个长期口径，不只是这一句。

### B6 三份 ADR 的「状态」行怎么标

- `0015` / `0016` 仍是「已接受」，没有「部分被收窄」的标记（仓库里有 `0004` / `0005` 的「部分作废」先例）。
- `0024` 自身写「已接受」，但**尚未落地**。`0021:3` 的写法是「已接受——已实施」。
- **代价**：标不标是形式，但标了以后，下一个读 `0015` 的人才知道它的出厂值那一段已经不作数。

### B7 工单拆几条

轴 1 的判断：这不是宽重构（爆炸半径 4 个字符串 + 若干文档，没有调用点迁移）。按 `doc-guide` 的竖切可以拆成 3 条——模板改值（无阻塞）；手册与 README 重写（阻塞于前者，因为样例要与出厂值逐字一致）；CHANGELOG 与代码注释（无阻塞）。

- **选项一**：拆 3 条，可并行一部分。
- **选项二**：并成 1 条——总量很小，拆开反而多三次交接。
- **代价**：拆多，交接成本高；拆少，一条做不完就要重开上下文（`doc-guide` 的硬指标是「一个上下文窗口装得下」）。

### B8 乱码一节的结论要不要随 A9 降级一并改写标题

A9 把「实测支持」的范围修正了，但第四节标题「乱码：不属于本工具」是判断句。

- **选项一**：保留标题，靠正文的标注区分——论断与标注并存。
- **选项二**：标题改为更保守的说法（如「乱码：本工具不改字节」）。
- **代价**：保留，读者更容易记住结论；保守，读者更容易记住证据边界。这条影响的是这份 ADR 作为「将来被引用时的口径」。

## 四、审计方法与限制

- **六路并行**：五条按视角切的轴（可派生性、标注诚实度、结论边界、上游关系、乱码边界），加一名**不接现成轴、自建框架**的审计员（它按「谁会出事、在哪一步出事」切，抓到 A13、A14 两条轴内的盲区）。
- **实测来源**：3.1 的 WSL2 双发行版、`C` 下 python 的失败形态、perl 的警告行数、`cut -c` / `${#s}` 的字节与字符差异，由轴 3 在 WSL 里实跑（临时探针写 `build/axis3-tmp/` 后已删除，仓库零改动）。
- **代码主张**：第四节五条论据逐条核对到函数，四条属实、一条不确（A10）。
- **两处冲突由主审计仲裁**：perl 行数与「200 组抽样」——裁决依据是「同批产物写 bash 2 行」与「`build/` 内检索零命中」；xlsx 改写点——以读过 `xlsx.go:40-46` 的一侧为准。
- **一份轴内结论落了空**：轴 2 报告里有一条「`xlsx.go` 之外还有 `reporter.go:515-519` 按 rune 截断、非法字节变 U+FFFD」——**这一条本轮没有复核，因此没进 A 类**。如果工单要引用 A10，应连同这一处一起查。
- **未覆盖 / 未证实**：
  - 「留空」候选的实际行为未实测（B4 只讨论要不要处置这个候选，不讨论它的行为）；
  - `node` / `php` / `java` / `ruby` / `lua` 在 `LC_ALL=C` 下的行为**未实测**（WSL 里没有这些运行时）；`interpreterTable` 里还有 `ruby` / `lua` / `luajit` / `nodejs` 等，A3 的可外推范围仅到「python 系列 + shell」，其余为推理；
  - 3.8 的百分比在没有原脚本的情况下**无法复核**，A5 的处置是「补产物或删数字」，不是「证明它错」；
  - uutils coreutils 那一条（`0024:329-331`）在 `build/` 里同样零产物，性质同 A5，但没进 A 类是因为它只作旁证、不承重——**若工单里要引用它，按 A5 同一标准处理**；
  - A1 只核实到「打包脚本复制模板」这一步，程序运行时是否回写工作区那份 conf**未核**（见 A1 证据）。
