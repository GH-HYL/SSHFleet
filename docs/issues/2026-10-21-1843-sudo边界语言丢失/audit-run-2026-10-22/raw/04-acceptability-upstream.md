## 1. A2「拼接形态不变」的验收写法与现有观察点

**结论：现有测试不能判死「形态未变」。** 拿「现有测试全绿」当 A2 的验收是假验收。

### 1.1 现有测试里可用的哨兵（只有两条）

| 观察点 | 位置 | 能判什么 | 判不了什么 |
| --- | --- | --- | --- |
| `TestBuildCommandEmptyEnvPrefix` | `command_test.go:36-43` | 空前缀下 sudo 形态**逐字**钉死：`sh -c 'bash'`、`sh -c 'sudo bash'` | 空前缀恰好绕开了 A2 的核心（`export` 与 `sudo` 的先后） |
| `TestBuildCommandCommandTextNotOnCommandLine` | `command_test.go:229-245` | 外壳仍是**一层** `sh -c '…'`，单引号恰好一对 | 同上；且只覆盖 direct 路径 |

### 1.2 现有测试判不死的三处

1. **非空前缀 + sudo 的拼接顺序无逐字断言。** `TestBuildCommandSudo`（`:77-82`）只判 `strings.Contains(cmd, "sudo bash")`；`TestBuildCommandCommandMode`（`:14-33`）在 sudo 路径上是**反向**断言（`!Contains(cmd,"sudo")`）。把下发串改成 `sh -c 'sudo bash -c "export …; …"'`，两条测试都仍会绿。
2. **日志侧与下发侧不是同一个串。** `TestDescribeCommandScriptMode`（`:353-377`）期望说明里出现 `sh -c 'export LC_ALL=C; sudo bash'`，而脚本模式下 `BuildCommand` 还要补 `. /dev/stdin` 与脚本名（`TestBuildCommandScriptKeepsScriptName:135-150`）。两条期望**互斥**，至少有一侧不是逐字下发串。哪一侧，需要 `command.go`——不在本轴白名单（见 U1）。
3. **`-a` 交互路径没有形态断言。** `InteractiveCommand` 在 `command_test.go:429-434` 只被断言 `perl -e `，无外壳、无 `export` 位置断言。A2 只写「两条路径」（非 sudo / sudo），这条是第三个构造点（见 J2）。

另注（不构成缺陷，但会误导验收）：测试夹具的 env 常量一律写作 `export LC_ALL=C;`（`:15`、`:299`、`:354`、`:381`）——裸拼、无引号，与 ADR-0016 的「值一律双引号」不符。它只是入参字面量，但照抄成验收基线会让人以为下发串里没有引号。

### 1.3 A2 的可验收写法（建议落点与判据）

- **落点**：既有接缝 `ssh.BuildCommand`（`command_test.go` 已覆盖），**不新增接缝**。
- **验收项**（均可由外人判定）：
  1. `BuildCommand("ls -l","","","bash",`export LC_ALL="C";`,false,false)` 返回值**逐字等于** `sh -c 'export LC_ALL="C"; bash'`。
  2. 同参数 `asRoot=true` 逐字等于 `sh -c 'export LC_ALL="C"; sudo bash'`。
  3. 反向断言（任一命中即红）：不含 `sudo env`、不含 `sudo -E`、不含 `--preserve-env`；`strings.Count(cmd,"sh -c")==1`；sudo 路径下 `Index(cmd,"export") < Index(cmd,"sudo")`。
  4. 解释器遍历 `bash` / `python3` / `perl` / `php` 各一条：`export` 段在内层最前、紧接 `<sudo ><解释器>`，且 `export` 不出现在解释器之后。
  5. 保留 `:36-43` 两条空前缀回归（不得删除）。
  6. 日志侧另立一条：`DescribeCommand` 的渲染串含第 1/2 条的命令行；**但不得作为 A2 的唯一判据**（1.2 第 2 点）。
- **判死依据**：任何人把 `export` 挪到 `sudo` 之后、或改走 `sudo env`，第 1–4 条必红。今天的测试在这个改动下全绿——这句要写进工单，防止「跑一遍现有测试就算过」。

### J3（判断题）6.6「只证实、不推翻」的二分不够用

6.6 引 0015:54 全句后判定「括号里的『多数发行版保留 `LC_*`』在本轮被**证实**，不是被推翻」（`0024:293-297`）。以 0015 正文为准，该条有三段：

- 末句「**不带外部依赖就修不了这一点**」——前提是「过不了」；3.1 实测能穿过后，这句失去对象。它不是被「证实」，是**不再适用**。

- 选项 B：维持「证实 / 不推翻」二分。代价：0015 主句与末句继续以「已证实」姿态存活，复审者不会去动它。

## 5. 第八节「不探测目标机环境」vs 12.2 的补法

**结论：未发现冲突。** 作用域不同，且第八节自己划了边界。

- `0024:312`：「**不在下发时探测**目标机环境再配套传变量……包括『先探 `locale -a` 再决定传哪个值』这类只读探测。**取值一次定死，全量下发。**」

## 6. 第一节 / 第二节 / 第四节 / 9.1 / 更新记录 的自洽性

### 【硬伤 H3】「最后核对：无复审」与更新记录互斥

> `0024:5`：「**最后核对**：2026-10-21（本轮建立，**无复审**）」<br>
> `0024:403`：「2026-10-21：**复审后的修订**（两份独立审计的结果）」

同一份文件的两处元数据对「有没有复审过」给出相反答案。前者会让复核者跳过「复审已改过什么」这条线索。

### 【硬伤 H4】第一节的现象 2 仍保留了被判定为「检索不到」的环境归属

> `0024:37`：「2. 在**外部 SSH 工具与服务器物理控制台上**，`ls` 列中文文件名会显示成「方块和特殊符号」。」<br>
> `0024:222`：「开发者描述『`ls` 列中文名出现方块』时**没有说明发生在哪个环境**——本轮 21 条作者原话里检索不到『只在外部 SSH 工具 / 物理控制台见过』这类表述。」<br>
> `0024:405`：「**删掉**「他随后确认，乱码只发生在外部 SSH 工具与物理控制台上」——本轮 21 条作者原话里检索不到这句」

第四节删了、更新记录说删了，第一节用陈述语气留着同一个归属。三处不能同时为真。第四节是 A5 的依据，第一节是读者看到的第一段——读者会先信第一节。

### 【硬伤 H5】第二节 2.2 的实验命令按原文照抄测不出所记现象

> `0024:56`：`printf 密码 | sudo -S bash -c "printf 密码 | sudo -S bash -c 'echo $LANG $LC_ALL'"`

外层是**双引号**，`$LANG` / `$LC_ALL` 会先被本地 shell 展开，内层 `echo` 拿到的是字面值。实际输出（未用 sudo，只验引号语义）：

```
$ DEMO=local-value bash -c "bash -c 'echo $DEMO'"
local-value
$ DEMO=local-value bash -c "bash -c 'echo inner=\$DEMO'"
inner=
```

第一行就是 2.2 的写法：内层变量在内层作用域里根本没有被读。所以按原文照抄，无论 sudo 怎么重置都观察不到「`LANG` 被重置成 `C.UTF-8`」。2.2 记的观察只能来自另一个（未记录的）写法——这条「当时怎么测的」不可复现，而它正是 2.3 与 12.1-1 的方法论立论来源。

### 【硬伤 H6】第四节「工具不产生乱码」是全称化过头（判点②）

> `0024:209`：「取证结论是**工具不产生乱码**」<br>
> `0024:213`：「写 xlsx 全仓唯一的改写是 `strings.ToValidUTF8(s, "\uFFFD")`——只处理**非法** UTF-8，合法字节一字不动」

ADR 自己承认：**非法** UTF-8 会被替换成 U+FFFD。目标机若输出 GBK（如 `zh_CN.GBK` 或码页 936 下程序输出），在 UTF-8 视角下就是非法字节序列 → 进 xlsx 时被改写 → 那就是「工具产生的乱码」（一串 `�`）。所以正确的全称只能是「**对合法 UTF-8 输入**，工具不产生乱码」。

这条承重：A5「乱码不作为处置对象」的依据就是它。范围洞不补，A5 的排除面就少一块（非 UTF-8 输出）。

### 【硬伤 H7】第四节判据表把 `?` 归因给码页，与 9.1 的根因冲突

> `0024:231`：「`涓╣慨` / `锟斤拷` / **`?`** | **编码 / 码页不一致** | 调字号无效，形状不变」<br>
> `0024:321`：「`emoji😀.txt` 变成 **`emoji?.txt`**……根因在 **coreutils 面向终端时的显示宽度判定（`iswprint`）**，不在工具，也不在传输层」

同一个 `?`，两种根因；而第四节的判据（「调字号无效，形状不变」）对两者都成立，无法区分。手册若照这张表给判据（轴 5 域），9.1 的 emoji 案例会被误判成编码问题。

### J7（判断题）9.1 的复现环境与 9.3 并列时缺少实现名

## 锚质疑

### 质疑 A3：落点在 0016 不存在

- 质疑对象：A3「不收窄、不废除 0015/0016 正文，**只各加一行更新记录**指向本 ADR」。
- 来源：0016 正文（`grep -n "^## "` 只有 背景/决定/理由/影响/备选方案）+ `git show f185e8c`（0016 为 `-1/+1`，落在备选方案表内）。
- 差异：A3 假设两份上游 ADR 都有「更新记录」容器。0015 有；0016 没有。因此「只各加一行」在 0016 无处落，已发生的改动只能是正文改写——这已经不是 A3 描述的形态。
- 影响：决定 3 无法派生可验收工单（10.3 的判据 2 需要先建节）。要么 A3 改成「0015 加一行更新记录；0016 新建更新记录节并迁入该句」，要么承认「0016 允许正文追加一句」——两者是不同的授权范围，需作者 / 复核定。
- 本轴不改锚：只报差异，改法由 spec 侧定。

### 质疑 A5 的边界（不质疑 A5 本身）

A5「乱码不作为本决策的处置对象」的取证依据是第四节「工具不产生乱码」。H6 显示该结论只对**合法 UTF-8 输入**成立。若 A5 的排除面按现状写，会连「目标机输出非 UTF-8 时 xlsx 出现 `�`」一起排除。这不是 A5 的授权问题（作者确实说过乱码不处置），是**范围表述**与第四节结论的口径不一致——建议 A5 保持，第四节的全称收窄，二者即可自洽。

### 未质疑的锚

A1、A2、A4 未发现与白名单内材料冲突。A2 的「两条路径」与代码里的第三个构造点（`-a`）之间的关系见 J2，不构成对 A2 本身的质疑。
