## 一、我这一套框架是什么、为什么这么切

### 1.1 为什么不用现成五轴的切法

五轴都按「**面**」横切：派生落点面、结论边界面、产物面、可验收面、文档面。横切的长处是每一格都能判「真/假、可追/不可追」；短处是**没有一条轴负责「合起来能不能用」**——而本轮题目问的恰恰是「这份 ADR 够不够格**派生** spec 与工单」，那是**下游可用性**问题，不是「每一节是否正确」问题。

横切的第二个短处：分域是按**节号与文件名**划的，**节与节之间、以及不在任何轴清单里的段落**（文首 20–28 行、第八节、第十二节的自述与内容）天然落在缝里。缝不是边角料，§2 里三条真缝都通向硬伤。

所以我换成一纵一横：**纵向四道闸判「从读到用会不会卡」**，**横向一道元闸判「节与节之间是否自相矛盾」**。

### 1.2 五道闸

| 闸 | 问法 | 判据 | 抓到什么（本轮实例） |
| --- | --- | --- | --- |
| **闸 1 可编译性** | 拿 ADR 当**唯一输入**、假装我是没参加过对话的实施者，把五条决定各写一份工单草稿 —— 在哪儿被迫补脑？ | 出现「指认了 A、实际要改 B」「找不到落点」「要自己编文案」即未过闸 | H1、H2、J5 |
| **闸 2 决定闭合** | 每条决定是否三件齐备：**变更对象**（哪个文件/哪类机器）、**验收谓词**（可观测、可否证）、**越界声明**（谁不管） | 缺一即「未闭合」，未闭合的决定派生不出可判死的工单 | H1、H2、J6 |
| **闸 3 前提出处** | 把理由链上的断言拆两类：**世界事实**（解释器行为、发行版机制 —— 有轴 2/3 在测）与**需求前提 / 文档现状前提**（「同批逐字可比」「2000 台」「十数年」「存量配置不改」—— **五轴无人测**） | 承重前提必须能指到出处；指不到就得降级措辞 | N2（有出处）、N3（有出处）、J6（后果无人认领） |

| **闸 5 结构自洽（元闸）** | 跨节矛盾、同一条写两遍、交叉引用指错、状态与时间链 | 需附原文两处坐标 | H6、H7、J1、J3 |

### 1.3 这套切法会漏什么（自查）

- 漏「单个事实的真假」：3.1/3.2 的发行版机制我判不了（U1），只能交给轴 2/3。
- 漏「文档措辞的一贯性」：手册里哪些句子要改，我没逐句扫（归轴 5）。
- 漏「工单字段规范」：我没读 `issue-tracker.md` 的必填项（归轴 1）。

也就是说：**这套框架不与五轴竞争覆盖率，它补的是「缝合处的可用性」**。凡我报的发现与某轴重叠，我在条目末尾写明；重叠不等于重复——轴看的是「这一节对不对」，我看的是「读者在这一步会不会卡」。

## 二、我认为五轴的五处盲区（附证据，不是猜测）

**盲 1 · 文首前言（20–28 行）没有任何轴的主审。**
`prompts-v3.md` §3 的覆盖表把「一、二、四、9.1、更新记录」判给轴 4，把「五、七、9.2」判给轴 1，把「三」「六（6.1–6.5）」判给轴 2 —— **文首这 9 行不在任何一格**。而文首含一条与决定 3 冲突的断言（「它**收窄** ADR-0015 的「影响」一节」，`0024:24`）。这条断言若被工单采用，会派生出一张「改 0015 影响节」的工单；而 0015 自己的更新记录写着「该条**无需修改**」（`0015:69`）。见 J1。

**盲 2 · 「决定 3 能不能落地」与「决定 3 改得对不对」是两个问题，只有后者有人审。**
轴 4 Q2 的问法是「A3 与 `0015:69`、`0016:43` 的**实际改动**逐项比对」——即拿已落盘的改动去核锚。但派生工单要问的是「照 A3 写，实施者能不能落笔」。`grep -c '更新记录' docs/adr/0016-环境变量值由目标机展开.md` = **0**：0016 没有「更新记录」这一节，A3 的「各加一行更新记录」对这一份**无处可落**（实际那一行被塞进了 `0016:43` 的备选方案表格里）。见 H2。

**盲 3 · 上游 ADR 的「决定」正文里也有出厂值，没人判它是否过期。**
轴 4 的白名单含 0015 全文，但 Q2 只让它比 `0015:69` 那一行；轴 1 的白名单不含 0015。于是 `0015:28-29` 这两行——

```
  LANG   = "en_US.UTF-8"
  LC_ALL = "en_US.UTF-8"
```

——它们就躺在 0015 的**「决定」第 1 条正文里**，A1 实施后即为过时事实，而所有轴的问题清单都不指向它。见 §3 锚质疑。

**盲 4 · 分类关键词与 A1 的耦合无人认领，因为 `keywords_*.conf` 被显式排除了。**
固定件写「三份 `keywords_*.conf` 已核**不含** `[env]` / `LANG` / `LC_ALL`（0 命中），审计时按「排除」处理」。这个排除是对的——它排除的是**关键词文件里有没有 env 配置**。但 A1 改变的是**目标机程序输出的语言**，而失败分类正是拿这些关键词去匹配目标机输出。这是一个真交叉问题，被「0 命中」这句排除话术顺手关掉了。我核了，结论是没问题（N3），**但那是运气好，不是有人查过**。

**盲 5 · 量化的「复算基准」没人区分。**
轴 3 Q3 要求复算 3.8 并「报你得到的比例与 ADR 数字的差异」。但本机是 uutils 0.12.0 + 无 `en_US.UTF-8`，ADR 的基准是 GNU coreutils 8.22 + 已生成的 `en_US.UTF-8`（CentOS 7.9）——两边的「B 组」根本不是同一个东西。照 Q3 的原话，审计员很容易把「0% / 90% vs 0% / 85%」写成「数字对不上」，而真相是「数字对得上，基准不可比」。我在 N1 里按「先归因工具链、再判数字」处理。

**盲 6（轻）· 「谁来实施、在哪验收」不在任何轴里。**
五轴都在判「工单能不能写」，没有轴判「这批工单交给谁、在哪验」：本机 `sudo` 不可用、无 CentOS / Ubuntu-26.04、`build/` 按天清理。阶段 A 不需要答这个，但派工单前需要知道「验收要靠外借环境」。这不是某条轴的错，是切法本身的留白。

## 三、锚质疑（单列，不并入普通发现）

### 锚质疑 1：A3「只各加一行更新记录、不碰正文」与 ADR-0015 正文及本仓既有做法冲突

- **锚**：A3 =「不收窄、不废除 ADR-0015 与 ADR-0016 的正文，只各加一行更新记录指向本 ADR」（`0024:237`）。
- **冲突来源**：上游 ADR 正文（属锚质疑的合法来源）。
- **证据一**：`0015:24-31` 的「决定」第 1 条正文里，出厂值是以**代码块**形式写死的，当前内容为 `LANG = "en_US.UTF-8"` / `LC_ALL = "en_US.UTF-8"`（`0015:28-29`）。A1 实施后，这两行成为与出厂值相反的过时事实；按 A3 不许碰正文，它就会**一直留在 accepted 状态 ADR 的「决定」节里**。
- **证据二**：同一个文件里已有**相反的先例**。`0015:70`（2026-10-09 的更新记录）处理同一类冲突时，做法是**点名正文里失效的段落**：「上文「决定」第 3 条里…、「理由」中…、「备选方案」中…均**不再约束**」。也就是说本仓的既有做法比 A3 更重：既加记录，**也**在正文层面声明失效。
- **冲突在哪**：A3 把「不碰正文」定为纪律，而 0015 的正文里正躺着一个 A1 会改掉的值；两者只能保一个。这不是「A3 对不对」的问题——A3 是一份范围判断，但它的范围**没有覆盖到「正文包含被改对象本身」这种情形**。
- **我不改锚**。可选出路（供 spec 决定，不是我的建议）：① A1 的工单范围显式包含 `0015:28-29`；② A3 追加一句「正文中与出厂值矛盾的代码块以更新记录为准，不改字」；③ 维持 A3，接受 0015 决定节带一处过时值。
- 与轴 4 的问题域：**重叠**（同属 A3；轴 4 Q2 比对的是已落盘的那一行，未覆盖 0015 决定节正文）。

> 除此之外**没有**发现其他锚与实测 / 源码 / 上游正文 / spec / 四判点冲突。A1、A2、A4、A5 我没有可据以质疑的证据；A5 的范围声明与第四节结论一致。

## 四、发现

### 硬伤

#### H1【硬伤】第七节指认的落点，恰好是唯一「不随包发布」的那份配置

- **判点①**（决定 1 能否落成可验收工单）
- **证据**
  - `0024:301`：「**配置**：`config/SSHFleet.conf` 的 `[env]` 段，`LANG` 与 `LC_ALL` 两行由 `"en_US.UTF-8"` 改为 `"C"`」——全文只有这一处指认落点，且是单数。
  - `grep -n 'for-linux\|for-windows\|打包\|build-linux\|build-windows\|模板' docs/adr/0024-env穿过sudo边界.md` → **0 命中**。
  - `build-linux.sh:15-17`：「出厂配置按平台取：config/SSHFleet-for-linux.conf / SSHFleet-for-windows.conf 各自复制成包内的 config/SSHFleet.conf。**工作区里那份 config/SSHFleet.conf 是作者本机在用的配置，不随包发布。**」
  - `build-linux.sh:101` / `:103`：`cp -f "$CFG/SSHFleet-for-windows.conf" "$WPKG/config/SSHFleet.conf"` / `cp -f "$CFG/SSHFleet-for-linux.conf" "$LPKG/config/SSHFleet.conf"`。
  - `build-windows.bat:102-104` 同上，且注释写明「**不能**拷工作区里那份 config\SSHFleet.conf」。
- **为什么是硬伤**：照第七节写工单、验收也照第七节判（`grep` 那份文件确已变成 `"C"`），**发出去的包内仍是 `en_US.UTF-8`**。这是「工单验收通过、使用者拿到的值不同」的完整路径，不是理论风险。
- **附带**：这条同时使 J6 更严重——按第七节改，连**新装用户**都拿不到新值。
- 与轴 1 的问题域：**重叠**（正是轴 1 Q2 的那条路径）。

#### H2【硬伤】决定 3 对 ADR-0016 无处落笔

- **判点①**
- **证据**
  - `0024:237`：「只各加一行**更新记录**指向本 ADR」。
  - `grep -c '更新记录' docs/adr/0016-环境变量值由目标机展开.md` → **0**。0016 的章节是 背景 / 决定 / 理由 / 影响 / 备选方案，**没有「更新记录」节**。
  - 0016 里指向 0024 的那句话实际长在**备选方案表的一格里**（`0016:43`），且不是「一行更新记录」，而是一段含新判断的话：「本条在 2026-10-21 复核后**维持不变**——ADR-0024 曾考虑改为 `sudo env` 承载，实测证明现状的 `export` 已能穿过 `sudo`，改造无收益…」。
  - 对照 0015：`0015:69` 确有更新记录节，那一份是照 A3 做的。
- **为什么是硬伤**：A3 的两个对象里，一个能落、一个没有落点。实施者拿到的工单会写「给 0016 加一行更新记录」，打开文件找不到该节 —— 要么自己发明一节（改变文档结构，超出决定授权），要么塞进别处（即现状）。两种做法都没有判据可判死。
- 与轴 4 的问题域：**重叠**（同属 A3；轴 4 Q2 判「改得对不对」，本条判「能不能落笔」）。

#### H3【硬伤】6.1 的「永远成功、永远安静」对 python 不成立，且失效形态比警告更脏

- **判点②**（理由链全称化过头）
- **证据**：`0024:251`「`C` 则**永远成功、永远安静**、永远是英文、永远按字节。」
  - 本机 python 3.14.8 **默认开着 UTF-8 模式**（`sys.flags.utf8_mode == 1`），所以 `LC_ALL=C` 下 print 中文正常 —— ADR 的结论在这一台上碰巧成立，但**成立的原因不是 `C`，是 PEP 540/686**。
  - 关掉 UTF-8 模式（等价于「无 `C.UTF-8` 可用时的 Python ≤ 3.13」；PEP 686 的默认开启落在 3.15）：

    ```
    $ env -i LC_ALL=C PYTHONUTF8=0 PATH=/usr/bin:/bin python3 -c 'import sys,locale;sys.stderr.write("stdout=%s pref=%s\n"%(sys.stdout.encoding,locale.getpreferredencoding(False)))'
    stdout=ascii pref=ANSI_X3.4-1968
    $ env -i LC_ALL=C PYTHONUTF8=0 PATH=/usr/bin:/bin python3 pyw.py     # 文件内容 print("中文")
    UnicodeEncodeError: 'ascii' codec can't encode characters in position 0-1: ordinal not in range(128)
    rc=1
    $ env -i LC_ALL=C PYTHONUTF8=0 PATH=/usr/bin:/bin python3 -c 'open("cn.txt").read()'
    UnicodeDecodeError: 'ascii' codec can't decode byte 0xe4 in position 0: ordinal not in range(128)
    ```
  - 对照：同一台、同一解释器、`LC_ALL=zh_CN.UTF-8` + `PYTHONUTF8=0` → `stdout=utf-8`，`rc=0`。
- **为什么是硬伤**：这条全称句是 A1 的**主承重理由**（3.4/6.1 的「失效形态不存在」）。对 python 而言：
  1. `C` 下并不总是「成功、安静」；
  2. 失败时是 **traceback 多行 + 非零退出码**，比 3.5 拿来否定 `en_US.UTF-8` 的「1 行警告」更脏（而且 rc=1 会改变执行结果的判读）；
  3. 更关键的方向性后果：在**已生成 `en_US.UTF-8`** 的机器上，python 脚本原本可用；A1 之后变成 rc=1。**这是净退化，不是净改善**，而 ADR 的代价清单（3.7）只写了「按字节/按字符」，没有这一条。
  4. ADR 全文没有出现 `PEP 538` / `PEP 540` / `PEP 686` / 「UTF-8 模式」任一概念 —— 机制完全没进论证。
- **标注**：`PYTHONUTF8=0` 是**可控模拟**，不是原生 3.6 二进制（本机无更老 python）；结论的适用范围我按「≤3.13 或无 `C.UTF-8` 的目标机」写，不外推。ADR 的 12.1 第 3 条要求的正是这种「在哪台机器、什么形态」的标注，这一条没做到。
- 与轴 2 的问题域：**重叠**（轴 2 Q1/Q4）。

#### H4【硬伤】3.5「perl 那 7 行的构成是固定的」——本机 perl 是 19 行，且构成随版本变

- **判点②**
- **证据**
  - `0024:157`：「perl 那 7 行的构成**是固定的**：`Setting locale failed.` / … / `Falling back to the standard locale ("C").`，第 8 行才是程序自己的输出。」
  - 本机实测（perl 5.42.3，`LC_ALL=en_US.UTF-8` 未生成）：

    ```
    $ env -i LC_ALL=en_US.UTF-8 PATH=/usr/bin:/bin perl -e 'print "hi\n"' 2>&1 >/dev/null | wc -l
    19
    ```

    stderr 依次列出 `LANGUAGE`、`LC_ALL`、`LC_CTYPE`、`LC_NUMERIC`、`LC_COLLATE`、`LC_TIME`、`LC_MESSAGES`、`LC_MONETARY`、`LC_ADDRESS`、`LC_IDENTIFICATION`、`LC_MEASUREMENT`、`LC_PAPER`、`LC_TELEPHONE`、`LC_NAME`、`LANG`，**每个类别一行**；ADR 那份 7 行只列了 3 个变量。
- **为什么是硬伤**：数字不是「固定的」，是**随 perl 版本枚举多少 LC_* 类别而变**。这条数字承重两处：3.5 的表格与 6.1 的「每次 perl 多 7 行警告灌进输出」（`0024:249`）。数字错不改变 A1 的方向（19 行比 7 行更难接受），但**改变了工单里若引用该数时的写法**——写「7 行」会被现场打回。
- **范围**：ADR 的 7 行是 CentOS 7.9（perl 5.16 时代）得到的，那一版的具体行数我**判不了**（无该环境，见 U1）；能判的是「固定」这个全称词在现行 perl 上不成立。
- 与轴 2 的问题域：**重叠**（轴 2 Q2）。

#### H5【硬伤】9.3「uutils 遇到任何非 `C` / `POSIX` 的 locale 名就一律按码点排序」——机制句反了

- **判点②**
- **证据**（uutils 0.12.0，Ubuntu 26.10；语料 `b A a B _x`）

  ```
  sort: C -> A B _x a b | C.utf8 -> A B _x a b | POSIX -> A B _x a b
        zh_CN.UTF-8 -> a A b B _x | xx_YY.UTF-8 -> a A b B _x | de_DE.UTF-8 -> a A b B _x | <unset> -> A B _x a b
  码点序（python sorted）: A B _x a b
  ls:   C -> A B _x a b ; zh_CN.UTF-8 -> a A b B _x ; xx_YY.UTF-8 -> a A b B _x
  ```

- **判读**：
  - 「**不检查是否真的装了**」这半句**成立**：`xx_YY.UTF-8`（不存在的 locale 名）与 `zh_CN.UTF-8`、`de_DE.UTF-8` 给出**完全相同**的顺序。
  - 「**一律按码点排序**」这半句**不成立**：非 `C` 名的输出是 `a A b B _x`，而码点序是 `A B _x a b`。它用的是**某种不随 locale 名变化的排序规则**（大小写不敏感的 collation），不是码点序。
  - 于是 9.3 的**结论**（「同一个 `en_US.UTF-8`，GNU 与 uutils 上排序结果可能不同」）**方向仍然成立**，但成立的理由与文中写的相反：不是「uutils 走码点」，而是「uutils 走固定 collation、GNU 在未生成时回落 `C` 走字节」。结论对、机制错，正是最容易被下游照抄进测试用例的那种错。
- **范围**：ADR 写的是 **0.8.0**（Ubuntu 26.04），本机是 0.12.0；0.8.0 上的行为我**判不了**（无该版本）。但 9.3 通篇没有写「本结论只对 0.8.0 成立」，这是可判的：适用面没写清。
- 与轴 3 的问题域：**重叠**（轴 3 Q5 问适用面；本条进一步给出机制反证）。

#### N1【未发现问题】3.8 的量化表：数字方向可独立复算
