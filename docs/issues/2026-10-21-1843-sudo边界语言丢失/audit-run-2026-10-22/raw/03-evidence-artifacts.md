## 3. 第 3 问：3.8 那张表的复算

脚本：`build/audit-2026-10-22-axis3/repro-3.8.sh`、`sens-3.8.sh`（均可用 `bash` 重跑）。
核心工具：**uutils coreutils 0.12.0 的 `sort` / `ls`**；生成器 **mawk 1.3.4**；驱动 **bash 5.3.9**。

### 3.1 直接结果

```
lower:  结果不同 0 / 200 组
mixed:  结果不同 200 / 200 组
16 行清单里位置不同的行数: 16
ls 16 项里位置不同的行数: 16
```

| ADR 3.8 行 | ADR 数字 | 本轴复算 | 差异 |
| --- | --- | --- | --- |
| 纯小写字母 + 数字 | 0%（200 组） | **0 / 200 = 0%** | 一致 |
| 大小写混合 + 下划线 + `IP` | 85%（170/200） | **200 / 200 = 100%** | **+15 个百分点** |
| 典型主机名清单（16 行） | 12 行位置不同 | **16 / 16 行** | **+4 行** |

### 3.2 为什么不能据上表说「ADR 的 85% 错了」

ADR **没有给出**样本生成规则（每组几条、词干怎么造、16 行清单具体是什么），所以这不是「同一实验的第二次结果」，而是「同构重建」。我做了敏感性检查，固定 200 组、只改每组条数：

```
per=2  seed=20261022 → 不同  61 / 200   (30.5%)
per=3  seed=20261022 → 不同 114 / 200   (57.0%)
per=5  seed=20261022 → 不同 167 / 200   (83.5%)
per=8  seed=20261022 → 不同 198 / 200   (99.0%)
per=12 seed=20261022 → 不同 200 / 200  (100.0%)
```

**只改「每组几条」这一个未公开参数，比例就从 30.5% 漂到 100%。** 85% 落在 `per≈5` 附近——说明这个数字编码的是某个未写出的抽样规则，而不是「大小写混合数据」的固有属性。16 行清单同理：我用的清单每两行构成大小写对，天然最大化重排，所以 16/16；ADR 的清单里若有未成对的名字，12/16 完全可能。

结论：**3.8 的三个数字在缺少生成器时不可复核**。0% 这一格方向稳健（凡纯小写+数字，两种 collation 在 ASCII 上同序），另两格不可复核。

### 3.3 与 ADR 3.8 的另一处结构性差异

3.8 没有标注复算环境。对照 3.6 明写「（CentOS 7 / GNU 工具链）」，3.8 连「GNU 还是 uutils」都没写。而本机 uutils 0.12.0 的 `sort` 在 `en_US.UTF-8`（**该 locale 在本机根本没安装**）下确实做大小写折叠排序：

```
$ printf 'Z\na\nB\n_b\n' > codepoint.txt
$ LC_ALL=C sort codepoint.txt
B
Z
_b
a
$ LC_ALL=en_US.UTF-8 sort codepoint.txt     # stderr 为空
a
_b
B
Z
```

即：`C` 与 `en_US.UTF-8` 在这台机器上**有差异**（因此「差异存在」这个方向成立），但实现与 0.8.0/GNU 8.22 是否同构，无法在本机确认。**版本不写清，这组数字就没有确定的外延。**

## 5. 第 5 问：9.3 的 uutils 结论，适用面写清了没有

**没写清，且本机实测部分反证。** 三个层次：

**（a）版本只在两处出现，且互相打架。**

- `0024:331`：「`ls` / `sort` 等是 Rust 重写的 uutils **0.8.0**」
- `0024:349`：「Ubuntu-26.04（… uutils coreutils **0.8.0**）」
- 但 `0024:321`（9.1）：「Ubuntu 26.04（**coreutils 9.5**）不复现」

同一个 Ubuntu 26.04，一处说 uutils 0.8.0、一处说 coreutils 9.5。这两个不可能同时成立（9.5 是 GNU 版本号谱系）。ADR 没有解释这处并存，读者无法判断 9.3 的结论到底绑在哪个二进制上。这是**硬伤（标注不一致）**，见 §6-H2。

**（b）「按码点排序」这一条在本机 0.12.0 上不成立。** 输出见 §3.3：`en_US.UTF-8` 下 `a`/`_b`/`B`/`Z`，不是码点序（码点序应为 `B`/`Z`/`_b`/`a`）。也就是说 0.12.0 对非 `C` locale 做了大小写折叠的 collation，而不是「一律按码点」。

**（c）「不检查是否真的装了」这一半**：`en_US.UTF-8` 在本机 `locale -a` 里没有（`locale -a | grep -c '^en_US'` → `0`），`sort` 照常按该 locale 的规则排、stderr 为空；而 `locale` 命令自己会报 `Cannot set LC_ALL to default locale`。这一半与 ADR 的描述相容。

**适用面判断**：结论被绑定在「Ubuntu 26.04 + 0.8.0」这一格，但正文用「Ubuntu 26.04 已改用 uutils coreutils」这种发行版级口吻陈述，且未写「此结论仅对 0.8.0 成立」。当前 Ubuntu 26.10 已到 0.12.0，行为已变。**该结论不能作为长期事实引用；作为旁证可以，但必须带版本，且版本要与 9.1 的口径统一。**

判定需要 ADR 作者指出 3.1 的原始记录位置。**本轴记「不可判（无产物）」。**

## 7. 四个判点的结论（只报差异）

**① 每条决定能否落成可验收工单** —— 本轴不判（属判点总责，非本轴域）。

**② 理由链里有没有全称化过头的事实主张** —— 报两处：

- `0024:331`「它遇到**任何**非 `C` / `POSIX` 的 locale 名就**一律**按码点排序」：全称量词 + 具体行为断言，本机 0.12.0 反例（§3.3）。属全称化过头。
- `0024:110`「**两代都保留**，只是代码路径不同」：这句把 1.6.9/1.7.x 与 1.8.5+ 一起打包成「都保留」，但同句前半承认 1.8.5 起只剩 `env_check`（字符过滤而非保留白名单）。「保留」的语义在两代不同，用一个词覆盖，属轻度全称化。位置 `0024:110`。

**③ 承重量化结论有没有产物可追** —— 见 §2、§4。结论：**Q1/Q2/Q3/Q6 四条承重结论全部无有效产物；Q7 半承重且不可定量复现。**

**④ 标注是否诚实（实测／源码推断／未验证）** —— 总体是**诚实度较高**的一份文本：`0024:219-222` 主动区分实测/未能复查/推断，`0024:370-371` 主动点名「CentOS 5/6 是源码推断」「3.1 的表格是在 WSL2 上测的」。差异只有三处：

- 3.8 全节无环境标注（对照 3.6 有），且数字精确到 170/200。
- 3.5 标了「实测行数」但没标机器与工具版本，而 perl 行数强依赖 perl 版本（本机是 perl 5.42.3，与 ADR 测的那台未必同版本）。
- 9.1 的「coreutils 9.5」与 9.3 的「uutils 0.8.0」并存，未标注取舍。

## 9. 结论口径汇总

### 【硬伤】（均附命令输出或原文引用）

**H1｜`0024:348` 指定的证据底本在工作区不可读。**
`git status` 显示 `D findings-2026-10-21.md`；内容在 `HEAD`（10953 字节）。复核者按文中路径打开会失败。归因：工作区状态（删除未提交，起因本轴不掌握，可能是本次审计准备时清场），非 ADR 文本错误，但影响可追性。

**H2｜9.1 与 9.3 对同一台 Ubuntu 26.04 的 coreutils 版本自相矛盾。**
`0024:321`「Ubuntu 26.04（coreutils 9.5）」 vs `0024:331`「uutils 0.8.0」。两者不能同真。

**H3｜第十一节列举的四类沙盒产物，三类零命中，一类无效。**
`0024:350` 列「i18n 取证、`-a` 探针、locale 对比脚本、结论汇总」。实际：`find build -iname '*i18n*'` 空、`find build -name '结论汇总*'` 空、无排序/locale 对比脚本；唯一存在的 `build/probe-a-1/` 4/4 运行 connection refused。且 `git log --all -- build/` 为空（无 git 证据，不判「从未产出」）。

**H4｜3.1 的「实测」与 ADR 自引底本、议题 spec 正面冲突。** 见 §6，双方原文已引。

**H5｜3.8 的三个数字不可复核，且量级随未公开参数从 30.5% 漂到 100%。**
复算输出见 §3。ADR 未给生成器、未给 16 行清单、未标环境与工具链。不能判 85% 为假，只能判「不可复核」。

### 【判断题】（选项与代价）

**J1｜3.8 那张表怎么处置。**

- A. 补产物：把生成器与输出补进议题目录（不放 `build/`，因为按天清理）。代价：需要作者回忆/重建当时的抽样规则，补出来的未必是原来那份；若重建后仍是 100%/16 行，等于自己承认原数不可复现。
- B. 降为定性：删掉百分数，改成「抽样见过差异；纯小写+数字未见差异」。代价：失去「代价可接受」的量化支撑，但 6.1/6.2 的论证不依赖具体比例，仍成立。
- C. 删整节。代价：3.7 的表格仍保留了「按字节还是按字符」的代价，3.8 只是量化，删掉不伤主线；但会让「`sort` 无 `-n` 时可能不同」失去示例。
- 本轴倾向 B（代价最小、不制造假精确），但选择权不在本轴。

**J2｜9.3 的 uutils 结论怎么处置。**

- A. 限定版本：改成「0.8.0 上如此；0.12.0 起改为 collation，不再按码点」，并统一 9.1 的版本口径。代价：要重测 0.8.0 才能写全，否则只能写「0.8.0 的记载如此，0.12.0 已不同」。
- B. 删掉。代价：零，因为它是自标旁证，且 `C` 在两套实现下一致这一点不依赖它。
- 本轴倾向 B 或 A 的弱化版（只写「uutils 与 GNU 对同一 locale 名的排序可能不同，版本相关」）。

**J3｜3.1 怎么处置。**

- A. 补产物（WSL 跑一遍，落 `terminal-output.txt` + 版本自证）。代价：需要 WSL 环境；Ubuntu 26.04 + sudo 1.9.17p2 已非当前版本，补测只能证明「当前版本如此」。

- 本轴倾向 B（诚实且不动决定），A 作为后续工单。
