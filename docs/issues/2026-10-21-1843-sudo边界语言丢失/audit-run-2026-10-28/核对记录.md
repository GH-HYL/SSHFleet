## 核 1：片段与下发行的字节数（锚 8 的数字）

**为什么要核**：轴 3 说「整条 174 造不出来，实测 170/175/184/263」，与 ADR-0030 第四节写的「片段 162、整条 174」对不上；两处必有一处错。

**怎么查**：把 `modules/SSHFleet_Go` 整份复制到 `build/audit_run_2026-10-28/lead-check/mod/`，加一个 `cmd/dump/main.go` 直接调 `ssh.LocaleFragment` 与 `ssh.BuildCommand` 的真实实现，离线跑（`GOPROXY=off GOSUMDB=off`）。仓库零改动。

```text
english=false fragment=162
english=true fragment=184
noenv+english=off downlink=175  <sh -c 'if … fi; bash'>
env+english=off downlink=251
env+sudo+off   downlink=256
```

**结论**：

- **片段 162 字节：对**（ADR-0030 四节、spec 影响节都对）。
- **整条 174 字节：错，实际 175**。ADR 数的是「`sh -c '` + 片段 + ` bash'`」，但它把 `sh -c '` 记成 6 字节（实际 7）、` bash'` 记成 6（实际 6），合计 174；真实串是 `sh -c '…fi; bash'` = 7+162+5+1 = 175。
- 而且 **174/175 只在「`[env]` 为空 + 不开英文 + 不带 sudo」这一种形态下成立**，ADR 没写这个条件；出厂配置的 `[env]` 有 `PATH` 与 `TERM`，实际整条是 251（带 sudo 256），开英文 197。
- 轴 3 报的 170 我未能复现，按同一段代码量不出这个数；它的 184（`LocaleFragment(true)`）与我的 184 一致。

## 核 2：`174` 这一格，轴 2 与轴 3 的说法是否打架

**为什么核**：轴 3 说「实测 170 / 175 / 184 / 263」，轴 2 说「`sh -c '<片段> bash'` 实测 175，174 只在解释器名恰好 3 字节时成立」，ADR 写 174。

**怎么查**：见核 1 的同一次运行（调真实 `BuildCommand`，解释器 `bash`）。

**结论**：两轴不打架——**解释器是 `bash` 时整条 175**，与我的实测同值；`174` 只在解释器名 3 字节（`ash` / `ksh` / `zsh`）时成立。轴 3 的 `170` 仍未能复现（它没写清量的哪条串）。**ADR 的 174 属「没写条件的具体形态」，且默认解释器 `bash` 下应为 175。**

## 核 3：`grep` 那一环漏字（轴 2 报的硬伤，我独立撞到过）

**怎么查**：我自己在 `build/audit_probe_2026-10-28_15-20/` 造了个只放 `sh`（dash）与 `sh`+`grep` 的两种 PATH，跑同一段片段：

```text
$ env -i PATH="$D/bin" $D/bin/sh -c '<片段>; echo ok'
build/audit_probe_2026-10-28_15-20/bin/sh: 1: grep: not found
ok
```

**结论**：`grep` 缺席时，`sh` 自己那条 `not found` 走的是 `grep` 的 stderr，而片段只对 `locale` 写了 `2>/dev/null`——这行会漏进 stdout/stderr 合并采集的 `Output`。另一路（`locale` 缺席、`grep` 在）实测是静默的，与轴 2 的结论一致。

## 核 4：0030 决定 1 与 0024 第八节是不是真冲突（轴 5 的 H1）

**怎么查**：直接读 `docs/adr/0024-env穿过sudo边界.md` 三处原文。

- `:3` 状态行：「部分作废（partially superseded by ADR-0030）—— 决定 1 与 6.1 的立论不再约束，**其余仍有效**」。
- `:369` 第八节：「**不在下发时探测目标机环境再配套传变量。** 作者 U12 原话：……——**包括「先探 `locale -a` 再决定传哪个值」这类只读探测**。取值一次定死，全量下发。」

**结论**：冲突成立，而且是**决策层**的冲突，不是文字问题。0030 决定 1 第 3 步做的正是 0024 第八节点名禁止、且记为**作者明示**的那件事。两份 ADR 同时声称「禁止探测」与「要求内建判断」，没有任何一处写清哪句还压着。同类还有 `:359`「下发形态不变，`DescribeCommand` 不用改」——本轮恰恰改了 `DescribeCommand` 的入参，而它被状态行的「其余仍有效」判为有效。

## 核 5：`TERM=dumb` 那一段「本机没有这两个程序」

**怎么查**：`command -v whiptail` 与 `dpkg -l whiptail`。

```text
/usr/bin/whiptail
ii  whiptail  0.52.25-1ubuntu3  amd64  Displays user-friendly dialog boxes from shell scripts
```

**结论**：`whiptail` 本机装着。ADR-0030 第五节写「ncurses 类交互安装器（dialog / whiptail）预期也会失败——本机没有这两个程序，未测」，第六节又把它列进「没证实的」——**一句能当场验的话被记成未测**。轴 5 已用 `script` 造 PTY 实测（`TERM=dumb` 退出 1、打「terminal lacks the ability to clear the screen」；`TERM=xterm` 正常画框），结论方向与「会失败」一致，但「未测」这个标注不成立。

## 核 7：目标机自带 `LC_ALL` 时片段是否空转（复核员 H2）

**怎么查**：用 `env -i` 造「目标机自己带着 `LC_ALL=C`」的会话，跑同一段片段，看 `charmap` 与 `cut -c1-2`：

```text
$ env -i PATH=/usr/bin:/bin LC_ALL=C sh -c '<片段>; echo charmap=$(locale charmap); printf "中文\n" | cut -c1-2 | od -An -c'
LC_CTYPE=[C.utf8] charmap=ANSI_X3.4-1968
 344 270                        ← 只有 2 字节，半个字
```

**结论**：`LC_ALL` 压过 `LC_CTYPE`。片段照锚 1 做完了全部四步（挑到 `C.utf8` 并 `export LC_CTYPE`），`charmap` 仍是 `ANSI_X3.4-1968`，`cut -c` 照旧切半个字。**实现符合锚 1，效果不落地**——这正是「非交互会话拿不到 `LANG`、却可能带着 `LC_ALL=C`」的那批机器（cron、docker、部分 sshd 配置）。ADR-0030 决定 6「不再设 `LC_ALL`」与这一格的关系没写。

对照：`LANG=zh_CN.utf8` 的机器上片段按设计不动手（`charmap=UTF-8`，`LC_CTYPE` 留空），符合锚 1 第 2 步。
