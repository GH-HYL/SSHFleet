## 【硬伤】

### H1 CHANGELOG 漏了本轮唯一的不兼容：照 Removed 那条做，旧配置起不来

三处拼起来是一条完整的事实链：

- `modules/SSHFleet_Go/internal/config/config.go:219` 把 `locale.english` 放进了必填表（`definedStr(md, "locale", "english")`），字段**不出现**即报错，值留空也不行（键不在表里）。
- `CHANGELOG.md:27` 的原句：「**出厂配置的 `[env]` 只剩 `PATH` 与 `TERM` 两行**，`LANG` / `LC_ALL` 撤掉。升级后自己动手删掉这两行即可；不删也不报错，它们照普通环境变量一样下发。」——只交代了删 `[env]` 那两行，**没有一个字**说还得补一个 `[locale]` 段。
- 上一版是**真的发出过包**的：`release/SSHFleet_2026-10-22_12-40-08_linux/config/SSHFleet.conf` 里 `[env]` 是四条（`LANG` / `LC_ALL` / `PATH` / `TERM`，44–49 行），全文没有 `[locale]`。

实测：新二进制加载上一版随包配置，直接拒绝启动。

```
$ go run . /home/hfg/桌面/Code/SSHFleet/release/SSHFleet_2026-10-22_12-40-08_linux/config/SSHFleet.conf
ERR: 配置缺少必填字段：locale.english
提示：请使用随包提供的配置文件，不要删掉里面的任何一行
```

即：按 CHANGELOG 的升级指引（删掉两行、其余不动）操作完，用户得到的是一份**启动即失败**的配置，而报错里那句「不要删掉里面的任何一行」既没说是哪一段，也没说该补什么——`Load` 对 `[paths]`、`[execution.env]` 都给了专门的迁移提示（`config.go:160-171`：段名改成什么、整段删掉即可），对 `[locale]` 只有这一句通用提示。

严重度不是主观判断：`tools/release/release.py:313-315` 把档位规则写在代码里——「**配置里新增必填字段**」列在「不兼容」一侧，「删除配置字段」也在。所以这条既该进 CHANGELOG 的 Changed/Removed，也该让发版时按不兼容处理；现在两处都没有。

### H2 `docs/2` 的「进阶配置」清单没把新段算进去，从基础册进门的读者看不到 `[locale]` 存在

`docs/2-基础配置手册.md:8` 原句：

> - **进阶配置**——凭据、远端环境变量、输出开关、交互代填、解释器、改密、上传并发

七项，与 `docs/3` 的实有章节（`1 凭据` … `6 远端环境变量`、**`7 语言与编码`**、`8 解释器`、`9 改密配置`、`10 上传并发`）对不上：清单里少了「语言」，而 `docs/3-进阶配置手册.md:316` 正是本轮新开的 `## 7 语言与编码`，出厂模板 `config/SSHFleet.conf:50-52` 也新增了 `[locale]` 段。docs/2 是「要改配置先看哪一册」的入口，它列的项就是读者会去找的项；漏掉一项且全文没有别的指向 §7 的指针（`grep` docs/2 无 `locale` / `语言`），结果是只看基础册的人不知道有这个开关。

## 【判断题】

### J1 `LC_ALL` 留在 `[env]` 里会让 `english = true` 静默失效，而 CHANGELOG 正劝人留着它

`CHANGELOG.md:27` 说旧的两行「不删也不报错，它们照普通环境变量一样下发」；`docs/3-进阶配置手册.md:335` 只写了 `LC_ALL` 会盖掉工具设的 `LC_CTYPE`；`docs/3:328` 与 `config.go:83` 说开关打开后「目标机上**所有程序**的提示语一律英文」。三句拼起来漏了一种情形：`LC_ALL` 是**全类别**覆盖，不止盖 `LC_CTYPE`，也盖 `LC_MESSAGES`。

实测（本机，glibc；`locale` 打印的是最终生效值）：

```
$ env -i LC_ALL=zh_CN.UTF-8 LC_MESSAGES=C /usr/bin/locale | grep LC_MESSAGES
LC_MESSAGES="zh_CN.UTF-8"        ← 先设 LC_MESSAGES=C 也没用
$ env -i LC_ALL=C LC_MESSAGES=zh_CN.UTF-8 /usr/bin/locale | grep LC_MESSAGES
LC_MESSAGES="C"
```

代价：上一版出厂配置里 `LC_ALL = "en_US.UTF-8"` 就在 `[env]`（`release/SSHFleet_2026-10-22_12-40-08_linux/config/SSHFleet.conf:47`），升级者按 CHANGELOG「不删也不报错」原样保留、再打开 `english = true`，开关在这台机器上**一句都不生效**，且没有任何告警。若他那台机器的 `LC_ALL` 是 `zh_CN.UTF-8`（作者笔下的失败现场正是中文输出），失败分类照旧整批落「未归类」——而 CHANGELOG 同时承诺这个开关就是解这个的。所以「所有程序一律英文」这句在用户可配 `LC_ALL` 的前提下过强；docs/3:335 那半句也只交代了 `LC_CTYPE` 一侧。

### J2 「默认 `false`」与「所有字段必填、不设隐藏默认值」两套口径同时出现在使用者文档里

- `docs/4-进阶知识手册.md:85`：「所以做成一个开关（`[locale]` 的 `english`），**默认跟随目标节点**，要拿输出逐字比对时再打开。」
- `README.md:109`：「配置里**所有字段都必须写出来**……**工具不设任何隐藏默认值**，缺字段或取值不合法会在启动时一次告诉你是哪几项。」
- 实现：`config.go:219` 必填，缺 `english` 就报错（见 H1 实测）。

「默认」在读者那里只有一个意思——不写就取这个值；但这里不写是启动失败。`docs/3:327` 与 `CHANGELOG.md:19` 写作「`false`（出厂）」，与 README 口径一致；只有 docs/4:85 用了「默认」。代价不只是措辞：它让人以为升级时可以不动这一行（H1 的现场）。同一事实在 ADR 侧已被记过（轴 5 的 H9），此处只判使用者手册内部的口径不统一。

### J3 「未归类」的 FAQ 只教改关键词表，没提本轮为它做的开关

`docs/5-常见问题.md:231-233`：

> **Q：分类那一列显示的是一大段报错原文？**
> 那说明这个原因没能匹配到任何已有分类……如果它反复出现，可以把它的特征词补进 `config/keywords_error.conf` 里对应的分类……

本轮 `[locale] english` 的动机（`CHANGELOG.md:19`、`docs/3:328`、`docs/4:85`）正是「失败分类的判据是英文原话，目标机出中文就整批落未归类」。FAQ 是撞到该现象的人第一个翻的地方，它给的两条路里没有「目标机语言不是英文」这一条，也没有指向「7 语言与编码」。代价：用户去改一份英文关键词表来匹配中文报错（或者根本改不动），而现成的开关就在隔壁一节。

### J4 「触发词要按目标机的提示语言写」没随开关更新，开 `english` 会反过来打中 `-a`

- `docs/5-常见问题.md:139`：「**触发词要按目标机的提示语言写**，中文机器出中文提示」
- `docs/6-示例.md:151`：「出现「触发词未命中」说明有机器上脚本问的话没认出来（触发词要按**目标机的提示语言**写）」

这两句在 `english = false` 下仍然成立。但开关打开后，`LC_MESSAGES=C` 会把**代填正在匹配的那些提示**一并改成英文（`-a` 吃的是目标机程序的输出，锚 5 也把 `-a` 算在片段的覆盖范围内）。于是「按中文提示写的触发词」在 `english = true` 时整批「触发词未命中」，而五份使用者文档里没有一处把这两件事连起来说：docs/3 §7 讲开关、§5 讲代填，互不交叉；docs/5/docs/6 那两句仍是「按目标机语言写」，没加「开了 `english` 就得写英文」的前提。代价：一次批量全部落「触发词未命中」，排查方向还被引向「提示词表里没有那条措辞」。

### J5 `docs/3` 的「`[env]` 一条都不要」在删掉段头时被必填表拦下，文档没说段头得留

`docs/3-进阶配置手册.md:299`：

> - **一条都不要**：`[env]` 下不写任何条目即可——工具就完全不导入环境变量。

实测两种读法结果不同（`config.go:218` 的必填项是 `{"env", definedStr(md, "env")}`，只认段头）：

```
$ go run . fixtures/emptyenv.conf      # 保留 [env] 段头、下面一条不写
OK: env=map[] locale.english=false
$ go run . fixtures/noenvsec.conf      # 把 [env] 段头也删了
ERR: 配置缺少必填字段：env
提示：请使用随包提供的配置文件，不要删掉里面的任何一行
```

「下不写任何条目」按字面可以理解成「这一节整个不要」，而这正好踩中必填表；报错又只报 `env`、提示还是「不要删掉任何一行」，读者很难想到「段头本身是一行」。代价：一次启动失败 + 一轮猜。同类边界在 `config.go:277-282`（值留空 = 丢弃该条）是成立的，我实测 `PATH="" TERM=""` → `env=map[]`，出厂注释 `SSHFleet.conf:44` 那句「把某一行的值留空 = 关掉这一条」与实现一致，问题只在「整节不要」这一句。

### J6 出厂面没有「三份模板与必填表一致」的任何把关，打包前也不实跑一次

`tools/release/release.py:161-163` 的 `precheck` 对三份模板只做 `p.exists()`；`stage_pkg`（`release.py:234-235`）按平台把模板改名成包内 `config/SSHFleet.conf`，之后不打补丁、不校验、不启动。测试侧只拿 Linux 那份当输入（`internal/config/config_test.go:95`、`:118`），作者本机那份 `SSHFleet.conf` 与 `SSHFleet-for-windows.conf` 不进任何测试（测试质量归轴 6，此处只记出厂面）。

代价：新增必填字段这类改动只要漏改**任意一份**模板，`go test` 全绿、`--dry-run` 也全绿，坏包要到用户第一次启动才暴露（H1 就是这个形态的镜像：代码先加了必填、模板后补；这次是补上了，但没有任何机制保证下次补上）。打包脚本本身又规定「除非开发者明确要求，否则不要跑」且 `release/` 只留最新一次产物，事后无法回看上一版包里的配置长什么样——本轮 H1 能取证，靠的是 10-22 那次产物还在。

### J7 `CHANGELOG.md:23` 的「工具每次下发前」比实现覆盖的范围宽

原句：「**目标机的字符编码改由工具处理，配置里不用再写**：工具**每次下发前**先问目标机的 `locale charmap`……」实测（`BuildCommand` 探针）：片段只出现在命令 / 脚本两种形态的 `sh -c` 里；`--no-shell` 原样下发不带（`docs/4:66` 也这么写），上传 / 下载 / 改密三条不拼 `sh -c` 的路没有下发行。所以「每次下发前」只对「命令 / 脚本且没加 `--no-shell`」成立。

代价不大（CHANGELOG 是概览，docs/4:66-67 有准确边界），但这一条同时被 `docs/3:318`「每次下发前工具自己问目标机」继承——把「上传一批文件也会先问编码」这种预期留给读者。实现覆盖面的判断归轴 3（其 J5/J6），此处只判使用者可见面的措辞。

## 【未能验证】

**U1 Windows 出厂模板能否被加载。** 本机是 Linux，`config.normalizeConfigPath`（`config.go:404-443`）在非 Windows 上会把 `C:/SSHFleet/keys` 判成「Windows 盘符写法」而拒绝，所以 `SSHFleet-for-windows.conf` 在这台机器上根本走不到校验完；只能做到「文本上 `[env]` / `[locale]` 与另两份逐字相同」（已 diff 确认）。要验的是：Windows 上 `go run`/二进制加载这份模板能通过，并读出 `PATH` / `TERM` / `english=false`。

**U2 打包产物里的 `config/SSHFleet.conf` 与模板逐字一致。** 授权明确禁止跑 `release.py`，`release/` 里也只有 10-22 那次产物（早于本轮）。所以只能读代码推断 `stage_pkg` 是 `shutil.copy2`（`release.py:235`，逐字节复制）；没有实际解一次包比对。

**U3 `LC_CTYPE` / `LC_MESSAGES` 能否穿过 sudo。** `docs/3-进阶配置手册.md:312` 承诺「`--sudo` 时这些变量在 `sudo` 之前导入，能不能穿过 sudo 取决于目标机的 sudoers（多数发行版保留 `LC_*`）」。本轮 `sudo -n` 被内核挡死（`sudo: The "no new privileges" flag is set`，`NoNewPrivs: 1`），无 2222/2223 监听、无 `sshpass`，造不出「免密 sudo 且 sudoers 保留/清除 `LC_*`」的两种现场，无法确认这句「多数发行版保留」在目标机上是否兑现——而这正是 `english = true` 在 `--sudo` 下有没有效果的分水岭。

**U4 `english = true` 在真中文目标机上的整批效果。** 本机只能验单条命令：`env -i LANG=zh_CN.UTF-8 dpkg -l nosuchpkg` 出「没有找到与 nosuchpkg 相匹配的软件包」，加 `LC_MESSAGES=C` 后出「no packages found matching nosuchpkg」——说明开关对 gettext 程序有效。但「整批分类是否因此不再落未归类」需要一台装了中文翻译包、且跑真实失败命令的目标机；容器本轮起不来（rootless `newuidmap` 被拒），无法构造。

**U5 上一版 Windows 包用户升级的现场。** 无 Windows 环境，且 `release/…_windows/` 里那份配置是 `C:/` 形态，在 Linux 上连加载都过不了（同 U1），没法复现「升级后第一次启动」的报错原文是否与 Linux 侧一致（我验的是 Linux 包那份，两者只差三行路径，按代码应一致，但这是推断）。
