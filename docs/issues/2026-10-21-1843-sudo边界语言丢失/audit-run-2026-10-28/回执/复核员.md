## 〇、框架说明

六轴按**代码位置**切（片段 / 链路 / 配置 / 文档 / 测试），判据全部是**锚**。这个切法有一个结构性后果：**每一轴都在问「这里符不符合锚」，没有一轴在问「锚本身在什么条件下为真」**。于是「锚对、代码对、合起来在真机上不生效」这一类问题，逐轴看全绿。

我按**「决定 → 前提 → 生效」**重切，四块：

| 块 | 问的问题 | 判据 |
| - | - | - |
| **A 前提审计** | 六条决定各自依赖哪条没写进 ADR 的环境事实？成立吗？ | 实测，不是文本 |
| **B 生效判据** | 不看下发行长什么样，只看**执行后从目标机读回来的** `locale charmap` 与各 `LC_*` 分量 | `locale` 自报为准，串对了不算数 |
| **C 边界与承诺** | 决定 1 新增了什么依赖、破坏了哪三处既有承诺（用户可自由增删 / 零依赖 / 永不降级） | 实测 + 引文 |
| **D 收益口径** | 决定 1 声称的收益，真的来自 `LC_CTYPE` 吗？ | 拿"设了也不理 locale"的实现验 |

为什么这么切：本轮真正的风险不在「哪段代码写错」，而在**「每条决定单看都成立，联立到真实机器上不成立」**。下面三条都是这个形状——单独验任何一条都过，合起来是假：

1. 锚 1 四步做完，`LC_CTYPE` 确实被设了（块 B 读回来却被 `LC_ALL` 盖住）；
2. 锚 7「不碰 `LC_ALL`」确实守住了（正因为守住，才被目标机原有的 `LC_ALL` 盖死）；
3. 锚 1「不是 UTF-8 就换成 UTF-8」确实执行了（在本来按字符的 GB18030 机器上，这一换就是降级）。

## 一、六轴的盲区

- **轴 1（规范/规格符合度）**：判据就是锚。「实现符合锚 1」与「锚 1 有效」是两件事，后者不在它的判据里。锚 7 的三条不变式它只能逐条对照实现，无法发现「守住锚 7 反而让锚 1 失效」。
- **轴 2（片段语义）**：造的场景是三态——UTF-8 / 非 UTF-8 有候选 / 非 UTF-8 无候选。**GB18030 落在第二态**，会被当成「该修」的机器，而不是「本来就对、别动」的机器；它按锚 7 判「永不降级」时，若把判据定成「只会往 UTF-8 升，所以不降级」，正好把这条放过去。另外它问「`LC_ALL` 有没有被碰」，实现答「没碰」，全绿——**碰不碰与生效与否是两件事**。
- **轴 3（拼装链路）**：量的是「串到没到」。锚 1 的失效发生在「到了之后环境不认」，链路层面看不见。用户 `[env]` 里的 `LC_CTYPE` 被片段覆盖，属语义冲突，不属拼装顺序，它按第 6 条只会判「片段在 export 段之后，顺序对」。
- **轴 4（配置与出厂面）**：它的 grep 词表是 `LANG|LC_ALL|LC_CTYPE|[locale]`。README:404「目标机上也不需要装额外的东西」不含这些词，扫不到；「用户仍可自由增删」与「片段会覆盖 `LC_CTYPE`」也不会被放在一起看。
- **轴 5（ADR 描述）**：会抓 174、会抓决定间自洽，但方式**是读文本**。「决定 1 在 `LC_ALL` 下失效」读文本只能读成「决定 6 已经处理过 `LC_ALL` 了」——恰恰相反，决定 6 承认了机制却没回填给决定 1。§1 与 `spec.md:72` 的口径冲突要跨文件对，而它的文件域里 spec 只用于「ADR 不清导致 spec 跑偏」，反方向不查。
- **轴 6（测试与回归）**：全是**拼串断言**。「环境里有 `LC_ALL`」「`locale -a` 里两个名字都没有」这类场景要改的是**运行环境**，不是串；断言写得再死也造不出来。所以「测试有效性」这一轴再严，覆盖的是「串没写错」，不是「串有没有用」。

## 二、锚质疑

### 锚质疑 1：锚 1 缺一条适用前提——目标机自带 `LC_ALL` 时四步全做完也不生效

- **哪条锚**：锚 1（四步 → 「挑到就**只** `export LC_CTYPE`」）。
- **证据（实测）**：
  ```
  $ env -i PATH=/usr/bin:/bin LC_ALL=C LC_CTYPE=C.utf8 locale charmap
  ANSI_X3.4-1968            # LC_CTYPE 设了，被 LC_ALL 盖住
  $ env -i PATH=/usr/bin:/bin LC_ALL=C LC_CTYPE=C.utf8 sh -c 'export LC_CTYPE=C.utf8; echo $LC_CTYPE; locale charmap'
  C.utf8
  ANSI_X3.4-1968
  ```
  按片段原样跑（`run_frag.sh`，S3）：`LC_CTYPE=[C.utf8]`，`locale charmap` 仍是 `ANSI_X3.4-1968`。片段「成功」了，效果为零。
- **为什么是锚的问题而不是实现的问题**：实现逐字照做，没碰 `LC_ALL`（锚 7 要求）。失效来自 glibc 的优先级 `LC_ALL > LC_* > LANG`——**这条机制在同一份 ADR 的决定 6 里写着**（「它设错会刷屏，还会盖掉语言开关」），却没回填给决定 1。
- **按什么判**：四步全部执行完后，「目标机 `locale charmap` 是否变成 `UTF-8`」。`LC_ALL` 存在且非 UTF-8 时为否。
- **影响面**：目标机 `/etc/environment`、PAM `pam_env`、包装脚本给了 `LC_ALL` 的机器，决定 1 整体无效且无痕。ADR §1.3 只对「这两台容器」核过（sshd 没配 pam_env、`/etc/environment` 空），没外推。
- 不给修法；改不改锚由开发者定。

## 三、硬伤

### 硬 1　「非 UTF-8 = 按字节」是事实错误；实现据此会把 GB18030 机器降级，违反锚 7

`docs/adr/0030-编码内建与语言开关.md:39`：

> 任何一个静态值，都只能让一半机器按字符、另一半按字节

这句话把「不是 UTF-8」等同于「按字节」。glibc 的 `zh_CN.GB18030` / `zh_CN.GBK` / `zh_TW.Big5` 都是**多字节** locale（`MB_CUR_MAX > 1`），在那类机器上 `cut -c` / `wc -m` 本来就按字符。片段把它们判成「不是 UTF-8」→ 换成 `C.utf8`。

实测（`gb.txt` = 「中文」的 GB18030 编码 `d6d0 cec4`）：

```
LC_CTYPE=C        bash ${#x} = 4      # 按字节
LC_CTYPE=C.utf8   bash ${#x} = 4      # 仍是按字节——片段给的就是这个
对照：UTF-8 的「中文」
LC_CTYPE=C        = 6
LC_CTYPE=C.utf8   = 2                 # 这条证明判据本身能区分两个语义
```

GB18030 字节流在 `C.utf8` 下不是合法 UTF-8，于是退化成逐字节——**比不动它更差**。锚 7 写的是「永不降级」，这是降级的直接反例。

（另一半「在真 `zh_CN.GB18030` 下应为 2」本机无该 locale，见第四节。）

### 硬 2　锚 2 的「`LANGUAGE` 不用清——在 `C` 下 gettext 会忽略它（实测）」只对 glibc 的 C 实现成立

`docs/adr/0030-...md:49`、`modules/SSHFleet_Go/internal/ssh/command.go:84` 都把它写成无条件事实。实测两向：

```
# glibc gettext（自己编的 C 程序 + 手搓 .mo）
LANG=C LC_MESSAGES=C LANGUAGE=zh_CN  → hello            # 忽略 LANGUAGE，ADR 说的是这个
LANG=zh_CN.utf8                       → 你好，世界
# Python 的 gettext（同样的 .mo）
LANG=C LC_MESSAGES=C LANGUAGE=zh_CN  → 你好，世界        # 不忽略，直接命中 LANGUAGE
LC_ALL=C        LANGUAGE=zh_CN        → 你好，世界        # 连 LC_ALL 都不看
```

Python 的 `gettext.find()` 按 `LANGUAGE → LC_ALL → LC_MESSAGES → LANG` 取第一个**非空**的，与 locale 是不是 `C` 无关。CentOS 7.9 的 `yum`、RHEL 8+ 的 `dnf` 都是 Python——正是本议题里「失败分类关键词全英文」最想覆盖的那类程序。而 `LANGUAGE` 在 RHEL 的 `/etc/sudoers` `env_keep` 里（ADR-0024:117 的同一张表），能穿过 sudo 到达目标程序。

不是实现没照做，是**决定的依据取了一个实现的实测，却写成了通例**。

### 硬 3　决定 1 的收益口径里混进了一个它修不好的例子

`ADR-0030:39` 用「`cut -c` / `awk substr` 切中文会切坏」作为旧值 `C` 的代价来立论。实测两个常见实现，`LC_CTYPE` 对它们**完全无效**：

```
输入 UTF-8「中」（e4 b8 ad）
                       C        C.utf8
mawk 'substr($0,1,1)'  e4       e4      # 两处都切出首字节
busybox cut -c1        e40a     e40a    # 同上
```

`spec.md:72` 已经记了这件事（「`mawk` 本来就按字节（与 locale 无关），uutils 的 `wc -m` 两处都按字符」），但 ADR 的 §1 仍把这两个工具列在「按字节」的代价里。结果是：**在 busybox 目标机上，决定 1 即使生效也不改变这两个工具的行为**，收益被高估。两处文档口径互斥，属于「因文档写错导致判断跑偏」。

### 硬 4　用户 `[env]` 里显式配的 `LC_CTYPE` 会被无声覆盖，与决定 3 冲突

`ADR-0030:52`（决定 3）：「用户仍可自由增删自己的变量」。实测：

```
用户配 LC_CTYPE=zh_CN.utf8（合法 UTF-8）→ 执行后 LC_CTYPE=[zh_CN.utf8]   保留
用户配 LC_CTYPE=zh_CN.GB18030           → 执行后 LC_CTYPE=[C.utf8]       被改掉
```

`command.go:74-75` 的注释把承诺缩成了「用户显式配了**有效的 UTF-8** 就不动手」——「有效」被悄悄定义成「UTF-8」。一个在 GB18030 机器上**有意**配了 `LC_CTYPE` 的用户，工具会把它改掉，且这是他一辈子都不会被告知的一次覆盖。

### 硬 5　README 的「目标机上也不需要装额外的东西」被决定 1 打破

`README.md:404`：「它是单一程序：没有子进程、没有本地端口，**目标机上也不需要装额外的东西**。」

片段现在每次执行都要目标机上有 `locale` 和 `grep` 两个二进制（`command.go:78`）。本机 busybox 构建不含 `locale` applet（`busybox --list | grep -x locale` 空输出），此类目标机上决定 1 完全落空。ADR §6 只把「`locale` 被裁掉」记成「安全退化，只是不生效」——**对工具是对的，对产品承诺是错的**。这条不是轴 4 能扫到的：它的 grep 词表里没有「额外的东西」。

## 四、判断题

### 判 1　开关两态不对称：`english=false` 兑现不了「中文」，在 §1.3 描述的那类机器上两端都是英文

- 决定 2「关 → 不加任何东西，语言跟随目标节点」；决定 3 把 `LANG` 从出厂删掉。
- ADR §1.3 自己说：「非交互会话通常拿不到 `LANG`」。
- 两条合起来：**默认配置 + 无 `LANG` 的目标机 = 英文**。实测：
  ```
  env -i locale | grep LC_MESSAGES   → LC_MESSAGES="POSIX"
  同一 gettext 程序：无 LANG → hello；LANG=zh_CN.utf8 → 你好，世界
  ```
- 于是 `english` 这个开关在 §1.3 描述的那类机器上**没有区分度**（两端都是英文）；只在目标机自带中文 `LANG` 时才有「关=中文/开=英文」的差别。
- 可权衡：这是「默认不干预」的必然代价，不是 bug。但要认清：**开关名说的是语言，实际控制的是「是否强制英文」**，另一半（强制中文）根本没有对应能力，且被锚 3 / 锚 6 堵死。ADR 的措辞（「语言只留一个开关」）容易让读者以为两个方向都能控。

### 判 2　决定 1 的覆盖面仍由「两个名字」决定，第三类机器静默无效

`locale -a` 里 `C.utf8` 与 `en_US.utf8` 都没有的 glibc 机器（只装了 `en_GB.utf8`、或 `ja_JP.utf8` 的机器）——stub 实测：

```
locale -a → C / POSIX
执行后 LC_CTYPE=[]，locale charmap → ANSI_X3.4-1968，无任何输出
```

ADR §1 只论证了「两台机器没有交集」，没回答「两个都没有的机器占多少」；§6 只列了「`locale` 命令被裁掉」，没列「`locale` 在、名单里没有」。方案从「一个静态名」扩到「两个静态名 + 运行时挑」，覆盖面仍然是**枚举出来的**，不是「有 UTF-8 就用」——真正的一般解是「挑 `locale -a` 里任何一个 charmap 为 UTF-8 的」，但那样会碰到 `tr_TR` 的字符分类问题（§3 的理由）。这是一个明确的取舍点，ADR 没把它摆出来。

### 判 3　失效不可观测，与 §4「影响」的代价清单不符

三类失效——目标机 `LC_ALL` 覆盖、`locale -a` 无候选、`locale`/`grep` 缺席——在「命令行」日志里长得**一模一样**：都只有片段原文，没有「探测到什么 / 设成什么 / 没设」。

§4 只写了「可读性下降，属已知代价」，没把「出乱码时无法判断是片段没生效还是程序本身不吃 locale」列为代价。这是运维面的账：决定 1 把「静默」当成安全（§3「挑不到不设……唯一安全的实现方式」），代价是**排障时没有任何抓手**。

### 判 4（同轴 5，不同判据）　174 应为 175

同轴 5 会用「复算公式」判；我用**跑真代码**判：沙盒里给 `ssh` 包加一条 dump 测试（`src/internal/ssh/zz_dump_test.go`），`BuildCommand` 的输出长度：

```
english=false len=175
english=true  len=197
frag len=162  frag+english=184
```

`ADR-0030:66` 说「含 `sh -c '` 与 ` bash'`」174 字节；`7 + 162 + 6 = 175`。差 1，是漏算了片段与解释器之间的那个空格。片段本身 162 是对的。

### 判 5（同轴 2，不同判据）　「永不告警」在 `grep` 缺席时破——三条命令的静音不对称

同轴 2 会逐场景看漏字；我给的是**不对称性**这个判据：`locale charmap` 与 `locale -a` 各带一个 `2>/dev/null`，**`grep` 没有**。实测（PATH 里去掉 grep）：

```
./run_frag.sh: 3: grep: not found
LC_CTYPE=[]
```

下发行里这行会进合并后的 `Output`（轴 2 已注明工具把 stdout/stderr 合并采集），即一条正常命令的输出里多一行来历不明的 `grep: not found`。ADR §6 的风险清单只列了 `locale`，实现却把 `grep` 放进了必经路径。
