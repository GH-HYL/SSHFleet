## 【判断题】

### J1 片段那 7 条断言是**拼写检查**，不是语义回归网

`command_test.go:39` 的 `wantEncodingFragment` 是手写字面量（这点做对了：期望值不取自实现），`command_test.go:43-69` 用 `!=` 逐字比。M1/M7/M8/M10 四组变异（改 `LC_CTYPE`→`LC_ALL`、挑名正则放宽、判断条件换成 `locale -a`、往 stderr 加一句 `echo`）全部 7 条一起红，说明**任何改字都会红**。

但反过来：文本不变、行为变，这条网一条都接不住。本轮最容易出的那类问题恰好是行为——`grep -Eixm1` 在 busybox grep / 老版本 GNU grep 上认不认、`locale -a` 输出带尾随空格时 `-x` 会不会失配、`$(...)` 在 dash 下的行为。这些**只有轴 2 的人工实测覆盖，没有一条自动化测试**（全仓没有一处测试真的把片段交给 `sh` 跑）。代价：以后有人为了让片段在某个目标机上更稳而改语义、但字面量只改一个字符时，测试只会告诉他「字符串变了」，不会告诉他「行为对不对」。

要不要为此加执行级测试（在测试里 `exec.Command("sh","-c",fragment)` 配假 `locale`/`grep`）是可权衡的：好处是锚 1 的四步第一次有了回归保护；代价是测试从此依赖 PATH 上的 `locale`/`grep`，跨平台（Windows 开发机）会变成 skip 或 stub，测试面变脏。

### J2 用 `Contains` 的断言清单：多数有整串断言兜底，四处没有

`command_test.go` 里用 `HasPrefix`/`Contains` 的：

- `:21-32`（命令模式形态）、`:168-173`（sudo）、`:208-222`（脚本模式）、`:320-336`（命令不进命令行）、`:389-409`/`:412-426`/`:429-441`/`:444-468`（Describe 四种形态）——**都有同形态的整串断言在别处**（`:43-69`、`:121-134`、`interactive_test.go:82-90`），宽断言在这里只是冗余，不算漏洞。
- 真正只有宽断言、没有整串对照的四处：
  - `command_test.go:471-485` `TestDescribeCommandPythonScript`：只查 `Contains(text, "; python3'")`。python 脚本形态的日志没有整串断言。
  - `command_test.go:520-525` `TestInteractiveCommandUsesProgramArg`：只查 `Contains(got, "perl -e ")`。
  - `interactive_test.go:93-104`：sudo 的 `-a` 形态只查 `Contains(root, "sudo bash -c")`。
  - `interactive_test.go:108-117`：`-a` 脚本名只用「`base64 -d)` 之后是否含 `(1.2.3.4).sh`」判断。

  这四处的共同弱点：**在正确子串之后/之前多塞东西不会红**。M9（把 `sudo` 改成 `sudo --preserve-env`）之所以被抓住，靠的是 `:43-69` 的整串断言与 `:168`/`:128`，不是这四处。

### J3 `TestDownlinkForbiddenForms`（`command_test.go:529-546`）不是那道网，词表也窄

它只查三条字面量（`sudo env` / `sudo -E` / `bash -c 'export`）。M9 用的 `sudo --preserve-env` 同样属于「改外壳形态」，**不在词表里**，拦住它的是整串断言。也就是说：这个测试的实际价值只在「有人把整串断言也一起改了」的时候起作用（纵深防御），单看它自己，拦不住同族变体（`sudo  env` 双空格、`sudo -n env`、`env sudo`）。

另外它只跑 `english=false`、没有 `NoShell` 用例（`:531-538` 四个 forms），跟 J4 的缺口叠加。

### J4 `--no-shell` + 开关同时开：没有一条测试

全仓 `Options{NoShell: true, English: true}` 的组合零出现。我补了一次探针（沙盒里的临时 `_test.go`，跑完即删）：

```
no-shell + english（命令）: "ls -l"
no-shell script + english: "bash -c '. /dev/stdin' 't.sh'"
```

行为是对的（`--no-shell` 不附加任何东西，`LC_MESSAGES` 也不加），但**行为对不等于被测**。已有断言能间接挡住一部分（`:176-181` 用 `!=` 整串、`:185-205` 用 `Contains(cmd,"export ")` 挡脚本那条），所以漏的是 `english` 这一维：如果哪天把 `envHead` 挪到 `NoShell` 分支前面、只在 `English` 为真时才生效，命令模式会因为 `:178` 整串红，脚本模式只靠 `Contains("export ")`——若那句写成 `LC_MESSAGES=C; `（不带 `export`）就漏了。

### J5 出厂配置的三条内容不变式（锚 3 / 锚 4 / 锚 6）一条断言都没有

| 变异 | 改了什么 | 结果 |
| --- | --- | --- |
| N1 | linux 模板 `[env]` 加回 `LC_ALL = "en_US.UTF-8"` | **绿** |
| N2 | linux 模板 `[env]` 加回 `LANG = "zh_CN.UTF-8"` | **绿** |
| N3 | linux 模板删掉 `TERM = "dumb"` | **绿** |

`config_test.go` 只验「`english` 能读、缺了报错」，从不看 `[env]` 里到底有哪几条。锚 3 说「出厂只留 `PATH`」、锚 4 说「`TERM=dumb` 保留」、锚 6 说「不再设 `LC_ALL`」——三条都是**出厂配置的内容约束**，本轮把它们从 `[env]` 里删掉了，却没有一条测试保证它们不会被加回来。这处风险很实际：`config/SSHFleet.conf`（作者本机那份）与两份随包模板是三个独立文件，谁手滑往其中一份里贴回 `LC_ALL`，测试不会响。

### J6 `-a` 的长度上限没有边界断言，片段把边界整体推了 162 字节

`internal/cli/answer_test.go:411-435` 两个用例用的正文是 130000 / 100000 字节，离上限 122880 都有 1 万以上的余量——**只测了「明显超」和「明显不超」**，没测边界。本轮片段给每条 `-a` 下发行加了 162 字节（`english=true` 再加 22），正文的实际上限因此整体下移；轴 3 用探针量出 `english=false` 时最大可通过正文 91929 字节（同轴 3 J4），一个断言也没有。

要不要补一条边界用例（正文 = 上限 − 常数 ± 1）可权衡：补了会把这个数钉死，以后改片段的字节数就得同步改测试（这恰恰是想要的告警）；代价是测试里出现一个「魔法常数」，且它随解释器名长度变（`/usr/bin/python3` 比 `bash` 长）。

### J7 `config_test` 拿模板当夹具，`strings.Replace` 一旦失配，红得**报文误导**

`:141`/`:149`/`:153` 三处都靠 `strings.Replace(template, "english = false", …)`。把模板改成 `english  = false`（多一个空格，TOML 语义不变）后：

```
$ go test ./internal/config -run TestLoadLocaleEnglish -v
    config_test.go:146: english = true 应读成 true，实际 false
```

红是红了（不会静默放过），但报文说的是「读不出 true」，真原因是「夹具替换没命中」。下一个人会去查解码代码，而不是查模板空格。这类耦合在 `TestLoadAllowsRelativeSecretDirWhenEncryptOff`（`:94-113`）里更危险：它替换 `secret_dir` / `encrypt` 两行，**失配时 `Load` 仍会成功**，测试会绿着变成一个空用例。

判断：这不是本轮引入的结构（`TestLoadAllowsRelativeSecretDir…` 是旧用例，`TestLoadLocaleEnglish` 沿用了同一套写法），修法也很便宜（替换后断言「真的换到了」，或直接内联一份最小 TOML），但我按轴 6 的职责记它——它是这三个测试文件里唯一一处「测试可能悄悄不测东西」的形状。

### J8 162 / 174 这组数没有任何断言（数字本身归轴 5 / 轴 2）

`grep -rn "162\|174" --include=*_test.go internal/` 零命中。我实测：

### J9 三个测试文件挑不出「从实现取期望值」的毛病——除了模板当输入这一处

逐个看过：
- `command_test.go` 的期望串全是手写字面量（`:39`、`:72`、`:52-62`），`interactive_test.go:86` 的 base64 由标准库现算，不是从实现拿的；

### J10 测试钉死了「`english` 缺行 = 报错」，与锚 2 的「默认 false」是两种口径（同轴 4，判据不同）
