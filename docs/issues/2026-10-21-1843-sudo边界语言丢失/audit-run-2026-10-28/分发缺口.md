# 分发缺口 · 提示词包 v1（2026-10-28）

只审提示词的设计，不评价技术结论。每条：缺什么 → 补哪个轴 / 补哪条约束。带【必补】的是会直接产出错回执的。

## 前置核对：26 个文件的归属

逐个对过 `git diff dbcb797 e8c47a7` 的 26 个文件：

- 24 个被至少一条具体轴的**文件域**点名（轴1 的「整个实现 diff」不计，它是兜底）。
- 3 个只吃到轴1 兜底：`go.mod`、`internal/ssh/interactive_test.go`、`command_test.go` 的一部分。
- 结论：**名义上无空洞，实际有三处「有轴、无判据」**——轴1 兜底的判据只有「规范符合度 / 规格（锚）符合度」，这三块落不到这两条判据上。所以下面不是「漏了一个文件」，是「漏了一个判据」。

## 一、轴间缝隙

### G1 公共段的范围声明把轴5 的对象关在门外【必补】

- 缺什么：公共段（`提示词.md:22`）把工作区钉成「实现范围 `git diff dbcb797 e8c47a7`（26 文件）」，并按「每份提示词逐字附上公共段」下发。而轴5 的全部被审对象都在这个范围之外——
  - ADR-0030 的 88 行主体写在 `f7e6ab8`，是 `dbcb797` 的祖先；`dbcb797..e8c47a7` 里 0030 只改了 **1 行**（160→162、172→174 两个数字）。
  - ADR-0024 的状态行（`docs/adr/0024-env穿过sudo边界.md:3`）与更新记录（`:471`）、ADR-0015 的更新记录（`docs/adr/0015-远端环境前缀进配置.md:69`）同样出自 `f7e6ab8`，**一行都不在先声明的 diff 内**。
  - 也就是说：轴5 收到「范围＝26 文件」，而它要审的东西 90% 不在里面；交接清单反而写着 0030「本轮新建」、0024「本轮被取代」——两份材料的范围口径不一致。
- 补哪里：公共段改成**两个范围并列**：实现范围 `dbcb797..e8c47a7`；文档范围 `f7e6ab8..471c0a8`（ADR / 手册 / CHANGELOG / spec / 工单）。并在轴5 抬头一句「ADR 不在实现 diff 内，按全文审，取 `471c0a8` 工作区版本」。

### G2 `go.mod` 有兜底、无判据【必补】

- 缺什么：`modules/SSHFleet_Go/go.mod` 把 `go 1.27` 改成 `go 1.26.0`——这是把声明的最低 Go 版本**下调**，属兼容性声明改动。轴1 的两条判据（规范符合度、锚符合度）都指不到「声明的 Go 版本该不该降、与本次实现有没有关系」，其余四轴文件域都不含它。
- 补哪里：轴1 加一条独立检查项：「`go.mod` / 构建声明类改动单列，判『是否本次实现所必需』」；或干脆在公共段声明「`go.mod` 不在本轮范围」，并把「26 文件」改口径，别让兜底假装覆盖了。

### G3 测试文件归属不完整【必补】

- 缺什么两处：
  1. `internal/ssh/interactive_test.go`（diff 改 1 行，断言里加上 `wantEncodingFragment`）——轴2 文件域只到 `command.go` + `command_test.go`（`提示词.md:78`）；轴3 文件域只列 `interactive.go` 本体（`:93`），不含它的测试。而这条断言恰恰是「`-a` 下发行确实带上了片段」的**唯一**自动化证据，正属轴3 的「五种模式逐一对照 / 逐跳到位」。现在它只吃到轴1 兜底。
  2. `command_test.go` 本轮 +168 行，轴2 只认领了「对应断言」（片段那几条），但该文件主体是 `BuildCommand` / `DescribeCommand` 的整串断言与「开关开/关」两态——属轴3 的「量的串＝发的串＝日志的串」。轴3 文件域不含任何测试文件。
- 补哪里：轴3 文件域加 `internal/ssh/interactive_test.go` 与 `command_test.go` 的拼装类断言；同时轴2、轴3 各写一句切分规则：「同一测试文件按被测函数分——片段类断言归轴2，整串/说明文案断言归轴3」。

### G4 测试自身能不能失败，没人判【必补】

- 缺什么：`command_test.go` 546 行、`config_test.go` +44、`interactive_test.go` 都在被审对象清单里（交接清单 `:22`，写明「整串断言、开关开关两条、禁用形态反例」）。但五轴对测试的处理全是「断言与实现是否一致」——没有任何一条问「这些断言写宽了没有、改坏了会不会仍然通过、是不是把实现抄了一遍变成同义反复」。这是本轮唯一的真空区：一处断言写宽，等于这一整块改动没有回归保护，而五份回执都会说「未发现问题」。
- 补哪里：新增一条横向约束（放公共段，或并入轴1）：「每条新增/改写的断言，报『它能否在实现回退到 `dbcb797` 时失败』；不能失败的单列【判断题】」。

### G5 口径冲突：公共段把文档降为「顺带记」，轴5 却是重点【必补】

- 缺什么：公共段 `提示词.md:10`「本轮只审代码与实现效果；文档问题顺带记，因文档跑偏的着重记」；交接清单 `:5` 的开发者口径是「重点放在实现与 ADR 的描述上」，轴5 标题直接写「（开发者点名重点）」（`:107`）。公共段逐字附在轴5 前面，两种说法同时到达同一个子 agent，最省力的解读就是「ADR 只顺带记」——轴5 会系统性少产。且「因文档跑偏的着重记」是循环定义：跑没跑偏要靠审了才知道，不能当前置条件用。
- 补哪里：公共段那句改成按对象分档：「代码面按硬伤标准审；ADR 描述为开发者点名重点，同标准审；手册 / README / CHANGELOG / spec / 工单为顺带记」。

## 二、轴间重叠

### G6 轴1 的 `docs/` 把轴4、轴5 的地盘整个吞了一遍【必补】

- 缺什么：轴1 文件域写「整个实现 diff（`modules/`、`config/`、`docs/`、`README.md`、`CHANGELOG.md`）」（`:63`）。其中 `docs/` 与 `README/CHANGELOG` 正是轴4 的全域（`:105`），`docs/adr/*` 正是轴5 的全域（`:121`）。更要紧的是轴1 的「规格符合度」判据已被换成锚——同一批 ADR 文本，轴1 拿锚判、轴5 拿 doc-guide 判，两条轴会各自报出方向相反的条目（例如「ADR 这段与锚不一致」vs「ADR 这段标注合规」），主 agent 还得多一轮核实。轴1 还点名用 `/code-review` 的两轴切分，而它对文档只会产出规范类意见，与轴4/轴5 的判据不重叠但对象重叠。
- 补哪里：轴1 文件域收窄成 `modules/`（代码），并加一句：「`docs/`、`README.md`、`CHANGELOG.md` 只做**格式与仓库约定**符合度，内容与实现是否对得上一律交轴4，ADR 交轴5；同一处若两轴结论冲突，以对象归属轴的结论为准，另一轴只留一行指向。」

### G7 轴2 与轴3 在 `envHead` / 片段位置上交接不清

- 缺什么：轴2 覆盖项 6 判「片段在 `[env]` 的 `export` 段**之后**、`sudo` **之前**——这个位置……对不对」（`:76`）。这是**拼装顺序**，正是轴3 「量的串＝发的串」的地盘；轴3 文件域也明确拿了 `command.go` 的 `BuildCommand`/`innerCommand`（`:93`）。两边都没写「位置这件事归谁判」。轴3 只单向写了「不碰片段本身」，轴2 没写「不判拼装顺序」。
- 补哪里：二选一写死——要么轴2 只判「片段内部语义与副作用」，位置与顺序整体归轴3；要么轴2 判「位置是否满足锚1/锚7」，轴3 引用轴2 的结论不再重判。现状是两边都在判，且判据不同（轴2 用锚1/锚7，轴3 用「同源」）。

### G8 轴4 与轴5 都判三份出厂配置

- 缺什么：轴4 覆盖项 1 判三份 conf 的段一致性与注释口径（`:99`）；轴5 覆盖项 2 判「决定……与三份出厂配置有没有互相打脸的地方」（`:114`）。同一份文件、两条轴、两套判据。轴4 若发现 conf 自身不一致，轴5 可能判成「ADR 与 conf 打脸」，实际是 conf 写错了。
- 补哪里：轴5 加一句「conf 自身是否正确归轴4；轴5 只判『ADR 的说法与 conf 现状是否矛盾』，且冲突时以轴4 的事实认定为准」。

### G9 轴4 的 grep 起点跨进 ADR 与 issues【建议补】

- 缺什么：轴4 覆盖项 4 给的起步命令是 `grep -rn 'LANG\|LC_ALL\|LC_CTYPE\|\[locale\]' docs/ README.md CHANGELOG.md`（`:102`）。`docs/` 含 `adr/` 与 `issues/`，这条命令会把 ADR-0024/0030 与 spec 里所有提到 `LC_ALL` 的行拉进轴4 的候选清单，而这两块明写「ADR（轴 5）」「spec 只作对照」。
- 补哪里：把起点收窄到 `docs/1-*.md docs/3-*.md docs/4-*.md docs/5-*.md README.md CHANGELOG.md`，并补一句「`docs/adr/`、`docs/issues/` 的命中不计入本轴，转交轴5」。

## 三、预设污染

### G10 四处反问句已经把结论递到手上【必补】

- 缺什么：以下句子不是「查什么」，是「已经认定有问题，你去证实」：
  - `:82` 轴3 开篇：「而本轮给下发行加了一段恒在的片段、一个开关。**哪条路没跟上？**」——预设至少有一条路没跟上。子 agent 为了回答这个问题，会把「全都跟上了」写成「某某跳虽到位但不够优雅」之类凑数条目。
  - `:90` 轴3-5：「那条串现在多了 162–184 字节——长度检查量的还是同一条串吗？上限还够不够？」——「还够不够」预设了临界。
  - `:99` 轴4-1：「『值留空 = 关掉这一条』这类既有说明**还成立吗**」——预设不成立。
  - `:100` 轴4-2：「`locale.english` 进了必填表——这与锚2『默认 `false`』**是不是一回事**？」——预设不是一回事（否则不会单独拎出来问）。
- 补哪里：统一改成可判形式：「逐条核对 A/B/C 是否一致；全部一致就写『全部一致』，不一致的按【硬伤】记」。并把「没发现问题就明说」从回执段（`:24`）**抬到每个轴的覆盖项末尾**，别只放在公共段末尾——子 agent 读到覆盖项时，反问句的势能大于结尾那句免责。

### G11 锚表转述失真，基准本身被改动【必补】

- 缺什么：轴5 覆盖项 1 判的是「每条『决定』的授权来源，与实际能不能对上」（`:113`），对照基准就是这张锚表。而提示词里的锚表与交接清单的锚表**不是同一份**：
  - 锚2：交接清单 `:43` 是「**「提示语要能统一英文」作者明示**；开关位置与 `LC_MESSAGES` 取值助手推导」；提示词 `:33` 只剩「开关位置与取值为助手推导」——**作者明示那一半被删了**。按提示词的锚表，`[locale]` 开关整体都是助手推导，轴5 会判 ADR 把它标成作者明示是错的；而按交接清单，ADR 标得对。这是唯一一处会让轴5 直接产出假硬伤的地方。
  - 锚8：交接清单 `:49` 是「形态与字节数推导；**无 shell 目标走 `--no-shell` 作者明示**」；提示词 `:39` 只剩「形态与字节数推导」，同样削掉了作者明示的部分（内容还在句尾，来源标注没了）。
  - 锚3、锚4、锚5、锚6、锚7 两边一致，已核。
- 补哪里：锚表逐条对齐交接清单，**来源标注不能只写「助手推导」**；并加一句「锚表是本轮唯一的授权来源基准，与交接清单不一致时以交接清单为准，并在回执开头记一条『基准不一致』」。

### G12 轴2 开篇的事实断言未标注【建议补】

- 缺什么：`:67`「这一段是**唯一**碰目标机 shell 语义的地方，其余全是拼字符串」。这是主 agent 的结论，写成了事实。它同时起两个作用：给轴2 划界（合理）、和让轴2 不去看别处（越界）。若 `innerCommand` / `scriptStdinInner` 里的 `printf`/`base64` 那层其实也动了 shell 语义，轴2 不会去查，轴3 又只看「同源」不看语义。
- 补哪里：改成「本轴假定……；若在实测中发现别的拼装点也影响 shell 语义，另记一条并注明属越界发现」。既保留划界，又留了出口。

## 四、边界与产出

### G13 锚7 的「永不降级」没有可判形式【必补】

- 缺什么：锚7（`:38`）三条不变式里，「只动 `LC_CTYPE`」在轴2-2 被展开了（列出了 `LANG`/`LC_ALL`/`LC_MESSAGES`/`LC_COLLATE`），「永不告警」也被展开成「有没有往 stdout/stderr 漏字」。只有「**永不降级**」在 `:72` 只有一句「会降级吗？」——什么算降级没定义。至少三种读法会给出相反结论：a) 目标机已是 UTF-8 时仍然 `export` 算不算；b) 用户自己在 `[env]` 里设了 `LC_CTYPE=zh_CN.GB18030`，片段把它覆盖掉算不算；c) `charmap` 报非 UTF-8 但 `LC_CTYPE` 已是 UTF-8 名字时，导出同一族名字算不算。轴2 与轴5（判 ADR 的决定自洽）会各按一种读法判。
- 补哪里：在锚7 或轴2 里写死可判形式（以上三种情形逐条给「算 / 不算」），或明确「降级＝把目标机原本可用的 UTF-8 环境改成非 UTF-8；其余情形不算，另列判断题」。

### G14 锚质疑会与普通发现重复记【必补】

- 缺什么：锚质疑要求「发现某条锚与源码、实测或上游 ADR 对不上……另起『锚质疑』一节」（`:42`）。但轴5 覆盖项 1 本身就在判「授权来源与实际能不能对上」——授权来源写错，既是「锚质疑」又是「ADR 标注缺陷」，两条会被记两遍；反之，轴2/3 发现实现与锚不符时，「报锚不报工单」（`:28`）与「锚质疑」的界线也没写：实现不符是普通硬伤，锚本身错才是质疑，这句话两种读法都通。
- 补哪里：加一条分工：「实现与锚不符 → 普通【硬伤】，写明『实现偏离锚N』；锚本身与源码/实测/上游 ADR 不符 → 只进锚质疑，不再另记 ADR 缺陷；同一条既偏离锚又说明锚错时，两处各一行并互相指向。」

### G15 回执缺「本轮未能验证」一节【必补】

- 缺什么：回执只要求「没发现问题就明说『未发现问题』」（`:24`）。但本轮环境把验证面切掉了大半：无 `sudo`、无容器、无双机、无 `sshpass`（`:17-18`）。轴2 的 6 项里至少 3 项（真机 sudo 穿透、CentOS 7.9 的 `locale -a`、目标机缺命令）在本机造不出来；轴3 的「五种模式逐一对照」没有端到端环境；轴5 的「实测能复现吗」也只能算字节数。**没有「未验证」这一节，子 agent 会把测不了的项静默略过，主 agent 收到的「未发现问题」就是假的**——这比漏一个文件严重，因为它污染的是全部五份回执的可信度。
- 补哪里：回执固定三节：【硬伤】【判断题】【本轮未能验证（写清缺什么条件、靠什么替代）】，「未验证」也计入回执完整性；只有三节齐了才算交付。顺带把 `:24` 的「只报问题，不给修法」与「判断题要写清理由与代价」接一句：「代价只写『不这么判会付什么』，不写替代方案」——否则判断题会普遍写成修法建议，与「不给修法」打架。

### G16 造场景的手段没授权，与「不许声称跑过真机」互相掐【必补】

- 缺什么：轴2 要求覆盖「目标机缺某条命令」「候选不在」「`locale` 不存在」等场景（`:72`），但公共段只允许 `env -i`（`:19`），而本机 `locale -a` 只有 `C`/`C.utf8`/`POSIX`/`zh_CN.utf8`/`zh_SG.utf8`——造不出「有 `en_US.UTF-8` 无 `C.UTF-8`」那一类。唯一的做法是写 `locale`/`grep` 的 stub 并前置 `PATH`，但提示词既没说允许，还反复强调「不许声称跑过容器或真机」（`:18`）。子 agent 的合理反应是跳过这些项，然后「未发现问题」。
- 补哪里：轴2 明确「允许在 `build/audit_run_2026-10-28/轴2/` 下写 `locale`/`grep` 的 stub 并前置 `PATH`；回执必须标明哪几条结论来自 stub 环境、在真实目标机上未证」。与 G15 的「未验证」一节配套。

### G17 轴名 / 目录名 / 回执名三套并存【建议补】

- 缺什么：公共段写「`build/audit_run_2026-10-28/<轴名>/`」（`:4`）；提示词标题是「轴 1–5」（`:54` 起）；轴2 的文件域把目录写死成 `build/audit_run_2026-10-28/轴2/`（`:78`）；交接清单 `:80` 用的是「规范轴 / B 片段语义 / C 拼装链路 / D 配置与出厂面 / E ADR 描述」；复核员完全没有轴名（`:123`）。回执又要「由主 agent 收进 `回执/`」——六份产物会落在三套命名里，收的时候没法机械核对齐没齐。

### G18 复核员没有产出格式，也没有去重约束【必补】
