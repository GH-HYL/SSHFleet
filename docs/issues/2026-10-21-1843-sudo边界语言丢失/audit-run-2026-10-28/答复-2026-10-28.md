## Q2 续｜GB18030 那一格

> 「q2 你就把握一个原则，咱们可以配置，但一旦配置，就不能退化，因为退化就会输出错乱，直接破坏 工具的本身功能，一个工具连执行脚本 准确性都不能保证，要这工具做啥，这是原则问题」

**落定（判据）**：**可以配置，配了就不能退化。** 退化 = 从「按字符」掉到「按字节」，直接破坏脚本执行的准确性。

**由此推出一条判据，把「不等于 UTF-8」换成白名单**：只在 `locale charmap` ∈ {`C`, `POSIX`, `ANSI_X3.4-1968`, `US-ASCII`} **且** `locale -a` 里有候选时才动手；其余一律不动。
理由：这四种是「确知按单字节在跑」的名字，换成 `C.utf8` 只会多出多字节能力，不会掉；`GB18030` / `GBK` / `Big5` 落在白名单外，一律不动。

**顺带解掉两个缺陷**（同一处改动带来的）：
- 用户在 `[env]` 里显式配了 `LC_CTYPE`（如 `zh_CN.GB18030`）时，`charmap` 读到的就是它 → 不在白名单 → 不动，不会再有「无声覆盖」（`回执/复核员.md` 硬 4 与 `回执/轴2.md` 判断题 8 的那处打架随之消失）。
- `LC_ALL=C` 的机器仍会动手但无效（Q2 原结论：认这个边界），不因这条改动变化。

## Q2 追加红线｜配了不能退化，`cut` / `awk` 的截取不能受影响

> 「可以配置、但配了不能退化  还有个最高优先级 cut awk 配了的，那种截取不能受影响，这决定了工具本身能不能用，这是根本问题了，可以说是红线了  不能将脚本 原版功能破坏，这可是批量操作，截取意外，就表示可能出现 严重破坏行为，绝不能允许」

**实测**（`build/audit_run_2026-10-28/cutawk/`，GNU coreutils `cut`、mawk 1.3.4）：

| 场景 | `LC_CTYPE=C` | `LC_CTYPE=C.utf8` | 是否变化 |
| --- | --- | --- | --- |
| `cut -c1-4`（ASCII `abc123456`） | `abc1` | `abc1` | **不变** |
| `cut -c5-7`（ASCII） | `234` | `234` | **不变** |
| `awk substr($0,1,4)`（ASCII，mawk） | `abc1` | `abc1` | **不变** |
| `cut -d= -f2`（`id=42 cpu=…`） | `42 cpu…` | `42 cpu…` | **不变** |
| `cut -c1-2`（中文） | `e6 9c`（半个字） | `e6 9c 8d e5 8a a1`（完整两字） | 变，方向是「修」 |
| `awk substr`（中文，mawk） | `e6 9c` | `e6 9c` | **不变**（mawk 与 locale 无关） |
| `grep -o '[[:alpha:]]*'`（中文） | 无输出 | 匹配到中文 | 变，方向是「不再漏」 |

**结论**：按白名单判据，红线成立——ASCII 数据上 `cut` / `awk` / 字段切分逐字节不变；本来按字符算的机器（`GB18030` 等）一个字节都不碰。
**唯一残留**：非 ASCII 数据上，截取从「半个字」变成「完整字」、`[[:alpha:]]` 从「匹配不到」变成「匹配得到」。这两处的方向都是「从坏到好 / 从漏到中」，但严格说仍是输出变化，**须开发者确认这不算破坏**。
