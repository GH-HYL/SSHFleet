## 问题

客户机的 Windows 10 1909 上，Go 版本该上色的地方全部变成转义序列残骸：

```text
【96m▶ 权限类型  -→【0m   【38;5;214msudo【0m
```

根因已定案（证据见 `findings-2026-10-16.md`）：1909 的 conhost 出厂默认**不启用**虚拟终端（VT）处理，
而 Go 版**从来没有人去开它**，却无条件输出 ANSI 转义序列 —— 序列于是被当普通文字逐字节画上屏。

**同一个工具，旧的 Python 版不出这个问题**：它在 import 阶段经 `loguru → colorama` 把 VT 打开了。
也就是说，这**不是新需求，是回退后的修补** —— 新版退回"什么都不做"，是能力上的净损失。

使用者是运维人员，工具部署在**他的**环境里。让他为一个工具去改注册表或换终端，
等于把工具的兼容责任转成他的系统管理负担。

---

## 方案

**方案 C：主动开 + 拿不到就降级。**（作者 2026-10-16 选定）

| 部分 | 做什么 | 什么时候起作用 |
| --- | --- | --- |
| **A 主动开** | 启动时尝试为输出流打开 `ENABLE_VIRTUAL_TERMINAL_PROCESSING` | 有控制台句柄、只是 VT 没开（**客户机 1909 的情形**） |
| **B 降级** | 开不成就不输出转义序列，纯文字 | 确认了是控制台、但 VT 打开失败 |

两部分为什么都要：**只有 A**，遇到"是控制台但开不成"的环境仍会外泄；**只有 B**，
在本来能上色的机器上也无条件放弃颜色——治了病，也治掉了功能。

## 使用者故事

1. 作为在 Windows 上跑 SSHFleet 的运维人员，我想让工具自己适配控制台，
   这样我不必为了一个工具去改自己机器的注册表，或换掉我习惯用的终端。
2. 作为在 Windows 10 1909（或更早）上工作的运维人员，我想让参数确认屏正常上色，
   这样我能在按下 `y` 之前一眼分清哪是字段名、哪是值。
3. 作为运维人员，我想让确认屏的字段名与值用不同颜色区分，
   这样我核对"这次到底要执行什么"时不用逐字读。
4. 作为运维人员，我想让确认屏的边框与横幅带色，
   这样屏幕上的信息块有边界，长输出滚动时不会串读。
5. 作为运维人员，我想让「以上确认无误，开始执行？」这句提问醒目，
   这样我不会在一片文字里找不到该在哪儿回车。
6. 作为运维人员，我想让危险命令警告有醒目的颜色，
   这样它不会被我正在看的命令内容淹掉。
7. 作为运维人员，我想让致命错误的 `[ERROR]` 前缀是红的，
   这样失败时我能一眼定位到那一行。
8. 作为运维人员，我想让「操作已取消」这类提示是黄的，
   这样我能把它与正常输出区分开。
9. 作为运维人员，我想让统计块与结果明细按成功 / 失败着色，
   这样几百台机器跑完，我能扫一眼看出整体结果而不是逐行数。
10. 作为运维人员，我想让节点清单清洗相关的提示（`[INFO]` 那类）带色，
    这样"表头行被移除了""某行被跳过了"这些提示不会被忽略。
11. 作为运维人员，我想让主密钥与凭据相关的提示带色，
    这样凭据出问题时我能立刻看到，而不是在日志里事后翻。
12. 作为使用者，我想让工具在**确实无法上色的环境**里干净地退成纯文字，
    而不是吐出一串看不懂的残骸。
13. 作为使用者，我想让这个适配**不需要我配置任何东西**——装好、跑起来就该是对的。

## 实施决定

### 1. 新增：颜色能力探测（`internal/common`，平台分文件）

仓库已有平台分文件先例（`internal/output/link_windows.go`）。

| 文件 | 构建约束 | 职责 |
| --- | --- | --- |
| 跨平台一份 | 无 | 持一个包级只读结果；提供取值辅助：不启用时把颜色码换成空串 |
| Windows 一份 | `//go:build windows` | 真实探测：取控制台句柄 → 判 VT 位 → 未开则开；开不成返回"不启用" |
| 其他平台一份 | `//go:build !windows` | 恒返回"启用"，**行为不变** |

探测在**包级初始化**时跑一次，此后只读。这保证它早于 `main()`、更早于任何一行颜色输出。

**判定顺序是三步，各自对应一种真实失败，不做二次探测**：

```text
取控制台句柄失败  → 不是控制台。本议题不处理该场景，按「输出颜色」处理（维持现状，见「不在本次范围」）
取到了，VT 位已开 → 启用
取到了，VT 位未开 → 尝试打开；成功则启用，失败则停用（纯文字）
```

### 2. 改动：26 个 ANSI 颜色常量由 `const` 改为 `var`

值改为经取值辅助获得，不启用时得**空串**。

| 文件 | 常量数 |
| --- | :---: |
| `main.go` | 3 |
| `internal/common/interactor.go` | 3 |
| `internal/confirm/confirm.go` | 8 |
| `internal/credential/masterkey.go` | 2 |
| `internal/nodelist/fields.go` | 3 |
| `internal/output/terminal.go` | 7 |
| **合计** | **26** |

六个文件各一个 `const` 块。**MUST NOT** 顺手重命名、**MUST NOT** 调整顺序、**MUST NOT** 合并或拆块。

**为什么是改常量而不是改调用点**：颜色都是**包级值**，引用形态是字符串拼接。值变空串后，
那一行自然退成无色文本——**所有调用点一处都不用碰**。这是当初把它们做成常量（而非内联字面量）白捡的红利。

### 3. 不动：所有调用点

一处也不许改。

### 4. 不动：进度界面

`internal/output/progress.go` 走 lipgloss 自带配色，对上述 26 个常量引用数为 **0**；
且 bubbletea 启动时会自己开 VT，它本来就不外泄。

### 5. 已核实的三条前提

```text
① 26 个常量没有被用在需要常量表达式的地方（case 标签 / 数组长度 / 索引）→ 全仓零命中，改 var 不会编译失败
② 四个目标包（confirm / output / nodelist / credential）都已 import common → 不用加依赖
③ 包级初始化早于 main() → 天然满足「第一行颜色输出之前」
```

### 6. 行为边界

| 场景 | 现在 | 本次改动后 |
| --- | --- | --- |
| Windows 控制台，VT 已开 | 上色 | 上色 |
| **Windows 控制台，VT 未开（客户机 1909）** | **外泄** | **主动开后上色** |
| Windows 控制台，VT 打开失败 | 外泄 | **纯文字** |
| 输出重定向到文件 / 管道 | 带转义序列 | **不变（本次不碰，见「不在本次范围」）** |
| 非 Windows 平台 | 上色 | **不变** |
