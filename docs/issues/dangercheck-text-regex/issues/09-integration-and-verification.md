## 不通过时怎么办

**语料全绿不是目的，它与规则的意图一致才是。** 这条工单允许——也鼓励——在语料不通过时提出质疑，而不是想办法让它变绿。

遇到不通过的用例，先分清是哪一种：

| 情况 | 怎么判 | 怎么做 |
| --- | --- | --- |
| **规则写错了** | 期望值有生产场景支撑，但正则没覆盖到 | 改规则 |
| **期望值错了** | 期望本身站不住（比如把日常操作判成危险） | 改语料，并在 `备注` 写明为什么原期望是错的 |
| **两边都说得通** | 例如「`print("reboot")` 该不该判 forbidden」 | **不改任何一边，列出来交开发者定** |
| **规格本身有问题** | 两条规则对同一命令给了矛盾结论 | **停下来报告**，不要自行选一条 |

**MUST NOT** 为了让测试通过而把期望值改成代码的实际输出——那等于用代码给自己判卷，语料就白写了。

**已知会踩到这种分歧的地方**（实施时很可能遇到，提前说明）：

- **字符串与注释里出现危险词**：`print("reboot")`、`echo "rm -rf /"` 在纯文本口径下会命中。这是 ADR-0019 明示接受的误伤，但**是否接受、接受多少，仍有商量的余地**——如果实施中发现这类误伤在真实脚本里太频繁，应当报告，而不是默默承受。
- **`argv` 顺序问题**：`echo /etc | xargs rm -rf` 里目标路径在 `rm` 前面，只认「rm 后跟路径」的正则抓不到。要不要为它加正则，是设计选择。
- **跨语言等价命令**：`shutil.rmtree("/etc")` 原文里没有 `rm`，要不要为它单独开分支，取决于「封到什么程度」的取舍。
- **`kill -1 -1`** 这类「语法上打不出去、语义上极其危险」的边角。

这些都不是「实施者自己看着办」的事——**列出来，交开发者裁决**。
