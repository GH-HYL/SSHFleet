# 危险命令检测改为纯文本正则 · 规格

Status: ready-for-agent

> **来历**：本议题从 `docs/issues/defect-scan-2026-10-17/` 的 D1 里拆分而来（2026-10-18）。方向已由开发者定案，见 ADR-0019。
>
> **性质**：这是判定引擎的重构，不是打补丁。规则文件、匹配器、手册、测试语料整体按新方案重写，**不考虑兼容旧配置**（开发者 2026-10-18 定）。

---

## 问题陈述

危险命令检测按 **shell 语法**把 `-c` 命令 / `-s` 脚本整份解析成命令段，再拿命令段文本去比规则正则。这个前提有两个毛病：

- **解释器一多就崩**：解释器表认可 15 种解释器，其中 `python` / `luajit` / `lua` / `node` / `nodejs` / `perl` / `ruby` / `php` 共 8 种不是 shell。非 shell 内容被当成 shell 解析，要么解析成功但命令段与真实执行内容无关（漏报），要么解析失败退化成逐行文本判（误报）。
- **判定不稳定**：同一份 python 脚本走语法树还是走逐行回退，取决于它在 shell 语法下能不能整份解析通过，于是同类脚本有时拦、有时不拦。

以上原先是从 `parse.go` 的分支结构推出（`parse.go:74-115` 只认 shell 语法节点，`:304-332` 是逐行回退），**当时未经探针实证**——`sshfleet/internal/*` 受 Go internal 规则保护，包外探针调不进去。

**2026-10-19 已在沙盒内实证**（做法：把 `modules/SSHFleet_Go` 整份复制到 `build/atest-2/probe/`，在副本里以包内身份加探针测试；仓库内代码未被触碰）。实测结果：

| 输入 | 现引擎判定 |
| --- | --- |
| `rm -rf /etc`（bash 等价物） | forbidden / 递归删除系统目录 |
| `python3 -c 'os.system("rm -rf /etc")'` | **不响（漏报）** |
| `perl -e 'system("rm -rf /etc")'` | **不响（漏报）** |
| `node -e 'execSync("rm -rf /etc")'` | **不响（漏报）** |
| `php -r 'shell_exec("rm -rf /etc")'` | **不响（漏报）** |
| `lua -e 'os.execute("rm -rf /etc")'` | **不响（漏报）** |
| `ruby -e '`rm -rf /etc`'` | forbidden / 递归删除系统目录（**唯一侥幸命中的一种**——因为反引号内的字面量恰好在 shell 语法下也解析得通） |
| `python3 -c 'print("reboot")'` | **forbidden / 系统重启（误报）** |

同一台机器、同一条 `rm -rf /etc`，写成 bash 就拦得住，写成 python / perl / node / php / lua 就整条溜过去——**D1 的漏报与误报都是实测事实**，不再是推断。误报那一行同时实证了 ADR-0019 记下的「误伤明示为可接受」：`print("reboot")` 被判 forbidden。

（脱敏后的最小复现步骤与探针源码见本次 Comments；探针在 `build/` 沙盒内，按规范**不进版本库**。）

开发者 2026-10-18 定方向：**检测器只是提醒使用者有危险命令，不是防线。** 不追求 100% 封堵，只追求减少漏报与误报；**不按解释器枚举**，用统一的一套思路，从底层「一对多」地封。

## 方案

**判定对象统一为原始文本，只用正则匹配，不再按语言解析。**

1. **判定对象 = 原始内容**：`-c` 的命令原文、`-s` 的脚本全文，解码后原样参与匹配。下发时套过什么外壳、编过什么码，与判定无关。
2. **统一路，不分语言**：不按解释器选解析器；`-c` 与 `-s` 用同一套匹配器。
3. **去掉注释**：整行注释、行尾注释、纯空白行不参与匹配。其余内容全部参与，包括代码字符串与参数里的字面量。
4. **一条危险命令可配多条正则**：一条规则下面挂多条正则，命中任意一条即该规则命中。用枚举写法覆盖各种旗标变体，而不是硬憋一条正则堵所有写法。
5. **语法树解析退役**：不再作为判定源，也不作为「补充召回」。理由见 ADR-0019。
6. **档位行为不变**：`forbidden` 档命中即打印警告框、以 1 退出；其余档位提示后确认。
7. **规则文件整体重写**：`keywords_dangerous.conf` 的规则按纯文本语义重写，**不兼容旧写法**。

**接受漏报**：变量拼接（`${X}rf`）、命令替换、运行时拼出来的命令，**不保证识别**（不是原理上判不出来——原文里可能整段可见，取决于规则怎么写）。

## 使用者故事

1. 作为运维人员，我希望 `-c` 或 `-s` 里出现的危险命令**不论用什么解释器写**，都能被提示出来。
2. 作为运维人员，我不想同一份脚本有时拦、有时不拦——判定结果要稳定、可解释。
3. 作为配置使用者，我想为同一条危险命令写多条正则来覆盖它的各种写法。
4. 作为运维人员，我不想因为脚本里一句注释而整批跑不了。
5. 作为接手这个仓库的人，我想知道这套检测**能封到哪一层、封不到哪一层**。

## 实现决策

> 这 5 条决定的是「规则长什么样、引擎边界在哪」。**2026-10-19 已全部定案**，形态见下方「定案 A–E」；工单照它们拆。

| # | 决策 | 定案形态 |
| --- | --- | --- |
| 1 | **规则文件形态**：规则挂多条正则；旧写法不保留 | `regex` 改为**字符串数组**，单条也写成数组；无兼容分支（定案 A）；另增 `reason` 说明字段（定案 K） |
| 2 | **规则命中即停**：任一正则命中即该规则命中，规则级去重，提示列出全部命中位置 | 整份原文一次匹配；同一规则多处命中合成一条提示，提示里列出全部行号（定案 B） |
| 3 | **规则全部外置**：认哪个命令、什么写法算危险，全在规则文件；代码只做读取与匹配 | 代码里不存在命令白名单/黑名单表（定案 C） |
| 4 | **去注释**：在匹配器里做预处理，不依赖语言解析 | 纯文本预处理，剔除整行/行尾注释；引号内 `#`、`$#`、`url#frag` 不算注释 |
| 5 | **判定层退役重估**：语法树解析、逐行回退、朴素分词退役；「包装命令剥离 / rm 旗标归一 / 间接执行递归」的结构在纯文本下不再具备，38 条规则需逐条重写 | 前四项退役；**路径归一保留**并降为纯文本整备（定案 C）；38 条逐条过一遍（删/并/改档的判决见 `audit.md`），配对照表 |

### 定案 A–E（2026-10-19）

**定案 A · 规则文件字段形态**：`regex` 由字符串改为**字符串数组**，是唯一写法——只挂一条也写成一行数组。其余四个字段（`name` / `example` / `risk_level` / `enabled`）不变；另有新增字段 `reason`（说明，见定案 K，必填）。旧写法不保留兼容分支。

- 为什么选数组而不是「字符串 + 另一字段取并集」：一条规则挂多条正则是新语义的**正式形态**，单条只是特例；两处可写会长期留一个要维护的分支，正是 ADR-0019 备选表里已否掉的写法。
- 代价：现有 38 条规则必须全部过一遍并改写成数组形态（原有写法一律拒绝加载并指名报错）。**规则不是照抄 38 条**——删 / 并 / 改档的判决见 `audit.md` 第九节，落地后条数会变，本文不预先钉死最终条数。

**定案 B · 判定粒度、行号与多命中展示**：**整份原文一次匹配**，规则**不得跨行匹配**（不加 `(?s)`）。行号由命中起点的字节偏移反算（= 该偏移之前的换行数 + 1）。

- 命中内容取**命中所在行的原文**（去首尾空白），行号取该行——提示里「内容」显示的仍是使用者自己写的那一行。
- 同一规则命中多处 → 只出一条提示，行号处列出全部命中行（如 `行号: 3, 7, 12`）。
- **每块命中显示 7 行**（2026-10-19 定）：`来源` / `行号` / `内容`（可截断）/ `规则` / `示例`（规则的 `example`）/ `说明`（规则的 `reason`）/ `级别`。
- **全部列出，不做折叠**（开发者 2026-10-19 定）：一段脚本命中几条规则就列几块，框行数按命中数增长（3 条 ≈ 21 行）。**MUST NOT** 只显示最高档、把其余折叠成「另有 N 条」。理由：`--yes` 无人值守时框里的内容就是唯一提示，折叠等于把信息藏起来。
- 为什么不由逐行切分来做：逐行切分虽然行号天然准确，但跨行**续行符**（`rm \` 换行 `-rf /`）会因被切断而判不出。整份匹配 + 禁跨行是能写进配置头注释、使用者一眼看懂的口径。
- **知情漏报**：真写成跨行的危险命令判不出，记入「接受漏报」。
- **落地的连带影响（2026-10-19 补记）**：现 `Match` 的行号是**单个整数**，呈现层与 `main` 的日志都按单值用。改成「列出全部行号」意味着**字段形态要变**，并同步改呈现与日志三处。这不违反下方「测试决策」的接缝约定——接缝管的是 `Analyze` 的**入口**，`Match` 的**字段形态**不归它管。

**定案 C · 引擎边界：路径归一保留，其余四项退役**：

| 旧结构 | 去留 |
| --- | --- |
| 语法树解析 / 逐行回退 / 朴素分词 | 退役（删干净） |
| 包装命令剥离（`sudo` / `env` / `xargs`…） | 退役；纯文本下改为在各条规则里用一条可选前缀正则表达 |
| rm 旗标归一（`-rf` / `-r -f` / `--recursive` 拍平成固定次序） | 退役；改为**枚举写法**：一条规则挂多条正则，各管一种旗标写法 |
| 间接执行递归（`shell -c` / `eval` / `ssh` 远端）与命令替换递归 | 退役；原文里整段可见，由规则自己按长相命中 |
| **路径归一**（合并重复斜杠、去尾斜杠、词法解 `.` 与 `..`） | **保留**，但降为纯文本整备 |

- 路径归一为什么留：它不建命令结构、不认语言，只是把文本里的路径片段按字面整备一遍（`//x` → `/x`、`/etc/` → `/etc`、`/a/../b` → `/b`），与「不解析」的原则不冲突。留它，`rm -rf //` / `rm -rf /.` 这类写法不必在每条规则里枚举斜杠变体。
- 实现约束：它必须是**纯文本片段替换**（扫出路径样式的片段，原地整备），不得演变成分词或结构识别；替换不改变换行数，行号口径不受影响。
- 匹配用整备后的文本，**显示用原文**——使用者看到的始终是自己敲的那一行。

**定案 D · 读取侧与下发侧以哪侧为准**：**同一份文本**。检测读脚本时按与下发侧相同的整备处理（剥 UTF-8 BOM、去整块首尾空白），两侧不再各读一份不同的文本。

- 整备只做一次、只有一处来源，不另抄一份实现。

**定案 E · 手册中的错误表述一并改**：使用手册写着「同一条命令命中多条规则时，只显示风险最高的那一条」，与实际行为（全部列出）不符，且正落在决策 2 要改的那一处。本轮按决策 2 的最终口径重写，不另立议题。

**定案 F · 规则本身要过筛子，不是 38 条照抄重写（2026-10-19 追加）**：开发者要求「每条是否真有提醒的必要、能不能合并，尤其中低档还要不要检测」。实测取证与逐条判决见 `audit.md`，此处只记定案：

1. **判据只有一条**：这条规则防的，是不是「生产批量作业里**绝无正当形态**」的动作？是 → 可留 `forbidden`；不是但后果重且难回滚 → `high` / `medium`；**是日常正当操作 → 删**。
2. **`low` 档保留为合法取值，只是出厂配置里不预置任何一条 `low` 规则**（2026-10-19 开发者定，订正此处原判「整体取消」）。理由：`high` / `medium` / `low` 三档走**同一条**确认路径、呈现层只换颜色与措辞，**没有任何处置差异**——`low` 不承担独立语义。（`--yes` 下三档都会打印警告框，只是不阻断；所以删 `low` 不丢失「被看见」这一点。）
3. **`forbidden` 只留给误报几乎不存在的动作**。它是唯一会**整批作废**的档位（`--yes` 也不放行），配不上它的动作一律降档。
4. **合并优先于保留**：同一件事的多种写法（旗标变体、等价命令）用**一条规则挂多条正则**表达，不并列成多条规则。定案 A 的数组形态正是为此准备的。
5. 判决结果：38 条 → **17 条**（`forbidden` 10 → 6，`high` 9 → 5，`medium` 13 → 6，`low` 6 → 0 条**入出厂配置**，档位本身保留）。逐条删/并/改档的理由见 `audit.md` 第九节；`high` 比 9.2 的 7 条再少 2，是定案 J 把 `格式化非主盘` / `dd 覆盖非主盘` 并进 forbidden 后删掉的。

> **这是本议题最容易做偏的一处**：把「重写正则」当成纯机械活，38 条照抄成数组形态。那样等于把现有的噪音与漏报原样搬进新引擎。**必须先按定案 F 过筛子，再写正则。**

**定案 G · 本轮只做删减与合并，不新增规则（2026-10-19 追加）**：实测查出若干真实漏报（NVMe 盘符、Debian 系包管理、`fdisk` / `wipefs` / `shred`、截断关键文件），**本轮一条都不加**。理由：本议题定位是「重构，不是打补丁」，把「该加什么」塞进来会让一次作业同时改两件事，验收扯不清。缺口清单留在 `audit.md` 第十节，另开议题。

> **三条不属于「新增规则」、必须在本轮做的**（都是「把已在的规则修对」而不是「加新规则」）：
> 1. `dd` 抹盘补 `/dev/nvme0n1` 这类盘符——不是加规则，是把既有规则漏掉的写法补上（`audit.md` 8.3）；
> 2. 「停止·禁用服务」的名单换成 `sshd` / `network`——不是加规则，是原名单枚举反了（`audit.md` 8.2）；
> 3. `shutdown -c` 从「关机停机」里过滤掉——不是加规则，是原正则把撤销动作也拦了（`audit.md` 8.1）。**开发者 2026-10-19 明确：不新增规则，过滤即可。**

**定案 I · 语料与规则冲突时允许质疑，不强迫凑绿（2026-10-19 追加）**：本规格与逐条的规则判决**不保证没有错**。实施中语料不通过时，**先把分歧分辨清楚**——是规则写错了、还是期望值本身站不住、还是两边都说得通——**列出来交开发者裁决**，而不是改期望去迁就代码。

- **MUST NOT** 为了让测试变绿而把期望值改成代码的实际输出，那等于用代码给自己判卷。
- **预期会撞到分歧的地方**已在工单 09 的「不通过时怎么办」列出（字符串里出现危险词、`xargs` 参数在前的写法、跨语言等价命令、`kill -1 -1` 这类边角）。这些**不是实施者自己看着办**的事。
- 理由：本议题的规则删减判决（38 → 17）是**判断**，不是定理。把它当不可质疑的输入，就会把一个可能的错误固化进代码。

**定案 H · 旗标写法归规则自己吃（2026-10-19 追加）**：原配置头注释向使用者承诺「不用管用户怎么写旗标，工具会先归一化」。**该承诺随旗标归一退役而失效**，改为：**每条规则自己用多条正则列全它认的旗标写法**，配置头注释照新口径重写。不走「保留一道轻量旗标归一」——那与定案 C 直接冲突。

> **实现提醒**：Go 的 `regexp` 是 RE2，**不支持负向断言** `(?!...)`（沙盒实测 `Compile` 直接报错）。「排除某写法」只能用**整行锚定 + 字符类排除**表达，且**不能省行尾锚定**——早退会看不见后半段的排除项。这条已在 04 工单里给了验证通过的写法。

**定案 J · 盘符规则不分主次，`mkfs` / `dd` 一律 forbidden，high 里那两条重复规则删除（2026-10-19 追加）**：`格式化主盘` / `抹盘 dd` 两条**不区分系统盘与数据盘**，凡命中盘设备即 forbidden。原判据「那条盘是不是系统盘」不成立——检测器跑在**几千台不同机器**上，同一个 `/dev/sda` 在这台是系统盘、在那台是数据盘，正则**无从知道**每一台的盘符布局。

- 开发者判据（原话：「这个是匹配工具，都写内容，他在批量的场景下，就是最高级别风险，就是强制拦截」）：批量工具里写进命令的盘设备，即便在单机上是数据盘，下发到整批也可能是各机系统盘；**误伤的代价是整批拒绝一次，漏掉的代价是整批不可恢复**。
- **影响判决**：原 `high` 里的 `格式化非主盘` / `dd 覆盖非主盘` 两条**整条删除**——`forbidden` 的 `格式化主盘` / `抹盘 dd` 已覆盖全部盘符，留着就是同一件事的第二份定义，日后两处必然不一致。
- **最终条数由 19 改 17**：`forbidden` 6、`high` 5、`medium` 6、`low` 0（出厂配置）。不是凑数：条数按「一条规则一件事」算出来，不为了对上旧数而保留重复规则。
- 语料随之一致：`mkfs.* /dev/<任意盘>`、`dd of=/dev/<任意盘>` 的期望**一律 forbidden**，规则名归 `格式化主盘` / `抹盘 dd`；原写 `high` + `格式化非主盘` / `dd 覆盖非主盘` 的行逐条改过来并订正理由。
- **「按主机分组给不同档位」不属本议题**：那要改规则加载器（按 `--host`/清单给不同规则集），属新增功能，见「不在本次范围」。

**定案 K · 规则挂一句「为什么拦」的说明，警告框与日志都显示（2026-10-19 追加）**：规则文件新增第五个字段 `reason`，写这 10 余字的场景判断（如「删掉系统配置目录，整批同时无法恢复」）。它出现在：

1. **警告框**：每块新增两行——`示例:`（规则里的 `example`）与 `说明:`（规则里的 `reason`）；
2. **`--yes` 下的日志留痕** 与 **确认后的日志**（`main.go` 的 `autoNote` / `dangerNote`）：与警告框同口径带上这句说明。

**`example` 与 `reason` 分工不同，两行都要有**（开发者 2026-10-19 定）：

| 字段 | 上屏 | 回答的问题 | 给谁看 |
| --- | --- | --- | --- |
| `example` | 是，一行 `示例:` | 「**大概是什么命令**触发的」——正则使用者看不懂、原命令内容又乱，只有一条示例能让人一眼定位 | 终端使用者（定位） |
| `reason` | 是，一行 `说明:` | 「**为什么**这条要拦」 | 终端使用者（理解） |

形态与校验：

- 字段名 `reason`，**规则级必填**——空则加载失败并**指名是哪条规则**（与 `name` / `example` 同一套校验）。
- **`reason` 与 `example` 长度上限都是 30 个汉字宽度**（终端显示宽度，一个汉字算 2），超了**加载失败并指名**，不静默截断。两者走**同一套校验逻辑**（开发者 2026-10-19 定）。
- **`reason` 的超宽校验属于规则加载报错**，与「命中危险命令时的提示框」是**两件事**，互不相干（开发者 2026-10-19 明确）。报错形态与「定案 O」其他加载报错一致：能定位、能理解、能处置。
- **为什么超宽是报错而不是截断**（开发者 2026-10-19 定）：`reason` 只影响显示、**不影响任何执行行为**，使用者改它的成本很低；默认配置**一条都不会报错**，只有自己加了或改坏了才会报错——报错本身就把「为什么」说清楚了，「改一下」就好。截断恰恰相反：它**不声不响**，使用者看到半句话不知情，会以为是程序算错了。报错只发生一两次，代价是一次性的；截断是持续性的困惑。
- **校验的是框架，不是内容**：只查「有、且不超宽」，不查措辞是否准确。内容随时可改，改它不必动代码；措辞不准确不是加载错误。

**定案 L · `内容:` 行遇超宽只截断、不撑破框（2026-10-19 追加）**：警告框的 `内容:` 行**只是一个位置提示**——使用者按行号回原脚本看原文即可。单行超过显示宽度时**截断显示**（加省略号），**MUST NOT** 让框线被撑歪。

- 现有实现 `output/danger.go` 的 `内容` 行只截一次 46 列，但 `规则:` 行同为单次截断；本轮要保证的是**任何宽度下每行框线等宽**，现有测试 `TestDangerBoxLinesAreEqualWidth` 只覆盖短内容，需补超宽用例。
- 行号与内容互为索引：**行号必显示，内容可截断**。

**定案 M · `low` 保留为合法档位，出厂配置不预置（2026-10-19 追加，订正定案 F 第 2 条）**：`low` **不取消**。它是四档之一，规则文件里写 `low` **正常加载、正常显示**，用户自己加的 `low` 规则可以用。出厂配置**一条 `low` 也不放**——原来那 6 条 low 规则照删（它们本就是日常运维动作）。

- 为什么订正：定案 F 第 2 条的原理由是「三档走同一条确认路径、`low` 没有独立语义」。开发者判定：**合法取值与出厂预置是两件事**——取值层多留一档不增加任何维护成本，反倒省掉「用户旧配置写了 `low` 就起不来」这一刀。
- 落地形态：`riskOrder` 仍是**四档一个来源**（`forbidden < high < medium < low`），校验与排序共用；`output/danger.go` 的 `riskLevelText` 保留 `low` 分支（显示「低」）。**MUST NOT** 在校验处特判放行 `low`——那会变成两处真相。
- 验收口径仍是「加载失败要指名」，但**不再有「`low` 写进去就报错」这一条**；对应的验收改为「手工加一条 `low` 规则 → 正常加载、警告框正常显示」。

**定案 N · 停用（`enabled = false`）的规则只校验 `name`（2026-10-19 追加，订正现有配置注释）**：规则被停用后，加载时**只要求 `name` 非空**，其余字段（`example` / `reason` / `regex` / `risk_level` / `enabled` 之外的一切）**一律不校验**：可以是空、可以是非法值、正则可以不编译。

- 现有配置头注释写「停用只是不参与判定，其余四项仍要照旧写全」——**这句话是错的**，按本定案改写。
- 为什么只留 `name`：停用规则不参与判定，却因为一个不参与判定的字段启动失败，等于「停用也要被拦」；但 `name` 是人在配置里认规则的唯一标识，连它都不要求，配置日后就没人看得懂。
- 启用（`enabled` 缺省或 `true`）时，全部字段照常校验，口径见定案 O。
- **停用的规则当作不存在**（开发者 2026-10-19 明确）：不校验、**不统计**（不进条数下限的计数口径之外的东西）、**不提示**——启动时不打「有 N 条规则已停用，未校验」这类提醒。

**定案 O · 规则加载报错必须「能定位、能理解、能处置」（2026-10-19 追加）**：`rules.go` 报出的每一条加载错误，**MUST 让使用者只凭这条报错**就能做到三件事：

1. **定位**——指名是**哪条规则**（有 `name` 用 `name`，没有就用「第 N 条」）与**哪个字段**；
2. **理解**——说清期望的形态，而不是只说「非法」。例如 `regex` 写成了字符串：指出「`regex` 需写成数组」，并给一行可照抄的正确写法；
3. **处置**——给出下一步怎么办。

适用面：`rules.go` 的**全部**加载报错（缺字段、`risk_level` 非法、正则编译失败、`reason` 超宽、`regex` 旧写法、条数不足），不是只改新引入的那几条。

- **约束**：报错是**使用者可见文案**，按规范「四·4」写——简洁、只写当下、不写沿革；不用内部符号名（`Rule` / `riskOrder` 之类）。
- **`example` 必填**（定案 K 的配套）：`example` 会**显示在警告框里**——正则使用者看不懂、原命令又乱，只有示例能让他一眼知道「大概是哪类命令触发的」，所以它是**必填**的，不是可选。
- 这一条**不扩到其他模块**：只覆盖规则加载这一处，别的报错本轮不动。

**定案 P · 检测器不做「按机器分组」（2026-10-19 追加）**：所有机器**一套规则**。规则文件不引入按主机／清单区分的字段，加载器也不按目标挑规则集。理由：那要改规则加载器与清单的耦合，属新增功能；本议题定位是重构，不顺手加能力。

- **期望值 MUST 独立于被测代码**：语料里的期望规则名与级别由人按生产场景判断后给出，**不得由规则文件反推**。

  - 为什么不用「随机抽查人工确认」：抽查是**动作**不是**机制**，这次抽了下次未必抽。要求每行写理由，是把判据钉进语料本身。
