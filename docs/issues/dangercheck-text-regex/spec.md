# 危险命令检测改为纯文本正则 · 规格

## 问题陈述

危险命令检测按 **shell 语法**把 `-c` 命令 / `-s` 脚本整份解析成命令段，再拿命令段文本去比规则正则。这个前提有两个毛病：

- **解释器一多就崩**：解释器表认可 15 种解释器，其中 `python` / `luajit` / `lua` / `node` / `nodejs` / `perl` / `ruby` / `php` 共 8 种不是 shell。非 shell 内容被当成 shell 解析，要么解析成功但命令段与真实执行内容无关（漏报），要么解析失败退化成逐行文本判（误报）。
- **判定不稳定**：同一份 python 脚本走语法树还是走逐行回退，取决于它在 shell 语法下能不能整份解析通过，于是同类脚本有时拦、有时不拦。

以上是从 `parse.go` 的分支结构推出（`parse.go:74-115` 只认 shell 语法节点，`:304-332` 是逐行回退），**未经探针实证**——`sshfleet/internal/*` 受 Go internal 规则保护，包外探针调不进去。

开发者 2026-10-18 定方向：**检测器只是提醒使用者有危险命令，不是防线。** 不追求 100% 封堵，只追求减少漏报与误报；**不按解释器枚举**，用统一的一套思路，从底层「一对多」地封。

## 方案

**判定对象统一为原始文本，只用正则匹配，不再按语言解析。**

1. **判定对象 = 原始内容**：`-c` 的命令原文、`-s` 的脚本全文，解码后原样参与匹配。下发时套过什么外壳、编过什么码，与判定无关。
2. **统一路，不分语言**：不按解释器选解析器；`-c` 与 `-s` 用同一套匹配器。
3. **去掉注释**：整行注释、行尾注释、纯空白行不参与匹配。其余内容全部参与，包括代码字符串与参数里的字面量。
4. **一条危险命令可配多条正则**：一条规则下面挂多条正则，命中任意一条即该规则命中。用枚举写法覆盖各种旗标变体，而不是硬憋一条正则堵所有写法。
5. **语法树解析退役**：不再作为判定源，也不作为「补充召回」。理由见 ADR-0019。
6. **档位行为不变**：`forbidden` 档命中即打印警告框、以 1 退出；其余档位提示后确认。
7. **规则文件整体重写**：`keywords_dangerous.conf` 的规则按纯文本语义重写，**不兼容旧写法**。

**接受漏报**：变量拼接（`${X}rf`）、命令替换、运行时拼出来的命令，**不保证识别**（不是原理上判不出来——原文里可能整段可见，取决于规则怎么写）。

## 使用者故事

1. 作为运维人员，我希望 `-c` 或 `-s` 里出现的危险命令**不论用什么解释器写**，都能被提示出来。
2. 作为运维人员，我不想同一份脚本有时拦、有时不拦——判定结果要稳定、可解释。
3. 作为配置使用者，我想为同一条危险命令写多条正则来覆盖它的各种写法。
4. 作为运维人员，我不想因为脚本里一句注释而整批跑不了。
5. 作为接手这个仓库的人，我想知道这套检测**能封到哪一层、封不到哪一层**。

| # | 决策 | 产出 | 验收 |
| --- | --- | --- | --- |
| 1 | **规则文件形态**：规则挂多条正则；旧写法不保留。字段名在工单 01 里定 | 新 `keywords_dangerous.conf` 格式 + 加载器 | 旧配置被明确拒绝并报错；无旧写法兼容分支 |

| 5 | **判定层退役重估**：语法树解析、逐行回退、朴素分词退役；「包装命令剥离 / rm 旗标归一 / 间接执行递归」的结构在纯文本下不再具备，38 条规则需逐条重写 | 规则重写清单 + 影响面 | 每条旧规则的等价新写法有对照表；无规则遗漏或语义漂移 |

**这 5 条为什么单列成前置工单**：它们决定的是「规则长什么样、引擎边界在哪」，先定它们，实施才是可执行的动作；不定就动工，等于把规格又猜一遍。

## 测试决策

**这是重构，测试是验收的主体。**

- **接缝**：包内测试直调 `Analyze`，与 `dangercheck_test.go:56` 同形。若新匹配器另起导出符号，接缝在工单 01 里定。
