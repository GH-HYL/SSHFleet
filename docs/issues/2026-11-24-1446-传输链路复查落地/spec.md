# 传输收场三处对齐：下载的半成品、一台的账、环节名对照判据表

- **Status**：done
- **日期**：2026-11-24
- **关联**：ADR-0021（失败原因统一为报文）、ADR-0022（上传失败即回滚）、ADR-0063（sftp 会话整体提权）、ADR-0065（清理动作不受超时与中断影响）

## Problem Statement

下载这一台的传输预算到点时，如果那次取文件还卡在传输里没退出来，收场只报一句「到点了，目标机上没有本次留下的东西」——而本机下载目录里，那个写了一半的文件就在那儿。使用者照这份报告清现场，清不到它；下回把同一个目录当成交付物，里面混着半截文件，没人知道它是哪一次留下的。

同一份报告里的「打算传几个、成了几个」也不总可信。四个数与明细行由十几处各写一遍，新增一条早退路径忘写一处，报告里的文件数就印错；下载的到点收场会把已经传成的数抹成 0（那条路把当时的成功数与字节当成 0 交出去），下载与上传的失败早退又只写四个数、不写统计行。「写之前先把远端路径挂上账、确认远端没有它才消账」这条不变量没有地方承载，于是「文件建出来了、写却挂了、尾巴也没交上来」的那一路照样漏账：报告说目标机干净，其实上面躺着这个名字。

进度条底下两套逐字节包装同构，改一处漏一片。

## Solution

下载到点卡住时，报告与本机实际一致：那个写了一半的本机文件被点名列出，不再说「什么都没留下」。

一台传输的四个数与明细行只有一个出口：早退、到点、中断、逐文件失败都落到同一个记账动作；报告里的文件数不会因为多一条路径而印错；目标机上「现在可能有什么」由账本自己保证，收场不用再猜。

进度仍然是那一套节流与那一帧补推，底下只剩一个计数包装。

新加环节名而忘了配判据表，闸门当场红，不用等使用者报「这类失败没分类」。

## User Stories

1. 作为运维，下载因超时停下时，我希望报告点名本机那个写了一半的文件，因为清现场要照着这份报告清。
2. 作为运维，我希望下载目录里的半截文件不会被说成「哪都没留」，因为下一次拿这个目录交差时，半截文件会被当成完整文件。
3. 作为运维，我不希望工具替我把那个本机文件删掉再报「删过了」——它可能还在被写，我要的是它报出这个路径，由我决定什么时候清。
4. 作为运维，一台传输的「打算传几个、成了几个」必须和我在目标机上数到的对得上，不能因为失败在哪一步发生而变。
5. 作为运维，上传中途失败时，报告里「删掉了哪些、还剩哪些」要覆盖所有已经落到目标机上的名字，包括那次还没写完的。
6. 作为运维，进度条不能因为底层合并了两套实现就变慢、少报数或不报最后一帧。
7. 作为以后给传输加环节名的人，我希望在跑闸门时就被指出判据表缺条目，而不是等使用者报上来。
8. 作为以后维护这块代码的人，我希望「哪一步收场、说哪句话」和「这台打算传几个、成了几个」是两件事，改一件事不用动另一件。

## Implementation Decisions

### 下载卡住时，本机那个半成品要报出来

现状：取文件那次调用卡在流式拷贝里，传输时钟在收尾预算内也没等到它退出来（`armStuck`）；下载侧的收场把「这一次没跑完」一律当成超时，只发一句「目标机上没有本次留下的东西」。可本机 `os.Create` 建出来的那个文件、已经写进去的字节都还在——删它那一步只在取文件那次调用返回之后才跑，卡在这儿就永远轮不到。

要改的是收场那一格，不是那句报文：`armStuck` 时把这次正在写的本机落点当成「已登记、尾巴没交上来」，与上传侧处理在飞文件的写法对齐；收场时本机有半成品就追加本机那条半成品报文（`local_partial_left`），与逐文件失败那条路用的是同一个构造点。目标机零写入仍然是事实，「目标机上没有本次留下的东西」那句不动。

不删那个文件：写它的那次调用还没退出来，删的是正在被写的那个；报出路径，由使用者决定什么时候清。

这条属缺陷，先立一条能复现的用例再动生产代码；复现不出来就报「复现不了」并说明试过什么。

**未落地**（2026-11-24）：试过但没有复现出来——假目标机那侧无法让「往本机写」卡住（可造的只有「服务端读客户端发来的字节」那一头，即上传的写侧），改用 1MB 远端文件加 `stallSftpSendAfter(256<<10)`、收尾预算压到 3 秒之后，实测 `closeSFTP` 会把卡住的那次读解开、`getFile` 走 `copyErr` 分支把本机半成品删掉、`arm` 返回 `armExpired`，收场报的「目标机上没有本次留下的东西」与事实一致。按红线 5，复现不了就不动生产代码；这一格留给开发者定夺（改成防御性报告，或撤掉）。

### 一台传输的账本（缩水版）

新类型 `transferAccount`，只装四样：四个数、明细行、一个 `settle`。`settle` 是**唯一**把四个数与明细行写进 `res` 的地方（`res.Transfer` 与 `res.Output` 一起写，两者本来就成对）。

- `written`／`half` **不进**共用对象：上传要、下载用不上，塞进去就是「传整个对象只用两个字段」的反面。它们留在上传自己手里。
- 各路径的**收场句子不动**：超时、中断、回滚各说各的，句子不是账本的事。本轮只把「拼参数」这一半收进去，「为什么收场」这一半留在原处。

上传自己那张「远端挂账」表按一条纪律维护：**写之前登记**（这条路径可能已经落到目标机上），**确认远端已无此名才消账**（删成功、或确实没建出来）。于是收场时「目标机上现在可能有什么」就是这张表里还挂着的那几条，不用再从几处零散变量里拼。少了这条，建出来又写挂、尾巴也没交上来的那一路照样漏。

范围之外的账不动：`res.Transfer` 的字段与含义不增不减；判定层读的仍然是四个数，不因为这次改动而换口径。

### 两个逐字节进度包装合成一个

`progressWriter` 与 `progressReader` 各带一套同样的字段、同样的节流判断，差别只有「写」与「读」，外加读侧在读到结尾时补推一帧。

合成一个计数包装（套在被读／被写的那个流上，按节流间隔回调一次）+ 一次结尾补推，上传与下载两条拷贝入口合成一条。补推只发生在读侧：读侧看得见流到了头，写侧看不见，所以上传侧不会因此多出回调——这不是行为变化。

参数个数不承诺变少：合并之后仍要传那几个（回调、序号、IP、总字节、总文件数、被包的流）。合并图的是「一处判断、一处计数」，不是签名变短。

### 环节名对照判据表

方向**单向**：代码里产出的每个环节名，随包的判据表里必须有一条 `sshfleet.<环境>.<环节>` 条目，缺一条即红。反向不判——判据表里有些条目由别的站产出，只看执行站看不全。

「随包的判据表」不止一张：错误分类一张（`config/keywords_error.conf`），改密那一摊另有一张（`config/keywords_passwd.conf`），危险命令一张（`config/keywords_dangerous.conf`）。所以不去点名哪一张，而是读 `config` 下全部 `.conf`，由表自己说它认哪个环境：一张表里认了这个环境的任何一条，它就是这个环境的表，这个环境的其余环节名也得在它里面。这样既不必在检查器里再抄一份「环境→表」的对应，又能抓住「条目写到了不该它认的那一张」——那一条运行时同样认不出来。

落点按先例：`internal/guard` 的检查总线里挂一条 `CheckStages`，与 `check_tip_symbols.go` 那种「判一件事」的检查同形；于是 `tools/check.sh --guard` 自动带上，**不新开开关**、不往包清单那张规则表加行。

取值从语法树上取：环境名与环节名都是常量，把常量块解析成字符串值再比，不靠正则扫源码文本。两格各有三条来路要收：直传常量与字面量、经一层参数转传（到调用点去取）、先赋给本地变量再拼；另有一类「挑名字」的辅助函数（拨号错误归哪一格、握手错误归哪一格），把它每个 `return` 的值也算一处产出——新加一个名字忘了配表，最常漏的就是它。两层以上的转传取不到，今天每一处传参都只有一层。

判据表的路径跟着检查目标的根目录走，于是测试里可以指一份迷你判据表，不必动真文件。

今天一对都不缺（真工程收出 44 对，全部有条目），所以这条检查上线当天是绿的；它防的是以后加名字忘配。

## Testing Decisions

**接缝**：`execute.Run`——执行站入口，递一张纸收一张纸。用例只断言那张纸上的四个数、报文与明细行，以及假目标机与本机临时目录上的文件；不断言内部类型与函数。既有用例都用这个接缝，不新开。

**下载卡住那条（新）**：照 `TestRunDownloadOverFakeTarget` 的造法，把目标机上那个文件换成大于 256KB 的，让假目标机在收到若干字节之后不再应答（`stallSftpAfter`），收尾预算压到 1 秒，于是「等它退出来」等不满。断言三样：记了超时；报文里出现本机那个落点的名字；报文里不出现「目标机上没有本次留下的东西」以外的「什么都没留下」暗示——本机那个文件仍在原处，没人删它。

造法先手跑一遍当复现：今天这一步应当失败（报文只提目标机干净、本机半截文件没人提）。

**上传已有同形用例**（写到一半那次调用到收尾预算也没退出来时，报出在飞的那个远端路径），下载这条与它对齐，两边判据一致。

**账本那条的判据是「数不变」**：既有上传／下载用例里对四个数、明细行、回滚清单的断言全部原样跑绿。重构的正确性靠这批旧断言钉，不新造面向内部类型的断言。

**进度包装**：`progress_test.go` 既有用例原样跑绿；另加一条钉「读侧到结尾补推一帧」，并把「无回调时直通、不套包装」也钉住。

**校验器**：在 `internal/guard` 的用例里造两个小模块——一个用了有判据表条目的环节名、一个用了没有的——各自应该绿与红；绿的那个还要点名四对：直传常量、经一层传参、同一个本地变量的两种取值都收得着（只看「零违规」判不出漏收）。真工程那一侧不另加断言：`TestProjectIsClean` 要求零违规，`CheckStages` 挂上之后它自然覆盖。反向（判据表里多一条没人产出的条目）不判，写明原因，免得后来的人当成漏项补。

**真机**：卡死那条只在假目标机上验——真机上没有稳定的「传到一半不再应答」样本；`-tags integration` 的既有下载用例照常跑，覆盖不卡死的那些路。

## Out of Scope

- 改报文措辞、改环节名：判据表认工具报文只到环节名为止，改名字等于换一类。本轮一句报文措辞都不动，新增的只有「本来就有构造点、只是这次用上」的那条半成品报文。
- 把 `written`／`half` 塞进共用账本对象。
- 统一收尾的两份协议（传输时钟里那份「到点后等它退出来」与收场里那份「清理不等」）：它们故意不一样，本轮不动。
- 合并 `closeSFTP` 的三处定义；调整传输与收尾两段预算的默认值。
- 判据表里「有条目、没人产出」的反向检查。
- 新开 ADR：这一轮的「为什么」已经在既有那几篇里；落地时若「写之前登记」与 ADR-0022 的残留口径打架，再单独议。

## Further Notes

- 顺序：先账本，再超时链路，最后校验器。理由不是依赖——收场靠回调，不依赖账本；是风险：账本动的是数，超时链路动的是收场时机，校验器只读。
- 进度包装那条碰上就做，不单开一轮。
- 校验器不往包清单那张规则表加行，`TestProjectIsClean` 里对规则行数的断言因此不动。
- 落地前的闸门：只动文档时跑文档档；动了 `.go` 之后跑全档。提交信息中文，标题只写做了什么。
- 本规格落地仍需开发者说「授权开工」四个字；在那之前只做只读核对与复现准备。
