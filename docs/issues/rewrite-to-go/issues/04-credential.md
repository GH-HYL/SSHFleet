## 一、已查明的事实

### 1.1 内容格式分类（`classify_credential`，无需密钥）

判定顺序关键：**加密 token 本身也是合法 base64，必须优先判加密。**

| 结果 | 判定方式 |
| --- | --- |
| `encrypted` | base64 解码后长度 ≥ 49 且首字节 == `0x01`（版本号） |
| `base64` | 合法 base64 **且重编码后与原文逐字符一致**（"重编码一致性回验"，避免恰好合法的明文被误判为 base64） |
| `plain` | 其余 |

### 1.2 格式 × 密码安全等级 错配矩阵（`_check_fmt_level`）

| 内容格式 | 等级 1（明文） | 等级 2（base64） | 等级 3（加密） |
| --- | --- | --- | --- |
| `encrypted` | `mismatch_encrypted` | `mismatch_encrypted` | ✅ |
| `base64` | `mismatch_base64` | ✅ | `bad_cipher` |
| `plain` | ✅ | `bad_base64` | `bad_cipher` |

> 模块注释明确：此矩阵曾是**三份重复实现**（`csv.py` 两套 + `upgrade.py` 一套），已收敛为单一来源。**Go 版必须保持单一实现**。

### 1.3 解码（`decode_credential`）

- 等级 1：原样返回
- 等级 2：base64 解码为 UTF-8
- 等级 3：取主密钥 → `decrypt_password`；失败归 `bad_cipher`

### 1.4 错误码 9 类 + 两套文案

| 错误码 | 短文案（`credential_error_label`，校验汇总用） |
| --- | --- |
| `missing` | 不存在 |
| `read_error` | 无法读取 |
| `empty` | 内容为空 |
| `bad_base64` | 不是有效的Base64编码 |
| `empty_decoded` | 解码后内容为空 |
| `bad_pem` | 不是有效的PEM格式（缺少 -----BEGIN 头） |
| `bad_cipher` | 不是有效的加密格式或主密钥不匹配（请先用 --convert-password 转换该文件） |
| `mismatch_encrypted` | 文件是本工具等级3（加密）格式，与当前密码安全等级不匹配 |
| `mismatch_base64` | 文件是等级2（base64）格式，与当前密码安全等级不匹配 |

另有 `credential_error_detail` 给**退出路径**用的完整指引文案（含"请把配置改为 3"这类可执行建议），与短文案分属两条路径。未知错误码有兜底，不再 KeyError。

### 1.5 私钥 PEM 走**独立通道**

`read_credential_pem` 只做：存在 / 可读 / 非空 / `-----BEGIN` 前缀，**不参与 1.2 的矩阵**——这是有意区分：PEM 私钥本身就是文本，套等级矩阵会误伤。

### 1.6 解码缓存

`(path, level) → 明文` 进程内缓存。理由（注释原文）：等级 3 时每个节点都会重复读盘 + 取主密钥；凭据文件运行中不变，无需失效。

### 1.7 主密钥

| 项 | 旧行为 |
| --- | --- |
| 环境变量名 | `SSHFLEET_KEY` |
| 生成算法 | `secrets.token_urlsafe(36)`（约 48 字符） |
| 缺失时 | 报错退出，并提示"请先生成主密钥：python sshfleet.py --gen-key" |
| Windows 持久化 | `setx SSHFLEET_KEY <key>`（写 `HKCU\Environment` 注册表） |
| Linux 持久化 | 写 `~/.bashrc`：已存在 `export SSHFLEET_KEY=` 行则**替换**，否则追加（带 `# SSHFleet 主密钥` 注释行） |
| 生成后提示 | Windows："请重新打开终端后再使用"；Linux："请执行 source ~/.bashrc 或重新打开终端后生效" |
| 覆盖保护 | 已有密钥（环境变量或持久化位置任一存在）→ 打印警告"旧密钥加密的凭据文件将永久无法解密" → 交互确认覆盖；**`--disinteractive` 时直接拒绝覆盖**，并提示"去掉 --disinteractive 后重新执行" |

### 1.8 凭据转换（`--convert-password`）

- **路径解析**：先按用户输入原样找（含 `~` 展开），找不到且是相对路径且有 `secret_dir` → 按 `secret_dir` 拼；两处都没有 → 报错
- **自适应识别**：明文 / base64 / 加密，统一还原为明文，再按目标等级重新编码
- **升降级矩阵**：明文↔base64↔加密 任意方向；降级（加密→base64→明文）需主密钥
- **已是目标格式**：打印"无需转换"并返回（不报错）
- **写回**：就地覆盖 → **从磁盘回读校验**（而非信任内存变量）→ 只输出转换摘要与内容长度，**不回显内容本体**（避免明文泄到终端）
- **防御**：空文件 / 含 NUL（二进制）/ 多行但非 base64 或加密格式 → 均报错

## 二、问题

### ❓ E1 — "重编码一致性回验"是否保留

旧版判 `base64` 时不只看字符集合法，还把解码结果重新编码比对，防止"一个恰好长得像 base64 的明文密码"被误判。

➡️ 推荐**保留**。这是个精巧的防御，成本就是一次编码；去掉会引入一类难查的误判。

### ❓ E2 — 错配矩阵的五条规则是否原样

➡️ 推荐**原样**，并加一句注释说明"`encrypted` 必须优先于 `base64` 判定"——这个顺序是矩阵能成立的前提，容易在重写时被忽略。

### ❓ E3 — 九类错误码 + 两套文案是否保留

➡️ 推荐**全保留**。理由：短文案用于"一次性列出所有错误"的汇总场景，详文案用于"读失败即退"的指引场景，两者受众不同，合并会让某一边变差。**并且这是你修过 bug 的地方**（旧版 if 链与字典两张表措辞漂移、且互相缺码）。

### ❓ E4 — 解码缓存在 Go 里怎么做

- (a) 保留：以 `(路径, 等级)` 为键的进程内 map，加锁
- (b) 不缓存：每次读盘
- (c) 在读取阶段一次性把明文凭据填进节点信息，后续直接用（不依赖缓存）

➡️ 推荐 **(c)**。旧版需要缓存是因为"校验阶段"和"使用阶段"两次读盘；新版若把两条路径合并成一次"读 → 校验 → 直接用"，缓存就没必要了——这是**能简化掉的复杂度**，符合 D8 全面择优。

### ❓ E5 — 主密钥持久化方式

旧版只认两种：Windows `setx`、Linux `~/.bashrc`。

- (a) 照旧两种
- (b) Linux 侧扩展到 `~/.zshrc` / `~/.profile`（检测用户 shell），或写到 `~/.config` 下的独立文件并提示 source
- (c) 不再自动写 shell 配置，只打印密钥让用户自行保存

➡️ 推荐 **(b) 的保守版**：Linux 侧**优先写 `~/.bashrc`，若检测到用户 shell 是 zsh 则写 `~/.zshrc`**。理由：旧版往 `~/.bashrc` 追加是硬编码，用 zsh 的人会"生成成功但读不到"，这类静默失败最难查。(c) 对手动操作要求太高，不值得。

### ❓ E6 — `--gen-key` 的覆盖保护

旧版：已有密钥时警告 + 交互确认；`--disinteractive` 下**直接拒绝覆盖**（因为有旧密钥加密的凭据文件会永久打不开）。

➡️ 推荐**保留**。这条保护的分量很重（数据不可逆），值得原样搬。

### ❓ E7 — 凭据转换的行为细节

三处要你确认：
1. **"已是目标格式则跳过"** —— 保留？
2. **就地覆盖原文件** —— 保留？（不是另存新文件）
3. **只输出摘要不回显内容** —— 保留？

➡️ 推荐**全部保留**。1 与 2 是你既有的使用习惯（README 里写的就是"就地转换后的文件可复用"）；3 是安全考虑，不应后退。

### ❓ E8 — `--convert-password` 的路径解析顺序

旧版是"先按原样找，找不到再按 secret_dir 拼"——**与清单里凭据列的解析规则不同**（后者是 `resolve_secret_path` 的纯字符串梯子，不做"先找找看"）。

➡️ 推荐**保留现状**，但**在文档里明确写出两套规则并存**，避免后来人以为是漏改。若你觉得应当统一，这属于改变行为，需你裁定。
