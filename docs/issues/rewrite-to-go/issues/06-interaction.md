## 一、已查明的事实

### 1.1 两个交互原语的语义

**`prompt_text(prompt, validator, sensitive)`** —— 文本输入

- 循环直到通过：打印提示 → 读输入 → 交给 `validator` → 返回 `(值, 错误信息)`；错误信息非空则打印后**重试**
- `sensitive=True` 走 `getpass`，**不回显**
- `Ctrl+C` 或 `EOF`（管道/重定向结束）→ 打印"用户取消输入"，`exit(1)`

**`get_user_confirmation(prompt, yorn, disinteractive)`** —— 是/否确认

| 情形 | 行为 |
| --- | --- |
| 正常，`yorn=True` | 提示 `[Y/n]`，**直接回车 = y** |
| 正常，`yorn=False` | 提示 `[y/N]`，**直接回车 = n** |
| `disinteractive=True` | **不询问，直接返回 `yorn`**（即"自动确认"或"自动拒绝"） |
| `Ctrl+C` / `EOF` | 打印取消提示，`exit(1)` |

### 1.2 参数确认流程（`arguments_confirm`）

顺序固定为六步：

1. **上传并发建议**（仅上传模式）：按文件总大小给建议并发数 → 询问是否采用
2. `args.n == 0` → 置为**节点数**（即默认全并行）
3. 非交互模式 → 打印 `[非交互模式] 跳过执行参数确认环节，直接执行` 并**直接返回**
4. 打印横幅（`SSHFleet - 执行参数确认`，用 `╔═╗` 框线）+ 信息表格
5. 上传模式额外打印 `-u` 路径的**一层内容树**
6. 询问"是否执行上述参数？"（`yorn=True`）→ 答 n 则打印"操作已取消"并 `exit(1)`

**信息表格字段与顺序**：

| 顺序 | 字段 | 条件 |
| --- | --- | --- |
| 1 | 权限类型 | 恒有 |
| 2 | 执行模式 | 恒有（命令/脚本/上传/下载） |
| 3–4 | 执行命令 / 脚本路径 / 本地+远程路径 | 随模式 |
| 5 | CSV文件路径 | 恒有 |
| 6 | 节点数量 | 恒有 |
| 7 | 并发数值 | 恒有 |
| 8 | 连接超时 | 有 `-T` 时 |
| 9 | 执行超时 / 传输超时 | 有 `-t` 时（文案随模式） |
| 10 | 备注信息 | 有 `-r` 时 |

对齐方式：按 **`display_width`（全角按 2 列）**计算补偿空格。行格式为
`▶ <标签>-→   <值>`，标签亮青、值亮橙、`▶` 亮青。

### 1.3 上传并发建议的算法

| 文件总大小 | 建议并发数 | 是否询问 |
| --- | --- | --- |
| `< small_file` | `0`（不限制） | **不询问**（直接返回） |
| `> large_file` | `1`（串行） | 询问 |
| 中间 | `medium_concurrency` | 询问 |

- 大小计算：单文件取大小；目录递归累加，**跳过符号链接**
- 答 y → 把建议值写进 `args.n`；答 n → **保留原值继续执行，不退出**

## 二、问题

### ❓ I1 — `disinteractive` 下 `get_user_confirmation` 返回 `yorn` 的语义

这是旧实现里最容易读错的一处：`--disinteractive` 在 README 里描述为"跳过所有确认/询问直接执行"，但代码里 `disinteractive=True` 是**返回 `yorn` 参数的值**，而不是恒返回 `True`。

实际影响面：

| 调用点 | `yorn` | 非交互下结果 |
| --- | --- | --- |
| 参数确认"是否执行？" | `True` | 自动通过 ✅ 符合预期 |
| 危险检测确认 | `True` | 自动通过 ✅ 符合预期 |
| "是否应用于后续空字段节点？" | `True` | 自动通过 —— 但**这条实际到不了**：非交互模式下不会有交互输入（`prompt_text` 会先 EOF 退出） |

➡️ 推荐 **(a)**：新实现改为**显式**表达——`disinteractive` 时直接返回"确认"（不再借用 `yorn` 的值），并把那处到不了的调用点在代码里注明"非交互下不可达"。
理由：`return yorn` 这个写法让"跳过确认"和"自动拒绝"共用一个参数，读代码的人得回溯每个调用点的 `yorn` 值才能判断行为——属于可以消掉的认知成本。

### ❓ I2 — 参数确认的**字段与顺序**是否照旧

➡️ 推荐**照旧**。这是你每次执行前扫一眼的那张表，字段增减都会改变你的核对习惯。

### ❓ I3 — 参数确认的**视觉呈现**（框线、`▶`、配色、`-→`）

这是"表现形式"而非"行为"（D20 中归为可自由实现的一类）。

- (a) 用 `lipgloss` 做出等价观感（同一套信息，配色与边框可更规整）
- (b) 逐字符照旧
- (c) 从简（纯文本对齐，不上色）

➡️ 推荐 **(a)**。理由：`lipgloss` 本来就要引（D17），边框与对齐交给它比手工拼字符串可靠；信息内容与顺序不变，你的核对习惯不受影响。

### ❓ I4 — 上传并发建议是否保留

➡️ 推荐**保留**。它是"按文件大小自动限流"的入口，去掉后大文件上传会重新面临"全并发打满"的问题。

### ❓ I5 — 非交互模式下的提示语

旧版在非交互模式下会打印一行 `[非交互模式] 跳过执行参数确认环节，直接执行`。

➡️ 推荐**保留**。批量脚本跑的时候，日志里能看出"为什么没让我确认"很重要。

### ❓ I6 — 取消的退出码

用户答 n 取消参数确认 → `exit(1)`；`Ctrl+C` → `exit(1)`。

➡️ 推荐**保留 `exit(1)`**。虽然语义上"用户主动取消"不是错误，但改成 `0` 会让调用方无法区分"取消"与"正常完成"——反而更糟。

### ❓ I7 — 上传内容树只展一层

旧版 `_show_upload_content` 只列 `-u` 目录的**直接子项**，不递归。

➡️ 推荐**保留一层**。它的作用是"让你确认选对了目录"，不是浏览整个树；递归会把确认界面撑爆。

### ❓ I8 — `prompt_text` 的重试与取消

旧版：校验失败**无限重试**；`Ctrl+C`/EOF 直接 `exit(1)`。

➡️ 推荐**保留**。无限重试配合明确错误信息是交互输入的合理形态（用户随时可 Ctrl+C 退出）。
