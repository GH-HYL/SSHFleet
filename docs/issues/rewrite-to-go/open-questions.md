## 当前前沿：待回复项（2026-09-11 记录，2026-09-14 部分裁定）

用户外出期间按「先记录、先实施」处理：以下各项均已按**暂定实现**落地，回来裁定后如需改动再调整。

### Q4（Q3 遗留下半）：密钥节点要不要套用配置默认密码？

- 旧代码档位顺序：清单密码列 > **配置默认密码** > 密钥认证（有私钥则空）> 记忆 > 交互
  —— 即节点有私钥、清单密码列空时，只要 `account.password` 配了值，仍会套用默认密码；且默认密码文件损坏会直接退出，哪怕该密码对密钥登录无用。
- 关联事实（用户问「私钥无口令时带着密码连接会怎样」）：旧 Go 引擎 `BuildAuthMethods` 是**密钥优先、密码 fallback**；密钥认证成功则密码根本不会被发送。只有当密钥被拒绝时才回退尝试密码——此时多余的默认密码可能触发失败次数累计/锁定与日志噪音，也会掩盖「密钥失效」这个事实。
- **暂定实现**：密钥认证优先（有私钥 → 密码置空），配置默认密码只给「清单密码列空、又无私钥」的节点兜底。

### Q5（2026-09-14 已裁定）：全部取消写死默认值 ✅

- 用户裁定：**全都不写死**——超时值（10/60/300）、开关（true）、`password_security`（2）的默认值全部取消，改为「所有字段必填 + 配置预检查（缺字段 / 取值合规）」；`execution.mode` 的默认值只来自配置文件。
- 已落地：`config.validate` 覆盖全部字段必填 + port/mode/超时/阈值取值校验；已落 spec **D43**。

### Q6（2026-09-14 已裁定：保持现状）✅

- 用户裁定：**顺序无关，保持现状**——工具是一次性执行的串行逻辑，「哪里有问题就退出」，配置文件缺失与互斥错误谁先报都不影响结果。
