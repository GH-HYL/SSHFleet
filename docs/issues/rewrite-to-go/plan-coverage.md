# SSHFleet 全 Go 重写 · 规划覆盖面

Status: needs-info

> 本文件定义**规划要覆盖哪些面**，以及每一期怎么按面推进。
> 目的：防止"拆东补西"——盯着一段旧代码改得挺好，回头发现另一个面上有个老行为没接住。

---

## 一、为什么要有这份文件

重构最容易出的问题不是写不出来，是**漏面**。旧代码两年攒下来的行为分布在四个维度上（配置、清单、凭据、规则、输出、边界），任何一处只靠记忆去覆盖，都会漏。

所以：**每个里程碑动工前，先对着这份名单过一遍本期的面**，把要回答的问题列出来，再动工。不跳步、不凭印象。

## 四、每期动工的规程

1. **先过面**：把本期应覆盖的面逐条列出，写成**问题清单**（此时不碰代码）。
2. **以旧代码为事实来源**：每个问题都去旧实现里找答案，不凭印象、不凭这份文件里的摘要（D20）。
3. **三问**：① 能不能优化 → ② 优化后是否**保持原功能** → ③ 保持不了、或确有更优方案 → **ask 用户裁定**。
4. **结论三种归宿**：

   | 结论性质 | 归到哪 |
   | --- | --- |
   | 定下的决策 | `spec.md` 的决策表 |
   | 难回退 + 不看背景会疑惑 + 真有权衡 | 新写一条 ADR（`docs/adr/`） |
   | 术语 | `CONTEXT.md` 词表 |

5. **不确定就挂待定**：写进 `spec.md` 的「待定」段，不靠猜往下推。
