## 六、发现

### 【硬伤】1 条

#### H1 `parse` 用裸字面量取分类名，绕开了唯一常量；改名后改密会静默起不来

- **位置**：`modules/SSHFleet2_Go/internal/parse/tables.go:59`（同一行两处）；源头是 `internal/message/category.go:14-18`。
- **证据**：
  ```bash
  grep -rn '"密码过期"' modules/SSHFleet2_Go --include='*.go' | grep -v _test | grep -v guard/testdata
  # message/category.go:18  const CategoryPasswdExpired = "密码过期"
  # parse/tables.go:59      ... keywordsOf(cats, "密码过期")) == 0 && ... keywordsOf(exitCats, "密码过期")) == 0 {
  # → 常量 1 处、裸字面量 1 行 2 处
  ```
- **事实**：`message/category.go:14-18` 的注释是「代填拿它的关键词当中止词、改密拿它当入场信号——两处都从这里取，改名只改这一处」，`execute` 那两处确实用了常量（`run_answer.go:111`、`run_passwd.go:289`）；只有 `parse/tables.go:59` 手写。**这不是文案重复，是判据键重复**——`parse` 拿这个串去判据表里找分类，找不到就当场判「起不来」。
- **没有兜底**：`internal/parse` 的测试里没有一条钉住这个分类名（`grep '密码过期' internal/parse/*_test.go` 只命中两处帮助文案），所以改名不会红，只会静默变行为。
- **后果（可推演，未跑）**：判据文件里把这一类改名后，`message.CategoryPasswdExpired` 改了、配置文件改了，`parse` 仍找旧名 → `keywordsOf` 返回空 → 改密模式**启动即报「改密缺少入场信号」**（`tables.go:60-64` 那条 `cannotStart`），而不是「照新名跑」。
- **伤哪一条**：**腐蚀架构**（ADR-0032 第四条的「唯一改字处」在这条路上被绕开；绕法只有一行，正是三核心第一条说的「省事那条路」）。
- **分母**：分类名常量共 3 个（`CategoryPasswdExpired`／`CategoryUnknown`／`exitCodeCategoryPrefix`），逐个查引用：另两个没有裸字面量（`grep '"原因未知"'` 只命中 `message/category.go:21` 定义处，`"执行失败(退出码"` 只有定义那一处）。**3 个常量、1 个被绕开、2 处裸用。**

### 【判断题】7 条

#### J1 `identityLabel` 同名同逻辑两份，屏与日志各算一次「实际身份」

- **位置**：`message/confirm.go:136-142` 与 `execute/log_session.go:118-127`。
- **证据**：两份函数体逐字相同（`if run.Sudo && !run.NoShell { return "root" }` / `return "登录用户"`）。
- **代价**：身份判据改一处漏一处，确认屏与执行期日志会各说各的——而这两处正是给人核对「到底以谁的身份跑」的地方。
- **说明**：轴 05 已在 execute 侧记过这一处（包内形态）；本轴补的是「`message` 里还有一份相同的」，属跨包重复。
- **伤哪一条**：**只是架构取舍**（可以争论：屏与日志的字本来就分住两包）。

#### J2 凭据失败的「一句话」有两套词表，同一事实可能出两句不同的话

- **位置**：`message/passwd.go:69-77`（按 `code` 字符串，6 档）与 `parse/nodes.go:222-233`（按 `error`，3 档＋default）。
- **证据**：`"path_missing"` → 长句；`os.ErrNotExist` → 同一句长句。但 `message` 有 `"empty"`／`"empty_decoded"`／`"not_ciphertext"` 三档，`parse` 只有 `ErrKeyMissing`／`ErrBadCipher` 合成一档、其余一律 `"无法读取"`。
- **代价**：同一份凭据文件出问题，走「启动段解析」与走「报告站翻码」两条路，屏幕上的原因可能不同——`parse` 那侧会把「空文件」也说成「无法读取」。
- **伤哪一条**：**只是架构取舍**（两边词表本来不同源；但这是「同一个事实两个产出地」的典型，改口径要两边都改）。

#### J3 「请检查文件是否存在、当前用户有没有读权限」4 处 2 包

- **位置**：`message/answer.go:18`；`parse/material.go:38`、`parse/material.go:87`、`parse/nodelist.go:80`。
- **代价**：这是 `Problem` 第三段（提示）的固定句，四处各写一份；改口吻漏一处，同一个工具会对「读不到 `-a` 文件」与「读不到 `-f` 文件」说两种话。
- **伤哪一条**：**只是架构取舍**（`parse` 那三处是 `message.Problem(...)` 的实参，不是自成一句）。

#### J4 解释器名单两份（15 项）

- **位置**：`parse/downlink.go:228-244`（带 `-c/-e/-r` 与 shell 家族）与 `message/modename.go:131-134`（只列名字，顺序即显示顺序）。
- **证据**：两处都 15 项、集合相同；保证不漂的只有一条测试（`parse` 侧「按集合比对」）。加一个解释器要改两处，漏一处测试会红——至少不是静默的。
- **伤哪一条**：**只是架构取舍**（属性归解析、显示归 message 是 ADR-0013 的分法；重复的是名字列）。

#### J5 解释器归一的两份实现

- **位置**：`parse/downlink.go:281-293` `interpreterBaseName`（`path.Base` ＋ `TrimRight("0123456789.")`）与 `message/confirm.go:144-159` `isBashInterpreter`（`LastIndexAny("/\\")` ＋ 同样的 `TrimRight`）。
- **证据**：两处实现细节已经不同（一个用 `path.Base`、一个用两步切片；对 Windows 反斜杠的处理也不同），注释只说「同源」。
- **代价**：`/bin/bash`、`bash5` 这类写法在两侧的判定可能分叉，表现是「确认屏多／少一行解释器」。
- **伤哪一条**：**只是架构取舍**（显示门槛那点逻辑小到不值得跨包依赖；但要接受两份实现会各自演化）。

#### J6 选项名有两份名单，且注释说只有一份

- **位置**：`parse/options.go:20-41`（20 条正表，带 `takesValue`）与 `parse/argv.go:514` `flagParamLongs`（4 个开关手抄）＋ `argv.go:508-511` `batchParamLongs`（11 个带值项手抄）。
- **证据**：`argv.go:507` 的注释写「名字不另抄一串，按长名回选项表查（新增一个选项只改选项表那一处）」，紧接着的第 514 行就是手抄的一串。
- **代价**：加一个「只看给没给」的开关，只改选项表不够——`flagParamLongs` 不改，它就不会被「不能和密钥命令一起给」那条检查认出来。
- **注**：`options` 里已有 `takesValue` 一列，名单可从表里派生；但 `--yes` 是**有意**不在 `flagParamLongs` 里的（`argv.go:504` 说明），所以派生不是纯 `!takesValue`。
- **伤哪一条**：**只是架构取舍**（名单确实要按语义挑，不是全等表）。

#### J7 `contract/plan.go` 里两句相反的注释，指着下发行该在哪拼

- **位置**：`internal/contract/plan.go:72-75`（「拼法全在执行站一处（ADR-0015）」）与同文件 `plan.go:97-101`（「Downlink 是成品……拼装只此一处……都在解析站成形」）。
- **证据**：代码是后者（`parse/downlink.go` 唯一一处 `sh -c` 拼装，`grep '"sh -c'` 3 个返回点全在该文件）；前一句是 `b8c831d` 时期的原文，`3c19274` 搬家时没改。

- **伤哪一条**：**腐蚀架构**（不是文档对账：这条注释就贴在字段上，是下一个改这里的人第一眼看到的东西；按它做就是重演一次层漏）。归判断题是因为眼下代码是对的。
