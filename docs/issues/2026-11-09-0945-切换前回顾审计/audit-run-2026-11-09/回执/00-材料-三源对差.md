## 二、逐处展开（只写差异落点）

**01 轴数。** A 说「轴按代码结构定，但这一次的结构从上往下就这四个问题」——这句是**在用四问替代轴切法**，执行者读到的动作是「切四份」。C 说「照说明第一节，不改」，却又给出十轴，并明说站内三站并入第三问。两者审的是同一批东西，但**派发份数不同**，文件域白名单、账号分配、回执份数全部跟着变。这不是措辞差。

**02 六类/七类。** 见第五节第 1 条：这不是笔误级差异，六与七差的正是 `check_mask`——本轮为「遮只能从一处出」新加的检查面。照 A 会把本轮最新加的那一类整个漏掉，而它恰好最可能是「为了过关改了检查面」的现场。

**03 基准方向。** B 的整条锚链是「ADR 是唯一基准，规格不可信」；A/C 把母规格 Destination 抬到第 1 层、把施工 ADR 压到第 3 层。这不是层级多寡，是**同一个冲突两种判法**。A 自己也承认是在改技能默认口径（说明:3、5），而 C 的「底本」一栏直接引 A——即 C 认为 B 的默认口径已被覆盖。三方没有一处写明「B 的默认口径在这一议题失效」，B 的措辞仍是绝对的「唯一基准」。

**04 施工 ADR 的身份。** 三方各一种：B = 基准；A = 第 3 层锚（但开篇说在被审范围，**A 自身就不一致**）；C = 被审对象。后果具体到一句回执：某轴发现 `ADR-0035` 与代码不符，照 B 报「实现跑偏」，照 C 报「决策本身要重议」，两条会落到报告的不同段（第二段 vs 第三段），处置方式也不同。

**05 抄锚范围。** A 的 43 篇与 C 的 12 篇差三倍工作量，且改变锚的性质：把 `0013`–`0031` 抄成锚，等于把「老版本来怎么跑」固化成正解，A1「老版行为等价」的参照面就没了——C 已把这句写进「审歪的样子」之外，并留了「待开发者点头」。但 C 末尾又写「没点头之前，锚质疑按说明原口径报」——**同一份文件里两种口径并存**，执行者轮一抄锚时仍要自己选一次。

**06 `/code-review`。** B 是硬要求（「规范轴直接派」，且给了改写它基准的固定句）；C 的十轴里 02 只审 `guard` 本体、04–09 只审腐蚀与站内，**通用规范面（命名、错误处理、重复代码的常规 smell）无人承接**。照 C 跑，B 那条「不重复 `/code-review`、只补它覆盖不到的部分」的分工前提就不成立了。

**07 再问一次。** B 的问不是可选项，是段二出场清单里的一条（SKILL:44），漏了「环境靠猜」。C 把三样答案写死在 spec:95。C 的做法在事实上更省，但**没有一处写「B 2.4 本轮免行」**，只在 C 里说「不要再问」。照 B 严格执行的人会再问一遍。

**08 派发节奏。** 差别不在四段/四轮的名字，在闸门内容：B 段三的进门判据是「各轴与复核员**都已派出**」，这是全量一次派发的模型；C 是「机械批先跑、人读批后派、边收边派」。照 B 的门，轮二的收账动作在门内做不了；照 C 的门，B 的段三/段四边界消失。

**09 目录与只读。** 这是最容易撞车的一处：B 的落档铁律说 `分发缺口.md` 写完即只读、错了另开 `audit-run-<新日期>/`；C 说同一目录里「每轮一版」「每轮改一次」。两者对**同一个文件能不能第二次写**给出相反答案。若照 C 就地改，违反 B 的只读铁律；若照 B 另开目录，C 的「轮一～轮四」就散在四个目录里，交接清单的「现在到哪」没有单一载体。

**10 报告。** B 的第二段是「已定缺陷」，A/C 的第二段是「架构与腐蚀的账（四问各一节 + 数字）」。这不是排版差异：照 B 写，报告主体是缺陷条目，四问的答案只能塞进第一段的「归拢」里；照 A/C 写，缺陷条目反而要另找位置（A 只说「顺带」一节）。另外 B 明写「不是决策」，A/C 第一段要求一句「能不能切」——**是否给结论直接相反**。

**11 阶段 03。** A 的清单是 04、07、09（09 作 A/B 证据），C 加了 03。`docs/issues/2026-11-01-2244-建站03-起不来与拒绝/issues/16-audit-mustfix.md` 实际存在（见第五节第 3 条），说明 C 有据、A 是漏列。照 A 会重审 03；照 C 则 03 的 mustfix 结论不会作为既有结论传下去，轴可能重新发现同一批问题。

## 四、A（底本）自身的两处不一致

这两处不是三方之差，是 A 自己前后打架；照 A 单独执行的人一定撞上：

1. **施工 ADR 的地位**：开篇「它们本身就在被审范围里」（说明:5）↔ 第二节「第 3 层：各阶段 ADR 的决定」（说明:22）。
2. **ADR 篇数**：开篇「四十三篇 ADR 是重构自己产出的」（说明:5）↔ 实际只有 `0032`–`0043` 十二篇（见第五节第 2 条）；C 已把这处标为「要开发者点头」（spec:37、180），A 未标。

## 五、我另行核过的事实（供判定用，非代码审计）

1. **`guard` 类数**：`modules/SSHFleet2_Go/internal/guard/` 下现成 **8 个** `Check*(m *Module)` 入口——`CheckContract`、`CheckDeps`、`CheckExit`、`CheckFailure`、`CheckHandoff`、`CheckMask`、`CheckTerminal`、`CheckTestSite`（各 `check_*.go`），另有 `CheckRedline`（`redline.go:108`）。`docs/adr/0032-按五站分层重构工程结构.md:192` 的 2026-11-06 更新记录写明「结构检查加**第七类**「遮的构造点」……上文第四条那五类（后经 ADR-0037 与建站 06 增为六类）不改，类七是新加的一条」。→ A 的「六类」落在加类之前；C 的「七类」与 ADR 一致。至于代码里为何有 8 个 `Check` 入口、「类」的边界算到哪，文件本身没写死，**这一句要开发者定死**，否则照七类核也未必对齐。
2. **ADR 篇数与分段**：`docs/adr/` 共 43 篇；`0032`–`0043` 恰 12 篇，`0013`–`0031` 恰 19 篇（= C 说的参照物），其余 12 篇为 `0001`–`0012`。C 的「十二篇 / 十九篇」在文件数上成立。
3. **阶段 03 的审计确实存在**：`docs/issues/2026-11-01-2244-建站03-起不来与拒绝/issues/16-audit-mustfix.md`。→ C 第 11 项有据，A 漏列。

## 六、要开发者一句话定死的三处（其余可由主 agent 按 C 执行）

1. **基准口径**：本议题是否整体覆盖 B 的「ADR 唯一基准」？若不是，A/C 的三层优先级与 B 的默认口径在报告的**第二段/第三段归属**上会直接对撞（03、04）。
2. **`guard` 到底几类**（六/七/八），以及是否把 `check_mask` 算进「遵从度」的必核面（02）。
3. **`audit-run-<日期>/` 的单位是一轮还是四轮**——即 B 的「多轮各自独立成目录 + 写完即只读」是否被 C 的单目录四轮覆盖（09）。
