# 01: --sudo 上传直接写最终路径

**要做的**：`--sudo` 上传时，`sftp` 会话以 root 跑，文件直接写到最终路径——目标机上不再出现 `/tmp/.SSHFleet_tmp/` 下的暂存目录，也不再走 `sudo mv`。做完之后，往一个 700、属主 root 的目录上传能成，失败时不再有 `tmp_failed`／`sudo_failed` 这两种环节名。

**Blocked by:** 无，可立即开工。

**Status:** done

- [ ] `--sudo` 上传到 700、属主 root 的目录成功，落位文件属主是 root
- [ ] 上传结束后目标机上不存在 `/tmp/.SSHFleet_tmp/`，过程中也不出现
- [ ] 探不到 `sftp-server` 时，该台失败，报错原文含 `sshfleet.transfer.client_failed` 与 `sftp-server not found under sudo`
- [ ] sudo 拒绝提权时，该台失败，报错原文含 `sshfleet.transfer.client_failed` 与 `sudo refused to run sftp-server`，并带 sudo 原话
- [ ] 非 `--sudo` 上传行为不变：既有上传用例全绿

## Comments

- 2026-11-20：两项失败验收没有自动化用例——假目标机没有 sshd、没有 sudo，造不出这两种环境。按 `docs/agents/按需-测试环境.md` 的 WSL 目标机手工验过，报错原文如下（两条都归「目标机不支持 SFTP」）：
  - 不在 sudoers 的账号：`sshfleet.transfer.client_failed: sudo refused to run sftp-server: sudo: I'm sorry nosudoer. I'm afraid I can't do that`
  - 把 `/usr/lib/openssh/sftp-server` 临时挪走：`sshfleet.transfer.client_failed: sftp-server not found under sudo`
- 2026-11-20：已知的一处归类边界——sudo 的原话里若含 `Permission denied`，判定会先命中「权限不足」那一类（它排在「目标机不支持 SFTP」之前），分类名与报文说的不是一件事。实际见到的三种拒绝语都不含这句，暂不调判据表顺序。
