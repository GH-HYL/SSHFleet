# 失败分类统计的同分次序偶发错乱 · 规格

Status: done（2026-10-19 定为首现序并修复统计与报告两处）

> **来历**：2026-10-19 收尾内联清单议题（`docs/issues/inline-list-backslash-newline/`）时全量跑测试撞见，与本议题范围外，开发者定单独立项、后面自己分析。

## 问题陈述

统计块的「失败分类统计」承诺**数量相同时按首次出现的先后排序**（测试注释原话：`与「原因未知」同为 2，先出现者在前`，期望 `拒绝网络连接` 排在 `原因未知` 前面），但实现没兑现这个承诺：**同分的两个分类谁在前是随机的**。使用者大多数时候看到碰巧对的顺序，偶尔看到错的——同一批节点跑两次，统计块的分类次序可能不一样。

同一批分类的第二处出口——归档报告 `report.txt` 的「节点清单统计」段——有同样的问题（2026-10-19 核出，见「影响」）。

## 现象

```text
--- FAIL: TestStatisticsFailCategoriesSortedByCountDesc (0.00s)
    statistics_test.go:156: SortedFailCategories = [{连接超时 3} {原因未知 2} {拒绝网络连接 2}],
        期望 [{连接超时 3} {拒绝网络连接 2} {原因未知 2}]
```

**复现（统计侧）**（偶发，约 10 次撞 1 次；复现的是「map 遍历顺序随机」这件事本身，不是确定性输入）：

```bash
cd modules/SSHFleet_Go
mkdir -p ../../build/gotmp-1019
export GOTMPDIR=$PWD/../../build/gotmp-1019 TMP=$GOTMPDIR   # 临时目录必须留在工作区内，见 docs/个人开发规范.md「三、结构·1」
for i in 1 2 3 4 5 6; do go test -count=1 -run TestStatisticsFailCategoriesSortedByCountDesc ./internal/result/ 2>&1 | tail -1; done
```

2026-10-19 实跑：三批合起来 **43 跑 6 红**（约 14%，1/7 量级）——第一批 12 跑 2 红（第 7、第 12 次）；第二批为抓断言输出、首跑即红即停（1 跑 1 红）；第三批 30 跑 3 红。

**复现（报告侧）**：改前 `report.txt` 的「节点清单统计」段没有现成测试接缝，当轮在沙盒 `build/atest-9/` 里搭了桩——构造三个各 2 台的失败分类，调 `WriteReport` 写 40 次，回读分类次序：

> 桩与它的输出是**一次性**的，未留档（`build/` 按天清理，留档也留不住）。下面的计数是当轮实测值，事后无法重算。

```text
   6 次  原因未知 > 连接超时 > 拒绝网络连接
  27 次  连接超时 > 拒绝网络连接 > 原因未知
   7 次  拒绝网络连接 > 原因未知 > 连接超时
```

同一份输入出现 3 种排列。修好后接缝落进 `internal/output` 的正式测试，桩不再需要。

## 根因

两处的根因同源：**map 遍历序顶替了首现序**。

`internal/result/statistics.go` 的统计构造分两步：

1. `for category, count := range counts { ...append... }` —— `counts` 是 **map**，遍历顺序在 Go 里刻意随机化；
2. `sort.SliceStable(...)` —— 稳定排序保的是「同分保持**进入切片时**的顺序」。

两步合起来：稳定排序想保的「先出现者在前」，保的是 **map 随机给出的顺序**，不是节点结果里分类**首次出现**的顺序。测试期望的判据（首次出现序）与实现给的判据（map 随机序）不同源，于是偶发失败。

`internal/output/report.go` 的「节点清单统计」段同理：分类键取自 `for k := range stats.CategoryIPMap`（同样是 map），随后那层手写插入排序只比 `len(ips)`、相等不交换（稳定），于是它保住的也只是 map 随机序。

**这不是测试写错**：测试钉住的是注释里承诺的行为，是实现在撒谎。

**判据不用另选——旧实现本来就给首现序。** 旧 Python 版（`modules/SSHFleet_py/src/output/statistics.py`，`d952f5b` 之前）：

```python
category_counts = Counter(d.get("result_category") for d in results)
sorted_fail_categories = sorted(category_counts.items(), key=lambda x: x[1], reverse=True)
```

`Counter` 是 dict 子类，Python 3.7+ 保插入序 → 键序即分类**首次出现**序；`sorted`（含 `reverse=True`）稳定 → 同数量保持首现序。旧 `report.py` 的节点清单统计同理（`category_ip_map` 按 results 顺序首次出现插入，`sorted(..., key=lambda x: len(x[1]))` 稳定）。**是 Go 版改用 map 时把插入序丢了**，首现序不是新引入的口径，是原样兑现。

## 影响

- 使用者可见：
  - 终端统计块的失败分类次序不稳定（分类统计行、其下的「提示：」逐行说明都跟着抖），同分时两次运行可能一先一后；数量不同时排序不受影响，降序那层是对的
  - 归档报告 `report.txt` 的「节点清单统计」段分类次序同样不稳定
- 开发者可见：`TestStatisticsFailCategoriesSortedByCountDesc` 偶发红（实测 43 跑 6 红，约 14%），容易误判成自己的改动弄坏了它

## 方案

**按首次出现序**（2026-10-19 定）。扫描 items 时记下每个分类**首次出现的先后**，让分类按这个次序进入切片，后面那句 `sort.SliceStable` 保的就成了首现序。报告侧改为复用统计给出的分类次序，不再自己去 map 取键。

原列的三条待选与弃用理由：

| 待选 | 处置 |
| --- | --- |
| 按首次出现序 | **选定**——与旧版行为一致（见「根因」末段），且与测试注释对得上 |
| 按分类名序 | 弃——判据换了一个，使用者看到的历史次序会变；且与旧版不一致，那不是修复而是改行为 |
| 放弃承诺（改测试注释） | 弃——只解决「测试偶发红」，使用者可见的次序照样抖，与使用者故事 1 相抵 |

## 使用者故事

1. 作为看统计块的运维人员，我想同分的分类按一个**说得出理由**的固定次序排列，而不是每次跑都不一样。
2. 作为改代码的人，我不想跑全量测试时被一条**与本轮改动无关**的偶发红测试干扰判断。
3. 作为翻归档报告的人，我想同一份 `report.txt` 里分类的先后与终端统计块一致，两次跑同一批机器拿到的报告可以逐行比对。

## 实现决策

- 判据统一为**首次出现序**：次序取「分类在结果切片里第一次出现的先后」；结果切片本身由 `internal/batch` 的 `sortBySeq` 按清单序保序，故首现序 = 清单里该分类第一次出现的位置。
- **统计侧**（`internal/result`）：`Statistics` 扫描 items 时按首现序记下分类名，汇集阶段按这个序列进入 `SortedFailCategories`（成功分类就地跳过），`sort.SliceStable` 与其后逻辑不动。
- **报告侧**（`internal/output/report.go`）：不再遍历 `CategoryIPMap` 取键。`Stats` **不新增导出字段**——`SortedFailCategories` 与 `CategoryIPMap` 的键集在 `Statistics` 内部同源（同一批分类、同样剔除成功分类），报告侧复用它已排好的次序即可；这层「键集相同」的不变量由一条测试钉住。报告要求的是按 IP 数量**升序**（对位旧报告），故对这批键做一次稳定的升序重排——稳定排序接住上游那层首现序，两者不冲突。
- 不动 `SortIPs`、不动 `CategoryIPMap` 的值序、不动 xlsx 侧。

## 测试决策

- **统计侧**：现有 `TestStatisticsFailCategoriesSortedByCountDesc` 就是验收工具，期望值不改。修好后**连跑 20 次全绿**才算修好，单次绿不算——偶发缺陷的验收标准是概率而非单次（改前实测失败率约 14%，20 次全绿的误判概率约 (1−0.14)²⁰ ≈ 5%，判据有区分力）。
- **报告侧**：接缝定在导出函数 `WriteReport`（断言的是输出文件内容，不碰内部实现），归档目录用 `t.TempDir()`。断言写确定的字面量次序，**不用「跑 N 次看随机性」**——修好后判据是确定性的，N 次既慢又可能漏判；确认无偶发靠 `-count=20` 连跑。
- 两处测试都只测外部行为：断言的是「同数量分类的先后」与「报告里分类段落的先后」，不读私有字段、不数内部调用。
- 报告侧补一条**键集一致**的断言（哪些分类出现在报告里），钉住「报告侧复用 `SortedFailCategories` 次序」所依赖的那层不变量。

## 不在本次范围

- 成功分类、IP 排序等其他统计项（已扫过全部产出次序点的代码，未发现同类问题）
- xlsx 两份产物内的次序（按结果切片，已保序）
- 报错文案「多条同时非法时报哪一条」的次序（`config.go` 的 `[env]` 校验、超时校验等遍历 map，多条同时出错时先报哪条不定）——不是排序问题，未观察到影响，按红线 4 只报告不动
- 测试稳定性改造的全局方案（若以后再撞见别的偶发测试，另行考虑）
- **失败节点分类名与成功分类名撞名**（2026-10-19 审计发现，改前既有、非本次引入）：分类名来自用户可编辑的 `keywords_error.conf`，用户可自造出「执行成功」这类名字；此时该台失败机会被并进成功段（实测 `SuccessCounts=1 FailCounts=1 SuccessIPsCount=2 SortedSuccessIPs=[10.0.0.1 10.0.0.2] SortedFailCategories=[]`，报告里显示在「执行成功（2）」下）。触发前提是用户自造同名分类，概率低；先记档，不在本次改
