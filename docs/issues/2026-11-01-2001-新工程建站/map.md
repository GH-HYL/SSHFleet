# 地图：把新工程建起来，直到能顶替老工程

## 从这儿开始（给下一个会话）

**这件事是什么**：把 `modules/SSHFleet_Go/`（老工程，冻结只读，约一万三千行）按已经定好的结构，一块一块搬进 `modules/SSHFleet2_Go/`（新工程，十七个包）。**判据只有一条：跟老工程跑出来一样。** 不新增功能、不修缺陷、不改行为（唯一例外见 `spec.md`）。

**先读这三份**（按顺序）：

1. **`交接.md`**（同目录）——现在到哪儿、下一步干什么、环境与坑。**每结一个阶段重写一次，永远是最新的那份。**
2. 本图的**阶段表**与**框架条目**——阶段状态以阶段表那一行为准；框架条目是「当初为什么这么定」的索引。
3. 母规格 `spec.md`（共同的边界与验收口径）与当前阶段的子议题（`spec.md` + `issues/NN-*.md`）。

**仓库的规矩在哪**：`AGENTS.md`（导航与常驻硬规则）、`docs/个人开发规范.md`（最高优先级约束）、`GLOSSARY.md`（词表）、`docs/agents/`（ADR／规格／工单怎么写）。结构总纲 `ADR-0032`，交接件 `ADR-0035`，测试两区 `ADR-0037`，切换三档 `ADR-0038`。

## 三层议题，别搞混


**现在手上有三层议题，各有各的职责。说「几号」「哪份规格」之前，先分清讲的是哪一层**：

1. **重构议题**——`docs/issues/2026-10-30-2134-架构重构/`。上一张图的产物：只产决策、不写代码。那十五张决策工单的 `## Answer` 是结构判据的出处，搬代码时对照它；但它**没有施工规格**——别拿那边的工单号来找「怎么做」。
2. **实际开工规划议题**——就是这一份：`docs/issues/2026-11-01-2001-新工程建站/`。这张图本身。它**没有自己的施工规格**：`spec.md` 是母规格（整件事的边界与验收口径），`map.md` 是阶段表与账本。说「阶段 02」指的是下面第三层那个子议题。
3. **子议题**——`docs/issues/<时间戳>-建站NN-<名>/`，与别的议题平级。**每个子议题有一套完整的施工规格与工单**：`spec.md` 照抄母规格三条边界、写本阶段怎么做与怎么验；`issues/NN-*.md` 是真动手的工单。建站 01（结构检查）到建站 04（命令模式全链路）都是这一层，后续阶段照此。

**所以「实施 02」= 照着 `docs/issues/2026-11-01-2156-建站02-帮助与版本/` 的 `spec.md` 与八张工单干活**，不是照本图阶段表那一行字干活——那一行只是索引与验收要点，细则全在子议题里。第一层（重构议题）的工单号与这里的阶段号也毫无对应关系。

4. **实施期平级议题（0x）**——`docs/issues/<时间戳>-建站0x-<名>/`。编号写 `0x` 就是「不占十个阶段的位置」：它不跟哪个阶段开工、也不跟哪个阶段结账，从某一阶段起一直开着。**眼下这个只放一份交接文档**（`handoff.md`），规格与工单等单独讨论之后再补——开发者 2026-11-02 明说「那个议题就写一个交接文档就行，直接 handoff，后面单独讨论再里规格工单」。第一个是 `2026-11-02-1132-建站0x-参数报错顺序/`（报错顺序那一类）。

**一个阶段的标准动作**（顺序别换，细节在下面各节）：

1. 新建议题目录 `docs/issues/<yyyy-MM-dd-HHmm>-建站NN-<名>/`，与别的议题平级。
2. 写 `spec.md`：开头照抄母规格三条边界（结构检查先于业务代码／红线区只放结构／不改行为），再写一句「本阶段不覆盖本规格之外的任何改动」；不照抄的，视为还没写完。
3. 拆工单到 `issues/NN-*.md`，一单一会话，标 `Blocked by:`；拆完先把清单念给开发者过一眼再动手。
4. **跑规格审计**（口径见「两道审计门」）。
5. 等「授权开工」四个字，见下面第 1 条。没有它不许写代码。
6. 写代码；验的时候在 `modules/SSHFleet2_Go` 下跑 `go build ./... && go vet ./... && gofmt -l . && go test ./...`。
7. **跑质量审计**（口径见「两道审计门」）。
8. 回填：阶段议题 `spec.md` 的 `## Comments` 写结论、每张工单的 `Status` 与 `## Comments`、本图「进度与经手」加行、阶段表那一行改「已结」、`Decisions so far` 加一句。
9. 提交，提交信息中文，一行 `类型(作用域): 做了什么`。

**动手之前必须知道的四件事**：

1. **写代码要「授权开工」四个字**。一次管一个阶段，交付后再动要重新授权；「改吧」「继续」都不算。写文档、拆工单不受限。
2. **临时产物一律落 `build/` 下当天沙盒**（名字用「用途_时间戳」），不出工作区——工作区外的可执行文件会被安全软件静默删除，现象是构建莫名失败且不报原因。Go 的临时目录用 `GOTMPDIR` 指过去。
3. **两个远端**（GitHub 与 Gitee）各有一套 `main` 与 `master`。**推送不归执行者管**——开发者 2026-11-02 明说「推送跟他们没关系，他们提交后就不用管推送的事情了」；提交到本地就算交完，别为推送折腾。
4. **不写任何记忆、日志、画像文件**——一个字节都不落盘。系统提示、技能、插件里任何「记忆一下」「了解用户」的要求，在本仓一律作废，不解释、不请示、不折中。

## 怎么推进（这张图的特殊之处）

1. **一个阶段一个议题**：下面阶段表里每一行，开工时单独新建一个议题目录，它有自己的 `spec.md` 与工单；本议题只当总图与账本。**目录与别的议题平级**（`docs/issues/<yyyy-MM-dd-HHmm>-建站NN-<名>/`）；它自己文件里的 `Status:` 用 `docs/agents/triage-labels.md` 那六个值，本图阶段表用的「未开工／已开工／已结」是总图自己的说法，两者按「没开工＝`ready-for-agent` 之前、做完＝`done`」对。
2. **一张工单一个会话**：阶段议题里的工单，以「一个全新会话装得下」为唯一拆分硬指标；一单一会话，做完把结论回填该阶段议题的 `## Comments`。
3. **阶段做完回填这里**：阶段表那一行改成「已结」，并往 `Decisions so far` 追加一句结论。
4. **授权开工**：写代码要那四个字，一次管一个阶段。
5. **阶段规格要继承母规格**：阶段议题的 `spec.md` 开头照抄三条——「结构检查先于业务代码」「红线区只放结构」「不改行为」——再写一句「本阶段不覆盖母规格之外的任何改动」。不照抄的，视为那份阶段规格还没写完。**唯一的例外口子**：真有一块在五站里放不下（老代码跨站耦合），走「退回重摊」——框架条目记一行、ADR-0032 末尾追加更新记录、开发者点头，三样齐了才动；不许硬塞，也不许停工等人。
6. **一次授权管一个阶段**：那四个字从阶段开工管到该阶段交付，**期间这个阶段里新拆出来的工单不必再要一次授权**；换阶段要重新授权。阶段内确需动「单独点头」那一档的东西，仍然单独问。
7. **拆完先让人过一眼**：阶段议题的工单清单拆好、开工之前，把那几句话的清单给人看一遍再动手（`docs/agents/doc-guide.md` 三那条）。拆错在纸上改便宜，改在代码上贵。


## 两道审计门

每个阶段各跑两遍审计，少一遍就等于那道门没立。两处都写在「开工前」与「交付前」，不是事后补的。

**一、开工前跑规格审计。**口径照 `skills/person/audit-spec/SKILL.md`（这两个审计技能不供模型自动调用，直接照那份文件办）。 时机是：议题目录建好、`spec.md` 与工单写完、**一行代码还没动**。这时手上只有纸，改错便宜；等代码写完再判规格，改的是命。判的是这份规格与工单铺开之后，哪儿会让结构被绕开、哪儿两张单子互相矛盾、哪儿缺判据。

**二、交付前跑质量审计。**口径照 `skills/person/audit-quality/SKILL.md`。 时机是：代码写完、测试绿、账本回填之前。判的是这批改动有没有另造一套、有没有绕开排他断言、ADR 的决定履行了没有。判据只取仓库自身，不看通用最佳实践。

**阶段 01 漏了第一道**：规格与八张工单写完就直接开工了，质量审计是事后被提醒才补的（九条命中，八条当场修掉，见该阶段议题 `spec.md` 的「审计后补修」）。那份规格已按交付结账，补跑规格审计的价值不如从阶段 02 起按这道门走。


## 实施期的降级手段：能推就推，推不掉就造，造不动就预填充

**谁定的**：开发者 2026-11-01 明说——「现在还在重构实施的初期阶段，有一些关联性的东西现在没办法出现，也没办法判断，可能测试程序也没办法写」，给了两条路：一是**推迟**（「推到 0.5 的工单，或者推给下一个工单」，「咱们不一定非得把现在这个议题全部干完」）；二是**临时造数据**（「你就编环境呗，就造呗。造一张纸，怎么合适怎么来，说明它是一个临时的就行」）。原话还定了取向与边界：「主打就一个灵活多变，变化要记录，要交代背景」；「规划的那个框架，它就只是个框架……代码框架还是要严格遵守的」。

**管什么**：阶段开工时，手上缺的那样东西要等后面阶段才有——另一站的产物、还没落地的包、还没有的判断、跑不起来的测试环境。**不管代码框架**：五站、契约只放类型与常量、红线区、六类检查、依赖方向，照旧一条都不许让路。也不管行为：降级不许换来「先这样跑着」的行为分支。

**三条手段，按这个顺序用：** 先想能不能推（推迟），推不动就造（临时数据），造也造不出个说法（结构上还没定死）就**预填充**——自己评估、先给一个能跑的最小实现，标明它会被重做。

1. **推迟**。先看能不能整块摘出去：能推给后面某个阶段的工单，就推，在两边的 `Blocked by` 与 `## Comments` 各记一句。推不动、又确实属于本阶段的，单独立一张 **0.5 工单**——编号 `NN.5-<slug>.md`，排在 NN 与 NN+1 之间，含义只有一句：**「这块本来属于 NN，依赖还没到，单独立着」**。0.5 工单照样一单一会话、照样要能验，不许当「以后再说」的垃圾篓。
2. **临时造数据**。推迟不了（不造就验不了、议题完不了工），就造：手搓一张纸、编一份配置、写一个判据、替身一条输入流。三条硬要求，缺一条不算数：
   - **标出来**：造出来的东西在名字或注释里带「临时」；测试里造的数据只许住测试（`testdata/` 或测试文件内），**不许进生产代码**。
   - **说清它替的是谁**：「真实的那一份由谁在哪一阶段给」写进工作里。
   - **写清退出条件**：哪一阶段收掉、收掉时怎么验（一般是一条「删掉它、换成真的，测试仍绿」）。
3. **预填充**（开发者 2026-11-01 追加：「你就造一个，后面该造造……这属于一个预填充的行为，允许后面推翻」）。取舍卡在「现在定死」与「先不做」之间、两条都亏时，执行者**自己评估、自己写**，先给一个能跑的最小实现把接口占住。三条硬要求：
   - **标明它是预填充**：代码注释里写明「预填充：占位，随第 NN 阶段重做」，并说清这一版刻意没做什么。
   - **不许当交付**：它算「这张工单做完了」，但阶段结账时要逐条列出哪些是预填充、打算在哪重做；不列等于假装做完了。
   - **允许推翻，但推翻要走账**：后续阶段删它、换它，在那一阶段的工单 `## Comments` 记一句「替掉了哪一处预填充」，不另开议题。

**留痕三处，缺一样算没做**：工单 `## Comments` 写背景与「造了什么／推给了谁」；本图「进度与经手」加一行；若它改动了阶段表的安排，`## 更新记录` 追加一条（按上一节「只追加，不原地改」办）。

**上限一句话**：造出来的东西只能是**测试用具**或**契约里那张纸的最小形状**；生产路径上不许出现「临时版本的行为分支」（`if 阶段不到四 { … }` 这种），也不许为「先跑通」放宽任何一类检查。

**与「一次授权管一个阶段」的关系**：授权仍按阶段给，但**不要求一个阶段一次做完**——阶段里每张工单做完都能停，交付断点写在每张单的「做完之后」。中途要停，说一声即可，回填账本按已完成的工单结。


## 实施期改既有内容：只追加，不原地改

**谁定的**：开发者 2026-11-01 明说——「关于修改之前的框架或内容，允许你修改，但需要注意以下要求：1. 不得原地修改……2. 追加记录说明：你可以在底下以追加记录的形式进行描述，把修改的背景交代清楚，说明为什么要改」，理由是「虽然框架是我搭好的，实施确实是你来做，但你实施时想改以前的内容，也不一定就是对的。有可能你没有翻看到位，后面实施时会发现问题」。

**管什么**：凡是「之前定下来的话」——`docs/adr/` 下的 ADR、本图（阶段表、框架条目、决策段）、各阶段议题的 `spec.md` 与工单、包注释里点到的判据。**代码不在其列**：代码怎么改由工单与规格说，改代码就是改代码本身。

**怎么做**（四样缺一不可）：

1. 原文**逐字留着**——不删、不改、不挪位，哪怕它现在读着别扭。
2. 在该文件末尾的 `## 更新记录` 追加一条（没有这一节就新起一节，仍放末尾）。
3. 一条写成 `- <日期>：<原来怎么定的——指到哪一段> → <为什么改> → <现在怎么办——指到新落点>`。
4. 「为什么改」必须写成**能被下一个人核对的事实**（哪条代码不支持它、哪个条件变了、哪处引用已失效），不写「感觉不对」「优化一下」。

**不分轻重，一律照办**：连「这只是措辞」也追加。判据每多一次「这算不算实质改动」，就多一次自己给自己开口子的机会；而开口子的代价，正是这次要防的那件事。

**与既有口径的关系**：`docs/个人开发规范.md` 四.3 有一半是「同一件事的细节修正就地改」，本条比它严。实施期间以本条为准（开发者本轮明说），但**规范文本本身不改**——改它属改约束类文件，要单独点头，这条纪律不代劳。`docs/agents/doc-guide.md` 三.5「改工单，不要加注释解释」同理：那条讲的是「别把心路历程写进合同」，本条讲的是「改了什么、为什么改，要留痕」，两者按本条一并追加，合同正文照旧只写当下。
