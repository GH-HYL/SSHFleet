# 08: 传输失败时，统计块与明细要对得上「成了几个」

**状态**：wontfix（2026-10-20，当天立、当天撤，见下）

> **撤掉理由**：作者同日决定「上传失败即回滚」，改由 `docs/issues/upload-rollback/` 承担——失败时不留任何本次文件，传输只剩「全成 / 全不成」两种形态，**不存在「部分成功」**，本工单要修的「成功 0 而实际成了 1 个」这种中间态自然消失。
>
> 决策见 `docs/adr/0022-upload-rollback-on-failure.md`。报文议题的 `README.md` 状态表已同步。

## 原文（保留备查）

**要做的**：上传 2 个文件、第 2 个失败时，终端统计块今天显示 `成功：0  失败：1`——它数的是**节点**，不是文件。使用者看一眼会以为一个都没传成，而实际上第 1 个已经完整落在目标机上。

## 撤单前已取的证据（2026-10-20 真机，上传 3 个文件、第 2 个重名）

终端统计块：

```
  节点总数： 1  完成总数：1
  成功： 0   失败： 1
  失败分类统计 >>>  部分成功 ×1
```

同一份归档的 `terminal-output.txt`：

```
【172.28.118.49】 上传: 失败 - 0.012s
【172.28.118.49】 错误详情: two.bin: 上传失败 - sshfleet.transfer.remote_exists: file already exists on the remote host
sshfleet.transfer.finished: 2 of 3 files transferred
【172.28.118.49】 分类: 部分成功
total_files=3, success_files=2, failed_files=1
```

`report.txt` 的【结果统计】同样只写 `成功：0    失败：1`。**同一屏上 `成功 0` 与 `2 of 3 files transferred` 并存**，正是本工单要消除的歧义——而回滚方案从根上消除了中间态。

## Comments

- 2026-10-20：问题在 04 的磁盘满实测里暴露（两个文件只放得下一个 → 分类「部分成功」，统计块却写 `成功：0`）。根因是两套计数各走各的：逐文件失败会中断该节点剩余传输，`SuccessFiles` 记到中断前（=1），而统计块的 `成功` 数的是 `Verdict == Success` 的**节点**（部分成功的节点整台判失败）。
