# 01: 进度条滞后于明细行

Status: done
Blocked by: 无

**现象**（开发者 2026-10-07 报，2026-10-08 复述确认）：1000+ 台批量执行命令时，终端明细行已经刷出几百行，总进度条与百分比还停在 `0.0%`，过一两秒（甚至更久）才追上来。开发者同时确认：**同一行里的「已完成 N/总」与「成功/失败」计数是一直在涨的，只有条和百分比是死的**——这一条把问题锁定在"显示值"而不是"数据"上。

## 根因：动画值被"饿死"，不是刷新慢

`bubbles/progress` 的动画帧是**按 tag 认领**的（源码 `bubbles@v1.0.0/progress/progress.go`）：

```go
func (m *Model) SetPercent(p float64) tea.Cmd {
    m.targetPercent = ...; m.tag++      // 每设一次目标，tag +1
    return m.nextFrame()
}
case FrameMsg:
    if msg.id != m.id || msg.tag != m.tag { return m, nil }   // 过期帧丢弃，且不重排
```

而本项目**每来一份快照就重设一次目标**（`syncBars`）。于是只要快照比动画帧还密（间隔 < 16.7ms = 60fps），在途的那一帧必被下一次重设作废、作废后又不重排 → **弹簧一步也迈不动，显示值冻结**。

**冻结时长 = 快节奏持续多久**，不是一帧的 16ms——所以能卡 1~2 秒甚至更久，与"刷新率不至于这么慢"的直觉不矛盾：它根本不是慢，是不动。

排除了"渲染/投递慢"这条：日志里快照投递等待合计 **0.244s**、最长 0.007s；事件循环 View 合计 0.703s、单帧最长 0.003s。渲染器一直按 60fps 重绘，只是重绘的是同一个冻结值。

## 证据

**一、真机日志（1109 台）**

| 秒 | 快照数 | 说明 |
| --- | --- | --- |
| 0–4 | 364 / 204 / 146 / 146 / 61 | 成功爆发（> 60/s 持续约 4 秒）→ 条冻结在 0 |
| 5、7–9 | 0、1 | 骤停 → 弹簧终于迈步 → 条才开始从 0 往上涨 |
| 10 | 134 | 那批连接超时的机器一起回来 |

相邻快照间隔中位数 **5ms**，**98.4% 的间隔 ≤ 16.67ms**——全程踩中。

**二、仿真复现**（临时夹具，模拟真机消息时序，读实际渲染出来的那一行）

| 快照节奏 | 真实 11.1% | 33.3% | 66.7% | 100% |
| --- | --- | --- | --- | --- |
| 3ms/份（333/s）· 修复前 | **0.0** | **0.0** | **0.0** | 2.5 |
| 30ms/份（33/s）· 对照 | 6.0 | 28.2 | 61.5 | 94.9 |

慢节奏那行正常 → 只有快于帧率时才冻结，这也解释了**为什么本地一直复现不出来**（本地节点数与时序从没到过 60/s）。

**三、修复后真机复现**（1000 台指向秒拒端口，制造爆发，在 pty 里录渲染流）：录到 **415 个不同的百分比取值**，从 `0.0%` 平滑走到 `100.0%`。

## 修法

**去掉弹簧动画，条与百分比按目标值直接渲染**（`ViewAs`）：

- `barView` 恒 `ViewAs(target)`；`syncBars` 不再下发目标、也不再给每个节点建一个动画模型；`Update` 去掉 `FrameMsg` 分支；`final` 终帧标记与"定格"逻辑一并消失（显示值恒等于真值，不存在"追不上"）。
- 得到的性质正是这块要的：**不滞后**（快节奏下不会饿死）、**不回退**（`progress()` 单调不减）、**终帧天然准确**。

保留的：细线字符、scaled 渐变、暗空档色、百分比加粗（用户在 demo 里选定的那套观感）。失去的：缓动——而缓动在批量场景下本来就看不出来（快照比帧还密），只在节点很少时略有观感差别。
