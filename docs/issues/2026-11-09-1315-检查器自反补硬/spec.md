# 规格：检查器自反补硬

**状态**：已完成（done）——四张工单 2026-11-09 全部落地，`go test ./internal/guard` 绿
**底本**：`docs/adr/0045-检查器要能发现自己被拆掉.md`（决定）
**事实底本**：`docs/issues/2026-11-09-0945-切换前回顾审计/audit-run-2026-11-09/回执/02-检查本体.md`（轮一，检查器形状）、`11-规范面.md` §二（补硬后会当场红的现存项）

## Problem Statement

这套自动检查是「结构被改坏时跑测试就红」的唯一凭据。但它自己有洞：把检查入口那份测试文件删掉，`go test` 全绿；把某条红线的断言删掉、只留对符号的引用，指纹照对、全绿；放行台账只填「哪条规则 ＋ 哪个文件」，为什么放、谁批的留空，照样放行。

结果是：防得住手滑，防不住存心拆——而切换之后正是没人盯的时候。

## Solution

三种拆法都在 `go test` 里显形：删入口 → 红；掏空断言 → 红；台账缺格 → 红。绿就是「检查确实跑过、而且没被削」，不再分不清「全绿」与「检查不在」。

## User Stories

1. 作为维护者，我希望删掉检查入口时跑测试就红，而不是看见一片绿。
2. 作为维护者，我希望有人偷偷删掉一条断言时能看出来，而不是只看到名单没变。
3. 作为审计者，我希望每条放行记录都能说清「为什么放、谁批的」，空白不算。
4. 作为下一个接手的人，我希望「改检查面」这件事留下的痕迹比改一行代码更重。

## Implementation Decisions

- **自反登记**：红线名单、每条测试名、检查入口文件本身，各生成一份登记指纹；缺项即红。形态沿用现有指纹（钉名字与符号，不钉字节）。
- **断言强度入指纹**：每条红线测试的**断言条数**与**直接引用的生产符号集**并入指纹；数目或集合变化即红，恢复原状要走 `ADR`。取数与现有指纹同源，不另建一套扫描。
- **台账四格**：规则、文件、理由、批准人；缺任一格即红。台账文件本身进自反登记。
- **三条都归「检查本体」**：改它们的程序与改红线区一致（`ADR-0032` 更新记录第 7 条「单独点头」档）。

## Testing Decisions

- 接缝是 `go test ./...` 本身——不新开接缝。
- 在 `build/` 的模块副本里做三次**真实拆解**，每次都跑一次：
  1. 删掉检查入口文件 → 必须红，且报「登记缺了一项」；
  2. 删掉某条红线测试里的一条断言 → 必须红，且指出是哪条测试的断言数变了；
  3. 台账加一条只有两格的放行记录 → 必须红，指出缺哪两格。
- 三次拆解之后还原副本，再跑一次确认全绿——证明红是拆解带来的，不是环境。
- 不做「假绿灯」测试：不 mock 检查器自身。
