# 由程序定性的失败分类，其分类名改由配置登记 · 规格

Status: done（2026-10-20 实施，见 issues/01 的 Comments）

> 来源：2026-10-20 架构审查候选①（`/tmp/architecture-review-2026-10-20_115438.html`）。审查说「判据表开了两扇门、消费方被迫知道内部形状」——那部分经复核是**形态说重了**（消费方只有 `Has` / `TipOf` / `PasswordExpired` 三个方法，没有直接摸表内部）；审查真正点到痛处的只有一处：**代码按结构事实定性的分类名，与「兜底原文」靠一张手写名单区分**。本规格只做这一处。

## Problem Statement

一次执行结束后，终端统计块把失败分类分成两组：`>>>` 之后一行是**已归类**的，下面缩进单排的是**未归类**（判据没命中、直接显示报错原文）。区分它们的判据是：这个分类名在判据表里登记过没有。

问题在于：有一批分类名**不是查表得来的**，是程序按结构事实直接给的——「部分成功」「密码未过期」「提示词没认出」「没等到提示」「远端无响应」「改密未完成」。它们的提示语（tip）写在配置里，名字却不算"登记过"。为了让它们不掉进「未归类」，代码里被迫维护一张手写名单；而同一件事在配置里又写了一遍（「密码未过期」「改密未完成」确实登记在改密配置里）。

后果有三条：

1. **名单没跟上，分类就上屏成「未归类」。** 2026-10-14 把改密失败形态改成按结构事实定性时，新增的「提示词没认出」「没等到提示」「远端无响应」没有进名单，直到 2026-10-18 才被发现补上；那次漏掉的代价是这四个分类整整四天上屏成"未归类"。2026-10-20 复核该工单时按代码复跑，现状确已生效——但这恰恰说明**它只能靠"有人想起来"**，名单本身没有任何东西在提醒。
2. **加一个代码分类要同时改两处。** 改 `verdict` 里的常量要记得去同一文件下方那张名单补名字，改错了编译不报错、测试也不报错，只在上屏时露出来。
3. **配置与代码各说一套。** 「密码未过期」在改密配置里登记着（因为它有 tip），但真正决定它是不是"未归类"的是代码名单——配置写了什么与这判断无关。使用者按配置文件的说明"停用一个分类"，对这几个名字不生效。

## Solution

把「哪些分类名由程序定性」交给配置说：**判据表里登记了名字，就算已知分类**，有没有关键词不影响这个判断。

程序定性的分类因此与查表得来的分类走同一条规矩——在配置里登记名字（关键词留空）+ 写提示语，它就进「已归类」那一行；没登记，就被当成兜底原文单排。代码里那张手写名单删掉，「新加一个代码分类必须同时改代码两处」这件事从结构上消失。

使用者视角：改密流程里反复出现的「没等到提示」「提示词没认出」这类分类，从此与别的失败原因一样落在正常位置，不再混在"报错原文"那一堆里；配置文件里写明"分类名由程序给出、这里留名字与提示语"的口径，从此也真是配置在管。

## User Stories

1. 作为使用者，我希望改密卡住时看到的分类（「没等到提示」等）落在失败分类统计的正常位置，而不是混在"未归类"里，这样我一眼就知道原因是工具认得的那种。
2. 作为使用者，我希望配置文件里登记了名字、写好了提示语的分类，真的按我的配置显示，而不是由程序内部另有一份名单决定。
3. 作为使用者，我希望提示语跟着分类名一起在配置文件里维护，删掉一个分类的登记，它就从统计里消失（与其余分类同一套规矩）。
4. 作为维护者，我希望加一个"由程序按结构事实定性"的分类时，只需要在配置里登记名字与提示语，不需要在代码里另找一处补名字，因为记不住补的地方就是故障。
5. 作为维护者，我希望"是不是兜底原文"这个判断只有一条规则（登记了就是已知），不再有"登记了 + 名单 + 退出码"三段拼起来的判断。
6. 作为使用者，不认识的报错原文照旧单排在下面并给出"可把特征词补进配置"的引导——这条行为不变。
7. 作为使用者，我升级后拿着原来的配置还能照旧跑；就算配置文件是旧的、少了几个新名字的登记，程序也要能启动，只是那几个分类会显示成未归类。
8. 作为维护者，我希望判据表里出现"登记了名字却没有任何关键词、也不是程序定性的分类"这种配置错误时，能在启动时被告知，而不是安静地永远匹配不上。

## Implementation Decisions

- **兜底判定只认一件事**：分类名是否在判据表里登记（两块并集）。「程序定性」不再是一份单独的名单，而是靠配置里有这一条登记。
- **名单从代码里删除**：原先在判定包里手写的那组名字（含只对改密有意义的几个，判定包还有一条"引用 cli"的依赖边正是为了它们）整体移除；判定包里留一条注释说明"新增定性分类要在配置里登记名字"。
- **配置补登记**：改密判据配置里补上「提示词没认出」「没等到提示」「远端无响应」三条（只有名字 + 提示语，不带关键词）；通用判据配置里补上「部分成功」。
  - 它们带提示语是**收益**，不是额外要求：原先仅有的「触发词未命中」「部分成功」两条没有 tip，每次出现都不给解释；补了之后统计块的「提示：」块会为它们各出一行。
- **提示语的冲突要定死一条**：这几条名字现在同时可能出现在两处——改密配置（主）与通用判据表被补进的那一份（只留名字、占位提示语）。按现有「先出现且非空者胜」的规矩，用户改通用判据表里的占位提示语不会生效。改密配置里那几条的注释要写明"提示语以本文件为准"。
- **登记了却匹配不上，要能报出来**：一个分类既没有关键词、又没标明"由程序定性"，就是条坏配置。判据表加载时做一次校验，报错并指出是哪个分类。这需要登记处有一个可选字段（布尔）标明"本分类由程序定性"，默认不写即为普通分类。
  - 这是**唯一新增的配置字段**：可选、不写不影响旧配置，故不构成不兼容改动。
  - 判据表第一组（没有退出码时用）、第二组（退出码归类用）都做这项校验。
  - **改密配置那一侧只警告、不拦启动**：它随程序发布，旧版本里本来就没有这些标注，拦住等于让升级后起不来（2026-10-20 实测撞过，见工单 Comments）。通用判据表的坏条目是使用者自己改出来的，启动即报是对的。
- **不做的**：不引入门面类型、不改变 `Keywords` 的导出面（消费方只有三个方法，改造的收益不明显）；不动 `PrependCategories` 的注入次序；不动判定逻辑本身。

## Testing Decisions

- 接缝取现有唯一的调用口：判定包的兜底判定函数（`IsFallbackCategory`）与统计块渲染入口（`PrintStatistics`），两者都已有测试（`TestFallbackCategory`、`TestPrintStatisticsUnclassifiedGuide`）。不新增接缝。
- 测的是**外部行为**：给定"分类名 + 判据表（从真实配置加载）"，判定结果是什么；给定统计块输入，输出里那一类落在哪一行。不断言内部名单存在与否、不测私有函数。
- 期望值用已知字面量：`"部分成功"` → 不是兜底；`"提示词没认出"` → 不是兜底；一段不在配置里的报错原文 → 是兜底；`""` 与「原因未知」→ 不是兜底（既有语义，保持）。
- 配置校验要有一条用例：给出"有名字无关键词、且未标为程序定性"的分类，加载失败并指名该分类；标了该字段的则加载通过。
- 既有用例 `TestFallbackCategory` 里那四条（`部分成功`、`触发词未命中` 等）在改动后必须仍然通过——它们是"程序定性名字不该被当兜底"的回归网。

## Out of Scope

- 审查报告里的其它四个候选（结果流水线、参数屏/报告字段清单、`buildTasks` 拆计划、模式开关收进模式表）。
- 判据表的门面类型化（`Keywords` 导出面重排）。
- 「改密未完成」「密码未过期」这两条已有的登记——它们已经是配置登记的，本次只是不再靠代码名单。
- 把任何分类关键词挪到别处、或改动的判定结果。

## Further Notes

- 判据包现有的依赖边「只允许引用 ssh 与 cli」中，引用 cli 有一部分是为了那张名单。名单删除后如仍有正当用途则保留，若无则应一并在复查时确认（不强制删除——删依赖边属另一件事）。
- 报错文案要能指路：配置校验失败时，应告诉维护者"要么补关键词，要么加一行标明由程序定性"，而不是只报"错误"。
