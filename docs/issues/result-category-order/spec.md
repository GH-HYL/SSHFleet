# 失败分类统计的同分次序偶发错乱 · 规格

Status: needs-triage

> **来历**：2026-10-19 收尾内联清单议题（`docs/issues/inline-list-backslash-newline/`）时全量跑测试撞见，与本议题范围外，开发者定单独立项、后面自己分析。

---

## 问题陈述

统计块的「失败分类统计」承诺**数量相同时按首次出现的先后排序**（测试注释原话：`与「原因未知」同为 2，先出现者在前`，期望 `拒绝网络连接` 排在 `原因未知` 前面），但实现没兑现这个承诺：**同分的两个分类谁在前是随机的**。使用者大多数时候看到碰巧对的顺序，偶尔看到错的——同一批节点跑两次，统计块的分类次序可能不一样。

## 现象

```text
--- FAIL: TestStatisticsFailCategoriesSortedByCountDesc (0.00s)
    statistics_test.go:156: SortedFailCategories = [{连接超时 3} {原因未知 2} {拒绝网络连接 2}],
        期望 [{连接超时 3} {拒绝网络连接 2} {原因未知 2}]
```

**复现**（偶发，6 次约撞 1 次；复现的是「map 遍历顺序随机」这件事本身，不是确定性输入）：

```bash
cd modules/SSHFleet_Go
for i in 1 2 3 4 5 6; do go test -count=1 -run TestStatisticsFailCategoriesSortedByCountDesc ./internal/result/ 2>&1 | tail -1; done
```

2026-10-19 实跑：6 次中第 3 次 FAIL，其余 PASS。

## 根因

`internal/result/statistics.go` 的统计构造分两步：

1. `for category, count := range counts { ...append... }` —— `counts` 是 **map**，遍历顺序在 Go 里刻意随机化；
2. `sort.SliceStable(...)` —— 稳定排序保的是「同分保持**进入切片时**的顺序」。

两步合起来：稳定排序想保的「先出现者在前」，保的是 **map 随机给出的顺序**，不是节点结果里分类**首次出现**的顺序。测试期望的判据（首次出现序）与实现给的判据（map 随机序）不同源，于是偶发失败。

**这不是测试写错**：测试钉住的是注释里承诺的行为，是实现在撒谎。

## 影响

- 使用者可见：统计块的失败分类次序不稳定，同分时两次运行可能一先一后；数量不同时排序不受影响（降序那层是对的）
- 开发者可见：`TestStatisticsFailCategoriesSortedByCountDesc` 偶发红，容易误判成自己的改动弄坏了它

## 方案

未定。待选方向（供分析时参考，不作决定）：

1. **按首次出现序**：扫描 items 时记下每个分类**首次出现的下标**，排序键改成 `(count 降序, 首现下标升序)`——与测试注释承诺的判据一致
2. **按分类名序**：同分按分类名字典序——判据换一个，但确定性同样成立，且不依赖扫描顺序
3. **放弃承诺**：改测试注释，明说「同分次序不定」——代价是使用者看到的统计块顺序仍会变

选定前不改代码。

## 使用者故事

1. 作为看统计块的运维人员，我想同分的分类按一个**说得出理由**的固定次序排列，而不是每次跑都不一样。
2. 作为改代码的人，我不想跑全量测试时被一条**与本轮改动无关**的偶发红测试干扰判断。

## 测试决策

现有 `TestStatisticsFailCategoriesSortedByCountDesc` 就是验收工具：修好后**连跑多次全绿**（例如 20 次）才算修好，单次绿不算——偶发缺陷的验收标准是概率而非单次。
