# 目标机磁盘满 · 议题

> **这是一份独立议题的入口**，从「报文分类」议题里拆出来的：那边的磁盘满实测用的是 WSL 的 tmpfs（吃的是虚拟机内存），**没验证过真实磁盘**，而且「磁盘满」与「权限/IO 错误」在 SFTP 层返回同一个码，工具分不出来。

## 为什么单独立这个议题

1. **现有分类分不出磁盘满**。上传写失败时，OpenSSH 回的是通用的 `SSH_FX_FAILURE`，工具把它归到 `SFTP失败`，提示语里写着「远端目录权限/磁盘、账号受限、传输中断」——使用者只能猜。
2. **磁盘满与「传一半才满」是两种不同的问题**。前者一开工就失败，后者是写盘写到中途才失败，可能涉及半成品文件的清理、已经成功的那几个文件的归属。
3. **验证环境不能想当然**。tmpfs 吃内存、ext4 吃磁盘，两者在「写满」时的失败时机与错误码未必一样；上一次实测因此只能算「勉强能说明分类是 SFTP失败」。

## 判据：什么时候该正式立 spec

摸底之后如果答案是「做不到，或者代价远超收益」，本议题**以结论结案**，不立 spec。
如果答案是「能做到，且值得」，再落 `spec.md` 与后续工单。

## 已知的坑

- **别拿 tmpfs 当磁盘**。WSL 的 `/tmp` 是 `tmpfs`，默认占内存约宿主一半。要测真实磁盘，得用一个有容量上限的真实块设备（如 loop 挂载的小 ext4 镜像，需 root 与 `losetup`），或在目标机上放一个刚好写不下的真分区。
- **`SSH_FX_FAILURE` 是通用码**，不要拿它当「磁盘满」的判据。它同样出现在权限失败与服务器内部错误里。
- 测试会在目标机上写满一个卷，**用完必须清理**，别留在开发者自己的环境里。
