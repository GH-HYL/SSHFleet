# 超时收尾：连接卡住时，远端残留怎么算

- **Status**：ready-for-agent
- **日期**：2026-11-19（2026-11-20 定稿）
- **关联**：ADR-0065（清理动作不受超时与中断影响）、ADR-0063 决定 6（传输超时按 ctx 收场）与决定 10（超时不进单文件重试）、ADR-0022 决定 1／2／3／5（回滚范围与陈述）、ADR-0021（失败分类按报错原文匹配）
- **前提**：ADR-0063 已落地（sudo 下直接写目标，暂存目录与 `sudo mv` 撤掉），本规格排在它之后。清理清单里的「本次写过的路径」指的就是目标机上的最终路径；若并行开工，sudo 那一路要另写一份口径。

## Problem Statement

传输卡住——多半是对端已经不通——`timeout_transfer` 到点，程序要「先清理再报错」。但清理命令走的是同一条已经卡住的连接，发不出去。于是目标机上留着本次写了一半的文件和已写成功的文件，而程序只报一句「传输超时」：使用者不知道留下了什么，下次重传撞上「远程文件已存在」才发现，还得逐台手工去找。

## Solution

到点之后不再只是报一句。程序先解开卡住的那一步，再在同一条 SSH 连接上另开一条通道，把本次写过的（含写到一半的那个文件）删掉，然后照实报结果：

- 删干净了：分类名就是「传输超时」，使用者可以直接重传。
- 没删干净、或来不及删：分类名是「传输超时未清干净」，错误详情里列出还留着的路径，先手工清再重传。

使用者不必去目标机上翻，也不必分辨「工具试过没试过」——分类名决定下一步做什么，详情决定清哪些。

## User Stories

1. 作为运维，传输超时之后，我想知道目标机上到底留下了什么，好在重传之前处理掉。
2. 作为运维，目标机已经干净时，我想从分类名直接看出「可以直接重传」，而不是去读整段报错。
3. 作为运维，目标机还有残留时，我想从分类名直接看出「要先手工清」，并在详情里拿到路径清单。
4. 作为运维，我不想因为一次超时就在几千台上逐台 `find`——能删的由工具删掉。
5. 作为运维，我不想一台卡住的机器把整批拖住：超时之后这一台最多再多花一个连接超时。
6. 作为运维，我不想看到「删了 0 个」这种分不出「没删掉」还是「没来得及删」的句子。

## Implementation Decisions

### 时钟：每台一份，每次发起前按剩余武装

一台一份，起点是 `upload`／`download` 的入口（枚举、空间预检、逐文件写都在里面），不是建连——建连有自己的 `timeout_connect`。

**不写成「整段包一层 `WithTimeout`」**：到点时 ctx 只是变成取消状态，`io.CopyBuffer` 不会醒，没有任何东西去关通道。动作要落在每一次发起之前：

- 取剩余 = 截止时刻 − 现在。剩余 ≤ 0 就不发起、直接收场——这也是「任务完成即完成」的落点：最后一个文件写完、循环结束，没有下一次发起，就不会被判超时。
- 否则把这次调用武装起来：跑完了就往下走；到点就关掉它自己那条通道，并等它真的退出来——不等就去删同一个文件，删的是正在被写的那个。
- 武装点三处：枚举那一条 `find`、预检那一段（建 SFTP 客户端、`Stat`、`StatVFS`）、每个文件的「写 + 写完核大小」。

形态照 `internal/execute/run_command.go` 的 `runWithTimeout`（起一条协程跑，本协程等它或等到点），区别只在粒度：它包一次，这里每次发起都包一次。

到点之后先分清是哪种：父 ctx 已取消 → `Cancelled`；否则 `TimedOut`。两者互斥，与命令模式同口径。

这一台的所有文件一起作废，不回到单文件重试（ADR-0063 决定 10）。

### 到点必须先解开阻塞

`io.CopyBuffer` 不认 ctx，卡住的读写不会被 deadline 叫醒。到点的第一个动作是**关掉这一刻占着连接的那条通道**：

- 正在写文件时，是那条 SFTP 通道；
- 卡在枚举／预检的那条 `find`／`test` 上时，是那条 exec 会话通道——关 SFTP 通道对它不起作用，因为卡住的不是它。

只关通道，不关整条 SSH 连接：连接还要留给清理（取消只是标记，解开阻塞必须是一个真动作，ADR-0063 决定 6）。

### 换钟：一进收尾，到点动作就得停

这台机器上的时钟同一时刻只许有一个在管事，交接点是「决定收尾」这一句。

- 「传」这一段归 `timeout_transfer`：到点就关掉当时卡住的那条通道。这个动作**只许响这一次**——响过就解除，没响过也解除，此后不再动作（ADR-0065）。
- 「收尾」这一段（不论是文件失败触发的回滚，还是超时触发的清理）归 `timeout_connect`：到点即停，剩下的照实报。
- 中断不是清理的停止条件，也不给它另设时钟：它停在文件边界、不关通道，清理照做（ADR-0065）。卡在死链上等不到边界时，仍由「传」那笔预算到点把这次调用解开——中断之后的收尾因此也不会无限挂着。

**为什么必须换**：失败回滚也跑在这个 300 秒里。一次失败发生在第 290 秒、回滚要 20 秒时，若到点动作还挂着，它会在回滚做到一半时把通道关掉——本来是工具自己能清干净的，被自己的超时打断成残留，还报成 `rollback_partial`。这不是使用者的目标机有问题，是工具自己制造的残留。

**清理里不许看 ctx**：执行站里 ctx 只穿透到两处——拨号（`DialContext`）与命令超时；SFTP 与 `exec` 那几层根本不看 ctx。所以「到点或中断之后清理还能不能用」，不取决于 ctx 是什么状态，只取决于两件事：清理另起一份上限、不从任何已取消的 ctx 派生，以及收尾循环里别照抄文件边界那两句 `ctx.Err()`——照抄进去，第一个文件就退出了。

### 清理走同一台机器的另一条通道

不重拨、不重认证：在同一条 SSH 连接上另开一条**命令会话**，跑下一节那条删除命令——与枚举、预检走同一条路。不重拨的另一个好处是第二次握手不会发生，服务端提示那一格（参与分类）不会被重写。

不新开 SFTP 客户端逐条 `Remove`：一个文件一次往返，几千个文件就是几千次，收尾那份上限会被文件数吃掉。

### 删法：一条远端循环

一次往返删完，删不掉的把路径打回来：

```sh
for p in '<路径1>' '<路径2>'; do rm -f -- "$p" || printf '%s\n' "$p"; done
```

- 路径逐个按 `criterion.EscapeSingle` 转义；不扫目录、不用通配符（ADR-0022 决定 2 不变）。
- 打回来的那些就是 `left`，精确到路径。
- sudo 模式在最前面加 `sudo -n `。
- 路径总长过大时按长度分批，每批一条命令——一条命令装不下几千个长路径；但**上限只有一份**，分批不重发。

**「没来得及删」与「没删干净」的分界**：那条命令压根没发出去（会话开不起来，或开起来就已经耗完上限）算「没来得及」；发出去了、只是有路径没删掉，算「没删干净」，照打回来的报。

### 清理的时限

`timeout_connect`，不新增配置项。到点即停：没删掉的与没来得及删的**全部**列进残留——宁可报全，不许漏报。

这一趟不继承任何一个已经到点、或已经被取消的 ctx——派生出来就是过期的，清理一个字节都发不出去。清理启动之后，超时与中断都不是它的停止条件，只有这份上限能停下它（ADR-0065）。

### 残留清单的范围

本次**已写成功**的远端完整路径，加上**当前写到一半**的那个文件。中间目录不删、不列（可能是别人早先建的）。

### 报文

超时这一格按「目标机还剩什么」分三句（示例里的 `300` 是本次配置值，不是写死的数）：

| 情形 | 报文 |
| --- | --- |
| 超时，目标机上没有本次的东西（没写过，或写过的已删干净） | `sshfleet.transfer.timeout: 300s exceeded; no file left` |
| 超时，删过、没删干净 | `sshfleet.transfer.timeout_left: 2 of 3 written files removed, left: /a /b` |
| 超时，没来得及删 | `sshfleet.transfer.timeout_left: cleanup not attempted, left: /a /b /c` |

「写过的已删干净」这一种，第一句之后照旧再跟一句 `sshfleet.transfer.rolled_back: 3 of 3 written files removed`（ADR-0022 决定 3 的追溯用途不变），两句各说一件事、不重复；分类名仍由「传输超时」认领，见下一节。

停在写第一个文件之前、还是卡在传输中间，不另写一句：看同一行的四个数就分得出——文件总数为 0 是卡在枚举／预检，有总数而成功数为 0 是卡在第一个文件。

到点与单文件失败撞在同一次调用上时（重试期间到点），以超时收场：那次失败不再单独成句——它的后果已经含在「还剩什么」里。

### 分类：新增两条，排在既有回滚两条之前

写进 `config/keywords_error.conf` 第一组，顺序是这样：

| 分类名 | 关键词 |
| --- | --- |
| 传输超时未清干净 | `sshfleet.transfer.timeout_left` |
| 传输超时 | `sshfleet.transfer.timeout` |
| 上传回滚未清干净（既有） | `sshfleet.transfer.rollback_partial`、`sshfleet.transfer.partial_left` |
| 上传失败已回滚（既有） | `sshfleet.transfer.rolled_back` |

`sshfleet.transfer.timeout` 是 `sshfleet.transfer.timeout_left` 的**子串**——两条顺序反了，「未清干净」那一档永远轮不到。这与文件里既有那句「必须排在『执行超时』前面」是同一个坑。

这两条排在既有回滚之前，因为它们是同一档的东西：判据表把「目标机现在是什么状态」排在各条「为什么失败」之前，而超时这两条的 tip 也是一半讲状态、一半讲下一步。「传输超时」压在「上传失败已回滚」之上，只因两句说的状态相同（都是干净），而前者多给了根因——不是把超时当成了更优先的失败原因。

tip 各一句：

- 传输超时：`这一台在传输里超时，目标机上没有本次留下的东西——可以直接重传`
- 传输超时未清干净：`超时之后没能把本次传过的文件清干净，目标机上还有残留——先手工清掉再重传，否则会撞「远程文件已存在」`

### 落格：只进报错原文

残留清单只进 `contract.NodeResult.ErrorText`。**不加契约字段、不加表格列**：`results.xlsx` 的「报错原文」一列已经带它，多一格没人读，也违反 ADR-0035「后一张只加本棒结论」。

### 不落标记文件

目标机上不放任何标记。写标记的时机与残留产生的时机是同一刻（连接已经卡住），能写进去的时候恰恰不需要它；而 ADR-0063 决定 3 就是「目标机上不留本次的任何东西」。追溯靠这一格的报文与本地 `history/`。

### 下载

远端零写入，没有残留清单这回事：本地半成品删掉、报 `timeout`。ADR-0022 决定 5 不动。

### 使用者可见面

- `docs/4-进阶知识手册.md` 讲「上传失败不留残留」那一段：补超时这一格——到点停传、随后清理，分「传输超时」与「传输超时未清干净」两类。
- `docs/5-常见问题.md` 对应那一问：把新分类名一并列出。
- `docs/1-使用手册.md` 的「并发与超时」：写明超时之后这一台还要做一次清理，单台最多多花一个连接超时。

## Testing Decisions

**接缝**：`execute.Run`——站的入口（递一张纸、收一张纸），是 ADR-0037 定的三种接缝之一，已与开发者确认。测试只从这一处进，只断言这张纸与假目标机上的文件，不碰内部函数。

**怎么造「卡住」**：给既有假目标机加一个开关（写到第 N 字节后不再应答）。同一个假件上的一个开关，不新造假件；自定义区允许伸进内部。

**分两段断言**：

1. 超时且清得掉：纸里该台 `TimedOut` 为真、分类名是「传输超时」、`ErrorText` 里有 `sshfleet.transfer.rolled_back`；假目标机上本次写过的路径一个都不在。
2. 超时且清不掉：分类名是「传输超时未清干净」，`ErrorText` 里 `left:` 后面那串路径与假目标机上真实留下的文件逐个对得上。

**计时**：`timeout_transfer` 设小值（配置以秒为单位，`1` 够），不等真超时；清理那一趟另有一条用例让它到点，断言「到点即停、报全」。

**收尾不被自己打断**：另有一条用例钉住换钟——假目标机的删除卡在一个闸门上，测试等到点那一刻过去再放开闸门，断言回滚照样做完了（分类不是「上传回滚未清干净」）。同一形态再跑一遍，把「到点」换成「父 ctx 已取消」，断言清理照做——这条钉的是 ADR-0065。

**不动红线区**：这一格的测试住在 `internal/execute` 的自定义区，不改既有红线测试的名单与指纹。

**判据**：`internal/execute/verdict_test.go` 的 `classifyTables` 里按随包配置的顺序补上这两条，再各加一条用例——原文只含 `sshfleet.transfer.timeout` 的归「传输超时」，只含 `sshfleet.transfer.timeout_left` 的归「传输超时未清干净」。第二条就是钉「后者不会被前者吃掉」的那一条：顺序一颠倒，它会把「传输超时」说出来。

## Out of Scope

- 断点续传（ADR-0063 决定 3 已否）。
- 连接正常时的回滚口径（ADR-0022 决定 1、3 已定，不动）。
- 既有两条回滚（`rolled_back`／`rollback_partial`）的删法：它们现在是逐个删，与本文的「一条远端循环」不一致。**本轮不换**，另开一项再议。
- 传输卡住时对端到底发生了什么（链路、sshd、磁盘）：工具只陈述现象，不做归因。

## Comments

- 2026-11-19：从上传下载稳定性调研拆出。来由是 ADR-0063 定稿前的审计：决定 6 要求「到点先收尾再返回」，而超时最常见的情形正是连接已死、收尾发不出去，这一格当时没有覆盖。
- 2026-11-20：四个待定项定完。时钟＝每台总时长、走 ctx（开发者明示：「原设想是这个，而且之前设想走的是协程的上下文，就像执行阶段的命令执行超时一样」）；清理的时限复用 `timeout_connect`（开发者明示）。超时之后另开通道清理、分类名落成「传输超时」与「传输超时未清干净」、残留只进报错原文、不落标记文件（开发者采纳推荐：「其他的按照你的推荐走」）。既有两条回滚的删法按范围外处理。
- 2026-11-20：清理与「超时／中断」的关系单独立成 ADR-0065（开发者明示：「不管是超时还是中断，都得不能影响清理动作」）。据此改掉本文一处旧写法：清理原本挂在上一级 ctx 上、取消仍能停下它；现在清理只受自己那份上限约束。
