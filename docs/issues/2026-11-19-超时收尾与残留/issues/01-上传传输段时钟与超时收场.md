# 01: 上传的传输段时钟：到点解开阻塞，照实报残留

**要做的**：一次上传有一份 `timeout_transfer` 的预算，起点是 `upload` 的入口。预检与每个文件的「写 + 写完核大小」在发起之前按剩余时间武装：跑得完就往下走；到点就关掉当时占着的那条通道、等那次调用退出来，这一台就此收场。到点与中断分开记（父 ctx 已取消算中断），两者都不进单文件重试。

收场时照实说目标机上还剩什么：本次已写成功的完整路径，加上当前写到一半的那个文件，按路径去重。这一条工单**不清理**，所以那一句是「cleanup not attempted」那一档，分类落到「传输超时未清干净」。

**Blocked by:** 无，可立即开工。

**Status:** done

- [x] 到点后那一次调用真的退出来了（关通道在前、等它退出在后），不发生「边写边删」
- [ ] 报错原文里有 `sshfleet.transfer.timeout_left: cleanup not attempted, left: …`，路径与假目标机上真实留下的文件逐个对得上——留给 02（02 之后这一档只剩「清理发不出去」那一种，由 02 的用例钉）

## Comments

- 2026-11-23：「卡住」用假目标机的 `stallSftp` 造——服务端读满版本交换那 9 个字节之后停一次，客户端的下一次请求没人应答。停的时间有上限（`stallFor`）：不限的话客户端关掉 SFTP 通道之后服务端还堵在闸门上，永远看不到 EOF，「关通道能不能解开阻塞」这件事反而测不出来。这条同时给 ADR-0065「未证实清单」第一条补了一个本机样本：关掉 SFTP 客户端确实能让挂起的 `Stat` 返回。
- 2026-11-23：`transfer_transfer` 为 0 时按「不设预算」办（直接跑、不武装）。配置层不允许 0（`execution.timeout_transfer` 至少 1 秒），这条路只给直接拼纸的调用方——既有用例都是这么拼的。
