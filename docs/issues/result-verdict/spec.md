## 一、要解决的问题

「这台机器到底算不算成功」这句话，现在全工程**十处各写一遍**。口径可核对：**所有直接读 `Result.ExitCode`
判成败或分类的位置**，删完应当为 **0 处**：

| # | 位置 | 形态 |
| --- | --- | --- |
| 1 | `result/classify.go:39` | 有退出码就按退出码定案（分类的权威分支） |
| 2 | `result/statistics.go:78` | `ExitCode != nil && *ExitCode == 0` |
| 3 | `batch/progress.go:111` | 同 2（逐字相同） |
| 4 | `output/terminal.go:90` | 同 2 |
| 5 | `output/xlsx.go:178` | 同 2 |
| 6 | `output/reporter.go:262` | 同 2 |
| 7 | `output/reporter.go:348` | `isFailedResult`——**条件更宽**：多一条"有报错原文也算失败" |
| 8 | `main.go:414` | 同 2 |
| 9 | `ssh/client.go:156` | `isCleanSuccess`——**再多要求"无失败文件"** |
| 10 | `ssh/passwdsession.go:147` | 改密收尾的"正常收场"判定 |

另有 `result.IsSuccessResult`（`classify.go:101`）写成了函数、**零个调用点**。

根子更深一层：**执行侧一边记事实、一边编结论**。它把已经知道的结构事实
（代填哪几条没送出去、改密有没有出现过期信号、文件成了几个败了几个）**降级成一句文案**，
再用"把已经拿到的退出码抹成空"的手法，让下游靠文本匹配把它认回来。

活例（走查场景 2）：「触发词未命中」这个分类，是靠把「触发词未命中：第 1 条（…）」这句话写进报错、
把已经拿到的 `0` 抹掉、再让它去第一组关键词里撞出来的。而这件事在执行侧的真身只是
**`AnswersMissed = [1]` 这么一个结构事实**。

**目标**：执行侧只写事实；成败、分类、定论退出码**只在结果判定阶段产生一次**。

## 三、结果结构体

一个结构体，**两个区，谁都不碰对方的格子**（D3 的落地形态：不是"整个结构体只许写一次"）。

### 事实区（执行侧写，只此一次）

现有：`Seq` · `IP` · `Port` · `User` · `AuthMethod` · `ConnectSuccess` · `ConnectCostTime` ·
`ExecCostTime` · `Output` · `Error` · `TotalBytes` · `TotalFiles` · `SuccessFiles` · `FailedFiles`

新增：

| 字段 | 含义 | 取代了现在的什么 |
| --- | --- | --- |
| `CommandExitCode *int` | **目的那条命令**的退出码（命令 / 脚本 / 代填写它；有就有、没有就 `nil`） | 不再写进结果退出码；不再靠"err 为 nil 就推 0" |
| `Steps []StepResult` | **中间步骤命令**各自的退出码（带语义名，来源见 D38：预检 / 枚举 / 改密收尾） | 不再塞进结果退出码（现 `sftp.go:205` 下载预检查、`sftp.go:247` 远程文件枚举 `find`，都是塞进去的） |
| `TimedOut` / `Canceled` | 到点收场 / 外部中断 | 不再压在 `Error` 文本里 |
| `SessionBegun` | 命令是否真的下发成功 | 现在靠 `Error` 是否为空反猜 |
| `ServerBanner` | 认证阶段服务端提示原文，**无条件写**（D34） | 现在被追加进 `Error`（`applyBanner`） |
| `AnswersMissed []int` | 哪几条代填没送出去 | 现在渲染成一句话写进 `Error` |
| `AbortLine` | 中止词命中的原文行 | 现在写进 `Error` |
| `AnswersExhausted` | 代填已送空（用于区分"表空了还超时"） | 现在追加进 `Error` 文本 |
| `EnterSignalSeen` | 改密：**整场出现过"要求改密 / 密码已过期"的服务端信号**没有 | 现在靠 `Error`=「密码未过期」+ 抹掉退出码 |
| `PasswdEarlyClose` | 改密：远端当场重问（早收场） | 现在无对应字段 |

**不用新加的**：上传/下载"未尝试的文件数"——失败即 `break`，`TotalFiles − SuccessFiles − FailedFiles` 就是它。

### 结论区（结果判定写，只此一次）

| 字段 | 含义 |
| --- | --- |
| `Verdict` | `success` / `other`（英文枚举） |
| `Category` | 失败时的分类名；成功时留空 |
| `ExitCode *int` | 定论退出码（判定最后一步赋或保持 `nil`） |

**注意 `ExitCode` 不是新增字段**（`types.go:29` 现役），本轮的改变是**换主人**：原来执行侧写、四处再各自判；
现在**执行侧一个字都不写**，只由判定在最后一步赋或保持 `nil`。

## 四、结果判定

### 4.1 两级（D6）

- **一级 = 结构事实**（执行侧比谁都清楚的那些）：`AnswersMissed` 非空 → 「触发词未命中」；
  传输模式有成功有失败 → 「部分成功」；改密未见过期信号 → 「密码未过期」……**直接定性，不查表**。
- **二级 = 文案**：一级没有命中时，才拿文本去判据表里匹配。

单入口，内部先一级后二级；**不按执行路径分入口**（那会退化成"各判一遍"）。

### 4.2 模式由入口传参（D32）

判定需要知道模式（4.5 的成功规则按模式分），但 `Result` 里**不装模式**——装了会成环（`cli` 已经 import `ssh`）。
做法：**新立模式枚举类型**（落在 `cli`，与 `ModeName()` 同处），`Args.ModeName()` 的返回类型从裸 string 换成它；
执行入口把它作为入参传给判定。

**边界（容易越界，先说清）**：本轮只换**类型**，不动那些调用点的**逻辑**——
`batch/batch.go:225`、`result/statistics.go:43`、`output/report.go:47`、`output/archive.go:208` 四处
只做类型适配，**不许顺手把"模式 → 文案"的映射表合并**。合并映射表是 ADR-0003 重开的独立议题。

### 4.3 选组：纯字段判定（D15 + D33）

conf 分两组（第一组 `[[categories]]`、第二组 `[[exit_code_categories]]`）。**选组只看一个字段**：

> **`CommandExitCode != nil` → 第二组**（目的那条命令真的跑了并给了退出码 → 它可能是被拒，也可能是自己失败）
> **`CommandExitCode == nil` → 第一组**（没有"目的命令"的退出码：连不上、认证失败、传输失败、改密……）

为什么它成立：`CommandExitCode` 只装**目的那条命令**的退出码（D33），所以"这条命令是不是目的本身"这个问题
在结构层就已经答完了。**判据不再需要模式、也不再需要段**，环自然解开。

逐场核对过，与现状**一致**：

| 场 | `CommandExitCode` | 选组 | 现状走哪组 |
| --- | --- | --- | --- |
| 命令/脚本正常或自己失败 | 有（0 或非 0） | 第二组 | 同（退出码非 0 → 第二组） |
| 密码过期被拒 | 有（1） | 第二组 | 同 |
| 上传/下载失败 | 无 | 第一组 | 同（退出码 nil → 第一组） |
| 预检查失败 | 无（进 `Steps`） | 第一组 | **不同**：现状因预检退出码被塞进结果退出码而走第二组——这正是 D27 要消掉的那处补丁 |
| 改密 | 无（`:` 进 `Steps`） | 第一组 | 同 |

同时：**定论退出码赋不赋**也看同一个问题——是"目的命令"且真有退出码 → 赋；否则保持 `nil`。

#### 为什么第二组里原本还有一条「远程路径不存在」（历史，已查明）

**不是"有意分两组"，是被"预检查退出码塞进结果退出码"逼出来的补丁。**

- `docs/issues/error-classification/spec.md` §4.7 当初就写明：凡退出码非 `0` 的结果都进第二组，**包括「预处理失败」**。
  （注：该稿写在文件改名之前，里面写的 `config/error_keywords.toml` 就是现在的 `config/keywords_error.conf`。）
- 于是下载侧预检查（`test -e`）失败时，预检自己的退出码 `1` 进了结果退出码，分类只能走第二组；而第二组里没有对应判据，结果落成没用的**「执行失败(退出码1)」**。
- 2026-09-24 的 `ce4bdaf` 就是去补这一刀的（原号 `3eb936a`，经历史重写已变），commit message 第一行写着：
  「O1 下载预检失败按报错原文归类：**第二组补「远程路径不存在」，不再顶成执行失败(退出码1)**」。
  同一次提交在 conf 里留下的注释是：「预检自己的退出码 1 会进结果——于是这条走上的是第二组，**与第一组里同名的那条各判各的**」。

**新框架下这个补丁自然消失**：`Steps` 独立成字段、结果退出码保持 `nil` → 上传与下载两侧统一走**第一组** →
第一组那条同名分类命中 → **用户看到的分类名一个字母都不变**（仍是「远程路径不存在」）。

风险处置（作者 2026-09-29）：「分两组一定是有原因的，但我不记得了…你就先弄成一组，**有问题回来再说**。」
→ 真机复跑专项确认这两侧的分类名不变（9.5 #1）。

### 4.4 匹配文本源

`ServerBanner + Error + Output` 三者合成后匹配（D14）。现在只匹配 `Error + Output`，banner 被并进 `Error`
才搭上车；独立成字段后必须显式带上。

### 4.5 什么算成功

`Verdict` = 判定按该模式的成功规则给出的结论；**与退出码是否为 0 无关**（走查场景 2：退出码 `0`
而 `Verdict = other`）。这正是「不再有 0 就是成功」。

**成功规则**（作者 2026-09-29 认下，见 D31；判定只读事实区的值）：

| 走哪条路 | `Verdict = success` 的条件 |
| --- | --- |
| **会话里执行命令的三类**（命令 / 脚本 / 代填） | `SessionBegun` 且 `CommandExitCode == 0` 且 `AnswersMissed` 空 且 `AbortLine` 空 且 非 `TimedOut` / `Canceled` |
| 上传 / 下载 | `FailedFiles == 0`（下载还要求 `SuccessFiles > 0`；"一个文件都没枚举到"已在采集阶段拦下） |
| 改密 | `EnterSignalSeen` 为真 且 非 `PasswdEarlyClose` 且 非 `TimedOut` / `Canceled` 且 `Error` 为空 |
| 任一模式 | 连接失败 / 超时 / 中断 → 一律 `other` |

两处要点：

- **命令 / 脚本 / 代填并成一行**（原稿把代填单列，是错的）：按原写法，一次普通的 `-c "false"`（没配代填，
  `AnswersMissed` / `AbortLine` 天然为空）会满足代填行的全部条件，**命令失败被报成成功**。
  并表后没配代填时那两个条件自然退化，反例消除；而且 `ModeName()` 本来也不返回"代填"，判定根本选不中单列的那一行。
- **改密不能看 `CommandExitCode`**：按 D33 改密的 `:` 归 `Steps`，所以它恒为 `nil`。
  "改密对话走完了"用 `EnterSignalSeen` + 非早收场 + 未超时/中断 + 无报错原文 表达。

### 4.6 判据的顺序

改密专用的失败分类（`keywords_passwd.conf`）仍由装配层**插到通用表最前面**（现状机制不变）：
同一个词在两张表都出现时，改密的分类先命中。
