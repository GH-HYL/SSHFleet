# 终端明细看不到目标输出（2026-10-20）

Status: done（2026-10-22 收尾：真机取证已回，见 §六）

> **来源**：使用者 2026-10-19 用 Windows 连 iBMC 跑 `ipmcget -d health`，13 台全部「执行成功」，但终端明细里每台只有「连接 / 执行 / 分类」三行，命令输出**全是空白行**；同一批运行的 `terminal-output.txt`、`terminal-output.xlsx`、`results.xlsx` 里却有 `System in health state.`。
>
> **本文件是证据底本**：记「根因是怎么被定下来的、哪些方向已证否」。工单只写要做什么。

---

## 一、真机现象

| 去向 | 看到的内容 |
| --- | --- |
| 终端 | 每节点 3 行状态 + **空白**，输出两段显示成空行 |
| `terminal-output.txt` | `System in health state.`、`System Events:` / `16 major events.` 都在 |
| `terminal-output.xlsx` / `results.xlsx` | 内容都在（xlsx 侧替 CR 做了替换） |

**必然复现**；当时只有少数命令这样、其余都正常——后来查明那不是「命令」的区别，是**输出行宽**的区别（§三、§六）。执行选项一致：`--no-sudo --no-shell --yes`。

## 二、链路

单条结果由 `ResultLine` 拼成一段文本，去向两个：

1. 写 `terminal-output.txt`（`fmt.Fprintln`）——**只写文件，不做任何解释**；
2. 打到终端（`tea.Println`）——**先经 bubbletea 的渲染器，再按终端语义解释**。渲染器把这段文本按 `\n` 拆成一行一条入队，对**宽度小于终端宽度**的行，在行尾补一个 `ESC[K`（擦光标到行尾，`standard_renderer.go` 的 `flush`）。

两条链路吃的是同一段字节。所以「文件里有、终端没有」**不是渲染丢了内容**，而是终端把控制字符**解释**掉了——而且中间还夹着渲染器那一步：行尾那个 `\r` 先把光标送回第 0 列，紧跟着的 `ESC[K` 就从行首擦起，**整行被擦空**，屏幕上只剩状态行与分隔线。§1 里 xlsx 能看到内容，正是因为它多做了这一步替换（`cleanForExcel` 把 `\r` 换成 `\n`），而 txt 与终端没有。

> 渲染器这一层是 2026-10-22 补上的（读 bubbletea v1.3.10 源码 + 屏幕模型复算），见 §三与 §六第 3 条。

## 三、复原实验（本机可控字节，`--no-shell` 原样下发）

远端回什么字节，工具就原样采集——用 `od -c` 看归档，**CR 一个不少**：

```
System in health state.\r\n==...
                       ^^^^^^^ 输出行末尾的 CR 原样进了 terminal-output.txt
（改动前的采集侧只按 \n 切行，不认 \r）
```

再把同一段字节按 Windows 控制台语义重放（一个 80×24 的屏幕模型，支持 `\r` 回行首、`\n` 换行、`\b` 退格、CSI 零宽）。**这次重放只模拟了终端的裸语义，没有模拟渲染器补 `ESC[K` 那一步**——所以下面第三行是错的，保留在此仅作「当时怎么想的」：

| 输出原文 | 重放画出来 | 真机上 |
| --- | --- | --- |
| `第一行\r第二行\r` | **只有分隔线**——两行全被吃掉 | 同左 |
| `System in health state.\r不健康` | `不健康tem in health state.`——前半截被覆盖 | 同左 |
| 正常 CRLF 单行 | 重放显示正常（末尾的 `\r` 恰好无害） | **空白**——补 `ESC[K` 后整行被擦，2026-10-22 真机推翻 |

**结论**：**行尾带 CR 的那一行就会消失**——CRLF 与孤立 CR 一样致命，差别只在「擦掉多少」，不在「擦不擦」。原先按本机复算得出的「末尾恰好一个 CRLF 的单行输出不受影响」**是错的**，2026-10-22 真机取证把它推翻了（见 §六）：出问题的那条命令，回的正是每行都以 CRLF 结束的 25 字节短输出。

「为什么只有那两条命令」也换了答案：**不是**因为它们带回车（真机上 13 台、四条命令，台台都带），是因为**行宽**——宽于终端宽度的行走的是截断，不补 `ESC[K`，内容反而留了下来；窄行才被整行擦掉。那两条无回显的命令，输出行只有 23~50 字节。

## 四、已证否的方向

| 方向 | 怎么证否的 |
| --- | --- |
| 渲染器把内容丢了 | 读 bubbletea v1.3.10 的 `flush` / `stop`：只丢弃比自己短的行，不吞内容 |
| 进度界面把明细盖掉了 | `flush` 的 `CursorUp(linesRendered-1)` 在执行期间恒为 0（自首帧起就是 2 行）；`queuedMessageLines` 不会触发 |
| 输出字符串本身有问题 | 把归档原文整段重放，完整显示——送进终端的那段文本是干净的 |
| 工具改写了字节 | `--no-shell` 原样下发，没有改写点 |
| 与 `--yes` / 并发 / 连接快慢有关 | 13 台全成功、耗时正常；`--yes` 只影响「教学类提示不上屏」 |
| Windows 颜色能力导致（VT 未开时的「残骸」） | 程序自己开 VT；且该问题表现为残骸，不是空白 |

## 五、本次修复涉及的两处

1. **采集侧**：整备只按 `\n` 切行，`\r` 原样流向后继所有去向。已改为先归一（CRLF / 孤立 CR → LF）。
2. **呈现侧**：终端明细直接透传原始控制字符，没有「别让终端吃掉它」这一层。已改为把 `\r`、`\b`、NUL 等换成可见图示。

真机上真正起作用的是第 1 处：2026-10-22 那四次运行里，最终交给终端的文本控制字符个数全是 0（§六），第 2 处的替换表一次也没触发。它现在的身份是**保险**——只要采集侧哪天漏了、或换了别的字节流，它顶住；**别因为「没触发」把它当死代码删掉**（理由见 §二 与 `showControlChars` 上面那段注释）。

## 六、真机取证（2026-10-22，收口）

取证走 2026-10-20 定的那条路：换可执行文件、照原方式跑一次、把归档发回来（工单 03 的取证日志）。**拿到四次运行、每次 13 台的完整字节**，本议题需要的东西齐了。

| 运行 | 改前表现 | 远端原始输出（整备之前） | 交给终端的文本 | 归档 txt 的 CR |
| --- | --- | --- | --- | --- |
| 健康状态查询 | 终端一片空白 | 13/13 台都带回车：一行正文 + CRLF，25 字节 | CR=0、LF=4 | 0 |
| 另一条短查询 | 终端一片空白 | 每台两行、各自 CRLF（CR=2） | CR=0、LF=5 | 0 |
| 温度 / 事件表 | 有回显 | 每台 CR=9（部分 26），逐行 CRLF | CR=0 | 0 |
| 进风温度表 | 有回显 | 40 KB 里只有 1 个 CR，其余纯 LF | CR=0 | 0 |

三句话收口：

1. **CR 从哪来：有了。** 13 台、四条命令，台台都带——「只有那两条命令带回车」这个旧猜测不成立。
2. **归一确实生效，也确实解决了问题。** 四次运行的汇总行一致：「远端带 CR 的节点 13 个；最终文本仍带控制字符的节点 0 个」；屏幕上输出都在；四份 `terminal-output.txt` 的 CR 个数都是 0。
3. **「为什么只有短输出看不见」也答了：行宽。** 空白那两次的输出行平均 35~39 字节、最长 50；有回显那两次平均 121~158 字节、最长 160~195。分得干干净净——宽于终端列数的行走截断、不补 `ESC[K`，窄行才被整行擦空。

那两条「原有回显」的命令**不是没踩到 CR**（台台都带），是它们的输出行宽超过终端列数、走截断那支，擦不到。

仍属未证实、但**不影响结论**的三条，写在这里免得下次重查：

- **CR 由 iBMC 的哪条指令产生**：只验到「这条命令的整段输出带回车」，没做单条指令级隔离。也不必做——工具侧不该依赖源的形态。
- **「宽行不补 `ESC[K`」这一步是源码推断 + 本机屏幕模型复算，未在真机单独构造验证**；它与四次真机的表现逐条吻合（窄行空白、宽行有回显），但不是实测。
- **终端列数当时没记**：取证日志记了「是否终端 / `TERM` / VT」，没记列数，所以「宽于列数」是拿两次运行的对照推出来的（≤50 字节全空、≥121 字节有回显），不是量着列数算的。要坐实，下次把列数记进环境行就行。

另有一条代价要知道：归一之后，靠 `\r` 原地覆盖做进度条的输出（`curl`、`dd` 之类）会变成多行。目标场景用不到，取舍见 §二。
