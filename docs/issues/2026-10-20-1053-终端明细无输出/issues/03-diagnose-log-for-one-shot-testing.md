# 03: 一次运行就把取证信息记齐（日志）

**要做的**：换一个可执行文件、照常跑一次，归档里就有判定「终端看不到输出」根因所需的全部事实，不必再补测。

**被谁阻塞**：无，可立即开工。

**状态**：done（2026-10-20 实施）

- [x] 每台机器记下**整备之前**的远端原始输出：字节构成（CR/LF/ESC/NUL/其它控制字符）、行尾形态、转义形式、前 512 字节十六进制
- [x] 每台机器记下**最终交给终端**的那段文本的字节构成与转义形式（与上一段并排，一眼看出是哪一层出的问题）
- [x] 记下环境事实：版本与构建标识、平台、stdout 是否为终端、颜色序列开关、Windows 控制台 VT、会话 tty 的实际口径（命令/脚本不申请 pty，代填与改密会申请）
- [x] 日志落在归档目录、与 `report.txt` 同层
- [x] 收尾写汇总：收到多少条、远端带 CR 的节点数、最终仍带控制字符的节点数、点名前几个回 CR 的节点（ESC 不计入——颜色是正当用途）
- [x] 同一节点重复登记只记一次；诊断器 nil 时所有调用点安全（既有测试全绿）

## Comments

- 2026-10-20：诊断记录器是新包 `internal/diagnose`，不改变任何执行行为——它只读事实、只写日志。接在三个点上：采集侧（整备前抓原始字节）、呈现侧（打屏前抓最终文本）、主干（环境与汇总）。
- 为什么记「原始 + 最终」两份而不是只记一份：只记原始，分不清「采集正常、终端吃了」与「采集就没拿到」；两份并排，读日志的人不必回问。
- 本机端到端验证：`printf 'System in health state.\r\n'` 经 `--no-shell` 跑一遍，日志里 `2e 0d 0a` 与「CRLF=1」同时出现，最终文本 CR=0。

- 2026-10-20（复查后修订）：去掉「先写工具日志、再 Rebind 到归档」的可变出口——日志出口不再跨模块流转，归档一建好才建记录器（规范「结构·2」）。同时：终端判断改用与呈现层同一个库同一口径；错误详情与错误行也做控制字符可见化（原先只护住 `Output`，错误原文同样是远端字节）；最终文本补十六进制转储；汇总算全传输类节点。
- 2026-10-22（取证已回，工单使命结束）：一次运行就把该记的记齐了——四次运行、每次 13 台，远端原始输出与最终文本并排可比，汇总行直接给出「远端带 CR 13 个 / 最终仍带控制字符 0 个」。结论已落进 `findings-2026-10-20.md` §六，**不再需要这份日志存在**。
