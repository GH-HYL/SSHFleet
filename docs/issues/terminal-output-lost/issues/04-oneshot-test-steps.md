# 一次取证测试 · 操作步骤

Status: ready-for-human

> 给替我们跑测试的人看的。目标：**换一个可执行文件、照原来的方式跑一次、把日志发回来**，就能判定根因，不再来回测。
>
> 为什么只测一次：目标环境（Windows + iBMC）这边碰不到，每次测试都占用对方的人。所以本工具把「判定根因要用的每一个事实」都记进了归档目录里的一个文件。

## 三步

**第 1 步** 把 `SSHFleet.exe` 换成本次给的那一个，其它文件一律不动。

**第 2 步** 用原来那套参数、照原来的方式跑一次。就是之前终端上看不到输出的那两条命令；两条都跑最好，只跑一条也能定案。

**第 3 步** 到这次运行的归档目录里，把 `SSHFleetDiagnose.log` 整个复制发回来。

归档目录在平时运行 SSHFleet 的目录下 `history\<时间戳>_<模式>\`，取最新那个文件夹。`SSHFleetDiagnose.log` 与 `report.txt`、`terminal-output.txt` 在同一层。

## 日志里能看到什么

每个节点两段并排，读的人一眼能看出是「采集没拿到」还是「终端吃掉了」：

```txt
DIAG> ── 节点【10.x.x.x】远端原始输出（整备之前）──
DIAG>   字节构成：共 25 字节：CR=1 LF=1 ESC=0 NUL=0 其它控制字符=0 合法UTF-8=true
DIAG>   行尾形态：CRLF=1 只LF=0 只CR=0 无换行=0
DIAG>   转义形式："System in health state.\r\n"
DIAG>   十六进制：
DIAG>       00000000  53 79 73 74 65 6d ... 2e 0d 0a

DIAG> ── 节点【10.x.x.x】最终交给终端的文本──
DIAG>   字节构成：共 191 字节：CR=0 LF=4 ...
```

文件开头记环境事实：版本与构建标识、平台、stdout 是否为终端、颜色序列开关、Windows 控制台 VT、会话是否申请 tty。
文件结尾是汇总：收到多少条、远端带 CR 的节点数、最终仍带控制字符的节点数，并点名前几个回 CR 的节点。

## 怎么读

| 远端原始输出 | 结论 |
| --- | --- |
| 有 CR（`CR` 大于 0） | 根因确认：回车在捣乱，本版已修好，终端应能正常显示 |
| 没有 CR，但终端仍空白 | 不是这个根因；日志里的其它字段会指出下一步查哪里。同样请发日志，价值一样大 |

## 发回来之前

- 含服务器地址与账号名，**不含密码**——工具本来就不记密码。
- 嫌内部信息敏感时，可以只发 `DIAG>` 开头的行：用文本编辑器搜 `DIAG>`，全选复制即可。
- 每次运行生成新的归档文件夹，不会混入以前几次的内容。

## 风险与边界

- 只读：不改变任何执行行为，命令照旧下发、结果照旧处理。
- 唯一新增的是多写一个文件 `SSHFleetDiagnose.log`，放在本次归档目录里。
- 不改配置、不改 iBMC、不碰生产节点。
