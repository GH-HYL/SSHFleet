一、一句话结论
------------------------------------------------------------------------

输出其实「到了」终端，终端把其中的「回车符（CR）」当成了「回到行首」
这个控制指令，于是把行首覆盖成空白、把整行吃掉，屏幕上只剩分隔线，
看起来像「没有输出」。而归档文件不做这种解释，所以字字都在。


二、为什么只有那两条命令出问题
------------------------------------------------------------------------

远端回的行尾如果是 Windows 风格（CRLF，即 \r\n），或回显里夹了孤立的
\r，就会触发；普通的单行输出（只回 \n）不会。

  · 用 --no-shell 时，命令原样下发，远端回什么字节，工具就原样收到、
    原样交给终端。
  · 隔离条件一致（--no-shell --yes --no-sudo），唯一变量就是「这条命令
    回了什么字节」。这就是「只有那两条命令」的原因：它们的回显里带 \r。

本机已用可控字节复原：
  远端回 "第一行\r第二行\r"  →  终端只剩分隔线（两行全没了）
  远端回 "System in health state.\r\n"  →  正常显示（末尾单个 \r 恰好无害）


三、现在已在工具侧修掉的两处（不用真机也能验证）
------------------------------------------------------------------------

1. 采集侧：远端回 CRLF 或孤立 CR，先归一成换行再落盘
   —— 归档里不再残留 \r（实测 CR 个数为 0）。
2. 呈现侧：终端明细里把 \r、\b、NUL 这类控制字符显示成 ␍、␈、␀
   —— 即使还会夹，终端也不会再显示成空白，而是当场看得见。
   全量测试 13 个包全部通过。

也就是说：即使不改远端任何东西，下一次跑那两条命令，终端上应该能
直接看到输出了（或至少看到 ␍ 标记，一眼知道里面夹了什么）。


四、为什么还想要一次真机取证
------------------------------------------------------------------------

上面两条是「治症状」，把 \r 的破坏力消掉了；但 \r 究竟从哪来、
是 CRLF 还是夹在行中间，本机测不到——那两条命令只有 iBMC 才回。

现在手里的归档（2026-10-19_14-47-50_..._iBMC健康状态）里看不到任何
控制字符，说明出问题那次的原始字节已经丢了，只剩「看起来正常」的文本。

需要一次实验：在能连 iBMC 的机器上，把同一批里**一条正常命令**和**一条
出问题的命令**，各跑一次，留住原始字节。


五、要做的实验（越简单越好，不碰生产）
------------------------------------------------------------------------

前提：任意一台 Windows（或 Linux）机器，能 SSH 到一台 iBMC，账号
能用 ipmcget。只要连一台即可，不需要 13 台。

步骤 A：看远端到底回什么（最关键，一条）

  在能连 iBMC 的那台机器上执行（把 <地址> <账号> 换掉）：

    ssh <账号>@<地址> "ipmcget -d health" | od -c | tail -20

  期待看到行尾是 \r \n 还是只有 \r，以及最后一行有没有换行。

  如果 od 不可用（Windows 自带 cmd）：
    ssh <账号>@<地址> "ipmcget -d health" > out.txt
    再在记事本里打开、或用 PowerShell 跑：
    (Get-Content out.txt -Raw).ToCharArray() | % { [int]$_ } | Select-Object -Last 40
    ——  看到 13（CR）出现在哪里，就是问题所在。

步骤 B：对照组（一条）

    ssh <账号>@<地址> "uname -a" | od -c | tail -5

  对照组应该看不到 13（CR），或只在行尾成对出现。这能证明「差别在
  命令回的字节」，而不是工具或网络。

步骤 C（可选，想要更完整的证据）：用修好的新版本再跑一次

    SSHFleet.exe -f bmc.csv -c "ipmcget -d health" --no-sudo --no-shell --yes

  看终端明细里：
    · 输出正常显示        → 这次回显里没有 CR，问题已不再出现；
    · 输出里带 ␍ 符号     → 回显里有 CR，已被工具标出来，把带 ␍ 的那段
                             原样发回来即可，那就是根因的物证。


六、要回报什么
------------------------------------------------------------------------

  1. 步骤 A 的 od 输出（或 PowerShell 的数字列表）——整个粘回来就行。
  2. 步骤 B 的对照输出。
  3. 如果有步骤 C：终端截图 + 该次归档里的 terminal-output.txt。

  这些拿回来后，议题里的「六级未定论」就能收口，修复也就有了真机依据。


七、不做什么
------------------------------------------------------------------------

  · 不需要改 iBMC 的任何配置；
  · 不需要改生产节点的任何东西；
  · 全程只读，不写远端；唯一写的是步骤 C 那一次正常的工具运行，
    产物落在工具自己的历史目录里。
