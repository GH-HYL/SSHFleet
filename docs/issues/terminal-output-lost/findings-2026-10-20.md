# 终端明细看不到目标输出（2026-10-20）

Status: ready-for-agent

> **来源**：使用者 2026-10-19 用 Windows 连 iBMC 跑 `ipmcget -d health`，13 台全部「执行成功」，但终端明细里每台只有「连接 / 执行 / 分类」三行，命令输出**全是空白行**；同一批运行的 `terminal-output.txt`、`terminal-output.xlsx`、`results.xlsx` 里却有 `System in health state.`。
>
> **本文件是证据底本**：记「根因是怎么被定下来的、哪些方向已证否」。工单只写要做什么。

---

## 一、真机现象

| 去向 | 看到的内容 |
| --- | --- |
| 终端 | 每节点 3 行状态 + **空白**，输出两段显示成空行 |
| `terminal-output.txt` | `System in health state.`、`System Events:` / `16 major events.` 都在 |
| `terminal-output.xlsx` / `results.xlsx` | 内容都在（xlsx 侧替 CR 做了替换） |

**必然复现**，且只有少数命令出现；其余命令都正常。执行选项一致：`--no-sudo --no-shell --yes`。

## 二、链路

单条结果由 `ResultLine` 拼成一段文本，去向两个：

1. 写 `terminal-output.txt`（`fmt.Fprintln`）——**只写文件，不做任何解释**；
2. 打到终端（`tea.Println`）——**由终端按控制字符解释**。

两条链路吃的是同一段字节。所以「文件里有、终端没有」**不是渲染丢了内容**，而是终端把控制字符**解释**掉了。§1 里 xlsx 能看到内容，正是因为它多做了这一步替换（`cleanForExcel` 把 `\r` 换成 `\n`），而 txt 与终端没有。

## 三、复原实验（本机可控字节，`--no-shell` 原样下发）

远端回什么字节，工具就原样采集——用 `od -c` 看归档，**CR 一个不少**：

```
System in health state.\r\n==...
                       ^^^^^^^ 输出行末尾的 CR 原样进了 terminal-output.txt
（改动前的采集侧只按 \n 切行，不认 \r）
```

再把同一段字节按 Windows 控制台语义重放（一个 80×24 的屏幕模型，支持 `\r` 回行首、`\n` 换行、`\b` 退格、CSI 零宽）：

| 输出原文 | 终端实际画出来 |
| --- | --- |
| `第一行\r第二行\r` | **只有分隔线**——两行全被吃掉 |
| `System in health state.\r不健康` | `不健康tem in health state.`——前半截被覆盖 |
| 正常 CRLF 单行 | 正常显示（末尾的 `\r` 恰好无害） |

**结论**：会让输出「消失成空白行」的，是**输出中间或行尾的孤立 CR**；末尾恰好一个 CRLF 的单行输出不受影响。这解释了为什么只有那两条命令出现——它们的回显里带了 CR，其余命令不带。

## 四、已证否的方向

| 方向 | 怎么证否的 |
| --- | --- |
| 渲染器把内容丢了 | 读 bubbletea v1.3.10 的 `flush` / `stop`：只丢弃比自己短的行，不吞内容 |
| 进度界面把明细盖掉了 | `flush` 的 `CursorUp(linesRendered-1)` 在执行期间恒为 0（自首帧起就是 2 行）；`queuedMessageLines` 不会触发 |
| 输出字符串本身有问题 | 把归档原文整段重放，完整显示——送进终端的那段文本是干净的 |
| 工具改写了字节 | `--no-shell` 原样下发，没有改写点 |
| 与 `--yes` / 并发 / 连接快慢有关 | 13 台全成功、耗时正常；`--yes` 只影响「教学类提示不上屏」 |
| Windows 颜色能力导致（VT 未开时的「残骸」） | 程序自己开 VT；且该问题表现为残骸，不是空白 |

## 五、本次修复涉及的两处

1. **采集侧**：整备只按 `\n` 切行，`\r` 原样流向后继所有去向。已改为先归一（CRLF / 孤立 CR → LF）。
2. **呈现侧**：终端明细直接透传原始控制字符，没有「别让终端吃掉它」这一层。已改为把 `\r`、`\b`、NUL 等换成可见图示。

## 六、还没定论的部分（要真机才能收口）

- 本次只拿到 13 台里 1 台带事件输出（`.8`），且那份归档里**看不到任何控制字符**——说明出问题的那次运行，其归档只保留了「看起来正常」的那份文本，**原始字节已经丢了**。所以「CR 具体从哪来、是 CRLF 还是孤立 CR」**没有真机证据**，只有机制上的推理。
- 需要补的证据：在那条命令的原始字节里看到 CR。
- 取证方式（2026-10-20 定）：不走「让对方敲 `od -c`」，改走**日志**——本工具已把每台机器的「整备前原始输出」与「最终交给终端的文本」逐台记进 `history` 下的日志（见工单 03）。对方只需换掉可执行文件、照原来的方式跑一次、把日志发回来。理由：测试机会只有一次且由别人替我们跑，不能依赖对方会看二进制或愿意敲多条命令。
