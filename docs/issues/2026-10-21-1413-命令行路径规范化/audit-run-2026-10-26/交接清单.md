## 四、必须知道的背景

**被证伪的方向（不要再走）**：

1. **判断「路径有没有被改写」不能看 Windows 上的运行结果。** Windows 的 `os` 同时认 `\` 与 `/`，`-s A\b.sh` 与 `-s A/b.sh` 都能打开，改没改在那里看不出差别。要么在只认一种分隔符的平台上验，要么直接断言进入程序的那个字符串。
2. **不能拿上传模式的 `-p` 结论去推下载模式。** `-p` 的含义随模式反转，推出来的是相反结论。
3. **`TestParseDoesNotRewriteWindowsStylePath` 在 Windows 上是 SKIP，不是通过。** 它自己判 `runtime.GOOS == "windows"` 就跳过；把 SKIP 当证据会得出「已验证」的错觉。
4. **「日志里有 `r=` 就说明命令被受理」不成立。** 那行写在合规检查通过之后；命令被拦时日志里根本没有 `r=`，只能看终端报错。

**踩过的坑（方法，不传结论）**：验证下载失败那类场景时，只看「成功 / 失败」没有判别力——改前改后都可能是「失败」。要连**报错原文与回显路径**一起取。
