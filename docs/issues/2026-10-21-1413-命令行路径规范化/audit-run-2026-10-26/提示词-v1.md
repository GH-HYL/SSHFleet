**锚（ADR-0025 的决定）**：

- **A1**〔作者明示〕八个收路径的选项（`-s` `-u` `-p` `-d` `-f` `-a` `--convert-secret` 及打开加密时的 `--change-password`）**值一律原样交给系统**：不去两端空白、不换分隔符、不归一盘符、不做 `path.Clean`、不拼前缀。程序唯一的动作是「拦」。
- **A2**〔作者明示〕`-p` 是唯一随模式换库的值：上传＝远端语义、下载＝本机 `filepath`；`-d` 恒远端；`-s` / `-u` 恒本地；`--change-password` 打开加密时是本地文件路径、不打开时是密码本身。取文件名、取后缀这类动作**一律用与路径归属一致的那套**。
- **A3**〔作者明示〕远端两个值（上传的 `-p`、`-d`）不做任何加工，只判形态：**必须绝对、不含空白（含两端）、不含 `//`、不含 `.` / `..` 段**，四类都在参数阶段报出；值本身一个字节不改。
- **A4**〔作者明示〕`secret_dir` 只服务清单**第 4/6 列**（含 `-f` 的同一条内联记录），且**只在打开加密时**；关着加密时它既不参与补齐、也不做任何检查，写相对目录不拦人。
- **A5**〔作者明示〕清单**第 5 列**（私钥）**不拼** `secret_dir`、不展开 `~`、不去空白，原值直接交给 `os`。
- **A6**〔作者明示〕配置文件里的凭据路径必须写本机绝对路径，**不参与补齐**，配置侧不再调用补齐函数。
- **A7**〔作者明示〕报错分两层：**参数与前置检查阶段**（含 `-f` / `-a`、`--change-password` 凭据读不到）写「问题 / `原因：`系统原文 / `提示：`怎么改」三行；清单那一侧是逐行汇总、原文在行内；`main` 的三处 fatal 外层改成冒号收尾，**一屏只留一个「原因：」**。`sshfleet.<环境>.<环节>` 报文只服务执行阶段，本轮不动。
- **A8**〔**助手推导**〕传输层把文件落到目标目录时的**路径合成维持现状**；但远端取到的名字在本机写不下去时，**按下载失败报出**，不改名、不换目录、不静默落成别的名字。
- **A9**〔作者明示〕清单第 4/6 列的解析以 OS 库为核心：去首尾空白程序自己做；绝对性用 `filepath.IsAbs`；拼接用 `filepath.Join`；拼完用 `filepath.Clean` 复解析一次，此后只交 `os.Stat` / `os.ReadFile`；**`~` 不展开**。
- **A10**〔作者明示〕**不抬主版本**，记进 CHANGELOG 当天段的修订档（`[12.0.2]`）。
- **A11**〔作者明示〕用户给的值**不做转义**；拼远端命令时由程序用单引号整体包住，这层不动。

**锚质疑出口**：发现某条锚与源码、实测或上游 ADR（0002 / 0023）对不上，**不许改写锚，也不许并进普通发现**——另起一节「锚质疑」，写清哪条锚、哪份证据、按什么判。

**被证伪的方向（不要再走）**：

1. 判断「路径有没有被改写」**不能看 Windows 上的运行结果**——Windows 的 `os` 同时认 `\` 与 `/`，两种写法都能打开，看不出差别。要么在只认一种分隔符的平台上验，要么直接断言进入程序的那个字符串。
2. **不能拿上传模式的 `-p` 结论去推下载模式**——`-p` 的含义随模式反转。
3. **`TestParseDoesNotRewriteWindowsStylePath` 在 Windows 上是 SKIP，不是通过。**
4. **「日志里有 `r=` 就说明命令被受理」不成立**——那行写在合规检查通过之后。

**环境事实（已核的实测，不要自己再摸）**：

- Windows（`win32`）+ Git Bash；仓库根 `D:\Desktop\Code\SSHFleet`；`HEAD = 44fd1eb`（master）；`git status --short` 为空。

- 沙盒 `build\win-verify\` 在（exe、config、scripts、dl、history）。
- 禁止：`build-windows.bat`、改工作区任何文件、改 `modules\SSHFleet_Go\config\SSHFleet.conf`、把 WSL 里的 go 当 Windows 原生 go 用。

## 轴二 · 架构与跨模块不变量

**审什么**：

1. **唯一定义落点**：同一条规则是否只有一处定义。重点看这几个概念在几处出现、是否真的一致：
   - 「这条路径属于哪一边」（本机 / 远端）与对应该用的库（`path` vs `filepath`）；

   - 面向用户的配置文件展示路径；

## 轴三 · 判定与覆盖

**审什么**（判定/决策层的经典缺口）：

1. **多出的判定**——永远认领不到的分支：某条 `if` 的条件在真实调用路径上不可能成立；某个兜底分支不可达；某条错误码没有任何调用方会产出，却能进汇总。
2. **遗漏的判定**——永远归不了类的情形：某种输入落到哪个分支都不合适，最后按一个误导读者的类别报出去。
3. **优先级次序**：同一份输入同时踩两条规则时，报出来的是哪一条、是否是最该先说的那一条。
4. **旧概念撤净否**：被新规则取代的旧检查（字符串规范化、远端空格检查、`~` 展开、第 5 列补救）是否真的撤净——有没有哪条路径仍在用它，或留下一条只在注释里存在、代码里已无对应物的说法。
5. **计数与结果对象**：失败/成功数、明细行、`result.Error`、进度回调是否指向同一件事；出现一个失败时其余同类项还处不处理。

## 轴四 · 报错呈现与测试有效性

**审什么**：

1. **三行套结构**：锚 A7 要求「问题 / `原因：` / `提示：`」齐备。逐个报错点核：是否三行齐、`原因：` 后面是不是**系统原文**、`提示：` 是否真给了一条能照做的去路。
2. **系统原文的取法**：从 `*os.PathError` / `*os.LinkError` 里取内层，取不到时退回什么；会不会退出一条比原文更难懂的串；会不会把路径重复一遍。
3. **一屏只有一个 `原因：`**：`main` 的外层包装与内层的组合，在各类失败上实际拼出来是什么样（列出至少三种：配置加载失败、参数合规检查失败、`-f` 值既不是文件也不像记录）。有嵌套时是否真的只剩一个。
4. **清单侧形态**：逐行汇总时行号、列名、原文在括号里的位置是否与单值场景明显不同——会不会让读者以为是两套体系。
5. **测试有效性**：新增/改动的测试是否真能失败（断言是不是恒真）、期望值是字面量还是用被测同款算法重算、有没有为旧文案留兼容用例、`TestParseDoesNotRewriteWindowsStylePath` 这个既有的死断言（工单 06）现在到底什么状态。

**文件域**：`internal/cli` 的报错文案、`main.go`、`internal/credential/credential.go` 的文案部分、`internal/cli/*_test.go`、`internal/nodelist/nodelist_test.go`、`internal/config/config_test.go`。**不审**判定分支对不对（归轴三）。

**议题文档**：`spec.md` 的 Testing Decisions、`issues/04`、`issues/06`。
