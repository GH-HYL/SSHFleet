## 0. 一个会毁掉全部证据的环境坑（先记）

Git Bash 会把形似 POSIX 绝对路径的参数改写成 Windows 路径再交给程序：

```text
$ ./sshfleet.exe -f "1.2.3.4,22,root,pw" -d /var/log -p afile.txt
[ERROR] [function:cli] 选项/参数合规性检查未通过：-d 参数指定的远程路径不干净：不能含空格或制表符，当前值：C:/Program Files/Git/var/log
```

`/var/log` 被 MSYS 换成 `C:/Program Files/Git/var/log`，于是"含空格"。**后面所有实测都在
`MSYS_NO_PATHCONV=1 MSYS2_ARG_CONV_EXCL='*'` 下重跑**。这不是普遍现象（`-p /opt//app/` 这种带 `//`
的就没被换），但只认单个 `/` 开头的绝对路径（`-d /var/log`、`-p /opt/`）会被换。凡在 **Git Bash**
里验收远端形态检查的，不设这个变量就可能拿到 MSYS 的错；PowerShell 里跑没有这个问题。

## 2. 系统原文的取法与退化形态

- **取法**：`internal/cli/check.go:366-376`（`systemReason`）与 `internal/credential/credential.go:157-167`
  （`systemReasonOf`）同形——`errors.As` 命中 `*fs.PathError` 取 `pe.Err.Error()`，再试 `*os.LinkError`
  取 `le.Err.Error()`，都不命中则退到 `err.Error()`（原样全串，含路径）。
- **剥得对**：`open ./nosuch.enc: The system cannot find the file specified.` → `The system cannot find the file specified.`，
  实测见 §3（一条 `/` 都没剩，路径没重复）。`LinkError` 那两个路径也一并剥掉，方向正确。
- **退化形态**：非 `*PathError` 时原串上桌。`credential.go:256` 就是没走这个函数、直接用 `%v`
  的反例（J3）。
- **空值风险**：`systemReason(nil)` 会走最后一行 `err.Error()` → panic。现有调用点都在 `if err != nil`
  里，但 `check.go:96` 的 `_, dirErr := os.ReadDir(a.Path)` 没有任何非 nil 保证，靠"不是目录就必然报错"
  这一推断兜着（H1 的另一面）。

### 【硬伤 H1】`-p` 指向已存在的普通文件时，「原因」与第一行互相打脸，提示也对不上

- **位置**：`internal/cli/check.go:91-98`，关键在 `:96` 的 `os.ReadDir(a.Path)` 与 `:97` 的文案。
- **命令**：`./sshfleet.exe -f "1.2.3.4,22,root,pw" -d /var/log -p afile.txt`（`afile.txt` 是真实存在的普通文件）
- **原文**：

  ```text
  [ERROR] [function:cli] 选项/参数合规性检查未通过：下载模式：-p 参数指定的本地路径不是目录：afile.txt
  原因：The system cannot find the path specified.
  提示：这个目录要在本机上先建好，工具不会替你建
  日志：D:\Desktop\Code\SSHFleet\build\axis4-verify\history\SSHFleetTools.log
  ```

- **事实**：第一行说"不是目录"（存在、是文件），第二行说"找不到路径"（不存在），第三行让用户"先建好目录"
  ——三行各说一件事，照第三行做也解决不了（路径就在那儿）。
- **根因**：`:94-95` 的注释写明用意是"去要一句系统原文，不去编一句 not a directory 冒充它"。
  可 Windows 上 `os.ReadDir(<普通文件>)` 返回的是 `ERROR_PATH_NOT_FOUND`，不是 `ENOTDIR`；
  于是"借来的原文"跟要解释的事不是一回事。（Linux 上 `readdirent` 对文件返回 `ENOTDIR`→"not a directory"，
  这条是**推断**，本机跑不了，未实测。）
- **代价**：这是唯一一条"三行齐但整体误导"的报错，且正好落在最容易犯的错上（`-d` 的 `-p` 写成文件）。
  修法两选一：这条不引系统原文、由工具写死"这是一个文件，不是目录"（并附 `os.Lstat` 的模式信息），
  或保留探测但按 `errors.Is(err, syscall.ENOTDIR)` 分档、非 ENOTDIR 时不冒充系统原文。
  顺带说，该分支**没有任何测试**（`grep -rn "不是目录" --include=*_test.go` 只命中 verdict 的另一件事，
  见 §5.2/J9），所以一直没被发现。

## 5. 测试有效性

### 5.1 【硬伤 H3】两条以"旧文案"为判据的断言已经失效（恒真）

**(a) `internal/cli/args_test.go:777` 与 `:782`**

```go
if strings.Contains(err.Error(), "不能有空格") {          // :777
if err := CheckArguments(a); err != nil && strings.Contains(err.Error(), "不能有空格") {  // :782
```

`grep -rn "不能有空格" --include=*.go .` 只命中这两行与 `args.go:441` 的**注释**；生产文案本轮已改成
`check.go:327` 的「不能含空格或制表符」。所以 `TestPathSpaceCheckSkipsLocalPaths` 的四条子用例
（`:767-770`）**永不可能**命中该分支，整条测试对"本地路径被空格检查拦下"这一回归失去判别力——它现在恒绿。

实测这条测试的四个输入在程序里报的都是别的错，例如：

```text
$ ./sshfleet.exe -f "1.2.3.4,22,root,pw" -u "my file.txt" -p /opt/
[ERROR] … -u 参数指定的上传文件或目录读不到：my file.txt
原因：The system cannot find the file specified.
```

（"读不到"里没有"不能有空格"→ 断言通过。）修法：判据换成新的「不能含空格或制表符」，或干脆断言
`err == nil`/不报空格类错，别用文案当负向判据。**代价**：留着不改，任何人把本地路径重新纳入空格检查
都不会变红。

**(b) `internal/cli/answer_test.go:215`**

```go
if strings.Contains(err.Error(), "文件不存在") {   // 意图：别落到「文件不存在」那条
```

新文案是「文件读不到」，这个负向断言永远为假——同一类问题，严重度低一档（该用例的正向断言
`第 1 行不合规` 仍有判别力）。

### 5.2 【判断题 J9】清单侧"行内带系统原文"这一新行为没有任何断言

- **位置**：`internal/credential/credential.go:102`、`:106`、`:140`、`:144`（本轮把 `""` 换成 `systemReasonOf(err)`）。
- **事实**：`grep -rn "The system cannot\|no such file" --include=*_test.go .` 与

### 5.6 `TestParseDoesNotRewriteWindowsStylePath` 的真实状态与可触发性（定性）

- **状态：Windows 上 SKIP，不是 PASS。** `source_test.go:201-203` 自己 `t.Skip`：

  ```text
  === RUN   TestParseDoesNotRewriteWindowsStylePath
      source_test.go:202: Windows 的 `\` 本来就能被系统解析，这条钉的是「不做字符串加工」
  --- SKIP: TestParseDoesNotRewriteWindowsStylePath (0.00s)
  ```

- **可触发性：在 Linux 上能真红，判据是第一条断言。** 夹具在 `dir/nodes/a.csv` 造了真文件，
  输入是 `dir\nodes\a.csv`。若有人把 `\`→`/` 的改写加回来，`os.Stat` 会命中那个真文件 →
  `CheckArguments` 返回 nil → `t.Fatalf("原值在 Linux 上找不到，应报错…")`（`source_test.go:218-220`）。
  这条有判别力。
- **第二条断言偏弱**：`strings.Contains(cerr.Error(), winStyle)`（`:221`）之所以成立，是因为
  `source.go:102` 的格式串无条件插 `raw`；只要报错还走这条格式串，不管程序对值做了什么加工它都成立。
  真正抓"改写"的是 `cerr == nil` 那条，不是这条。
- **Windows 侧不是无保护**：本轮新增的 `TestParseKeepsPathValuesVerbatim`（`args_test.go:715-740`）
  直接断言 `Args` 四个字段逐字相同，`TestUploadPathErrorEchoesRawValue`（`:744-756`）断言报错回显原值，
  在 Windows 上都跑。所以"SKIP 就等于没测"这个担心在本轮不成立——但**这两条只覆盖 `Parse` 阶段**；
  若有人把加工加在 `CheckArguments` 的 stat 之前（`resolveSource`），Windows 上没有任何用例能发现
  （`\` 与 `/` 在 Windows 都能打开，这正是"被证伪的方向 1"）。Linux 上由 5.6 这条兜着。
- **工单 06 的 Comments 与代码不符**：「这条测试没有被删、也没有被跳过」（`issues/06` 第 25 行）
  ——它不是"没被跳过"，是**在 Windows 上一直跳**（跳过是原有的平台前提，但这句话写错了）。
  不影响裁定，属文档错误，见 §7。
