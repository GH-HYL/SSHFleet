# 使用错误提示整改 · 规格

Status: done（2026-10-15 三条工单全部完成，随 `[9.1.5]` 发布）

> 目的：把「使用者用错了工具」这一类报错，从**答非所问**改成**指得出他该改哪个字**。
> 范围只碰**面向使用者的报错文案与取值来源**；**检查逻辑本身（什么算违规）不在本次范围**。
>
> 事实依据：同目录 `audit.md`（2026-10-15 实测枚举，全部输出为实机抓取，非代码推断）。
> **本文件是实施依据**，商讨中每定一条落一条，不另开平行文档。

## 一、要解决的问题

审计枚举出的问题不是一类，是三类。**它们必须用三种不同办法处理**——这是本规格的核心判断，
也是「抽象处理不好抽、逐条细化又太乱」这个两难的出路。

| 类 | 是什么 | 规模 | 办法 |
| --- | --- | --- | --- |
| **第 1 类** | 文案本身没写清 | 约 10 条 | **单点改，不建机制** |
| **第 2 类** | 同一份文案被多个选项复用，复用处说不上话 | 1 处 × 5 个面 | **参数化**（照 `modeTable` 范例） |
| ~~**第 3 类**~~ | ~~该说的从没说过（使用者不知道 A/B 的区别）~~ | ~~确认屏~~ | ~~补在确认屏上，不是改报错~~ **（已撤销，见文末更新记录）** |

### 为什么不做统一抽象

报错原因彼此没有共同结构（「文件是二进制」与「选项不搭配」之间抽不出东西）。
硬抽会得到一个空壳模板，比现状更难懂。依据：规范 三、结构·2「**MUST NOT** 为『以后可能要用』预留抽象」。

### 为什么不逐个报错加判断、猜使用者意图

上一轮讨论过的「`-s` 失败时回头看像不像命令，像就建议 `-c`」**本规格不采纳**，理由三条：

1. **要猜**：`-s data.txt` 是想跑这个脚本，还是想把文件内容当命令跑？猜错给错建议，比不给更糟。
2. **治不了静默通过**：审计实测有 5 格**根本不报错**（如 `-c afile.txt`、`-s good.sh`），
   它们走不到报错分支，改报错文案对它们无效。
3. **有更可靠的替代**：使用者自己看确认屏就能发现敲错了，不需要工具替他判断。

**报错的职责只有一个：说清这次到底哪里不对。** 判断使用者意图不归它管。

## 三、第 2 类：参数化（本次的核心）

### 3.1 问题

`internal/cli/args.go:460` 的 `pathWithoutSpace` 被 **5 个选项共用**（`-s`/`-u`/`-d`/`-p`，
加 `-f` 的文件分支），但文案里**没有选项名**，举例固定写死 `-u`。实测四个面输出一字不差：

```
-s 值=my script.sh  →  路径参数中间不能包含空格 / 提示：…例如 -u "D:/my dir/app"
-u 值=my file.txt   →  （同上，一字不差）
-d 值=/var/my log   →  （同上）
-p 值=/opt/my dir/  →  （同上）
```

### 3.2 办法：照 `modeTable` 的参数化惯例

仓库现有 `modeTable`（`args.go:179`）就是「同一件事的多个名字收在一处，用时按 key 取」，
注释写明它的由来是「加一档模式原先要逐处核对 7 个点、手改 4 处」。

本条照此办理：**建一张「路径选项 → 它是什么」的小表**，报错时按传进来的那个选项取，
文案本身仍各自说话。

- 机制**只有一处**（改一处生效五个面）
- 文案**不抽象**（每个选项说自己的话）

### 3.3 硬要求

- **MUST** 由调用方把「当前是哪个选项」传给检查函数，**MUST NOT** 在报错文案里写死选项名。
- 提示里的举例**MUST** 用当前这个选项，**MUST NOT** 出现别的选项。
- 每条提示**MUST NOT** 给出做不到的出路。「加引号」对「值里带空格」是**假出路**
  （引号在 shell 层已被剥掉，加了也没用），**MUST NOT** 作为唯一出路给出。

### 3.5 空格检查收窄到远端参数

**这一条是判定口径变更，不是文案改动。** 它推翻了本规格开头「检查逻辑本身不在范围」那句。

`pathWithoutSpace` 被 `-s`/`-u`/`-d`/`-p`/`-f` 五个选项共用，且跑在**存在性检查之前**，
于是把七条本来更准的报错全部截胡（清单见 `issues/03-narrow-space-check-to-remote.md` 第一节）。

**正确的分类不是「路径参数」一类，而是「本地路径」与「远端路径」两类：**

| 参数 | 性质 | 能验存在性 | 空格检查 |
| --- | --- | --- | --- |
| `-s`/`-u`/`-f`/`-d 的 -p` | 本地 | ✓ | **去掉**——存在性验证更准 |
| `-u 的 -p`/`-d 的值` | 远端 | ✗ | **保留**——验不了，只能靠匹配拦 |

- **MUST** 让本地四个参数的空格检查去掉，交给各自的存在性验证。
- **MUST** 保留两个远端参数上的空格检查。
- 原始依据：`SSHFleet_py/src/core.py:96` 的注释「路径中间不能包含空格，**不是路径不能包括空格**」
  ——这条线当初就划过，代码没实现、Go 重写时连注释一起丢了。

### 3.6 验收

| 输入 | 改前 | 改后（要求） |
| --- | --- | --- |
| `-s 'cat /etc/os-release'` | 报空格，举例 `-u` | 报「脚本文件不可读：cat /etc/os-release」（自带答案） |
| `-u 'my file.txt'` | 报空格，举例 `-u` | 报「上传文件或目录不存在：my file.txt」 |
| `-u afile.txt -p '/opt/my dir/'` | 报空格 | **仍报空格**（远端，验不了） |
| `-d '/var/my log' -p ./adir/` | 报空格 | **仍报空格**（远端，验不了） |
| ~~`-f 'my list.csv'`~~ | ~~报「文件不存在」，提示只讲内联~~ | ~~提示补上「路径带空格时加引号」~~ **（已撤销：本地参数不再拦空格，且「加引号」是假出路，见 3.3 与 3.5）** |

## 四、第 3 类：确认屏补模式语义

> **本节已整条撤销（2026-10-15）。** 下面是当时的原始记录，保留以便看出当时是怎么想的，**不再约束本议题**——其中的要求与验收标准**MUST NOT** 照做。撤销缘由见文末《更新记录》。

### 4.1 问题

审计实测 14 格模式错配里，**5 格完全不报错**：

```
-c 'afile.txt'                        → 不报错，确认屏显示「执行命令: afile.txt」（本意是上传）
-s good.sh                            → 不报错，确认屏显示「上传模式」（本意是跑脚本）
--change-password 'cat /etc/os-release' → 不报错，当新密码收下，屏显 ca****se
```

且 **14 格里没有一格提到正确选项**——`-c` 与 `-s`、`-c` 与 `-u`/`-d` 的区别，
系统从没在任何一处告诉过使用者。

### 4.2 办法

**在参数确认屏上把模式语义写明**，而不是往报错里加判断。确认屏本就是给人复核的地方，
这是唯一能覆盖「静默通过」那 5 格的落点。

- **MUST** 让使用者在确认屏上看得出「这次到底要做什么动作」，与他的本意可对照。
- 现有确认屏已有「执行模式-→ 命令模式」这样的行（审计实测抓到了），**本条的增量是把语义说透**，
  不是新增栏目——具体形态留给实施时定，但**MUST NOT** 变成又一处需要维护的重复文案。

### 4.3 本条的处理次序

**放在第 2 类之后做**：第 2 类性价比高且改法已定，本条要先定确认屏形态口径。

## 五、第 1 类：单点改

### 5.1 不点名选项的条目（审计 3.4）

以下条目的文案里**通篇不含任何选项名**，使用者看到文件名却不知道是哪个参数带进来的：

| 位置 | 现状文案 |
| --- | --- |
| `check.go:136` | `%s 是二进制文件` |
| `check.go:139` | `%s 不是 UTF-8 编码` |
| `check.go:172` | `%s 是二进制文件` |
| `answer.go:91` | `%s 是二进制文件` |
| `answer.go:101` | `读取代填失败：%v` |
| `answer.go:104/107` | `读取代填失败：…第 %d 行格式读不了…` |
| `answer.go:116` | `代填文件 %s 第 %d 行不合规：%s` |
| `answer.go:124` | `代填文件 %s 里没有一条代填` |
| `answer.go:152` | `只有一列：缺触发词…` |
| `answer.go:156` | `触发词不能为空` |

- **MUST** 让每一条都说清「是哪个参数/哪个文件」出的事。
- 注意 `%s 是二进制文件` 在 `-s`、`-f`、`-a` **三处复用**，只有提示段不同——
  实施时按第 3.2 条同样的精神，或参数化、或各自写清，**MUST NOT** 留三份无从分辨的相同首行。

### 5.2 改法约束

第 1 类**一条一条改，不建机制**。

## 六、明令不动的部分

审计 3.5 实测确认**写得好**的一批，是本轮的对照基准，**MUST NOT 顺手改**：

```
-u 必须搭配 -p 参数使用        提示：-p 写文件要放到服务器上的哪个目录，例如 -p /opt/app/
-d 必须搭配 -p 参数使用        提示：-p 写文件要存到本机的哪个目录，例如 -p ./logs/
-p 不能搭配 -c 或 -s 使用      提示：只有上传、下载才用 -p；命令与脚本模式不需要它
-p 必须是以 / 结尾的目录        提示：-p 只表示"放到哪个目录"，工具不会替你改文件名
-u 指定的上传文件或目录不存在    提示：-u 后面要写本机上真实存在的文件或目录
-n/-t 参数格式错误             提示：给一个正整数（单位见该选项的说明）
不认识的选项：-x                （使用 -h 查看帮助）
```

其中 `check.go:71-74` 的 `-p` 那条是**范本**——它不只报错，还主动排除了「把 `-p` 当目标文件名」
的误读（ADR-0002 的消歧义约束）。**本轮第 1、2 类的改法应向它对齐**：这一条证明了
「点名选项 + 说清语义 + 给可行出路」在仓库里已有现成写法，不必另发明。

**依据**：红线 4——本轮范围外的问题只能报告，不许顺手修。

## 七、范围与约束

**在范围内**：`internal/cli/args.go`、`check.go`、`answer.go`、`passwd.go`、`interpreter.go`
的面向使用者报错文案与取值来源；参数确认屏（`internal/confirm/`）的模式语义说明。

**不在范围内**：
- 检查逻辑本身（什么算违规、什么该拦）——变更判定口径是另一件事
- 确认屏之后（执行期）的报错
- 工具/环境类故障报错（配置读不了、磁盘写不了等）

**约束**：
- 文案约束照规范 四、产出·4「使用者可见文案」：站使用者那边写、简洁干练准确、只写当下不写沿革
- 每批改动**MUST** 附改前/改后实测输出（规范 二、流程·3「交付要给证据」）
