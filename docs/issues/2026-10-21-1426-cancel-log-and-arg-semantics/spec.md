# 取消路径留痕与参数字段语义 · 规格

Status: 已完成（done）

> 来源：2026-10-21 对提交 `3febb0c`（改密显示面修正）的五轴审计。两件事都由那次审计翻出，按开发者当日裁定合在这一份里：① 当场修；② 本次不解决，只记录。

---

## Problem Statement

**一、取消之后，日志不说它为什么停。**

脚本后缀没配解释器时，工具会在开跑前问一句「继续用 bash 作为解释器吗」，默认否。使用者答「否」即终止：屏幕上有「已取消：脚本后缀没有配置解释器，本次执行终止」，**工具日志里却一个字都没有**——最后一行停在「选项/参数解析成功，解析结果：…」，看不出这是使用者自己取消的，还是程序半路出了事。

同一份日志里，另一条取消路径（危险命令确认答「否」）是留了 `[WARN] 执行已取消，SSHFleet工具已退出` 的。同类的事，两种待遇。

**二、一个字段兼着两种含义，下一次还会有人踩。**

改密参数 `--change-password` 的取值装在同一个字段里，它同时是两样东西：

- **模式判据**：非空即表示「这次是改密模式」，五选一的模式计数、归档目录名、超时默认值、批量管线分支全读它；
- **命令行原值**：装着使用者敲的那串字，而那串字在加密开关打开时是**密文文件的绝对路径**、关闭时才是密码本身。

2026-10-21 的显示面缺陷正是第二重含义造成的：参数确认屏、归档报告、工具日志三处都拿这个字段当密码显示，加密模式下落成了 `/h****xt` 这样的路径形态。那次已把三处各自改成取解密后的值，**但混淆源还在**——下一个改代码的人仍要自己分辨「这个字段此刻装的是密码还是路径」。

---

## Solution

**一、答「否」终止时，工具日志里留一条 `[WARN]`**，与危险命令取消同一口径：`执行已取消（脚本后缀没有配置解释器）`。屏幕文案、退出码、`[ERROR]` 前缀的处置一律不动。

**二、字段按含义拆开——本次不解决，只记录方向。** 模式判定改用独立的显式取值（本次是哪一种执行模式），命令行原值改名为一眼能看出「这是原值，不一定是密码」的名字。涉及十来处判定点与对应测试，需单独一轮，不塞进本次。

---

## User Stories

1. 作为运维，我答「否」终止一次运行之后，翻开工具日志就能看到「执行已取消（原因）」，不必再猜是不是程序出了问题。
2. 作为维护者，我希望工具里每一种「因为使用者取消而终止」的路径都在日志里留下原因，而不是有的留、有的不留。
3. 作为维护者，我希望改密参数的字段名自己就能说明「这是命令行原值，不一定是密码」，这样我给它加新用途时不会顺手把它当密码显示。
4. 作为维护者，我希望「这次是哪一种执行模式」由一个显式取值回答，而不是靠「某个参数字段非空」间接推论。
5. 作为使用者，我不希望这次修复改变任何屏幕文案、退出码或既有行为——我只想日志里多一行。

---

## Implementation Decisions

**一、留痕落点：主干调用「解释器回退确认」处就地写 warn。**

- 不塞进 `fatal` 的统一分支：各取消站点有自己的原因文案，参数确认屏那条取消已经自己写过 warn，统一处理会出现重复行。
- 不放进入交互器（`Notice` 只上屏、非交互下静默，是它既定的职责），也不改 `Interactor` 的对外形态。
- 文案口径沿用既有那条：「执行已取消（<原因>）」，原因写「脚本后缀没有配置解释器」。
- 取消仍属非致命终止：退出码 1、不加 `[ERROR]` 前缀、屏幕文案不变。这是 2026-09-14 的既有裁定，本次不动。

**二、字段拆分：本次不解决，记录已定方向。**

- 方向：模式判定与「命令行原值」分开，原值改名带「原值」字样；原值在加密模式下是路径这件事，写进名字能触达的地方（注释不够——注释不跟着签名走）。
- 范围：约十来处判定点（模式计数、模式名、默认超时、批量管线分支、日志回显等）与对应测试，属一轮独立工作。
- 不在本次动：三处显示点已经各自取对值，本项不修也不会再错，只是护栏。

---

## Testing Decisions

- 已有接缝已覆盖本项的判定点：「回退解释器确认答否 → 返回使用者取消」在 cli 层有测试。
- 日志那一行落在主干，**不新开测试接缝**（主干不可单测，为一行日志造一套进程级测试不划算）。验收靠工单里写的复现命令，改前改后各跑一次比对日志末尾。
- 字段拆分若将来开工，接缝在「模式名」这个既有公开取值上，不在字段名上。
