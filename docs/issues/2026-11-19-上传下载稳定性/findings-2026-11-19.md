# 上传下载稳定性：调研底本

- 日期：2026-11-19
- 用途：下一次会话继续讨论上传下载的稳定性；不是规格、不是工单，也不含实现。
- 状态：调研中，代码未动。

## 1. 诉求与背景

- 开发者对现有工具的功能设计满意，功能基本都不能去掉。
- 真正的担心是**上传下载的稳定性**。
- 想法：找成熟产品整体替换上传下载；如果没有合适的整体替换，就退一步，把其中一些传输步骤换成成熟库已有的能力。
- 边界：不为了换库改掉现有功能语义；如果必须改语义，要先由开发者拍板。

## 2. 结论先行

1. **协议层已经用了成熟库**：`github.com/pkg/sftp v1.13.11`（MIT，仍在维护）。SFTP 协议、包收发、并发请求、`StatVFS` 这些不是自己写的。
2. **没有成熟产品能整体替换且保住现有语义**。rclone、rsync、Ansible 都能传文件，但没有一个同时提供「重名不覆盖」「失败回滚本次已写」「sudo 暂存后 mv（这里是因为链接账号通常不是root，遇到没有权限的路径，可以先上传，靠免密sudo去mv移动，如果有传输工具，能够提权传输，就不需要曲线完成，我更希望看见这种）」「逐台四数」「按现有判据表分类」。
3. **可行的路线是保留语义，把传输步骤换成 `pkg/sftp` 已有的能力**。收益最大的三处：
   - 用 `OpenFile(..., O_CREATE|O_EXCL)` 做原子创建，去掉 `Stat` + `Create` 之间的竞态；
   - 用 `File.ReadFromWithConcurrency` / `File.WriteTo` 替换手写复制循环；
   - 非 sudo 的下载枚举用 `Client.Walk`/`ReadDir` 替换远端 `find -printf`。
4. 如果开发者愿意接受语义变化，rclone 是唯一能整体接管的候选；rsync 次之；Ansible/parallel-ssh 是整工具替换，不是可引用的库。

## 3. 现有语义（不能丢）

- **上传**：远端重名不覆盖，该文件计失败并终止本节点；失败删掉本次已写成功的文件；sudo 先写远端暂存目录再 `sudo mv`；写第一个文件前检查目标分区空间；链接类过滤并留名；逐文件进度。
- **下载**：按节点 IP 建本地子目录，保留远端相对层级；链接类过滤但列出；本机落不下的名字整批失败；写到一半的本地半成品删掉；不做整批回滚。
- **结果**：每台记录总文件数、成功数、失败数、实际传输字节数；失败分类按报文原文匹配配置，不按代码里的枚举。
- **进度**：逐节点面板，显示字节、文件数、速度；节点侧 500ms、聚合侧 200ms 两级节流。
- 也不是不可以接受变化，但需要提出来，让开发者抉择，是否值得放弃原来的设计理念，比如重名不覆盖，如果目标只是一个节点，覆盖就覆盖了，但这是批量工具，运维着数千节点，如果静默覆盖，那可能是灾难性的，不如提示出来，让使用者，自己去单独处理个别差异节点，重新补传更安全

## 4. 网上调研

### 4.1 rclone

- 定位：成熟的文件同步工具，MIT，单文件二进制，SFTP 是 Tier 1 后端。
- 对得上场景的能力：
  - `--sftp-server-command "sudo /usr/libexec/openssh/sftp-server"`：让 SFTP 子系统以 sudo 启动。
  - `--sftp-skip-links`：列举时跳过软链接与其他非普通文件。
  - `--transfers`、`--checkers`、`--sftp-concurrency`、`--sftp-multithread-upload`：并发传输与单文件多连接。
  - 校验、重试、`--stats`/`--progress`、`--use-json-log`。
- 与现有语义冲突的地方：
  - 默认会更新目标里变化过的文件，并普遍使用「临时文件 + 改名」；没有「失败后把本次已写的文件删掉」这一层。
  - `--ignore-existing` 是静默跳过，不是像现在这样报「远程文件已存在」。
  - `--sftp-server-command` 让整个 SFTP 会话以 root 跑，下载会连 root-only 文件也能读；现有约定是「下载仍以登录用户身份读」。
  - 逐文件结果要做日志解析才能接回现有 `TransferStat`；不是现成的结构化 API。
  - 作为 Go 库嵌入是可行的，但它是为自家 CLI 写的，官方文档主要面向命令行，嵌入方要自己拼 `fs.Fs`、配置和过滤。
- 结论：整引擎替换成本高，且会碰 ADR-0022、ADR-0026 和下载身份约定；适合「愿意改语义、换成熟引擎」的路线。

### 4.2 rsync

- 定位：增量同步与断点续传最成熟；`--partial`、`--append-verify`、`--ignore-existing`、`--rsync-path="sudo rsync"` 都能对上。
- 硬前提：**两端都要装 rsync**；Windows 侧还得带 cwRsync 或等价物。
- 与现有约定冲突：现在只需要 SSH/SFTP，引 rsync 就把「目标机只开 sshd 即可」变成「目标机还要有 rsync」。
- 结论：目标机环境完全可控时才值得考虑；不适合作为默认路线。

### 4.3 Ansible / parallel-ssh

- 它们解决的是「整台批量运维工具」，不是「给现有 Go 程序引一个传输库」。
- `copy`/`fetch` 模块的语义也不等于现有语义；换过去等于换掉工具的执行模型。
- 结论：不作为候选。

### 4.4 `pkg/sftp` 本身（最值得先看）

- `Client.Walk(root)`：递归遍历，底层是 `ReadDir` + `Lstat`，**不跟随软链接**，和现有「链接类过滤」方向一致。
- `Client.ReadDir(p)`：目录枚举，返回 `os.FileInfo`，可识别 `ModeSymlink`。
- `Client.OpenFile(path, flag)`：支持 `os.O_EXCL`，会映射到 SFTP 的 `SSH_FXF_EXCL`；文件已存在时打开失败，且不会跟随已存在的符号链接。
- `File.ReadFromWithConcurrency(r, n)`：显式并发上传，多个请求同时写不同偏移。
- `File.WriteTo(w)`：下载时默认并发读；只有 `UseConcurrentReads(false)` 才退回顺序读。
- `Client.StatVFS(p)`：空间预检已经在用。
- `Client.PosixRename(old, new)`：OpenSSH 扩展，原子替换目标；但它会覆盖已存在目标，和「不覆盖」冲突。
- 客户端参数：`MaxConcurrentRequestsPerFile(n)`（默认 64）、`MaxPacketChecked(size)`（默认 32KiB）、`UseConcurrentReads(bool)`、`UseConcurrentWrites(bool)`、`UseFstat(bool)`。
- 错误类型：`*sftp.StatusError` 的 `Code` 是导出的，`FxCode()` 可和 `sftp.ErrSSHFx*` 比较；比字符串匹配稳。
- `pkg/sftp` 不提供：断点续传、自动重试、远端校验和；这些仍要自己加，或者换 rclone/rsync。

## 5. 可替换的步骤（按稳定性收益排序）

### 5.1 远端创建：`Stat` + `Create` → `OpenFile(O_CREATE|O_EXCL)`

- 现在：先 `Stat` 判重，再 `Create` 写；两步之间目标机可能被别人建了同名文件，`Create` 会截断它。
- 换成：`OpenFile(path, os.O_WRONLY|os.O_CREATE|os.O_EXCL)`。
- 收益：判重和创建合成一个原子操作；`O_EXCL` 不会跟随已存在的符号链接。
- 风险：错误码要映射回现有的「远程文件已存在」分类；部分服务端只回 `SSH_FX_FAILURE`，需要保留预检做分类兜底。sudo 暂存路径也应同样用 `O_EXCL`。

### 5.2 上传复制：手写 `io.CopyBuffer` + 进度包装 → `ReadFromWithConcurrency`

- 现在：`io.CopyBuffer(dst, src, 1MB)`，`dst` 是 `*sftp.File`，外面包一层手写 `progressWriter`。
- 换成：`(*sftp.File).ReadFromWithConcurrency(progressReader, n)`。
- 收益：用库自带的多请求并发写；进度只包读取侧；短读、偏移、错误处理交给库。
- 风险：并发写失败可能在文件里留空洞；现有语义是失败即删文件，所以可接受，但要确认删除路径覆盖。`ReadFromWithConcurrency` 是显式并发，不依赖全局 `UseConcurrentWrites`。

### 5.3 下载复制：手写 `io.CopyBuffer` + 进度包装 → `File.WriteTo`

- 现在：`io.CopyBuffer(dst, src, 1MB)`，`src` 是 `*sftp.File`，外面包一层手写 `progressReader`。
- 换成：`(*sftp.File).WriteTo(progressWriter)`；进度包在目标 writer 上，不要包在源上。
- 收益：恢复库自带的并发读。当前包装器让 `io.CopyBuffer` 看不到源上的 `WriterTo`，并发读被绕开。
- 风险：`WriteTo` 内部会 `Stat` 文件；某些「读一次就删」的服务端会失败，可用 `UseFstat(true)` 或 `UseConcurrentReads(false)` 兜底。

### 5.4 下载枚举：远端 `find -printf` → `Walk`/`ReadDir`（仅非 sudo）

- 现在：远端 `find -printf 'F %s %P\n'`，按行拆；文件名含换行会拆错，且依赖 GNU find。
- 换成：非 sudo 用 `Client.Walk`；sudo 仍保留 `sudo find`，因为 SFTP 以登录用户身份读不到 root-only 目录。
- 收益：不依赖 GNU find；文件名含空格、换行不再拆错；链接识别交给 `Lstat` 语义。
- 风险：sudo 分支必须保留，不能一刀切；sudo find 若要继续用，建议改成 NUL 分隔输出并配 NUL 解析。

### 5.5 错误分类：字符串匹配 → `StatusError`

- 现在：失败原因写进报文原文，判定层再按配置匹配关键词。
- 可补：在记录事实时用 `*sftp.StatusError.Code`/`FxCode()` 区分「已存在」「权限不足」「空间不足」等，再生成同一条报文。
- 收益：分类不依赖服务端返回的英文原话。
- 风险：现有判据表按原文匹配是 ADR-0021 的决定；改成类型判定要单独评估，不能顺手改。

### 5.6 中断响应：只在文件之间检查 `ctx`

- 现在：大文件传到一半按 Ctrl+C，要等当前文件的 `io.Copy` 结束；`pkg/sftp` 的 `ReadFrom`/`WriteTo` 不带 context。
- 可补：`ctx.Done()` 时关闭 SFTP client，让复制立刻失败，再走现有半成品删除/回滚。
- 收益：中断响应及时。
- 风险：关闭连接会让当前文件留下半成品；删除/回滚路径必须能接住。

### 5.7 不建议为稳定性引入的

- **`PosixRename` 临时文件 + 改名**：最终路径确实不会出现半成品，但它会覆盖已存在目标，和「不覆盖」正面冲突；为它加占位文件又会让回滚更复杂。
- **为了提速调大 `MaxPacket`**：这是性能项，不是稳定性项；要按目标机实测，不能全局写死。
- **为了「以后可能要」抽一层传输接口**：现有语义已经够窄，抽象层只会增加维护面。

## 6. 方案对比

| 方案 | 代价 | 适合 |
| --- | --- | --- |
| A. 保语义，用 `pkg/sftp` 加固 | 断点续传、重试、校验仍要自己加；不引入新产品 | 功能不能动、只担心稳定性 |
| B. rclone 子进程 | ADR-0022/0026 要重写；sudo 身份与逐文件结果要适配；发布包多一个二进制 | 愿意接受语义变化，换成熟引擎 |
| C. rclone Go 库 | 依赖面和构建体积明显变大；嵌入层要自己维护；官方主要面向 CLI | 坚持单进程，又想要 rclone 能力 |
| D. rsync | 两端都要装 rsync；Windows 侧要带 cwRsync；不再只依赖 SSH/SFTP | 目标机环境完全可控，追求增量/断点 |

## 7. 待定问题

1. **「稳定性」具体指哪一格**：中断响应、重名竞态、枚举兼容、失败回滚、还是大文件传输速度？不同答案对应不同优先级。
2. **是否接受语义变化**：如果接受，rclone/rsync 才有意义；如果不接受，只能走 A。
3. **是否要加断点续传、自动重试、远端校验和**：这三样 `pkg/sftp` 都不提供；不加的话，A 路线解决不了「大文件断线重传」。
4. **本地同名文件是否允许覆盖**：下载现在用 `os.Create`，重跑会覆盖；手册没写死。若要防误覆盖，本地也要改成 `O_EXCL`，但会改变重跑行为。
5. **sudo 下载的身份约定是否要改**：现在「枚举用 sudo、读取用登录用户」；rclone 的 `--sftp-server-command` 会让读取也变成 root。这是一条产品语义，不是实现细节。

- 不要把「引用成熟库」理解成必须换引擎：`pkg/sftp` 已经是成熟库，重点是把它已有的能力用上。
