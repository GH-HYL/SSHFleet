## 三、逐字比对（一个场景，新旧两个二进制）

老工程 `modules/SSHFleet_Go_bak` 现编 `sshfleet_old.exe`，与新工程吃同一份清单、同一条命令（`-c "uname -s; id -un; echo done"`），各在自己的沙盒里跑。

## 四、没铺开的分支（已判不补，理由在后）

| 项 | 为什么不再补 |
| --- | --- |
| `--gen-key` 的真生成 | 真机上生成要覆盖本机唯一的主密钥，覆盖会让既有密文永久解不开；生成路径本身有三条用例盖住：`TestGenerateMasterKeyShape`（`credential`）、`TestGenKeyConfirmYesOverwrites`、`TestGenKeyWritesPersistedKey`（`keytool`），都绿 |
| 上传的目录树、软链接过滤、同名冲突 | 这轮只跑单文件；目录树、目标盘空间、回滚那几条在 `internal/execute` 的集成用例里，另有建站 07 那轮的历史验收 |
| 多台并发与 `-n` 的边界 | 只有一个节点；并发池与取消在 `internal/execute`／`interrupt` 的用例里，另有建站 06 的历史验收 |
| `sudo=true`／提权 | 目标账号没有 NOPASSWD，本次按 `sudo=false` 跑；提权路径在建站 04 那轮真机验过（沙盒已按天清掉，结论在该议题的 Comments） |
| 两张 xlsx 的逐格内容 | 内容由 `internal/report/xlsx_test.go` 判；这轮只确认产出 |
| POSIX 侧 `keytool` 三条进程级用例 | 2026-11-16 在 WSL 里跑过（那次之后 `docs/issues/未收尾清单.md` 才清空的） |

## 五、结论

三条门槛都过了：五站贯通绿、五模式与三条密钥子命令各跑通、A/B 比对无行为差异。没铺开的那些分支逐条判了不补（见上表）。**重构到此结束**，剩下的只是发布（开发者）与「老工程什么时候删」这一件由时间决定的事。
