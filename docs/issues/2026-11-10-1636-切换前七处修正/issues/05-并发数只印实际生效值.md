## Comments

**2026-11-10 收账**

- **三个读数点各是谁**：确认屏走 `message.concurrencyText` → `concurrencyValue`；`report.txt` 走 `message.stats.go` 那一行 → 同一个 `concurrencyValue`；执行期日志走 `execute/log_session.go` 的 `logSessionHead(lg, p, limit)`，`limit` 由 `execute/run.go` 算好（那里本来就写了 `if limit <= 0 || limit > len(p.Nodes) { limit = len(p.Nodes) }`）。
- **漂在哪**：只有 `concurrencyValue` 这一处不封顶——它只把 0 换成节点数，`-n 100` 原样返回 100。于是同一次运行里屏上 100、报告与日志 5。
- **改法**：`concurrencyValue` 改成「0 或比台数大 → 台数」，注释写明三处共读；不新造第二个换算点。执行站那一份不必改，它已经是封顶后的值——两处若各写一套封顶，就是同一判据两份。
- **被顶红的两条既有用例**：`TestConfirmScreenShowsGivenConcurrency`（`-n 4` 配 1 台）、`TestReportTextConcurrencyFromLedger`（「闸门改成了 3」配 1 台 1 节点）。它们要断言的是「指定了就印指定的数」，但台数不够，封顶之后必然印 1——**是场景不成立，不是判据错**。改法是让台数够大（`-n 4` 配 5 台；报告那条把 `Total` 一并给成 3），而不是把封顶退回去。
- **新增一档**：`TestReportTextConcurrencyFromLedger` 加「纸上比台数大（5）→ 印封顶后的 3」，钉的是老纸（闸门没封顶那种）进来也不许印原值。`TestConfirmScreenCapsConcurrencyAtNodeCount` 钉 `-n 100` 配 5 台印 5 且屏上不出现 100。
- 实跑：`gofmt -l .` 无输出、`go build`／`go vet` 干净、`go test ./...` 十七包全绿。
