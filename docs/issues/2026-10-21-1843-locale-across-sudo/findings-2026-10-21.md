# 排查记录：目标机输出语言在 sudo 边界丢失（2026-10-21）

> 本文件是 `spec.md` 的证据底本。它记的是**怎么查到的、哪些方向已经证否**，不是实施清单。
> 结论一句话：**工具确实下发了 `[env]`，`-a` 与普通路径完全一致；语言丢在 `sudo` 这一层**，系统间的表现差异来自各发行版 sudoers 的 `env_keep`、locale 数据与翻译包三件事。

---

## 一、起点

开发者报：`-a` 代填运行时，脚本里那部分「按环境语言输出」的内容中英混排，导致中文触发词没匹配上。当时怀疑：`-a` 这条路径没把配置文件里的语言设置带下去。

## 二、排查路径（按实际顺序）

| # | 做了什么 | 得出什么 |
| --- | --- | --- |
| 1 | 核对配置 → 参数载体 → 下发行的拼装链路 | `[env]` 在解析阶段就拼成 `Args.EnvPrefix`（`cli/args.go:425`），`-a` 的下发行装配时带上了它（`cli/answer.go:208`）→ `ssh/interactive.go:97` |
| 2 | 找齐所有拼装点 | 三处：`ssh/command.go:282`（`innerCommand`）、`ssh/command.go:425`（`scriptStdinInner`）、`ssh/interactive.go:97`；日志侧 `DescribeCommand` 复用同两个函数 |
| 3 | 用 release 二进制在沙盒里实跑，取真实下发串 | 沙盒 `build/probe-a-1/`，把 `credential.encrypt` 改 false、指向本机端口 1 让它连不上，只为了让它把下发行写进执行日志 |
| 4 | 对照 `-a` 与非 `-a`、`-s` 与 `-c` | 三种下发行的 `export` 段**逐字相同**（原文见第三节） |
| 5 | 换个方向找「混排」：本机 locale 齐不齐 | `locale -a` 只有 5 条，**没有 `en_*`** → 把配置里的 env 原样套上去，复现了中英混排 |
| 6 | 验「`C.UTF-8` 能不能当通用值」 | 不能：它是 UTF-8 编码的 C locale（提示恒英文），且 CentOS 7（glibc 2.17）根本没有这个名字 |
| 7 | 定位「为什么 CentOS 与 Ubuntu 不一样」 | sudo 的 `env_keep` 默认值决定 export 过不过得去（文档证据见第五节）；CentOS 侧未验证 |
| 8 | 验「设对 locale 是不是就全中文了」 | 不是：翻译包按程序缺失，同一 locale 下 `dpkg` 中文、`ls` 英文 |

## 三、证据 A：`-a` 的下发行里确实有 env

`-a` + `-s`（执行日志「最终命令」那行的原文；末尾的 `'\''` 是日志按 shell 引号规则转义后的写法，base64 段解出来就是脚本正文）：

```text
sh -c 'export LANG="en_US.UTF-8" LC_ALL="en_US.UTF-8" PATH="/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin" TERM="dumb"; sudo bash -c "$(printf %s IyEvYmluL2Jhc2gKZWNobyBoaQ== | base64 -d)" '\''t.sh'\'''
```

不带 `-a`（同一份配置、同一个脚本）：

```text
sh -c 'export LANG="en_US.UTF-8" LC_ALL="en_US.UTF-8" PATH="…" TERM="dumb"; sudo bash -c '\''. /dev/stdin'\'' '\''t.sh'\'''
```

`-a` + `-c`：

```text
sh -c 'export LANG="en_US.UTF-8" LC_ALL="en_US.UTF-8" PATH="…" TERM="dumb"; sudo bash -c "$(printf %s ZWNobyBoaQ== | base64 -d)"'
```

**读法**：三种形态的 `export` 段逐字相同，差别只在结尾怎么承接正文（`-a` 走 base64 进 argv，普通路径走 stdin，脚本模式多 `. /dev/stdin` 补 `$0`）。所以「`-a` 丢配置」这个假设当场被否掉。

## 四、证据 B：混排可以在完全不涉及 `-a`、不涉及 sudo 的情况下复现

本机 `locale -a`：

```text
C
C.utf8
POSIX
zh_CN.utf8
zh_SG.utf8
```

把配置里的两个值原样套上，跑一个探针脚本（自带一句中文 echo、回显 `LANG`/`LC_ALL`、调一句外部命令、末尾 `locale` 自检）：

```text
$ env -i PATH=/usr/bin:/bin LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8 bash probe.sh
bash: warning: setlocale: LC_ALL: cannot change locale (en_US.UTF-8): No such file or directory
脚本自带提示：请选择架构                                    ← 中文：脚本里写死的
LANG=[en_US.UTF-8] LC_ALL=[en_US.UTF-8]                   ← 变量确实是配置里的值
ls: cannot access '/nonexistent-path-xyz': No such file or directory   ← 英文：C locale
（末尾 locale 自检另有 3 行 “Cannot set LC_* to default locale”，略）
```

**读法**：变量设上了、程序仍说英文——因为 glibc 找不到这个 locale 就回落 `C`。**「配置生效」与「程序说哪种语言」是两件事**，这是整件事最容易看错的地方。

## 五、证据 C：sudo 那一层（文档证据，非行为实测）

本会话跑不了 sudo：`/etc` 被映射成 `nobody:nogroup`，两个实现都在启动检查处退出——

```text
$ sudo -n true
sudo: 无效的配置：/etc 必须属于 root                  # sudo-rs 0.2.14
$ /usr/bin/sudo.ws -n true
sudo: /etc/sudo.conf is owned by uid 65534, should be 0
```

所以这一节给的是文档与二进制证据：

1. **sudo 包自带的 sudoers 样例里，「保留 locale」那一行是注释掉的**：

   ```text
   $ grep -n "" /usr/share/doc/sudo/examples/sudoers.dist | sed -n '56,58p'
   56:## Locale settings
   57:# Defaults env_keep += "LANG LANGUAGE LINGUAS LC_* _XKB_CHARSET"
   58:##
   ```

   同文件里**未注释的 `env_keep` 只有一条**，是给 `visudo` 用的（第 46 行：`Defaults!/usr/sbin/visudo env_keep += "SUDO_EDITOR EDITOR VISUAL"`，`grep -nE '^Defaults.*env_keep'` 只出这一行）。即「保留 locale」是**可选项，默认不打开**。

   同一份样例第 51 行还有 `Defaults secure_path="/usr/local/sbin:…"`——它是 spec「顺带查出」里 `PATH` 那条的依据：`sudo` 默认会保留调用者的 `PATH`，但 `secure_path` 有值时**直接替换**掉它，于是 `export PATH` 拼在 sudo 之前等于没生效。

2. **`sudoers(5)`**：`env_reset` **关闭时**，「未被 `env_check` / `env_delete` 明确拒绝的变量才会从调用进程继承」——反过来读，默认开启时不继承。

3. **`sudoers-rs(5)`**：「`env_reset` 在 sudo-rs 里不可关闭；命令以**新的、最小环境**执行；HOME/SHELL/LOGNAME/USER 按目标用户初始化；DISPLAY、PATH、TERM 只有在 `env_keep` / `env_check` 允许时才保留。」

4. 与之相符的**说法**是：RHEL / CentOS 系的默认 `/etc/sudoers` 预置了 `env_keep`（`LANG LC_ADDRESS LC_CTYPE … LC_ALL LANGUAGE LINGUAS _XKB_CHARSET` 等，未注释）。这能解释「CentOS 上看着正常」——**但这条是发行版既有事实，本轮没有 CentOS 环境，未验证**（见第八节）。

**目标机自查（不需要改任何东西）**：

```bash
sudo sh -c "grep -v '^#' /etc/sudoers | grep env_keep"     # 有 LANG/LC_* = 这台保留
LANG=zh_CN.UTF-8 LC_ALL=zh_CN.UTF-8 sudo bash -c 'echo "LANG=[$LANG] LC_ALL=[$LC_ALL]"'
```

第二条打印空 → 不继承；打印出值 → 这台机器预置了 `env_keep`。

## 六、证据 D：同一个 locale 下也能混排（翻译包按程序缺失）

```text
$ LC_ALL=C.UTF-8     dpkg -l nosuchpkg ; ls /definitely-not-exist
dpkg-query: no packages found matching nosuchpkg
ls: cannot access '/definitely-not-exist': No such file or directory

$ LC_ALL=zh_CN.UTF-8 dpkg -l nosuchpkg ; ls /definitely-not-exist
dpkg-query: 没有找到与 nosuchpkg 相匹配的软件包        ← 中文：本机有 dpkg.mo
ls: cannot access '/definitely-not-exist': …           ← 英文：本机没有 coreutils.mo
```

本机 `/usr/share/locale/zh_CN/LC_MESSAGES/` 里有 `apt.mo`、`dpkg.mo`、`debconf.mo`，**没有** `coreutils.mo`、`bash.mo`。CentOS 的 coreutils 包据称自带 `zh_CN.mo`（即同一句 `ls` 在那边出中文）——**这条同样未在 CentOS 上验证**，只用来解释「两系统表现不同」的一半。

**结论**：语言 = f(sudoers 的 env_keep, 目标机是否生成该 locale, 目标机是否装了该程序的翻译包)。三层都不在使用者手里，「整批输出语言一致」靠配置 locale 是做不到的。

## 七、已证否的方向

| 假设 | 判定 | 依据 |
| --- | --- | --- |
| `-a` 没把 `[env]` 带下去 | 否 | 三种下发行的 export 段逐字相同（第三节） |
| `-a` 与普通路径的环境语义不同 | 否 | 只有 PTY、正文承载、stdin 归属三处不同，均不影响 locale |
| 换成 `C.UTF-8` 就能解决 | 否 | 它是 C locale 的 UTF-8 编码，提示恒英文；且 CentOS 7 无此名 |
| 设对 locale 就会整批统一语言 | 否 | 翻译包按程序缺失（第六节） |
| 是脚本自己写错了 | 否（至少不全是） | 变量与 locale 数据两层可以互相矛盾（第四节） |

## 八、未能取证的部分

- **sudo 的行为实测**：本会话 sudo 起不来（第五节），只能给文档证据 + 自查命令。要落成实测结论，得在真实终端或目标机上跑那一行。
- **CentOS 侧的一切**：本机没有 CentOS 环境，RHEL/CentOS 7 的 sudoers 预置 `env_keep` 属发行版既有事实，未在本轮验证。
- **开发者那台机器的翻译包清单**：只看了本机。

## 九、候选方案（未选定，供排期时评估）

| 方案 | 形态 | 代价与风险 | 备注 |
| --- | --- | --- | --- |
| ① `sudo env` 后置 | `sh -c 'sudo env K=V … bash -c "…"'` | 多一次 exec；`env` 由 sudo 按 `secure_path` 解析（POSIX 必有 `env`，默认 `secure_path` 含 `/usr/bin`）；长度几乎不变（少 `export ` 与 `;`）；改两处拼装函数 + `ExportPrefix` 多一个 `K=V` 形态；**日志与报告里的「命令行」形态随之变化**（兼容性档位见 spec 待定 4） | 不改目标机的前提下，唯一能「一次配置、全发行版生效」的做法 |
| ② env 塞进正文 | 正文第一行加 `export …` | 改用户脚本原文（行号、`$LINENO`、shebang）；`-a` 下用户可用体积被吃掉；日志「原始脚本」与实际不一致 | 否 |
| ③ `sudo -E` / `--preserve-env=` | — | 需 sudoers 的 `SETENV` 许可，默认被拒 | 否 |
| ④ 目标机加 `env_keep` | — | 每台都要改，几百台不现实 | 只作兜底文档 |
| ⑤ 只改 `[env]` 的值 | — | 只在 CentOS 生效，Ubuntu 依旧失效 | 半程 |

方案 ① 不碰既有约束的理由（逐条）：正文仍不进 argv（`-a` 的 base64 不变）／`$0` 补名形态不变／值的 `$` 仍由目标机在同一层展开／“量的串 = 发的串 = 日志的串”的单点性质不变（`DescribeCommand` 复用的是同两个函数）／`--no-shell` 分支不动／`-a` 的 120KB 上限不受影响。
