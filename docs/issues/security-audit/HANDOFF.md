## 二、任务背景

### 这是什么工具

SSHFleet 是**一次性执行的批量 SSH 运维工具**（Go，单可执行文件），不是 Web 应用。运行形态是"启动 → 解析输入 → 执行 → 退出"：

- 没有 HTTP 服务、不监听端口
- 本地几乎不执行命令（全仓仅 `credential/masterkey_windows.go` 一处 `exec.Command`，用于 Windows 下调 `setx`）
- 五种执行模式：命令 / 脚本 / 上传 / 下载 / 批量改密

### 开发者的真实场景（这决定了一切判断口径）

| 维度 | 实情 |
|---|---|
| 使用规模 | **2000 个节点**，各由不同业务维护 |
| 目标环境 | 高度异构，"什么问题都可能出现" |
| 本机 | 可靠，不考虑被攻陷 |
| 目标节点 | 可信，不考虑恶意主机 |
| **主要风险** | **脚本或执行目录被投毒**——脚本量大，人工看不全 |
| 解释器 | **可自由配置**，什么脚本都可能（`.sh` / `.py` / `.pl` / `.rb` / `.js` / `.php` / `.lua`） |
| 危险检测定位 | 开发者明确：只有 `forbidden` 档才该无条件拦，`high` 上提会误伤日常运维 |

**关键推论**：2000 台批量执行**必然使用 `--yes`**（否则确认无法点完）。所以任何"只在交互模式下生效"的机制，在真实场景中等于不存在。

## 四、待实施的问题（摘要，详情看 `final-report.md`）

### S1 + S2｜同一根因的两个方向（**高危，优先**）

**根因**：`dangercheck` 用 `mvdan.cc/sh/v3/syntax`（**shell 语法**）解析一切内容，而 `internal/ssh/command.go` 的 `interpreterTable` 支持 **15 种解释器**。

| 方向 | 表现 |
|---|---|
| **S1 漏报** | python 的 `os.system("rm -rf ...")` 完全不被检测，命令真的执行了 |
| **S2 误报** | 无害 python 脚本里出现 `rm -rf` 字样，被判成**「禁止」档** → `os.Exit(1)` → **整批作业一个节点都跑不了** |

**S2 的优先级高于 S1**：漏报是"没拦住"，误报是"全拦住且没有绕过手段"。

**建议方向**（见 `final-report.md` 第四节，三条路各有代价）：按解释器分流 / 明确声明边界 / 非 shell 时只做关键词扫描。**具体选哪条需要开发者拍板**，上游会话未做决定。

### S3｜`--yes` 下放行危险命令时终端无提示（中危，**改动量最小**）

`main.go` 步骤 5 里，`autoNote` 字符串（"非交互模式放行危险命令（最高级别 X，分类 Y，来源行 N）"）**已经拼好，只是没往终端送**。

改动量限于"把它往终端送一次"——不询问、不阻断、不改 `--yes` 语义、不改档位。

**注意**：上游会话确认过 `--yes` 下放行 `high`/`medium`/`low` 是**有意设计**且判断口径合理，**不要顺手把档位改了**（那是红线 4 说的"顺手发现的问题"）。

### S4–S7｜设计边界

都是**记录性质**，开发者已确认不按风险计或属已知边界。**除非开发者单独要求，不要动**。

**另有两项经复核为"实现完善、无需处理"**（`final-report.md` 第三节末尾有专节）：`--no-shell` 与 `--sudo` 的冲突提示（`confirm.go` 有三层保护）、清单脱敏（正常流程下有效）。**不要把它们当问题去改。**

1. **规范红线 1**：改代码前确认开发者说了「授权开工」。一次授权管一个阶段。
2. **规范红线 4**：实施 S1–S3 时**顺手发现的其他问题只能报告**，不许自己修。

4. **沙盒清理**：`build/atest-1/` 是当天沙盒，按规范"当天与昨天建的一律留着"，不必急删。
5. **CHANGELOG 规则**：若实施修复，按规范第四节改 CHANGELOG（只改顶部当天段落，不改已封口段落）。注意本仓库 CHANGELOG 有严格格式要求，动手前读那一节。

7. **上游报告的推断可能有错**：上游会话曾有三条静态推断被实测推翻并撤回（`xargs` 绕过、深度上限绕过、解析回退绕过）。**实施前若对某条结论存疑，照 `live-report.md` 的命令实测一遍再动手。**
