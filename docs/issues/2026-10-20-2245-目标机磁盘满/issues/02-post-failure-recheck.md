# 02: 传一半才失败时，把原因归到具体那一侧

**要做的**：上传写到中途失败时，工具再探一次两侧的可用空间——确实是那一侧装不下，分类就落在「目标磁盘已满」或「/tmp 空间不足」；两处都够，维持原来的分类（说明满不是这次的原因）。探测本身失败一律降级，不改上传结果、不新增分类。

**被谁阻塞**：01（分类名、报文名与判据都在 01 里建好）。

**状态**：已完成（done）—— 2026-10-27

**依据**：`../spec.md`「失败后再查」；决策理由见 ADR-0026

## 验收

- [ ] **卷只够放下第一个文件**：第二个文件失败 → 分类「目标磁盘已满」，同时回滚报文照旧出现（目标机干净）
- [ ] **失败另有原因**：目标目录不可写而空间充足 → 分类仍是「目标机写入失败」，不被改判成空间不足
- [ ] **探测本身失败**（服务端不支持、路径不可达、超时）→ 分类与没有这次探测时完全一致
- [ ] **撞名失败时的错误详情里不出现空间报文**（撞名、本地读不了、取消这三个出口都不探测）
- [ ] **需要量用「剩余未传量」**：已写过又会被回滚的部分不算进去；报文里不出现「没写过文件」那句
- [ ] 既有回滚八场景照旧全过（回滚范围与顺序未被改动）
- [ ] `go build ./...`、`go vet ./...`、`go test ./...` 全绿

## Comments

- 2026-10-27：**实现**。接线在写失败那一个出口，**放在回滚之前**——回滚会把本次写进去的删掉、把空间还回去，删完再探就永远「够」，满会被自己抹平。需要量两侧不同：目标侧是剩余未传量，暂存侧是剩下文件里最大那个。
- 2026-10-27：**验收里那条「卷只够放下第一个文件」按原样验不了**。预检（工单 01）已经把「总量装不下」挡在门外，所以「预检通过、写到一半才满」现实中只剩一种来路：别人同时在占这块盘。这条不是猜的——先按原样造，用例当场被预检拦下（报文里带 `no file written`），说明拦得对、场景本身不成立。工单改成两条可判定的验收：①判据直接调（`spaceShortAfterFailure` 喂数，确定性）；②并发占盘真机用例（`SSHFLEET_TEST_RACE=1` 才跑，默认跳过——它依赖时序，放 CI 里会偶发红）。后者连跑三次都过。
- 2026-10-27：**真机取证（同为 WSL2 / OpenSSH 10.2p1）**：并发塞 45MB 占盘后，30MB 的单文件传到一半失败，错误详情是 `sshfleet.transfer.target_space_short: …: 6.33 MB available, 40 MB needed; left to send`——没有 `no file written`，回滚报文照旧。
- 2026-10-27：**不改口的两条也验了**：往卷根（root 属主、普通账号不可写）传 1KB → 仍报 `remote_file_failed`，没有空间报文；撞名时错误详情里只有 `remote_exists` 与 `rolled_back`，没有空间报文——三个非写失败出口确实不探。
- 2026-10-27：`go build ./...`、`go vet ./...`、`go test ./...` 全绿；`-tags integration` 整套（含回滚八场景）在真机上全过。
