# 个人开发规范

**通用配置，适用于所有个人项目。**

**条款分三级：`红线` 违反即终止；`MUST` 逐字执行；其余为取向，按项目实际情况权衡。**

**程度词不是刻度。条款里出现「过多」「一件事」「过大」这类既无数值、又无列举的词时，含义是「依实际情况判断」——执行者遇到它**调 `/grilling` 问清楚**（见上节），不要自行补一个阈值再照做。需要严格执行的地方，本文件会直接写出可核对的动作或形态；没写出这种形态的，就不是硬约束。**

**未经要求的重构、依赖、设计模式、新增文件，一律不引入。**

## 怎么读本文件

**本文件是手册，不是每轮要背的清单。** 二百余行，按需要查，不必通读。

| 读什么 | 什么时候 |
| --- | --- |
| **第零节 红线（5 条）** | **要动手时对一遍**——每条自带适用场景，只在做那个动作时才需要看。**纯问答、纯查看不必过红线** |
| 其余各节 | **跳到相关的那一节看**——改 CHANGELOG 就看第四节，动结构就看第二节 |

**红线的权重高于本文件其余一切。** 后面各节的 `MUST` 再多，也不与红线同级：红线是「违反即终止」，其余是「按实际情况权衡」。

**红线不是自省清单。** 它不是「每轮回头检查自己有没有越界」，而是「到某个动作跟前时，看一眼这道门开不开」——动作没到，就想都不必想。

## 说不清时：调 `/grilling`，不要自己拿主意

**本文件要求你「先问用户」的地方不止一处，但「问」不是让你列一堆散问题，更不是让你在两个都说得通的方案之间反复取舍。**

**判断自己正处在哪种状态**：如果你发现自己在**来回权衡、反复推翻**，那多半不是你没想清楚，而是**目标本身就模糊**——此时继续想，只会越想越偏。**该做的是停下来问。**

**先做一件事：查既有口径。** 在认定「两个方案都说得通」之前，**MUST** 先看看代码里、ADR 里、既有实现里是不是已经有一个惯例把答案说出来了——**用户没明说的东西，既有的先例可能已经说了**。

> 实例（2026-10-13 实测）：某次改密提示的修法有 A/B/C 三案，执行者按本条停在原地等口径，空耗许久。事后它自己复盘：「A 之所以对，是因为下载侧那两条中间步骤本来就在失败时才记，改密那条无条件记是**唯一的不对称**——A 就是把改密对齐到既有口径。**这属于工程判断，不是目标模糊**：用户没说的，代码已经说了。」查过先例之后，B、C 根本站不住，**不是「两个都说得通」**。
>
> 判据：**先例找得到 → 按先例做，不必问；先例找不到、两条路真的都站得住 → 这才轮到下面那张表。**

**查完先例，确认仍然无解时，遇到下面任一条，MUST 调 `/grilling` 技能**，由它一轮一轮问到双方理解一致，再动手：

- **目标模糊**：你理解的做法的和本文件／用户说的方向对不上，各有各的道理
- **撞上程度词**：条款里出现「过多」「一件事」「过大」这类词，需要判断
- **该说定却没说定**：测试接缝、验收标准、改动边界这类必须事先讲清的东西还没讲清
- **两个方案都说得通**：需要用户在两者间选一个
- **取舍链条变长**：你已经在同一件事上权衡了三轮以上还定不下来

**MUST NOT** 用这些方式代替它：
- 自己挑一个「最合理的」继续干
- 自己挑一个「最保守的」继续干
- 把疑问攒到最后一次性甩给用户
- 在报告里写「我按 X 处理了，如果你觉得不对请告诉我」

> **理由**：模糊不清是**最贵的状态**——它既不产出结果，又持续消耗，最后还常常交付一个双方都不满意的半成品。`/grilling` 的价值在于它**给「问」这件事规定了形式**：一轮问几个、每个带推荐答案、答完再问下一轮。这比「有问题随时问我」可执行得多。
>
> **注意**：这条是**通用**的，不限于某个项目或某个环节——所有项目都用这套技能。

### 本规范的空缺，多半是「某个分支没写」

**这是本文件出问题时的第一诊断方向。**

当本文件说「先问用户」「说定之后再动手」，却**没说那个动作做不到时怎么办**——这个空缺一定会被执行者自己填上，而且填得通常**很有道理**（挑个最保守的、把未决项标记出来），所以你**事后很难发现**。

> 实例（2026-10-13 实测）：某次派出的子 agent 读到「测试接缝要先说定，没说定不写」，随即判断「我是派来的，问不了」，于是**自行选了保守口径就把 754 行测试写进了仓库**。它的推理链是自洽的：既要干活、又要守规矩，那就折中。**错不在它——是「问不了」这个分支本文件没写。**

**所以：遇到本文件没覆盖的情况，MUST NOT 自己折中。** 那不是「规范没管到、我可以看着办」，而恰恰是**该调 `/grilling` 的信号**——空缺就是本节要捕捉的那个状态。

**补本文件的正确姿势**：先问「这是缺一条约束，还是缺一个分支？」。**多数时候是缺分支**——照着加约束，只会让文件更长、而洞还在。

### 子 agent 问不到人时怎么办

**子 agent 没有与用户对话的通道**（`ask_user_question` 调不动）。它遇到需要用户定的问题，唯一的路是把问题回报给**主 agent**。回报之后怎么走，分两步：

1. **回报时把话说全**：问题是什么、有哪些选项、**你推荐哪个、依据是什么**。只丢一个问题过去，等于让主 agent 替你重新调查一遍。
2. **回报完不要空等。** 若判断自己**还能做只读的、不受该问题影响的工作**（把证据核到 file:line、把方案写到可执行、把不依赖该决策的部分做完），就**继续做**，别停在那儿反复权衡。

**MUST NOT** 用「回报完就静默轮询」代替干活——**空等和折中一样是白花的力气**，只是换了个形式。

> 实例（2026-10-13 实测）：某子 agent 报了三个方案、附了推荐，然后**空等七分钟**，其间什么都没做。它事后复盘：「正确做法应该是把『我倾向 A 及其证据』写成一份可执行的方案发出去，同时说明『若无回复我将按 A 执行并标注』，而不是静默轮询。」
>
> **注意**：这不等于给它自己拍板的权力。它**仍然不许在没授权时动代码**——只是不许把等待当成停工的理由。

**写得好的判据会自己长出执行手段。** 例如「期望值 MUST 独立于被测代码」这一条，实测中执行者据此**自发去做了变异测试**（改坏代码看测试红不红），本文件从没要求过变异测试。这说明：**判据要写清「为什么」，不要只罗列「做什么」**——前者能衍生，后者只能穷举。

## 总览：这套规范怎么用

本文件由三层叠成，三者不冲突，互为补充：

| 层 | 是什么 | 谁定的 | 改动权限 |
| --- | --- | --- | --- |
| **个人习惯** | 本机环境、目录落点、文案口味、工作节奏 | 长期用出来的 | 只增不删，除非本人明说 |
| **流程规范** | 一件事从想法到交付怎么走 | 总结出来的 | 可按工程设计调整 |
| **技能（skills）** | 流程上某些环节的具体做法 | 外部技能包 | 按需引用，不照搬 |

**主干流程**（一件事从头到尾的走法）：

```
想法 → 拷问成形 → 落成规格 → 拆成工单 → 实现 → 复查 → 回灌
        /grill-with-docs  /to-spec  /to-tickets  /tdd  /code-review  /retro
```

- 走到哪一步、这一步有没有对口的技能，**以本文件第五节为准**。
- 技能是主干上**某些环节的具体做法**，不是另一套并行规矩；技能与本文件冲突时，以本文件为准（红线 5）。
- 日常小活儿不必从第一格起，可以从中间的格子切入——第五节会说明每格的入口条件。
- **纯问答可跳过**：与代码完全无关的问答不受本流程约束。

## 零、红线（违反即终止）

> **每条只在它标明的场景下适用。** 场景没到就别管它——尤其别为了确认「我没违规」而回头自查一遍。

1. **开工以「授权开工」四个字为准，一次授权管一个阶段。**
   *适用：要写／改代码时。*
   - **说出口才能动手**：只有用户明确说出「授权开工」，才能开始写／改代码，不设例外；没说出口时只能读代码、梳理条目、报告发现、整理文档——问题再显然、改法再确定，也不得动手。
   - **阶段从「授权开工」起，到交付止**：我把这一轮活儿干完、该整理的整理完、把结果报出来，这个阶段就结束了。
   - **阶段内插进来的需求，不再重新授权**：干的过程中用户又提出新的改动（「那块也一起改一下」「这里改成这样」），照做——它落在同一个阶段里，不必再要一次「授权开工」。
   - **阶段结束之后再动，重新授权**：活儿已交付、用户又起新话题或新需求，哪怕改的还是同一个文件、还是同一件事的收尾，也要等下一次「授权开工」。
   - **文档不受此限**：ADR、手册、README、配置注释等说明性文字可以直接改（本文件除外，见第 2 条）。
   - **子 agent 不自行判断授权**：本条由**主 agent**负责——派活之前先确认授权状态，并在给子 agent 的指令里写明「本轮已获授权开工」或「只做只读分析」。**子 agent MUST NOT 自行认定已获授权**：它看不到开发者与本轮的对话，「用户」在它那里指向不明。指令里没有那句话时，子 agent 一律按**未授权**处理——给出方案并回报，由主 agent 向开发者确认，不得动手。
     > 由来：2026-10-13 实测。派出的子 agent 收到一句祈使句（「把它补充完善一下」），读了本规范、也对照了红线 1，仍直接改了仓库里 754 行测试——它无从区分「开发者授权」与「别人让我干活」。**这不是子 agent 的错，是本条原先依赖的人称在子 agent 场景下不成立。**
2. **未得明确授权，不得修改本文件。**
   *适用：要动本规范时。*
3. **不得绕过 `.gitignore`（禁 `git add -f`）**——已放行的文件在策略范围内可直接 `git add`，未放行的要先经用户确认。
   *适用：要 `git add` 时。*
4. **顺手发现的问题只能报告，不许自己修**——审计、排查、读码或做别的事时发现的、**不在本轮任务范围内**的问题（无论多小、多显然），一律先讲出来，由用户决定修不修、何时修。本轮授权范围内的事照做，不因此停手。
   *适用：发现了本轮范围外的问题时。*
5. **改缺陷前 MUST 先有复现手段**——指得出**一条已经跑过一次**的命令，它当场重现用户描述的那个现象；说不清「怎么算修好了」，就是还没到能动手的条件，此时只能报告「复现不了」并说明试过什么，**不得凭读代码猜出的原因直接改**。
   *适用：要改缺陷时。*
   - 复现手段优先取现成的：既有测试、程序自身的命令与开关、可重复的手工步骤。**MUST NOT** 为复现而在生产代码里加临时探针；确需临时桩子时放 `build/` 下的沙盒（见第一节），用完按沙盒清理规则办。
   - 现象是**间歇性**的（时好时坏、概率出现）时，判据从「每次都能重现」降为「有可重复的触发方式，且已知大致触发概率」。
   - 完整做法（如何把复现收紧成秒级、如何列假设、如何收尾）见 `/diagnosing-bugs` 技能。**本红线只管住那道门**：没有复现手段就不开工。
   - 非缺陷类改动（加功能、改文案、调结构）不受本条约束，仍按红线 1 的授权开工执行。

## 一、工作区结构

**提示：路径非强制，按工程需要选用**

- `modules/` 各语言工程，目录名 `项目名_语言`；旧工程（**只读不改**）为 `旧工程名_bak`
- `docs/` 规则文件、经验总结等需持久化的文档
- `tools/` 辅助脚本、打包工具 | `build/` 构建中间产物 | `release/` 最终可运行发布产物

### 构建产物不出工作区

- **MUST NOT** 把任何编译产物、测试临时文件写到工作区之外（含系统临时目录、`$TEMP`、`/tmp`、`~/` 下）。**MUST** 全部落在工作区内，构建中间产物放 `build/`、最终可运行发布产物放 `release/`
- 工具链的**编译缓存**走默认位置，不必指定（如 Go 的 `GOCACHE` / `GOMODCACHE`）——它可复用、不是产物
- 工具链的**临时目录 MUST 指到工作区内**（Go 用 `GOTMPDIR` 配 `TMP` / `TEMP`），跑 `go test` / `go build` 之前先设。那个目录里放的是**编译出来的可执行文件**（如 `go test` 的 `<包名>.test.exe`），不是缓存——落在 `$TEMP` 下会被本机 360 当木马删掉，现象是构建／测试莫名失败且不报原因（2026-10-09 实测：`go test` 报「木马文件 `%TEMP%\go-build…\config.test.exe`，已成功拦截」）。指向 `build/` 下当天那个沙盒即可
- 验证/试验用的临时沙盒放 `build/` 下的子目录，**必须清理，但不必建完就删**——同一个问题常要来回验几轮，留着能直接复用；建一个删一个，下一轮又得重建，反而费事
- 多个沙盒用编号区分先后（`build/atest-1`、`build/atest-2`…），当天新建的排在最后，一眼看得出新旧
- **清理按天**：当天与昨天建的一律留着；第三天开工先扫一眼 `build/`，把前前天及更早的沙盒整个删掉，保留昨天和今天的，用与参考借鉴
- 沙盒里常含临时凭据，**MUST NOT** 进版本库；它不在 `.gitignore` 的放行名单里，正常 `git add` 带不走；非root的临时账号凭据等信息可以暂时保留，这些信息不是特别敏感，只要不扩散即可
- 理由是环境约束不是洁癖：本机装了 360，工作区外的可执行文件会被静默删除——构建命令不报错、产物却不见了，排查成本极高

## 二、工程结构（仅 `modules/` 下的 Go、Python 工程）

- 入口文件放工程根目录，**以入口为中心的集中式编排架构**（初始化 → 运行 → 退出）；其余文件均为其中某个环节的分支实现，由入口统一调用并回收结果
- **MUST NOT** 在子模块反向驱动主流程（回调控制生命周期、全局状态跨模块流转）
- 根目录**必须**建 `src`（Py）/ `internal`（Go）：其内只建功能目录、不放散文件，且**必须**含 log 模块
- 代码按功能分目录存放。文件需要拆分时，按**功能边界**拆——**不按行数**机械切割

### 模块化

- **模块** = 代码的最小可独立引用单位（Go 的 package、Py 的模块目录）
- 模块内各文件的用途，应能被一句独立的话说清
- 判断该不该**动结构**（拆包、并份、移函数、删死代码）：只看当下**指得出来**的事实
- 明确**不算**理由：观感类（看着乱、更好读）、预测类（以后可能要用）、度量类（行数变少、更好接测试）
- **MUST NOT** 读写他模块的**包级可变状态**（全局变量、模块级可变对象）
  - **判据是「有没有人真的写它」，不是「语法上能不能写」。** 常量性质的查找表、哨兵错误这类**约定不改**的包级值不在此列——例如 `ErrHelp`、`modeTable` 这种建好就只读的，读写它们不算违规。**MUST NOT** 拿本条去要求把这类值也塞进函数里。
- 接新环节优先**新增**实现文件；**MUST NOT** 靠给既有模块加 `if` / `switch` 分支来接入
  - **它防的是「最小改动」本能**：AI 加功能时倾向于在既有代码里塞几行，一次无害，十次之后同一个 `if / switch` 会串成一长排，且**新功能散落在五六个文件里**，出问题难找、改一处怕碰坏别处。
  - **例外出口**：如果加分支**明显更合适**——比如只有三五行、确实属于同一个功能多出的一种情况——**先说出来**由用户定，**MUST NOT** 默默加、也 **MUST NOT** 因为本条就把该合并的东西硬拆成两个文件。

### 可扩展 / 低耦合

- **MUST NOT** 为「以后可能要用」预留抽象，或引入设计模式、框架。**是否属于「以后可能要用」由用户判定，不由执行者推测**；除非明确预留需求，否则只看**当下**
- 这里的「依赖」指**运行期依赖**（会进产物的）。本地工具链的配置不在其内——lint、格式化、构建脚本这类可以直接加。
- 发现缺陷可以排期整改，但**不得据此发起未授权重构**——红线 1 管的是所有改动，包括「顺手改」。
- 判断耦合，逐条核对下面三件，**不数依赖个数**；三条都答「否」即为健康：
  1. 每个依赖是否必要——是否只用了对方少数几个字段，却把**整个对象**传了进来
  2. 有没有实际发生过「改了 A 不得不改 B」
  3. 是否读写了对方的包级可变状态（**能写的**那些；只读查找表与哨兵值不算，见上）

### 代码怎么写

> 本节管**动了之后代码长什么样**，与上面管「该不该动结构」的几条分开。

- **测试只写在预先说定的接缝上。** 「接缝」＝从外面调用就能观察到的那个口子（公开函数／命令入口／进程出入口）。动手前先把「这回测哪个口子」跟用户说定，**没说定不写测试**。
  - **说定不了时的兜底**：**MUST NOT** 自作主张挑一个「最保守的」口径就开写。**改调 `/grilling`**（见开头「说不清时」一节）——把你打算测哪几个接缝、各覆盖什么摆出来，由用户定。这条同样适用于**子 agent**：它无法与用户当场说定，所以子 agent 收到的写测试指令，默认按「接缝待定」处理，除非指令里已明确写了接缝。
    > 由来：2026-10-13 实测。子 agent 明说「无法与你当场说定」，然后自己选了保守口径继续写——**结论碰巧合理，但那是运气，不是规则的功劳**。规则要求「先说定」却没说「说定不了怎么办」，就会退化成本条要防的那种自作主张。
- **MUST NOT** 测内部实现：不 mock 自己写的模块、不测私有函数、不断言内部调用次数、不绕过接口去查旁路。判据：**重构后行为没变，测试却红了**——那说明测错了地方。
- **期望值 MUST 独立于被测代码**：用已知的正确字面量、手算样例、或规格里的数；**MUST NOT** 用和被测代码同样的算法把期望值再算一遍——那样按构造必然通过，永远不可能和代码不一致。
- **一次一个纵切**：一个测试 → 一点实现 → 再下一个。**MUST NOT** 先把测试全写完再写实现（批量测试验的是**想象的**行为，不是真行为）。
- 循环怎么转（先红后绿、一次一片、重构不掺在循环里）照 `/tdd` 技能走；本节只固定上面几条不能含糊的。

## 三、Git 提交

- 提交信息**必须中文**，格式 `类型(可选作用域): 简短描述`；类型 `feat` | `fix` | `refactor` | `docs` | `chore` | `style` | `test`
- 功能完成且文档整理完毕后，自动提交
- **提交信息只放「做了什么」，不放「为什么」**——**标题**保持一行 `类型(作用域): 简短描述`，**MUST NOT** 为了塞理由把标题撑开成一整段。
- **「为什么」写正文**：标题下空一行，可写一到两句说明取舍或原因（git 的标准形态，`git log` 默认不显示、`git show` 能看到）。这是**中等改动**的去处——比一句话复杂、又够不上开 ADR 的那些。
  - **按分量分去向**：**大决策** → ADR（见第七节）；**某件事的过程与结论** → 该工单的 `## Comments`（见第五节）；**调试类修复** → 把最后确认的那条原因写进工单 Comments，让下一个查的人直接看到；**其余** → 提交信息正文。
  - **MUST NOT** 把正文写成流水账或改动清单——那份东西 `git diff` 已经有了；正文只写**从 diff 里看不出来的**（为什么这么选、放弃了什么、踩过什么坑）。
- `chore` 多半会碰到新文件（配置、脚本、杂项），**与红线 3 是同一个口子**：新增跟踪文件前先确认 `.gitignore` 覆盖是否完整，未放行的先经用户确认。

## 四、CHANGELOG 与版本号

**只记用户能直接体验到的**功能新增、体验优化、问题修复。 **不记**：内部代码符号（函数 / 变量 / 模块 / 文件名）、实现细节与重构拆分、测试与构建工具链。

**两个概念分开**：版本号 = 功能基线（人工定，当天可抬）；构建标识 = 哪一次代码（自动注入，不用管）。

### CRITICAL: 读取方式

**MUST** `Read(file_path="CHANGELOG.md", limit=60)` 部分读取后再编辑（部分读取同样满足 Edit 的前置要求）。只改**顶部当天那一段**，**MUST NOT** 编辑任何**已封口**的段落。

### 版本号

- **一天一段，段头即版本号**：`## [x.y.z] - 改动发生当天`。开段前先扫当天有无段落——有则记入该段（必要时抬号），无则开新段；**MUST NOT** 为同一天另起第二个号，也 **MUST NOT** 用「待定」这类无号段头
- **号取段内最高档位**：不兼容改动 → 主版本；有新增 → 次版本；只有修正 → 修订。当天出现更高档位 **MUST** 当天抬号，**MUST NOT** 下调
- **「不兼容」怎么判**：只问一句——**升级之后，使用者拿着他原来的配置、原来的命令，还能不能照旧跑起来？** 跑不起来（当场报错、静默换个行为、结果与他预期不同）就是不兼容，主版本；照旧跑得起来，就不算，按新增／修正判
  - **判的是使用者的东西，不是代码**。使用者手里只有三样：**配置文件、命令行参数、脚本／清单这类输入文件**。改这三样中的任何一样的**名字、格式、取值含义、必填性**，都算；改代码内部结构不算——他看不到包怎么分、函数怎么拆
  - **算的**：删掉或改名一个选项／配置字段（旧名不再接受）；配置里新增必填字段（旧配置直接报错）；某个字段的取值语义变了（如三态压成两态）；默认行为变了、旧命令跑出不同结果；规则文件改名或换了查找位置；输出结构变了而使用者的脚本要解析它；目录／文件名改了而他写进了自己的脚本
  - **不算的**：内部重构、包结构调整、函数改名；新增选项或新增可选配置字段（旧的照旧能用）；只改报错文案、日志措辞、界面排版；修 bug 而修的是错的行为；补文档
  - **拿不准就按不兼容算**——代价不对称：多抬一次主版本只是号大一点，漏抬一次则**使用者的东西坏了却没有任何提示**
- **当天可改，过天封口**：**当天**对同一件事继续修改（措辞不准、形态又变了、补漏），**MUST** 直接改当天那一段的原文，**MUST NOT** 追加第二条平行描述、也 **MUST NOT** 留「此前写法是……现已改为……」这类历史沿革——CHANGELOG 记的是**最终形态**，不是修改过程。理由：当天段落尚未对外发布，读者只需要知道这个东西最终长什么样，不需要知道中间改了几版
- **封口条件**：第二天动手即视为上一段已封口，开新段；已封口段落 **MUST NOT** 再改（含号与日期）。段头日期 = 改动发生当天，不因之后的任何动作改写
- **改不动就新开条目**：当天修改若已超出原条目的描述范围（不再是同一件事，而是另一件事），则保留原条目、另起一条，**MUST NOT** 把两件事糅进一句话
- **同一个号落两处**：CHANGELOG 段头 + 程序入口的版本常量，**MUST** 在同一次提交里同步改——两处不一致即为错误

### 程序里的版本显示

- 帮助信息（`--help` 或无参运行）**MUST** 在首行下方单独一行显示版本号，值取自程序入口的版本常量——**MUST NOT** 另立第二处版本来源
- **MUST** 在同一行附上构建标识，形如 `版本: v<版本号>+<短提交号> (<提交时间>)`。`<短提交号>` = 构建来源的 git 短提交号（工作区有未提交改动带 `-dirty`），括号内为该提交的时间
- **MUST NOT** 手工维护构建标识，也 **MUST NOT** 由打包脚本向程序注入版本或时间：能自动注入的平台（如 Go 在仓库内 `go build`）就用自动注入，取不到时退化为只显示版本号
- 问「这是哪一次代码」**以构建标识为准**，不靠版本号——同一天可能编译多次，号相同而构建标识不同即由此区分

### 发布包

- 包名用时间戳（`项目名_yyyy-MM-dd_HH-mm-ss_平台`），只用于区分前后两次打包
- 包名时间戳是**打包时刻**，与构建标识的**提交时刻**不同源，**MUST NOT** 用于定位代码
- 工作区有配套的打包、发布脚本，如bat文件存在，但不必关心脚本具体实现逻辑

## 五、主干流程

**一件事从想法到交付的走法。** 每格写清：什么时候进这一格、这格产出什么、有没有对口技能。

**技能是某一格的具体做法，本文件是流程本身。** 两者冲突时以本文件为准（红线 5）。

### 什么时候必须走流程

- 一轮对话**干不完**的（要跨会话、要分几次交付）——**MUST** 先落规格与工单，再动手。
- **一轮能干完的小活**（改一处文案、修一个明确的小缺陷）——不必起规格，但**红线 1（授权）与红线 5（复现）照样管**。

**「一轮干不完」怎么判（别凭感觉，对着下面数）：**

| 数到的现象 | 判定 |
| --- | --- |
| 改动**跨两个以上模块／包**，且其中一个不是纯粹的调用点适配 | 跨轮——先落规格 |
| 要**删或移**既有公开符号（导出函数／类型／包） | 跨轮——先落规格 |
| 得先**做一轮调查**才知道要改什么 | 跨轮——调查本身就该落成工单 |
| 要分**几批**交付、每批各自能独立验证 | 跨轮——先落规格 |
| 上面都不沾：一处逻辑（或一处逻辑 + 跟着它的手册／CHANGELOG 措辞），改完当场能验证 | 小活，直接做 |

**「跟着它的手册／CHANGELOG 措辞」不算额外批次**——那是一次改动的自然配套，不是另起一件事。

**拿不准时按跨轮处理。** 代价不对称：多写一份规格只是白花点功夫；该起规格而没起，跨轮的工作就没有载体，下一轮接不上。

**这条判据只管「起不起规格」，不管「能不能动手」**——授权是红线 1 的事，先复现是红线 5 的事，各管各的。

### 主线七格

| # | 这一格 | 什么时候进 | 产出 | 对口技能 |
| --- | --- | --- | --- | --- |
| 1 | **想法** | 有个说不清、还没定型的念头 | —— | —— |
| 2 | **拷问成形** | 想法在脑子里，但细节没想清 | 定下来的决策 | `/grill-with-docs` |
| 3 | **落成规格** | 定了，且一轮干不完 | `docs/issues/<slug>/spec.md` | `/to-spec` |
| 4 | **拆成工单** | 规格写完 | `docs/issues/<slug>/issues/NN-*.md` | `/to-tickets` |
| 5 | **实现** | 工单在手 | 能跑、已验证的代码 | `/tdd`，逐条走 `/implement` |
| 6 | **复查** | 代码写完 | 两份报告：规范符合度 / 规格符合度 | `/code-review` |
| 7 | **回灌** | 交付之后 | 本文件或 `AGENTS.md` 的改动 | `/retro` |

- **小活儿从第 5 格切入**：改动明确、一轮能完，直接实现。抠不动的设计问题**可以退回第 2 格**问一轮，不必硬猜。
- **想不清的大活儿可以退回第 1 格**，走 `/wayfinder` 先把雾推开再回来。
- **一格没走完不进下一格**——尤其第 4 格：工单没拆完就开工，等于把规格又猜了一遍。

### 各格的硬要求

- **第 3 格（规格）MUST 落到 `docs/issues/<slug>/spec.md`**，载体与字段以 `docs/agents/issue-tracker.md` 为准（一个功能一个目录；工单一条一个文件；状态写顶部 `Status:` 行）。
- **第 4 格（工单）MUST 一条一个文件**，编号从 `01` 起，标出 `Blocked by:`。**MUST NOT** 合并成单个工单文件。
- **工单是竖切不是横切**：一条工单要切穿「改到的每一层」，做完能独立验证；**MUST NOT** 按「先做完全部数据层、再做完全部界面层」这样横着切。
- **第 5 格（实现）**：缺陷走红线 5 先复现；测试写法按第二节「代码怎么写」。
- **第 6 格（复查）MUST 分两轴看，不许合成一个结论**：一轴看「符不符合本文件」，一轴看「对不对得上规格」。两轴会得出相反结果（完全合规但做错了事、完全做对事但坏了规矩），**合起来看就会互相掩盖**。
- **第 7 格（回灌）产出的是本文件或 `AGENTS.md` 的改动**，不是代码改动——复盘看的是「下次怎么少犯」，不是「这次哪里错了」。

### 交付要给证据

报「做完了」时**MUST** 给得出可核对的东西，至少一样：

- 命令 + 它的实际输出（改前 vs 改后）
- 或者：哪条命令改前是红的、改完绿了

**MUST NOT** 只写「已修复」「已实现」了事。理由是红线 5 的下半段——能复现才叫开工，那交付时自然也要拿复现手段收回场。

### 复盘（第 7 格）看什么

照着 `/retro` 的分类找：**找不到文件**（要不要加导航指针）、**机械错误**（能不能变成自动检查——lint、类型检查、CI）、**判断类错误**（要不要进本文件当条款）、**白花的力气**（哪些工具调用是浪费的）、**失效指令**（本文件里有没有说了等于没说的条款）。

> **分类原则**：机械错误交给**自动检查**，判断类错误才写进**本文件**。凡是 lint / 类型检查 / CI 能机械抓住的，**MUST NOT** 只写一条规矩了事——规矩靠自觉，检查靠机器。

## 六、使用者可见文案

**使用者**指工具做出来之后用它的那个人（本文件其余条款里的「用户」仍指发布指令的人）。

- **一律站在使用者那边写，不站开发者角度**：假定读者没用过这套工具的源码、也不懂它是怎么实现的——凡是要靠内部知识才看得懂的说法（模块名、函数名、库名、内部步骤、行话），一律换成他的语言；一件事讲不清，就先想他此时要做什么，再写他做的那一步
- 一切使用者可见的描述信息——配置注释、帮助、报错、提示、文档——**MUST** 写得**简洁干练准确**：不写解释、铺垫、车轱辘话。判据：删掉这句，使用者不会少知道一件他需要知道的事，就删
- **只写当下，不写沿革**：使用者可见面描述的是**这东西现在是什么样、怎么用**——**MUST NOT** 出现「此前是……」「以前叫……」「现已改为……」「不再……」这类历史。使用者是从这份文档开始用工具的，他既不知道也不关心它改过几版；删掉沿革那半句，他不会少知道任何事。**新增功能按「它本来就这样」写**，不交代它替代了什么
- **沿革有它该待的地方**：决策与备选 → ADR；变化本身 → CHANGELOG（记最终形态，见第四节）；为什么这么写 → 代码注释（见下一条）。这三处是给维护者的，可以（也应当）写透——使用者可见面不承担这个职责
- **代码注释不受此限**：注释是给维护者看的，可以写透

## 七、文档与决策的更新

**先分清是「同一件事的细节修正」还是「旧决策被新决策取代」——两者处理相反。**

- **同一件事的细节修正：就地改。** 改的是**同一个**决策的范围内的措辞、补漏、形态微调（含同一件事当天的改动）——直接改原文，**MUST NOT** 追加「更新记录」，也 **MUST NOT** 留「此前是……现已改为……」这类话。判据：新旧只是同一个决策的两版表达，不是两个决策。
- **旧决策被新决策取代：不改旧文，在它末尾追加一段「更新记录」。**
  - 记三件：日期、新决策是什么、旧内容哪一部分不再约束（并指出替代它的地方）。
  - 旧内容原样留着，**MUST NOT** 就地改写、删段或挪位置：那是当时的判断，改掉就看不出决策是怎么变的了。
  - 新决策本身值得留档时，另开一条 ADR 记它，在「更新记录」里指过去。
- 「只写当下、不写沿革」（见第六节）只管**使用者可见面**；ADR 与 issues 是给维护者的，取代关系**应当**写清。
- 形态：`## 更新记录` 起段，一条一行，写成 `- <日期>：<新决策一句话>；上文「<哪一段>」不再约束，替代见 <新决策所在处>`。
