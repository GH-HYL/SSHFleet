# ADR-0033: 规格审计单独立一个技能，专门挡「结构被绕开」

- **状态**：已接受（accepted）
- **日期**：2026-10-30
- **决策人**：作者明示（2026-10-30 本轮对话）
  - 「质量审计一般都是在我分支该提交的时候才做的，那时候代码都已经写完了，如果再发现问题，修改的代价太大了」
  - 「所以我想弄一个规格审计，尽量在开工前就把它约束住，这时候的成本还是比较低的」
  - 「审计的重心就是不要破坏我现有的框架，我就怕他随意从上游拿东西，然后自己拼接」
  - 「其实咱们大的模块都还好说，就怕后面有新的需求，需要来回穿插的那种模块」
- **实施载体**：`skills/person/audit-spec/SKILL.md`

## 背景

现有五个审计里，与本议题相关的是这四个，**没有一个落在「实现合同写好、开工之前」这个位置上**：

| 技能 | 时点 | 判据 | 挡得住结构被绕开吗 |
| --- | --- | --- | --- |
| `/audit-adr` | ADR 定稿前 | 决定有没有出处、与旧篇打不打架 | 不涉及代码结构 |
| `/audit-docs` | 一批文档改完 | 自洽、规范、说法属不属实 | 不涉及代码结构 |
| `/audit-quality` | 分支该提交时 | 有没有另造一套、ADR 决定履行了没有 | **挡得住，但太晚** |
| `/audit-retrofit` | 议题全走完 | 实现与 ADR 对不对得上 | 挡得住，但更晚，且重型 |

`/audit-quality` 的 1.1 轴（「同一形式由两个及以上写入点各自拼出，说明本来就该有一个构造点」）**正是要挡的那件事**，但它的时点是提交时——代码已经写完。改法是重写，不是改一句话。

作者对失效路径的描述很具体：不是大模块出问题，**是某个新需求需要来回穿插的那种模块**——「有一个玩拼接的，就有第二个玩拼接的」，越维护越坏。

## 决定

**新建 `/audit-spec`，在实现合同写好、还没说「授权开工」时跑，每回都跑。**

它的重心只有一条——**照这份规格写出来，ADR-0032 的哪一条会从「结构上做不到」退化成「纪律上不该做」**。

**为什么是这个口径**：作者 2026-10-30 指出，拼接只是他举的一个例子——「我看你这个规格审计一直在说拼接的事儿，但实际上破坏架构不止拼接吧。实际上我审计这块只是拿拼接举例，我是担心一切破坏我这次重构的。」

所以判据是找**架构腐蚀**（architecture erosion）——边界不是被一次违反，是被一条条「看着都合理」的改动磨掉的。拼接之所以排第一，是因为它把「够不着」改成「够得着，只是不该」，从那一刻起后面每个 AI 都有了一条可走的路。

查的形状分五组十五条：

| 组 | 找什么 | 条数 |
| --- | --- | --- |
| 甲 数据流被绕开 | 穿站回取、同一件事算两遍、共享可变状态 | 3 |
| 乙 唯一出口被绕 | 自己出字、自己退场、契约长出行为、横切长出业务、塔尖变厚 | 5 |
| 丙 形状被改 | 加站劈站并站、反向依赖、阶段顺序被动过、新模块无家 | 4 |
| 丁 接口变浅 | 导出零件而不是整件事、接口变宽 | 2 |
| 戊 例外口子 | 「暂时」「特殊情况」「先这样」「这次例外」 | 1 |

**十五条是形状，不是判据本体。** 每条的形状留在技能里（那是执行者按图索骥用的），**真正撞的是哪条结构决定，去 ADR 读，技能里不抄**。抄一遍就有两份，ADR 改了口径这一份不会跟着改——那是第二个真相。

**每组每条都附带一句「退化成什么」**，那句才是判定标准——想不出退化后的样子，这条不成立，不许报。这是防止审计自己编问题的那道闸。

判据取仓库，三类按可靠性排：已 accepted 的结构 ADR 与 `Status: resolved` 的决策工单；`GLOSSARY.md` 与既有导出符号；规格里每条「决定」的出处。

**判据没落定的写「判据不足，跳过」，不拿通用最佳实践补位。**

## 理由

**为什么不并进 `/audit-docs`**：文档审计的判据是「这份文档自洽吗、合规范吗、说法属实吗」，它的受众表里没有「代码结构」这一栏。并进去会让它同时背两套判据，而这两套的时点、对象、失效方式都不同——文档审计面对的是任意一批文档（手册、规范、词表），规格审计只面对一个议题目录、且必须通读全文（工单脱离 spec 判不出结构风险）。

**为什么不并进 `/audit-quality`**：它的时点是对的，位置错了。而且它审的是 diff，规格审计审的是文档——**没有 diff 可看的时候，它无从下手**。

**为什么必须在开工前**：这是唯一一条能改写法的时点。同样一个问题，在规格里发现是改一句话，在提交时发现是重写一段，在议题结束时发现是重开一轮。

## 影响

- **审计链变成五段**，时点互不重叠：

```text
ADR 定稿前   → /audit-adr       决定有没有出处、与旧篇打不打架
规格改成实现合同 → /audit-spec  架构会不会被磨掉、验收与边界写没写   ← 本条新增
一批文档改完 → /audit-docs      自洽、规范、说法属实
分支提交时   → /audit-quality   有没有另造一套、决定履行了没有
议题全走完   → /audit-retrofit  实现与 ADR 对不对得上（重型，只用于重视的议题）
```

- **它接的是「实现合同」，不是「交接书」**。作者的实际流程是两段：改代码时撞见问题先开议题，AI 自动生成的那份 `spec.md` 只是交接书，不审；等腾出手来、写完 ADR 再重写规格，那时它才是实现合同，才跑这个审计。判据要机械：引用 ADR / 有验收项 / 有 Out of Scope，三条一条都不满足就是交接书，直接报「尚未进入合同阶段」收尾。
- **它会在施工期大量输出「判据不足」**。结构定义仍在施工（`docs/issues/2026-10-30-2134-架构重构/` 的 01–13 号工单），凡落到还没定的那一块都判不了。这不是它的缺陷，是施工期的正常状态；随着工单逐张结算，可判的部分会变宽。
- **作者每回都跑，所以它必须能空手而归**。ADR 审计、规格审计、质量审计都已经长在作者的工作流上——这是为了弥补「不懂开发」而立的规矩，不靠记性。既然每回都跑，没有命中的时候必须一句话收尾，不许为了显得有用而凑条数。
- **结论必须让不读代码的人能判**。作者不看代码，所以每条要写成「原文 → 撞的是哪条决定 → 照这么写会退化成什么」，不需要打开文件就能定轻重。
- **`/audit-quality` 不变**。它已经是「挡得住但太晚」的那一道，本条不取代它——晚的那道仍然要留，因为规格审不出「实际写出来的代码有没有照着规格做」。
- **`/audit-conversation` 计划退役**（作者 2026-10-30：与 ADR 审计重合，暂时留着）。

## 代价

- **多一个技能要维护**。它的判据依赖 ADR-0032 与后续决策工单；那些一旦改口径，这个技能跟着过时。
- **不查「有没有替开发者拍板」**：那与 `/audit-docs` 的一致性轴重复，同一个问题问两遍只会让人两头看。代价是规格若在这一层出问题，只能等文档审计那一轮才发现。
- **五组十五条是穷举，不是收敛**。`/audit-quality` 只用三条轴就能覆盖代码，因为它面对的是 diff、能机械扫；规格面对的是散文，只能按形状枚举。形态一多，漏的形状就难发现——补的办法只有一个：每撞上一次没被抓住的腐蚀，往这十五条里加一条，别改判据。
- **只在开工前有效**。代码写完之后它一点用没有——这是设计，不是缺陷，但意味着它必须真的被调用，否则等于没有。作者的做法是每回都跑。

## 备选方案

| 备选 | 否掉的理由 |
| --- | --- |
| 扩 `/audit-docs`，加一轴「结构风险」 | 那批文档里多数与代码结构无关（手册、词表、规范），加一轴会让它每次都要先判断「这批文档跟结构有没有关系」，多一步且容易跳过 |
| 把 `/audit-quality` 提前到规格阶段跑 | 它审 diff，规格阶段没有 diff。硬提前等于重写成另一个技能 || 靠 `/audit-adr` 顺带管 | ADR 审的是「决定有没有出处」，管不到「规格会不会引导出坏结构」；而且 ADR 只在有 ADR 时才有得审 |
| 不立技能，靠规范里加一句纪律 | 纪律是建议，不是判据。这套框架立身的理由就是「建议挡不住」——见 ADR-0032《背景》 |
