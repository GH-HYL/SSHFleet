# ADR-0012: 架构审查不以可测性为收益依据

- **状态**：已接受
- **日期**：2026-09-29

## 背景

2026-09-29 的架构审查（产物：`build/architecture-review-2026-09-29_14-57-17.html`）列了五个候选，其中两个的收益**几乎全部**来自"更好测"：

- **候选 ②**（在 `internal/batch` 与 `internal/ssh` 之间引入一个可替换的接缝）：唯一理由是 `batch` 因为自己 `ssh.NewClient` 造真连接而无法测试。
- **候选 ④**（把 `internal/confirm` 的输出落点改成可替换，与 `internal/output` 统一）：两条理由里有一条是"参数屏可断言"。

作者（2026-09-29）对测试的定位：**「测试只是测试，我不管代码是不是好接测试，甚至在我眼里测试代码放那里，只是有可能下次用到，并不是开发的重点，重点是我的业务代码没问题。」**

## 决定

**架构审查、重构建议、候选排序，一律不把「好不好测」当收益依据。**

具体边界：

1. **不把测试当审查对象**：审查只看业务代码（`modules/` 下的实现），不看测试内容、不评测试覆盖、不因缺测试而提候选。
2. **以可测性为唯一理由的候选，直接作废**，不列入报告。
3. **可测性不作为排序依据**：即便某个改动"顺带"更好测，排序时也不给它加权。
4. **审查的收益口径固定为三条**：业务正确性 · 改动面 · 维护成本（后者按《个人开发规范》二「拆分判定标准」即以改动历史判定）。

## 理由

- 审查的产出是改动建议，而作者对测试的投入产出判断是"不是重点"：以可测性为收益，会把审查的重点从"业务代码对不对"拽到"测试方不方便写"上。
- 可测性作为收益有一个**不可验证性**：它许诺的是"以后改得轻松"，而《个人开发规范》二明写"得有实际发生过的干扰才拆"——同一个"将来才兑现"的口子，不该在审查里单独开后门。
- 这条不影响"要不要写测试"这个独立议题：本 ADR 只约束**审查的收益口径**，不禁止写测试、不要求删既有测试。

## 影响

- **候选 ② 作废**（唯一理由是测试）。
- **候选 ④ 降为不做**：两条理由去掉测试那条后，只剩"同样的事两种做法"这一点一致性，不值得单独开一轮；将来真要改 `confirm` 的输出时顺手统一即可。
- 后续每一轮架构审查**不得再以 testability 为由提候选**——这是本轮之后最容易复发的一条，故立此 ADR。
- 与 ADR-0003 同类：都是记下"某个标准做法在本工程刻意不走"，供后续审查免得反复重提。

## 备选方案

| 备选 | 否掉的原因 |
| --- | --- |
| 保留可测性作为收益之一，只是排序靠后 | 排序靠后等于没立规矩——候选 ② 那种"唯一理由就是测试"的条目仍会挤进报告，每轮都要重新解释一遍 |
| 完全禁提测试相关话题（含不写新测试） | 越界了。本 ADR 管的是**审查的收益口径**，不是"要不要写测试"；把两件事绑一起会把一个口径问题变成开发流程问题 |
