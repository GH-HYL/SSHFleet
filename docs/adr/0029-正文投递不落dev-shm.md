# ADR-0029: 正文投递继续走下发命令行 / stdin，不落 `/dev/shm`

- **状态**：已接受（accepted）
- **日期**：2026-10-28
- **决策人**：作者（2026-10-28 原话「那就不考虑，那还是命令拼装吧」）
- **实施载体**：无代码改动；正文投递维持现状

---

## 一、被否的提议

2026-10-22 作者提过：不论 `-c` / `-s` / `-a`，先把正文落到目标机 `/dev/shm` 的一个文件，再用配置的解释器执行该文件。

**动机是拼装**，不是穿透 sudo 边界：一是少维护「每种解释器的程序文本参数」，二是看能不能顺手解决 `-a` 里 `$0` 与 stdin 的取舍。这一点必须先说清——它与 ADR-0024 的 locale 决定正交，采纳与否都不改变那边的结论。

## 二、它确实能解决的

- **`-a` 的编排简化**：不必再按解释器取 `-c` / `-e` / `-r`，表外解释器（`tclsh`、`deno`、`awk`）也能跑，「解释器可随意配置」在 `-a` 上才真正成立。
- **体积上限换了个位置**：从 argv 的 `MAX_ARG_STRLEN`（正文约 92KB）换成 tmpfs 容量——不是没有上限。
- **PTY 回显变短**：从整条 base64 变成一行 `bash /dev/shm/x.sh`，输出污染与触发词误匹配的面都小了。
- **`$0` 与位置参数**：shell 家族可用 `. 文件 原名` 保住 `$0`；非 shell 家族 `sys.argv[0]` 从 `-c` 变成真实路径，是改善。

## 三、为什么不采纳

**压不住的结构性代价**：

1. **新增 sftp / 第二会话的硬依赖**。现状「只要有 exec 通道就能跑」；落文件后「还得有可用 sftp 且没被 chroot」。2000 台里只要有一批关了 `Subsystem sftp`，`-a` 在那批上整体失效——而那批往往正是环境最不规整的那批。
2. **`/dev/shm` 的容量与存在性不可控**（本机 10MB；精简系统、chroot、非 Linux 可能没有）。
3. **source → exec 的语义变化**：顶层 `return` 从「立即返回」变成「报错后继续」，退出码可能 N → 0。
4. **日志失去正文可复原性**：`-a` 现在 base64 与原文都在，事后能回答「到底跑了什么字节」；落文件后只剩一个执行完就删的路径。
5. **每台多一次往返**：2000 台逐台建连，总时延与失败概率都乘以二。

**可控、但必须一并做对的**：随机文件名 + `O_EXCL` / `O_NOFOLLOW` + 0600 + 写完校验长度 + 原子 rename + `trap` 清理 + 永不走 shebang。少一条就会落在「截断被执行」「符号链接覆盖任意文件」「644 泄露」这三条上（均已实测）。

一句话：它把「一条流」换成「一个文件 + 一次往返 + 一套清理」，换来的只是拼装代码短一点。

## 四、影响

- 正文投递维持现状：`-c` / `-s` 走会话 stdin，`-a` 走 base64 argv + PTY。
- `-a` 的 92KB 正文上限、`interpreterTable` 的表内限制**都留着**；要突破它们另立议题，不在本决策范围内。
- 证据：`docs/issues/2026-10-22-shm投递方案/findings-2026-10-22.md`（该提议的完整分析，含 ENOSPC 截断、符号链接穿透、644 残留、并发同名四条实测）。
- 重新评估的条件：目标机群确认 `sftp` 与 `/dev/shm` 都可用，且「`-a` 跑大脚本」成为主要用法。届时按第三节末那组约束实现，不要只做「落文件」这一步。
