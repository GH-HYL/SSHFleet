# ADR-0028: 报错文案的拼法收进构造点，射程只到「使用者能当场改」那一层

## 一、背景

使用者看到的报错，形状是「问题 / 原因 / 提示」三行（ADR-0025 决定 6）。但**拼法没有人管**：每处报错自己打字符串，于是同一套话长出了四种形态。

2026-10-27 实测（仓库 HEAD，Windows 本机 `grep`；非测试代码）：

| 形态 | 处数 | 例 |
| --- | --- | --- |
| 问题 + 原因 + 提示 | 16 | 本地路径读不到、上传文件读不到 |
| 问题 + 原因（缺提示） | 19 | 配置解析失败、归档目录建不出来 |
| 问题 + 「常见原因：」+ 提示（另一套标签） | 1 | 多余参数 |
| 问题 + 提示（无原因） | 36 | 参数形态检查、配置项写法 |
| 一行，无任何标签 | 2 | `--change-password 的值有问题` |
| 问题 + 裸第二行（无标签） | 2 | `--change-password 不能和 --no-shell 一起用` |
| 问题 + 出处 + 出路（另一套标签） | 十余 | 危险命令规则文件 |

这 36 处带「原因：」的报错横跨 8 个包（batch、cli、config、credential、dangercheck、output、ssh、verdict）加 `main.go` 的执行前守卫。四种形态并存说明它不是一次性疏漏，而是**常态**：新增报错点的人只能去抄一段最近的，抄漏一行没有任何东西拦他——那两处一行报错就是这么来的。

**计数口径要写清**：这 36 处里有 5 处是拆行拼接（`"…\n" + "原因：…"`），还有 1 处用的是「常见原因：」小标题，只用 `\n原因：` 去 grep 这两类都数不到。本次第一版统计（30 处）正是漏在这里，**门也照抄了这个盲区**——所以门必须同时认「`\n原因：`」与「新起一行字面量 `"原因：…"`」两种拼法；「常见原因：」是那一处自带的小标题、中段是编号列表，门不把它算作口径，理由见决定 5。

同时，**执行阶段已经有自己的构造点**：报文由 `ssh.Message(env, stage, detail)` 统一产出（ADR-0021）。也就是说「报错要有个统一出口」这件事，在那一层早已成立，只是形状是 `sshfleet.<环境>.<环节>: <英文描述>`，不是中文三行。

本 ADR **不推翻** ADR-0025 决定 6（三行套的形态）与 ADR-0021（执行阶段报文），只补一件事：这些文字**由谁拼、由哪一层拼**。

## 二、决定

1. **拼法收进一处。** 每个报错点只给「内容」（第一行、系统原文、怎么改），标签与换行由构造点加。构造点放在所有报错点共同的下游包里，且该包不依赖任何内部包，避免成环。
2. **射程按受众切，不按包、不按位置。** 构造点只覆盖「使用者看见后能当场做点什么」的报错——参数与前置检查、执行前守卫。两类不进：
   - **执行阶段的单机失败**：仍以报文为唯一载体（ADR-0021），不套三行。终端与报告里「这是什么意思、怎么办」由分类提示块承担，那是同一件事的另一种做法，不重复做第二遍。
   - **日志 / panic / 内部断言**：只给维护者看，保留现场，不加「提示：」（`docs/个人开发规范.md` 四·4 的判据）。
3. **「内部错误」单列一种形态。** 使用者看得见、却没有任何动作能让这次跑通的那类（执行期内部状态不一致），第三行恒定是「这是内部错误，请把本次命令反馈给作者」。它与「你去改」不是一个语义，不并进同一条构造点；恒定那句话由构造点负责，不由调用点各写一遍。
4. **只抽格式，不抽文案。** 不新增、不改写任何一句现有提示；第三行该怎么写仍由写那个报错点的人就地决定。由此构造点必须容得下现成的缺项形态（有原因没提示、有提示没原因），迁移才可能是逐字节等价的。**三行是否必须齐、19 处缺提示该不该补，本 ADR 不表态**（见《复审》）。
5. **靠门兜住「不用它的人」。** 函数管得住愿意用的人，管不住绕开的人——Go 没有编译期强制。所以配一条交付前必跑的判据：「原因：」这个标签只允许出现在构造点所在目录，`_test`（那里是断言，不是拼装）与构造点目录一并排除。判据必须同时认两种拼法——`\n原因：` 与「新起一行的字符串字面量」，否则拆行拼接的报错能躲过去。**不纳入门的两种**：带缩进的 `"  原因：`（`--key-status` 的状态输出，不是报错）、「常见原因：」小标题（那一处中段是编号列表，纳入门只会逼着改文案）。函数负责「一处改、处处生效」，门负责「漏了会被发现」，缺一样都不算落地。
6. **不重复造第二个构造点。** 执行阶段报文已是同一件事在另一层的完成态，不并入、不改形。

## 三、理由

- **为什么必须收。** 现状是 36 处手打、七种写法并存。不收，改一次标签要翻八个包加 `main.go`，查一处报错齐不齐只能读中文；而漏项没有任何机器判据能发现——这一条是本次实测出来的，不是推测。
- **为什么按受众切，不按包切。** 「按包」会把报文与报告正文一起拖进三行套，两种载体互相污染。受众判据仓库里已经有一条现成的（规范四·4：这段文字出现时使用者能做点什么），照它切，不需要新造标准。
- **为什么执行阶段不下探。** 两个具体代价：一次跑两百台，每台三行等于六百行刷屏，进度界面当场不可用；报文是 `sshfleet.` 前缀形态，成功判定与排查都按这个前缀认（ADR-0021），把中文三行裹进「原因」栏会让这条判据失去着力点。**这一条是源码推断，没有真实用户反馈佐证**（见《复审》）。
- **为什么内部错误不并进使用者那一条。** 同样是「提示」两个字，一处要他去改命令，一处要他别动、把命令发回来。并在一起，提示栏就有了两种语义，下一批新增的人看注释也分不清该用哪个——那是把今天的**形态**混乱换成语义混乱，代价更大。
- **为什么用几个语义化名字，而不是一个函数加空参数。** 空参数在调用点看不出意图（补的是哪一行？留空是「没有」还是「忘了」？），而且 grep 数不出每种形态各有多少处——而「数得清」正是这个决定要买的东西。
- **为什么只抽格式。** 文案集中会立刻遇到「这条提示要带路径」「那条要带名单」，于是构造点开始收参数，很快退回字符串拼接——病症原路返回。口吻统一是另一件事，该单独做。
- **为什么加了函数还要门。** 这是本决策唯一不体面的地方，得明说：函数只能把「忘记」变成「要绕开就得自己打中文标签」，绕开在 Go 里照样能编译。真正让漏项可发现的是那条 grep，不是函数。

## 四、影响

- **新增报错点**：只能走构造点，且交付前过门。门指不到的地方（刻意另写、半角冒号、无标签）不受约束，这是已知缺口。
- **现有文案**：迁移本身一条都不变，纯迁移不记 CHANGELOG。使用者能看见的只有两处：作者追加的「密文内容被当值传入」检查（两种模式各一句），以及「值有问题」那支补的提示。两处都已记一条。
- **测试**：三条既有断言里带着标签字面量（`internal/cli/answer_test.go`、`internal/nodelist/nodelist_test.go` 带 `\n原因：`，`internal/cli/source_test.go` 带「原因：」），它们断言的是行为，不是拼装，门必须排除 `_test`，且**不许改这三条断言**。
- **文档**：本议题 `spec.md` 与旧工单的现状描述四处与实况不符——处数（写 28，实为 36）、覆盖面（写 8 个包，实为 8 个包加 `main.go` 执行前守卫）、门命令（按文件名过滤 `common`，迁移后每行都含构造点调用，门会变成空门；且只搜 `\n原因：` 漏掉 5 处拆行拼接）。实施前已按本 ADR 改写。
- **不涉及**：报文形态、报告正文、清单逐行汇总（行内文字，不是独立报错）、日志格式、退出码与 `[ERROR]` 前缀。

## 五、备选方案

| 方案 | 否掉的原因 |
| --- | --- |
| 不做，只补那两处一行报错 | 四种形态照旧，下次照抄照样漏；这正是上一个议题漏掉它们的原因 |
| 每个包各放一个 helper | 36 处横跨 8 个包加 `main.go`，等于把同一段拼装复制九份，改格式仍要翻九处 |
| 一个函数，空参数表示缺行 | 调用点看不出意图；grep 数不出每种形态的分布，「数得清」这个收益没了 |
| 三行套下探到执行阶段每台机器 | 六百行刷屏；报文前缀判据失去着力点；与分类提示块重复做同一件事 |
| 「内部错误」并进使用者那一条 | 「提示」栏出现两种语义（你去改 / 你来反馈），比形态混乱更难纠正 |
| 文案集中到构造点的一份常量表 | 上下文相关的提示要带路径与名单，很快开始收参数，退回字符串拼接 |
| 门按「文件名含 common」过滤 | 迁移后每行都写着构造点调用，全被自己滤掉，门永远是开着的空门（本次核对工单时发现） |

## 六、复审

**方法纪律**：判定一段文本属于哪一层，只看两条——它出现时使用者能不能当场做点什么；它最终出现在终端给使用者看，还是只进日志给维护者看。**不按包名、不按代码位置推断受众**；写进本文的处数必须是当天 grep 出来的实数，并注明机型与范围。

**未证实清单**：

- **门能兜住「新增自造格式」——未证实。** 门只认「原因：」这个标签的两种写法。半角冒号、把「提示」写成别的词、整条不带标签、改用「常见原因」「出处」这类变体，统统抓不到。它拦的是「照抄时漏了一行」，不是「刻意另写」。**别把它当成形态的保证。**
- **「执行阶段不该下探三行套」——未证实。** 依据是刷屏规模与报文前缀判据，两者都是源码推断，没有真实用户反馈；若将来有人报「执行阶段看不懂」，第一个该重看的就是这条。
- **三行是否必须齐——无判据。** 19 处只有「问题+原因」，本 ADR 只保证迁移不改文案，不表态哪种形态才对。要定这件事，得先有判断「提示」该不该强制出现的依据，现在没有。
- **两处计数口径较粗——会被挑战。** 带「原因：」的 36 处已把拆行拼接算进去并逐条看过；「问题+提示」那 36 处是按 `fmt.Errorf` / `errors.New` 行粗数，未剔除其中第二行只是注释说明的个例，实施时以实际迁移清单为准。
