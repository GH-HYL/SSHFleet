# ADR-0009: 三个 batch executor 维持薄壳，不合并

状态：已接受（2026-08-27）

## 背景

架构审查（architecture-review-20260827-114310.html 候选 #5）提出：`internal/core/batch_executor.go` / `batch_upload_executor.go` / `batch_download_executor.go` 三兄弟字段、New 构造、Run 外壳重复，建议合并为单一泛型执行器。

## 评估（2026-08-27 复核）

并发骨架已在 `runPool`（batch_core.go）唯一化——worker 池、任务提交、取消、进度回调、结果通道关闭均为一份实现；三个执行器各剩约 30 行机械样板（字段 + New + 并发上限 clamp + Run 壳 + work 闭包）。调度层接口也已统一：`batch.go` 的 `batchRunner` 泛型接口 + `batchOperation` 配料表 + `runBatch` 骨架，调用方不感知三个执行器的差异。

## 决策

**不合并，维持三个薄壳。**

理由：

1. **重复已收敛到机械样板级**：并发逻辑（约 80%）唯一，剩余重复是稳定的 clamp 一行与字段声明，风险趋零。
2. **接口层已统一**：抽象统一的目的（调度侧不感知差异）已由 batchRunner + 配料表达成。
3. **Go 泛型基类收益为负**：Go 泛型不能用于方法，泛型 Runner 需塞 work 字段或工厂闭包，删 ~90 行样板换类型参数噪音；现有薄壳签名（`Run([]*SSHTask) <-chan *ExecResult`）类型安全且更直白。
4. **删除测试**：内联进配料表或泛型 Runner 均为复杂度转移（batch.go 变胖 / 参数噪音），非集中。
5. **YAGNI**：三种模式短期内无第四种执行器（脚本模式复用命令执行路径）。

## 后果

- **正面**：保持类型安全与职责边界，无泛型参数噪音；并发逻辑仍单点维护。
- **负面**：新增执行器模式时需复制一份薄壳（约 30 行样板，概率低）。
- **边界**：若未来出现第四种执行器且壳重复再次扩散，再评估泛型 Runner 或内联方案。
