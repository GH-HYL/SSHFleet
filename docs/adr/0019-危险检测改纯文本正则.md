# ADR-0019: 危险命令检测改为纯文本正则，按写法枚举而不按解释器枚举

- **状态**：已接受（accepted）—— 实施已完成，验收见 `docs/issues/2026-10-19-0004-危险检测改文本正则/issues/09-integration-and-verification.md`
- **日期**：2026-10-18
- **决策人**：作者（2026-10-18 本轮对话）
- **实施载体**：`docs/issues/2026-10-19-0004-危险检测改文本正则/spec.md`
- **最后核对**：2026-10-20（更新记录共 13 条：10 条与 spec 定案 A–P 对齐；3 条为实施末期开发者改口——重启族与清空防火墙升回禁止、取消规则条数下限、实施完成收尾）

## 背景

危险命令检测（`internal/dangercheck`）此前的做法是：把 `-c` 的命令原文或 `-s` 的脚本全文交给 `mvdan.cc/sh/v3/syntax`，**按 shell 语法**整份解析成命令段，再拿命令段文本比规则正则；解析失败时退化为逐行、再退化为朴素分词。

解释器表（`ssh/command.go` 的 `interpreterTable`）认可 15 种解释器，其中 `python` / `perl` / `ruby` / `node` / `lua` / `php` 等 8 种不是 shell。于是出现两种坏结果：

- **漏报**：`python3 -c` / `perl -e` / `node -e` 里的 `rm -rf /etc` 全部未拦，同内容的 `bash -c` 能拦（2026-10-18 实跑）。
- **判定不稳定**：走语法树还是走逐行回退，取决于整份文本在 shell 语法下能不能解析通过；同一份 python 脚本于是有时拦、有时不拦。

开发者此前的做法，是因为**变量拼接、前置后置旗标不好用正则拦**，只能借语法解析把命令结构拆出来。

2026-10-18 定方向前，作者先问了一句：能不能直接对原始文本做正则？随后给出三条指导：

1. **检测器只是提醒**，不是防线；不追求完全封堵，只尽量减少漏报与误报。
2. **不要枚举**（不按解释器各写一套匹配），要**统一思路**。
3. **从底层一对多地封堵**：按危险命令的长相封，一次覆盖多种写法。

## 决定

**判定引擎改为纯文本正则，不再按任何语言解析。**

1. **判定对象 = 原始内容**：`-c` 的命令原文、`-s` 的脚本全文，解码后原样参与匹配。不管下发时套过什么外壳、编过什么码。
2. **统一路，不按解释器分**：不给每种语言配解析器，`-c` 与 `-s` 共用一套匹配器。
3. **匹配前去掉注释**：整行注释、行尾注释、纯空白行不参与匹配；其余内容全部参与，包括代码字符串与参数里的字面量。`print("reboot")` 命中就是正确结果，不降级。
4. **一条危险命令可配多条正则**：规则挂多条正则，命中任意一条即该规则命中。**用枚举写法**，而不是硬憋一条正则去堵所有漏洞——这正是原方案借语法解析想解决的那个难点，现在改用配置表达。
5. **语法树解析整体退役**：不作判定源，也不作补充召回。它本身就是「时拦时不拦」的来源，留着等于保留一个行为不可预测的判定源。
6. **档位行为不变**：`forbidden` 档命中即打印警告框、以 1 退出；其余档位提示后按既有流程确认。
7. **规则全部外置**：认哪个命令、什么写法算危险，都写在规则文件里；代码只保留「怎么读规则、怎么匹配」的引擎。
8. **不兼容旧配置**：规则文件按新语义整体重写，旧写法不留兼容分支（作者 2026-10-18 定：重构不考虑兼容）。

**接受漏报**：变量拼接（`${X}rf`）、命令替换、运行时拼出来的命令，**不保证识别**——不是原理上判不出来，原文里可能整段可见，取决于规则怎么写。这是知情的取舍。

**误伤明示为可接受**：作者原话「`print reboot` 就算危险行为，没事儿你打印它干啥？误伤就误伤了」。

## 理由

- **统一路让「按解释器」整件事消失**。原方案要么认 8 种语言的语法（维护 8 套解析器），要么对非 shell 不判——两条都走不通。正则不依赖语法，`-c` 与 `-s` 一条路，漏报与「时拦时不拦」同时消失。
- **原文完整可信**。核查过：`-c` 命令以原文进入下发行；`-s` 脚本体 base64 编码后下发、远端解码即原文。正则能看到的，就是真要执行的那份内容。
- **多条正则比一条复杂正则可维护**。危险命令的写法五花八门（旗标顺序、空格、引号、路径前缀），一条正则堵所有写法必然又长又脆；拆成多条各自负责一种写法，加一种写法就加一条，可读、可测、可停用。
- **检测的定位不是防线**。既然是提醒，能封住的就封、封不住的就认，不必为了"看起来封得全"去做语言级解析。`forbidden` 档仍保留直接退出，因为那几条规则真的会毁机器。
- **统一引擎省掉的是长期维护**：语言有多少种不定（解释器表本就可配），按语言枚举等于跟着它无限地写。

## 影响

- **`internal/dangercheck` 的解析层整体退役**：语法树解析、逐行回退、朴素分词不再承担判定职责。
- **规则文件整体重写**：`keywords_dangerous.conf` 的 38 条规则按纯文本语义重写，一条规则挂多条正则，**不兼容旧写法**（开发者 2026-10-18 定：重构不考虑兼容，配置全部服务于新目标）。
- **判定层要重估**：包装命令剥离、rm 旗标归一、间接执行递归——正则直匹配之后这些结构信息不再自然具备。旧规则依赖「已归一化的命令段」（`-rf` / `-r -f` / `--recursive` 视为同形、`sudo` / `xargs` 剥除），新语义下这些改由**多条正则**表达。**这是本议题里最容易被低估的一块**：规则重写量约 25 条，而 `keywords_dangerous.conf` 的头注释与两份手册都向使用者承诺过「不用管用户怎么写旗标」，这些要一并改。
- **`dangercheck` 不再需要知道解释器**：`Check` 不传 `Args.Interpreter` 是本方案的既定设计，不再是缺陷。
- **误伤成为既定行为**：代码字符串、参数里的危险词会被拦，此后**不要当缺陷报**。原缺陷清单的 D11 已按此改记为设计边界（`defect-scan-2026-10-17/spec.md` 的「设计边界」一节）。
- **读取侧与下发侧的内容落差**：脚本含 BOM 或首尾空白时，检测读到的文本（`check.go` 不剥 BOM、不 `TrimSpace`）与下发的正文（`cli/script.go` 会整备）可能不一致。这不是独立缺陷，属实施议题里的**待定项**，一并定「以哪一侧为准」。
- **工作量与风险**：判定引擎重构，必须配充分的语料测试；验收以语料驱动为主（细节见 `docs/issues/2026-10-19-0004-危险检测改文本正则/spec.md`）。

## 备选方案

| 备选 | 否掉的原因 |
| --- | --- |
| 保留 shell 语法树、只有非 shell 走正则 | 正是「按解释器分路」的枚举方向，与作者的统一思路相反 |
| 按解释器分别解析（python 用 AST、perl 用解析器……） | 要维护 8 套语法；语言清单本身可配，等于无限扩写 |
| 非 shell 一律不做判定，只在确认屏声明「未检查」 | 漏报从隐藏变成明示，功能上等于对非 shell 关掉检测 |
| 保守拦截：非 shell 解析不出结构就整条按危险处理 | 误报从一条放大成所有非 shell 脚本，`-s python` 这条路直接不可用 |
| 正则为主 + 语法树补充召回 | 保留一个行为不可预测的判定源，同一脚本仍可能时拦时不拦 |
| 一条规则只用一条复杂正则 | 写法一变就得改那条超长正则，脆且难测；拆成多条枚举更好维护 |
| 命中字符串时把 `forbidden` 降级为提示 | 作者否掉：打印 reboot 本身就值得拦；降级等于给误伤开后门 |
| 把识别命令写进代码（内置匹配器） | 认哪些命令该由使用者自己定；内置表会变成第二份需要维护的东西 |
| 规则字段兼容旧写法（单条 `regex` 与多条并存） | 作者 2026-10-18 定：重构不考虑兼容。两套写法的加载分支会长期存在，且旧规则在新语义下本就要逐条重写，兼容只是把旧形态多养一份 |
