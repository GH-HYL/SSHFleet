## 一、为什么静态取值这条路走不通

三条实测（2026-10-28，Ubuntu 26.04 与 CentOS 7.9 两个容器）：

1. **两类机器没有交集**。CentOS 7.9（glibc 2.17）有 `en_US.UTF-8`、**没有** `C.UTF-8`；Ubuntu 26.04 反过来——只有 `C` / `C.utf8` / `POSIX`，没有 `en_US`。任何单一名字都盖不住两类。
2. **「机器没有」不等于「不生效」**。`LC_ALL` 设一个不存在的名字，每次调用吐一行 `setlocale` 告警，并把进程落到 `C`（按字节）；而类别变量（`LC_CTYPE`）设错是**静默**回落，不告警。
3. **非交互会话通常拿不到 `LANG`**。CentOS 的 sshd 没配 `pam_env`、`/etc/environment` 是空的；Ubuntu 的 `/etc/default/locale` 只有一行注释。所以「不配置」在多数机器上等于按字节跑。

合起来：任何一个静态值，都只能让一半机器按字符、另一半按字节；「配了就一定有」这件事不存在。ADR-0024 取 `C` 的决定因此作废——它保住了零告警，代价是全场按字节，`cut -c` / `awk substr` 切中文会切坏。

## 二、决定

1. **编码不让用户配**，工具内建，每次执行按**白名单**判断：
   1. 问机器：`locale charmap` 是什么；
   2. 是 `C` / `POSIX` / `ANSI_X3.4-1968` / `US-ASCII` 之一（**确知按单字节在跑**）→ 继续；
       其余一律不动——包括已经是 UTF-8 的机器，也包括 `GB18030` / `GBK` / `Big5` 这类
       **多字节但非 UTF-8** 的机器（换掉它们会退化，见 §三）；
   3. 在 `C.UTF-8` / `en_US.UTF-8` 两个中性名里挑一个**确实存在**的（大小写、连字符都不计）；
   4. 挑到就**只** `export LC_CTYPE=<挑到的>`；挑不到、`locale` 不存在、输出为空 → 一个变量都不设。
2. **语言只留一个开关**：新开 `[locale]` 段，键 `english`，**必填**（缺这一行启动即报错，不设隐藏默认值），**出厂取 `true`**。
   - 开 → `export LC_MESSAGES=C`。`LANGUAGE` 不用清——glibc 的 gettext 在 `C` 下忽略它（实测；Python 的 gettext 例外，见 §六）。
   - 关 → 不加任何东西，语言跟随目标节点。
   - **开关放 `[locale]` 而不是 `[env]`**：`[env]` 是环境变量表，一个布尔混进去会被读成"可以传下去的一个变量"；而且编码已经没有开关，语言这个开关需要一个说得清归属的位置。
   - **出厂 `true` 的代价**：`-a` 代填吃的是目标机提示，提示变英文后，按中文写的触发词会整批「未命中」。这一条写进 CHANGELOG 与手册，由使用者自行决定改 `false`。
3. **`[env]` 收缩**：出厂只留 `PATH` 与 `TERM` 两行；`LANG` / `LC_ALL` 从出厂配置里删除（由第 1、2 条接管）；用户仍可自由增删自己的变量。
4. **`TERM=dumb` 保留**，理由与代价见第五节。
5. **`-a` 用同一套**：片段进 argv，`sh -c` 外壳不变。
6. **不再设 `LC_ALL`**：它设错会刷屏，还会盖掉语言开关。**目标机自己带着 `LC_ALL` 时，本决策在那台机器上不生效**（`LC_ALL` 压过 `LC_CTYPE` 与 `LC_MESSAGES`）——属已知边界，工具不告警、也不改它。

## 三、理由

- **判据用白名单，不用「不是 UTF-8 就换」**：`zh_CN.GB18030` / `GBK` / `Big5` 都是多字节 locale，本来就按字符算；把它们换成 `C.utf8` 之后，那些字节不是合法 UTF-8，程序退回逐字节——`cut -c` 从「切完整字」变成「切半个字」，是把好的改坏。上限就取「确知按单字节在跑」的四个名字。
- **红线：配置可以动，动了不能让截取变形**（2026-10-28 作者定，理由见文首原话）。实测（GNU coreutils `cut`、mawk 1.3.4）：纯 ASCII 输入下 `cut -c` / `cut -f` / `awk substr` 在 `C` 与 `C.utf8` 下**逐字节相同**；只有中文输入会从「半个字」变成「完整字」，那是修不是变。批量操作里切错字等于改错数据，所以判据宁可窄。
- **只动 `LC_CTYPE`**：它只管「一个字符算几个字节」，不碰语言（`LC_MESSAGES`）、不碰排序（`LC_COLLATE`）、不碰时间与数字格式。
- **只挑两个中性名**：`tr_TR` 一类会改大小写映射（`I` / `i`），脚本里的 `tr`、`[[:alpha:]]` 会跟着变；`C.UTF-8` 与 `en_US.UTF-8` 的字符分类是中性。
- **挑不到不设**：不设就是保持机器原状（`C`，按字节），且零告警——「有就用、没有就不生效」是唯一安全的实现方式。
- **只有这一条路**：静态指定任何值都会让一半机器退化（§一），所以只能利用目标机现有的编码数值，在目标机上现场判断。这与 ADR-0024 第八节「不在下发时探测」直接冲突，该禁令已由作者作废（见更新记录）。

## 四、影响

- **下发行**：`sh -c 'case "$(locale charmap …)" in C|POSIX|… ) …;; esac; <英文开关那一行>; [sudo ]解释器 …'`。
  - 片段本身 **201 字节**；`english=true` 时 223 字节（2026-10-28 实测，`printf '%s' … | wc -c`）。
  - 「整条」不是固定数，随 `[env]`、解释器名与开关变：`[env]` 空、解释器 `bash`、不开英文时 **214 字节**；带出厂 `[env]`（`PATH` + `TERM`）时 **302**，带 `sudo` 307，开英文 324（同轮实测，调 `BuildCommand` 量的）。
  - `-a` 的 122880 上限几乎不受影响：正文经 base64 进 argv（4/3），片段吃掉 201×3/4 ≈ **151 字节**的正文额度（开英文 ≈ 167）。
- **日志**：「命令行」那一行会带上这段判断，可读性下降，属已知代价。
- **`--no-shell`**：按契约不套外壳、不设环境，本决策不生效。
- **没有 `sh` 的目标**（交换机、小型机）：走 `--no-shell`，不在本决策范围内。
- **开销**：`charmap` 是 UTF-8 的机器（不进白名单分支）只多 **1** 次外部命令（`locale charmap`）；进了白名单分支且挑到候选时 **3** 次（`locale charmap`、`locale -a`、`grep`）。毫秒级。
- **失效不可观测**：目标机自带 `LC_ALL`、`locale -a` 里两个名字都没有、`locale`/`grep` 被裁掉——这三种在「命令行」日志里长得一样，都只有片段原文。排障时无法从日志判断片段是否生效，这是选择的代价。
- **存量配置**：工具尚未发布，不考虑兼容。旧的 `[env]` 里若还留着 `LANG` / `LC_ALL`，工具照原样 `export` 下去（没有特判），而它们可能盖住本决策——升级时该删。

## 五、`TERM=dumb` 的实测与代价

- **有 PTY（`-a`）**：`TERM=xterm` 下 `ls --color=auto` 带转义，`TERM=dumb` 下 0 行——真的压得住（目录内容不同则行数不同，不带实现名与目录状态时这个数不可复现）。
- **无 PTY（`-c` / `-s`）**：两种取值都 0 行，本来就没有彩色；那里它没有任何收益。
- **代价**：依赖终端能力的程序会失败。实测 `clear`、`tput cup` 返回 1；**`whiptail` 实测**（2026-10-28，0.52.25-1ubuntu3，`script -qec` 造 PTY）：`TERM=dumb` 下退出码 1、打印「Your terminal lacks the ability to clear the screen or position the cursor.」，`TERM=xterm` 下正常画框。`dialog` 本机未装，未测。
- **判断**：保留。收益落在彩色最脏的地方（`-a` 的 PTY），代价落在「需要光标寻址的交互界面」，而那种界面本来不是代填的主场景。

## 六、没证实的

- **AIX / HP-UX** 的 `locale -a` 输出格式。匹配用 `-i`，大写 `EN_US.UTF-8` 理论上吃得下，但无环境验证。
- **`charmap` 子命令不存在的系统**（BSD 系据手册没有这个关键字）：`charmap` 为空 → 不在白名单 → 不设。这是对照片段逐句推出的**推断**，不是观测：安全退化，只是不生效。
- **`dialog` 在 `TERM=dumb` 下的行为**（`whiptail` 已测，见第五节）。
- **Python 实现的 gettext 不看 `LC_MESSAGES=C`**：Python 按 `LANGUAGE → LC_ALL → LC_MESSAGES → LANG` 取第一个非空，`LANGUAGE` 有值时不忽略（实测：自造 `.mo`，`LC_MESSAGES=C LANGUAGE=zh_CN` 仍出中文）。CentOS 的 `yum` / RHEL 8+ 的 `dnf` 都是 Python，所以「开 english 就整批英文」对这类程序不成立；`LANGUAGE` 又在 RHEL 的 `env_keep` 里，能穿过 sudo。影响多大未测。

## 七、边界（已认下，不修）

- **目标机自带 `LC_ALL`**：`/etc/environment`、PAM `pam_env`、包装脚本给了 `LC_ALL` 的机器上，片段照做但无效。作者口径：「如果什么都检测不到、或者真的 `=C` 了，只要咱们的配置不退化添乱，就允许」（2026-10-28）。
- **白名单外的多字节 locale**（`GB18030` / `GBK` / `Big5` 等）：一律不动，保持它们原本的按字符语义。作者口径：「一旦配置就不能退化」。
- **`latin1` 一类清单外的单字节 locale**：不在白名单里，不动 = 不生效。缺口已知，取舍见 §三。
