# ADR-0010: 命令与脚本体不再经会话 stdin 交付

- **状态**：已接受（含 2026-10-07 补充，见文末《补充（2026-10-07）》）
- **日期**：2026-09-28

一次 SSH 会话只有一条 stdin 通道。代填要从这条通道喂输入，与「命令/脚本体经 stdin 直喂」直接冲突——实测（`docs/issues/remote-interaction/spec-已闭环.md` 第二节 F4/F5/F7）两者共用时，远端 `read` 会把**脚本体自己的下一行**当成答案吃掉，后半段**静默消失**且不报错。故命令与脚本正文改由 **base64 编入命令行**，远端 `base64 -d` 后作内层解释器的 `-c` 参数（`bash -c` / `python3 -c`）；会话 stdin 整条让给代填。

**范围（2026-09-28 修正）：仅交互分支（`--answer`）。** 普通 `-c`/`-s` 路径维持 stdin 交付、无长度上限——「全工具统一形态」已评估并否决：统一换来的是普通路径被长度上限约束、argv 暴露面扩大，收益（形态单一）不抵。

## Considered Options

| 备选 | 否掉的原因 |
| --- | --- |
| 旧 Py 侧的原形态 `printf %s <base64> \| base64 -d \| bash` | 实测无效：内层 bash 的脚本来源仍是那根管道，fd 0 被管道占住，`read` 照样抢脚本体。旧代码注释自称"经 stdin 通道传递"，指的是远端 shell 内部自建的管道，与会话 stdin 是两回事 |
| 就地把正文转义后嵌进命令行 | 正文里出现任一引号都会让「外层单引号 + `bash -c` 的参数」两层引号必然嵌套（实测仅一个单引号就把命令行炸成一串 `'"'"'`）。base64 字符集 `[A-Za-z0-9+/=]` 在 shell 里没有任何特殊含义，天然免疫 |
| 正文落 `/tmp` 再 `bash` 该文件 | 会碰硬盘。作者手上有几千台目标机，**磁盘满是常态**，落 `/tmp` 会因磁盘失败 |
| 正文落 `/dev/shm`（tmpfs） | 避开了硬盘，但新增对 tmpfs 的依赖、多一次写入与清理——能不用就不用 |
| `bash <(…)` 进程替换 | `sudo` 默认关掉 3 号以上 fd，`sudo bash <(…)` 在异构环境里不可靠 |

## Consequences

- **长度上限**：整条远端命令行由 sshd 以 `$SHELL -c "<整条>"` 交给内核 `execve`，是**单个 argv 串**，受 Linux `MAX_ARG_STRLEN`（`PAGE_SIZE × 32 = 131072`）约束 → 128KB；base64 膨胀 4/3 后**原文约 96KB 封顶**。超限由工具在**本地参数合规检查阶段**拦下退出，不放到远端执行时才报错（该检查仅 `-a` 运行执行）。
- **内容进入 argv**：目标机的 `ps` 与 auditd/HIDS 能看到那串 base64 且可直接解码，等同明文暴露。相对旧 Py 版**不是退步**（它本来就在 argv 里），相对当前 Go 版（正文经 stdin，不进 argv）才是——但交互分支是**显式开启**的，退步只发生在用了 `--answer` 的运行里。
- **顺带修好一处旧坑**：正文不再占 fd 0 之后，脚本里裸 `read` / 裸 `cat` 不再读到脚本体剩余的字节。
- **`$0` 与位置参数无变化**：原先脚本经 stdin 喂给 bash 时 `$0` 也是 `bash`、`$#` 也是 0，与 `bash -c` 一致，脚本行为无回归。

## 补充（2026-10-07）：交付通道的收敛，与 `-a` 的解释器范围

同日「解释器可配置」改动（ADR-0014）把 `-a` 的内层解释器也变成可配，于是重新审视了"正文交付通道"这条决策——结论：**没有第四条通道，本 ADR 的取舍仍然成立**。

**为什么没有第四条。** 一次 SSH exec 会话，本地往远端送数据只有两个入口：会话 stdin 与命令行 argv（落盘也要先经这两者之一把数据送到远端，它不提供新入口）。stdin 已整条让给代填，于是正文只能走 argv——这是 SSH 的结构，不是实现取舍。

**逐一否掉的新候选**：

| 备选 | 否掉的原因 |
| --- | --- |
| 落 `/dev/shm`（内存文件系统）+ argv 送正文 | 正文仍进 argv，长度上限照旧；只多出"落文件 + 清理"一道手续 |
| 落 `/dev/shm` + stdin 分时复用（`head -c N` 先收正文、剩下的留给代填） | 技术上可行，但 `-a` 的会话是 PTY：① 经 stdin 送进去的正文会被**回显**到 stdout（污染要收集的输出）；② 终端按行缓冲，单行超 `MAX_CANON` 会被截断；③ 超时/中断时残留文件删不掉 |
| 由第一个消费者从 stdin「拆」出正文、余下的转交下游 | 拆出来仍要交给解释器，落点只有 argv（上限）/ 文件（落盘）/ 管道（脚本的 stdin 变成管道、代填失效）三条——回到同一组墙 |
| 第二条 SSH 会话 / SFTP 通道专送正文 | 代填必须进**那条**解释器的 stdin，别的通道够不着；正文到了远端仍要落成文件才能被解释器读到 |
| 正文 gzip 压缩后 base64 进 argv | 只提高上限（文本压缩常 3~5 倍），不解根，且新增对远端 `gzip` 的依赖——作为"上限不够用"时的后备记录在案，不采用 |

**随之定型的 `-a` 解释器范围。** `-a` 的正文要作"一段程序文本"交给内层解释器，而各家的启动参数不一样（2026-10-07 实测）：shell 家族与 `python` 是 `-c`，`perl` / `ruby` / `node` / `lua` 是 `-e`，`php` 是 `-r`。这三类由工具自动适配；表外的解释器（`tclsh`、`deno` 等没有统一的"程序文本"入口）在参数合规检查阶段**当场报错并列出支持范围**，不再静默不跑。

## 补充（2026-10-09）

### 一、下发行只拼一次，长度闸门量的就是发的那条

本 ADR 的长度上限语义建立在「量到的字节 = 发出去的字节」之上，实现上却一直靠**两处各拼一遍、碰巧相等**：下发行当时在三个地方各拼一次——`cli` 拼一份只为量长度、`batch` 拼一份写日志、`ssh.RunInteractive` 内部再拼一份**真正发出去**；入场值又在 `cli` 与 `batch` 两处各装配一遍。2026-10-08 因此漏过一次：脚本模式下量长度那侧没给脚本名，闸门放进来一条比它以为的更长（长出一个文件名）的命令，`8efd65d` 补的就是那一格——补的是值，结构没动，还能再来一次。

本次改成**参数合规检查阶段拼一次、存进 `Args.Downlink`**（与 `Args.Interpreter` 同一口径：算好一次，执行侧直接取用）：`ssh` 新增 `DownlinkSpec`（决定下发行的五格），`cli.downlinkSpecOf` 是全场唯一装配点，`ssh.RunInteractive` 收下发行参数、不再自己拼，`InteractiveInput` 相应收窄为执行期三格（代填表、匹配口径、中止词）。

**量到的串与发出去的串由同一个变量保证**，「少给一格」这类漏法在结构上不再可能。一处可观测的行为变化：`-s` 加 `-a` 时正文取检查阶段读到的那份（原先执行侧会重新读文件）——正常流程无差异，文件在确认后被改动的场合，改后执行的是确认时看到的那份。

### 二、支持范围以代码里的登记表为准

上面《随之定型的 `-a` 解释器范围》只写了"三类由工具自动适配"，没指定**范围以哪份清单为准**。当时代码里散着三份：一张「要不要补 `$0`」的 shell 家族表（7 个）、一张「用哪个程序文本参数」的表（15 个）、外加 `sourceStdinBody` 里对 zsh 的一处特判；面向用户的「支持范围」又是**手抄的第四份**——`cli/interpreter.go` 的报错文案与 `README.md` 两处穷举都只有 13 个名字，抄漏了 `luajit` 与 `nodejs`，而这两个配进来是**能跑**的（都在参数表里，取值 `-e`）。

本次把四份收成一份：`ssh` 包的 `interpreterTable`，一行一个名字，四格——程序文本参数、是否 shell 家族、source 前要关的选项、显示顺序。报错文案由 `SupportedInterpreters()` 生成，文档照它写。

**上面那句范围描述由此作废，以表为准。** 表内 15 个：shell 家族（`bash` / `sh` / `dash` / `ksh` / `zsh` / `mksh` / `ash`）与 `python` 用 `-c`；`perl` / `ruby` / `node` / `nodejs` / `lua` / `luajit` 用 `-e`；`php` 用 `-r`。
