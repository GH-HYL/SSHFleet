# 命令与脚本体不再经会话 stdin 交付

一次 SSH 会话只有一条 stdin 通道。代填要从这条通道喂输入，与「命令/脚本体经 stdin 直喂」直接冲突——实测（`docs/issues/remote-interaction/spec.md` 第二节 F4/F5/F7）两者共用时，远端 `read` 会把**脚本体自己的下一行**当成答案吃掉，后半段**静默消失**且不报错。故命令与脚本正文改由 **base64 编入命令行**，远端 `base64 -d` 后作内层解释器的 `-c` 参数（`bash -c` / `python3 -c`）；会话 stdin 整条让给代填。

**范围（2026-09-28 修正）：仅交互分支（`--answer`）。** 普通 `-c`/`-s` 路径维持 stdin 交付、无长度上限——「全工具统一形态」已评估并否决：统一换来的是普通路径被长度上限约束、argv 暴露面扩大，收益（形态单一）不抵。

## Considered Options

| 备选 | 否掉的原因 |
| --- | --- |
| 旧 Py 侧的原形态 `printf %s <base64> \| base64 -d \| bash` | 实测无效：内层 bash 的脚本来源仍是那根管道，fd 0 被管道占住，`read` 照样抢脚本体。旧代码注释自称"经 stdin 通道传递"，指的是远端 shell 内部自建的管道，与会话 stdin 是两回事 |
| 就地把正文转义后嵌进命令行 | 正文里出现任一引号都会让「外层单引号 + `bash -c` 的参数」两层引号必然嵌套（实测仅一个单引号就把命令行炸成一串 `'"'"'`）。base64 字符集 `[A-Za-z0-9+/=]` 在 shell 里没有任何特殊含义，天然免疫 |
| 正文落 `/tmp` 再 `bash` 该文件 | 会碰硬盘。作者手上有几千台目标机，**磁盘满是常态**，落 `/tmp` 会因磁盘失败 |
| 正文落 `/dev/shm`（tmpfs） | 避开了硬盘，但新增对 tmpfs 的依赖、多一次写入与清理——能不用就不用 |
| `bash <(…)` 进程替换 | `sudo` 默认关掉 3 号以上 fd，`sudo bash <(…)` 在异构环境里不可靠 |

## Consequences

- **长度上限**：整条远端命令行由 sshd 以 `$SHELL -c "<整条>"` 交给内核 `execve`，是**单个 argv 串**，受 Linux `MAX_ARG_STRLEN`（`PAGE_SIZE × 32 = 131072`）约束 → 128KB；base64 膨胀 4/3 后**原文约 96KB 封顶**。超限由工具在**本地参数合规检查阶段**拦下退出，不放到远端执行时才报错（该检查仅 `-a` 运行执行）。
- **内容进入 argv**：目标机的 `ps` 与 auditd/HIDS 能看到那串 base64 且可直接解码，等同明文暴露。相对旧 Py 版**不是退步**（它本来就在 argv 里），相对当前 Go 版（正文经 stdin，不进 argv）才是——但交互分支是**显式开启**的，退步只发生在用了 `--answer` 的运行里。
- **顺带修好一处旧坑**：正文不再占 fd 0 之后，脚本里裸 `read` / 裸 `cat` 不再读到脚本体剩余的字节。
- **`$0` 与位置参数无变化**：原先脚本经 stdin 喂给 bash 时 `$0` 也是 `bash`、`$#` 也是 0，与 `bash -c` 一致，脚本行为无回归。
