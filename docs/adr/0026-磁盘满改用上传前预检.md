# ADR-0026: 磁盘满改由上传前预检判定，并按两侧分开归类

- **状态**：已接受（accepted）
- **日期**：2026-10-26
- **决策人**：作者（2026-10-26 本轮对话）；每条下面注明是原话、《个人开发规范》、还是执行者提议后经作者选定
- **实施载体**：`docs/issues/2026-10-20-2245-目标机磁盘满/spec.md`

## 背景

磁盘满在本仓库一直是「能被观察到、不能被说出来」的一件事。

2026-10-20 在报文议题的 04 里实测过：上传写到目标机装不下时，服务端只回 `sftp: "Failure" (SSH_FX_FAILURE)`，工具把它归到当时那个 `SFTP失败`（这个分类后来按语义拆成了几条），提示语把「磁盘满 / 无写权限 / 传输中断」写成一句。实测当次的形态是**一开工就不够**与**传一半才不够**两档，后者当时留下「先传成的那个文件完整留在目标机上」与「部分成功」分类。因为那次实测环境是 WSL 的 `tmpfs`（作者 2026-10-26 指出：那不是真实磁盘，生产目标机是物理盘），当时就把「分不出磁盘满」这件事单独立成议题 `2026-10-20-2245-目标机磁盘满`。

此后 ADR-0022（上传失败即回滚）完工，形态变了两处：

1. 「传一半留下残留」不存在了——失败时把本次已写的全部删掉，取消也回滚；
2. 「部分成功」分类退役——只剩成功与失败两档。

于是本议题原本担心的第一件事（半成品留存、已成功那几个算谁的）已经有答案，剩下的只有两件：**使用者仍不知道失败是不是空间造成的**，以及**能不能在传之前就拦住**。

作者 2026-10-26 给出方向（原话）：「预检查做一遍，传输检查再查一遍。如果传输过程中失败了，咱们再检查一遍。如果目标满了，就归类为『目标已满』……传输前和传输失败后的这两次检查都得做。」

## 决定

### 1. 探测走 SFTP 的 `statvfs@openssh.com`，不给命令通道 `df` 留兜底

（执行者提议，作者 2026-10-26 复「按你推荐目标」选定。）

`pkg/sftp` 已封装为 `Client.StatVFS(path)`，返回结构化的块大小与可用块数；依赖早在 `go.mod` 里，不新增库。**源码事实**（`github.com/pkg/sftp v1.13.11`，`client.go:765`、`packet.go:1227`）。

选它而不是另开一条命令通道跑 `df`：

- 复用现有 SFTP 连接，每次上传只多发一两个包（`--sudo` 时目标与 `/tmp` 各一个），不新开 exec 通道；
- sftp-only / scponly 账号也能用（这类账号禁 exec，而运维环境里常见）；
- 拿到的是数字，不用解析列宽、单位与 locale，也不用自己匹配挂载点——按路径问，服务端算的是该路径所在文件系统。

服务端不支持这个扩展时**静默跳过**（执行者提议，作者未反对）：预检失效可以，挡住上传不行。不新增「探测失败」分类。降级按侧算——某一侧探不出来就少那一侧的判断，另一侧照常，两侧都探不出来等于没有预检。

### 2. 两侧各按自己的峰值判，硬比不留余量

（目标的量取法由执行者提议、作者 2026-10-26 原话选定：「按你推荐目标，按总量暂存，按最大文件量」。余量口径为作者原话：「判断硬笔一点余量不留，就硬笔真的判断错了。后面实际上还有传输失败后回滚兜底呢」。）

`--sudo` 上传是两段写：先进登录账号的暂存目录，再以 root 移到目标目录。**源码事实**：暂存根是常量 `/tmp/.SSHFleet_tmp/`，每个文件建一个随机子目录、`sudo mv` 后删除（`internal/ssh/sftp.go:20`、`:507`–`:565`，由循环逐文件调用 `:173`）。所以两侧的峰值不是一个数：

| 一侧 | 需要量 | 可用量取谁 |
| --- | --- | --- |
| 目标目录所在分区 | 本次总量（文件在目标目录里累加；跨分区时 `mv` 退化为复制，仍是累加） | `--sudo` 下 root 写，取 `Bfree`；非 sudo 取 `Bavail` |
| 暂存目录所在分区 | **最大单个文件**（传一个移一个，暂存区任何时刻只有一个文件） | 登录账号写，取 `Bavail` |

判据：`可用 < 需要` 即判满，不留余量。判宽判窄的代价不对称——误拦是「本来传得动却传不了」，误放是「白传一次，回滚兜底」。作者选硬比，等于承认偶尔会白传真到边缘的情况，换判据简单。

不判断两侧是否同一分区：同区时暂存侧的需要量天然小于目标侧，不会多拦一次，多一个 `Fsid` 比较只增加分支。

### 3. 分类按两侧拆开，不合成一条

（作者原话：「关于『暂存目录已满』，单独给它分类，分类要分得细一点：到底是『目标磁盘分区已满』，还是说『暂存目录分区已满』，都细化一点。」）

- **目标磁盘已满**：非 sudo 与 `--sudo` 都可能；
- **/tmp 空间不足**：只在 `--sudo` 且登录账号不是 root 时可能出现——非 sudo 是直接写目标，没有暂存这一步（源码事实：`sftp.go:469` `sftpClient.Create`）。

两个名字是作者 2026-10-26 混搭选定的（原话：「A 的目标磁盘已满，C 的 temp 空间不足」）：目标侧用「已满」直说，不再解释；`/tmp` 侧名字里带路径，因为「暂存目录」是我们自己的说法，使用者认不出来。

报文各一条（只陈述事实、带两个数）：`sshfleet.transfer.target_space_short` / `sshfleet.transfer.tmp_space_short`。两种场景的细节不同——预检那条多一句「no file written」，失败后再查那条给「还差多少」，不说没写文件（那时已经写过并回滚）。

分类名**不区分「有没有开始传」**（作者 2026-10-26）：「不管他有没有开始传，咱们都有兜底删除……到达目标一定是干净的。用户不需要区分有没有开始传，只需要区分目标是不是满了。」这句话进了报错原文，进日志，不进分类。

排序不新立规则：回滚那两条仍排在所有传输失败原因之前（ADR-0022「顺序规则」），这两条排在其后。

### 4. 失败后再探一次，只改归类不改行为

（作者原话「如果传输过程中失败了，咱们再检查一遍」；「只在写失败出口探、探测失败静默降级」为执行者提议，作者未反对。）

- 只在**写失败**这一个出口加探测。撞名、本地读不了、取消这三个出口不加：原因已经明确，探测只会多一条会失败的路径。
- 判据与预检同源：`可用 < 剩余未传量` → 归到对应那一侧；否则维持原分类（说明满不是这次的原因）。
- 探测本身失败一律降级，不改变上传结果——**删是必做的，探测只影响呈现**。这条性质是这个设计敢加第二次探测的前提。

### 5. 不做的事

- 不在失败后另开命令通道探 `df`（见备选方案）；
- 不做逐文件探测（只买到「早一步知道」）；
- 不给暂存目录加配置项（已知缺陷：出现「/tmp 空间不足」时使用者手上没有可调的开关，本决定只把现象报出来）；
- 不管配额（`StatVFS` 是分区级，用户/组配额不在其中）；
- 下载侧不做（ADR-0022 决定第 5 条）。

## 实测记录（2026-10-26）

环境：目标机 WSL2 Ubuntu 26.04（`SSH-2.0-OpenSSH_10.2p1 Ubuntu-2ubuntu3.6`），Windows 侧用 `pkg/sftp v1.13.11` 直连；登录账号是一个临时创建的非 root 账号。容量上限用 64MB ext4 镜像经 loop 挂载成真实块设备（不是 tmpfs）。

| 验的事 | 结果 |
| --- | --- |
| 服务端支不支持 `statvfs@openssh.com` | **支持**。`StatVFS` 返回 `Blocks/Bfree/Bavail/Frsize`，无需回退 |
| 是否按路径所在文件系统取值 | 是。那块 64MB 卷的 `Fsid` 与根分区不同，返回值也是 55MB/51MB，不是根分区的 1TB |
| 目标目录是 700 root 时还能不能查 | 能（实测）。为什么能只是推断：探测大概只需要路径可达、不需要目录本身可读可写——这一句没有单独构造用例验证 |
| 「查得到」是否等于「写得进」 | 不等于。同一目录非 sudo `Create` 直接 `permission denied` |
| 写满时服务端回什么 | 往 52MB 可用的卷写 60MB，到 53,805,056 字节时回 `sftp: "Failure" (SSH_FX_FAILURE)`，状态码 4——与旧 tmpfs 实测同一形态，换到真实块设备上不变 |
| `Bfree` 与 `Bavail` 差多少 | 满盘后 `Bfree`=1150 块（约 4.5MB）、`Bavail`=4 块（约 16KB）。决定 2 里「sudo 读 `Bfree`」不是理论洁癖 |
| 半成品谁删 | 原始客户端不删，文件留在目标机（53MB，属主是登录账号）；删它的是工具自己（非 sudo 走 `Remove`）。旧记录里「半成品已删」说的是工具的行为，两者不矛盾 |

**局限**：只在 OpenSSH 10.2p1 上验过；同为 OpenSSH 的 7.4（CentOS 7）没验，非 OpenSSH 派生的服务端也没有样本。

## 理由

- **「失败后说出原因」在原协议上做不到，所以只能事前问**。`SSH_FX_FAILURE` 是通用码，实测过（报文议题 04）；把它当磁盘满的判据会连权限失败一起认走。事前问是唯一拿到数字的地方。
- **收益点是「别白传」，不是「让失败可解释」**。回滚已经保证失败不留残留、可以直接重传，所以事后知道原因的边际价值低；而事前拦住能省掉整段传输时间。
- **两侧的峰值本来就不同，用一个数会有一侧判错**。100 个 1MB 的文件、`/tmp` 只剩 10MB：按总量判会拦下一个本来传得完的任务；反过来按单文件判目标侧会严重漏判。
- **`StatVFS` 的失败模式是「没有」，而 `df` 的失败模式是「多一条错误」**。前者最坏退回今天的样子，后者会往分类表里塞一条新的失败原因。
- **分类拆两条是因为处置动作不同**：清目标目录所在分区（或换 `-p`）与清 `/tmp` 是两个地方，合成一条会指错盘。

## 影响

- **执行侧**：上传流程在进入逐文件循环前多一到两次探测（非 sudo 一次，`--sudo` 两次）；写失败出口再各有一次。这些探测都可能不存在（服务端不支持，或某一侧探不出来）。
- **报文**：新增 `transfer.target_space_short` / `transfer.tmp_space_short`，需同步判据表与语料。报文名说「空间不够」、分类名说「已满」，两者不同源：判据是 `可用 < 需要`，未必真到 0；分类名由作者定为直说的「已满」，报文按事实给两个数。
- **配置接线**：分类名只从 `keywords_error.conf` 的 `[[categories]]` 里来，`keywords` 必须写报文全前缀，否则该条失败永远匹配不上、统计块直接显示英文原文（这是这批改动最容易漏的一步）。
- **分类与配置**：出厂配置新增两条分类，各带一句「怎么改」的提示。「目标机写入失败」的提示语目前把「磁盘满」列为自己的一种原因；本决定生效后，装不下会先在预检处被拦下，那句提示语要不要撤掉「磁盘满」由措辞轮次判定，不影响本决定。
- **使用手册**：上传一节要写清「空间不够会在开始前报出来，本次不写任何文件」以及「`--sudo` 时两块盘都算」。
- **不改变**：回滚范围与顺序、撞名不覆盖、取消回滚——本决定只加探测与归类。

## 备选方案

| 备选 | 否掉的原因 |
| --- | --- |
| 失败后另开命令通道跑 `df`，解析出剩余空间 | 要 exec 权限（sftp-only 账号直接不可用）、要解析文本与挂载点、多一条会自己失败的命令路径；而拿到的是同一份信息 |
| 用一次 `find`/`du` 估算目标目录已用量 | 目标目录可能混着别人的文件，算出来也不是可用空间；且大目录下这本身要跑很久 |
| 预检不发报文，只打一行提示 | 使用者拿不到分类，统计块里看不出问题；而这一档恰恰是「传之前就该知道」的事 |
| 两侧都按总量判 | 暂存侧会误拦，最坏差到「总量 ÷ 最大单文件」倍 |
| 两侧都按最大单文件判 | 目标侧严重漏判——文件在目标上是累加的 |
| 每个文件写之前都探一次 | 每次多一个包与一条失败分支；而真到那时候前面已经白传，回滚照样全删，回收不了时间 |
| 留一点余量（如总量 1%） | 作者定硬比：边缘失败由回滚兜底，判据简单优先 |
| 分类合成一条「磁盘空间不足」 | 「清哪块盘」的动作不同，合成一条会把 `--sudo` 的使用者指向目标盘而实际满在 `/tmp` |
| 把暂存目录做成可配置，让使用者自己挪 | 本轮范围外；但它是「/tmp 空间不足」这条分类没有处置手段的根，已作为已知缺陷记下 |

## 复审

**方法纪律（下次要重新判定时照这几条看）**：

1. **先量再改判据**。判据是否合适取决于「实际发生过的边缘失败次数」，这个数只能从真实使用里攒；在攒到之前不动阈值，也不加余量。
2. **探测的支持面按机器统计，不按产品名推断**。本仓库只验过 OpenSSH 10.2p1（见「实测记录」）；换一类服务端就得重新跑一次，别拿这一条去推断「OpenSSH 都支持」或「某产品不支持」。
3. **失败后再查的判据若与预检出现分歧，先合并口径再谈放宽**——两套数字并存会让人拿不同的结论讨论同一件事。
4. **报文与分类名改动走既有登记路径**，不在本 ADR 里就地改写。

**未证实清单（引用前需重新确认）**：

1. **生产目标机的 `/tmp` 落在一块什么分区上**——只有作者陈述（2026-10-26：生产机是物理盘），本仓库未复核。它只影响「暂存侧满」有多常见，不影响判据本身。
2. **跨分区 `mv` 退化为复制**——依据是源码里的一句注释（`sftp.go:556`）加源码推断，未实测；它决定「同区时两侧判据是否重复」，若结论反了，暂存侧判据会偏严。
3. **磁盘真满时回滚能否删干净**——未实测。删除不需要空间，推断可行；`--sudo` 路径的临时文件不进回滚清单，靠另一条报文单独报，这一档也没在真满的卷上验过。
4. **非 OpenSSH 服务端支不支持 `statvfs@openssh.com`**——没有任何样本。支持度只验过 OpenSSH 10.2p1（见上「实测记录」）；不支持的机器上预检静默失效，行为与今天一致。
