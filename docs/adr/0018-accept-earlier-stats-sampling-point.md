# ADR-0018: 接受统计取样点提前，不为此复原

- **状态**：已接受（accepted）
- **日期**：2026-10-17

## 背景

2026-10-07 的架构审查整改里，有一项是「成功 / 失败的个数数了三遍」——`batch/progress.go`（进度条实时聚合）、`result/statistics.go`、`main.go`（主干收尾行）各数一遍。做法是删掉主干自己数的那段，把 `Statistics` 的计算上移到收尾行之前，收尾行四个数全部读统计。

上移时把它的实参 `time.Now()` 也一并带到了前面，于是统计的「执行结束时间 / 总耗时」取样点比原来早——早了旧主干的计数循环、收尾行与两项检查那点耗时，量级在微秒。

这件事在当轮的 A/B 里没被发现：A/B 把时间数值归一化掉了，结构上看不见这一类漂移。是后来的审计（提交 `1d622fb`）查出来的。

## 决定

**接受这个取样点的提前，只为它订正措辞，不把取样点改回去。**

## 理由

要严格回到原取样点只有两条路：

1. **把收尾行移到 `fatal` 检查之后**——代价是**出错时执行期日志不再有收尾行**。
2. **二次取样回填**——多一份状态，且「结束时间」变成两个时刻拼出来的值。

**两条路都比现状差。** 而漂移本身只在 `report.txt` 的「执行结束时间」六位小数里看得出，对使用者没有实际影响。

## 后果

`report.txt` 的「执行结束时间」自 `a699f7e` 起与重构前不同（早微秒级）。这一条此后**不要当成缺陷来报**——它是知情且明示的取舍。

由此还带出一条验证方法上的教训：**A/B 里把时间数值归一化掉，这类漂移就看不见了**。以后做「逐字一致」类验证时，要把「归一化掉了什么」写清楚，别让归一化掩盖掉一类变化。
