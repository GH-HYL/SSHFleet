# ADR-0013: 执行模式的名字集中到一处（判定仍留 ModeName）

- **状态**：已接受（**已实施**，提交 `b2956d5`；真机 A/B 复验通过，2026-10-07——见文末《2026-10-07 实施记录》）
- **日期**：2026-10-07
- **前身**：ADR-0003《执行模式判定不做集中化》（2026-09-29 已被推翻）

## 背景

ADR-0003 的《2026-09-29 推翻》节裁定重开此事，理由是其唯一前提「模式集合已封闭」被 ADR-0011 打破（改密成为第 5 档）；并明写「集中化的形状重新开放，**新决定另立 ADR**」，文末留了三个待定项。本 ADR 就是那个新决定。

代价已被实测过一次：落地改密那一档，整个特性一次动了 **28 个文件、8 个 Go 包**；其中模式名字相关的核对点 7 处、要手改的 4 处（`cli/check.go` 的五选一互斥、`batch/batch.go` 的文案表、`output/report.go` 的报告段落、`confirm/confirm.go` 的参数屏）。

现状：一个事实——「这次是哪种模式」——有 **9 套叫法**，散在各包里各写各的（行号为 8.1.1 时点）：

| 叫法 | 位置 |
| --- | --- |
| 判定 | `cli/args.go` `ModeName()`——**唯一的正规判据点** |
| 日志中文名 | `batch/batch.go` `execModeName` |
| 归档目录英文名 | `output/archive.go` |
| 报告「执行参数」段落 | `output/report.go` |
| 统计档名 | `result/statistics.go` `ModeOf` |
| 「算不算传输类」 | `result/statistics.go`、`output/terminal.go` |
| 超时行措辞 | `confirm/confirm.go`、`output/report.go` |
| 参数屏模式行 | `confirm/confirm.go` |
| 动作中文名（执行/上传/下载/改密） | `output/terminal.go` `ActionName` |
| 成功分类中文（执行成功/传输成功/改密成功） | `result/statistics.go`、`output/terminal.go` |

2026-10-07 的 `8.1.1` 已先用最小改动把改密的两个漏格补上（参数屏与报告看不到超时值、改密成功被显示成「执行成功」），但「各写各的」这套结构没动，所以才需要本 ADR。

作者 2026-10-07 对第六档的判断：**可预见范围内没有，但不能断言永远不会有**。故按「会不期而来」准备。

## 决定

**判定不动，名字集中，消费方一律去问它。**

1. **判定保持单点**：`cli.Args.ModeName()` 继续是全工具唯一的「这次是哪种模式」判据，调用方式不变。
2. **名字集中一处**：每种模式的**全部叫法**——判哪档、日志中文名、归档英文名、报告段落标题、统计档名、算不算传输类、超时行措辞、参数屏模式行、动作中文名、成功分类中文——集中到一处维护，挂在**既有的 `cli.Mode` 类型**上（不新建包）。
3. **消费方只问它**：其余各处不再自行比对参数与字符串（`args.Command != ""` 这类），改为向这一处取名字。
4. **漏改不静默（启动期自检）**：Go 没有编译期的穷尽检查（见《理由》第三条，已实测）。改为程序**启动时**遍历模式全集做一次自检：任一格的名为空即停下，并明确报出漏了哪个模式。用标准库实现，不引入任何外部工具。

## 理由

1. **为什么做**：新加一档的代价已被实测（28 文件 / 8 包 / 7 处核对 + 4 处手改），而这套结构的问题不是「将来可能痛」，是**已经痛过一次**（《个人开发规范》二认这条：得有实际发生过的干扰）。可预见范围内虽无第六档，但无法断言永远没有；把名字收成一处，成本远低于每加一档散改一轮。
2. **为什么只集中名字、不动判定**：痛的部位是**派生名字的分散**，判定本身早就是单点。连判定一起类型化，要把 5 个消费方从「读字符串」改成「走新枚举」，改动面从「一张映射表」涨到「一批调用签名」，而业务正确性不因此增加。这也是审查报告候选一自己写下的形状。
3. **为什么不用编译期保证**：`漏改编译不过` 这句话在 Go 里**不成立**。已实测：显式长度的数组字面量允许少给元素（缺的补零），`switch` 也从不要求穷尽——少写一格，编译照样过，只是那格为空。要接近这个效果只有两条路：引入 `exhaustive` 一类的静态检查工具（多一个依赖，且它报的是 lint、不是编译；本地构建脚本还要多一步），或在程序启动时自检。选后者：零依赖，把「安静的错误」变成「一启动就响」。
4. **为什么不借机扩大**：本次只做名字集中。执行流程、结果判定、参数校验的既有分工一概不动。

## 影响

- `cli` 包新增一张模式名字表（挂在既有 `Mode` 类型上）；`output` / `result` / `batch` / `confirm` 的对应映射改为读它。**这四个包本来就 import `cli`，不新增任何依赖边**。
- **`ssh` 包不参与**：`ssh/command.go` 里那两处「这次发的是命令还是脚本」是 `BuildCommand` / `DescribeCommand` 的**输入契约**判断，不是「这次是哪种模式」的叫法；该包刻意不认识参数载体（见该文件头注释）。收进去反而要给 `ssh` 引 `cli` 依赖、破坏这条边界。
- **`cli/check.go` 里数「指定了几个模式」的互斥校验不合并**：它要报「指定了几个」，不是取哪一档。ADR-0003 已明写，本条继续成立。
- **与 D2 的关系（`docs/issues/result-verdict/spec.md`）**：D2 管的是「结果结构体只存英文成败枚举，中文由消费侧按模式给」。本 ADR **不改这条实质**——结果结构体仍存英文，转换仍发生在消费侧，只是**映射表搬到了 `cli`**、消费侧改为调它。D2 里「统计侧按模式转中文」的**位置措辞**随之更新，**不是翻案**。
- **第六档的代价从此收敛**：以后加一档，改这一张表 + 编译器/自检指路，不必再逐处核对 7 个点。
- 三处写着「四种 / 四选一」的过时注释（`batch/batch.go`、`output/archive.go`、`cli/args.go`）随名字集中一并清掉。
- 实施落在 `docs/issues/mode-centralization/`（`spec.md` 记实施形状 + 实现工单 `01`–`04`）；来源工单是 `docs/issues/architecture-review-2026-10-06/issues/05-mode-centralization.md`。完成后本条《状态》改为「已实施」。

## 备选方案

| 方案 | 为何未采用 |
| --- | --- |
| 连判定一起类型化（新枚举取代 `ModeName()`） | 改动面从映射表涨到调用签名，业务正确性不增 |
| 什么都不加，漏改就漏改 | 等于放弃集中化唯一没打折的好处，回到「靠人记住还有几处要改」 |
| 引入 `exhaustive` 一类静态检查工具 | 多一个工具依赖（《个人开发规范》二：未经要求的依赖一律不引入）；它报的是 lint 而非编译，与「编译不过」仍不是一回事；本地构建脚本要多一步 |
| 名字表放新建的独立包 | 无必要：`cli` 已经持有 `Mode`，各消费方也都已依赖 `cli`；新建包只多一层间接 |
| 顺手把 `ssh/command.go` 那两处也收进来 | 会破坏 `ssh`「不认识参数载体」的既有边界，且那两处本就不是模式叫法 |

## 2026-10-07 实施记录

**代码已落地**（提交 `b2956d5`，17 文件）。三票完成：名字表 + 启动期自检、统计与呈现侧迁移、日志/报告/归档/参数屏迁移。

本节两处待定项的定答：名字表取**一张描述表**（`ModeInfo` + `modeTable` + `func (Mode) Info()`，挂在既有 `Mode` 上）；自检落点为 `cli` 包的 `init()`，报错形如 `执行模式名字表缺格：模式 "script" 没登记`（已实测：故意删空一格，启动即 `panic` 并指名到模式）；导出符号的迁移方式取**改签名**（`ActionName` / `displayCategory` / `NewReporter` / `WriteOutputXlsx` / `WriteResultsXlsx` / `newProgressModel` 的 mode 入参由 `string` 换成 `cli.Mode`），`result.ModeOf` 与三个 `SuccessCategory*` 常量**删除**。

**一处实施后才看清的边界——本 ADR《影响》节写得满了，以本节为准**：

「加一档只改一张表」这句**只对名字成立**。每个模式在参数屏、报告、执行期日志与任务构建里**显示哪些字段、构建哪条任务**是**结构性差异**，不是名字，那几处仍是各自分派，第六档还要各加一路。实施后仍会碰到的位置：

- `cli/check.go` 的「指定了几个模式」互斥校验（刻意不并，见 ADR-0003）；
- `batch/batch.go` 的 `buildTasks` 与 `work`（每档构建的任务不同）；
- `output/report.go` 的「执行参数」段落（每档显示的字段不同）；
- `confirm/confirm.go` 的 `buildInfoTable`（同上）；
- `output/reporter.go` 的 `logNode`（命令/脚本看退出码，传输看文件数，改密看耗时）。

所以第六档的真实代价是「**名字零改 + 结构分派照旧**」。这不是缺陷，是分工：名字能单源，结构不能。

**旁证**：迁移后除 `cli` 的名字表外，全仓**生产代码**里已无任何模式字符串或模式文案字面量（已逐处 grep 核对；`config` 的 TOML 段名 `upload`、`ssh` 的中间步骤语义名 `passwd`、`dangercheck` 的包装命令名 `command` 属别的域，非模式叫法）。

**真机复验（2026-10-07）**：重构前后各编一个二进制，用同一份配置、同一份清单、同一组参数跑五条执行模式路径，归一化（只抹时间数值与二进制自身路径）后**逐字比对** stdout 与六项归档产出（`report.txt`、`terminal-output.txt`、`SSHFleetExec.log`、两张 xlsx 的文本）——**全部一致**。唯一差异是改密路径的远端回显行（脱敏后形如 `****`）：6 轮重复下两个二进制**各自**都会出现 2 或 3 次，属远端 tty 回显与 `passwd` 关回显之间的竞态，与本次改动无关。明细见 `docs/issues/mode-centralization/issues/04-closeout-and-verify.md`。
