# ADR-0021: 失败原因统一为「报文」，分类名一律由配置匹配决定

- **状态**：已接受（accepted）—— **已实施**（2026-10-20，工单 01–07 全部完成；实施过程中与初始框架的偏差见文末「实施进度」与各工单 Comments；`transfer.finished` 及「部分成功」由 ADR-0022 接替退役）
- **日期**：2026-10-20
- **决策人**：作者（2026-10-20 本轮对话；同日多次修订，见文末「更新记录」）
- **实施载体**：`docs/issues/2026-10-20-1604-报文式失败分类/spec.md`

## 背景

一次执行里，「这台机器为什么失败」这件事，现在有两个来源：

1. **远端与系统说的话**：sshd 的拒绝语、PAM 的提示、`dial tcp: connection refused` 这类原始错误。它们进结果的事实区（报错原文 / 服务端提示 / 输出），交给判据文件按关键词归类。
2. **工具自己编的话**：`建立连接失败 - …`、`申请终端失败 - …`、`远程路径不存在: …` 这类**中文前缀**，以及「部分成功」「任务已取消」「没等到提示」这类**直接写死的中文分类名**。

第二个来源是问题所在。2026-10-14 那轮改造已经把「执行侧编一句『改密没有完成』、判定层再靠关键词认回来」这种形态治掉过一次，但只治了改密那一族。实际上它还散在这些地方：

- `internal/ssh` 里 **47 处**产出中文文本的位置：`Error = strPtr("…")` 11 处、中文 `fmt.Errorf` 21 处、用 `fmt.Sprintf` 拼出的中文原文 15 处（后者集中在上传 / 下载，其中一部分进报错原文、一部分进输出明细）；
- `internal/batch` 里 10 处中文 `fmt.Errorf`（上传清单缺失、解释器未解析、下发行未拼出、文件类型不支持等）；
- `internal/verdict` 里 **11 个中文分类常量**——它们不查表，由代码直接给；
- 判据文件里 **23 条关键词**匹配的**正是工具自己编的中文**，散在 10 个分类里：`SFTP失败` 8 条、`本地文件错误` 4 条、`无法建立会话` 3 条、`远端没有文件` 2 条，`握手超时`、`执行超时`、`远程路径不存在`、`远程文件已存在`、`sudo失败`、`密钥解析失败` 各 1 条。它们都是拿程序里的字面量当匹配串——改程序措辞就静默失效；
- 兜底判定靠代码里一张手写名单区分「程序定性的分类」与「兜底原文」——名单与配置是同一事实的两份副本，2026-10-18 就漏补过一次。

作者 2026-10-20 的判断：**工具的报文也是事实，它和远端报文没有本质区别，就不该有两套规矩。要么都交给配置匹配，要么都别交给配置。**

## 决定

### 1. 报文：工具自己说的话统一成一种格式

```
sshfleet.<环境>.<环节>: <英文描述>
```

- `sshfleet` 是固定前缀——一眼看出这条是工具报的，不是远端、不是系统；
- `<环境>` 是报文所属的一摊，取值固定为：`connect`（建连与认证）、`session`（会话与终端）、`run`（命令执行）、`transfer`（传输）、`passwd`（批量改密）、`answer`（代填）、`abort`（中断与取消）；
- `<环节>` 是该摊里的具体情形，小写、单词间用下划线；
- 冒号后接一句英文陈述；跟在 Go / 系统原始错误后面的，**原始错误原样保留、不吞不改**。

示例：

```
sshfleet.connect.refused: dial tcp 10.0.0.5:22: connect: connection refused
sshfleet.connect.handshake_timeout: handshake not completed within 5s
sshfleet.session.create_failed: ssh: session rejected
sshfleet.session.pty_failed: ssh: pty request failed
sshfleet.run.timeout: exceeded 30s
sshfleet.transfer.finished: 6 of 10 files transferred
sshfleet.transfer.remote_missing: remote path not found: /data/app
sshfleet.passwd.no_signal: no password prompt seen before timeout
sshfleet.abort.canceled: canceled after the session was established
```

### 2. 格式本身要固定下来

前缀、环境取值、分隔符、冒号后一句陈述，都写在代码注释里（放置「报文格式」那处声明），新增报文一律照此写，不另立样式。

### 3. 分类名一律由配置匹配决定，代码不再直接给中文分类名

- **所有失败原因都以报文形式进入「报错原文」这一格**，包括两类：
  1. **工具自编的错误文本**（建连失败、申请终端失败、文件不可读……）——直接换成报文；
  2. **结构性结论**（传输有的成有的没成、改密卡在哪一步、被中断、代填补送不完……）——由**看见该事实的那一处**在收尾时生成一条报文陈述事实（`sshfleet.transfer.finished: 6 of 10 files transferred`），而**不是**由判定层编造；
- 判据文件里一个分类可以挂两类关键词：远端与系统的话、工具自己的报文，**同一套匹配、同一套优先级**；
- 匹配不到任何分类时，分类就是报错原文本身（与今天「未归类」的口径一致）。

**判定层不再有任何「按结构字段直接给分类名」的分支。** `Judge` 不再读 `FailedFiles` / `AbortLine` / `AnswersMissed` / `EnterSignalSeen` 这类字段去决定分类名——它只读**成功规则**所需的字段，以及待匹配的文本。

**唯一例外是 `执行失败(退出码N)`**：那个名字里带一个数字，配置文件写得了前缀、写不了变量，做不成报文可匹配的关键词。它仍由判定层按退出码拼出，是本议题唯一一处「代码给名字」；其余任何地方都不许再出现。

### 4. 删掉为「程序定性」另开的那条通道

判定层不再有那 11 个中文分类常量，也不再需要豁免名单。2026-10-20 当天引入的配置字段 `code_defined` **随本决策一并下线，视同从未存在**——它标记的「分类名由程序给出、不查表」这件事，在本决策下不再存在。一个分类名是否「已知」，只看它在判据文件里有没有登记；登记的途径只有关键词，而关键词现在能认报文。

### 5. 中文只出现在两个位置

- **配置文件里的分类名与提示语**（`name` / `tip`）；
- **呈现层的中文译文**：报文在终端、`output.txt`、`report.txt` 里翻译成中文给用户看；`results.xlsx` 与执行日志保留报文原文，作为排查底本。

**报文是给程序和配置认的，中文是给人看的，两者不再混在一起。**

### 6. 不动 Go 库与系统给出的原始错误

`dial tcp …: connect: connection refused` 这类是权威原文，它跟在哪条报文后面就原样待着。报文前缀是**我们的**，它后面那段是**别人的**，含混信息一律不吞。

### 7. 不考虑兼容

这是重构，旧配置整体重写，不留兼容分支（作者 2026-10-20 定）。

### 8. 执行侧与判定层的界：只许无损翻译，不许替使用者下结论

这件事有第三方参与：`golang.org/x/crypto/ssh` **已经做了分类**（`*ssh.ExitError`、`*ssh.ExitMissingError`、`*ssh.PassphraseMissingError`、超时错误）。因此「谁分类」不是两层而是三层，边界必须写死：

| 层 | 做什么 | 不许做什么 |
| --- | --- | --- |
| ① 库 | 已经分好类的错误 | —— |
| ② 执行侧（`internal/ssh`、`internal/batch`） | 把 ① 的分类**无损翻译**成报文；把库没分类的原始文本原样附在报文后 | **不许说「这算什么分类」**——②并不知道配置里那条分类叫什么名字 |
| ③ 判定层（`internal/verdict`） | 拿报文与远端原文去查表 | **不许自己定义分类名** |

三条硬规矩：

1. **每一层只许做无损翻译。** 库已有的分类信息**不许丢**。当前 `extractExitCode` 只认 `*ssh.ExitError`，`*ssh.ExitMissingError` 被直接丢弃、退化为靠关键词 `remote command exited without exit status` 匹配库的提示原文——库升级改了措辞就会静默失效，与「工具自编中文」属同一隐患，按本决策改为由 ② 翻译成报文（`sshfleet.session.exit_missing`）。
2. **报文只陈述位置与事实，不陈述结论。** 环节名说清「哪一步、什么现象」（`session.create_failed`、`transfer.finished`、`abort.canceled`），**不写 `partial` / `failed` 这类替使用者下结论的词**。叫不叫「部分成功」，是配置里的 `name` 说了算。因此传输收尾的报文是 `sshfleet.transfer.finished: 6 of 10 files transferred`（这批 10 个里成了 6 个），不是 `partial`。
3. **判定层读结构字段只为成功规则。** 成功与否仍按各模式的成功规则从结构字段判定（退出码为 0 且未超时未中断等）；**失败分类则一律从报文查表**。判定层不存在「如果失败文件数 > 0 就给某个名字」这样的分支。

### 9. 密码过期不套用上面的分类：它是远端说的话，不是工具说的话

「密码过期」在 11 个旧分类常量里是最特殊的一个，本决策必须单独交代它，否则会被误当成「又一个结构性分类」。

**它实际长什么样**：连接与认证**全部成功**，`ConnectSuccess` 为真，看不到任何异常。真正的事发生在会话内部——客户端请求执行命令时，sshd / PAM 先把会话切成改密对话（`WARNING: Your password has expired.`、`You must change your password now…`、`Current password:`），**标准输出收回来的不是命令的输出，而是改密向导的对话**；改密没走完，会话随即以**非 0** 收场。

**它因此在三个模式里有三种走法，但指向同一批关键词**：

| 模式 | 怎么走到这里 | 查哪一组判据 |
| --- | --- | --- |
| 命令 / 脚本 | 会话以非 0 收场 → 有退出码 → 拿输出与报错去查表 | 第二组（有退出码） |
| 代填（`-a`） | 输出里出现中止词 → **中止会话、提前结束**，命中原文并入待匹配文本 | 第一组 |
| 改密 | 同一批提示是**入场信号**：没出现过在场的提示，就说明这台机器不需要改密 | 入场门（`Keywords.PasswordExpired`） |

由此确定三件事：

- **那个非 0 退出码不属于任务。** 它是会话结束时的状态码，密码过期时来自 PAM 改密对话。**它来自哪里不重要**——客户端看不见、也分辨不了。重要的是「会话以非 0 收场」这个信号本身，它把判定导向第二组；真正定分类的，始终是输出里那几行改密向导的原话。判定层**不许**为了这个码再发明任何「它是不是命令的」判断。
- **判定层不许写死「密码过期」这个名字。** 现在 `Judge` 里有一条 `if res.AbortLine != "" { 分类 = "密码过期" }`——中止确实意味着密码过期，但分类名不该由代码给。改为：`AbortLine` 仍作为事实保留（呈现层用它说明会话为何提前结束），其原文并入待匹配文本，分类照常由判据表给出。
- **改密的入场信号与代填的中止词取的是配置里「密码过期」那条分类的关键词**（`Keywords.PasswordExpired` → `KeywordsOf("密码过期")`）。**它是按分类名查表的**，所以：换那条分类的 `keywords`，两个用途一起跟着变（改配置就改行为，这是想要的）；改那条分类的 `name`，查表会落空、两个用途一起失效——改名的落点在代码里，必须同步改 `keywords.go` 里的那个字面量。这条限制在本次改造前后都成立，本决策不改它。

**因此密码过期没有报文**，它的报文全在远端。这不与第 3 条冲突：第 3 条说的是「工具自己看见的结构事实也要说成一句报文」，而密码过期从头到尾是远端的输出，工具只是把它读了出来。

## 理由

- **两个规矩必然要分叉**：只要工具自己编的话走「代码直接给分类名」，它就和远端报文走在两条路上，迟早要为它再发明一个字段。2026-10-20 那版加的 `code_defined` 就是这种补丁——它让用户多学一个字段，只为了配合代码的写法。报文把两条路并成一条，那个字段就不需要了。
- **认领权交回配置文件**：用户能删一个分类、能改它的名字，这两件事在今天的「程序定性」分类上做不到（名字写死在代码里）。并成一条路之后，所有分类的增删改名是一个规矩。
- **格式固定才有长期价值**：报文能当关键词用，前提是它**可预期**。前缀带项目名，用户在配置文件里看到 `sshfleet.` 开头就知道这是工具报的，不会和远端报文混淆；`<环境>` 让一条关键词能按范围收放（认整摊、认单条）。
- **中文留在配置与译文两处，各自有主人**：想改用户看到的措辞，改配置文件或者改译文层，不用改代码内部。
- **「只许无损翻译、不许下结论」让三层各有其职**：执行侧只对自己看见的现场负责，判定层只对配置负责，配置归使用者。任何一层越界，另一层就无法自证——这正是 2026-10-18 那次事故的成因（执行侧写了结论，判定层的名单却没跟上）。

## 影响

- **`internal/ssh` / `internal/batch`**：47 处中文错误文本（`strPtr` 11 处 + `fmt.Errorf` 21 处 + `fmt.Sprintf` 15 处）改为报文；`internal/batch` 另有 10 处中文 `fmt.Errorf`。进「输出明细」而不进报错原文的那几处（逐文件的成功 / 跳过行）保持中文——它们是给人看的运行日志，不参与分类匹配。
- **有一小类不归报文管**：既不会被当作失败原因去匹配、也不是给用户看的报错——例如启动期写进工具日志的诊断提示、参数校验报错（`触发词不是合法正则：…`、`未提供有效的认证方式…`）。这些保持中文，不套报文壳子（报文是给匹配与呈现用的，不是给日志与参数校验用的）。
- **`internal/verdict`**：11 个中文分类常量退役，`Judge` 中「一级定性」那段分支删除；兜底判定不再需要豁免名单。**「密码过期」除外**，它按第 9 条处理：分类由输出原文查表给出，入场信号与中止词取 `Keywords.PasswordExpired`（配置里那条分类的关键词），不再依赖分类名由代码产出。
- **判据文件**：两份配置里那 10 条结构性分类改为挂报文；「密码过期」保持远端关键词（它在**通用表里有两份**：第一组与第二组各一条；改密配置里没有这一条，改密读的是合并后表里的那两份），但需核实词条覆盖改密向导的原话，因为代填中止后走第一组、只看这批词；**23 条以工具自编中文为关键词的条目全部改挂报文**——`本地文件错误` 4 条、`无法建立会话` 3 条、`SFTP失败` 8 条、`远端没有文件` 2 条，`握手超时`、`执行超时`、`远程路径不存在`、`远程文件已存在`、`sudo失败`、`密钥解析失败` 各 1 条；`code_defined` 字段删除。
- **`internal/output`**：新增报文 → 中文的译文层；终端、`output.txt`、`report.txt` 走译文，xlsx 与日志保留原文。
- **测试影响面大**：分类语料（`testdata/error_classification_cases.toml`）33 条里有 **17 条**的 `error` 字段是工具自编的中文，要换成报文输入（期望分类不变）；涉及 11 个分类名的测试断言实测 **72 处**，呈现层的字符串断言要跟着改。这是本议题里最容易被低估的一块。
- **使用者可见面**：终端与输出文件里的「错误」一行措辞会变（中间的报文前缀要翻译成中文）；配置文件的分类从此**都能挂报文当关键词**，而 `code_defined` 字段消失——它是 2026-10-20 当天引入、当天推翻、**未封包**的改动，视同从未存在，不构成对已发布配置的破坏。CHANGELOG 的写法按「这些功能本来就这样」处理（不交代沿革），版本号按不兼容抬主版本，使用手册需同步。

## 备选方案

| 备选 | 否掉的原因 |
| --- | --- |
| 只在判定层加一个字段（如 `code_defined`），保住代码直接给名字 | 用户要为配合代码写法学一个字段；名字仍然写在代码里，删不掉、改不了——补丁，不是根治 |
| 保留代码里的中文分类常量，只给它们加一份报文别名 | 一个分类有两个身份（常量 + 报文），两份要对得上，等于把分叉换个形状 |
| 只改判定层，`ssh` 包的中文前缀原样留着 | 工具自己编的话仍有两套规矩：`建立连接失败` 走关键词、分类名走代码。与「要么都交给配置」相反 |
| 报文只写中文，交给配置去认 | 中文当匹配串，改一个字就静默失效——正是本决策要消灭的形态 |
| 报文里不吞原始错误，改为全部翻译成中文 | 原始错误是权威原文，翻译不全且会丢信息；翻译只该发生在给人看的那一层 |
| 兼容旧配置（同时接受 `code_defined` 与新写法） | 作者 2026-10-20 定：重构不考虑兼容。两套写法长期并存等于把分叉多养一份 |
| 结构性分类不发报文，判定层继续按结构字段给名字 | 那就是两条路并存，只是换了个说法；且「部分成功」这类名字仍然删不掉、改不了（作者 2026-10-20 第 2 次修订推翻此方案） |
| 连上之后先统一发一条探测命令（如 `:`），提前判别密码过期 | 密码过期时那条探测命令**自己也跑不起来**——PAM 会先把它切成改密对话并以非 0 结束，于是得到的信息与之后真执行命令时完全相同；而在没过期的正常节点上，它只是一次白跑的往返。大集群里每台多一次往返是净成本，而命令本身就会说话。**改密模式的那条 `:` 不算在内**：那个模式下已经确知要改密，`:` 是它本来就需要的步骤，不是探测 |

## 更新记录
