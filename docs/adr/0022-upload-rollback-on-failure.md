# ADR-0022: 上传失败即回滚，不留「传一半」

- **状态**：已接受（accepted）
- **日期**：2026-10-20
- **决策人**：作者（2026-10-20 本轮对话）
- **实施载体**：`docs/issues/upload-rollback/issues/01-rollback-on-failure.md`

## 背景

上传一个目录时，若第 N 个文件失败，今天的做法是**中断该节点剩余传输**，把已写成功的文件留在目标机上，分类落成「部分成功」。理由是「已经传上去的是有用的，不该白删」。

2026-10-20 在报文议题的 04 里实测这个形态（两个文件只放得下一个）时，暴露出三件相互关联的事：

1. **呈现层口径打架**：统计块 `成功：0`（数节点）与错误详情 `finished: 1 of 2 files transferred`（数文件）同屏出现，使用者会误读成一个都没传成；
2. **`部分成功` 这个分类的边界很难讲清**：它要排在判据表第一组最前面才不被「权限不足」抢走，运维看到它仍要翻明细才知道哪个没传；
3. **重试的危险**：上传失败后重跑，撞上「远程文件已存在」就不再覆盖（既有行为），使用者得先手工判断哪些是上次的残留。

作者提出一个更简单的语义：**要么全传上去，要么一个都不留**。

## 决定

### 1. 上传失败即回滚

一个节点的上传只要有一个文件失败，就删除**本次已经写成功的那些文件**与**写到一半的半成品**，使目标机恢复到本次执行前的样子。

- 结果里照实记录「删了哪些、哪些没删掉」；
- 分类不再有「部分成功」：要么成功，要么失败。

### 2. 只删本次自己写的路径，绝不按目录扫

删除对象来自**成功写入时逐个记下的远端完整路径**，加上当前失败的那个文件。不 `find`、不匹配通配符、不删目录。

依据是上传的既有流程保证「写入前必查重名」：建 SFTP 后先 `Stat` 目标目录，逐文件再 `Stat` 远端路径，重名就停。所以**真正被写进去的每一个路径，都是那一刻远端确认过不存在的**，删它们不会碰到目标机原有的文件。

中途按需创建的中间目录留着不删——它们可能是别人早先建的。

### 3. 回滚失败要照实说

清理本身也可能失败（权限、连接已断、sudo 不可用）。这时：

- 不隐瞒、不重试到天荒地老，失败即停；
- 在报错原文里写一句陈述事实的报文：`sshfleet.transfer.rollback_failed: 2 of 3 written files removed, left: /data/app/x.bin`（措辞以实现为准，环节名以 `transfer.` 开头）；
- 成功清干净时也写一句 `sshfleet.transfer.rollback: 3 of 3 written files removed`，让使用者知道目标机没留下东西。

理由：下次执行撞上「远程文件已存在」时，使用者得能回过头看出是上次没清干净。

### 4. 「部分成功」与 `transfer.finished` 一并退役

回滚之后，工具自己不会再产生「部分成功」。出厂配置里那条分类与 `transfer.finished` 这条报文一起删掉——留着就是认领一个永远不会发的报文。

### 5. 下载不做回滚

下载失败时**不删**本地已下载的文件。理由与上传不同：

- **不会重名**：下载按节点 IP 建独立子目录，每个节点写自己的那份；
- **本地满读不出有用结论**：本地磁盘写不进之后，往往跟着一串连锁失败，逐个清理不比直接删目录更省事；
- **重试成本低**：删掉本地目录重下即可，删的是自己的产物，不涉及别人的东西。

## 理由

- **上传重试成本高、风险大**：上传写的是目标机上的生产目录，运维终端往往是人工逐台确认过的路径；万一清错，删掉的是别人的东西。而「传一半」的状态交给使用者自己判断，正是最容易出错的环节。
- **语义简单才守得住**：「全成或全不成」一句话能讲完，判定层、呈现层、使用手册都不用为中间态再立一套口径。报文议题 08 那个「数字口径打架」的工单因此可以整个撤掉。
- **删除范围可证明**：不靠「记住哪些是本次传的」这种需要额外维护的清单，而是靠既有流程已经保证的「写入前必查重名」。范围窄、可核对。
- **下载与上传的差异是真实的，不是不一致**：一边动别人的机器，一边动自己的机器；两者遵循不同规则，比强行统一更安全。

## 影响

- **执行侧**：上传失败分支增加回滚；结果里多两类事实（已清理哪些、没清掉哪些）。
- **报文**：新增 `transfer.rollback` / `transfer.rollback_failed`；`transfer.finished` 退役。
- **判定与配置**：「部分成功」分类从出厂配置删除；`transfer.*` 的环节名集合变动，需同步判据表与语料。
- **呈现层**：统计块口径照旧数节点（另见报文议题 08 的讨论），但不再有「部分成功」这一档的歧义。
- **使用手册**：上传的行为说明要写清「失败会清掉本次已传的文件」——这是使用者会直接感知到的行为变化。

## 备选方案

| 备选 | 否掉的原因 |
| --- | --- |
| 维持「传一半」，只把呈现口径改清楚 | 中间态本身留着的风险没有消除：下次重试撞「远程文件已存在」、使用者要手工判断残留。只修显示不解决问题 |
| 失败时清空整个目标目录 | 会删掉目标机上原有的、不属于本次执行的文件。不可接受 |
| 上传前先记「要传哪些」清单，失败按清单删 | 清单要维护、要落盘、还要处理 sudo 路径；而「已成功写入的路径」在写的时候天然就有了，不需要另立一份 |
| 用一次 `find -newer` 之类的时间判断哪些是本次写的 | 依赖远端时钟与文件系统行为，多一次往返，且判断本身就是模糊的 |
| 下载也一起回滚 | 下载动的是本机自己的产物，删目录重下即可，回滚只会增加失败路径与连锁清理 |
