# ADR-0063: SFTP 会话整体以 root 跑，撤掉 sudo 上传的暂存目录与 mv

> 原话是证据，不是要求；要遵守的是下面「决定」一节。

- **状态**：部分作废（partially superseded）—— 决定 7 由 ADR-0066 取代；其余仍有效
- **日期**：2026-11-19
- **决策人**：
  - **开发者明示**（2026-11-19 本轮对话）：「既然都是 sudo 传输了，落位文件属主从登录账号变成 root 也是可接受的，想用 root 的权限就别用 sudo，这不算代价」；「sftp-server 路径不固定这个必须找到好的解决办法，而且如果找不到应该直接提示，因为几千个节点，目标的环境是极其复杂的」；「我的语义里面就不允许续传这个行为，如果出现了失败，所有文件都要清理，不能有残留」；「不能立刻停可以接受……传输完成的不算」；「中断是否清理，看的是传输任务本身是否完成，而不是某个文件是否完成」；「重名判断有一个时间窗口……这种不考虑，太极端了」；「本地同名文件不能覆盖，如果重名，必须在传输前就已经检查出来了」；「timeout_transfer 设计上走的是协程的上下文」；「某个文件失败了 不是这个文件重试吗」；「权限不足有重试的意义吗」；「不要校验了太麻烦了，降低 看 stat 大小吧」；「算重传一次」；「下载也做」；「就1次，多了不给」；「下载就没有清理的说法……上传遗留文件或者覆盖是灾难性的，下载哪里来的灾难性」；「只要是枚举行为，到底是什么做法又快又准又稳定……不需要拘泥于 sftp 的原生功能」；「没有mv了，以后也没有了」。
  - **执行者推导**（他未点名，本文标为推导）：决定 1 的形态（整条会话以 root 跑），他选定的是「要有提权传输，别绕路」与「属主变 root 可接受」这两个方向；决定 4 的枚举改造，他的原话只是「这个你看看有没有好的办法」；决定 6 后半段（到点要用什么动作解开阻塞）。
- **前身**：ADR-0022（上传失败即回滚）、ADR-0026（上传前空间预检）

## 背景

调研底本 `docs/issues/2026-11-19-上传下载稳定性/findings-2026-11-19.md` 的结论是：协议层已经在 `pkg/sftp` 上，不换引擎，只把库已有的能力用上。其中一处是「让整条 SFTP 会话以 root 身份跑」，替代现在 sudo 上传的「写暂存目录 → `sudo mv` 到位」。

开发者的原话把方向定死了：要 root 的权限就用 root 传，不要用绕路。同时他关心的不是某一条命令写错，而是这套代码对目标机做了太多没有说出口的假设——几千台机器、不同的人运维、发行版与 sshd 配置各不相同，任何一处假设不成立，现象都是「某几台莫名其妙失败」。

## 决定

### 1. sudo 场景不再走暂存目录（方向开发者明示，形态执行者推导）

`--sudo` 时，SFTP 客户端不再以登录账号起，而是自己开一条会话通道、`exec sudo -n <sftp-server>`，把该通道的 stdout／stdin 交给 SFTP 客户端（`pkg/sftp` 的 `NewClientPipe`）。此后所有读写都由那个 root 进程执行。

撤掉四段：远端暂存目录、暂存目录的 `chmod 777`、每文件的 `sudo mv`、建子目录用的 `sudo mkdir -p`（最后这一段是执行者推导：会话已是 root，子目录改用 SFTP 自己建，不必再发一条 shell）。

落位文件的属主从登录账号变成 root。**开发者接受，不计为代价**（他的口径：想要 root 的权限，就用 root 的身份去写）。

**没有退路**：暂存与 `mv` 撤掉之后不再装回来（开发者 2026-11-19：「没有mv了，以后也没有了」）。

### 2. 找不到 sftp-server 就直接报失败（开发者明示）

路径不写死。一次探测问清：候选 `/usr/lib/openssh/sftp-server`、`/usr/libexec/openssh/sftp-server`、`/usr/lib/ssh/sftp-server`，再退到 `command -v sftp-server`；用一条 `sudo -n sh` 递进去执行，探到就打印路径，探不到由脚本自己交 42（不用 127：远端 shell 找不到 `sudo` 也交 127，两件事不能共用一句报错）。

探不到、或 sudo 拒绝，**按失败记并明确报出来**，不隐性退回暂存目录那条路。

### 3. 不做断点续传（开发者明示）

语义上就不允许续传。失败即整批清理（沿用 ADR-0022），目标机上不留本次的任何东西。

### 4. 枚举：一条远端 find 带大小、NUL 分隔，不追求协议原生（取向开发者定，形态执行者推导）

开发者 2026-11-19：「枚举为了重名……不需要拘泥于 sftp 的原生功能」，按「又快又准又稳」挑。挑出来的形态：

- **主路**：一条 `find <路径> -type f -printf 'F %s %P\0'`，按 NUL 切记录。一次遍历、大小随行走、名字里有换行也不拆。实测 3003 个文件 7 毫秒；名字带换行时 NUL 分隔数出 2 条，按换行分隔数出 3 条。
- **同一条命令一并打 `L` 记录**：被过滤的软链接只交回相对路径，不上传、不下载，写进该节点的结果明细。
- **退路**：`find` 不认 `-printf` 的机器（BusyBox 一类），改用 `find -print0` 只拿名字，大小用同一会话上的 SFTP `Lstat` 逐个补。准，但每个文件一次往返，只在退路上用。

没采用 SFTP 自己的目录遍历（`ReadDir`／`Walk`）：它每进一层目录一次往返，深树上比一次 `find` 慢一个量级（按层数与往返估，未实测）。

代价：枚举仍依赖远端有 `find`，主路还要 GNU 的 `-printf`。

### 5. 中断可以不等，但必须清理（开发者明示）

按 Ctrl+C 不必打断正在进行的读写，可以停在文件边界（当前文件传完再收场）——开发者明言这一步可以接受。

**是否清理，判据是这次传输任务本身完成没有，不是某个文件传完没有。** 任务没完成就整批清理，与失败同口径（ADR-0022 决定 1 不变）：本次已写成功的文件与半成品一起删。只有整批传完才算完成，那时没有要清的东西。

**这一条只管上传。** 上传写的是目标机上别人的目录，遗留与覆盖在几千台上是灾难；下载写的是本机自己的产物，中断不清理、失败重下一次即可（ADR-0022 决定 5 不变）。

### 6. 传输超时按 ctx 收场（开发者明示）

`timeout_transfer` 的挂法是协程的上下文，不是 SFTP 层的某个参数。现状：执行侧没有任何地方读过它，只在解析、确认屏、运行日志、统计里出现过——等于没生效。

**执行者推导**：补的时候有个前提——`io.CopyBuffer` 不认 ctx，卡住的读写不会被 deadline 叫醒，到点必须先有动作去解开（收尾、退出、再清理），不能只在外面套一层 `WithTimeout` 就以为结束了。

到点时连接往往已经不能用了，收尾那几条命令也发不出去：这时不上报「已清理」，按 ADR-0022 决定 3 照实说哪些没清掉、留在哪个路径。超时是整批的事，不进决定 9 的单文件重试。

### 7. 下载前查本地重名，不覆盖（开发者明示）

枚举完、开传之前，把每个目标本地路径查一遍是否已存在；有重名就整批拦下（与远端重名同口径：报文件名、本节点终止），一个字节都不写。

现在的做法是 `os.Create` 直接截断，与「结果不能覆盖」相反。

### 8. 上传重名的「判重与创建之间被抢」不处理（开发者明示）

`Stat` 判重与 `Create` 建文件之间的时间差里，别人在这台机器上建了同名文件，会被截断。开发者明言不考虑：太极端。

### 9. 重试：单个文件、次数可配、发生在判定失败之前（开发者明示）

传输是逐个文件进行的。某个文件失败时，先删掉它自己的半成品，再从 0 重传这个文件（不做续传），最多 N 次，N 走配置、**默认 1**（开发者 2026-11-19：「就1次，多了不给」）。N 次用完仍失败，才计该文件失败并走 ADR-0022 的整批回滚——已传完的其它文件一个字节都不重发。

### 10. 只重试可恢复的错误（开发者明示）

可重试：连接断、读写出错、写完核大小不符。不重试：权限不足、目标分区空间不足、远端重名、路径不存在——这些立刻计失败，重试只是把同一个结果再等 N 遍。`timeout_transfer` 到点不在此列，那是整批的事（决定 6）。

### 11. 只核大小，不做 sha256（开发者明示）

上传：每个文件写完关闭后 `Stat` 一次，比对本地大小；不一致就按决定 9 的次数重传这个文件（默认 1 次），仍不一致才计该文件失败并走整批回滚。下载：本地写完后 `os.Stat` 本地文件，与枚举时远端给的大小比对，不一致重下一次。

- 成本近似为零：一次协议往返，不额外读盘，不上传任何哈希表，契约包不动。
- **放弃 sha256 的理由**（开发者 2026-11-19：「不要校验了太麻烦了，降低 看 stat 大小吧」）：实测 1GiB 约 5.7 秒（这台 i5-9400 没有 SHA 指令加速，约 180 MB/s），2000 个 10KiB 小文件逐文件起命令要 5.3～17 秒，批量场景下这笔钱不值。
- **代价**：只能抓「写了一半、被截断」，抓不到「字节数对、内容错」。这类静默损坏现在发现不了——开发者的取舍是接受。

## 理由

- **权限只在一处决定**：会话以什么身份起，读写就都是那个身份。现在的形态是一分为二——枚举用 `sudo find`、读取用登录账号，于是「能看见却读不到」这种中间态必须靠额外的判断去解释。
- **三处补丁一次消掉**：`chmod 777` 的暂存目录（那段时间内目标机上任何账号都能往里写）、`/tmp` 空间判据（ADR-0026 的一整条分支）、跨分区 `mv` 退化成复制（ADR-0026 里标着「未实测」的那条依据）。它们都是绕路的产物，不是需求。
- **对远端环境的依赖收窄**：枚举仍是远端一条 `find`，但不再要求它按行输出——名字带换行也拆不错；主路要 GNU 的 `-printf`，不认的机器走 `-print0` 加逐个 `Lstat` 的退路。没用协议自己的目录遍历：每层目录一次往返，深树上慢一个量级。
- **不换引擎的代价可控**：rclone／rsync 都能传文件，但没有一个同时具备「重名不覆盖 + 失败回滚 + 逐台四数」。换掉等于换语义，而语义是这套工具的全部价值。

## 实测与推断的分界

| 结论 | 强度 | 怎么取的 |
| --- | --- | --- |
| 提权会话可行：`NewClientPipe` + `sudo -n <sftp-server>`，能写进 700、属主 root 的目录 | 实测 | WSL Ubuntu 26.04 的 sshd（`127.0.0.1:2201`），账号 `sshfleet` uid 1001、NOPASSWD sudo；无终端的 exec 通道；两个客户端各测一次：原始 SFTP 报文（不依赖任何库）、`x/crypto/ssh` + `pkg/sftp`。落位文件 `-rw-r--r-- root root` |
| 同一账号不加 sudo 时写同一目录得 `PERMISSION_DENIED`；登录账号连目录都列不出 | 实测 | 同上，对照组 |
| Ubuntu 26.04 的 sftp-server 在 `/usr/lib/openssh/sftp-server` | 实测 | 候选清单探测脚本 |
| 没有 sudo 权限的账号，报错原文是 `sudo: I'm sorry <user>. I'm afraid I can't do that` | 实测 | 临时账号，测完已删 |
| 提权会话下 `StatVFS` 可用 | 实测 | 同一探针，`Bavail` 正常返回 |
| 1GiB 文件 sha256：缓存内 5.73～5.87 秒，清缓存后 6.07～6.18 秒（约 180 MB/s） | 实测 | i5-9400（无 SHA 指令）、ext4、`/var/tmp`；这就是放弃 sha256 的依据 |
| 2000 个 10KiB 文件 sha256：一次批量算 0.15 秒；逐文件单独调用 2.65 毫秒/次；`sudo -n` 逐文件 8.57 毫秒/次 | 实测 | 同上；逐文件即 5.3～17 秒 |
| 3003 个文件（30×100，三层）一次 `find -printf 'F %s %P\0'`：7 毫秒 | 实测 | 同机 ext4 |
| 名字里带换行的一个文件：NUL 分隔数出 2 条，换行分隔数出 3 条；NUL 记录里的换行原样保留 | 实测 | 同上，两个文件的样本 |
| `timeout_transfer` 在传输上没有执行点 | 源码事实 | 全仓搜它的引用：解析、`log_session`、`message` 三处，执行侧零处；传输的 ctx 只来自中断 |
| 其它发行版的路径、`internal-sftp` 的机器、`requiretty` 的机器 | 未验证 | 见文末清单 |

实验形态与真实形态的差别只有一处：探针的通道是 OpenSSH 客户端起的，程序里会换成 `x/crypto/ssh` 起；exec 通道、无终端、stdout／stdin 直连这三点一致。

## 影响

- **ADR-0026**：暂存侧判据（按最大单文件量判 `/tmp` 分区）整条作废，只剩目标侧一条；「/tmp 空间不足」这个分类失去触发场景。
- **ADR-0022**：口径不动——中断按「任务未完成」处理，与失败同样整批回滚。本文只把「任务是否完成」与「单个文件是否传完」这两件事分开。
- **失败分类**：`tmp_failed`、`sudo_failed` 两个环节名退役；新增「大小不符」一类（写完核大小不一致，重传一次后仍不一致）；判据表与语料要同步。
- **配置**：新增传输重试次数一项，默认 1；判据表不用改（重试用尽后仍是原来那几个失败分类）。
- **手册**：上传一节原「文件会先写进目标机的 `/tmp`，再搬到目标目录」整段作废，已改写为「root 直接写到目标目录、空间只判目标分区」；下载一节原「`--sudo` 模式下的下载，文件读取仍以登录用户身份进行……先用 sudo 命令模式把文件搬到登录用户可读的位置」也已改写——提权会话下 root-only 文件直接读得到，这条绕法连同它的建议一起撤掉。
- **直接代价**：探不到 sftp-server 的节点上，`--sudo` 上传从「能成」变成「明确失败」。这是决定 2 买来的，不退回。

## 备选方案

| 备选 | 否掉的原因 |
| --- | --- |
| 换 rclone 做引擎 | 会碰「重名不覆盖」（它是静默跳过或更新）、「失败回滚」（它没有这一层）、「逐台四数」（要解析日志）；sudo 只能整会话 root，与下载读取身份的约定冲突 |
| rsync | 目标机要装 rsync，与「远端只需要 sshd」直接冲突 |
| 保留暂存目录 + `mv` | 777 目录、`/tmp` 判据、跨分区退化这几处补丁都得继续带着；开发者已定「以后也没有了」 |
| 枚举走协议自己的目录遍历（`ReadDir`／`Walk`） | 不依赖远端 `find`，但每层目录一次往返，深目录树上比一次 `find` 慢一个量级；开发者要的是快准稳，不是协议原生 |
| 只把 `Stat` + `Create` 换成 `O_EXCL` 原子创建 | 竞态开发者明言不考虑；而且它不解决枚举与环境依赖，只是把判重与创建合成一步 |
| 探不到 sftp-server 时自动退回暂存路径 | 会造出两套并存的写入形态，失败分类与空间判据都要各写一份；开发者要的是「找不到就提示」 |

## 未证实清单

1. `sftp-server` 在真实节点上的覆盖率——只在 Ubuntu 26.04 上验过一处，几千台的分布未知。
2. 配 `internal-sftp` 的机器上，独立二进制是否存在（OpenSSH 的包一般都会装，未核实）。
3. `requiretty` 的老机器上 `sudo -n` 会不会被拒。现状的 `sudo mkdir`／`sudo mv` 走的是同一条无终端通道且能跑，但那是 exec 通道上的另一个命令，不是同一次调用形态，要复核。
4. 中断时的整批清理（含本次已写成功的文件）在提权会话下删不删得掉——连接仍在，推断能，未测。
5. 提权会话下 `StatVFS` 报的可用空间是否与写入者看到的一致。同一进程，推断一致，未测。
6. 不支持 `-printf` 的机器（BusyBox 一类）在真实节点里占多少——没有样本；那条退路（`-print0` 加逐个 `Lstat`）的成本也没实测，只知会按文件数线性增长。
7. 「协议遍历比 `find` 慢一个量级」是按每层一次往返估的，没有在同一棵树上两种做法各跑一遍。
