# ADR-0065: 清理动作不受超时与中断影响，两者都不是它的停止条件

> 原话是证据，不是要求；要遵守的是下面「决定」一节。

- **状态**：已接受（accepted）
- **日期**：2026-11-20
- **决策人**：
  - **开发者明示**（2026-11-20 本轮对话）：「我想要的就是 不管是超时还是中断，都得不能影响清理动作」；「这块我觉得 得写个adr记录下来」；对定稿前审计列出的三处，回一句「行按照你的建议改」。
  - **执行者推导**（他未点名，本文标为推导）：把上面那句拆成这六件——范围、停止条件、独立的额度、连接形态、收尾前必须先做完的两件事、中断那条的归属；以及那份负面清单（不许因为 ctx 已取消就跳过清理）。
- **前身**：ADR-0022（上传失败即回滚）、ADR-0063 决定 5（中断也必须清理）与决定 6（传输超时按 ctx 收场）

## 背景

传输失败、被 Ctrl+C、传输超时——三条路都要求「先清理再收场」：ADR-0022 定的是「要么全传上去，要么一个都不留」，ADR-0063 决定 5 明写中断也按「任务未完成」处理、整批清理，决定 6 明写超时到点先收尾再返回。

三条路也共用同一个东西：`context`。中断靠它往下传，超时靠它到点。于是出现一个结构性的事实——**需要清理的那一刻，ctx 一定是取消状态**：中断时父 ctx 已取消，超时时子 ctx 已过期。这不是意外，是必然。

顺着写下去就成了这样：清理之前先看一眼 ctx，取消了就不发请求；或者给清理套一个从那个 ctx 派生的 `WithTimeout`，一造出来就过期。两种写法都「看着很对」，结果一样——最需要清理的那两刻，一定不清。

## 决定

### 1. 范围：只管「一次上传里要撤掉的那一批」

失败、中断、超时，三条路走到的是同一次收尾——把本次已经写进去的那批文件撤掉（ADR-0022 决定 1）。本篇说的「清理」只指这一次。

**不在本篇**：下载侧删本地半成品（ADR-0022 决定 5）；单个文件失败重试前删它自己的半成品（ADR-0063 决定 9）。前者删的是本机自己的产物，删不干净下次重下覆盖；后者服务的是一次可能马上就被放弃的重试，被打断最多撞一次「已存在」。两样都不背「留一颗就是灾难」这个前提，也就用不上本篇这条规矩。

### 2. 清理的停止条件只有一个：它自己花完上限

清理一旦启动，超时与中断都不再是它的停止条件。

**不许写**：拿已经到点或已经取消的 ctx 去派生清理的 ctx（派生出来就是过期的）；清理循环里照抄「每进一个文件之前查一次取消」那两句（第一个文件就退出）；因为 `ctx.Err() != nil` 就跳过清理。

### 3. 那份额度与传输不是同一个数

「它自己花完」要能执行，额度就得单独算：传输那份预算到点时已经用光，清理接着用它，第一步就走不了。具体取哪个数属实现，按规格走。

### 4. 清理走同一条连接，另开一条通道

发请求得有一条能用、又不被卡住那一步占着的通道。形态定死：**在同一条 SSH 连接上另开一条命令会话**，不重拨、不重新认证。

不逐条开 SFTP 请求删：一个文件一次往返，几千个文件就是几千次，收尾那份额度会被文件数吃掉。

重拨被否掉的理由（多一次握手，服务端提示会被第二次写入，而那一格参与分类）留在备选方案。

### 5. 收尾之前，先把那条连接交出来

清理要独占这条连接，所以两件事必须在它开始前做完：

- **到点动作只许响这一次**。它是用来解开阻塞的——卡住的那次写靠它才返回。响过就解除，没响过也解除；此后它不再动作。
- **卡住的那次调用先退出来**。同一个文件上不许同时读写与删除：写还没退出来就去删，删的是正在被写的那个。

### 6. 中断不强行断连

Ctrl+C 停在文件边界，不关通道。

「停在文件边界」是 ADR-0063 决定 5 定的；**「不关通道」是本文为保住清理新加的**——那一条只说不必打断正在进行的读写，没说这条连接在收尾时怎么处理。

中断与超时在这里是两件事：中断是「这一台不要再往下做了」，超时是「对端多半不回来了，等不到边界」。

## 理由

- **不这么定，ADR-0022 的语义就是空话**。「一个都不留」包括了中断那一路（ADR-0063 决定 5 已明写）；清理被自己的取消信号掐掉，等于只在最顺利的时候才做得到。
- **到点那一刻恰恰最需要清理**。连接多半不通、残留最多，而那时 ctx 一定过期。顺着 ctx 写等于「在最需要清理的时刻一定不清」——这不是失手，是写法的必然结果。
- **换通道而不重拨，是为了不碰分类**。分类靠报错原文与那格服务端提示匹配；重拨要第二次握手，提示被重写一遍，同一个现象可能认成另一类。
- **这条刻意违背直觉，必须留档**。「按了 Ctrl+C 就该立刻停」是所有人的默认预期；不写下来，下一个读代码的人会把它当成 bug，而且修得看起来很对（加一句 `if ctx.Err() != nil { return }`）。

## 影响

- **使用者感知**：按 Ctrl+C 之后，最多还要等这一台把当前文件跑完、再做一次清理才退出。卡在死链上时「跑完当前文件」永远不到，实际是等满传输那份预算，再加一份收尾上限。手册要写明「中断之后仍会清理，所以不是立刻退出」。
- **清理期间再按 Ctrl+C 不会终止清理**。信号只登记一次、登记全程不撤（ADR-0042），所以第二次 Ctrl+C 本来就不起作用；这条让「清理必须做完」有了实际保障，同时意味着要硬退只能杀进程——那时什么也保证不了。
- **与 ADR-0063 决定 6 的关系**：决定 6 说「到点时连接往往已经不能用，收尾那几条命令也发不出去」——本文不改那个结论，改的是它前一步：不许在没试之前，就因为 ctx 是取消状态判定「发不出去」。试过之后发不出去，照决定 6 与 ADR-0022 决定 3 说清楚。
- **与 ADR-0032 第五条的读法**：那一节写「在跑的收手、没跑的记作未执行」——「收手」指不再往下做（不再派发、不再开新文件），不含收尾这一次撤除。两者不冲突，但字面挨着，写在这里免得后来的人照「什么都不许动」去改。
- **实现形态另行落定**：预算制（每次发起前按剩余武装）、武装点在哪几处——属实现，按规格与工单走。

## 备选方案

| 备选 | 否掉的原因 |
| --- | --- |
| 中断即停，残留交给使用者手工清 | 省时间；但 ADR-0022 的语义被掏空，几千台上「按一次 Ctrl+C 就得逐台手工清」正是当初立那条规矩要消掉的活 |
| 清理挂在原 ctx 上、随取消一起停 | 实现最省（一行 `WithTimeout`）；等于没有清理，且看上去完全正常 |
| 到点后重拨连接再做清理 | 能绕开取消状态；但多一次握手，服务端提示被第二次写、分类跟着变；而到点那一刻连接多半不通，重拨成功率并不比同连接另开通道高 |
| 把下载侧与单文件重试一并划进「清理」 | 三处风险不同：整批回滚删的是别人机器上的东西，下载侧删的是本机产物，单文件重试前那次删只为让这次重试干净。并进来要给同一条规矩写三套理由，只有一套站得住 |
| 二次 Ctrl+C 才终止清理 | 把「放弃等待」与「放弃清理」分成两档，语义要额外教给使用者；且信号只登记一次（ADR-0042），要先改中断包的形状，属另一件事 |

## 未证实清单

1. 「关掉那条通道能让卡住的写立刻返回」只有推断，未实测——`pkg/sftp` 的 `Close` 对被占用的写请求作用如何，要在真实卡住的链路上验一次。
2. 清理期间网络再断、或对端被杀时的行为未测：按本文，清理自己失败、照实报残留，这条路径没有实测过。
