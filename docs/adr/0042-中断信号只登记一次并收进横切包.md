# ADR-0042: 中断信号只登记一次并收进横切包——不再分两段两次登记

- **状态**：已接受（accepted）
- **日期**：2026-11-05
- **决策人**：
  - **开发者明示**（2026-11-05，阶段 06 开工之前）：
    - 「程序必须自己接管（signal.Notify） 这话还得能阻塞多次中断信号，别多中断几次就退出了」
    - 「a/b 相同 也可以开口，一切为了 最稳定 最正确的中断设计让步」
    - 「认，老板的不一定是对的，现在为最优设计让步，因为中断很重要，不能墨守成规」——认的是执行者当轮给出的「一次登记到底 + 状态位 + 收进横切包」那一版。
  - **执行者按此推导**（下列各条是推导，不是他的原话；复审时按推导档的强度看）：
    - 把「扛住多次中断」落成「登记全程不撤」这一条结构，而不是加缓冲、加计数。
    - 把信号层整体收进横切包，使塔尖的符号白名单不扩反收——撤掉 `signal.Notify` 一格，`syscall` 永不进塔尖。
    - 「A/B 可以让步」只让「连按多次」这一类不可复现的时序，不让屏幕、落盘与退出码。
- **实施载体**：`docs/issues/2026-11-03-1619-建站06-中断与取消/`（规格第一、六节，01 号工单）
- **前身**：ADR-0032 第五条末「取消（Ctrl+C）归塔尖，不新建包」；2026-10-30 架构重构议题 12 号单的 `## Answer` 第二节

## 背景

老版的中断是两段两次登记：进程一起来先 `signal.Notify` 一条只收一次的通道，收到就还控制台、`os.Exit(130)`；跑到执行期换成 `signal.NotifyContext`，取消经 `context` 送到每条连接，然后把前面那条通道 `Stop` 并关掉。两段之间靠「先建 `NotifyContext`、再 `Stop`」的次序压出一个零长度的交接窗口。

这套能用，但脆：**它靠次序正确来保证不出事**。窗口是零还是几微秒，取决于这两句的相对位置；将来谁在中间插一句、或者把先后调个个儿，都不会有东西报错，只会多出一个「谁都不管」的窗口——那几微秒里按 Ctrl+C，进程照旧被系统当场打死，`defer` 不跑、日志不落盘、上传残留留在目标机上。这正是阶段 06 要消灭的形态，而消灭它的办法不该是「要求每个人都记得先建后停」。

阶段 06 开工前的规格审计还撞上第二件事：照老版形状搬，塔尖要用 `os.Signal`、`os.Interrupt`、`signal.Stop`、`signal.NotifyContext` 四个符号，外加 `syscall.SIGTERM` 一格；而 `guard` 里那张塔尖符号表今天只有 `os.Exit`、`os.Args`、`signal.Notify`、`errors.As`、`errors.Is`。`syscall` 更彻底——它走的是「未登记的标准库整包放行」，塔尖一 import 它，等于多了一个检查够不着的包。

开发者 2026-11-05 据此加了两条约束：**中断必须扛得住连按**（不能多按几次就退），**A/B 逐字节同可以让步**，优先取最稳、最正确的中断设计。

## 决定

**一、信号只登记一次，从进程启动到退出都不撤。**

进程起来第一件事就登记（`SIGINT` 与 `SIGTERM`），同时建一个可取消的 `context`；这一处登记一直活到进程结束。中途不 `Stop`、不 `Reset`、不关通道、不重新登记。

理由是一条运行时的性质：**只要信号还登记在册，它的默认动作（当场终止进程）就是关掉的**。所以「按几次会被杀」只取决于一件事——登记有没有被撤。既然撤登记是唯一的危险动作，设计里就干脆没有这个动作；不是把它排对次序，是让它不存在。

**二、两段只是状态位，不是两次登记。**

同一处登记、同一条通道、同一个读到信号的循环。读到信号先取消 `context`，再看当前处在哪一段：

- **启动段**（还没开跑）：调塔尖给的收场回调——还控制台、关日志、退 130，一个归档目录都不建。
- **执行段**（已经开跑）：取消已经做过，此后什么都不做。第二、三、十次按下去都是这一条空分支，进程照常把已开工的机器跑完、归档、结算、出报告。

两段之间只有一个原子状态位的翻转，没有交接动作，也就没有交接窗口这个概念。

**三、信号这一层收进一个横切包，塔尖只做三个动作。**

登记、判段、取消、重复信号的忽略，全在一个横切包里。塔尖只碰三样：**起来时登记并拿到那个取消句柄**、**把取消通知递给执行站**、**在开跑那一刻翻状态位**。塔尖不认识 `os/signal`，也不认识 `syscall`。

这一条同时改了两处结构口径：

- **横切包从八个变九个**，包清单从十七行变十八行。新包只依赖标准库（不需要契约，它不产数据）。
- **塔尖符号白名单不扩反收**：`signal.Notify` 一格撤掉。往后塔尖只剩 `os.Exit`、`os.Args`、`errors.As`、`errors.Is`。

**四、行为不改。**

老版怎么收场，新版就怎么收场：启动段 130 且不建归档；执行段 0，屏幕补那句「已收到中断信号……」，统计块给「未执行：N」，`report.txt` 同一行带「（执行被中断）」后缀，`terminal-output.txt` 与执行期日志照写。这套次序由 A/B 逐字节比对守着，本条一个字不动。

**五、重复按的口径：一律忽略，不加强杀档。**

执行段里第二次及以后的中断信号不产生任何动作——老版也是这个行为（`NotifyContext` 重复取消是幂等的）。**不新增「连按两次直接退」**：那会让「收得完」这条保证多一个例外，而老版没有这一档，A/B 也会露。

**六、判据：逐字节同照旧，「连按」单独手工验。**

屏幕、退出码、`report.txt`、`terminal-output.txt`、执行期日志的逐字节比对仍是阶段 06 的结账判据，不放宽。A/B 让的那一步只让在「同一秒内连按 N 次」这种没法稳定复现的时序上——它不进逐字节比对，改为**单独手工验一次**：执行段连按五次，进程仍走完整收尾、退出码仍是 0。

## 影响

- **ADR-0032 第五条末那句「取消归塔尖，不新建包」不再约束**，替代见本条第三项。重构议题 12 号单 `## Answer` 第二节「订阅信号的点只许在塔尖」的**落点**跟着改：订阅仍然只许一处，只是那处不在塔尖、在新包；判据从「别处连订阅的资格都没有」变成「只有这一个包有订阅的资格」。
- **规则表要动两处**：多一行（新包，横切类，只依赖标准库）、`tipSymbols` 撤一格（`signal.Notify`）。两处都是检查本体，属「单独点头」档；开发者 2026-11-05 的「认」是就这套设计给的点头，落地时在工单里写明这一句。
- **横切包之间不多边**：新包不依赖契约、不依赖别的横切包，塔尖与其余各包依赖它不成环。
- **红线区一条不加**，仍是 39 条：中断只改行为，不改纸的形状与流向；新包的出口只有那三个动作，钉它属于自定义区（跟着包走）。
- **`exitcode` 不动**：130 与 0 两格本来就有。
- **包数口径的连锁**：母规格、建站地图、协作约定里「十七个包」的说法要跟着改成十八个——改的是数，不是布局原则。

## 尚未验证

- **「登记在册即关掉默认动作」是 Go 运行时的文档与源码结论，本仓库未实测。** 它是本条第一项的地基，落地第一件事就该验：执行段连按五次，看进程是否仍在、是否走完整收尾。验不出来（例如某个平台上连按仍会杀进程），本条第一项要回来改，不能当成已经成立的前提。
- **Windows 上的 `SIGTERM`**：老版把 `os.Interrupt` 与 `syscall.SIGTERM` 一起登记，新版照抄，不做平台分支。这一条是照搬，不是验证过的结论。

## 备选方案

| 备选 | 否掉的原因 |
| --- | --- |
| 给塔尖符号表加 `os.Signal`／`os.Interrupt`／`signal.Stop`／`signal.NotifyContext`，再给 `syscall` 开一格 | 这是审计当时被逼出来的第一版。它把唯一的符号级检查对塔尖关掉一角，`syscall` 从「整包不可见」变成「可见一格」，而收益只是省一个包 |
| 照老版两段两次登记（先建 `NotifyContext` 再 `Stop`） | 能用，但保证来自次序而不是结构；次序被改坏时没有任何东西报错。而且「扛住连按」这条要求下，撤登记这个动作本身就该消失 |
| 加缓冲、加计数来「扛住多次信号」 | 只把窗口推远，没消掉：只要还撤登记，撤的那一瞬就是可杀的；缓冲满了照样丢信号、照样可能撞上撤登记 |
| 把取消并进 `exitcode`（都是「收场」） | `exitcode` 只做种类到码的查表，没有订阅信号、持有 goroutine 的地方，并进去就是一文一武两件事 |
| 加「连按两次直接退」的强杀档 | 超出老版行为，A/B 必露；且给「收得完」这条保证开了个例外，正是本阶段要消灭的形态 |
