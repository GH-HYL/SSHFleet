# ADR-0040: 闸门可以在原纸上改一格值——「等宽」只管不造新纸，不管不改数据

- **状态**：已接受（accepted）
- **日期**：2026-11-03
- **决策人**：
  - **开发者明示**（2026-11-03，阶段 05 建议题之前）：先问「你看看闸门还有没有类似的情况，他需要改格子值的；如果有，那个原样交接的决策就废弃，当时决策没有想到那么多」，再定「废弃后，也就等宽约束了」；执行者追问「改值这算不算造新纸」，开发者的取向是不算——纸没换、格子没加。
  - **执行者按此推导**：把「废弃」落到可行的范围——查遍老版这一棒，只有一处改值，所以只废弃「不改数据」那半，保留「不造新纸」，并把准改的范围钉死在一格上。
- **实施载体**：`docs/issues/2026-11-03-0940-建站05-另外四种模式/`（规格第四节、08 号工单）
- **前身**：ADR-0035 决定一与 2026-11-02 的更新记录（闸门这一棒等宽）；ADR-0032 决定三「两张纸一样宽就不该造两次」

## 背景

阶段 04 结账时把闸门这一棒钉成「等宽：不造新纸、不加数据格，放行时塔尖把同一张 `contract.Plan` 递给执行站」。那条决定解决的是「同一形状的纸造两次」的问题，落得很干净。

阶段 05 一开工就撞上一个它没料到的场合：**上传模式的并发建议**。老版在确认屏之后问一句「按上传总大小建议同时传 N 个，改成 N 个？」，答是就把并发数改掉，再把参数屏重显一遍、把并发数那行加粗（`modules/SSHFleet_Go/internal/confirm/confirm.go:349`，重显那段在 `:74`）。这一句问话落在闸门这一棒上，它的结论不是「过还是不过」，而是「把执行参数改成一个新值」。

按 04 那条口径逐字读，闸门一格数据都不许动，这一句就问不出来。可它问的是**用户已经看过的那个数**，不给改的出口，上传大文件就只能按用户随手写的并发跑。

## 决定

**一、「闸门这一棒等宽」只管「不造新纸」，「不改数据」那半作废。**

纸还是那一张、格子还是原来那几格、递下去的还是同一个对象。造新纸指换一张纸、加格子，或把某一格的口径换掉——改一个已有格的值不在此列。

**二、准改的范围钉死在一格：`RunParams.Concurrency`。**

触发条件三条同时成立才准改：这次是上传、解析站算出了建议值、且建议值**不同于当前生效的并发数**（用户没给 `-n` 时，当前生效值就是节点数——老版在问之前已经把它补成节点数）。三个条件缺一个就不问、不改。别的情形下闸门仍然一格都不动。

**三、改完要让人看见。** 参数屏重显一次、并发数那行加粗（老版就是这么做的，观感一致），日志里留一行「按建议把并发数改成 N（原 M）」。

## 影响

- **闸门多了一个写口**。这是本条最该被复审的地方：往后谁都能拿「这条也影响执行」来要求往里加一格。挡住它的是本条第二条——**一格、三个条件**，加第二格要另开 ADR，不能援引本条。
- **「等宽」这个词从此有两种读法**，包注释与 `gate/run.go` 的注释按本条写明是哪一种，免得下一个人照旧注释去查、查不出为什么并发变了。
- **类六之二那张交接件对账表**（`guard/check_handoff.go`）仍没有可判对象：闸门递下去的仍是同一张纸，宽度没变。

## 备选方案

| 备选 | 否掉的原因 |
| --- | --- |
| 闸门造一张改过一格的新纸 | 与 ADR-0032 决定三那条边界正面撞：两张纸一样宽却造两次，正是那条边界要治的 |
| 纸上加「建议并发 + 依据」两格，闸门只问不改，另加一样返回值告诉执行站「采纳了」 | 动闸门的导出形状，红线区那几条入口测试跟着动；而且「采纳没采纳」这件事没有别的主人，加了格还是得有人写 |
| 这一句整个不搬 | 老版有这句屏、也会换并发；05 的 A/B 逐字比对必露，且大文件上传的并发行为与老版不同 |
| 把建议挪到解析站直接生效（不问） | 改行为：用户没点头就把他的 `-n` 换掉 |
