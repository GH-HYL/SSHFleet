# ADR-0038: 切换判据分三档，切换当天不给老工程改名

- **状态**：已接受（accepted）
- **日期**：2026-11-01
- **决策人**：
  - **作者明示**（2026-11-01）：「行，按照你的建议来」——点的是这套：判据分三档、切换不改名、退路靠已有的发布 tag 与脚本指向。
  - **执行者按此推导**（未经逐条拍板）：判据的具体取值（命令模式一台机器、通过标准三样、五步顺序），复审可推翻。
- **实施载体**：`docs/issues/2026-10-30-2134-架构重构/issues/09-cutover-criteria.md`
- **前身**：ADR-0032 第六条只定「两套并排、老工程冻结」，没定「什么时候敢换、换的时候动哪几处」

## 背景

重构做完之后要换出去，这是整件事唯一的对外动作：使用者手上的工具会换掉，配置可能重写、行为可能变，出问题得能退。

现状里三处与这件事有关：发布脚本里写死了取源码的目录名；忽略规则里有一条 `modules/*_bak*/`；两个远端各有一套 main 与 master。三处都能改，但顺序错了就回不去——最危险的一种改法是把老工程改名归档：它当场会被忽略规则吞出版本库，而它是当前发布版的唯一源码。

## 决定

**一、判据分三档，别混成一句。** 建站门槛最宽（能编译、红线绿）；可切门槛三条硬条件（五站贯通、五模式加三条密码子命令真机跑过、逐字比对最近一次通过）；切换当天的动作最窄，五步按序，任一步不对就停在当步。

**二、切换不改老工程的名。** 忽略规则会把它吞掉；而且改名解决不了任何问题——它躺在原地、还能编译、还能打包，就是退路。

**三、只改一处。** 发布脚本里那一行目录名。`.gitignore` 与 `APP_NAME` 都不动：不改名就不会命中；使用者看到的名字不该因为一次重构而变。

**四、退路先写，而且用已有的东西。** 锚是切换前最后一次发布打下的 `v<版本>` tag，不新造一套「带日期」的命名；退回只有「目录名指回去 + 提交 + 重新出包」。

**五、老工程不在切换当天删。** 原地留着、不再维护不再打包；等下一次大改再删。

## 理由

**为什么判据要分档。** 「能开始搬」与「可以对外切」被混成一句时，实际效果是永远不切或者一拍脑袋就切。分档之后，建站期宽松、切换期收紧，中间没有模糊地带。

**为什么判据要写成能判的样子。** 「五站贯通」「都跑过」「冒烟过了」这类话单看都对，落地时谁也判不出过没过。所以每一条都配了具体路径与通过标准（退出码、产出在不在、报告算不算成功）——**判据的合格形状是「照着这句，能指着结果说这算过、那不算」**。

**为什么冒烟不走发布脚本。** 发布脚本那条路是正式发布：封更新日志段、改版本常量、commit、打 tag。这些动作一旦在冒烟之前发生，冒烟失败就留下了一个已经发出去的版本号。冒烟要用临时编出来的二进制。

**为什么锚用现有的发布 tag。** 多一套命名就多一处要维护，而发布 tag 本来就钉住了那一刻的源码。仓库里能回到原点的手段，只需要一个。

## 影响

- 发布脚本只改一行，且这一行必须在打包前提交——脚本会查工作区干净。
- 切换当天多一个动作：确认 tag 两端都在。
- 老工程在切换后仍占着目录，直到下一次大改。
- 09 号工单的可切门槛里，第三条依赖 08 号答案第五节的归一化规则；两处说的是同一件事。

## 代价

- **仓库里并排躺着两个工程**，有人可能改错那一份。挡住它的只有「老工程冻结」这一句与检查不扫老工程。
- **退路依赖「切换前确实发布过」**。若那个提交从来没有对应过任何发布 tag，锚就不存在，得先按原样发一次——这会多一轮发布。
- **可切门槛第二条要真机器**，五模式加三条子命令各跑一遍不便宜；这是切换前必须付的账，不是可以省的。
- **冒烟只有三条**（帮助、空参数各敲一记、一条真机路径），故意窄：宽了就成了第二轮验收，切换会一直往后拖。

## 备选方案

| 备选 | 否掉的理由 |
| --- | --- |
| 把老工程改名成 `_bak` 归档 | 当场命中 `modules/*_bak*/`、从版本库消失；而它是唯一发布源。改名不解决任何问题 |
| 切换判据写成一句「全部跑通就可以切」 | 「全部」判不出来，等于没有判据 |
| 新造一套「带日期」的 tag 当退路锚 | 与发布 tag 并存两套命名，多一处维护；发布 tag 本来就够用 |
| 冒烟直接走发布脚本出包 | 脚本会改版本常量、commit、打 tag；冒烟失败就留下一个已发出的版本号 |
| 切换当天就把老工程删掉 | 删掉就没有对照物，出问题无法回退到同一份源码 |
