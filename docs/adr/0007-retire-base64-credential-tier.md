# ADR-0007: base64 档从可见面退役，实现保留为死代码

- **状态**：已接受
- **日期**：2026-09-24

## 背景

凭据文件在磁盘上原先有**三个等级**：

| 等级 | 形态 | 用户要做什么 |
| --- | --- | --- |
| 1 | 明文 | 直接写密码 |
| 2 | base64 | 写密码，再跑一次转换命令 |
| 3 | 加密 | 先生成主密钥、重开终端，再转换 |

等级 2 的位置很尴尬：它不提供任何**安全**（base64 不是加密，任何人都能解回来），只提供"看起来不是明文"的心理安慰，却要用户多记一层概念、多跑一次转换。而真正需要保护凭据的用户会直接上等级 3。

## 决定

**取消"等级"这个概念**，加密开关改为布尔字段 `account.encrypt`：

- `false`（不加密）：凭据位置写**密码 / 口令本身**
- `true`（加密）：凭据位置写**密文文件的绝对路径**

base64 这一档**在工具层面不存在**——配置、帮助、手册里都不出现这个词。读到 base64 形态的内容一律按当前开关要求报错，不转换、不兼容。

**相关实现保留不删**（`isProbablyBase64Text`、`ContentFormat`、`decodeStrictB64` 等），并注明"保留是为了随时改回来，不是为了兼容"。

## 理由

只剩两档时，**任何数字分级都会留下"为什么没有 2"这个永久疑问**。布尔让问题连同阶梯感一起消失，也与配置里已有的 `execution.sudo` 同形态——同一个配置文件里，两处开关长得一样。

保留实现而不删，是因为作者明确要求"留着供日后反悔时回溯"：退役的是**概念**，不是能力；把解码那几十行删掉，真要用回来时得重写。

## 影响

- `password_security = 3` 这类配置项消失，取而代之的是 `encrypt = true` / `false`
- 一处开关**同时改变四处写法**：`password`、`key_password` 与清单第 4、6 列，从不加密时的"密码本身"变成"文件的绝对路径"。改完开关后第一次运行若按新含义解释不通，报错里会点一句"你刚把加密打开/关掉了，这些位置的写法也要跟着改"
- 凭据转换命令的方向也改由这个开关决定（转成开关要求的那一种），不再由用户在命令行上选
- 主密钥预检查只在 `encrypt = true` 时出声——不加密还检查主密钥是纯干扰

## 备选方案

| 方案 | 为何未采用 |
| --- | --- |
| 保留三个等级，只把名字改直白 | 概念数没减少；而数字分级是"为什么没有 2"这个疑问的根源 |
| 保留 base64 但默认不用 | 留着就是留着——用户仍会在配置与文档里看到它、问它是什么 |
| 把 base64 换成别的编码（如 hex） | 换汤不换药，仍是"不提供安全却要多学一层"的中间档 |
