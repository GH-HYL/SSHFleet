# ADR-0067: 闸门的收场与传输的逐文件循环不合并

> 原话是证据，不是要求；要遵守的是下面「决定」一节。

- **状态**：已接受（accepted）
- **日期**：2026-11-24
- **决策人**：
  - **开发者明示**（2026-11-24 对话，原话）：「行，都按你的建议走，改吧」；补文档时：「补吧，补一条」。
  - **执行者推导**（他未点名，本文标为推导）：两处的建模、否掉的三条理由、重开的三条条件。
- **前身**：ADR-0062（同一副眼睛看过拒绝文案，判不合）、ADR-0036（五种模式不聚成包）、ADR-0012（审查收益的口径）

## 背景

2026-11-24 的架构审查提了几条候选，其中两条的处方是「合」：

- 把闸门里那一句「问完之后怎么收场」收成一个 `decision`：问句与两种收场载荷进去，三种结论出来。
- 把上传与下载「逐文件那一趟」收成一个 `attemptFile`：收下「传这一个」「清这一个」两个适配，序列与账只做一遍。

两条都不是从一处毛病出发，而是从「看起来像同一件事」出发。ADR-0062 已经用同一副眼睛看过一次拒绝文案，结论是不合。本条把这两处也答完，免得下一轮换个名字再来。

## 建模

**闸门那几处。** 每处收场的正文就是一句 `switch ask.Ask()` 加两句返回：一行给「输入结束」，一行给「答否」。其中「输入结束」那一支各处逐字相同——屏上那句「操作已取消」由 `ask` 自己打，闸门不叠。有分歧的只有两样：

- 答否之后留哪条痕：`CancelTrace`、`ChineseAnswerTrace`、`FallbackTrace`，或者什么都不留；
- 答否算不算停：闸门里是停；上传并发建议那一处是「保留原值继续跑」。

这两样都是各层自己的判据，不是可以搬到一处的版式。`confirm.go` 的头注释把这件事写成了这一段的职责：「这里只决定『答了否算不算停』」。

**传输那两条循环。** 三条规矩已经各只有一份：重试判据在 `transfer.go` 的 `retryableTransferError`，到点关通道在 `transfer_clock.go` 的 `arm`，残留清单在 `dedupePaths`、`partialLeft`、`localPartialLeft`。剩下的重复只有循环骨架，而骨架内外还挂着上传方向才有的事实：开传前的空间预检（ADR-0026）、跨重试累积的 `leftover` 与 `created` 语义、失败之后「先探空间再回滚」的次序、写成功才进 `written` 清单、面板按 `pacer` 节流。

审查把这两条说成「差别只在删远端还是删本机」，与代码不符：那只是两个适配，其余几样仍是方向特有的事实。

## 决定

**两条都不合，都不写代码。** 闸门各处的收场保持原形，上传与下载各保各的循环。

## 理由

**一、共性在版式上，版式已经抽完。** 闸门剩下能抽的是「留哪条痕」；传输剩下能抽的是循环骨架，而它牵动的几件事都在上传那一侧。抽掉版式之后再抽，只能抽到事实本身。

**二、合了必须带一格「用哪一套」。** `decision` 要收留痕载荷与「答否算不算停」；`attemptFile` 要收回滚、空间预检、跨趟累积、面板节流。参数化之后，读的人还要多跳一层才知道某一处到底停不停、留什么痕。

**三、审查引的证据指向别处。** 它说「改了 A 不得不改 B」在这个文件上真发生过，指的 `a3`、`08-4`、D 族那几处注释。它们都在 `run.go` 的危险与拒绝那条路上，性质是「从老版搬过来时漏了一条留痕」，不是「改了 A 必须改 B」。真正一次改到多处的是 `ask` 换签名那次（多一个 `AskQuestion`），而 `decision` 坐在调用点之后，对那件事一点忙都帮不上。

**四、本工程的尺子只认两种事实。** 动结构要指得出一条当下的事实：某个依赖没用上，或者真发生过「改了 A 不得不改 B」。观感类与「行数变少」不算。这两条候选给出的收益是「加一道门只加一行声明」——预测类，正是被禁的那一种。

## 影响

无代码变化。作用是：下一轮审查若再提这两条，先读这一篇；真要合，重新开一条 ADR 说明哪个前提变了。

## 代价

闸门那几处的形状相似而不相同，将来若真出现一条**全局**口径（例如「输入结束」那一支要统一改说法），得逐处改。这是有意留着的：那种改动到今天没有发生过一次，而每处多跳一层是每一次读都要付的。

传输那两条循环各保各的次序，判据改了要改两处——判据本身今天已经只有一份（上面点的几个符号），真正复制的是次序，而次序跟着各方向的事实走。

## 什么条件下该重开

1. **闸门出现第三种收场语义**：除「停·留痕」「停·不留痕」之外，又有新门把答否当成别的事。那时要解决的是「一处口径几处要一致」，与本条问的「几处相似要不要合」是两件事。
2. **`ask` 把答否收进自己**：如果「停还是继续」变成 `ask` 交回来的结论，闸门那一处才有东西可合。今天它只交答了是、否、还是没有输入。
3. **传输出现第三个方向**也走同一条骨架。那时骨架不再是一对一，合起来才有第三个样本可以对齐。

## 备选方案

| 备选 | 否掉的原因 |
| --- | --- |
| 合一个 `decision`，问句与两种收场载荷进、三种结论出 | 载荷与「停不停」都得由调用方给，省下的只有那两行；而且它描述不全——闸门里那几个问句分别走 `Ask`、`AskWith`、`AskQuestion` 三个入口，非交互那几支根本不问 |
| 合一个 `attemptFile`，两个适配收尾 | 上传那一段的空间预检、跨趟累积与回滚次序仍得做成钩子，合出来是一个带几个钩子的循环壳，比两条直写的循环难读 |
| 只合最像的一对 | 两者共享的正是那两行；剩下的是「留哪条痕」与「答是之后往哪走」，合起来只多一层 |
| 原样不动（本条） | 采纳 |
