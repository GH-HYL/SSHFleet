## 一、起点：一条被当成「配置没生效」的现象

起于 2026-10-21 的议题 `docs/issues/2026-10-21-1843-sudo边界语言丢失/`。开发者报两件事：

1. `-a` 代填运行时，脚本按环境语言输出的内容中英混排，中文触发词没匹配上，怀疑 `[env]` 没带下去。
2. 在外部 SSH 工具与服务器物理控制台上，`ls` 列中文文件名会显示成「方块和特殊符号」。

议题当时登记了现象与证据，没定方案，留了五个待定项（语言目标、落点、取值、兼容性口径、使用者可见面）。

## 二、本轮做了什么：先证伪，再取证

这一轮的工作方式值得记下来，因为它解释了本 ADR 为什么反复改了几版。

### 2.1 第一轮：把「sudo 边界」当成根因

先核对了拼装链路，确认 `-a` 的下发行与非 `-a` 的 `export` 段**逐字相同**，工具没有丢配置；于是问题被归到 `sudo` 那一层——`export` 拼在 `sudo` 之前，`sudo` 默认 `env_reset`，这段环境过不了边界。

在此基础上做了一组 WSL 实测，得出「Ubuntu 上 `LANG` 被重置成 `C.UTF-8`、`LC_ALL` 被清空；CentOS 上 `env_keep` 放行」。**这组结论后来被证明是错的。**

### 2.2 错在哪

那组实验的形态是「`sudo` 套 `sudo`」：

```
printf 密码 | sudo -S bash -c "printf 密码 | sudo -S bash -c 'echo $LANG $LC_ALL'"
```

变量是在**外层 sudo 之后**才读的——那时它已经被 sudo 的重置作用过了。**测的是「sudo 之后设的变量能否保留」，不是工具真实做的「sudo 之前 `export` 能否穿透」。** 实验形态与生产形态不符，结论自然相反。

### 2.3 纠正：用工具的真实形态重测

改用 `sh -c 'export …; sudo <解释器>'`——即工具实际下发的形态——结论完全翻转。见第三节。

**这一条作为方法论记在这里**：凡是要判断「某个变量能不能穿过 `sudo`」，实验必须让变量的设置发生在 `sudo` **之前**，且只经过**一层** sudo。否则测的是另一件事。

## 三、实测结论（均为工具真实形态）

### 3.1 sudo 边界：变量能穿过

在 WSL2 的两个发行版上，用工具真实形态、以**非 root 账号**实测：

| 发行版 | sudo 版本 | `LANG` | `LC_ALL` | `TERM` |
| --- | --- | --- | --- | --- |
| Ubuntu 26.04 | 1.9.17p2 | 穿过 | 穿过 | 穿过 |
| CentOS 7.9 | 1.8.23 | 穿过 | 穿过 | 穿过 |

自定义变量（如 `MYVAR`）两边都被丢弃。

并用**真实构建的工具**对 CentOS 7.9 实跑，让目标机自己打印它看到的环境：

```text
LANG=[en_US.UTF-8] LC_ALL=[en_US.UTF-8] TERM=[dumb]
locale charmap → UTF-8
id -un → root                                    ← 已穿过 sudo
```

`-a`（代填）模式下同样完整：`LANG` / `LC_ALL` / `TERM` 与无 PTY 时一致，中文触发词（「请选择架构」）匹配成功。

### 3.2 两个发行版，两种保留机制

「能穿过」的机制在两边并不相同——这点决定了能不能外推：

| 发行版 | 机制 |
| --- | --- |
| CentOS 7.9 | 红帽预置在 `/etc/sudoers` 里的 `env_keep`（含 `LANG` / `LC_ALL` / `LC_ALL` 等）+ sudo 内置 `env_check` |
| Ubuntu 26.04 | **仅靠** sudo 内置 `env_check`（`/etc/sudoers` 里生效的 `env_keep` 一条都没有） |

`env_check` 的语义是**字符过滤**、不是保留白名单：变量命中该表后，只要值里不含 `%` 或 `/` 就保留。实测边界（CentOS 7.9）：

```text
LANG=en_US.UTF-8     → 存活
LANG=en_US.UTF-8%x   → 丢失
LANG=a/b             → 丢失
LANG=a b / a$b / a:b / a.b / C → 存活
```

正常的 locale 值都不含 `%` 与 `/`，所以实际不触发。

源码层面，`LANG` / `LC_*` 的保留一路可追到 sudo 1.6.9（2007）：1.6.9 与 1.7.x 在 `rebuild_env()` 里有一段硬编码无条件保留，1.8.5 起该段删除、改为仅靠 `env_check`。**两代都保留，只是代码路径不同**。CentOS 5/6 属源码推断，本轮无环境实测。

### 3.3 语言不统一的真实来源

语言不是由 `LANG` / `LC_ALL` 单方面决定的，而是三件事的乘积：

```text
提示语语言 = f(目标机有没有该程序的翻译包, locale 是什么, 该 locale 有没有生成)
```

实测（三行分别是三种情况）：

| 目标机情况 | 表现 |
| --- | --- |
| 有翻译包（Ubuntu 的 `dpkg.mo`），`LC_ALL=zh_CN.UTF-8` | 真出中文：「没有找到与 nosuchpkg 相匹配的软件包」 |
| 同一台，`LC_ALL=C` | 英文：「no packages found matching nosuchpkg」 |
| 无翻译包（CentOS 7 的 `zh_CN/LC_MESSAGES` 里 0 个 `.mo`） | 任何 locale 下都出英文 |

**第三行说明**：`C` 与 `en_US.UTF-8` 对「提示语是英文」这件事**效果相同**——差别不在提示语，在失效形态。

### 3.4 取值对比：三种候选

| 取值 | 存在性 | 提示语 | 字符语义 | 失效形态 |
| --- | --- | --- | --- | --- |
| **`C`** | **100%**（glibc 编译内置，不在 `locale-archive` 里） | 英文 | 按字节 | **不存在**（零警告） |
| `C.UTF-8` | glibc 2.35+ 才有；**CentOS 7（glibc 2.17）没有** | 英文 | 按字符 | CentOS 7 上告警后回落 |
| `en_US.UTF-8` | 需目标机生成过 | 英文 | 按字符 | 未生成时**告警**并回落 |

`C` / `POSIX` 不在 `/usr/lib/locale/locale-archive` 里，不依赖 `locale-gen`、不依赖发行版，**因此不存在「未生成」这种失效**。实测两台机器上 `C` 与 `POSIX` 均 0 行警告。

`C.UTF-8` 在本场景被排除，理由不是「没有」这一条——它在 CentOS 7 上**其实可以由 `localedef` 生成**——而是：

1. 生成它要求工具去改目标机的 `/usr/lib/locale`，2000 台、十数年跨度，还要考虑只读的 `/usr`；这是操作系统的职责；
2. SUSE 的 `C.UTF-8` 是另做的一套，信创系统又各有实现，跨发行版行为无法枚举。

### 3.5 失效形态：本决策的关键

`en_US.UTF-8` 在没生成的机器上会往 **stderr** 吐警告，而工具把 stdout 与 stderr **合并采集**，于是警告会进入 `Output`、进入日志 txt、进入 Excel，并参与失败分类的关键词匹配。

实测行数：

| 情况 | bash | perl | awk / grep / sort / sed / cut / ls / free / df |
| --- | --- | --- | --- |
| `LC_ALL=C` | **0** | **0** | 0 |
| `LC_ALL=en_US.UTF-8`（已生成） | 0 | 0 | 0 |
| `LC_ALL=en_US.UTF-8`（**未生成**） | **1**（每个 bash 进程一行） | **7** | 0 |

perl 那 7 行的构成是固定的：`Setting locale failed.` / `Please check that your locale settings:` / `LANGUAGE = (unset),` / `LC_ALL = "…"` / `LANG = "…"` / `are supported and installed on your system.` / `Falling back to the standard locale ("C").`，第 8 行才是程序自己的输出。

用户脚本在缺 locale 的机器上的真实形态：

```text
bash: warning: setlocale: LC_ALL: cannot change locale (en_US.UTF-8)
=== CPU ===
top - 23:42:39 up  1:28,  0 users,  load average: 0.27, 0.36, 0.23
...
```

第一行是污染物：它会打乱「按第几行取数据」的解析，也会让同一份脚本在不同机器上产出不同的前缀。

### 3.6 用户实际用法下，两种取值零差异

开发者的脚本是 Bash，常用 `cat`、`awk`、`${变量}`，主要取 CPU / 内存使用率这类数字。按这个用法逐字节比对（CentOS 7 / GNU 工具链）：

| 场景 | 两取值是否一致 |
| --- | --- |
| `free -m`、`df -h`、`top -bn1` | 一致 |
| `awk` 解析 `/proc/meminfo` 算百分比（`%.2f`） | 一致（逐字节相同） |
| `sort -n`、`sort -k2 -n` | 一致 |
| `${#变量}` 数英文/数字 | 一致 |
| `cut -d: -f2` 取字段 | 一致 |
| `sed` 替换、`grep` 匹配英文 | 一致 |

**不一致的只有两处**：不带 `-n` 的 `sort`，以及**处理中文内容**时。详见 3.7。

### 3.7 代价：按字节还是按字符

| 命令 / 语法 | 处理英文数字 | 处理中文 |
| --- | --- | --- |
| `awk length / substr / index` | 一致 | **不同**（`C` 下按字节，`substr` 会切出半个字） |
| `cut -c` | 一致 | **不同**（`C` 下会切出非法 UTF-8 字节） |
| `${#s}` | 一致 | **不同** |
| `grep -o .`、`wc -m` | 一致 | **不同** |
| `sort`（无 `-n`） | **可能不同**（见 3.8） | 码点序，一致 |
| `[[:alpha:]]`、`[^[:print:]]` | — | **判定会变** |
| `sed`、`tr`、`grep -c .` | 一致 | 一致 |

### 3.8 排序差异的量化

不发 `-n` 的 `sort`，以及 `ls` 本身（`ls` 就按 locale 排序，不需要 `sort`）：

| 数据形态 | 结果不同的比例 |
| --- | --- |
| 纯小写字母 + 数字 | **0%**（200 组抽样） |
| 大小写混合 + 下划线 + `IP` | **85%**（170/200） |
| 典型主机名清单（16 行） | 12 行位置不同 |

## 四、乱码：不属于本工具

开发者的第 2 个诉求是「不乱码」。取证结论是**工具不产生乱码**：

- 采集侧 `lockedBuffer.Write` → `buf.Write(p)`，`[]byte` 原封不动；`outputtap.go` 同样 `string(p)`。
- 写 `terminal-output.txt` 与 `SSHFleetExec.log` 都是纯字节 `Fprintf` / `Fprintln`，无编码器。
- 写 xlsx 全仓唯一的改写是 `strings.ToValidUTF8(s, "\uFFFD")`——只处理**非法** UTF-8，合法字节一字不动，不是 GBK 转码。
- Windows 侧唯一的控制台调用是 VT 位，**不碰码页**；全仓 grep `chcp` / `codepage` / `SetConsoleOutputCP` / `936` / `65001` **零命中**。
- 实测：中文 / 日文 / 韩文 / emoji 文件名走完整链路，终端、txt、xlsx 三处与目标机 `od -c` 逐字节一致，U+FFFD 数为 0。

乱码发生在**屏幕那一环**：工具把 UTF-8 字节原样写 stdout，控制台按当前码页解释。大陆机器出厂码页是 936，UTF-8 字节被当成 GBK 双字节对偶来读，于是出现 `涓╣慨` 一类，表达不了的字符变 `?` 或方块。开发者本机 `ACP=OEMCP=65001`，所以**他自己一直看不出来**。

**这里必须分清哪些是实测、哪些是推断**：

- **实测（可复现）**：工具零转码；本机码页 65001；把宿主 `[Console]::OutputEncoding` 切成 936 后，同一份 UTF-8 字节会被解成 `涓╣慨` 一类。
- **未能复查**：开发者描述「`ls` 列中文名出现方块」时**没有说明发生在哪个环境**——本轮 21 条作者原话里检索不到「只在外部 SSH 工具 / 物理控制台见过」这类表述。该判断是助手与子 agent 的**推断**：既然工具零转码，现象若真出现在工具内，只能是宿主码页所致，而本机码页已被改成 65001。此外本轮也**没能在出厂 936 的机器上直接复现**这张屏。

因此本 ADR 对乱码的处置是：**不修改工具的字节链路**（实测支持），并把手册责任放在「告诉使用者往哪看」（见第七节）。若将来出现「工具内确实看到乱码」的报告，第四节结论需要重审。

另需区分「方块」与「乱码」两种现象——处置完全不同：

| 现象 | 根因 | 判据 |
| --- | --- | --- |
| 方块 □□□ / 空心方框 | 终端缺 CJK 字形（字体问题） | **调大字号，字出现了** |
| `涓╣慨` / `锟斤拷` / `?` | 编码 / 码页不一致 | 调字号无效，形状不变 |

## 五、决定

1. **`[env]` 出厂值里的 `LANG` 与 `LC_ALL` 改为 `C`。**
2. **拼接形态不变**：非 `sudo` 与 `sudo` 两条路径都维持 `sh -c 'export …; <sudo ><解释器> …'`。
3. **不收窄、不废除 ADR-0015 与 ADR-0016 的正文**，只各加一行更新记录指向本 ADR。
4. **`PATH` 与 `TERM` 保持出厂值不变**。`PATH` 在 sudo 下被 `secure_path` 替换属既有事实，另见 6.3。
5. **乱码不作为本决策的处置对象**（第四节）。

## 六、理由

### 6.1 为什么取 `C`：失效形态最稳

「提示语是英文」这件事，`C` 与 `en_US.UTF-8` 效果相同（3.3、3.6）。真正的差别只有一处：

> `C` 的失效形态是「不存在」；`en_US.UTF-8` 的失效形态是「取决于这台机器生成没生成、取决于它的 `/bin/sh` 是谁」。

2000 台机器里有多少台没生成 `en_US.UTF-8` 是不可知的，而一旦落到这种机器上，**每次 bash 调用多 1 行、每次 perl 多 7 行警告灌进输出**（3.5）。对一个要求「同批机器结果可逐字比对」的场景，这是不可接受的不确定性。

`C` 则永远成功、永远安静、永远是英文、永远按字节。**可预测性比最优性重要。**

### 6.2 为什么用户的实际用法不受影响，以及如何回应「我更想保住编码」

**先回应一处可能的冲突。** 作者在 U12 明说：如果非要二选一，他选「不要乱码」。本 ADR 选了 `C`，而 `C` 在字符语义上是退让的一方（3.7）。这是否与 U12 冲突？

**不冲突，因为这是两个不同的轴**：

- **「不乱码」轴**：字节会不会被改写。实测 `C` 下 `ls`、`echo`、`printf` 的中文输出**逐字节原样透传**，`od` 对比与 `en_US.UTF-8` 完全相同（3.6、3.3）。**`C` 不制造任何乱码。**
- **「字符语义」轴**：程序把几个字节算作一个字符。`C` 下按字节算（3.7），`cut -c` 可能切出半个汉字——这是**值被切坏**，不是**编码被改坏**。

作者 U12 要保住的是第一个轴上的「不乱码」，本 ADR 没有在任何地方让步。第二个轴上的退化才是代价，而它落在作者明说「一般这些东西不会是中文」的范围之外（U22）。**两者不是同一件事，所以不与 U12 的二选一冲突。**

**再看实际用法。** 开发者的脚本取的是 CPU / 内存 / 磁盘 / 数字字段（3.6），这些在 `C` 下与 `en_US.UTF-8` 逐字节一致。

### 6.3 为什么 `C.UTF-8` 被排除

见 3.4 末尾：不是「没有」，而是「要工具去改目标机的 `/usr/lib/locale`」以及「跨发行版行为不可枚举」。

### 6.4 为什么拼接形态不改

**最硬的理由是作者 U17 亲口指出的那条约束**：

> 解释器是可以随意配置的。比如遇到 `.sh` 文件用什么解释器，遇到 `.py` 文件就配置什么解释器……**正是因为有这个约束，才导致我之前的决策是现在这个拼接形态。**

环境段必须在**解释器被拉起之前**生效，而解释器可以是 `bash` / `python3` / `perl` / `php`——`export` 不是后三者的语法。所以环境只能挂在 shell 层，不能进正文。这一条与本 ADR 的取证结论方向一致：既然 `export` 已经能穿过 sudo（3.1、3.2），就没有任何理由去动它。

把它改成 `sudo env K=V …` 还会另外付出两份代价、换不到任何收益：

1. **绕过 `sudo` 的全部环境过滤**——`${}` 注入、`PATH` 劫持都不再受控；安全审计可能不认。
2. **要求 sudoers 允许执行 `env` 这条命令**——客户若配的是命令白名单（而非 `ALL`），会直接被拒。

### 6.5 关于「不惜代价」这条基调

作者在 U9、U16 反复申明「哪怕花大代价重构都可以」「不兼容的工作也无所谓」。**本 ADR 不采用这条立场，需要说明为什么。**

本 ADR 否掉候选时用的理由，全部是**技术可靠性**（会不会失效、会不会吐警告、行为是否可预测），**没有一条是「工作量大所以不做」**。第十节里唯一涉及成本的是「2000 台逐台改 sudoers 不可维护」——那不是工作量，而是**每台机器状态不同会让「同批可比」这个初衷失效**，属可靠性问题。

这条基调对**将来**的决策仍然有效：如果复审发现某个方案代价大但更可靠，**按 U16 应当选它**，不要用工作量当理由。本 ADR 如此取舍，是因为取证结果显示：更可靠的就是更简单的那个（`C` 不依赖任何目标机状态，`export` 现状已经能用）。

### 6.6 为什么这不是推翻 ADR-0015

ADR-0015 的「影响」一节原文写着：

> `--sudo` 下变量在 `sudo` 之前导入，能否穿过 sudo 取决于目标机 sudoers（多数发行版保留 `LC_*`；`PATH` 由 sudo 的 `secure_path` 决定）。不带外部依赖就修不了这一点，文档已写明。

该条括号里的「多数发行版保留 `LC_*`」在本轮被**证实**（3.2），不是被推翻。ADR-0015 的其余部分（配置驱动、键名排序、空表不导入、启动期校验）全部不动。本 ADR 只改**出厂取值**这一格。

## 七、影响

- **配置**：`config/SSHFleet.conf` 的 `[env]` 段，`LANG` 与 `LC_ALL` 两行由 `"en_US.UTF-8"` 改为 `"C"`，注释同步改口（现在的「统一字符集与排序」不再准确，因为 `C` 不提供 UTF-8 字符语义）。
- **老配置**：使用者的既有配置里若仍写着 `en_US.UTF-8`，本 ADR 不影响其行为——取值由配置决定，不是代码写死。是否改随使用者。**不提供自动迁移**。
- **下发形态**：**不变**。日志与报告里的「命令行」一行形态不变，`DescribeCommand` 不用改。
- **字符语义**：`awk` / `cut -c` / `${#s}` / `sort` 在处理中文时按字节（3.7、3.8），须写进配置手册，否则下一个写 `cut -c1-4` 切中文的人会踩到。
- **`en_US.UTF-8` 仍然可用**：使用者若确需按字符处理中文，把它改回 `en_US.UTF-8` 即可，代价是 3.5 的警告风险由他自己承担。

## 八、明确不做

- 不改拼接形态（不引入 `sudo env`、不引入 `sudo -E`）。
- 不改目标机的 `/etc/sudoers`、不代跑 `localedef`、不改目标机 locale。
- 不在工具里做码页检测或转码。
- **不在下发时探测目标机环境再配套传变量。** 作者 U12 原话：「还是尽量别去检测当前是什么环境，然后给它做一个配套的环境变量传进去。**别干这种活**。」——包括「先探 `locale -a` 再决定传哪个值」这类只读探测。**取值一次定死，全量下发。**
- **不按发行版做 locale 分档**（第十节最后两条）。
- 不处理 `-a` 的 PTY 丢字符（见 9.1，独立事项）。
- 不按发行版做 locale 分档。

## 九、附带记录（不在本决策范围内）

### 9.1 `-a` 的 PTY 下非 BMP 字符会变成 `?`

CentOS 7.9（GNU coreutils 8.22）在 PTY 下 `ls` 列 emoji 文件名，`emoji😀.txt` 变成 `emoji?.txt`；无 PTY 时完好。中文 / 日文 / 韩文名不受影响。根因在 coreutils 面向终端时的显示宽度判定（`iswprint`），不在工具，也不在传输层——`ls | cat`、重定向、`$(ls)` 全部完好。Ubuntu 26.04（coreutils 9.5）不复现。

开发者已明确表示此项无关紧要，单独另议。

### 9.2 `PATH` 在 sudo 下被 `secure_path` 替换

两个发行版都实测到：工具设的 `PATH` 在 `sudo` 之后被 `secure_path` 覆盖。这意味着「`/usr/local/bin` 里的程序在 sudo 下找不到」是一个**静默的**坑。此事与 locale 同源（都在 `sudo` 边界上），但处置方式不同，本 ADR 不处理。

### 9.3 Ubuntu 26.04 已改用 uutils coreutils

`ls` / `sort` 等是 Rust 重写的 uutils 0.8.0，与 GNU 行为不同：它遇到任何非 `C` / `POSIX` 的 locale 名就一律按码点排序，**不检查是否真的装了**。后果是「同一个 `en_US.UTF-8`，在 GNU 与 uutils 上的排序结果可能不同」——这是支持选 `C` 的一条旁证（`C` 在两套实现下行为一致）。

## 十、备选方案

| 备选 | 否掉的原因 |
| --- | --- |
| 维持 `en_US.UTF-8` | 在未生成的机器上告警污染输出（3.5）；对「英文」无额外收益（3.3） |
| 改 `C.UTF-8` | CentOS 7 不存在；要么工具代改目标机，要么接受每台状态不同；SUSE / 信创实现不统一 |
| 改 `sudo env K=V …` | 现状已能穿透（3.1），改造只增加安全面与 sudoers 兼容风险（6.4） |
| `sudo -E` / `--preserve-env=` | 需 sudoers 的 `SETENV` 许可，默认被拒 |
| 目标机改 `/etc/sudoers` 加 `env_keep` | 每台状态不同 → 无法保证「同批机器逐字可比」。**这是可靠性问题，不是工作量问题**（作者已表态不惜代价，故不以「维护麻烦」为否掉理由） |
| 按发行版分档（CentOS 一个值、SUSE 另一个值） | 发行版组合有几十种，每台的实际取值取决于它属于哪一档 → 同一批机器上会出现多种行为，**破坏「逐字可比」这个初衷**；且作者 U12 明令不探测环境 |
| 工具侧做 GBK ↔ UTF-8 转码 | 针对的是一类并不存在的乱码（第四节）；且无法可靠判断远端字节是什么编码，猜错会把好数据变成坏数据 |
| 在输出采集侧过滤 `setlocale` 警告行 | 治标：警告本身不出现才最干净；且「过滤掉用户可能想看的行」总是一个额外要解释的规则。留作将来若必须用 `en_US.UTF-8` 时的兜底 |

### 12.1 复审时必须守住的方法纪律

这四条不依赖本 ADR 的具体内容，是复审时通用的防呆——每一条都对应本轮一个真实踩过的坑。

1. **判断「变量能否穿过 `sudo`」时，变量必须在 `sudo` 之前设置，且只经过一层 `sudo`。**
   本轮最初正是因为「`sudo` 套 `sudo`」、变量在**外层 sudo 之后**才读，得出了与事实相反的结论（2.2）。这条的一般形式是：**实验形态必须与工具真实下发的形态逐字对齐**——不只是变量设置位置，还包括有没有 PTY、用的是哪个 shell、下发行里有没有外层 `sh -c`。

2. **「提示语是英文」与「字符语义正确」必须分开判。**
   两者正交：`C` 与 `en_US.UTF-8` 在提示语上效果相同（3.3），差别只在字符语义。混起来判就会得出「换 locale 能让提示语统一」这类错误结论。

3. **引用任何一条结论前，先问它是「实测」还是「源码推断」，以及是在什么环境里测的。**
   本 ADR 里至少有两类需要这样对待：
   - 3.2 的 CentOS 5/6 部分**是源码推断**，不是实测；
   - 3.1 的表格**是在 WSL2 上测的**，不是裸机目标机（第十一节）。

   把这两类当成「已实测」引用，是复审里最容易犯的错。

4. **不得把「`C` 永远存在」当成免检理由。**
   这是本 ADR 的结论（3.4），不是前提。复核时须**重新确认**：`C` / `POSIX` 是否仍在 `locale -a` 之外（即不依赖 `locale-archive` 或 `locale-gen`），且在各候选发行版上 `setlocale(LC_ALL, "C")` 是否零警告。任一条不成立，即应推翻第六节的第一条理由。

### 12.2 哪些结论还没被证实

分为三类，处置不同。

**（一）要补的——目标机群可能真的包含，且本轮零实测**

| 事项 | 现状 | 补法 |
| --- | --- | --- |
| SLES 10/11/12 | 完全未验证。SUSE 文档称 sudo 默认给最小环境，且 SLES 12 起默认配成类似 `su` 的行为（可能要求 root 密码）——**这比 locale 问题更优先** | 一台真机上跑 `sudo -V` 看 `env_keep` / `env_check` 两段，并确认 `targetpw` 是否为默认 |
| 信创系统（麒麟 / UOS / Deepin） | 未验证。其中 Debian 系应同 Ubuntu、RHEL 系应同 CentOS，但 libc 是否为 glibc 未确认 | 同上；另确认 `locale -a` 里有没有 `en_US` |

**（二）不补、但已知——已无可部署环境，不再投入**

- **CentOS 5/6 的 sudo 保留行为**（3.2 的源码推断部分）。结论是「保留」，依据是 sudo 1.6.9 与 1.7.x 源码里的硬编码保留段。**不再补测**：这批机器已停止维护，环境难取得；若真有机群仍在用，届时按 12.1 第 1 条的方法在真机上验一次即可。

**（三）不在本 ADR 范围内的**

- **`-a` 的 PTY 丢字符**：9.1 已记录，作者明示「无所谓」并单独另议，**不作为本 ADR 的未证实项**。
