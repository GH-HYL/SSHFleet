# ADR-0010: 一次性工具设计——全局 server 与分散 Shutdown 可接受

状态：已接受（2026-08-27）

## 背景

架构审查（architecture-review-20260827-114310.html 候选 #6）提出：`internal/httpserver/server.go:26` 的包级全局 `var server *http.Server` 与散落 13 处的 `go server.Shutdown()`（batch.go / common.go）违反个人规范「分支不得反向驱动主流程」，建议实例化进结构体、生命周期归 main 统一管理。

## 评估

SSHFleet 的 Go 后端是**一次性进程**：Python 前端拉起 → 处理一个批任务（execute/upload/download 单一请求）→ 进程退出。生命周期 = 一次执行。

在此前提下：

- 13 处分散 Shutdown 不会造成"该退没退/提前退导致服务不可用"——进程反正跑完就退，`http.Server.Shutdown` 幂等，重复调用无害。
- "请求校验失败 → Shutdown 退出"是一次性工具下的合理语义：请求错 = 任务错 = 进程退出，符合预期。
- 全局状态不利于单测的代价可接受：本工程 Go 侧无测试基建，且一次性进程的并发生命周期极简。

## 决策

**不重构，维持全局 server 与分散 Shutdown。**

理由：一次性工具的进程生命周期由单次执行驱动，不存在长驻服务场景下"谁有资格关服务器"的问题；分支反向驱动主流程在此语境下不构成实际摩擦。

## 后果

- **正面**：保持现状零改动，避免为不存在的场景引入结构。
- **负面**：若未来将 Go 后端改为常驻服务（连续多次执行、Web 界面），需重新评估生命周期管理——届时本 ADR 自动失效，需按新场景重构。
- **触发条件**：当出现第二个使用场景（如多次执行复用进程）时，重新审视本决策。
