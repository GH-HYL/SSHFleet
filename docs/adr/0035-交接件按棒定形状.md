## 背景

工单 03 问的是「交接件宽结构一份，还是每种模式各一份」。谈下来发现两个轴被混成了一件：

- **纸按哪一维分**——按站分，还是按模式分；
- **纸里装什么**——这一棒交给下一棒的东西，是上游那份的子集还是另一个更小的集合。

这两个轴一旦分开，答案就自己出来了：**纸属于「站与站之间」，所以按棒定；模式是纸里的一种变化，不该把纸劈成五份。**

另一处模糊来自执行与整理：作者指出「执行过程中就需要整理」，因为每跑完一台就要按配置归类、刷一行到屏幕上。这不是两个站搅在一起，而是「整理」这个词把两道工序合称了：**只依赖这一台的归类，和要依赖全体的汇总。**

## 决定

**一、信封只有一份，随站换三次口径。**

信封按「棒」定、不按模式定：整条线上只有一种信封结构，不是五种模式各一种。它换的是**口径**，不是结构——「要做什么」「发生了什么」「总共怎么样」。三张纸是按口径数的，不是三套不同的结构。

- **摄入交闸门：口径是「要做什么」。** 摄入站手里有配置全文、用户敲的整行命令、清单文件、日志开关；交出去只有：这次干什么活（五份载荷之一）、对谁做、判据表、摄入时发现的问题。配置全文和原始命令行**不进纸**——下游拿到了就会顺手用。
- **闸门交执行：同一张，原样往下递。** 闸门不改数据，只在纸上加一句结论（过了 / 要人点头 / 不让走）和一段留痕，然后原样交下去。它**不另造**，因为造出来也只会多一层抄写。
- **执行交整理：换口径，讲「发生了什么」。** 执行站手里有「要做什么」那张纸；交出去是每台机器的结论：原文、退出码、归到哪一类、成败。这张纸不再回答「这次要干什么」，只回答「刚才发生了什么」。
- **整理交呈现：再换一次口径，讲「总共怎么样」。** 统计、分类分布、按类归拢的机器清单。原文跟着走，因为报告要贴。

口径一换，服务对象就换了：前三棒服务的是「这一批活怎么干」，后两棒服务的是「干完之后怎么说给人听」。

**二、载荷格五份，不合并。**

命令、脚本、上传、下载、改密各一份，各自判断。命令与脚本共用的那段、上传与下载共用的那段，各写一遍——作者认了这笔重复。理由不是「合并不好」，是**现在没有事实支持合并**（ADR 规范三.2 不许为以后可能要用预留抽象）；将来真出现「改了一处不得不改另一处」，再合并，那时是事实驱动。

**三、同一个口径往下传时，后一张必须比前一张窄。**

这条只管前两棒——摄入交闸门、闸门交执行，它们讲的是同一件事（要做什么），后一张只能是前一张的子集加本棒结论。**两张纸一样宽 = 这一棒没过滤任何东西**，那就不该造两次，直接递上一份。

这条主要是给闸门立的：它不改数据，抄一份一模一样的诱惑最大，抄完还显得很守规矩。

**换口径的那两棒不受这条约束**：执行交整理讲的是「发生了什么」，本来就不该有「要做什么」的格子；整理交呈现讲的是「总共怎么样」，也不该有逐台的原文以外的过程数据。对它们的要求是另一句：**只装下一站要用的，用不上的不许带。** 装不上是缺字段，去上游加；带多了是把下游用不着的东西塞进来。

**四、单台归类留在执行里，全体汇总归整理。**

判据：**只依赖这一台机器的整理，放在执行里；要依赖全体才能算的，等跑完再算。** 归类只依赖「这一台的输出 + 判据表」，所以它必然长在执行里；把它挪到后面，只能靠回调，那是往回走。

执行交整理那张纸上装的不是「原始返回」，是「一台的结论」：原文、退出码、归到哪一类。

**五、判据表进信封，塔尖不单独递。**

它至少有两个人要用（执行侧认「密码过期」这类提示，整理侧看分类规则），而它只能由摄入站读一次。让塔尖单独递，等于塔尖得知道「谁要哪张表」——编排知识一进塔尖，它就开始长肉。

**它进第一张纸**，也就是摄入交闸门那张；后面换口径时，下一站还用它就跟着带，不用就不带。

**六、契约里不放函数。**

破例放一个校验，等于给「抽屉」开第一道门：有了第一个函数，第二个就有地方站。

**七、信封的合法性由闸门验。**

纸上写「上传」，格子里装的却是命令——这种对不上只在一处露头，验一次就完。

**八、塔尖只搬不装。**

「不单独递」的边界落在这里：塔尖把信封原样交给下一站，不许往里塞格子，也不许把某一项从信里抽出来当另一个参数递过去。塔尖手上除了信封和退出码，不该有第三样东西。

## 理由

**为什么信封不能按模式分**：信封属于「站与站之间」，模式是纸里的内容。按模式劈纸，等于每个站要开五个口子，加第六种模式每个站再多一个——**那是往浅模块走，不是往深模块走**。深模块要的是「一份纸、一种进法」，背后把五种模式的差别吃在自己肚子里。

**为什么「一样宽就不该造两次」**：两站之间要是没有东西被过滤掉，这道边界其实不存在。抄一份一模一样的，只会让「改一个字段要改两处」凭空多出来一次，而且会让下游误以为「我只拿到该拿的」——其实上游早把整本账递过来了。

**为什么归类不能往后挪**：它只依赖一台，不依赖全体。挪到整理站，要么得在执行过程中回调整理（反向依赖），要么得等全部跑完才刷屏（体验退化）。两条都比现状差。

## 影响

- **执行站变重**：要背判据表，要算归类。这是「单台归类留在执行」的直接代价。
- **刷屏是一条旁路**：执行过程中被打、不控制生命周期，与主链方向无关。谁来接这条旁路是塔尖的事（05 号），具体怎么刷是 13 号。
- **05 号少一个悬念**：塔尖不做「谁要哪张表」的编排，判据随信封走。
- **07 号多一条可机械验的**：交接件的字段集合，除本棒结论外，必须是上一棒的子集。
- **给 0032 决定三补了边界**：那条只说「必须新造」，没说「新造的要更窄」；不补，新造就会退化成抄写。

## 代价

- **重复**：命令与脚本、上传与下载共用的段落各写一遍。作者明示认下。
- **一改改一条线**：信封更厚、判据进纸，改一个需求要动的站更多。作者认这是重构的必然代价，不是副作用。
- **三次换口径 + 五份载荷 = 结构件变多**：读代码的人要先弄清「这一棒在哪个口径上、信封里那一格装的是哪种活」。
- **闸门要验信封合法性**，它比「只看问题清单」多一道活。

## 备选方案

| 备选 | 否掉的理由 |
| --- | --- |
| 五种模式五个信封 | 每个站开五个口子，加一种模式口子再多一个；深模块要一种进法，不是五种 |
| 命令与脚本合一、上传与下载合一（三份） | 现在没有事实支持合并，是预判。以后真出现「改 A 不得不改 B」再合，代价更低 |
| 全流程一个大兜，谁用谁取 | 下游拿得到全部字段，就会顺手用；「不许跨阶段回取」当场失效 |
| 归类放到整理站，执行只交原始返回 | 要么回调（反向依赖），要么延迟刷屏（体验退化） |
| 契约里放一个校验函数 | 契约一旦有行为，抽屉就有了第一道门 |

- **刷屏旁路怎么接、界面什么时候建**——13 号。
