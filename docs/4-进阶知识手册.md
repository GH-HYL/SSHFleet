# 4 进阶知识手册

这是**全部手册的附属手册**：讲工具内部是怎么处理的，以及为什么这么设计。

基础那几册回答"怎么做"；这一册回答"为什么这样、还能不能换个样子、代价是什么"。用不着它一样能把工具跑起来——想弄清一件事的来龙去脉时再翻。

每一节都按同一条线走：**它解决什么问题 → 为什么这么设计（别的做法差在哪）→ 现在怎么做 → 你会看到什么、边界在哪。**

> [!WARNING]
> 这一册讲得**细**、学习曲线**陡**——它拆的是工具内部怎么处理、为什么这么设计，**不是必读内容**。先把前面的手册用起来，遇到想不通的地方再回来翻。

## 1 命令在远端是怎么执行的

先看全貌——不论你跑哪种，发出去的都是下面这几种形态之一（"正文"指你要跑的东西：`-c` 是命令原文，`-s` 是脚本文件内容）：

| 你怎么跑 | 远端实际执行的命令行 | 正文走哪 |
| --- | --- | --- |
| `-c "hostname"` | `sh -c 'export …; bash'` | 会话 stdin |
| `-s deploy.sh` | `sh -c 'export …; bash -c ". /dev/stdin" "deploy.sh"'` | 会话 stdin |
| `-c` 加 `-a` | `sh -c 'export …; bash -c "$(printf %s <base64> \| base64 -d)"'` | 编进命令行 |
| `-s` 加 `-a` | `sh -c 'export …; bash -c "$(printf %s <base64> \| base64 -d)" "deploy.sh"'`（末尾的脚本名只在脚本模式有） | 编进命令行 |
| 任意一条加 `--sudo` | 上面各条里的解释器前多一个 `sudo ` | 不变 |
| `-c` 加 `--no-shell` | **命令原文，一个字不加** | 不用 stdin |
| `-s` 加 `--no-shell` | `<解释器> -c ". /dev/stdin" "<脚本名>"`，不套外壳、不设环境 | 会话 stdin |

两条规律先记住：**命令 / 脚本内容默认不走命令行**（走 stdin），只有配了 `-a` 才为了腾出 stdin 而编进命令行；**`--no-shell` 是唯一什么都不加的**——不加外壳、不设环境、也不加 `sudo`。

**它解决什么问题。** 你敲的是 `-c "df -h"` 或 `-s deploy.sh`，但**远端收到的不是这一句原文**。工具会把它包成一条"先备好环境、再启动解释器"的启动命令，你真要跑的东西（命令原文或脚本正文）从**另一条通道**送过去。所以日志里那行 `sh -c 'export …'` 不是你敲的——第一次看到容易以为工具把命令改坏了。知道每段在干什么，你才分得清哪些差异是工具加的正常包装、哪些得你自己负责（比如加了 `--no-shell`，环境就归目标机了）。

**为什么要套一层外壳。** `export` 只对当前 shell 及其子进程生效——必须先设好环境、再在**同一层**里启动解释器，环境才传得下去。这层外壳就是给"那几句 `export`"和"启动解释器"找一个共同的容器，让它们按顺序在同一个 shell 里发生。

- 为什么用 `sh`、不用 `bash -lc`：`bash -lc` 要靠登录 shell 去读 `/etc/profile` 来补环境，要求目标机装着 bash、shell 认 `-l`、profile 还得是它能解析的语法——三样都不保证。`sh -c` 不读任何配置、只依赖 POSIX 强制的 `/bin/sh`，到处都能跑。
- 为什么正文不放命令行：命令行会经过远端 shell 的解析，正文里任何引号、`$`、反引号都可能被吃掉或展开，得层层转义还容易错；从 stdin 送则**正文完全不参与解析**，也不占命令行的长度额度。

下面以 `-s deploy.sh` 为例，把上面表里那条逐段拆开（真机日志原样；日志里外层单引号内的引号会写成 `'\''`，这里为便于阅读略去）：

```text
sh -c 'export LANG="en_US.UTF-8" LC_ALL="en_US.UTF-8" PATH="/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin" TERM="dumb"; bash -c ". /dev/stdin" "deploy.sh"'
```

| 片段 | 是什么 | 为什么是它 |
| --- | --- | --- |
| `sh -c '…'` | 让远端的 `/bin/sh` 把单引号里那串当一条命令跑 | 见上——做"先设环境、再启动解释器"的容器 |
| `export LANG="…"` | 兜底的语言环境 | 有些程序 / shell 只认 `LANG` |
| `export LC_ALL="…"` | 把字符集与排序锁死 | 见「2 为什么要统一远端环境」 |
| `export PATH="…"` | 一组标准可执行目录 | 同上 |
| `export TERM="dumb"` | 统一成哑终端 | 抑制彩色与转义序列 |
| `;` | 分隔 | 先把 `export` 做完，再启动解释器 |
| `bash` | 跑你脚本的解释器 | 取 `[interpreter]` 里配的（`.sh` 默认 `bash`）；有 `--sudo` 时是 `sudo bash` |
| `-c` | "用后面这段程序文本启动我" | 各家不同（`perl` / `ruby` / `node` / `lua` 是 `-e`、`php` 是 `-r`），工具按解释器适配 |
| `". /dev/stdin"` | 让解释器把 stdin 上的正文读进来执行 | 正文不落盘，只能从 stdin 送 |
| `"deploy.sh"` | 把脚本名交回去当 `$0` | 见下 |

命令模式（`-c`）没有后两段——没有脚本文件、也没有要补的名字。

**脚本名（`$0`）为什么要单独补一次。** 脚本模式的正文不是从磁盘上的文件跑的（默认经 stdin、带 `-a` 时编进命令行），解释器眼里它只是"一段来自标准输入的内容"，`$0` 于是只是解释器名、脚本自己的来源信息是空的。凡是**靠自己的文件名取信息**的脚本（安装包常见：文件名里带目标 IP、站点类型）这时什么都取不到，后面拿这个空值做数值比较会直接报错（如 `[: -eq: unary operator expected`），脚本一声不响地走进"系统不支持"的分支。工具的办法：把脚本名作为 `-c` 之后的**第一个参数**交回去——shell 的 `-c` 后面第一个参数就是本次的 `$0`，脚本再取自己的名字就和"落在磁盘上跑"一模一样了，而正文依旧不落盘。两个边界：

- **只对 shell 家族补**（`bash` / `sh` / `dash` / `ksh` / `zsh` / `mksh` / `ash`）。python 不认这种补法——在它眼里 `-c` 之后那个名字不是脚本名，而是脚本的一个参数，补了等于往它参数表里塞个它不认识的东西，所以 python 维持原样。
- **zsh 要单独适配**：`". /dev/stdin"` 里的 `.` 是 `source`（把内容读进来执行），而 zsh 在 `source` 时会把 `$0` 重置成"被读的那个文件的名字"，等于把补回去的脚本名又盖成 `/dev/stdin`；工具对 zsh 先关掉这个行为再读，名字才能留住。bash、dash 等没有这个问题。

**你会看到什么、边界在哪。**

- 执行日志里 `交给 SSH 执行` 那一段，就是远端收到的东西（`report.txt` 记的是执行参数与结果统计，没有这一段）；带 `-a` 时那段换成 `原始命令 / 处理方式 / 最终命令` 三段。
- **`--no-shell` 关掉的是整层外壳**：不设 `export`、不走外壳、也不加 `sudo`，你写的命令**原封不动**交给目标机（由目标机自己的登录 shell 解析、用它自己的环境跑）。脚本模式同样支持——剥掉外壳后只剩解释器自己那条调用，正文照旧走 stdin、`$0` 照旧补回。它**与 `-a` 互斥**（代填要独占会话），冲突时当场报错。
- 用 `--no-shell` 的代价要清楚：**环境不再由工具统一**——`PATH` 只剩目标机给的那点（`sudo`、`python3` 可能 `command not found`），locale 也回到目标机默认值（中文可能乱码、各机输出形态可能不一致）。所以"批量要稳定结果"时不要加它；它适合你明确知道目标机环境、就要它原样跑一条命令的场合。
- 上传 / 下载 / 改密不涉及这一层——没有"你的命令"要下发，它们的中间命令另有固定形态（见「6 上传与下载的内部流程」）。

## 2 为什么要统一远端环境

**它解决什么问题。** 每条下发行的开头都有一小段 `export …`，它跟你的命令逻辑无关，唯一的目的是**让一批机器跑出同样的结果形态**。SSH 用非交互方式拉起的命令，拿到的环境是目标机自己的默认值，而**每台机器不一样**：locale 有的机器是 `C`、有的是 `POSIX`、有的跟着发行版是 `zh_CN.GB18030`、`ja_JP.UTF-8`；`PATH` 常常只剩 `/usr/bin:/bin`。

**不统一会坏在哪。** locale 管的事比多数人以为的多——**字符编码**（同一段字节按 UTF-8 解是中文、按 GB18030 解可能就是乱码）、**排序规则**（`sort`、`ls`、字符串比较的结果都会变）、**大小写与数字格式**（某些 `awk` / `printf` 的输出会变）。落到批量场景，后果正是最要命的：

- 同一条命令，A 机输出正常中文、B 机一片乱码；
- 工具要把输出归成"成功 / 失败 / 哪一类失败"，形态不一致时**分类可能失准**——该认出来的没认出来，报告与统计跟着错；
- 两台机器的输出没法放在一起逐字比对。

**为什么钉死成 `en_US.UTF-8`。** `LC_ALL` 优先级最高（设了就覆盖所有 `LC_*` 类别），`LANG` 是没有 `LC_ALL` 时的兜底，两个都写上，是防某些程序或 shell 只认其中一个。这样不管你连的是哪台机器、它原本什么 locale，工具跑出来的**中文都是正常中文、排序规则一致、输出可逐字比对、分类稳定**。选 `en_US.UTF-8` 而不是 `C.UTF-8`，是因为它在各类发行版上更普遍、行为更稳。

**`PATH` 为什么写死一组目录、而不读目标机自己的。** 非交互拉起的 `PATH` 常只剩 `/usr/bin:/bin`，而 `sudo` 在 `/usr/sbin`、`python3` 常在 `/usr/local/bin`、`/opt/…`——不补就是 `command not found`。靠登录 shell 去补环境（`bash -lc`）要求目标机装着 bash、shell 认 `-l`、profile 还得是它能解析的语法，三样都不保证；写死一组标准目录则**只要 `/bin/sh` 在就能跑**。

**出厂那四条，以及怎么改。** 这一段来自配置文件里的 `[env]` 段（顶层段，跟 `[account]` 那几段平级），出厂给了 `LANG` / `LC_ALL` / `PATH` / `TERM` 四条：前两条统一字符集与排序，`PATH` 补一组标准目录，`TERM=dumb` 抑制彩色与转义序列（批量的输出要拿去比对、归档，不带终端控制码才干净）。可以自行增删、把某一行的**值留空**即关掉那一条；具体怎么写见 [3 进阶配置手册](3-进阶配置手册.md) 的「6 远端环境变量」。

**值里的 `$` 是谁展开的。** 环境段里每个值都由工具包成双引号下发，**展开动作发生在目标节点导入的那一刻**——工具不代它展开、也不做任何替换。所以 `PATH = "/opt/bin:$PATH"` 拿到的是**那台机器非交互会话**原本的 `PATH`（常常只有 `/usr/bin:/bin`，不是登录之后的那份），各机器可能不同。想要一批机器形态一致，就把目录写全，别用 `$PATH`。

**两点要记住。**

- PATH 里列了目标机上**不存在**的目录不会报错（查找时静默跳过），不影响你的命令输出。
- 解释器装在**非常规位置**时，工具不知道，要你在 `[interpreter]` 里写**绝对路径**（见 [3 进阶配置手册](3-进阶配置手册.md) 的「7 解释器」）。
- 加了 `--sudo` 时，这些变量在 `sudo` **之前**导入，能不能穿过 sudo 取决于目标机的 sudo 配置 → [3 进阶配置手册](3-进阶配置手册.md) 的「6 远端环境变量」。

## 3 代填是怎么工作的

**它解决什么问题。** 安装脚本经常停下来问"请选择架构""要 deb 还是 rpm"——批量跑的时候没人守着按回车，整批会卡到超时。代填就是把你**预知**的答案先写下来：工具盯住远端输出，认出你指定的**触发词**，就把对应内容填进去，脚本自己接着往下走。

**为什么按"触发词"认、不按顺序喂。** 同一个值要填进去，得先知道"远端现在问的是哪一句"。按顺序喂（第 1 个提示填第 1 个答案）要求你把脚本的提问顺序背下来，脚本一改顺序就错位；按触发词认则是**认提示原文**——你把脚本实际打出来的那句话抄下来当触发词，它认得出就往里填，顺序变了也不影响。

**为什么 `-a` 要独占会话的输入通道、正文得改走命令行。** 一次会话只有**一条** stdin。代填要一直盯着远端输出、把答案写回去，这是它的生命线；而正文默认也从这条 stdin 送。两者挤一条通道时，远端 `read` 会把脚本体自己的下一行一起吃掉——**后半段脚本静默消失，还不报错**。所以一旦用 `-a`，正文就改走命令行：base64 编码后编进去，远端再解回来，**全程不落盘**（目标机磁盘满是常态，落 `/tmp` 会因磁盘失败）。代价是长度：命令行给单条命令留的位置有限（整条下发行上限 120KB），base64 又让体积涨到 4/3，所以**正文约 90KB 封顶**；超了工具在**开跑前**就本地拦下报错，不会跑到一半才失败。换句话说，这个上限换来的是"**脚本 + 代填能同时用**"——安装脚本往往又大、又要中途答题，这是最常见的组合。

**现在怎么做。** 你给 `-a` 的每一行是"值 + 触发词"（第 1 列是要填进去的值，第 2 列起是触发词）：

- **匹配口径**：默认是**子串包含、不区分大小写**——触发词是提示原文里的一小段就行，不必整句一字不差。改成按正则匹配、或改成区分大小写，见 [3 进阶配置手册](3-进阶配置手册.md) 的「5 交互代填」（这两项同时管改密的匹配）。
- **值留空**：合法写法，表示"这里只发一个回车"。
- **顺序**：按你在命令行给出的顺序，一条一条往外填。
- **中止词优先**：输出里一旦出现**中止词**（取的是判据文件里「密码过期」那一类的关键词），工具立即终止这台机器的会话、把这个节点归到「密码过期」——而不是继续傻等。（密码过期的机器会反复索要一个你给不出的新密码，及早中止比等到超时更有用。）

**改密为什么不用你配触发词。** `--change-password` 走的是**同一套**匹配机制（同样的正则 / 大小写口径），但提示词与答案都是内置的：远端依次问"当前的密码""新的密码""重新输入"，工具自己认、自己填——`current` 用它自己那台机器的登录密码，`new` 用 `--change-password` 给的新密码。什么时候开始填也不靠你配：它看判据文件里「密码过期」那几个关键词是否出现（也就是那台机器是否真的在要你改密）。这些开口都在 `config/keywords_passwd.conf` 里，撞到没见过的措辞可以自己补（见 [3 进阶配置手册](3-进阶配置手册.md) 的「8 改密配置」）。

**你会看到什么、边界在哪。**

- **两类收尾失败分得开**，含义完全不同：
  - **触发词未命中**——还有代填条目没送出去，说明远端停在了某个你没配触发词的提示上（或提示措辞变了）。这时第一步是回来看远端原文、把触发词补上。
  - **代填用尽后超时**——表里的条目**全送出去了**，之后仍等到超时。工具分不清这是"脚本卡在没配触发词的提示上"还是"任务本身就要跑这么久"，但"表已空"是确定的事实，按它归到这一类。
- **触发词要有区分度**：工具给远端开的是终端（PTY），**远端的回显也会被采集**——如果你的触发词太泛（比如就一个 `1`），可能在你不想填的地方也命中。触发词从提示原文里抄一段有辨识度的文字最稳。
- **与 `--no-shell` 互斥**：`--no-shell` 是"原样下发、工具不附加任何东西"，而代填要工具接管输入，两者冲突时当场报错、不会悄悄忽略。

## 4 结果是怎么定下来的

**它解决什么问题。** 一批机器跑完，"失败"两个字不够用——是**根本没连上**、还是**连上了、命令自己失败**、还是**密码过期**？不同原因要做的补救完全不同。工具把每台机器的结果判成一个分类，让你一眼能把它们分开。

**为什么要先看结构、后看文案。** 判定分两层，顺序不能反：

1. **先看结构事实**——连上没连上、命令有没有给出退出码、是不是超时或被中断。这些是确定的，能靠就先靠。
2. **再查文案**——剩下要区分"具体为什么失败"，才去比对远端报错里的话。文案是目标机 / 系统给的、会变，所以它放在第二层，且判据外置成一个你能改的文件。

**现在怎么做。**

- **成功怎么算**（各操作不同）：会话里跑命令（命令 / 脚本 / 代填共用一条）——**退出码为 0、且没超时没中断**；上传 / 下载——连接成功、没有一个文件失败、且有文件成功；改密——干净收场、且整场出现过"要改密"的信号。
- **先按结构事实分开的几类**（不经文案表，直接定性）：密码过期（中止词命中）、触发词未命中、代填用尽后超时、部分成功（上传 / 下载有成功也有失败）、密码未过期（改密整场没出现过期信号）、任务已取消（连上之后跑到中途被中断）、建连被取消（还在建立连接就被中断）。
- **其余按文案查表**：判据在 `config/keywords_error.conf`，分**两组**，用哪组看"目的那条命令有没有给出退出码"——
  - 命令**没**给出退出码（连不上、传输失败、改密…）→ 查**第一组**，先看报错原文（含服务端提示）、后看命令输出；
  - 命令**自己以非 0 收场**（会话被拒如密码过期、命令自身失败）→ 查**第二组**，命中的分类会顶掉笼统的「执行失败(退出码N)」，退出码本身照旧保留。
  - 两组都是**自上而下先命中算数**（具体的原因写在前面、笼统的写在后面），**不区分大小写**，中间会变的部分用 `*` 代替。
- **实在认不出时**：不显示笼统的"失败"，而是把报错原文（截断后）当作分类显示出来——保留具体内容，你还看得见目标机到底说了什么。两段都空才兜底显示「原因未知」。
- **退出码从哪来**：只有远端命令**真的给出了退出码**时才有（超时、中断这些收不到真实码）。`--sudo` 不做特殊处理，退出码就是被 `sudo` 包一层之后透传回来的那个。

**你会看到什么、边界在哪。**

- 每个分类可以带一句 **tip**（写在判据文件里），本批真出现过这个分类时，统计末尾跟着显示——告诉你"这一类可能包括哪些情况"。还没想好就留空，不影响使用。
- **判据文件你能自己改**：增删关键词、加新分类、停用某类，改完存盘、重跑即可，不用改程序。越具体的原因写在越前面。
- macOS / Linux 的若干系统提示、以及"密码过期"这类服务端文案，都是靠这个表认出来的——目标机换语言、PAM 换版本导致认不出时，往对应那条补一段关键词就行。

## 5 危险命令检测的口径

**它挡的是什么。** 你在 200 台机器上跑 `-c "rm -rf /tmp/x"`——手一抖写成 `rm -rf /`，这条会在 200 台上同时执行。工具在下发前先看一遍命令：命中严重规则直接拒绝，其余级别列出来让你确认。它是**提醒，不是闸门**——命令本身合法、只是看着危险时，决定权仍在你。

**为什么不用关键词。** 直接找 `rm`、`mkfs` 这类词，误报漏报都多：`grep rm` 里有 "rm"，注释里提到 `mkfs` 也会被拦；反过来 `$(echo cm0=)…` 这种拼出来的又认不出。所以工具先按 shell 语法把命令拆成结构（谁调用谁、参数是什么），再逐条判定——`grep rm` 不误伤，`xargs rm` 与 `rm` 落到同一条规则。命令本身语法就写错时，退回逐行判断。

**做成什么样。** 规则在 `config/keywords_dangerous.conf`，每条有 `name` / `example` / `regex` / `risk_level` / `enabled` 五个字段，级别是 `forbidden` / `high` / `medium` / `low`。`forbidden` 直接拒绝执行；其余级别打印警告、列出命中的规则，要你确认才继续（`--yes` 下只留痕放行）。它还会剥掉包装命令（`sudo` / `env` / `xargs` 之类）、归一 `rm` 的旗标，并递归解析"间接执行"（`shell -c`、`eval`、`ssh`）里的命令，最多钻 5 层。

**效果与边界。** 只覆盖你写的命令原文（`-c`）与脚本正文（`-s`）；上传 / 下载那些工具自己拼的中间命令**不看**。所以它拦的是"你的意图"，不是"一切会伤到机器的路径"——规则文件里的 `enabled` 可以逐条启停，你觉得某条太严就把它的关键词改具体，或直接停用。

## 6 上传与下载的内部流程

**它解决什么问题。** 批量传文件时你关心几件事：文件落在哪、会不会把目标机上的同名文件盖掉、目录里的软链接怎么办、为什么有时快有时慢。这几件都由工具的固定做法决定，不是随机的。

**为什么这么做。**

- **软链接一律跳过**：一个软链接可能指向目标机上的敏感文件（如 `/etc/shadow`），也可能绕成一个环。照传既危险、又没意义——你要的是文件本身，不是"指向它的那次指向"。所以上传时本地目录里的软链接、下载时远程目录里的软链接，都记进"已跳过"、不上传也不报错（整批**全是**链接才报错，那时多半是你选错了目录）。Windows 上 `.lnk` 快捷方式同理。
- **目标机上同名文件不覆盖**：批量场景里一次错误的覆盖很难追回。遇到同名，该文件直接判失败、不覆盖目标机上的原文件——宁可让你看着失败去决定，也不替你默默盖掉。这条背后是全工具的同一个取向：**工具干的是批量活**，同一个动作在成百上千台机器上同时发生，一旦"事后难追回"就没有补救余地——所以这类动作默认都不静默执行，宁可报错、或拦你确认一次。
- **加了 `--sudo` 时先传临时目录、再挪过去**：SFTP 用的是登录用户的权限，写不进只有 root 能写的目录。所以 sudo 上传时先把文件传到目标机的一个临时目录，再用 `sudo mv` 挪到目的地（下载侧则在读之前先判断能不能读）。
- **"小 / 中 / 大"文件那几个阈值不改实际并发**：它们只在**开跑前的确认屏**给你一句并发建议——总大小小于 `small_file` 就建议全并发，大于 `large_file` 就建议串行，介于两者之间用 `medium_parallel`（还会按你的节点数封顶）。真正的并发数始终是你给的 `-n`（节点级）——它只建议，不替你改。见 [3 进阶配置手册](3-进阶配置手册.md) 的「9 上传并发」。

**现在怎么做。**

- **上传**：本地先做一遍准备——采集要传的文件、滤掉软链接、拒收管道 / 设备 / socket 这类特殊文件、校验可读性、算出各自的相对路径。然后逐节点：建连接 →（sudo 时先清一把临时目录）→ 建立 SFTP → 确认目标目录存在且是目录 → 本地文件逐个预检 → 逐个传输（非 sudo 直接写目标位置，sudo 走"临时目录 → `sudo mv`"）。中途失败会删掉没传完的半成品。
- **下载**：先在目标机预检你要的路径在不在 → 逐个判断：是文件就直接下载，是目录就一次列全里面的**真文件**与**软链接**（软链接滤掉）→ 落到本地 `你指定的目录/<该节点 IP>/` 下，逐文件下载。**每个节点一个子目录**，多台机器同名文件才不会打架。

**你会看到什么、边界在哪。**

- 被跳过的软链接会列在"已跳过"里，不当作失败；但如果你给的目录里**一个能传的文件都没有**（全是链接），工具会报错——提醒你目录可能选错了。
- 下载的落点目录按节点 IP 分子目录，找某个节点的文件就是进它那个 IP 目录。
- 上传 / 下载不受 `[interpreter]` 影响——它们执行的中间命令是固定的那几条，与你配的解释器无关。

## 7 主密钥为什么要单独存放

**它解决什么问题。** 打开加密之后，密码与口令以**密文**形态存在磁盘上；要解开它，得有一把钥匙——**主密钥**。这一节讲的是这把钥匙放哪、作用范围有多大、丢了会怎样。

**为什么不和凭据放在一起。** 加密的意义就是"**光有凭据文件还打不开**"。钥匙要是和凭据存在同一个地方，那不过是把明文换成了另一串字符——谁拷走了凭据文件，就连钥匙一起拷走了，等于没加密。所以主密钥**单独存在本机的环境里**，和凭据文件分处两地：把它拷到别的机器，解密就失败。

**为什么它只在本机本用户有效。** 主密钥存在**你运行工具的那台机器、那个用户**的环境里：Windows 写进该用户的注册表环境变量，Linux 写进你登录 shell 的启动文件（bash 是 `~/.bashrc`、zsh 是 `~/.zshrc`）。所以它的作用范围就是**这个用户、这台机器**。

**据此判断要不要用加密**（出厂默认就是开着的，这里说的是要不要关掉它）：

| 你的情况 | 建议 |
| --- | --- |
| 在一台固定机器上长期跑（定时任务、日常工作机） | 适合打开 |
| 需要把凭据文件到处拷、或经常换机器执行 | **不要打开**——换机器、换用户、换终端会话都可能读不到主密钥 |

**现在怎么做。** 处理主密钥有三条命令——生成（`--gen-key`）、查看现状（`--key-status`）、转换凭据文件（`--convert-secret`）。三条都**单独使用**、不跟批量执行一起用；各自什么时候用、怎么用见 [3 进阶配置手册](3-进阶配置手册.md) 的「2 加密与密钥」。**生成之后要重开终端**——当前终端读不到刚写进去的环境变量。

**你会看到什么、边界在哪。**

- 工具每次运行都会比对"当前终端读到的"与"本机保存的"，对不上会当场说明现状与下一步。
- **两处不一致时，加密方向会被直接拦下**（用旧钥匙加密的文件，重开终端后就打不开了）；解密方向只警告、不拦。
- **丢了会怎样**：主密钥丢了，**已加密的凭据文件就解不开了**，只能重新把明文写进文件、重新加密一次。所以：不要把主密钥和凭据文件放在同一个地方备份；提示"本机已保存但当前终端没读到"时**不要重新生成**——重开终端就好，重新生成会换掉钥匙，已加密的凭据全部失效。

## 8 工具的内部骨架

**它解决什么问题。** 想知道它整体是怎么跑起来的、要不要在目标机上装东西、跑到一半中断会怎样——这一节给一张全局图，其余每一节的细节都能挂到这条链上。

**它是什么形态。** **一个独立的程序**：不用在目标机上装任何东西、不开本地端口、不起后台服务——本机直接连上目标机的 SSH 干活，传文件走 SFTP。

**一次运行的完整链路**，以及每一步在哪一节展开：

```text
解析与校验参数 → 危险命令检测 → 补全目标节点信息 → 参数确认 → 并发连接所有节点
     → 实时进度与结果回流 → 统计 / 报告 / 归档
```

| 这一步 | 它做什么 | 想看细节 |
| --- | --- | --- |
| 解析与校验 | 读清单与配置、校验参数组合是否成立、量一遍下发行的长度 | 「1 命令在远端是怎么执行的」 |
| 危险命令检测 | 把命令拆成语法结构逐条判定 | 「5 危险命令检测的口径」 |
| 补全目标节点信息 | 把配置里的默认值填进每台机器还没写全的字段 | [2 基础配置手册](2-基础配置手册.md) |
| 参数确认 | 开跑前把这次要做什么摊给你看，要你确认 | [1 使用手册](1-使用手册.md) |
| 并发执行 | 按节点并行连上去干活（命令 / 脚本 / SFTP） | 「6 上传与下载的内部流程」 |
| 结果回流 | 边跑边报进度，每台机器的输出与结果实时回填 | 「4 结果是怎么定下来的」 |
| 统计 / 报告 / 归档 | 汇总分类、出报告、把这次执行归档 | [1 使用手册](1-使用手册.md) |

**边界在哪。** 并发按**节点数**并行，可用 `-n` 限流。**中断（Ctrl+C）时停止派发新任务**，已经在跑的、已经完成的节点结果**照常整理归档**——不会把已经跑出来的东西丢掉。配置与规则文件在启动时一次校验完，问题一次报清，不用逐轮试。

## 9 哪些东西不开放配置

产物自身的文件名与目录名——执行记录目录、日志名、终端输出名、报告名、结果表名、规则文件名——**不开放配置**，由程序内置。

原因是这些名字被各处**互相引用**：归档目录里的报告、日志、结果表互相指着对方，打包与排查也按固定名字去找。让它们可配，等于让"这次执行的文件到底在哪"变得不可预期，反而添乱。你要改的是**内容**（配置项、判据关键词、规则），不是这些容器的名字。
