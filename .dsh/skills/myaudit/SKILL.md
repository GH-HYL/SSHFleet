# 审计

## 一、定方向

方向 = 查哪类问题。从下面挑，至少两个；对象沾不上的不挑。

| 方向 | 查什么 |
| --- | --- |
| 事实 | 引用是否成立：`file:line`、命令、提交号、版本号逐一对 |
| 一致性 | 文档之间、文档与代码打架；计数、编号不重不漏 |
| 形式 | 文件名、字段、状态值、编号合不合本仓约定 |
| 重复与分叉 | 同一判据、骨架、常量在两处各写一份，或两处已分叉 |
| 没人用的东西 | 无调用者的函数、没人读的参数、永远匹配不上的配置 |
| 缺防护 | 边界条件、错误处理、资源回收、危险操作的拦截 |
| 缺测试 | 关键路径没有测试，或整个包零测试 |
| 文案 | 报错与提示说不清、举例与实际不符、不点名到具体选项 |

## 二、派活：先估范围，再定谁去

**每个方向先估要看的文件**，估个大概就够。

**范围重合的方向，并给同一个子 agent 执行**——同一批文件被几个人读一遍是最贵的浪费。并的是执行者，**方向仍各算一个，结论仍各出一份**，只是同一个人看完。

发给子 agent 的提示词两样都要有：

- **查哪类问题**——照上表，不要只说「去审一遍」。
- **范围**——具体到文件或目录。跨模块的方向（重复与分叉、一致性）范围写「全对象」。

## 三、核验

**主 agent 核。** 子 agent 每条结论连依据（命令、`file:line`）回报，主 agent 逐条核过才进报告。照对象自述下结论不算。

## 四、报告要有这几样

1. **审了什么**——对象与范围，以及审的时候对应的提交。
2. **分了哪些方向、谁审的。**
3. **一条一个问题**，每条给：位置、问题、依据、建议。
4. **没核实的**——想查但因环境、权限、时间没查成的，明写，不隐去。
5. **落到哪**——被审对象能写就写进它的 Comments；写不了（如代码）独立成报告。

## 五、边界

- **只提结论，不改**——改不改、怎么改由作者定。
- **观感类不算缺陷**（「看起来乱」「更好读」不是问题）。
- **拿不准标「待作者确认」**，不替作者拍板。
- **范围外的问题只报告**。
