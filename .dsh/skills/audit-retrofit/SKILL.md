# 回顾审计

**用途**：审**代码实现与实现效果**。独立技能，不是 `/code-review` 的补丁——分界见「边界」。

锚链只有一条：议题说明**问题是什么**，只作引路；**ADR 的决定与理由是唯一基准**；规格与工单**不可信**，只当被审对象。

**派发审计只为一个目标：代码质量。** 文档不是审计目标——顺带发现的文档错误记下来提报；因文档导致实现跑偏的，着重记。

主 Agent 只做调度：摸底、切轴、写提示词、核实疑点，**不亲自审**。

**子 agent 一律后台跑**：不等、不轮询、不反复读回执；无活可做就提前结束本轮。唯一例外是**分发审**（见 2.3）。

**派出去、指向别的技能，都是为本次审计服务**：它们算工具，不算约束；约束上有差异，以本文件为准。

**大流程四段：梳理 → 分发 → 收集 → 收尾。**

## 一、梳理

### 1.1 确认主场

判据看三样：议题目录下有没有 `issues/` 子目录、`git diff` 有没有实现改动、ADR 头部元数据里的「实施载体」写的是「待排期」还是具体路径。三样齐了才是主场。

**只认「代码已落地」这一种形态**：手头只有 ADR、代码零改动的，不归这里；这种需求另走 `audit-docs`。

文档不齐、或还没验收就想跑：问开发者一次。他说强行跑，就按现有材料跑——**本技能不为它降要求，也不保证质量**。

### 1.2 定锚

**基准只取 ADR 的「决定」与「理由」。** 议题文档里的实施方法、行号、清单、勾选状态，全是待审对象。

把 ADR 的「决定」逐条抄成**大方向锚**，编号，随每份提示词下发。开头一句固定：

> 以此为准。议题文档里的具体修法是被审对象，不要被它带偏；发现实现与锚不符，报锚，不要报工单。

**每条锚要标授权来源**：开发者明示的，还是执行者推导的。**推导的那些是重点审对象。**

**锚可以被质疑，但只能单列回报。** 子 agent 发现锚与源码、实测或上游 ADR 对不上，**不许改写锚，也不许并进普通发现**——另起一节「锚质疑」，写清哪条锚、哪份证据、按什么判；改不改锚由开发者定。

### 1.3 盘代码面

- **git 范围**：从议题自述的摸底基准到 HEAD；`git show --stat` 确认主提交的文件面。开发者没说范围就自己定，并在清单里写清理由。
- **代码落点**：哪个模块目录、哪些包被大量改动。
- **复现环境**：有无现成测试机、账号、构建方式。

### 1.4 查既往审计记录

**审过的点不要再审。** 查议题目录有没有 `audit.md`、`findings-*.md`、`audit-run-*/`（本技能的产物目录）、其他历史报告；有就列出来：审过什么、结论是什么、改过没有。

### 1.5 传什么、不传什么

判据：**传「不要怎么走」，不传「路已经走过了」。**

| 类型                           | 传不传               |
| ------------------------------ | -------------------- |
| **被证伪的结论**（试过、错了） | **必传，且标明**     |
| **踩过的坑**（方法错误）       | **传方法，不传结论** |
| **已验证的结论**（测过、对了） | **不传**           |

写法：「X 这个方向已经证伪，原因是 Y，**不要再走**」，而不是「X 已经证伪，所以你只需要验 Z」。

### 1.6 交接清单

产物落议题目录下的 `audit-run-<日期>/`，**不落 `build/`**。里面放 `分发缺口.md`（分发审的缺口清单）、`提示词.md`（下发的提示词包全文，改一次留一版，标 `v1`/`v2`）、`回执/`（各轴回执）、`报告.md`（收尾）。清单六节：

1. **被审对象**——哪些文件、哪些代码，以及「只看不碰」的边界。
2. **关键前提**——是不是主场、文档齐不齐、有没有强行跑的授权。
3. **锚**——ADR 核心主张，编号，标授权来源。
4. **必须知道的背景**——被证伪的方向（含原因）、踩过的坑（只给方法）、已审过的轮次。
5. **建议的审计轴**——按代码结构定，不套模板。
6. **环境与授权**——环境事实（哪台机、工具与解释器版本、账号，写成已核的实测）、授权范围、只读声明。**每条子 agent 指令都要原样复述这些事实**，不许让它自己再摸一遍。

## 二、分发

按**代码结构**切，不按工单顺序切。每轴一个子 agent，文件域白名单隔离。

### 2.1 派谁

**规范轴直接派 `/code-review`**，只用下表的「用」那半：

| 用                                                                 | 不用                                                                                                                       |
| ------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| 两轴的切分：规范符合度、规格符合度                                 | **它的 Spec 基准**：它拿 spec 原句当判据（`Identify the spec source`、`quote the spec line`）。本技能里 spec 只作被审对象，**判据是锚**；spec 与锚冲突时按锚判，冲突本身走锚质疑 |
| 规范来源检索顺序：仓库文档 → 缺省 smell 基线                       | **它的收尾**：`## Standards` / `## Spec` 两节并列 + 一行总结。本技能收口只有回执 + 三段式                                  |
| smell 基线十二条，以及它自带的三个约束（仓库文档压过基线、smell 一律算判断题、工具能抓的跳过） | **前台并发**：它要求两个子 agent 前台同时发。本技能的子 agent 一律后台跑                                                    |
| diff 取点：三点 `...` 对 merge-base                                | **`Under 400 words` 上限**：回执不限字数，证据写全进文件                                                                    |
| —                                                                  | **它的两个前置**：`/setup-matt-pocock-skills` 那套 issue tracker（本仓库议题在 `docs/issues/<slug>/`）、「没有 spec 就跳过 Spec 轴」（本技能不跳，没有 spec 就纯按锚判） |

子 agent 提示词里固定写这一句：**本轮只用 `/code-review` 的轴与基线，不用它的基准、收尾、字数上限与并发方式；spec 是被审对象，不是判据。**

其余轴自己切，示例：

| 轴               | 审什么                                                                                       |
| ---------------- | -------------------------------------------------------------------------------------------- |
| **架构**         | 唯一定义落点是否最优、依赖方向、层级边界、窄接口、调用链                                     |
| **跨模块不变量** | 同一概念在多处的定义是否真的一致；不变量被谁破过                                             |
| **判定/决策层**  | 旧概念撤净否、优先级次序、覆盖缺口（**多出 = 永远认领不到；遗漏 = 永远归不了类，后者最重**） |
| **配置与映射**   | 配置条目与实际产出是否一一对应、顺序、退役条目撤净否                                         |
| **呈现层**       | 回落口径、统计口径、自有文本的边界                                                           |
| **真机复现**     | 构建 / vet / 全量测试 + 按场景分账号复现                                                     |

**隔离手段**：每份提示词写明文件域白名单（「不碰 X，那归另一轴」）。

### 2.2 提示词固定件

1. **大方向锚**：编号条目，配「以此为准」那句；**另加锚质疑出口**（规则见 1.2）：发现锚与证据冲突，单列一节回报。
2. **重心声明**：只审代码质量；文档问题顺带记，因文档跑偏的着重记。
3. **授权声明**：「只做只读分析，不得修改任何文件」。跑构建/测试的轴另写：临时产物只落 `build/`。
4. **文件域白名单** + 要对照的议题文档章节。
5. **回执写什么**：每条给**位置与证据**（命令或原文），照它能翻到原处；区分【硬伤】（事实错误、边界被破坏）与【判断题】（可权衡，说明理由与代价）；**没发现问题就明说「未发现问题」**。
6. **沙盒与资源**：写清本轴能用哪台机、哪个账号、哪些操作禁做。**测试账号按轴分发，不许两轴共用一个**。

### 2.3 分发审：发出去之前审提示词

派一个**分发审**，只审这包提示词本身，**不查代码**。它读的是地图，不读内容：这地盘多大、该切几块、切全了吗。

**给什么**：审计目标（一句话）、提示词包全文（**锚随包给，不算预设**）、被审对象的结构与规模（目录、文件数、行数）。
**不给什么**：主 Agent 的推理过程与预设结论、被证伪的历史（这些只给审计轴，见 1.5）、具体技术论证。

**四类必查，逐条给结论**：

| # | 查什么         | 判据                                                                              |
| - | -------------- | --------------------------------------------------------------------------------- |
| 1 | **轴间缝隙**   | 几轴文件域并起来，覆盖被审对象全部了吗？有没有哪块说好了「谁都不碰」              |
| 2 | **轴间重叠** | 有没有两轴审同一块——重叠会得出相反结论，还得多一轮核实                          |
| 3 | **预设污染**   | 提示词里有没有夹带主 Agent 的判断（「注意 X 可能有问题」已经是替子 agent 下结论） |
| 4 | **边界与产出** | 每轴的文件域、回执要写什么、硬伤/判断题的区分，写清了吗                           |

**产出**：只给**覆盖缺口清单**，落 `audit-run-<日期>/分发缺口.md`，每条说清「缺什么、补哪个轴或补哪条约束」。

拿到清单改完再发，**一轮就够，不循环**。

### 2.4 派发前问开发者

切完轴、提示词过完分发审，**发出去之前问一次**，用 `my-grill`：

- **测试环境与账号**：这轮在哪台机上跑、账号怎么给。议题文档没写、`build/` 又翻不到，就直接问，不要自己猜。
- **决策内容**：ADR 里哪几条是这次的重点、有没有没落进文档的口头约定。

**只读不需要「授权开工」。** 要动真机、要占账号、要跑构建与测试的，把那几条单独问一次再发。

### 2.5 复核员：独立自建框架

**另派一个复核员，它不接任何现成轴**：

1. 读锚（ADR 决定）、读改动面、读议题文档；
2. **自己设计一套本轮的审计框架**——本阶段特有的风险在哪、上面那些轴漏了什么；
3. 按自己的框架执行，或再派子 agent 执行；
4. 报告里写明**它设计的框架是什么、为什么这么切、上面哪些轴有盲区**。

**授权放宽**：只读，读什么、按什么顺序读由它定；**要的是不同的切法，不是审得更细**。

### 2.6 两个角色的分工

|                  | **分发审**                       | **复核员**                   |
| ---------------- | -------------------------------- | ---------------------------- |
| 时机             | 提示词写好、**发出去之前**       | 各轴**跑的同时**             |
| 靶子             | **审计设计**（提示词包）         | **审计内容**（代码与文档）   |
| 读什么           | 只读地图：结构、规模、提示词全文 | 深入读：锚、改动面、议题文档 |
| 能不能自己查代码 | **不能**，只审设计               | 能，授权放宽                 |
| 负责什么         | **查「有没有漏」**               | **查「框架对不对」**         |

**两个都要派。**

### 2.7 真机复现

- 先定复现方案再跑；跑不通如实记，**不许编造结果**。
- 明确禁危险操作；复现环境信息从议题文档抄，账号密码原样下发。
- **复现行为异常回主 Agent**，路由回对应实现轴定位——不要在复现轴里直接下结论。

## 三、收集

**子 agent 直接写自己的回执文件**，落本次目录的 `回执/`，一轴一份，文件名带轴号；复核员的也放这里，分发审的缺口另落 `分发缺口.md`。返回文本可以简略，完整证据在文件里。`回执/` 与 `分发缺口.md` 只读。

**盯着各轴的回执**。某轴迟迟不到就接着等，别替它提前收工；真卡住了，开发者会来说。

**跨轴矛盾不在子 agent 间互传**，一律回主 Agent 核实：自己读源码核过的，写明是自己核的、怎么查的；核不了的进第三段交开发者定。

## 四、收尾

按 **[REPORT.md](./REPORT.md)** 三段式，落 `audit-run-<日期>/报告.md`。

## 边界

- **只审计，不改被审对象。** 修复、补用例、改文档都等开发者授权，另开工作。
- **审计思路不得被工单塑造。** 轴的切法来自代码结构与 ADR 层级，不来自施工顺序。
- **不重复 `/code-review`。** 规范轴直接派它，本技能只补它覆盖不到的部分（架构、跨模块不变量、真机复现）。
- **不追对话。** 决策以 ADR 为准，会话记录不在审计范围内。
- 不预设仓库结构；摸底查到什么用什么。
