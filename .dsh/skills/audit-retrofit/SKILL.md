# 回顾审计

对一个**已经做到某个阶段的产出**做多轴并行验收。主 Agent（orchestrator）只做摸底、分发、核实疑点、聚合，**不亲自审**。

**派出去的是后台任务：子 Agent 真的在后台跑，主 Agent 不等它。** 各轴、分发审、复核员都用后台任务（subagent）启动；启动之后主 Agent 立刻转去做自己那摊事——核对基点、查既有审计记录、整理仓库的文档纪律；**真没活了自然结束本轮**，不要留在原地等回执。

**主 Agent 不等子 Agent 返回**：不 `sleep`、不轮询任务状态、不反复读回执文件，也不为了「先把结果拿到手再写结论」改成前台调用。子 Agent 跑完会自己把结果送回来，那就是下一轮。更**不要自己下场把某一轴跑一遍**——主 Agent 一旦变成审计员，独立复核就没了，并行也没了。有前后依赖的（分发审 → 改提示词 → 再发轴）按序等，那不算空等。

**核心是「回顾」，不是「重型」**——重型指范围大到单轴装不下、必须多轴并行，它是手段。真正要回答的只有一句：**这份产出，够不够格作为下一步的依据。**

**这不是看一次 diff。** 议题文档里充斥实施层主张（怎么修、行号、清单）——**它们不能当审计基准**，只能当被审对象。

## 零、适用情况：先判断这次审什么

**任何阶段都可能做回顾，审的对象不同，用的轴完全不同。** 摸底第一步就是判断当前处在哪个阶段。

| 阶段 | 手上有什么 | 审什么 | 不能用的轴 |
| --- | --- | --- | --- |
| **A. 只有 ADR** | 决策写完了，代码没动 | **ADR 够不够格派生 spec 与工单**：结论站不站得住、标注诚不诚实、落到工单会不会冒岔路 | 实现轴、复现轴——**没东西可审** |
| **B. 有了议题** | ADR + spec（可能带头几份工单） | **规格是否忠实于 ADR**：拆法会不会漏掉 ADR 的某条、验收项能不能被判死 | 尚未落地部分的实现轴 |
| **C. 完整流程走完** | ADR + spec + 全部工单 + 代码 | **实现是否符合 ADR 的方向**，以及文档是否跟上了实现 | —（全部适用） |
| **D. 只有代码，文档缺失** | 代码改了，ADR 没写或过时 | 先补文档还是先审代码？**建议先补 ADR**——没有方向锚，多轴审计会各说各话 | 全部轴都缺基准 |

**硬要求**：阶段判断错，后面全错。**拿不准就问用户「现在是哪个阶段」，不要默认按 C 审。**

**判断方法**：看议题目录有没有 `issues/` 子目录、`git diff` 有没有代码改动、ADR 文首的「实施载体」写的是「待排期」还是具体路径。

## 零·一、依赖什么、不依赖什么

这是本技能最容易做错的一处取舍：**新会话不继承老会话的记忆，但也不能对路径一无所知——什么都重测一遍，重型到没人跑得起。**

判据只有一条：**传「不要怎么走」，不传「路已经走过了」。**

| 类型 | 传不传 | 理由 |
| --- | --- | --- |
| **被证伪的结论**（试过、错了） | **必传，且标明** | 不传，新会话必然再走一遍同一条死路，白烧一轮。负资产传下去只减不增 |
| **踩过的坑**（方法错误，如实验形态不对） | **传方法，不传结论** | 传方法能防重复犯错；把结论也给出去，就变成了免检 |
| **已验证的结论**（测过、对了） | **不传** | 传了等于给它一个「不用验了」的借口。**审计的价值恰恰是独立复核**，让它自己测 |

**写法**：背景里写「X 这个方向已经证伪，原因是 Y，**不要再走**」，而不是「X 已经证伪，所以你只需要验 Z」。

## 与另外三个技能的分工

| 技能 | 审什么 | 什么时候用 |
| --- | --- | --- |
| `/code-review` | 一个 diff 的规范符合度 + 规格符合度 | 提交前、看一个分支或 PR |
| `/audit-docs` | 一批文档改动的自洽、规范、事实 | 文档刚改完 |
| `/audit-conversation` | 文档是否忠实于对话结论 | 长对话刚写完总结，趁记忆还在 |
| **本技能** | **某个阶段的产出能否作为下一步的依据** | **新开会话，独立复核** |

**本技能不重复它们的做法，只负责分工与调度**：文档轴直接派 `/audit-docs`，代码规范轴直接派 `/code-review`，本技能只补它们覆盖不到的部分（架构、跨模块不变量、真机复现）。

**只借本体，不借附件。** 派 `/audit-docs`、`/code-review` 时，只读它们的 `SKILL.md` 本体——轴、判据、报告格式；它们的附件是**收尾规程**（如 `audit-docs/REPORT.md` 的三段式），**不读、也不执行**，收口只有本技能的 `report.md`。**子 agent 提示词里写明这一句**，否则它会照着指针技能的结尾多造一份汇总。

**本技能不看会话记录。** 决策已由 ADR 与工单固化；要追「用户当时怎么说的」走 `/audit-conversation`，性质不同。

## 一、摸底：主 Agent 亲自做

**摸底要落成一份交接清单**（给子 Agent 与审计员用），六项见 1.4。

### 1.1 锚是什么：ADR，不是工单

**审计基准只取自 ADR 的「决定」与「理由」。** 议题文档里的实施方法、行号、清单、勾选状态，**全部是待审对象，不是标准答案**。

把 ADR 的「决定」逐条抄成**大方向锚**，编号，随每份子 Agent 提示下发。开头一句固定：

> 以此为准。议题文档里的具体修法是被审对象，不要被它带偏；发现实现与锚不符，报锚，不要报工单。

**每条锚要标授权来源**：是用户明示的，还是执行者推导的。**推导的那些是重点审对象**——用户没说过的结论，最容易被当成「已经定了」带进工单。

**为什么要这么定**：工单是施工顺序的产物，它记的是「当时怎么做的」；ADR 记的是「为什么这么做」。只有后者能判断「做对了没有」。

### 1.2 范围与结构

- **git 范围**：从议题自述的摸底基准（如 audit.md 里写的「摸底基准 cfb7ecc」）到 HEAD；用 `git show --stat` 确认主提交的文件面。**用户没说范围就自己定，并在清单里写清理由**——本技能把整个审计的决策交给主 Agent（切轴、分发、复核都是它定的），范围是这套决策的一部分，开发者没说就是留给你补的。这与文档审计相反：那边必须等开发者给基点。
- **代码落点**：哪个模块目录、哪些包被大量改动。
- **复现环境**：有无现成测试机、账号、构建方式。

### 1.3 查既往审计记录

**已经审过的点不要再审。** 查议题目录有没有 `audit.md`、`findings-*.md`、历史报告；有的话在清单里列出来，写明「已审过什么、结论是什么、改过了没有」。

**重复审已改过的问题没有意义**——这一轮要审的是**改完之后剩下什么**。

### 1.4 交接清单要写什么

摸底产出是一份文件（落议题目录下的 `audit-run-<日期>/`，与审计产物同处，见 1.5），六节：

1. **被审对象**——哪些文件、哪些代码，以及「只看不碰」的边界。
2. **关键前提**——这次处在哪个阶段、审的是什么（见第零节）。
3. **锚**——ADR 核心主张，编号，标授权来源。
4. **必须知道的背景**——被证伪的方向（含原因）、踩过的坑（只给方法）、已审过的轮次（见 〇·一、1.3）。
5. **建议的审计轴**——按阶段定制，不是套模板。
6. **环境与授权**——测试环境、账号、只读声明。

**第 2、4 节是本技能最容易被省掉、又最该写的两节。** 没有第 2 节，执行者会套错模板；没有第 4 节，执行者会重复走死路。

### 1.5 审计产物落哪

**落议题目录下，不落 `build/`**——`build/` 按天清理，而审计记录要长期留存。

```
docs/issues/<议题>/audit-run-<日期>/
  ├─ dispatch.md          ← 分发审的覆盖缺口清单
  ├─ raw/                 ← 各轴原始回执，子 Agent 自己写
  │   ├─ 01-architecture.md
  │   ├─ 02-docs.md
  │   └─ ...
  └─ report.md            ← 主 Agent 的结构合并
```

**三条铁律**（细节见 `ARCHIVE.md`）：

1. **子 Agent 直接写自己的回执文件**——返回文本可以简略，完整证据在文件里。
2. **`raw/` 与 `dispatch.md` 只读**，任何人不得修改。
3. **`report.md` 写完即锁死**，错了也不改，另立一轮再调查。

**同一议题可以有多轮审计**，各自独立成目录，互不覆盖。

## 二、切轴与分发

按**代码结构**切，不按工单顺序切。每轴一个子 Agent，文件域白名单隔离。

### 2.1 交给现成技能的两轴

| 轴 | 怎么派 |
| --- | --- |
| **文档** | 直接按 `/audit-docs` 的做法派：一致性 + 规范符合度 + 事实准确性三路。**额外加一条**：ADR 里「不再约束」「已被取代」的句子，对应实现是否真的撤干净了。**只取本体（轴与判据），不读其附件** |
| **代码规范** | 直接按 `/code-review` 的做法派：规范符合度 + 规格符合度两路 |

### 2.2 本技能独有的轴（示例，按重构实际调整）

| 轴 | 审什么 |
| --- | --- |
| **架构** | 唯一定义落点是否最优、依赖方向、层级边界、窄接口、调用链 |
| **跨模块不变量** | 同一概念在多处的定义是否真的一致；不变量被谁破过 |
| **判定/决策层** | 旧概念撤净否、优先级次序、覆盖缺口（**多出 = 永远认领不到；遗漏 = 永远归不了类，后者最重**） |
| **配置与映射** | 配置条目与实际产出是否一一对应、顺序、退役条目撤净否 |
| **呈现层** | 回落口径、统计口径、自有文本的边界 |
| **真机复现** | 构建 / vet / 全量测试 + 按场景分账号复现。先梳理复现方案再执行，跑不通如实记，**不许编造结果** |

**隔离手段**：每个提示词写明文件域白名单（明确「不碰 X，那归另一轴」）。跨轴疑点**不在子 Agent 间互传**，一律回主 Agent 核实（核出的结论标 `[主查]`，或转交开发者定）。

## 三、分发审：发出去之前先审一遍提示词

**主 Agent 写完提示词包后，先别发。** 派一个**分发审**，只审这包提示词本身。

**为什么要这一步**：主 Agent 写提示词时，最容易犯的错是**自己意识不到的**——在提示词里夹带了自己的预设判断；几轴都说「不碰 X」结果 X 没人审；两轴审同一块各得相反结论。**这些问题只有跳出提示词本身才能看见。**

### 3.1 给它什么、不给什么

| 给 | 不给 |
| --- | --- |
| **审计目标**（一句话，如「这份 ADR 能不能派生工单」） | 主 Agent 的**推理过程与预设结论** |
| **提示词包全文**（各轴任务、文件域、报告格式） | 被证伪的历史与踩坑背景（那是复核员用的） |
| **被审对象的结构与规模**——只看目录、文件数、行数 | 具体的技术论证内容 |

**一句话**：分发审读的是**地图**，不读**内容**。它要能回答「这地盘多大、该切几块、现在切全了吗」，不需要知道「这块地上种了什么」。

**为什么不给推理过程**：给了它就会被主 Agent 的思路带跑，只查「主 Agent 想到的地方」——而它存在的意义恰恰是查**主 Agent 没想到的**。

### 3.2 审什么：四类必查，不许自由发挥

提示词里固定写死这四条，逐条给结论：

| # | 查什么 | 判据 |
| --- | --- | --- |
| 1 | **轴间缝隙** | 几轴文件域并起来，覆盖被审对象的全部了吗？有没有哪块说好了「谁都不碰」 |
| 2 | **轴间重叠** | 有没有两轴审同一块？重叠会导致结论相反、还得多一轮来回核实 |
| 3 | **预设污染** | 提示词里有没有夹带主 Agent 的判断（「注意 X 可能有问题」这类——这已经是在替子 Agent 下结论） |
| 4 | **边界与产出** | 每轴的文件域、报告格式、硬伤/判断题的标注要求，写清了吗？没有的话子 Agent 会照自己的理解跑 |

**产出**：只给**覆盖缺口清单**，每条说清「缺什么、建议补哪个轴或补哪条约束」。**不自己下场查代码。**

### 3.3 产出之后

主 Agent 拿到清单，**改完再发**。补轴也好、改提示词也好，改完不必再过一次分发审——**一轮就够，别循环**。

**这轮等待是设计内的。** 重型审计本来就长，分发前多这一步能省掉后面几轮的返工与来回核实。**不要为了省时间跳过。**

## 四、复核员：独立自建框架

> 与「分发审」的区别：分发审在**发出去之前**审**提示词**；复核员在**发出去之后**审**内容**。两者都独立，但靶子不同。

**主 Agent 派出的轴，切法来自摸底时的视角，必然有盲区。** 所以要额外派一个**复核员**，它不接任何现成轴，任务是：

1. 读锚（ADR 决定）、读改动面、读议题文档；
2. **自己设计一套本轮的审计框架**——本阶段特有的风险在哪、上面那些轴漏了什么；
3. 按自己设计的框架执行，或再派子 Agent 执行；
4. 报告里必须写明**它设计的框架是什么、为什么这么切、以及上面哪些轴它认为有盲区**。

**给它的授权放宽**：它只读，但可以自由选择读什么、按什么顺序读。**它的价值在「不同的切法」**，不在于审得更细。

**注意**：它不需要「对话忠诚度」——决策已经固化在 ADR 与工单里，追「当时用户怎么说的」由 `/audit-conversation` 负责，性质不同，别混进来。

## 五、每份子 Agent 提示词的固定件

1. **大方向锚**：ADR「决定」的浓缩条目（编号），配那句「以此为准」的固定话。
2. **授权声明**：「只做只读分析，本轮未授权开工，不得修改任何文件」。跑构建/测试的轴另写：临时产物只落 `build/`。
3. **文件域白名单** + 要对照的议题文档章节。
4. **报告格式**：每条发现给 文件:行号 + 证据（命令/原文），区分【硬伤】（事实错误、边界被破坏）与【判断题】（可权衡，说明理由与代价）；**没发现问题就明说「未发现问题」，不许凑数**；400 字内。
5. **只给指针技能的 `SKILL.md` 本体**：派 `/audit-docs`、`/code-review` 时写明「只读 SKILL.md，附件不读」，收口自留。

## 六、真机复现的分工

- 允许直接复现时**按场景分账号**，避免多 agent 同账号互相打架；明确禁危险操作。
- 复现环境信息从议题文档抄，账号密码原样下发。
- **复现行为异常回主 Agent**，路由回对应实现轴定位——不要在复现轴里直接下结论。

## 七、落档

收尾规程在 **[ARCHIVE.md](./ARCHIVE.md)**：结构合并、三条禁令、归属标记、写完自查七条、不可篡改与再调查。**每次跑完都要读它**——本技能的收口只有它规定的 `report.md`。

**本技能不做三段式。** 那是 `/audit-docs`、`/audit-conversation` 独立跑时给开发者的口径，装在各家的 `REPORT.md` 里；派它们时不读。

## 八、两个独立角色的对照

| | **分发审** | **复核员** |
| --- | --- | --- |
| 时机 | 提示词写好、**发出去之前** | 各轴**跑的同时** |
| 靶子 | **审计设计**（提示词包） | **审计内容**（代码与文档） |
| 读什么 | 只读地图：结构、规模、提示词全文 | 深入读：锚、改动面、议题文档 |
| 不读什么 | 技术论证、主 Agent 的推理 | —（不受限） |
| 产出 | 覆盖缺口清单（四类必查） | 它自建的框架 + 按该框架的发现 |
| 能不能自己查代码 | **不能**，只审设计 | 能，授权放宽 |
| 负责什么 | **查「有没有漏」** | **查「框架对不对」** |

**两个都要派。** 少一个就会缺一块：只派复核员，没人查主 Agent 的分发是否周全；只派分发审，没人跳出框架看整体。

## 边界

- **只审计，不改被审对象。** 修复、补用例、改文档都等开发者授权，另开工作。
- **审计记录不可篡改。** `raw/`、`dispatch.md`、`report.md` 全部只读——发现错了在**新文件**里引用并写明分歧，不回头改。即使证明它错了，也不改：它代表那个时刻看到了什么。
- **汇总只合并结构，不写见解。** 不排优先级、不判谁对、不合并相似条目（详见 `ARCHIVE.md` 的 7.3）。
- **审计思路不得被工单塑造。** 轴的切法来自代码结构与 ADR 层级，不来自施工顺序。
