# 文档审计

对 `HEAD` 与一个固定基点之间的**文档改动**做多轴审计，各轴**并行**跑子 agent，最后分轴报告、不合并不重排。

**为什么分轴且不合并**：一份文档可以「格式全对、口径全错」，也可以「口径对、到处是互相矛盾的旧说法」。合成一个结论，两轴会互相掩盖。

**与 `/code-review` 的区别**：那个技能的两轴是给代码设计的（编码规范 + Fowler 坏味道）。文档的「标准」不在 `CODING_STANDARDS.md` 里，在**本仓库的文档规范与既有同类文件**里；而文档最要命的问题是**同一件事在多份文件里说法不一致**，这在代码那边不存在。

## 一、钉住基点

用户说的就是基点（提交号、分支、标签、`HEAD~5`）。没说就问，**不要自己猜一个**。

拿到后先确认它解析得开、diff 非空：

```bash
git rev-parse <基点>
git diff --name-only <基点>...HEAD -- '*.md'
git log <基点>..HEAD --oneline
```

**只留 `.md`**（以及 `GLOSSARY.md` 这类无扩展名或自定义扩展的文档）。若结果里混着代码，把代码剔除并告知用户——这份技能**不审代码**，那是 `/code-review` 的事。

**这个仓库的文档约定**（技能通用，但下面这条是硬事实，换仓库要改）：

- ADR：`docs/adr/NNNN-slug.md`
- 规格与工单：`docs/issues/<slug>/spec.md`、`docs/issues/<slug>/issues/NN-*.md`
- 领域词表：仓库根 `GLOSSARY.md`
- 格式模板与字段口径：`docs/agents/doc-formats.md`、`docs/agents/issue-tracker.md`、`docs/agents/triage-labels.md`
- 最高约束：`docs/个人开发规范.md`（「四、产出·3 文档」与「四·4 使用者可见文案」两节）

## 二、找齐每一轴的材料

| 轴 | 材料从哪来 |
| --- | --- |
| **一致性** | diff 涉及的全部文档 + 它们互相引用的文件（引用了未改的 ADR/spec 也要读） |
| **规范符合度** | 上面「文档约定」里的规范文件 + 同目录既有同类文件（照它们看实际体例） |
| **事实准确性** | 文档里引用的代码位置、行号、函数名、配置条目、计数——**逐个回源码核对** |

**事实准确性轴要回仓库查**，不是读文档猜。文档里写「`Judge` 里有一条 `if res.AbortLine != ""`」「`sftp.go` 有 8 处 `fmt.Sprintf`」，就要去 `modules/` 下真的数一遍。**这条轴不查，等于放行所有编造的数字。**

## 三、把「本轮的意图」写成清单

一致性轴与事实轴都要拿一个基准去对。基准来自：

1. 本轮改动所服务的**决策**（ADR 或对话里定下的事）；
2. 用户明确说过的判断。

把它们写成**编号清单**，逐条给子 agent。**没有清单就审不出「该说的没说」**——子 agent 只会说「写得挺通顺」。

若找不到这份意图（比如只是修错别字），**跳过清单**，一致性轴改为「内部自洽」：同一概念在改动范围内外的说法是否统一。

## 四、并行发子 agent

三个调用**写在同一条消息里**，前台执行，拿回报告后聚合。

### A. 一致性（Consistency）

```
只读审计，不改任何文件。

diff：git diff <基点>...HEAD -- '*.md'
提交：<git log 列表>

本轮意图清单（逐条核对文档是否落实）：
<编号清单>

请报告，每条都要**引用原文并给出文件:行号**：
(a) 同一件事在不同文件里说法不同（ADR 说 A、工单说 B、词表说 C）；
(b) 清单里有、文档里没有落实的；
(c) 文档里出现了清单外的说法（越权承诺、凭空新增的规则）；
(d) 引用了不存在的章节号、工单号、ADR 号。

不要评价文笔。找不到问题要明说「本轴未发现问题」，不要凑数。400 字内。
```

### B. 规范符合度（Standards）

```
只读审计，不改任何文件。

diff：git diff <基点>...HEAD -- '*.md'
提交：<git log 列表>

本仓库的文档规范：
- docs/个人开发规范.md（「四、产出·3 文档」「四·4 使用者可见文案」两节）
- docs/agents/doc-formats.md
- docs/agents/issue-tracker.md
- docs/agents/triage-labels.md

另读同目录的既有同类文件作为体例参照：<列出>

请报告：
(a) 违反上文规范条款的，**引用条款原文**；
(b) 与既有同类文件体例不一致的（字段名、标题层级、状态写法）；
(c) 使用者可见文案里的历史沿革说法（规范禁止「此前是……现已改为……」出现在使用者可见面）。

**跳过**任何格式检查工具已经能抓的（列表缩进、链接语法）。

另附一份通用的「文档坏味道」基线，逐条判断、**是判断题不是违规**，仓库规范优先于基线：
- 神秘命名：术语没定义就用了 → 补定义或换词
- 重复表述：同一段意思在两处写了 → 留一处，另一处指过去
- 投机性抽象：为将来预留的字段、参数、章节 → 删掉，等真需要再加
- 散弹式修改：一处改动要连带改七八个文件才能自洽 → 说明该收拢到一个地方
- 中间人：一节只是把别处的链接抄一遍 → 删掉

每条引用原文。400 字内。
```

### C. 事实准确性（Facts）

```
只读审计，不改任何文件。

diff：git diff <基点>...HEAD -- '*.md'

文档里凡是**断言仓库事实**的地方，逐条回源码核对：
- 具体文件、函数、行号是否存在、内容是否如描述
- 计数（「8 处」「11 处」「33 条」）是否属实 —— 用 grep/wc 实际数
- 配置条目、字段名、环境取值是否与 config/ 下的实际内容一致
- 引用的其他文档路径是否存在

请报告每一条**对不上的**，格式：
文档位置 → 文档说的 → 源码实际是什么 → 证据（命令 + 输出）

**只报对不上的**，对得上的不用列。查不到的（源码里根本没有这个文件/函数）优先报，那是最严重的一类。400 字内。
```

## 五、聚合

分三节呈现：`## 一致性`、`## 规范符合度`、`## 事实准确性`。**原文贴出或轻度清理，不合并不重排**。

结尾一行：

```
合计：一致性 N 条 / 规范 M 条 / 事实 K 条。各轴最重的一条分别是：……
```

**不要跨轴挑一个「总冠军」**——分轴的意义就是不让一轴掩盖另一轴。

## 六、审完怎么办

- **事实准确性的问题一律当场改**，那是硬错，没有商量余地。
- **一致性、规范的问题**报给开发者，由他定改不改、怎么改——文档是决策载体，措辞背后可能是他的判断。
- 改完**重跑一遍事实轴**（只改文档也可能改出新错）。

## 边界

- **只审文档**。代码走 `/code-review`。
- **不审「实施计划对不对」**——那是设计评审，不是文档审计。这里只查「文档内部是否自洽、合规范、说法属实」。
- **不评价写得好不好**。文笔、篇幅、结构美感不在范围内，除非规范里有条款。
