# 文档审计

对 `HEAD` 与一个固定基点之间的**文档改动**做多轴审计，各轴并行跑子 agent，分轴报告。

## 第零步：先定受众，再定审计方向

**这一步不做，后面的轴就是盲审。** 同一份文档，受众不同，判据完全不同：

| 受众 | 典型文档 | 审计的核心问题 |
| --- | --- | --- |
| **执行者（AI / 后来的维护者）** | ADR、议题、spec、工单 | 结论有依据吗？授权链清楚吗？换个人能照着执行吗？ |
| **工具使用者** | 手册、帮助、示例、常见问题、**程序的报错与提示** | 照它做能跑通吗？有没有内部行话？说了假话吗？说清怎么改了吗？ |

**动手前先写一句**：「本次审计对象的受众是 ___，因此判据以 ___ 为主。」**受众不明先问。**

判断依据：文件放在哪个目录、有没有「实施载体」字段、读者拿它是想看「为什么」还是照做。

### 使用者可见文本要单独看

如果改动涉及**程序的输出文本**（报错、提示、帮助、配置注释），判据与手册同一套，但形态不同：**三类输出——使用错误、程序缺陷、运行结果——各自怎么写，见仓库文档指南的「面向使用者的文本」一节。**

**审计时只查两件事**：

- 有没有把「使用错误」写成只说「哪里错」就完事，没说怎么改；
- 有没有把「程序缺陷」（panic、内部断言）包装成好听的使用者文案——那会丢掉排查现场。

## 一、钉住基点

用户说的就是基点（提交号、分支、标签、`HEAD~5`）。没说就问，**不要自己猜**。

```bash
git rev-parse <基点>
git diff --name-only <基点>...HEAD
```

**只留文档**：剔除代码文件，告诉用户剔了哪些。代码走 `/code-review`。

## 二、摸清这个仓库的文档怎么组织

```bash
ls *.md docs/*.md 2>/dev/null
grep -rl -i '文档规范\|contributing\|doc-format\|issue-tracker' --include='*.md' . | head
find . -type d \( -name adr -o -name issues -o -name specs \) -not -path './.git/*' | head
find . -maxdepth 2 -iname 'glossary*' -not -path './.git/*'
# 成文的「文档纪律」与「格式模板」分开找：前者答「不许怎么写」，后者答「长什么样」
grep -rln -i '纪律\|禁止\|MUST NOT\|坏味道' --include='*.md' docs/ | head
```

整理成表随子 agent 下发。**查不到就明说「本仓库没有成文规范」**，规范轴退化为「与同类文件体例一致」——**不要编标准**。

## 三、把「本轮意图」写成清单

一致性轴要拿基准去对。基准来自本轮改动服务的决策、或用户明确说过的判断。写成编号清单。

**没有清单就审不出「该说的没说」**——子 agent 只会说「写得挺通顺」。

只是修错别字就跳过清单，一致性轴改为「内部自洽」。

## 四、并行发三个子 agent

### A. 一致性

```
只读审计，不改任何文件。
diff：git diff <基点>...HEAD
受众：<第零步的结论>
本轮意图清单：<编号清单>

报告（每条引用原文 + 文件:行号）：
(a) 同一件事在不同文件里说法不同；
(b) 清单里有、文档里没落实的；
(c) 文档里出现了清单外的说法（越权承诺、凭空新增的规则）；
(d) 引用了不存在的章节号、工单号、路径。

不评价文笔。找不到问题就明说。400 字内。
```

### B. 规范符合度

```
只读审计，不改任何文件。
diff：git diff <基点>...HEAD
受众：<第零步的结论>
本仓库的规范与纪律：<第二步查到的路径+章节，或「无」>
体例参照：<同目录既有同类文档>

报告：
(a) 违反上列条款的，引用条款原文；
(b) 与同类文件体例不一致的；
(c) 按仓库条款检查使用者可见内容（仅当受众是使用者）：
    · 内部行话、未定义术语、泄漏实现过程
    · 出现沿革（「此前是」「现已改为」）
    · 报错只说「哪里错」、没说「怎么改」
    · 示例能不能原样照抄跑通
    · 有没有把程序缺陷包装成使用者文案（那会丢掉排查现场）

跳过 linter 能抓的（缩进、链接语法）。
另附判断题基线（命中不算违规，报给开发者定）：
- 术语没定义就用了
- 同一段意思在两处写
- 为将来预留的字段/章节
- 一处改动要连带改七八个文件才自洽
- 一节只是把别处链接抄一遍
- 手册里混进取证过程/沿革（该进 ADR 或 CHANGELOG）
400 字内。
```

### C. 事实准确性

```
只读审计，不改任何文件。
diff：git diff <基点>...HEAD

凡是断言仓库事实的地方，逐条回源码核对：
- 文件、函数、行号是否存在、内容是否如描述
- 计数是否属实（用 grep/wc 实际数）
- 配置条目、字段名、环境取值是否一致
- 引用的其他文档路径是否存在

每条对不上的给：文档位置 → 文档说的 → 源码实际 → 证据（命令+输出）。
只报对不上的。查不到的优先报。400 字内。
```

## 五、聚合

分三节：`## 一致性`、`## 规范符合度`、`## 事实准确性`。原文贴出，不合并不重排。

结尾一行：`合计：N / M / K。各轴最重的一条分别是：……`

**不要跨轴挑总冠军**——分轴就是不让一轴掩盖另一轴。

## 六、审完怎么办

- **事实错误当场改**，没有商量余地。
- **一致性与规范问题报给开发者**，由他定——措辞背后可能是他的判断。
- 改完**重跑事实轴**。

## 七、汇总给开发者：三段式

**最终回复按下面三段排，顺序固定，直接输出到终端，不另写文件。** 某段没有内容就**整段省略**，不要写「无」占位。

### 第一段：过程与待验证

这一轮实际跑过的命令、构建、本地实验，以及需要开发者自己确认的前提。每条写三样：**做了什么 → 结果 → 还差谁确认什么**。

**放在最上面**：它决定下面两段的可信度，读者要先知道哪些是验过的、哪些还没验。

### 第二段：缺陷清单

证据确凿、不需要开发者拍板的——事实错误、边界被破坏、引用了不存在的东西。逐条给 `文件:行号` + 现象 + 证据；**已经改掉的注明改在哪，没改的注明卡在哪**（未授权 / 还没复现）。

**不排优先级，不写修法**——排序是判断，修法要授权。

### 第三段：待决策

有歧义、两处说法打架、第四节 B 轴附的「判断题基线」里命中的——需要开发者在几条路里选一个。**用 `/grill-with-docs` 问。**

- **技能识别不到就直接读技能文件**：技能目录下找 `grill-with-docs`，按它指向的 `grilling`、`domain-modeling` 自己执行。**不要因为它没被加载就退化成随便问几句。**
- **先盘点，再发问**：把所有待决策项编号列全，每条只写一句话标题，不展开。这份总清单是「没漏」的唯一凭据，不许省。
- **一轮最多问 3 个**，按「卡住后续的先问」排序，每问带推荐答案与依据。
- **每轮末尾报进度**：`已问 3 / 共 12，剩 9`。**没清零不许收工**；回答里冒出新的分支就追加编号、重报总数。
- **收工判据**：清单清零，且最后一轮没有新增。问了三四个就结束，就是漏。

**为什么分批**：`grilling` 的规矩是一轮问完整个 frontier，但三段式本身已经不短，二三十个问题一起倒出来会刷屏。这里只取 frontier 里最靠前的三条；总清单只给标题，展开的只有当前这一轮那两三个。

**与第五节的关系**：第五节是三轴原样并列，本段按「谁来处置」重排。同一批发现有两种排法，**不要合并成一份**。

## 边界

- 只审文档；代码走 `/code-review`；「文档是否忠实于对话」走 `/audit-conversation`。
- 不审「实施计划对不对」——那是设计评审。
- 不评价写得好不好，除非仓库规范有条款。
- 不预设目录结构，第二步查出来为准。
