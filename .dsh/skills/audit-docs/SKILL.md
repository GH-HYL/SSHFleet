# 文档审计

对 `HEAD` 与一个固定基点之间的**文档改动**做多轴审计，各轴并行跑子 agent，分轴报告。

**三个角色按这一套用**：开发者下指令、拍板；执行者照技能干活（AI 或后来的维护者）；使用者用做出来的工具。

子 agent 一律后台跑：主 agent 不等、不轮询、不反复读回执，也不亲自审，腾出手来随时回复开发者；无活可做就提前结束本轮。

审计只针对语言描述性内容：代码本身不在范围内，代码里的输出与注释要审——判据见第零步末。

## 第零步：先定受众，再定审计方向

同一份文档，受众不同，判据完全不同：


| 受众       | 典型文档                                         | 审计的核心问题                                                             |
| ---------- | ------------------------------------------------ | -------------------------------------------------------------------------- |
| **开发者** | 决策征询、状态汇报、内部备忘                     | 够他拍板吗：取舍与代价写清了吗，还没定的前提标出来了吗？                   |
| **执行者** | ADR、议题、spec、工单                            | 结论有依据吗？授权链清楚吗？换个人能照着执行吗？                           |
| **使用者** | 手册、帮助、示例、常见问题、**程序的报错与提示** | 照它做能跑通吗？有没有内部行话？说了假话吗？要他动手的，把动作写出来了吗？ |

**动手前先写一句**：「本次审计对象的受众是 ___，因此判据以 ___ 为主。」判断不了的，留到第三节一并问。

判断依据：文件放在哪个目录、有没有「实施载体」字段、读者拿它是想看「为什么」还是照做。

**补充：程序输出与注释怎么判**

程序输出与注释这两类不算文档，判据只看它落在谁眼里。

先看程序输出的，它分两种。

一种是给使用者看的。提示信息、帮助文本、配置注释都算这类：说清是怎么回事；要他动手的，把动作写出来。没做到就是缺陷。

另一种是程序自己的，panic、内部断言、栈那种：不许包装成好听的使用者文案，那会丢掉排查现场。

剩下的代码注释是写给执行者的，按执行者那套判，不按使用者那套。

## 一、钉住基点

基点由开发者定：提交号、分支、标签、`HEAD~5`。没说就留到第三节一并问。

```bash
git rev-parse <基点>
git diff --name-only <基点>...HEAD
```

## 二、文档分类

改动的文档归四类：规范与纪律、决策记录、规格与工单、词表。体例参照取同目录下的同类文件。

手册、帮助、示例这类给使用者看的文档不入这四类，体例照同目录下同类使用文档取。

取不到就明说「本仓库没有成文规范」，规范检查退化为「与同类文件体例一致」，不要编标准。

## 三、派发前的提问

**用 `my-grill` 问开发者两类事。**

- 如果分不清审计目标是给开发者、执行者，还是使用者看的，直接问，可多选。
- 对这次审计本身还有什么疑问，例如：本次是否需要测试环境，要跑程序才能核实的，如果评估需要测试环境，就需要确定环境在哪；纯静态核对的，说明不需要。如果开发者没给、`build/` 里也翻不到，就直接问，不要自己再深找。还有其他会阻塞子 agent 排查的事，先在这一步问清，再分发。

此阶段有三类不问：被审内容对不对、某条具体该怎么改、子 agent 读文件能自己查到的细节。

问完把清单写出来：本轮改动服务的决策、或开发者明确说过的判断，写成编号清单，下发给查一致性的那一路。只改错别字的改动不列清单，按内部自洽审即可。

全部梳理好，等开发者说「授权开工」，再分发四个子 agent。

## 四、子 agent 分发分工参考

### A. 一致性

```
本轮只做只读分析，不改任何文件。
diff：git diff <基点>...HEAD
受众：<第零步的结论>
本轮意图清单：<编号清单>

报告（每条引用原文 + 文件:行号）：
(a) 同一件事在不同文件里说法不同；
(b) 清单里有、文档里没落实的；
(c) 文档里出现了清单外的说法（越权承诺、凭空新增的规则）；
(d) 引用了不存在的章节号、工单号、路径——点明即可，展开写篇幅太大。

不评价文笔。找不到问题就明说。
```

### B. 规范与文本

```
本轮只做只读分析，不改任何文件。
diff：git diff <基点>...HEAD
受众：<第零步的结论>
本仓库的规范与纪律：<规范文件，或「无」>
体例参照：<同目录既有同类文档>

报告：
(a) 废话：删掉这句话或这几个字，是否影响这份文档原有的目的与功能。
    不受损就是废话。每条给：文件:行号 + 原文 + 删掉之后文档少了什么。
    常见：同一段意思在两处写、一节只是把别处链接抄一遍、为将来预留的字段/章节、
    破折号后与括号里的解释理由、把上一句换个说法再说一遍。
(b) 违反上列条款的，引用条款原文；
(c) 与同类文件体例不一致的；
(d) 按受众检查内容。

受众是使用者：
· 内部行话、未定义术语、泄漏实现过程
· 只讲是怎么回事，要他动手的没把动作写出来
· 示例能不能原样照抄跑通
· 有没有把程序缺陷包装成使用者文案（那会丢掉排查现场）
· 有没有混进对话过程与沿革（「此前是」「现已改为」「我们讨论过」）——使用者不需要知道工具的变动历史。

受众是执行者：
· 结论有没有标来源：开发者明示，还是执行者推导
· 决策处有没有给取舍理由，还是只落了结论
· 引用能不能点回原文：章节号、工单号、ADR 编号

受众是开发者：
· 这类文档少，遇到就按受众表里开发者那一行的问题逐条看

同一份内容可能同时服务几类受众：分开审，每类受众单独过一遍。

跳过 linter 能抓的（缩进、链接语法）。
```

### C. 事实准确性

```
本轮只做只读分析，不改任何文件。
diff：git diff <基点>...HEAD

凡是断言仓库事实的地方，逐条回源码核对：
- 文件、函数、行号是否存在、内容是否如描述
- 计数是否属实（用 grep/wc 实际数）
- 配置条目、字段名、环境取值是否一致
- 引用的其他文档路径是否存在

每条对不上的给：文档位置 → 文档说的 → 源码实际 → 证据（命令+输出）。
只报对不上的。查不到的优先报。
```

### D. 补查

```
本轮只做只读分析，不改任何文件。
diff：git diff <基点>...HEAD
前三轴的分发提示词：<A/B/C 三块全文，参数已填好>

你自己决定查哪几块、查多深，补它们没覆盖到的地方。

力度上限：只挑少数几处，不重跑全量；能对上 A/B/C 已有条目的，不重复报。

报告：查了哪几块、为什么挑这几块、补出了什么。
```

## 五、成果输出

每收到一轴完整回执，就把它排成一份文件落盘，不等其他轴，也不做跨轴合并。

目录：`build/audit/<年月日时分秒>-<审计行为概述>/`

- `一致性.md`
- `规范与文本.md`
- `事实准确性.md`
- `补查.md`

回执里带着子 agent 自己的判断，原样贴出来读着乱：**允许排版**——分节、小标题、列表、代码块、表格；**不许改论述**——不删句、不改口径、不替它把话说轻或说重、不补它没说的结论。

正文用中文。`build/` 不进 git：审计产物与跑命令的临时产物都只落这里，除非开发者明说要留，不必归档。

**只报不改。** 不改被审文档，也不给修法、不排优先级——修复另开工作，另走授权。

四份都落盘后，按本节几条自查一遍，查完审计流程结束。

某轴回执迟迟不到，接着等就是：子 agent 还在后台跑，主 agent 结束本轮就行，回执传回会自动唤醒它，不用守着，也别替它提前收工。真卡住了，开发者会来说。

## 六、汇总给开发者

审计结束后按收尾规程办：**[REPORT.md](./REPORT.md)**，只输出开发者要关注的信息。

## 边界

- 不审「实施计划对不对」——那是设计评审。
- 不评价写得好不好。
