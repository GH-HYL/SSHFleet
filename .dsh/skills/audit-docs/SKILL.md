# 文档审计

对 `HEAD` 与一个固定基点之间的**文档改动**做多轴审计，各轴并行跑子 agent（所有子 agent 后台运行，不得阻塞主 agent 自行分析和回复开发者问题；主 Agent 不等、不亲自审，不轮询、不反复读回执，派完即结束本轮），分轴报告。

## 第零步：先定受众，再定审计方向

同一份文档，受众不同，判据完全不同：


| 受众                            | 典型文档                                         | 审计的核心问题                                               |
| ------------------------------- | ------------------------------------------------ | ------------------------------------------------------------ |
| **执行者（AI / 后来的维护者）** | ADR、议题、spec、工单                            | 结论有依据吗？授权链清楚吗？换个人能照着执行吗？             |
| **工具使用者**                  | 手册、帮助、示例、常见问题、**程序的报错与提示** | 照它做能跑通吗？有没有内部行话？说了假话吗？说清怎么改了吗？ |

**动手前先写一句**：「本次审计对象的受众是 ___，因此判据以 ___ 为主。」**受众不明先问。**

判断依据：文件放在哪个目录、有没有「实施载体」字段、读者拿它是想看「为什么」还是照做。

### 使用者可见文本要单独看

如果改动涉及**程序的输出文本**（报错、提示、帮助、配置注释），判据与手册同一套，但形态不同：**三类输出——使用错误、程序缺陷、运行结果——各自怎么写，见仓库文档指南的「面向使用者的文本」一节。**

**审计时只查两件事**：

- 有没有把「使用错误」写成只说「哪里错」就完事，没说怎么改；
- 有没有把「程序缺陷」（panic、内部断言）包装成好听的使用者文案——那会丢掉排查现场。

## 一、钉住基点

基点由开发者定：提交号、分支、标签、`HEAD~5`。没说就问，不要自己猜。

```bash
git rev-parse <基点>
git diff --name-only <基点>...HEAD
```

**只留文档**：剔除代码文件，告诉用户剔了哪些。

## 二、摸清这个仓库的文档怎么组织

```bash
ls *.md docs/*.md 2>/dev/null
grep -rl -i '文档规范\|contributing\|doc-guide\|issue-tracker' --include='*.md' . | head
find . -type d \( -name adr -o -name issues -o -name specs \) -not -path './.git/*' | head
find . -maxdepth 2 -iname 'glossary*' -not -path './.git/*'
grep -rln -i '纪律\|禁止\|MUST NOT\|坏味道' --include='*.md' docs/ | head
```

整理成表随子 agent 下发。**查不到就明说「本仓库没有成文规范」**，规范轴退化为「与同类文件体例一致」，不要编标准。

## 三、把「本轮意图」写成清单

一致性轴要拿基准去对。基准来自本轮改动服务的决策、或用户明确说过的判断。写成编号清单。

只是修错别字就跳过清单，一致性轴改为「内部自洽」。

## 四、并行发三个子 agent

### A. 一致性

```
本轮只做只读分析，不改任何文件。
diff：git diff <基点>...HEAD
受众：<第零步的结论>
本轮意图清单：<编号清单>

报告（每条引用原文 + 文件:行号）：
(a) 同一件事在不同文件里说法不同；
(b) 清单里有、文档里没落实的；
(c) 文档里出现了清单外的说法（越权承诺、凭空新增的规则）；
(d) 引用了不存在的章节号、工单号、路径。

不评价文笔。找不到问题就明说。400 字内。
```

### B. 规范符合度

```
本轮只做只读分析，不改任何文件。
diff：git diff <基点>...HEAD
受众：<第零步的结论>
本仓库的规范与纪律：<第二步查到的路径+章节，或「无」>
体例参照：<同目录既有同类文档>

报告：
(a) 违反上列条款的，引用条款原文；
(b) 与同类文件体例不一致的；
(c) 按仓库条款检查使用者可见内容（仅当受众是使用者）：
    · 内部行话、未定义术语、泄漏实现过程
    · 出现沿革（「此前是」「现已改为」）
    · 报错只说「哪里错」、没说「怎么改」
    · 示例能不能原样照抄跑通
    · 有没有把程序缺陷包装成使用者文案（那会丢掉排查现场）

跳过 linter 能抓的（缩进、链接语法）。

另附判断题基线（命中不算违规，报给开发者定）。
判据只有一条：
**删掉这句话或这几个字，是否影响这份文档原有的目的与功能。**
不受损 → 废话，报出来。

常见形态：
- 术语没定义就用了
- 同一段意思在两处写
- 为将来预留的字段/章节
- 一处改动要连带改七八个文件才自洽
- 一节只是把别处链接抄一遍
- 手册里混进取证过程/沿革（该进 ADR 或 CHANGELOG）
400 字内。
```

### C. 事实准确性

```
本轮只做只读分析，不改任何文件。
diff：git diff <基点>...HEAD

凡是断言仓库事实的地方，逐条回源码核对：
- 文件、函数、行号是否存在、内容是否如描述
- 计数是否属实（用 grep/wc 实际数）
- 配置条目、字段名、环境取值是否一致
- 引用的其他文档路径是否存在

每条对不上的给：文档位置 → 文档说的 → 源码实际 → 证据（命令+输出）。
只报对不上的。查不到的优先报。400 字内。
```

## 五、聚合

分三节：`## 一致性`、`## 规范符合度`、`## 事实准确性`。原文贴出，不合并不重排。

结尾一行：`合计：N / M / K。`

**不要跨轴挑总冠军。**

## 六、审完怎么办

**只报不改。** 审计阶段不改被审文档——事实错误也一样。跑命令的临时产物只落 `build/`。

**不给修法、不排优先级。** 修复另开工作，另走授权。

## 七、汇总给开发者

跑完之后按收尾规程办：**[REPORT.md](./REPORT.md)**——三段式、六个提问条目、收工判据都在那儿。

**被 `/audit-retrofit` 派为文档轴时不读这份附件**：它只要本体的轴、判据与报告格式，收口由它的 `report.md` 统一负责；上面第五节的三轴并列报告照出。

## 边界

- 不审「实施计划对不对」——那是设计评审。
- 不评价写得好不好，除非仓库规范有条款。
