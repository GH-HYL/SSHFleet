# 文档审计

对 `HEAD` 与一个固定基点之间的**文档改动**做多轴审计，各轴并行跑子 agent，分轴报告。

所有子 agent 后台运行，不得阻塞主 agent 自行分析和回复开发者问题。

主 Agent 不等、不亲自审，不轮询、不反复读回执，主 agent 无事可做可提前结束本轮。

审计只针对语言描述性内容，代码不在范围内。

## 第零步：先定受众，再定审计方向

同一份文档，受众不同，判据完全不同：


| 受众                            | 典型文档                                         | 审计的核心问题                                               |
| ------------------------------- | ------------------------------------------------ | ------------------------------------------------------------ |
| **执行者（AI / 后来的维护者）** | ADR、议题、spec、工单                            | 结论有依据吗？授权链清楚吗？换个人能照着执行吗？             |
| **工具使用者**                  | 手册、帮助、示例、常见问题、**程序的报错与提示** | 照它做能跑通吗？有没有内部行话？说了假话吗？要他动手的，把动作写出来了吗？ |

**动手前先写一句**：「本次审计对象的受众是 ___，因此判据以 ___ 为主。」**受众不明先问。**

判断依据：文件放在哪个目录、有没有「实施载体」字段、读者拿它是想看「为什么」还是照做。

**补充：程序输出与注释怎么判**

程序输出与注释这两类不算文档，判据只看它落在谁眼里。

先看程序输出的，它分两种。

一种是给用户看的。提示信息、帮助文本、配置注释都算这类：说清是怎么回事；要他动手的，把动作写出来。没做到就是缺陷。

另一种是程序自己的，panic、内部断言、栈那种：不许包装成好听的使用者文案，那会丢掉排查现场。

剩下的代码注释不是输出，是写给执行者的，按执行者那套判，不按使用者那套。

## 一、钉住基点

基点由开发者定：提交号、分支、标签、`HEAD~5`。没说就主动问，不要自己猜。

```bash
git rev-parse <基点>
git diff --name-only <基点>...HEAD
```

## 二、文档分类

改动的文档归四类：规范与纪律、决策记录、规格与工单、词表。体例参照取同目录下的同类文件。

取不到就明说「本仓库没有成文规范」，规范检查退化为「与同类文件体例一致」，不要编标准。

## 三、派发前的提问

**主：用 `my-grill` 问开发者两件事。**

- 对象不在表里列的这些里，这份东西是给开发者、执行者，还是使用者看的？三选一；选开发者的，再问一句按什么判。
- 对这次审计本身还有什么疑问。三类不算：被审内容对不对、将来派给子 Agent 查的具体问题、审计范围。

**次：顺带问要不要测试环境。**

要跑程序才能核实的，写明环境在哪；纯静态核对的写明不需要。开发者没给、`build/` 里也翻不到，就直接问，不要自己找。

问完把清单写出来：本轮改动服务的决策、或用户明确说过的判断，写成编号清单，下发给查一致性的那一路。只改错别字就跳过，内部自洽即可。

## 四、并行发四个后台子 agent

### A. 一致性

```
本轮只做只读分析，不改任何文件。
diff：git diff <基点>...HEAD
受众：<第零步的结论>
本轮意图清单：<编号清单>

报告（每条引用原文 + 文件:行号）：
(a) 同一件事在不同文件里说法不同；
(b) 清单里有、文档里没落实的；
(c) 文档里出现了清单外的说法（越权承诺、凭空新增的规则）；
(d) 引用了不存在的章节号、工单号、路径。

不评价文笔。找不到问题就明说。
```

### B. 规范与文本

```
本轮只做只读分析，不改任何文件。
diff：git diff <基点>...HEAD
受众：<第零步的结论>
本仓库的规范与纪律：<规范文件，或「无」>
体例参照：<同目录既有同类文档>

报告：
(a) 废话：删掉这句话或这几个字，是否影响这份文档原有的目的与功能。
    不受损就是废话。每条给：文件:行号 + 原文 + 删掉之后文档少了什么。
    常见：同一段意思在两处写、一节只是把别处链接抄一遍、为将来预留的字段/章节、
    破折号后与括号里的解释理由、把上一句换个说法再说一遍。
(b) 违反上列条款的，引用条款原文；
(c) 与同类文件体例不一致的；
(d) 按受众检查内容。

受众是使用者：
· 内部行话、未定义术语、泄漏实现过程
· 只讲是怎么回事，要他动手的没把动作写出来
· 示例能不能原样照抄跑通
· 有没有把程序缺陷包装成使用者文案（那会丢掉排查现场）

受众是执行者：
· 结论有没有标来源：用户明示，还是执行者推导
· 决策处有没有给取舍理由，还是只落了结论
· 引用能不能点回原文：章节号、工单号、ADR 编号

两种受众都查：有没有混进对话过程与沿革（「此前是」「现已改为」「我们讨论过」）
——该进 CHANGELOG 或 ADR，不该在正文。

跳过 linter 能抓的（缩进、链接语法）。
```

### C. 事实准确性

```
本轮只做只读分析，不改任何文件。
diff：git diff <基点>...HEAD

凡是断言仓库事实的地方，逐条回源码核对：
- 文件、函数、行号是否存在、内容是否如描述
- 计数是否属实（用 grep/wc 实际数）
- 配置条目、字段名、环境取值是否一致
- 引用的其他文档路径是否存在

每条对不上的给：文档位置 → 文档说的 → 源码实际 → 证据（命令+输出）。
只报对不上的。查不到的优先报。
```

### D. 补查

```
本轮只做只读分析，不改任何文件。
diff：git diff <基点>...HEAD
前三轴的分发提示词：<A/B/C 三块全文，参数已填好>

你自己决定查哪几块、查多深，补它们没覆盖到的地方。

力度上限：只挑少数几处，不重跑全量；能对上 A/B/C 已有条目的，不重复报。

报告：查了哪几块、为什么挑这几块、补出了什么。
```

## 五、成果展示

四个子 Agent 全部完成才聚合；回执内容多的，等它整份输出完再收。

收上来原样列，只做汇总，不改一个字、不带判断。

分四节：`## 一致性`、`## 规范与文本`、`## 事实准确性`、`## 补查`。原文贴出，不合并不重排，也不判哪条更要紧。

结尾一行：`合计：N / M / K / L。`

**只报不改。** 不改被审文档，也不给修法、不排优先级——修复另开工作，另走授权。跑命令的临时产物只落 `build/`。

## 六、汇总给开发者

跑完之后按收尾规程办：**[REPORT.md](./REPORT.md)**——三段式、六个提问条目、收工判据都在那儿。

## 边界

- 不审「实施计划对不对」——那是设计评审。
- 不评价写得好不好。
