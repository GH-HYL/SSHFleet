# 对话忠实度审计

审一份**总结性文档**是否忠实于**本轮对话真正得出的结论**。

**只审一件事**：文档写的，是不是对话最后真正收敛的那个。**不审代码、不跑实验、不核实技术事实。**

**由一个 agent 全程完成，不拆并行。** 工作内容单一（读对话、对文档），拆分只会让各路了半边对话、谁也判不出「结论变轨点」。

**整个审计作为后台任务（subagent）跑，主 Agent（orchestrator）不亲自审。** 派出去之后，主 Agent 可以继续做别的信息收集，**真没活干了自然结束本轮**——**不要 `sleep`、不要循环轮询、不要反复查任务状态或输出文件**；跑完会把报告送回来，那就是下一轮。**内部仍是单 agent**，后台不等于拆轴。

## 取数：先认环境，再读附件

本文只写**行为与判据**。会话记录长什么样、怎么翻、哪些行算用户原话，**按当前环境取对应附件**：

| 当前环境 | 怎么认 | 读哪份 |
| --- | --- | --- |
| **DSH** | 会话根 `~/.dsh/sessions`，目录里是 `session.v4.jsonl.zstd`（多帧 zstd） | [SESSIONS-DSH.md](./SESSIONS-DSH.md) |
| **WorkBuddy** | 会话根 `~/.workbuddy/projects`，明文 `.jsonl` | [SESSIONS-WORKBUDDY.md](./SESSIONS-WORKBUDDY.md) |

**两份附件不可混用**：路径规则、字段名、用户原话判据都不一样，照另一份取数会取错。认不出当前环境就先问，不要挑一份看着像的。

附件读完回到本文——下面是两套环境共用的判据与产出。

## 为什么只审对话

长对话的总结文档最容易出的错，不是「事实查错了」，而是**注意力涣散后的思维惯性**：会话经过多轮推翻，最终结论可能第 20 轮才收敛；到第 30 轮写文档时，模型写出**中间某个已废的版本**，或把**自己推的结论**写成「用户确认的」。这类错误**在文档内部读起来完全自洽**——它只会与对话不符。

## 第零步：先定受众，再定审计方向

**同一份文档，受众不同，「忠实」的含义不同：**

| 受众 | 典型文档 | 忠实于什么 | 常见的失真形态 |
| --- | --- | --- | --- |
| **执行者（AI / 后来的维护者）** | ADR、议题、spec、工单 | 用户定的**约束与取舍** | 把助手推导写成用户决定；用户明令的禁令漏掉 |
| **工具使用者** | 手册、帮助、常见问题 | 用户描述的**真实使用场景** | 把手里的推理过程、取证细节写进去，使用者看不懂也不必懂 |
| **使用者可见的文本** | 报错、提示、帮助文本 | 用户**当时**要表达的意图 | 写成只有维护者能看懂的机器话；丢掉了「怎么改」 |

**动手前写一句**：「本次审计对象的受众是 ___，因此重点核对 ___。」**受众不明先问。**

受众还决定**「哪些内容不该出现」**：使用者文档里出现「实验形态」「源码推断」这类内容，**本身就是一条审计发现**——不是内容对不对的问题，是它不该在这里。

## 一、审计四问

### Q1 结论是最后收敛的那个吗

先找**变轨点**：顺助手发出的消息搜「撤回」「纠正」「推翻」「改为」，标出轮次；再看文档落在哪一段。长对话会反复推翻，**取最后一次**。

### Q2 每条结论都有用户的明确同意吗

把「决定」类章节逐条拆开标：

| 标记 | 含义 |
| --- | --- |
| ✅ 用户明示 | 原话直接说了 |
| ⚠️ 概括授权 | 「你看着办」「以你判断为准」——可接受，但要标出来 |
| ❌ 助手推导 | 用户从未表态。**必须标出**，不能写成「用户决定」 |

**用户说了一句「你综合判断」，不等于他同意了后来推出的每一条。**

### Q3 有没有把推测写成事实

搜这些句式，逐条 grep 回原话：「他确认」「他提到」「用户明确表示」「实测证明」「已验证」，以及任何暗示是用户原话的引号表述。

**搜不到，就是推测写成了事实。** 最隐蔽的一类：用户描述了**现象**，文档写成了**范围界定**（「只在 X 场景」）。

### Q4 用户说过的话漏了没有

反向查。挑原话里**带约束性**的句子（「别」「不要」「必须」「宁可」），看文档有没有反映。最易漏三类：

- **优先级表态**（「二选一我选 A」）——尤其是与结论方向相反的那半句
- **禁令**（「别干这种活」「别去检测环境」）——注意有**强弱两档**，文档常常只留了弱的那档
- **代价立场**（「代价无所谓」）——文档若用「工作量大」「维护麻烦」否掉候选，就与它相悖

**若文档是面向使用者的（手册、报错、提示），多问一层**：用户描述的是**他遇到什么、想做什么**，文档里有没有变成**机器视角的说明**？真实形态：用户说「执行 `ls` 时中文文件名显示成方块」，报错或文档写成「UTF-8 字节被按 936 码页解释」——**后者是对的，但不是给使用者看的**。判据：把这句话给使用者，他知不知道下一步做什么。

## 二、症状表

| 症状 | 表现 |
| --- | --- |
| 授权漂移 | 写「决策人：用户」，但那条是助手推的。拆成两栏后常常数量对不上 |
| 幽灵确认 | 写「用户确认 X」，对话里搜不到 |
| 选择性引用 | 对结论有利的那句引了，相反的那句没引 |
| 结论停在旧版本 | 写了第 15 轮的结论，第 26 轮已重写 |
| 立场倒置 | 用户说代价无所谓，文档用成本否掉候选 |
| 约束失忆 | 明令的禁令，文档一个字没提 |
| 复审节错载体 | 塞了触发条件 / 补测计划 / 待办清单——那是工单形态 |
| 系统噪音当原话 | 把子 agent 回报、后台任务通知之类当成用户表态 |

## 三、产出

写报告，**不改文档**。

```markdown
# <文档> 对话忠实度审计
受众：<第零步的结论>
## 一句话总评
忠实 / 基本忠实但有偏差 / 有严重偏差
## 逐条核对
| 文档结论 | 依据（U几 / 原话片段） | 判定 |
## 必须修正
## 建议修正
## 无法核实
```

判定只用四个符号：`✅` 有依据 / `⚠️` 无明确授权 / `❌` 与对话矛盾 / `➕` 对话有但文档漏。

**每条必须修正写成两段**：错在哪 → 依据是哪句。**不给改法**——改法等于替开发者下结论，等授权后另开工作。

**区分改结论与改口径**：结论与对话矛盾才动结论；结论对、授权写错，只改变述方式（拆决策人栏，不推翻决策）。

**区分必须与建议**：必须 = 与用户原话直接矛盾、推测当事实、引用错误；其余进建议。**找不出问题就明说**，加一条假问题整份报告就废了。

## 四、如果仓库里有成文的文档纪律

形体层面的问题（复审节写了待办、决策没标授权），**先查仓库有没有把这类要求写下来**：

- 常见落点：`docs/agents/doc-guide.md`——它对 ADR、spec、工单、手册、使用者可见文本**各有一节纪律**。按审计对象的那一份去对。
- **有就引用它的原文**，比自己拟判据站得住，也不与既有约定打架；**没有就明说**，按「与同类文件体例一致」处理。
- 这是**判定依据**，不是审计对象。文档之间的自洽走 `/audit-docs`。

## 五、汇总给开发者：三段式

**最终回复按下面三段排，顺序固定，直接输出到终端；三段式本身不另存文件。** 某段没有内容就**整段省略**，不要写「无」占位。

第三节那张报告表照旧，本段是在它之上收口一次，**不另存汇总文件**。

### 第一段：过程与待验证

本技能不跑实验，这段通常省略。有下面两样时才写，每条写清：**是什么 → 结果 → 还差谁确认什么**：

- **无法核实**的条目——对话里找不到依据、需要开发者回忆或补一句的；
- **会话记录截到哪条**——当前步还没落盘时，写明截止的 `U几`。

### 第二段：缺陷清单

第三节的「必须修正」按这里重排：**与用户原话直接矛盾的、拿推测当事实的、引用错的**，都归第二段。逐条给文档位置 + 现象 + 依据（`U几` / 原话片段）。

**只列不改**——审计阶段不改被审文档；**不排优先级，不写修法**，修法等授权。

### 第三段：待决策

「建议修正」里的可权衡项（`⚠️` 无明确授权、`➕` 对话有但文档漏）归第三段：结论对不对、要不要动，开发者定。**用 `/grill-with-docs` 问。**

**审计到此已经结束**，可以按 `grill-with-docs` 的策略落 ADR 或词表条目；**只写它该写的，不碰被审文档**。

- **技能识别不到就直接读技能文件**：技能目录下找 `grill-with-docs`，按它指向的 `grilling`、`domain-modeling` 自己执行。**不要因为它没被加载就退化成随便问几句。**
- **先盘点，再发问**：把所有待决策项编号列全，每条只写一句话标题，不展开。这份总清单是「没漏」的唯一凭据，不许省。
- **一轮 3 个，最多 5 个**，按「卡住后续的先问」排序，每问带推荐答案与依据；推荐答案**只给取舍依据与代价，不写具体改法**。**超过 5 个就是刷屏**，剩下的排下一轮。
- **每轮发问前先对一遍总清单**（不落文档，脑子里过；**一轮问满 5 个之后这次必做**）：哪些问过、哪些没问、回答里新冒出哪些。发现漏了就补进编号并**重报总数**。清单只许变长，不许因为问过几轮就默认「差不多了」。
- **每轮末尾报进度**：`已问 3 / 共 12，剩 9`。**没清零不许收工**；总数变了按新数报。
- **收工判据**：清单清零，且最后一轮没有新增。问了三四个就结束，就是漏。

**为什么分批**：`grilling` 的规矩是一轮问完整个 frontier，但三段式本身已经不短，二三十个问题一起倒出来会刷屏。这里只取 frontier 里最靠前的三到五条；总清单只给标题，展开的只有当前这一轮那三到五条。

**`✅` 有依据的不进任何一段**——三段式只放「要处置的」，不是把第三节重抄一遍。

## 边界

- 不审代码、不跑实验、不核实技术事实。
- 审计阶段不改被审文档；会话导出落 `build/review/`，不进被审目录。
- **只审主会话**。子 agent 的会话算助手推导的一部分，不作为依据，也不单独审。
- 会话进行中时，当前步未必落盘；以已落盘为准，并在报告注明截止到哪条用户消息。
- **不跨环境取数**。DSH 的会话在 `~/.dsh/sessions`（zstd 多帧），WorkBuddy 的在 `~/.workbuddy/projects`（明文 jsonl），各读各的附件，别混读。
