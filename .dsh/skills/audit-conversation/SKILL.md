# 对话忠实度审计

审一份**总结性文档**是否忠实于**本轮对话真正得出的结论**——只审这一件事，**不审代码、不跑实验、不核实技术事实**。

**三个角色按这一套用**：开发者下指令、拍板；执行者照技能干活（AI 或后来的维护者）；使用者用做出来的工具。

要抓的错只有一种：文档内部读起来完全自洽，只与对话不符——第 20 轮改过的结论，第 30 轮写文档时写成中间某个已废的版本，或把执行者推的写成开发者确认的。所以每条判断都得回对话里找依据。

**定位用对话的锚**：`U12`（第几条用户原话）、轮次、原话片段。

**大流程四段：梳理 → 分发 → 收集 → 收尾。** 小流程随场景变，这四段不变。

## 判据

### Q1 结论是最后收敛的那个吗

先找**变轨点**：顺执行者发出的消息搜「撤回」「纠正」「推翻」「改为」，标出轮次；再看文档落在哪一段。长对话会反复推翻，**取最后一次**。

### Q2 每条结论都有明确同意吗

把文档里「决定」性质的句子逐条拆开，每条标：


| 标记       | 含义                                               |
| ---------- | -------------------------------------------------- |
| 明示       | 原话直接说了                                       |
| 概括授权   | 「你看着办」「以你判断为准」——可接受，但要标出来 |
| 执行者推导 | 开发者从未表态。**必须标出**，不能写成开发者的决定 |
| 该有而没有 | 对话里说了，文档漏了                               |

**一句「你综合判断」，不等于开发者同意了后来推出的每一条。**

**授权写错不等于结论错**：结论对得上对话、只是没说清是谁定的，只标授权，不动结论。

### Q3 有没有把推测写成事实

搜这些句式，逐条回对话核：「他确认」「他提到」「明确表示」「实测证明」「已验证」，以及任何暗示是原话的引号表述。

**搜不到，就是推测写成了事实。** 最隐蔽的一类：开发者描述了**现象**，文档写成了**范围界定**（「只在 X 场景」）。

### Q4 说过的话漏了没有

反向查。挑原话里**带约束性**的句子（「别」「不要」「必须」「宁可」），看文档有没有反映。最易漏三类：

- **优先级表态**（「二选一我选 A」）——尤其是与结论方向相反的那半句
- **禁令**——注意有**强弱两档**，文档常常只留了弱的那档
- **代价立场**（「代价无所谓」）——文档若用「工作量大」「维护麻烦」否掉候选，就与它相悖

### 症状

四问查不出来、扫一眼却知道有毛病的四种，报告写成后过一遍：


| 症状       | 表现                                                         |
| ---------- | ------------------------------------------------------------ |
| 选择性引用 | 对结论有利的那句引了，相反的那句没引                         |
| 立场倒置   | 说代价无所谓，文档却用成本否掉候选                           |
| 载体错位   | 复审、备忘里塞了触发条件、补测计划、待办清单——那是工单形态 |
| 噪音当原话 | 把回报、通知、系统注入的上下文当成了开发者的表态             |

## 一、梳理

### 取数

会话记录长什么样、怎么翻、哪些行算用户原话，按环境取附件：


| 环境          | 怎么认                                                                 | 读哪份                                           |
| ------------- | ---------------------------------------------------------------------- | ------------------------------------------------ |
| **DSH**       | 会话根`~/.dsh/sessions`，目录里是 `session.v4.jsonl.zstd`（多帧 zstd） | [SESSIONS-DSH.md](./SESSIONS-DSH.md)             |
| **WorkBuddy** | 会话根`~/.workbuddy/projects`，明文 `.jsonl`                           | [SESSIONS-WORKBUDDY.md](./SESSIONS-WORKBUDDY.md) |

**两份附件不可混用**：路径规则、字段名、用户原话判据都不一样，照另一份取数会取错。

### 受众

同一份文档，受众不同，「忠实」的含义不同：


| 受众                 | 典型文档              | 忠实于什么                   | 常见失真                                               |
| -------------------- | --------------------- | ---------------------------- | ------------------------------------------------------ |
| **执行者**           | ADR、议题、spec、工单 | 定下的**约束与取舍**         | 把执行者推导写成开发者的决定；明令的禁令漏掉           |
| **工具使用者**       | 手册、帮助、常见问题  | 使用者描述的**真实使用场景** | 把手里的推理过程、取证细节写进去，使用者看不懂也不必懂 |
| **使用者可见的文本** | 报错、提示、帮助文本  | 使用者**当时**要表达的意图   | 写成只有维护者能看懂的机器话；丢掉了「怎么改」         |

动手前写一句：「本次审计对象的受众是 ___，因此重点核对 ___。」

受众是使用者时（手册、报错、提示）多问一层：使用者描述的是**遇到什么、想做什么**，文档里有没有变成**机器视角的说明**？使用者说「执行 `ls` 时中文文件名显示成方块」，文档写成「UTF-8 字节被按 936 码页解释」——后者是对的，但不是给使用者看的。判据：把这句话给使用者，使用者知不知道下一步做什么。

### 截止与派发前问

会话边跑边写，最后几步未必落盘：以已落盘为准，在报告里写明截止到哪条用户消息。受众不明、环境认不出、截止点说不清，用 `my-grill` 问开发者，别自己猜；问完等「授权开工」再分发。

## 二、分发

按侧重点分三路，每路读整段对话、只答自己那一个问题。**拆的是问，不是对话**——按时间切段，谁也判不出变轨点。

每路的提示词写死四样：只读分析、会话导出在哪、截止到哪条、受众是谁；判据指到本文件哪一节，不抄条文。子 agent 看不到本轮对话。


| 路           | 判据      | 报告要什么                                                                                    | 什么时候派       |
| ------------ | --------- | --------------------------------------------------------------------------------------------- | ---------------- |
| **A 时间轴** | Q1        | 变轨点（第几轮 → 原来定的 → 改成什么 → 依据）；最终结论清单（编号 + 一句话 + 依据）        | 先派             |
| **B 出处**   | Q2、Q3    | 逐条：文档位置 → 文档写的 → 依据（U几 / 原话）                                              | A 的回执到手后派 |
| **C 查漏**   | Q4 + 受众 | 该在而没在（约束性原话 → 文档没有 → U几）；不该在而在（混进来的过程、沿革、推断、机器视角） | 与 B 并行        |

A 的回执是后两路的坐标：哪句是最终结论、第几轮变的，都以它为准。

## 三、收集

每收到一路完整回执，就排成一份文件落盘，不等其他路，也不做跨路合并。

目录：`build/audit/<年月日时分秒>-<审计概述>/`

- `时间轴.md`
- `出处.md`
- `查漏.md`

**允许排版**——分节、小标题、列表、代码块、表格；**不许改论述**——不删句、不改口径、不替它把话说轻或说重、不补它没说的结论。**只汇总，不决策。**

`build/` 不进 git；除非开发者明说要留，不必归档。

## 四、收尾

按 **[REPORT.md](./REPORT.md)** 三段式汇报。

## 边界

- 审计阶段不改被审文档；会话导出落 `build/audit/`，不进被审目录。
- **只有开发者本人的话算依据**。派出去干活的回报、系统注入的上下文，都不算。
- **不给改法**——改法等于替开发者下结论；修法另开工作，另走授权。
- **找不出问题就明说**，加一条假问题整份报告就废了。
